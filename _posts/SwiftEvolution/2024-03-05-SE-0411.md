## 한 줄 요약

기본값 식(함수의 default argument, 저장 프로퍼티의 초기값)이 자기를 둘러싼 함수나 프로퍼티와 같은 actor isolation 을 가질 수 있게 한다. 그래서 `@MainActor` 함수의 기본 인자에 `@MainActor` 타입을 만들어 넣을 수 있게 되고, 반대로 nonisolated init(어느 actor 에도 묶이지 않아서 어디서든 부를 수 있는 init)이 `@MainActor` 초기값을 몰래 부르던 구멍은 막힌다.

---

## 어떤 문제였나

Swift 에서 "기본값" 을 적을 수 있는 자리는 두 군데다. 함수 인자에 적는 기본 인자와, 타입의 저장 프로퍼티에 적는 초기값이다. 둘 다 `= 식` 모양이라 같은 규칙을 따를 것 같지만, actor isolation 규칙은 서로 달랐다. 한쪽은 너무 느슨해서 data race(여러 곳에서 같은 값을 동시에 건드려서 결과가 실행 순서에 따라 달라지는 문제)를 허용했고, 다른 쪽은 너무 빡빡해서 안전한 코드까지 막았다. 제안서의 Introduction 이 이 둘과, 둘이 서로 어긋난다는 점까지 세 가지를 문제로 든다. 하나씩 실제로 돌려 보면서 확인한다.

---

### 기본값 식이란?

기본값 식은 "값을 안 주면 이걸 쓴다" 는 뜻으로 적어 둔 식이다. `func f(x: Int = 3)` 의 `3`, `var count = 0` 의 `0` 이 그 예다. 숫자 리터럴만 되는 것이 아니라 함수 호출도 적을 수 있다. `var model = Model()` 이나 `func f(c: C = C())` 처럼 init 을 부르는 식도 기본값 식이다.

두 자리는 식이 계산되는 시점이 다르다.

- 기본 인자는 부르는 쪽(caller)에서 계산된다. `f()` 라고 쓰면 컴파일러가 그 자리에 기본값 식을 끼워 넣는다고 생각하면 된다. 함수 안으로 들어가서 "값이 안 왔네, 기본값을 쓰자" 하는 것이 아니라, 함수를 부르기 전에 이미 부르는 쪽이 값을 채워서 넘긴다. 그래서 식이 어느 isolation 에서 계산되는지는 함수가 아니라 부르는 쪽의 위치에 달려 있다.
- 저장 프로퍼티 초기값은 init 의 맨 앞에 끼워진다. init 본문이 시작되기 전에 컴파일러가 `self.count = 0` 같은 대입을 먼저 넣어 준다고 보면 된다.

---

### actor isolation 이 무엇을 지키나

`@MainActor` 가 붙은 함수는 main actor 위에서만 동기적으로 부를 수 있다. main actor 밖에서 부르려면 `await` 로 건너가야 한다. 이 규칙이 UI 처럼 main thread 에서만 만져야 하는 상태를 컴파일러가 지켜 주는 방법이다. 비유하면 은행의 "main 창구" 다. 그 창구 업무는 창구 안에 있는 직원만 처리할 수 있고, 밖에 있는 사람은 번호표를 뽑고(`await`) 기다렸다가 창구로 들어가야 한다.

이 개념은 앞 글들에서 다뤘다. 점진적으로 동시성 검사를 켜는 방법은 [[SE-0337] 글](https://haroldfromk.github.io/posts/SE-0337/)에, 전역 변수를 같은 방식으로 지키는 규칙은 [[SE-0412] 글](https://haroldfromk.github.io/posts/SE-0412/)에 있다. 이 글에서는 "isolation 이 맞아야 동기 호출이 된다" 는 것만 기억하면 된다.

### 느슨했던 쪽: 저장 프로퍼티 초기값

제안서 Motivation 의 첫 예는 저장 프로퍼티 쪽이다. 서로 다른 두 actor 에 묶인 프로퍼티를 가진 class 인데, 초기값이 각 actor 의 함수를 부른다. 이 코드를 Swift 5 모드로 빌드해서 실행해 봤다. Swift 5 모드와 Swift 6 모드는 앞의 제안서 정보에서 말한 언어 모드이고, 이 글은 같은 코드를 두 모드로 돌려서 어디가 달라지는지를 따라간다. `main.swift` 다.

```swift
import Foundation

@globalActor actor AnotherActor { static let shared = AnotherActor() }

@MainActor func requiresMainActor() -> Int {
    print("requiresMainActor on main thread:", Thread.isMainThread)
    return 1
}
@AnotherActor func requiresAnotherActor() -> Int {
    print("requiresAnotherActor called")
    return 2
}

class C {
    @MainActor var x1 = requiresMainActor()
    @AnotherActor var x2 = requiresAnotherActor()

    nonisolated init() {
        print("nonisolated init body")
    }
}

let t = Task.detached { _ = C(); print("done") }
_ = await t.value
```

#### Thread.isMainThread와 Task.detached로 main thread 밖에서 init 부르기

- [`@globalActor`](https://developer.apple.com/documentation/swift/globalactor){:target="_blank"} 는 `actor` 를 global actor 로 만드는 attribute 다. global actor 는 프로그램 전체에 하나뿐인 actor 를 이름으로 가리키는 장치이고, 이 이름을 선언에 붙이면 그 선언이 그 actor 에 묶인다. 이름이 되려면 `GlobalActor` 프로토콜을 만족해야 하는데, 요구 사항은 `static let shared` 하나다. 어느 인스턴스가 이 이름의 실제 actor 인지를 알려 주는 자리다. 여기서는 `AnotherActor` 라는 main actor 가 아닌 global actor 를 하나 만들려고 썼다.
- [`@MainActor`](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 는 main thread 에 대응하는 global actor 다. 이 글에서는 `requiresMainActor()` 가 main actor 위에서 돌아야 한다는 표시로 쓴다.
- [`Thread.isMainThread`](https://developer.apple.com/documentation/foundation/thread/ismainthread-swift.type.property){:target="_blank"} 는 지금 코드가 main thread 에서 실행 중이면 `true` 를 돌려주는 `Bool` 프로퍼티다. `@MainActor` 라고 적힌 함수가 정말 main thread 에서 돌았는지 눈으로 확인하려고 찍었다.
- [`Task.detached(name:priority:operation:)`](https://developer.apple.com/documentation/swift/task/detached%28name:priority:operation:%29-795w1){:target="_blank"} 는 지금 있는 actor 나 task 와 무관한 새 task 를 만들어 `operation` closure 를 실행한다. 호출한 쪽의 isolation 을 물려받지 않아서, 이 예에서는 main actor 밖에서 `C()` 를 부르는 상황을 만드는 데 썼다. 돌려받은 `t` 의 `value` 를 `await` 하면 task 가 끝나기를 기다린다.

실행 결과다. `xcrun swiftc -swift-version 5 main.swift` 로 빌드했고 진단은 하나도 없었다.

```text
requiresMainActor on main thread: false
requiresAnotherActor called
nonisolated init body
done
```

`@MainActor` 라고 적힌 `requiresMainActor()` 가 main thread 가 아닌 곳에서 동기적으로 실행됐다(`false`). 컴파일러는 아무 말도 하지 않았다. `C.init()` 은 `nonisolated` 라서 어느 스레드에서든 부를 수 있는데, 그 init 앞에 끼워 넣어진 초기값 식이 `@MainActor` 함수와 `@AnotherActor` 함수를 동기 호출한 것이다. 창구 비유로 하면 창구 밖 사람이 창구 직원 몰래 창구 안 서류를 만진 것이다.

이 호출들은 각각의 actor 안에서 돌고 있을 다른 코드와 동시에 실행될 수 있다. 제안서가 "may run concurrently with other code on their respective global actors" 라고 적은 부분이 이것이다. 규칙으로는 막혀 있어야 하는 data race 가 init 의 초기값을 통해 열려 있었다.

같은 파일을 Swift 6 모드로 빌드하면 이제는 빌드 자체가 안 된다. `xcrun swiftc -swift-version 6 main.swift` 의 출력이다.

```text
main.swift:20:5: error: return from initializer without initializing all stored properties
13 | 
14 | class C {
15 |     @MainActor var x1 = requiresMainActor()
   |                    `- note: main actor-isolated default value of 'self.x1' cannot be used in a nonisolated initializer
16 |     @AnotherActor var x2 = requiresAnotherActor()
   |                       `- note: global actor 'AnotherActor'-isolated default value of 'self.x2' cannot be used in a nonisolated initializer
17 | 
18 |     nonisolated init() {
19 |         print("nonisolated init body")
20 |     }
   |     `- error: return from initializer without initializing all stored properties
21 | }
22 | 
```

이 error 가 왜 이런 문구로 나오는지는 뒤의 "저장 프로퍼티 초기값과 init 의 isolation" 에서 설명한다.

### 빡빡했던 쪽: 기본 인자

반대쪽은 기본 인자다. 제안서의 두 번째 예를 파일로 만들었다. `Model` 은 `@MainActor` class 이고, `f` 는 그 `Model` 을 기본값으로 만들어 쓰는 `@MainActor` 함수다.

```swift
@MainActor class Model {}

@MainActor func f(model: Model = Model()) {}

@MainActor func useFromMainActor() {
    f()
}

func nonisolatedCaller() async {
    await f()
}

func nonisolatedSyncCaller() {
    f()
}
```

이 파일을 Swift 5 모드로 컴파일하면(`-swift-version 5`) 3 번째 줄에서 error 가 난다.

```text
DefaultArg.swift:3:34: error: call to main actor-isolated initializer 'init()' in a synchronous nonisolated context [#ActorIsolatedCall]
note: calls to initializer 'init()' from outside of its actor context are implicitly asynchronous
```

기본 인자는 항상 `nonisolated` 로 취급됐기 때문이다. 기본값 식 `Model()` 은 `@MainActor` class 의 init 을 동기 호출하는데, 기본 인자 자리는 어느 actor 에도 속하지 않은 것으로 간주되니 "main actor 밖에서 동기 호출" 이 되어 막힌다. `f` 자체가 `@MainActor` 라서 `f` 를 부르는 쪽은 어차피 main actor 위에 있거나 `await` 로 건너와야 하는데도 그랬다. 안전한 코드가 막힌 셈이다.

같은 파일 14 번째 줄(`nonisolatedSyncCaller` 안의 `f()`)에도 error 가 나는데, 이건 두 모드에서 똑같이 나오므로 다음 절에서 본다.

한쪽은 위험한 코드를 통과시키고 다른 쪽은 안전한 코드를 막는다. 게다가 두 자리가 서로 다른 규칙을 쓰니, 개발자는 기본값 식이 어디에 적혔는지에 따라 isolation 이 다르게 동작한다는 것을 따로 외워야 했다. 이 제안은 두 자리를 같은 원칙으로 묶는다.

---

## 무엇이 바뀌나

규칙은 한 문장이다. 기본값 식은 자기를 둘러싼 함수나 프로퍼티와 같은 isolation 을 가질 수 있다. 어느 isolation 이 필요한지는 식 안에서 동기적으로 부르는 것들이 요구하는 isolation 에서 추론된다(제안서 Detailed design 의 Inference). 예를 들어 `value: Int = requiresMainActor()` 라고 적으면, `requiresMainActor()` 가 `@MainActor` 라서 이 기본값은 `@MainActor` 를 요구한다고 읽는다.

기본값 식은 항상 동기 문맥에서 계산된다. 그래서 식 안의 호출은 모두 동기 호출이어야 하고, isolated callee(isolation 이 정해진 채로 불리는 쪽 함수)를 동기로 부르려면 식 자체가 이미 그 isolation 안에 있어야 한다. "식이 요구하는 isolation = 식 안의 호출들이 요구하는 isolation" 이라는 추론이 여기서 나온다.

이 규칙으로 기본 인자는 caller 의 위치에 따라 세 갈래로 나뉜다.

![@MainActor 함수 f 의 기본 인자 Model() 은 main actor 위에서 계산된다. main actor 위의 caller 는 그냥 부르고, nonisolated async caller 는 await 로 건너가서 부르고, nonisolated 동기 caller 는 건너갈 수 없어서 error 가 난다.](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-03-05-SE-0411/se-0411-default-arg-caller.png)

main actor 위에서 부르는 쪽은 그냥 부르면 된다. nonisolated async 함수는 `await` 로 main actor 에 건너가면서 기본값도 거기서 계산된다. nonisolated 동기 함수는 건너갈 방법이 없어서 막힌다. 이 세 갈래는 새로 만든 규칙이 아니라 `@MainActor` 함수를 부를 때 원래 적용되던 규칙 그대로다. 제안서도 "these rules already fall out of the semantics of calling actor isolated functions" 라고 적었다.

### 부르는 쪽에서 하는 기본 인자 검사

앞 절의 `DefaultArg.swift` 를 Swift 6 모드로 다시 컴파일했다(`-emit-sil` 로 돌렸고, 이유는 뒤의 "저장 프로퍼티 초기값과 init 의 isolation" 에서 설명한다). 3 번째 줄의 error 는 사라졌고, 남은 것은 14 번째 줄 하나다.

```text
DefaultArg.swift:14:5: error: call to main actor-isolated global function 'f(model:)' in a synchronous nonisolated context [#ActorIsolatedCall]
note: calls to global function 'f(model:)' from outside of its actor context are implicitly asynchronous
note: add '@MainActor' to make global function 'nonisolatedSyncCaller()' part of global actor 'MainActor'
```

`useFromMainActor` 의 `f()` 는 통과한다. main actor 위에서 부르니 `Model()` 도 거기서 계산하면 된다. `nonisolatedCaller` 의 `await f()` 도 통과한다. `await` 가 main actor 로 건너가는 지점이고, 기본 인자 `Model()` 은 그 건너간 뒤에 계산된다. 14 번째 줄의 `nonisolatedSyncCaller` 만 error 인데, 문제는 `Model()` 이 아니라 `f` 자체를 동기로 부르는 것이다. 이건 기본 인자가 없는 `@MainActor` 함수를 nonisolated 동기 함수에서 부를 때도 똑같이 나는 error 다. note 두 줄이 해법을 알려 준다. main actor 밖에서 `f` 를 부르는 호출은 암묵적으로 비동기가 되니(첫 번째 note) `nonisolatedSyncCaller` 를 `async` 로 바꾸고 `await` 를 쓰거나, 함수에 `@MainActor` 를 붙이면 된다(두 번째 note).

기본 인자에 대한 규칙은 "isolation 은 부르는 쪽에서 검사한다" 한 줄이다. 기본 인자 자체가 어디서 평가되는지가 아니라, 이미 있던 호출 규칙을 그대로 쓰기 때문에 새로 배울 것이 거의 없다.

### 인자 평가 순서가 바뀌는 경우

이 제안에서 가장 헷갈리는 부분이 인자 평가 순서다. 먼저 현재의 평소 순서부터 보자. 함수를 부를 때 인자는 이 순서로 평가된다.

1. 명시한 r-value 인자를 왼쪽에서 오른쪽으로 평가
2. 기본 인자와 formal access 인자를 왼쪽에서 오른쪽으로 평가

"formal access" 는 `inout` 인자를 `&x` 로 넘길 때 일어나는 일이다. `&x` 는 값을 복사해서 넘기는 것이 아니라 그 변수에 대한 접근을 "시작" 하는 것이고, 함수가 끝날 때까지 그 변수는 겹쳐서 접근할 수 없다. 이 접근의 시작을 formal access 라고 부른다. 반대로 `y: explicitVal` 처럼 값을 읽어서 넘기는 인자가 r-value 인자다.

isolated 기본 인자가 끼면 순서가 바뀐다. 기본 인자는 callee 의 isolation 안에서 계산되어야 하니, callee 의 actor 로 건너간 뒤에 평가한다.

1. 명시한 r-value 인자
2. formal access 인자
3. callee 의 isolation 으로 hop
4. 기본 인자

"hop" 은 한 actor 에서 다른 actor 로 실행 위치를 옮기는 것이다. 창구 비유로는 한 창구에서 다른 창구로 걸어가는 일이다. 이 순서를 직접 확인하려고 `Order.swift` 를 만들었다. nonisolated 함수와 `@MainActor` 함수가 같은 모양의 인자를 받고, 어느 인자가 언제 평가되는지 `log` 배열에 기록한다.

```swift
nonisolated(unsafe) var log: [String] = []

var defaultVal: Int { log.append("defaultVal"); return 0 }
var explicitVal: Int { log.append("explicitVal"); return 0 }
var explicitFormalVal: Int {
    get { log.append("explicitFormalVal"); return 0 }
    set {}
}

func evaluate(x: Int = defaultVal, y: Int = defaultVal, z: inout Int) {}

@MainActor var isolatedDefaultVal: Int { log.append("isolatedDefaultVal"); return 0 }

@MainActor func evaluateIsolated(x: Int = isolatedDefaultVal, y: Int = isolatedDefaultVal, z: inout Int) {}

nonisolated func nonisolatedCaller() async {
    await evaluateIsolated(y: explicitVal, z: &explicitFormalVal)
}

@main struct App {
    static func main() async {
        evaluate(y: explicitVal, z: &explicitFormalVal)
        print("nonisolated callee:", log)
        log = []
        await nonisolatedCaller()
        print("isolated callee:   ", log)
    }
}
```

`nonisolated(unsafe)` 는 attribute 가 아니라 declaration modifier 이고, 컴파일러의 동시성 검사를 끄는 표시다. 여기서는 `log` 를 여러 곳에서 간단히 쓰려고 붙였다([SE-0412 글](https://haroldfromk.github.io/posts/SE-0412/)에서 다뤘다). Swift 언어 문서의 [Declarations](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/declarations/){:target="_blank"} 장에 `nonisolated` 가 나온다. `@main` 은 이 타입의 `main()` 을 프로그램의 시작점으로 삼는 attribute 이고, [Attributes](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} 장에 나온다.

`xcrun swiftc -swift-version 6 -parse-as-library Order.swift` 로 빌드해서 실행한 결과다. `-parse-as-library` 는 파일을 최상위 코드가 있는 스크립트가 아니라 라이브러리 소스로 읽게 하는 옵션이고, `@main` 을 쓰는 파일에 필요하다.

```text
nonisolated callee: ["explicitVal", "defaultVal", "explicitFormalVal"]
isolated callee:    ["explicitVal", "explicitFormalVal", "isolatedDefaultVal"]
```

첫 줄은 평소 순서다. 명시한 `explicitVal` 이 먼저, 그다음 기본 인자 `defaultVal`(x 자리에만 쓰였으니 한 번), 마지막이 `&explicitFormalVal` 의 접근 시작이다. 둘째 줄은 isolated 기본 인자가 있는 경우로, `explicitVal` 다음에 `explicitFormalVal` 이 오고 기본 인자 `isolatedDefaultVal` 이 맨 뒤로 밀렸다. formal access 가 기본 인자보다 먼저 일어났다.

첫 줄의 평소 순서에는 경위가 하나 붙어 있다. pitch 에서 Holly 는 평소 순서를 "명시한 r-value 인자, 기본 인자, formal access" 세 단계로 설명했다(pitch #9, #28). 기본 인자가 formal access 보다 앞선다는 뜻이다. 리뷰에서 wadetregaskis 가 이 순서가 지금 언어의 규칙인지 이 제안이 만드는 규칙인지 물었고(리뷰 #5), Holly 는 지금 있는 규칙이 맞다고 답하면서 그 설명이 조금 틀려서 전날 PR #2198 로 고쳤다고 밝혔다(리뷰 #6). 고친 쪽이 이 글 앞부분의 두 단계 설명, 즉 기본 인자와 formal access 를 같은 단계에서 왼쪽부터 오른쪽으로 평가한다는 것이다. wadetregaskis 는 이 경위를 순서가 생각보다 덜 중요하다는 근거로 받았다(리뷰 #7). 자신도 그 규칙을 몰랐고, 제안서를 쓴 사람도 정확히 몰랐다는 것이다.

두 설명의 차이는 `inout` 인자가 기본 인자보다 왼쪽에 올 때 드러난다. `Order.swift` 의 `evaluate` 는 `z` 가 맨 오른쪽이라 어느 설명으로도 같은 결과가 나왔다. 그래서 `z` 를 왼쪽으로 옮긴 `OrderInout.swift` 를 따로 만들었다.

```swift
nonisolated(unsafe) var log: [String] = []

var defaultVal: Int { log.append("defaultVal"); return 0 }
var formal: Int {
    get { log.append("formal"); return 0 }
    set {}
}

func g(z: inout Int, x: Int = defaultVal) {}

@main struct App {
    static func main() {
        g(z: &formal)
        print(log)
    }
}
```

`xcrun swiftc -swift-version 6 -parse-as-library OrderInout.swift` 로 빌드해서 실행한 결과다.

```text
["formal", "defaultVal"]
```

`g(z: &formal)` 에서 `z` 는 기본 인자 `x` 보다 왼쪽에 있고, 평가도 `formal` 이 먼저다. 세 단계 설명대로라면 기본 인자가 먼저여서 `["defaultVal", "formal"]` 이 나와야 한다. 실제 규칙은 기본 인자와 formal access 를 왼쪽부터 오른쪽으로 섞어서 평가하는 것이다.

왜 이렇게 했을까. pitch 에서 Holly 가 반복해서 든 이유는 같다. `await useDefaults()` 한 줄이 보이지 않게 actor 사이를 여러 번 왔다 갔다 하면 안 된다는 것이다(pitch #9, #28, #32). 앞에서 말한 세 단계 순서는 당시 Holly 가 이해하고 있던 순서였고, 그 순서를 지키면 "r-value 인자는 caller 에서, 기본 인자는 callee 에서, formal access 는 다시 caller 에서" 처럼 caller 와 callee 사이를 오가야 한다고 봤다. 같은 이유로 pitch #32 에서는 기본 인자가 formal access 보다 먼저 평가되면 내가 넘긴 인자가 보이지 않는 hop 이 다 끝난 뒤에야 평가될 수 있어서 예상과 다르다고 적었다. 그래서 caller 쪽에서 평가할 것을 전부 먼저 끝내고, hop 을 한 번만 하고, 그 안에서 기본 인자를 평가하도록 기본 인자를 맨 뒤로 보냈다. 이것이 pitch 의 첫 버전에서 바뀐 가장 큰 부분이다(revision history 의 "changing the argument evaluation between formal access and default arguments").

리뷰에서 KeithBauerANZ 가 이 불일치가 조금 거슬린다고 했다(리뷰 #3). 모든 경우의 순서를 통일하면 안 되냐는 것이다. Holly 의 답(리뷰 #4)은 두 가지였다. 첫째, 달라지는 것은 async 와 sync 의 차이가 아니라 isolated 함수와 nonisolated 함수의 차이다. isolated 함수에 isolated 기본 인자가 하나라도 있으면 기본 인자 전체가 마지막으로 가고, 동기로 부르든 비동기로 부르든 똑같다. 둘째, 움직이는 것은 기본 인자뿐이라서 기본 인자에 부작용이 있거나 같은 값을 formal access 로 넘기고 있어야만 차이가 보인다. 순서를 전체적으로 바꾸면 순서에 기대는 이상한 코드가 컴파일 error 도 없이 다르게 동작할 수 있어서 영향 범위를 가늠하기 어렵다는 것이 통일하지 않은 이유다.

### closure 기본값의 isolation 추론

기본 인자가 closure 일 때도 같은 추론이 적용된다. 제안서는 closure 를 만드는 것 자체는 어느 isolation 에서든 할 수 있다고 한다. isolation 은 closure 를 부를 때 적용된다. closure 에 isolation 을 직접 적지 않았다면, 본문에서 동기로 부르는 callee 들의 isolation 을 합쳐서 추론한다. 파일로 확인했다.

```swift
@MainActor func requiresMainActor() -> Int { 1 }

@MainActor func useDefaultClosure(
    closure: () -> Void = {
        _ = requiresMainActor()
    }
) {
    closure()
}

func nonisolatedDefaultClosure(
    closure: () -> Void = {
        _ = requiresMainActor()
    }
) {}
```

Swift 6 모드 결과는 이렇다.

```text
Closure.swift:12:5: error: main actor-isolated default value in a nonisolated context
```

`useDefaultClosure` 는 통과한다. closure 본문이 `requiresMainActor()` 를 동기로 부르니 이 closure 는 `@MainActor` closure 로 추론되고, 둘러싼 함수도 `@MainActor` 라서 isolation 이 맞는다. `nonisolatedDefaultClosure` 는 둘러싼 함수가 nonisolated 인데 기본값이 main actor 를 요구하니 걸린다. 위치가 closure 본문의 호출 줄이 아니라 파라미터(12 번째 줄)라는 점이 눈에 띈다. 컴파일러는 "이 기본값을 이 자리에 둘 수 없다" 고 말한다.

Swift 5 모드에서는 두 함수 모두 closure 본문의 호출 줄에서 error 가 났다(5 번째, 13 번째 줄).

```text
Closure.swift:5:13: error: call to main actor-isolated global function 'requiresMainActor()' in a synchronous nonisolated context [#ActorIsolatedCall]
Closure.swift:13:13: error: call to main actor-isolated global function 'requiresMainActor()' in a synchronous nonisolated context [#ActorIsolatedCall]
```

기본값 closure 는 isolation 이 actor 인스턴스로 추론되는 일이 절대 없다. 인스턴스에 isolated 되려면 closure 가 isolated 파라미터(`isolated` 를 붙여서 이 함수가 어느 actor 인스턴스 위에서 도는지 지정한 파라미터)를 직접 갖거나 바깥의 isolated 파라미터를 캡처해야 하는데, 기본 인자 closure 는 값을 캡처할 수 없기 때문이다. 그래서 기본 인자 closure 에 추론되는 isolation 은 전부 global actor 다. isolated 파라미터를 closure 가 직접 선언하면 인스턴스 isolation 도 가능하지만, 그건 추론이 아니라 명시한 경우다.

### 서로 다른 actor 를 섞을 수 없는 제한

pitch 의 첫 버전은 `@MainActor` 함수가 `@AnotherActor` 를 요구하는 기본값을 가져도 되는 방향이었다. 그런데 토론 중에 이 제한이 들어갔다. 함수나 타입 자신이 isolation 을 가지고 있다면 기본값 식이 요구하는 isolation 도 같아야 한다. 파일로 만들었다.

```swift
@globalActor actor AnotherActor { static let shared = AnotherActor() }
@AnotherActor func requiresAnotherActor() -> Int { 2 }

@MainActor func mixed(value: Int = requiresAnotherActor()) {}
```

Swift 6 모드 결과다.

```text
Mixed.swift:4:23: error: global actor 'AnotherActor'-isolated default value in a main actor-isolated context
```

nonisolated 기본값과 섞는 것은 항상 괜찮다. 제한은 "isolation 이 있는 함수에 다른 isolation 을 요구하는 기본값" 만 막는다. 함수 자체가 `nonisolated` 라면 기본값은 `nonisolated` 여야 한다는 규칙도 있다. 앞의 `nonisolatedDefaultClosure` 가 그 경우였다. Swift 5 모드에서는 이 줄에서 `call to global actor 'AnotherActor'-isolated global function 'requiresAnotherActor()' in a synchronous nonisolated context` 라는 error 가 난다.

이 제한은 pitch 에서 두 단계로 만들어졌다. Holly 가 hop 을 한 번으로 모으려면 어떤 제약이 필요한지 정리하면서 두 가지를 던졌다(pitch #26).

- 첫째 제약: 함수 하나의 isolated 기본 인자는 모두 같은 isolation 이어야 한다. `@MainActor` 를 요구하는 인자와 `@AnotherActor` 를 요구하는 인자를 한 함수에 둘 수 없다.
- 둘째 제약: 함수 자체가 isolation 을 가졌다면 기본 인자의 isolation 도 그 함수와 같아야 한다. nonisolated 함수가 `@MainActor` 기본 인자를 가지는 것은 괜찮지만 `@MainActor` 함수가 `@AnotherActor` 기본 인자를 가질 수는 없다.

wadetregaskis 는 첫째 제약을 시작점으로 괜찮다고 봤다(pitch #27). 서로 다른 isolation 이 섞이면 무엇을 어떤 순서로 할지부터 모호하지만, 모두 함수의 isolation 이라면 컴파일러가 어떻게 처리할지만 남는다는 이유였다. 둘째 제약에는 Jumhyn 처럼 같은 `await` 아래에 두고 컴파일러가 알아서 처리하게 해도 된다는 쪽이었다(pitch #27). 그 뒤 KeithBauerANZ 가 허용하는 조합과 금지하는 조합을 표처럼 적었고(pitch #35), Holly 가 이 방향이 유망하다며 설계를 고치겠다고 답했다(pitch #36). 제안서의 revision history 에 "Require that isolated default arguments share the same isolation as their enclosing function or type" 으로 들어간 항목이다.

### 저장 프로퍼티 초기값과 init 의 isolation

저장 프로퍼티 쪽 규칙은 이렇다. 초기값이 요구하는 isolation 이 init 의 isolation 과 같을 때만 그 초기값이 init 앞에 끼워진다. 다르면 끼워지지 않고, 그 프로퍼티는 init 본문에서 직접 초기화해야 한다. 앞의 `main.swift` 와 같은 모양을 파일로 만든 `Stored.swift` 다.

```swift
@globalActor actor AnotherActor { static let shared = AnotherActor() }

@MainActor func requiresMainActor() -> Int { 1 }
@AnotherActor func requiresAnotherActor() -> Int { 2 }

class C {
    @MainActor var x1 = requiresMainActor()
    @AnotherActor var x2 = requiresAnotherActor()

    nonisolated init() {}
}
```

Swift 6 모드로 컴파일한 결과 전체다.

```text
Stored.swift:10:25: error: return from initializer without initializing all stored properties
 5 | 
 6 | class C {
 7 |     @MainActor var x1 = requiresMainActor()
   |                    `- note: main actor-isolated default value of 'self.x1' cannot be used in a nonisolated initializer
 8 |     @AnotherActor var x2 = requiresAnotherActor()
   |                       `- note: global actor 'AnotherActor'-isolated default value of 'self.x2' cannot be used in a nonisolated initializer
 9 | 
10 |     nonisolated init() {}
   |                         `- error: return from initializer without initializing all stored properties
11 | }
12 | 
```

error 는 초기값 쪽이 아니라 `nonisolated init() {}` 의 닫는 중괄호에 난다. 초기값 식이 틀렸다는 것이 아니라, 두 초기값이 이 init 앞에 끼워지지 않았으니 init 이 끝나는 시점에 `x1` 과 `x2` 가 비어 있다는 말이다. note 두 줄이 "이 초기값은 nonisolated init 에서 쓸 수 없다" 고 이유를 알려 준다. 앞에서 본 `main.swift` 의 error 문구가 이렇게 나온 이유다.

이 error 는 `-emit-sil` 로 컴파일해야 보인다. 명령은 이렇게 썼다.

```text
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 6 Stored.swift
```

`-emit-sil` 은 SIL 까지 만들고 멈추라는 옵션이고, `-o /dev/null` 은 결과물을 버려서 진단만 보게 한다. `-parse-as-library` 는 파일을 최상위 코드가 있는 스크립트가 아니라 라이브러리 소스로 읽게 하는 옵션이다. 이 글의 `@main` 을 쓰는 파일에 필요해서 모든 명령에 같이 붙였다. 일반 빌드(`xcrun swiftc -swift-version 6 -parse-as-library Stored.swift`)로도 같은 진단이 나온다.

`-typecheck` 로만 돌리면 이 파일은 Swift 6 모드에서도 진단이 0 개다. 컴파일러가 소스를 검사하는 과정은 대략 두 단계다. 먼저 타입 검사가 문법, 타입, isolation 호출 규칙을 보고, 그다음 SIL(Swift 의 중간 표현)로 바꾼 뒤 "모든 저장 프로퍼티가 초기화됐는가" 를 따지는 definite initialization 이 돈다. 이 `Stored.swift` 의 error 는 두 번째 단계에서 나온다. `-typecheck` 는 첫 단계에서 멈추니 이 진단을 빼먹는다. 이 글의 진단은 모두 `-emit-sil` 로 뽑았다.

고치는 방법은 제안서가 세 가지를 보여 준다. 프로퍼티를 init 본문에서 직접 대입하기, 초기값과 isolation 이 같은 init 쓰기, `async` init 에서 `await` 로 부르기다. 파일로 만든 `Stored2.swift` 다.

```swift
@globalActor actor AnotherActor { static let shared = AnotherActor() }

@MainActor func requiresMainActor() -> Int { 1 }
@AnotherActor func requiresAnotherActor() -> Int { 2 }

class C {
    @MainActor var x1: Int = requiresMainActor()
    @AnotherActor var x2: Int = requiresAnotherActor()

    nonisolated init(x1: Int, x2: Int) {
        self.x1 = x1
        self.x2 = x2
    }

    @MainActor init(x2: Int) {
        self.x2 = x2
    }

    nonisolated init() async {
        self.x1 = await requiresMainActor()
        self.x2 = await requiresAnotherActor()
    }
}
```

Swift 6 모드에서 진단이 하나도 나오지 않는다. 세 init 이 각각 다른 길을 쓴다.

- `nonisolated init(x1:x2:)` 는 두 프로퍼티를 직접 대입한다. 초기값이 끼워지지 않고 본문의 대입이 그 자리를 채운다.
- `@MainActor init(x2:)` 는 `x1` 의 초기값 `requiresMainActor()` 가 이 init 앞에 끼워진다. init 이 `@MainActor` 라서 `x1` 초기값의 isolation 과 맞기 때문이다. 제안서 주석의 "`self.x1` gets assigned to the default value" 가 이 뜻이다. `x2` 는 main actor 가 아니라 `AnotherActor` 에 묶여 있으니 본문에서 대입한다.
- `nonisolated init() async` 는 `await` 로 각 함수를 불러서 대입한다. `async` init 은 부르는 쪽이 이미 `await` 를 하니 안에서 actor 를 건너가도 된다.

리뷰에서 wadetregaskis 가 마지막 방법의 예를 보고 질문했다(리뷰 #5). `nonisolated init() async` 가 `x1` 을 대입한다면 `x1` 의 기본값은 쓸 일이 없는 것 아니냐는 것이다. Holly 의 답(리뷰 #6)은 이렇다. 기본값은 `nonisolated init` 본문에서는 평가되지 않아서 `requiresMainActor()` 는 한 번만 불린다. 그리고 같은 class 에 `@MainActor` init 이 따로 있으면 그쪽에서 기본값이 쓰이니 의미 없는 값이 아니다. 규칙을 한 줄로 줄이면 "isolation 이 다른 init 본문에서는 isolated 초기값을 평가하지 않는다" 이다. wadetregaskis 는 init 이 하나뿐인데 기본값이 아무 데서도 안 쓰이는 경우라면 경고가 있으면 좋겠다고 덧붙였는데(리뷰 #7), 이 제안의 범위는 아니라는 선에서 끝났다.

---

### Sendable 이란?

`Sendable` 은 값을 isolation 경계 너머로 안전하게 보낼 수 있다는 표시다. `Int`, `String` 처럼 복사하면 서로 영향을 주지 않는 값은 `Sendable` 이다. 반대로 같은 인스턴스를 여러 곳에서 쥘 수 있는 class 는 기본적으로 non-Sendable 이다. 창구 비유로 하면 서류 사본은 창구 사이로 주고받아도 되지만(`Sendable`), 원본 장부 하나를 두 창구가 동시에 쥐고 고치면 안 된다(non-Sendable). 이 글의 `NonSendable` 은 아무 표시도 없는 빈 class 라서 non-Sendable 이다. 아래 두 절, 합성 init 의 isolation 과 프로퍼티 초기화 규칙이 모두 이 구분에 달려 있다.

---

### isolated 프로퍼티를 경계 밖에서 초기화하기

합성 init 의 isolation 을 정하려면 함께 정해야 하는 규칙이 하나 있어서 이 제안에 들어간 내용이다. 제안서 문장은 global actor 에 묶인 저장 프로퍼티를 isolation 경계 밖의 init 이 초기화하면 안 된다고 모든 프로퍼티에 대해 말한다. 6.4 컴파일러가 실제로 막는 것은 non-Sendable 값이다. 먼저 non-Sendable 쪽을 본다.

```swift
class NonSendable {}

class C {
    @MainActor var ns: NonSendable

    init(ns: NonSendable) {
        self.ns = ns
    }
}
```

`init(ns:)` 는 isolation 이 없는 init 이다. 여기서 `self.ns = ns` 를 하면, 호출한 쪽 isolation 의 값이 `@MainActor` 가 지키는 프로퍼티로 흘러 들어간다. 제안서는 이것을 non-Sendable 값을 경계 너머로 보내는 것이라고 설명한다. 그 값을 다른 쪽에서도 쥐고 있으면 main actor 밖에서 같은 객체를 만질 수 있게 되기 때문이다.

Swift 5 모드에서는 warning 이고 error 가 될 것이라는 안내가 붙는다.

```text
CrossInit.swift:7:14: warning: main actor-isolated property 'ns' can not be mutated from a nonisolated context; this is an error in the Swift 6 language mode
note: mutation of this property is only permitted within the actor
```

Swift 6 모드에서는 같은 내용이 error 다.

```text
CrossInit.swift:7:14: error: main actor-isolated property 'ns' can not be mutated from a nonisolated context
note: mutation of this property is only permitted within the actor
```

제안서 본문 주석은 "passing non-Sendable value 'ns' to a MainActor-isolated context" 라는 문구로 적혀 있지만, 6.4 컴파일러가 실제로 내는 문구는 위와 같다. 해결은 `init` 을 `@MainActor` 로 만드는 것이다. 제안서의 표현으로는 global actor 에 묶인 저장 프로퍼티를 초기화하는 init 은 그 global actor 에 isolated 되어야 한다.

같은 모양에서 프로퍼티 타입만 `Int` 로 바꾸면 결과가 달라진다. `CrossInitInt.swift` 다.

```swift
class C {
    @MainActor var n: Int

    init(n: Int) {
        self.n = n
    }
}
```

`-swift-version 5` 와 `-swift-version 6` 둘 다 진단이 0 개다. `Int` 는 `Sendable` 이라서 경계를 넘겨도 되기 때문이다. 앞 절의 `Stored2.swift` 에서 `nonisolated init(x1:x2:)` 가 `@MainActor` 와 `@AnotherActor` 프로퍼티를 `Int` 로 대입하고도 통과한 것이 같은 이유다. 정리하면 이 규칙은 non-Sendable 값을 isolated 프로퍼티로 옮기는 대입만 막고, `Sendable` 값은 init 본문에서 그냥 대입할 수 있다.

### 컴파일러가 만들어 주는 init 의 isolation

struct 는 컴파일러가 memberwise init(프로퍼티마다 파라미터를 하나씩 받는 init)을 만들어 준다. 모든 저장 프로퍼티에 기본값이 있으면 struct 든 init 을 하나도 쓰지 않은 class 든 `init()` 도 만들어 준다. 이 합성 init 의 isolation 을 이 제안이 정한다. 규칙은 두 갈래다.

- 저장 프로퍼티 중 non-Sendable 이면서 actor 에 묶인 것이 있거나, 기본값이 actor isolation 을 요구하면 합성 init 도 그 actor 에 isolated 된다.
- 그런 프로퍼티도, 그런 기본값도 없다면 합성 init 은 `nonisolated` 다.

제안서의 두 예는 이렇다. 아래 주석 코드는 컴파일러가 합성한다는 것을 보여 주는 의사 코드이고, 실제로 쓰는 코드가 아니다.

```swift
class NonSendable {}

@MainActor struct MyModel {
  // @MainActor inferred from annotation on enclosing struct
  var value: NonSendable = .init()

  /* compiler-synthesized memberwise init is @MainActor
  @MainActor
  init(value: NonSendable = .init()) {
    self.value = value
  }
  */
}

@MainActor struct MyView {
  var value: Int = 0

  /* compiler-synthesized 'init's are 'nonisolated'
  nonisolated init() {
    self.value = 0
  }

  nonisolated init(value: Int = 0) {
    self.value = value
  }
  */
}
```

`MyModel` 의 `value` 는 non-Sendable 이면서 main actor 에 묶여 있으니 합성 init 도 `@MainActor` 다. `MyView` 의 `value` 는 `Int` 라 `Sendable` 이고 기본값 `0` 도 isolation 이 필요 없으니 합성 init 이 `nonisolated` 다. 이걸 실제로 확인한 `Synth.swift` 다.

```swift
class NonSendable {}

@MainActor struct MyModel {
    var value: NonSendable = .init()
}

@MainActor struct MyView {
    var value: Int = 0
}

func makeFromAnywhere() {
    let v = MyView()
    let v2 = MyView(value: 3)
    _ = (v, v2)
    let m = MyModel()
    _ = m
}

func makeAsync() async {
    let m = await MyModel()
    _ = m
}
```

Swift 5 모드에서는 `MyView()`(12 번째 줄)와 `MyModel()`(15 번째 줄)이 둘 다 같은 error 를 낸다.

```text
Synth.swift:12:13: error: call to main actor-isolated initializer 'init()' in a synchronous nonisolated context [#ActorIsolatedCall]
Synth.swift:15:13: error: call to main actor-isolated initializer 'init()' in a synchronous nonisolated context [#ActorIsolatedCall]
```

Swift 6 모드에서는 `MyModel()` 하나만 error 다.

```text
Synth.swift:15:13: error: call to main actor-isolated initializer 'init()' in a synchronous nonisolated context [#ActorIsolatedCall]
```

`MyView()` 와 `MyView(value: 3)` 은 통과하고, `await MyModel()` 도 통과한다. 즉 SwiftUI 의 `View` 처럼 타입에 `@MainActor` 가 붙어 있어도, `Sendable` 프로퍼티와 isolation 이 필요 없는 기본값만 있다면 그 타입의 init 은 어디서든 동기로 부를 수 있다. 제안서가 John McCall 의 관찰이라며 Acknowledgments 에 감사를 적은 대목이다. SwiftUI 의 `View` 프로토콜이 `@MainActor` 가 된 것은 Swift 6 언어 모드가 아니라 iOS 18 SDK(Xcode 16, WWDC24)의 변경이다. `View` 를 따르는 struct 가 main actor 에 묶이는데도, 이 규칙 덕분에 `Sendable` 프로퍼티와 isolation 이 필요 없는 기본값만 가진 단순한 struct 는 init 을 어디서든 부를 수 있다. Swift 6 마이그레이션 전반은 [WWDC24 Migrate your app to Swift 6 글](https://haroldfromk.github.io/posts/WWDC24-10169/)에서 다뤘다.

이 규칙은 합성 init 에서 기본값이 항상 유효하도록 한다. 기본값이 isolation 을 요구하면 합성 init 이 같은 isolation 을 가지니 기본값이 쓰일 수 있다. 문제는 서로 다른 actor 를 요구하는 두 기본값이 한 타입 안에 있는 경우다. 그 기본값은 영영 쓸 수 없으니 error 로 막는다. 파일로 만든 `Conflict.swift` 다.

```swift
@globalActor actor AnotherActor { static let shared = AnotherActor() }

@MainActor func requiresMainActor() -> Int { 1 }
@AnotherActor func requiresAnotherActor() -> Int { 2 }

struct S {
    @MainActor var a = requiresMainActor()
    @AnotherActor var b = requiresAnotherActor()
}
```

Swift 6 모드에서는 error 가 두 개 나온다.

```text
Conflict.swift:6:8: error: memberwise initializer for 'S' cannot be both nonisolated and main actor-isolated
 4 | @AnotherActor func requiresAnotherActor() -> Int { 2 }
 5 | 
 6 | struct S {
   |        `- error: memberwise initializer for 'S' cannot be both nonisolated and main actor-isolated
 7 |     @MainActor var a = requiresMainActor()
   |                    `- note: initializer for property 'a' is main actor-isolated
 8 |     @AnotherActor var b = requiresAnotherActor()
 9 | }

Conflict.swift:6:8: error: default initializer for 'S' cannot be both nonisolated and main actor-isolated
 4 | @AnotherActor func requiresAnotherActor() -> Int { 2 }
 5 | 
 6 | struct S {
   |        `- error: default initializer for 'S' cannot be both nonisolated and main actor-isolated
 7 |     @MainActor var a = requiresMainActor()
   |                    `- note: initializer for property 'a' is main actor-isolated
 8 |     @AnotherActor var b = requiresAnotherActor()
 9 | }
```

memberwise init 과 `init()` 이 각각 한 번씩이다. Swift 5 모드에서는 같은 파일이 진단 없이 통과한다. 이런 타입은 `async` init 에서 `await` 로 직접 채워야 한다. 리뷰에서 wadetregaskis 는 이런 경우에 컴파일러가 async init 을 합성해 주면 어떻겠냐고 물었는데(리뷰 #5), Holly 는 범위를 넘고 서로 다른 global actor 에 묶인 프로퍼티를 한 타입에 두는 것 자체가 좋은 패턴이 아니라고 답했다(리뷰 #6).

## 다른 선택지는 왜 안 됐나

이 제안이 고른 방향은 "isolation 을 기본값에도 허용하되 같은 것끼리만" 이다. 제안서의 Alternatives considered 에는 한 가지만 적혀 있지만, pitch 와 리뷰 스레드에서는 훨씬 많은 대안이 오갔다. 어떤 것이 왜 안 됐는지 정리한다.

---

### 모든 저장 프로퍼티 초기값을 nonisolated 로

제안서에 적힌 유일한 대안이다. SE-0327 이 원래 이렇게 제안했다. 저장 프로퍼티 초기값은 기본 인자처럼 항상 `nonisolated` 로 보자는 것이다. Kavon Farvardin 이 이 규칙을 구현했는데, 곧 되돌려졌다. `@MainActor` 타입이 다른 `@MainActor` 타입의 init 을 초기값으로 부르는 패턴이 너무 흔해서 많은 코드가 깨졌기 때문이다. init 을 `nonisolated` 로 풀 수 있는 경우도 있지만, init 본문에서 `@MainActor` 프로퍼티나 함수에 닿는 경우가 많아서 일괄로 풀 수 없었다. 그래서 이 제안이 SE-0327 의 해당 규칙을 줄이고 대신 "init 의 isolation 이 맞을 때만 쓴다" 로 바꿨다.

---

### 기본 인자를 callee 쪽에서 계산하기

pitch 에서 KeithBauerANZ 는 기본 인자를 callee 쪽에서 계산하게 하자고 했다. `@callerEvaluated` 와 `@calleeEvaluated` 두 종류를 만들고 Swift 6 의 기본을 callee 쪽으로 바꾸자는 안이다(pitch #19). 기본 인자가 caller 에서 계산되는 원래 결정이 틀렸다는 생각이었다.

Holly 는 세 가지 이유로 반대했다(pitch #20). 인자를 생략하는 조합의 수만큼 함수를 만들어야 해서 코드 크기가 조합적으로 늘어난다. 기본 인자의 존재 자체가 ABI(이미 컴파일된 바이너리끼리 맞춰야 하는 약속)가 된다. 이 overload 들이 타입 시스템에 들어가면 overload resolution(같은 이름의 여러 함수 중 부르는 식에 맞는 것을 고르는 과정) 성능에 영향이 크다. 이어서 John McCall 이 한 가지를 더했다(pitch #23). 진짜 파라미터를 Optional 로 만들어 두고 nil 이 오면 callee 에서 기본값을 계산하는 방식으로 구현할 수도 있겠지만, 그래도 기본 인자의 존재가 ABI 가 되는 문제는 같고, 차라리 프로그래머가 명시적으로 그렇게 쓰는 편이 낫지 않으냐는 것이다.

callee 쪽 계산이 필요하면 이미 도구가 있다는 것이 Holly 의 결론이었다. `@autoclosure`(인자로 쓴 식을 컴파일러가 closure 로 감싸서 넘기는 attribute) 로 계산을 callee 로 미루는 것이다(pitch #20). KeithBauerANZ 는 그러면 isolated 기본 인자만 `arg: @autoclosure @GlobalActor () -> Type = value()` 처럼 길어지고 함수 안에서 하나씩 평가해야 해서 불편하다고 했다(pitch #21). KeithBauerANZ 는 둘 다 가지는 해법은 없는 것 같다고 먼저 말했고(pitch #21), Holly 는 당연히 없다며 동의했다(pitch #22). Holly 는 선택지를 이렇게 나눴다. 값을 항상 caller 의 isolation 에서 평가하고 싶으면 아무것도 안 하면 되고, 기본 인자는 nonisolated 여야 한다. 항상 callee 의 isolation 에서 평가하고 싶으면 인자를 closure 로 감싼다. 호출하는 쪽에 따라 달라지는 평가는 `Task` 의 이니셜라이저가 `@_inheritsActorContext` 로 하는 것처럼 isolation 에 대해 다형적인 도구가 더 있어야 가능하다. 이 제안은 같은 isolation 의 호출이 많은 쪽을 우선한다. closure 로 감싸는 쪽은 isolation 경계를 넘어 부르는 쪽을 우선한다.

---

### 다른 actor 의 기본값도 await 로 묶어 허용하기

가장 길게 오간 논쟁이다. wadetregaskis 는 async init 이면 기본값들이 서로 다른 actor 를 요구해도 `await` 로 묶어 암묵적으로 처리하면 되지 않느냐고 물었다(pitch #2). Holly 는 init 본문에 보이지 않는 hop 이 여럿 생기는 것이 싫다고 했다(pitch #3). Jon_Shier 가 지금도 `await` 한 번이 인자 여러 개의 suspension point(`await` 로 적는, 실행이 멈췄다가 나중에 이어질 수 있는 지점)를 덮고 있지 않느냐고 반문했고(pitch #4, #29), Holly 는 그 `await` 안의 비동기 호출은 전부 코드에 명시되어 있어서 caller 가 끼어들 수 있다는 점이 다르다고 답했다(pitch #5).

benpious 는 API 작성자 입장에서 놀라울 수 있다고 했다(pitch #7). 기본 인자는 "사용자가 몰라도 되게" 하려고 쓰는데, 잘못된 isolation 에서 부르면 갑자기 기본값을 직접 `await` 해야 한다는 것이다.

Holly 가 내놓은 우회로는 부르는 쪽이 먼저 main actor 에 올라가는 것이었다. `let result = await MainActor.run { useDefault() }` 처럼 쓰면 되고, 컴파일러가 isolation 경계 너머에서 isolated 기본 인자를 쓰려는 코드에 이 fix-it 을 내 줄 수도 있다고 했다(pitch #9). Jumhyn 은 이 제안에 반대했다(pitch #14). fix-it 을 적용한 코드는 읽는 사람에게 이해하기 어렵고, 어디서 돌지는 callee 가 정하고 caller 는 신경 쓰지 않는다는 Swift concurrency 의 약속과 어긋난다는 것이다. 같은 글에서 Jumhyn 은 API 작성자가 이 번거로움을 피하려고 `@MainActor func f(c: C? = nil)` 로 바꾸고 본문에서 `let c = c ?? C()` 로 채우는 우회로 몰릴 것이라고 걱정했다. benpious 는 그 우회가 앞으로 `nil` 기본값이 더 낫게 되는 방향이라는 데 동의하면서, property wrapper 나 기본 인자를 `nil` 로 바꿔 주는 macro 로 풀 수도 있다고 했고(pitch #16), KeithBauerANZ 도 같은 말을 했다(pitch #18). 이 제안은 같은 isolation 을 맞추는 쪽에서는 그 우회가 필요 없게 만들고, 다른 isolation 을 부르는 쪽에서는 여전히 필요할 수 있다.

Jumhyn 은 호출자가 callee 가 어디서 돌지 신경 쓰지 않는다는 점을 다른 글에서도 되풀이했다(pitch #24). Holly 가 이 논쟁에서 가장 신경 쓴 것은 hop 이 한 번이어야 한다는 점이었고, 평소 순서 그대로는 불가능하다고 봤다. 평소 순서를 지키면 caller 의 인자를 평가하고, callee 로 hop 해서 기본 인자를 평가하고, 다시 caller 로 돌아와 formal access 를 평가하고, 다시 hop 하는 일이 일어날 수 있다고 이해했기 때문이다(pitch #9, 앞의 평가 순서 절에서 본 경위).

ellie20 은 actor 인스턴스의 isolation 에도 같은 걸 적용하자고 물었다(pitch #8). `actor SomeActor` 의 메서드 기본 인자에 `NSMutableString()` 을 넣었을 때 그 식을 actor 안에서 계산하면 non-Sendable 경고가 없어질 것이라는 것이다. Holly 는 호출 인자의 근본 규칙을 바꿀 수 없다며 non-Sendable 값을 경계 너머로 안전하게 보내는 것은 다른 pitch 의 몫이라고 했다(pitch #10). 그 pitch 는 이후 region 기반 isolation(non-Sendable 값이 어느 isolation 영역에 속하는지 컴파일러가 추적해서, 영역 안에서만 쓰이면 경계를 넘겨도 되게 하는 방식)으로 이어진 SE-0414 의 출발이다.

해결은 두 가지 제한과 순서 변경의 조합이었다. 같은 isolation 만 허용해서 hop 대상이 하나로 정해지게 했고(경위는 앞의 "서로 다른 actor 를 섞을 수 없는 제한" 에서 다뤘다), 기본 인자를 뒤로 보내서 hop 을 한 번으로 모았다. 앞에서 본 두 번째 줄 출력이 그 결과다.

### 리뷰에서 나온 이야기

리뷰는 2023-10-25 에 시작해 11-07 에 끝났다. 수락 글에서 Doug Gregor 는 피드백은 많지 않았지만 긍정적이었고, 리뷰 중에 제안서 설명을 몇 군데 다듬었다고 적었다. 스레드에서 실제로 글을 쓴 사람은 KeithBauerANZ, wadetregaskis, Holly 셋이라서 오간 이야기를 거의 다 따라갈 수 있다.

KeithBauerANZ 는 세 가지를 말했다(리뷰 #3). 첫째, 제안서 도입부가 읽기 어렵다. Holly 는 바뀐 의미를 옛 문장에 끼워 넣다가 생긴 일이라며 editorial PR 로 고치겠다고 했다(리뷰 #4). 둘째, 평가 순서가 isolated 함수와 아닌 함수에서 다른 것이 거슬린다. 이건 앞의 평가 순서 절에서 다뤘다. 셋째, 모든 제안서에서 배포 조건을 보고 싶다. Holly 는 Implications on adoption 의 "no deployment constraints" 가 이 뜻이라고 설명했다. 새 컴파일러만 있으면 되고 runtime 이나 standard library 의 특정 버전에 기대지 않는다는 말이다.

wadetregaskis 는 방향에 동의하고 다섯 가지를 물었다(리뷰 #5).

- `nonisolated init() async` 가 `x1` 을 직접 대입하면 `x1` 의 기본값은 쓸 데가 없지 않느냐는 질문이다. 앞의 저장 프로퍼티 절에서 본 대로 같은 class 에 `@MainActor` init 이 있으면 거기서 쓰인다.
- 평가 순서 설명이 지금 규칙인지 이 제안이 만드는 규칙인지 물었다. 이것도 앞 절에서 다뤘다.
- 왜 isolated 인 것만이 아니라 모든 기본 인자를 callee 의 isolation 에서 평가하느냐고 물었다. 이유로 두 가지를 들었다. 하나는 성능이다. 기본값 계산이 무거우면 callee 쪽으로 옮기는 편이 병렬성에 도움이 될 수 있지만, callee 가 main actor 같은 곳이면 오히려 해로울 수 있다. 다른 하나는 예측 가능성이다. isolated 인 것만 순서를 벗어나게 하면 nonisolated 기본값을 누가 평가하는지가 호출 지점에만 달려 있어서, callee 선언이 바뀌어도 영향이 없다.
- 서로 다른 actor 를 요구하는 기본값만 있는 타입에 컴파일러가 async init 을 합성해 주면 어떻겠냐고 물었다. 앞의 합성 init 절에서 다뤘다.
- `func foo(x: Int = requiresMainActor(), y: Int = requiresOtherGlobalActor())` 처럼 기본값이 서로 다른 actor 를 요구하는 함수가 어디서든 쓸 수 있는 것인지, 아예 금지인지 물었다.

Holly 의 답은 이렇다(리뷰 #6). 모든 기본 인자를 옮기는 이유는 기본 인자끼리는 항상 순서를 지키는 편이 이해하기 쉽기 때문이다. 기본 인자의 isolation 은 코드에 적혀 있지 않아서, 어느 인자가 옮겨지는지 프로그래머가 알아내기 어렵다. 순서 차이는 `inout` 인자가 끼어야 겨우 보인다. isolated 인 것만 옮기는 대안, 즉 r-value 인자, formal access 와 nonisolated 기본 인자, hop, isolated 기본 인자 순으로 평가하는 방식도 구현은 가능하고 Language Steering Group 이 원하면 그렇게 할 수 있다고 했다. 다만 더 낫다고 확신하지는 않는다고 덧붙였다. 성능 걱정에는, 대부분의 기본 인자는 리터럴, 상수, init 정도라서 비싸지 않고, isolated 기본 인자가 있는 함수는 다른 actor 의 isolated 문맥에서 부르는 일이 흔해서 caller 쪽에서 nonisolated 인자를 평가해도 actor 를 풀어 주는 효과가 늘 있지는 않다고 답했다. 가장 중요한 것은 isolation 경계로의 hop 이 한 번뿐이라는 점이고, 그 성질만 지키면 다른 해법도 괜찮다고 했다. 서로 다른 actor 를 요구하는 기본값 예시는 "nonisolated 함수의 기본값은 nonisolated 여야 한다" 는 제한 때문에 잘못된 코드라고 답했다.

wadetregaskis 는 몇 가지를 더 말했다(리뷰 #7). 다른 init 이 하나도 없는데 기본값이 아무 데서도 안 쓰이는 타입이라면 `final` 이나 `frozen` 처럼 알 수 있는 경우에 경고가 있으면 좋겠다고 했다. 평가 순서 경위는 앞에서 본 대로 순서가 덜 중요하다는 근거로 받았다. 성능 논의에서는 init 의 경우 caller 와 callee 가 어차피 직렬이라 차이가 없다고 정리했다. init 이 아닌 경우는 어느 쪽이 나은지 말하기 어렵고, "global isolation 도메인 밖에서 먼저 평가한다" 같은 규칙은 영리한지 끔찍한지 바로 판단이 안 선다고 했다. 또 isolation 도메인 사이의 hop 은 오버헤드가 작지 않다고 관찰했고, hop 을 최소로 한다는 데 동의했다. 마지막으로 서로 다른 actor 를 요구하는 기본값이 아예 금지인 것이 의외라고 했다. 저장 프로퍼티는 isolation 에 묶인 채로 다른 isolation 의 init 에서 직접 초기화하는 길이 열려 있는데 함수 쪽은 그렇지 않아서 어긋난다는 것이다. 이번 제안에서는 미뤄도 괜찮다고 했고, 이 건은 이후 개정의 todo 로 남았다.

## 개선했을 때의 기대 효과

이 제안의 효과는 두 방향이다. 숨어 있던 위반이 컴파일 시점으로 올라오는 것, 그리고 안전한 코드가 막히지 않는 것이다. 이 글에서 직접 돌려 본 것만 모았다.

- `main.swift`: Swift 5 모드에서는 `@MainActor` 함수가 main thread 밖에서 진단 없이 실행됐다(`on main thread: false`). Swift 6 모드에서는 같은 코드가 빌드되지 않는다.
- `CrossInit.swift`: isolated 프로퍼티를 경계 밖에서 초기화하는 코드가 Swift 5 에서는 warning, Swift 6 에서는 error 다.

안전한 코드가 통과하는 쪽은 error 개수로 비교했다.

| 파일 | Swift 5 모드 | Swift 6 모드 |
| --- | --- | --- |
| `DefaultArg.swift` | error 2개 (3 번째, 14 번째 줄) | error 1개 (14 번째 줄) |
| `Closure.swift` | error 2개 (5 번째, 13 번째 줄) | error 1개 (12 번째 줄) |
| `Synth.swift` | error 2개 (12 번째, 15 번째 줄) | error 1개 (15 번째 줄) |

`DefaultArg.swift` 에서 사라진 3 번째 줄은 `@MainActor` 함수의 기본 인자에서 `@MainActor` 타입을 만드는, 정말 안전한 코드였다. `Synth.swift` 에서 사라진 12 번째 줄은 `Sendable` 프로퍼티만 가진 `MyView()` 였다. 남은 error 들은 nonisolated 동기 함수에서 `@MainActor` 함수나 init 을 진짜로 동기 호출한 줄이라서, 실제로 위험한 호출만 남았다.

## Swift 6 언어 모드와 마이그레이션

Swift 6 언어 모드에서는 `IsolatedDefaultValues` 가 기본으로 켜진다. Swift 5 모드에서 미리 켜려면 컴파일러에 `-enable-upcoming-feature IsolatedDefaultValues` 를 주면 되고, SwiftPM 에서는 `.enableUpcomingFeature("IsolatedDefaultValues")` 를 쓴다.

Swift 5 모드에 이 flag 만 켜고 앞의 파일들을 `-emit-sil` 로 돌려 봤다. `Stored.swift`, `Closure.swift`, `Mixed.swift`, `Synth.swift` 가 Swift 6 모드와 같은 진단을 낸다. 그리고 이것들은 warning 이 아니라 error 다.

```text
Stored.swift:10:25: error: return from initializer without initializing all stored properties
Closure.swift:12:5: error: main actor-isolated default value in a nonisolated context
Mixed.swift:4:23: error: global actor 'AnotherActor'-isolated default value in a main actor-isolated context
Synth.swift:15:13: error: call to main actor-isolated initializer 'init()' in a synchronous nonisolated context [#ActorIsolatedCall]
```

`DefaultArg.swift` 도 14 번째 줄 error 하나로 Swift 6 모드와 같다.

flag 를 켜면 무엇이 깨질까. 기본 인자 쪽은 깨지는 코드가 없고 규칙이 풀리기만 한다. `DefaultArg.swift` 는 3 번째 줄 error 가 사라지고 14 번째 줄은 원래부터 error 였다. `Closure.swift` 는 5 번째, 13 번째 줄이던 error 가 12 번째 줄 하나로 모이는데, 이는 풀린 것과 위치가 옮겨진 것이지 새로 생긴 error 가 아니다. `Mixed.swift` 는 Swift 5 모드에서도 error 였고 위치만 호출 줄에서 파라미터로 옮겨졌다. isolated 기본 인자는 예전에 허용되지 않았으니 조용히 다르게 돌던 코드도 없다. 깨지는 것은 저장 프로퍼티 쪽이다. `Stored.swift` 와 `main.swift` 는 Swift 5 모드에서 진단 없이 빌드되고 돌았던 코드라서, flag 를 켜면 처음으로 error 가 나온다. 켜 보려면 빌드가 깨져도 되는 브랜치에서 시도하는 것이 좋다.

마이그레이션에서 가장 자주 만날 모양은 `nonisolated init` 이 있는 class 에 `@MainActor` 프로퍼티와 isolated 기본값이 함께 있는 경우다. 직접 만든 `@MainActor` 타입으로 확인했다. `Formatter2` 의 init 은 `@MainActor` 다.

```swift
@MainActor final class Formatter2 {
    init() {}
    func format(_ n: Int) -> String { "\(n)" }
}

final class ViewModelA {
    @MainActor var formatter = Formatter2()
    nonisolated init() {}
}
```

`ViewModelA` 는 Swift 6 모드에서 `Stored.swift` 와 같은 모양의 error(`return from initializer without initializing all stored properties`)가 난다. 고치는 길은 앞에서 본 것과 같다. 셋 모두 Swift 6 모드에서 진단 없이 통과했다.

```swift
final class ViewModelB {
    @MainActor var formatter = Formatter2()
    @MainActor init() {}
}

final class ViewModelC {
    @MainActor var formatter: Formatter2
    nonisolated init() async {
        self.formatter = await Formatter2()
    }
}

@MainActor final class ViewModelD {
    var formatter = Formatter2()
}
```

`ViewModelB` 는 init 을 `@MainActor` 로 해서 초기값이 끼워지게 했다. 대신 만드는 쪽이 main actor 위에 있어야 한다. `ViewModelC` 는 init 을 `async` 로 하고 init 안에서 `await` 로 대입했다. `ViewModelD` 는 class 전체를 `@MainActor` 로 해서 프로퍼티와 init 이 모두 같은 isolation 이 되게 했다. 대개는 마지막이 제일 간단하다.

기본 인자 쪽은 `@MainActor` 값을 쓰는 함수를 main actor 밖에서 부를 때 `await` 를 붙이거나 부르는 함수를 `@MainActor` 로 옮기면 된다. 앞의 `DefaultArg.swift` 에서 본 `nonisolatedCaller` 가 그 모양이다.

한 가지 더 알아 둘 점이 있다. 앞의 `Stored.swift` 에서 본 대로 `-typecheck` 만 돌려서는 이 종류의 error 가 보이지 않는다. 그리고 타입 검사 단계에서 다른 error 가 하나라도 있으면 SIL 단계의 진단이 아예 나오지 않을 수 있다. 마이그레이션 중에는 error 를 고쳐서 다시 빌드했을 때 새 error 가 나타나는 일이 이 때문에 생긴다.

## 정리

- 기본값 식(기본 인자와 저장 프로퍼티 초기값)이 둘러싼 함수나 프로퍼티와 같은 actor isolation 을 가질 수 있다. 필요한 isolation 은 식 안에서 동기로 부르는 호출에서 추론된다.
- 기본 인자는 부르는 쪽에서 isolation 을 검사한다. isolated 기본 인자가 있으면 hop 을 한 번으로 모으려고 기본 인자가 인자 평가 순서의 맨 뒤로 간다. 직접 돌려서 확인했다.
- 저장 프로퍼티 초기값은 init 과 isolation 이 같을 때만 끼워진다. isolation 이 다른 init 에서는 초기값이 끼워지지 않으니, 본문에서 직접 대입하지 않으면 `Stored.swift` 처럼 error 가 난다. 이 error 는 `-emit-sil` 로만 보인다.
- 합성 init 은 non-Sendable isolated 프로퍼티나 isolated 기본값이 없으면 `nonisolated` 가 된다. 그래서 단순한 `@MainActor` struct 는 어디서든 만들 수 있다.

앱에서 가장 먼저 만나는 모양은 `@MainActor final class ViewModel { var formatter = SomeMainActorFormatter() }` 처럼 `@MainActor` 프로퍼티에 `@MainActor` 타입을 기본값으로 둔 class 다. 그 class 에 `nonisolated init` 이 있으면 Swift 6 에서 걸린다. 대개는 class 전체에 `@MainActor` 를 붙이거나 init 을 `@MainActor` 로 하는 것으로 정리된다.
