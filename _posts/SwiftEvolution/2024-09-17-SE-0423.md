## 한 줄 요약

컴파일할 때 검사받지 않은 코드가 actor 에 묶인 동기 함수를 엉뚱한 thread 에서 부르면, 조용히 data race 를 내는 대신 그 자리에서 프로그램을 멈추게 한다. 검사는 그럴 위험이 있는 경계에만 넣는다. 6.4 에서 검사가 들어가는 곳은 `@preconcurrency` 를 붙인 protocol conformance 의 witness, isolation 을 지우는 함수 값, Objective-C 로 내보낸 메서드 세 곳이다.

---

## 어떤 문제였나

Swift 6 의 정적 검사는 컴파일러가 소스를 볼 수 있는 모듈 안만 지켜 준다. Swift 5 모드로 빌드된 라이브러리, Objective-C, C 로 쓴 프레임워크는 컴파일러가 안을 검사하지 못하고, "이 delegate(어떤 일이 생기면 대신 불러 달라고 맡겨 두는 객체)는 항상 main thread 에서 부른다" 같은 약속을 문서로만 한다. 약속을 믿고 `@MainActor` 클래스로 delegate 를 만든 앱이 있는데, 라이브러리에 버그가 있어 다른 thread 에서 delegate 를 부르면 어떻게 될까. 컴파일러는 모르고, 런타임도 막지 않고, main thread 에서만 건드린다고 믿었던 상태가 조용히 깨진다.

Airbnb 의 cal 이 1차 리뷰에서 비슷한 경험을 적었다(리뷰 #3). 기존 feature 코드에 concurrency 를 도입하려 했을 때 처음 부딪힌 큰 장애물 가운데 하나가 이것이었다고 한다. 타입을 concurrency-safe 하게 만드는 가장 쉬운 방법이 `@MainActor` 였는데, 그 때문에 이미 있던 protocol 에 대한 conformance 를 쉽게 구현할 수 없었다는 이야기다.

---

### actor isolation 과 main actor 란?

actor 는 자기 안의 상태를 한 번에 한 코드만 만지게 해 주는 타입이다. 은행 창구에서 번호표를 뽑고 한 명씩 들어가는 것과 같다. 이렇게 상태를 보호받는 것을 actor isolation(격리)이라고 하고, 프로그램 전체에 하나뿐인 actor 를 이름으로 가리키는 장치가 global actor 다. 대표가 main thread 에 대응하는 `@MainActor` 다. 선언에 `@MainActor` 를 붙이면 "이것은 main actor 의 창구 안에 있다" 는 표시가 되고, 다른 곳에서 그것을 쓰려면 창구에 줄을 서야 한다. 비동기 코드에서 그 줄서기가 `await` 다.

이 글에서 가장 중요한 사실은 동기 함수에는 줄 설 방법이 없다는 점이다. `await` 가 없으니, `@MainActor` 에 묶인 동기 함수는 부르는 쪽이 이미 main actor 위에 있어야만 부를 수 있다. 창구 안에 이미 들어와 있는 사람만 창구 안의 일을 할 수 있는 것이다. 컴파일러는 그 조건을 부르는 코드마다 따져서 막아 준다. 문제는 컴파일러가 그 코드를 볼 수 없을 때다. actor 의 자세한 설명은 이 시리즈의 [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/)에 있다.

---

### Swift 언어 모드와 upcoming feature flag 란?

이 글에서 "Swift 5 모드" 와 "Swift 6 모드" 는 컴파일러 버전이 아니라 언어 모드다. 컴파일러는 Xcode 27 에 들어 있는 Swift 6.4 하나인데, 같은 컴파일러가 `-swift-version 5` 를 받으면 옛 규칙으로, `-swift-version 6` 을 받으면 새 규칙으로 코드를 검사한다. 같은 시험관이 채점 기준표를 두 벌 갖고 있는 것과 같다. Xcode 의 빌드 설정에서는 Swift Language Mode 가 이 옵션이다.

언어 모드와는 별개로 concurrency 검사의 강도를 고르는 `-strict-concurrency` 옵션이 있다. `minimal` 은 concurrency 를 명시적으로 쓴 코드만 검사하고, `targeted` 는 `Sendable` 제약의 검사를 그 범위까지 넓히며, `complete` 는 Swift 6 와 같은 수준으로 모든 코드를 검사한다. Swift 5 모드의 기본값은 `minimal` 이다. 이 글에서 "Swift 5 complete" 는 Swift 5 모드에 `-strict-concurrency=complete` 를 준 상태를 가리킨다. 단계별 설명은 [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/)에 있다.

기준표를 통째로 바꾸지 않고 한 문항만 먼저 새 기준으로 채점해 보는 스위치가 upcoming feature flag 다. `-enable-upcoming-feature DynamicActorIsolation` 처럼 쓴다. 이 글의 표현으로 "Swift 5 + flag" 는 Swift 5 모드에 이 제안서의 동적 검사만 미리 켠 상태를 가리킨다.

### data race 란?

data race 는 두 thread 가 같은 메모리에 동시에 접근하는데 그중 하나 이상이 값을 쓰고 있고, 순서를 정해 주는 장치가 없는 상황이다. 겉으로는 평범한 코드인데 결과가 실행할 때마다 달라진다. 공용 게시판에 "방문자 수: 10" 이라고 적혀 있을 때 두 사람이 동시에 와서 둘 다 10 을 읽고 각자 11 을 적으면, 방문자는 둘인데 게시판은 11 이다. main actor 에 묶은 상태가 지키려는 것이 바로 이런 사고이고, main thread 말고 다른 thread 에서 그 상태를 건드리면 같은 일이 생긴다.

### 약속만 있는 라이브러리

문제를 재현하려고 라이브러리를 하나 만들었다. 이 라이브러리는 "요구사항은 항상 main thread 에서 부른다" 고 약속하는 protocol 을 제공하는데, 일부러 약속을 어기는 함수도 하나 넣었다. 제안서의 `NotMyLibrary` 예를 코드로 옮긴 것이다. Swift 5 모드로 빌드한다.

```swift
import Foundation

public protocol ViewDelegateProtocol {
  func respondToUIEvent()
}

// 약속을 어기는 버그: 다른 thread 에서 delegate 를 부른다.
public func fireEventFromBackground(_ delegate: ViewDelegateProtocol) {
  let done = DispatchSemaphore(value: 0)
  Thread.detachNewThread {
    delegate.respondToUIEvent()
    done.signal()
  }
  done.wait()
}

// 받은 closure 를 다른 thread 에서 부르는 API.
public func track(_ callback: @escaping () -> Void) {
  let done = DispatchSemaphore(value: 0)
  Thread.detachNewThread {
    callback()
    done.signal()
  }
  done.wait()
}
```

#### Thread.detachNewThread와 DispatchSemaphore로 다른 thread 에서 부르기

1. [`Thread.detachNewThread(_:)`](https://developer.apple.com/documentation/foundation/thread/detachnewthread%28_:%29){:target="_blank"} 는 새 thread 를 만들고 넘겨 준 closure 를 그 thread 에서 실행한다. 이 글의 모든 실험이 "main thread 가 아닌 곳에서 부르는 라이브러리" 를 흉내 내려고 이것을 쓴다. 호출한 쪽은 기다리지 않고 바로 돌아온다.
2. [`DispatchSemaphore`](https://developer.apple.com/documentation/dispatch/dispatchsemaphore){:target="_blank"} 는 thread 사이에서 "끝났다" 는 신호를 주고받는 장치다. [`DispatchSemaphore(value:)`](https://developer.apple.com/documentation/dispatch/dispatchsemaphore/init%28value:%29){:target="_blank"} 에 0 을 주면 신호가 하나도 없는 상태로 시작한다. [`wait()`](https://developer.apple.com/documentation/dispatch/dispatchsemaphore/wait%28%29){:target="_blank"} 는 신호가 올 때까지 현재 thread 를 멈춰 세우고, [`signal()`](https://developer.apple.com/documentation/dispatch/dispatchsemaphore/signal%28%29){:target="_blank"} 은 신호를 하나 보낸다. 위 코드에서 main thread 는 `done.wait()` 에서 기다리고, 새 thread 는 일을 마친 뒤 `done.signal()` 로 깨운다. 실험 프로그램이 새 thread 의 일이 끝나기 전에 끝나 버리지 않게 하려고 썼다.

`fireEventFromBackground(_:)` 가 `delegate.respondToUIEvent()` 를 새 thread 에서 부르는 것이 "라이브러리의 버그" 다. 문서에는 main thread 에서 부른다고 적혀 있겠지만 코드는 그렇지 않다. `track(_:)` 는 받은 closure 를 마찬가지로 다른 thread 에서 부른다.

이 라이브러리를 이렇게 빌드해서 클라이언트가 `import NotMyLibrary` 로 쓰게 했다. `-swift-version 5` 로 만든 `libNotMyLibrary.a` 와 모듈 파일이 나온다.

```bash
xcrun swiftc -parse-as-library -swift-version 5 -emit-library -static -emit-module \
    -module-name NotMyLibrary NotMyLibrary.swift -o libNotMyLibrary.a
```

### @preconcurrency 없이 conformance 를 쓰면

클라이언트는 이 protocol 을 `@MainActor` 클래스로 구현하고 싶다. 앱의 view controller 는 대개 main actor 에 있기 때문이다.

```swift
import NotMyLibrary

@MainActor
class MyViewController: ViewDelegateProtocol {
  func respondToUIEvent() {
    print("respondToUIEvent")
  }
}
```

이 글의 진단은 모두 `-emit-sil` 로 뽑았다. `-emit-sil` 은 타입 검사 뒤 SIL(컴파일러 중간 표현) 단계까지 컴파일해서 그 단계에서 나오는 진단까지 빠짐없이 낸다. 타입 검사까지만 하는 `-typecheck` 는 SIL 단계의 진단을 빼먹는다. `-o /dev/null` 은 결과 파일을 버리고, `-parse-as-library` 는 파일을 최상위 코드가 없는 일반 소스 파일로 다루라는 옵션이다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 5 -I lib conf/Plain.swift
```

Swift 5 모드의 결과다.

```text

2 | 
3 | @MainActor
4 | class MyViewController: ViewDelegateProtocol {
  |                         |- warning: conformance of 'MyViewController' to protocol 'ViewDelegateProtocol' crosses into main actor-isolated code and can cause data races; this is an error in the Swift 6 language mode [#ConformanceIsolation]
  |                         |- note: isolate this conformance to the main actor with '@MainActor'
  |                         `- note: turn data races into runtime errors with '@preconcurrency'
5 |   func respondToUIEvent() {
  |        |- note: main actor-isolated instance method 'respondToUIEvent()' cannot satisfy nonisolated requirement
  |        `- note: mark instance method 'respondToUIEvent()' 'nonisolated'
6 |     print("respondToUIEvent")
7 |   }

```

`-swift-version 6` 으로 검사하면 같은 내용이 error 로 나온다. "this is an error in the Swift 6 language mode" 꼬리만 사라지고 note 는 그대로다.

```text
conf/Plain.swift:4:25: error: conformance of 'MyViewController' to protocol 'ViewDelegateProtocol' crosses into main actor-isolated code and can cause data races [#ConformanceIsolation]
```

이유는 이렇다. protocol 요구사항 `respondToUIEvent()` 는 isolation 표시가 없는 nonisolated 함수라서 "어느 thread 에서든 부를 수 있다" 는 뜻이다. 그런데 `MyViewController` 의 구현은 main actor 에 묶여 있어서 main actor 위에서만 불려야 한다. 어느 thread 에서든 부를 수 있다는 약속을 main actor 에서만 부를 수 있는 구현이 채우면, 제네릭 코드가 다른 thread 에서 부르는 순간 data race 다. 컴파일러가 이 conformance 를 막는 것이 옳다.

note 세 개가 고칠 길 세 가지를 그대로 보여 준다.

| note | 의미 |
| --- | --- |
| `isolate this conformance to the main actor with '@MainActor'` | conformance 자체를 main actor 에 묶는다. protocol 을 쓰는 쪽도 main actor 위에서만 이 conformance 를 쓰게 된다. [SE-0470](https://haroldfromk.github.io/posts/SE-0470/) 이 다루는 isolated conformance 다 |
| `turn data races into runtime errors with '@preconcurrency'` | 컴파일 때의 막음을 풀고, 위반이 생기면 런타임에 멈추게 한다. 이 제안서가 다루는 길이다 |
| `mark instance method 'respondToUIEvent()' 'nonisolated'` | 구현을 nonisolated 로 바꿔서 어느 thread 에서든 불려도 되게 한다. 그러면 안에서 main actor 상태를 못 건드린다 |

첫째 길은 라이브러리가 "main actor 에서 부른다" 는 약속을 타입 시스템에 올려 둔 경우에 맞고, 셋째 길은 구현이 정말 thread 와 무관할 때 맞는다. 라이브러리가 Swift 5 로 쓰였고 문서의 약속만 믿어야 하는 이 글의 상황에 맞는 것은 둘째 길이다.

### @preconcurrency 란?

[SE-0337](https://haroldfromk.github.io/posts/SE-0337/) 이 `@preconcurrency import` 를 들여왔다. 아직 concurrency 정보가 없는 모듈을 import 하면서, 그 모듈의 선언 때문에 나오는 concurrency 진단을 가라앉히는 장치다. 아직 고쳐지지 않은 남의 코드 때문에 내 빌드가 막히지 않게 해 준다.

이 제안서의 Motivation 은 거기서 빠진 자리를 지적한다. `@preconcurrency` 는 import 에만 있어서, protocol conformance 에는 쓸 수가 없었다. 위 `Plain.swift` 의 error 를 가라앉힐 방법이 `nonisolated` 와 `MainActor.assumeIsolated` 로 직접 감싸는 것밖에 없었다는 뜻이다. 이 제안서로 conformance 에 붙이는 문법이 들어왔다.

```swift
@MainActor
class MyViewController: @preconcurrency ViewDelegateProtocol {
  var count = 0
  func respondToUIEvent() {
    count += 1
    print("respondToUIEvent, count = \(count)")
  }
}
```

protocol 이름 앞에 `@preconcurrency` 를 쓴다. 제안서는 이 표시가 conformance 안의 요구사항 구현에만 적용된다고 하고, primary declaration 에도 extension 에도 쓸 수 있다고 한다. witness 를 검사하는 컴파일러가 내던 actor isolation 진단은 사라지고, 대신 아래에서 볼 런타임 검사가 witness 에 들어간다.

### 동적 검사가 없는 Swift 5 모드의 조용한 data race

동적 검사가 꺼진 Swift 5 모드의 모양을 보려고, 위 클래스에 실행 코드를 붙인 파일을 Swift 5 모드로 빌드해서 실행했다.

```swift
import NotMyLibrary

@MainActor
class MyViewController: @preconcurrency ViewDelegateProtocol {
  var count = 0
  func respondToUIEvent() {
    count += 1
    print("respondToUIEvent, count = \(count)")
  }
}

@main
struct App {
  @MainActor static func main() {
    let vc = MyViewController()
    vc.respondToUIEvent()          // main actor 에서 직접: 괜찮다
    print("이제 라이브러리가 다른 thread 에서 부른다")
    fireEventFromBackground(vc)    // 라이브러리의 버그
    print("끝")
  }
}
```

#### @main과 MainActor로 실행 진입점을 main actor 에 두기

[`@main`](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} 은 이 타입의 `static func main()` 을 프로그램의 시작점으로 삼는다. `-parse-as-library` 로 빌드하는 파일에서 최상위 코드 대신 이 방식을 쓴다. `main()` 에 [`@MainActor`](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 를 붙여서 시작점이 main actor 위에서 돌게 했고, 그래서 안에서 `MyViewController()` 를 만들고 `vc.respondToUIEvent()` 를 직접 부를 수 있다. 이 직접 호출은 같은 actor 안이라 컴파일러가 허용한다.

```bash
xcrun swiftc -parse-as-library -swift-version 5 -I lib -L lib -lNotMyLibrary conf/Preconcurrency.swift -o app
```

`-I lib` 는 모듈 파일을 찾을 폴더, `-L lib` 은 라이브러리 파일을 찾을 폴더, `-lNotMyLibrary` 는 `libNotMyLibrary.a` 를 링크하라는 뜻이다. Swift 5 와 Swift 6 모두 이 파일의 컴파일 진단은 0 줄이다. 실행 결과는 이렇다.

```text
respondToUIEvent, count = 1
이제 라이브러리가 다른 thread 에서 부른다
respondToUIEvent, count = 2
끝
```

프로세스는 정상 종료(exit 0)한다. 두 번째 `respondToUIEvent` 는 `fireEventFromBackground` 가 만든 다른 thread 에서 실행되었다. main actor 의 상태 `count` 를 main actor 가 아닌 곳에서 건드렸는데 아무 일도 일어나지 않았다. 이것이 조용한 data race 다. 이번에는 두 thread 가 시간차를 두고 접근해서 우연히 값이 맞았을 뿐이고, 같은 코드를 두 thread 가 동시에 돌리게 되면 앞의 게시판 비유처럼 값이 사라진다. 문제가 보이지 않는다는 것이 이 구멍의 가장 나쁜 점이다. 이 제안서는 이 상황을 멈추는 쪽으로 바꾼다.

### witness 와 thunk 란?

witness 는 protocol 요구사항을 채우는 구현이다. `ViewDelegateProtocol` 은 "`respondToUIEvent()` 를 할 수 있어야 한다" 는 요구사항이고, `MyViewController.respondToUIEvent()` 가 그것을 채우는 witness 다. 이름은 어렵지만 "이 타입이 요구사항을 이렇게 채웠다고 증언하는 함수" 라고 보면 된다. 포럼에서 hisekaldma 가 witness 와 thunk 는 구현 용어가 아니냐고, 사용자로서는 읽기 어렵다고 지적했을 때(리뷰 #4) Holly 는 둘을 나누어 답했다(리뷰 #5). protocol witness 는 사용자에게 보이는 언어 의미론의 일부이고 요구사항의 구현을 가리키는 정식 용어다. thunk 는 컴파일러 구현에 더 가깝지만 이 제안서의 동작을 설명하려면 없을 수 없는 말이라서, 쓰이는 자리에서 정의를 더하겠다고 했다.

thunk 는 원래 함수를 감싸서 앞뒤에 일을 더하는 얇은 함수다. 택배 상자를 대신 받아서 열어 보고 안에 전달해 주는 경비실 같은 것이다. protocol 을 통해 부를 때 호출은 먼저 witness thunk 에 도착하고, 그것이 실제 구현을 부른다. 컴파일러가 만드는 함수라서 소스에는 보이지 않는다.

![검사는 메서드 본문이 아니라 protocol 을 통해 들어오는 문인 witness thunk 에만 있다. Swift 에서 직접 호출은 검사 없이 본문으로 가고, 라이브러리의 호출은 witness thunk 의 _checkExpectedExecutor 를 거쳐 본문으로 간다. 아래 요약에는 _checkExpectedExecutor 개수가 Swift 5 모드 0개, Swift 5 + flag 1개, Swift 6 모드 1개로 적혀 있다.](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-09-17-SE-0423/se-0423-witness-thunk.png)

이 제안서가 검사를 넣는 곳이 바로 이 thunk 다. 메서드 본문은 그대로 두고 문 앞에 검사를 세운다. 그래서 Swift 에서 `vc.respondToUIEvent()` 를 직접 부를 때는 thunk 를 거치지 않으니 검사 비용이 없다.

### @preconcurrency conformance 의 witness 검사

앞의 `Preconcurrency.swift` 를 Swift 6 모드로 빌드해서 실행하면 다른 thread 에서 부르는 순간 멈춘다. 그런데 멈춘 프로그램의 출력은 파이프나 파일로 받으면 사라진다. 터미널이 아닌 곳으로 나가는 출력은 프로그램이 buffer(내보낼 글자를 잠시 모아 두는 메모리 덩어리)에 모아 두었다가 한꺼번에 내보내는데, 프로세스가 비정상으로 멈추면 아직 내보내지 못한 몫이 그대로 사라지기 때문이다. `./app | cat` 으로 돌렸더니 `respondToUIEvent, count = 1` 줄까지 사라져서 아무것도 나오지 않았고, zsh 의 `pipestatus` 로 본 `./app` 의 종료 코드만 133 이었다. 파이프를 쓰면 `$?` 는 마지막 명령인 `cat` 의 종료 코드(0)를 담기 때문이다. 터미널에서 직접 돌리면 앞의 두 줄은 보인다. 그래서 lldb 로 돌린다. lldb 는 프로그램에 터미널(pty)을 주므로 출력이 남고, `-k` 는 프로세스가 멈춘 뒤에 실행할 명령이다.

```bash
xcrun lldb --batch -o run -k bt -k quit ./app
```

두 번째 `respondToUIEvent` 의 `count = 2` 는 출력되지 않았다. `thread #2` 는 `Thread.detachNewThread` 가 만든 thread 이고, 그 thread 에서 witness 에 들어서자마자 `EXC_BREAKPOINT` 로 멈춘 것이다. `EXC_BREAKPOINT` 는 CPU 의 breakpoint 명령(arm64 의 `brk #0x1`)이 일으키는 Mach 예외(커널이 프로세스에 알리는 저수준 예외)이고, 운영체제가 이를 SIGTRAP 신호(5번)로 프로세스에 전달한다. 그래서 lldb 없이 직접 실행하면 종료 코드가 128 에 5 를 더한 133 이다. 오류 문구는 출력되지 않았고, `./app 2>&1 | cat` 으로 stderr 까지 모아 봐도 빈 화면이었다. 멈춘 자리를 알려 주는 것은 backtrace 다. backtrace 는 멈춘 순간의 함수 호출 사슬을 거슬러 적은 목록이고, 줄 하나가 함수 호출 하나인 frame 이다. `frame #0` 이 멈춘 자리이고 번호가 클수록 먼저 불린 함수다.

아래에서 위로 따라가면 일이 일어난 순서가 된다. #10 과 #9 는 새 thread 가 시작되는 부분이고, #7 이 라이브러리의 `fireEventFromBackground(_:)` 안에 있는 closure, 곧 버그가 있는 호출이다. #6 은 컴파일러가 conformance 마다 만드는 protocol witness thunk 이고, 이 제안서는 그 안에서 #5 `_checkExpectedExecutor` 를 부르게 했다. 뒤에서 볼 `assumeIsolated` 판의 backtrace 에도 `protocol witness for` 프레임이 있으니, thunk 자체는 원래 있던 것이고 이 제안서가 그 안에 검사 호출을 넣은 것이다.

#4 와 #3 은 Swift runtime 이 현재 executor 가 맞는지 따지는 자리다. executor 는 actor 의 코드를 실제로 돌려 주는 주체다. actor 가 창구라면 executor 는 창구에서 손님을 한 명씩 받는 직원이다. main actor 의 executor 는 main dispatch queue 다. dispatch queue 는 libdispatch(Apple 이 만든 동시 실행 라이브러리, 흔히 GCD 라고 부른다)가 일감을 줄 세워 하나씩 돌려 주는 대기열이고, main dispatch queue 는 main thread 에서만 일감을 처리하는 대기열이다. #2 와 #1 과 #0 은 libdispatch 가 "지금 이 대기열 위인가" 를 확인하다 실패하는 자리다. 크래시 보고서에서 가장 알고 싶은 정보, 곧 누가 부른 것인지가 #7 에 그대로 보인다.

SIL 에서 센 개수와 위치도 같은 이야기를 한다. `_checkExpectedExecutor` 는 `respondToUIEvent()` 본문이 아니라 witness thunk 안에만 있다.

```text
sil private [transparent] [thunk] @protocol witness for NotMyLibrary.ViewDelegateProtocol.respondToUIEvent() -> () in conformance main.MyViewController : NotMyLibrary.ViewDelegateProtocol in main : $@convention(witness_method: ViewDelegateProtocol) (@in_guaranteed MyViewController) -> () {
```

모드와 옵션마다 `_checkExpectedExecutor` 개수와 실행 결과를 정리하면 이렇다. 6.4 에서 각각 빌드해서 센 값이다.

| 빌드 | 검사 개수 | 실행 |
| --- | --- | --- |
| Swift 5 | 0 (`-strict-concurrency=complete` 도 0) | `count = 2` 와 `끝` 까지 가서 exit 0 |
| Swift 5 + `DynamicActorIsolation` | 1 | 다른 thread 에서 멈춤, exit 133 |
| Swift 6 | 1 | 다른 thread 에서 멈춤, exit 133 |
| Swift 6 + `-disable-dynamic-actor-isolation` | 0 | `count = 2` 와 `끝` 까지 가서 exit 0 |

제안서의 Source compatibility 절은 기존 프로그램을 지키려고, 동적 검사를 명시적으로 `@preconcurrency` 를 붙인 conformance 의 witness 나 Swift 6 언어 모드에서 컴파일한 코드에만 넣는다고 쓴다. 6.4 에서 Swift 5 모드로 측정하면 `@preconcurrency` conformance 를 명시했어도 flag 를 켜기 전에는 검사가 0개이고, flag 를 켜면 1개가 된다.

`@preconcurrency` 는 그것이 억누를 진단이 없으면 아무 효과가 없다. 그런 경우 제안서는 "has no effect" warning 을 내라고 한다. isolated 가 아닌 평범한 클래스에 붙여 봤다.

```swift
public protocol Greeter {
  func greet()
}

final class Plain: @preconcurrency Greeter {
  func greet() { print("hi") }
}
```

제안서는 모듈 안에서는 컴파일러가 계속 진단을 낸다고도 쓴다. `@preconcurrency` conformance 를 해 둔 `Screen` 을 같은 모듈의 isolation 없는 함수에서 직접 부르는 경우다.

### 손으로 쓰던 MainActor.assumeIsolated 와의 관계

이 제안서 이전에 쓰던 방법은 제안서의 Motivation 에 나온다. 구현을 `nonisolated` 로 바꾸고 안을 `MainActor.assumeIsolated` 로 감싸는 것이다.

```swift
import NotMyLibrary

@MainActor
class MyViewController: ViewDelegateProtocol {
  var count = 0
  nonisolated func respondToUIEvent() {
    MainActor.assumeIsolated {
      count += 1
      print("respondToUIEvent, count = \(count)")
    }
  }
}

func callFromAnywhere(_ vc: MyViewController) {
  vc.respondToUIEvent()   // nonisolated 라서 컴파일러가 막지 않는다
}
```

#### MainActor.assumeIsolated로 main actor 위라고 가정하기

[`MainActor.assumeIsolated(_:file:line:)`](https://developer.apple.com/documentation/swift/mainactor/assumeisolated%28_:file:line:%29){:target="_blank"} 는 "지금 main actor 위에서 돌고 있다" 고 가정하고 closure 를 실행한다. 컴파일러는 그 가정을 믿어 주고 closure 안에서 main actor 상태를 만지게 해 준다. 가정이 틀렸는지는 런타임에 확인해서 틀리면 프로그램을 멈춘다. `file` 과 `line` 은 기본값이 있는 인자라서 평소에는 쓰지 않는다.

Swift 5 와 Swift 6 모두 이 파일의 컴파일 진단은 0 줄이다. 다른 thread 에서 부르는 실행 파일로 만들어 돌리면 backtrace 의 #5 가 `static MainActor.assumeIsolated(_:file:line:)`, #6 이 `MyViewController.respondToUIEvent()`, #7 이 `protocol witness for ViewDelegateProtocol.respondToUIEvent() in conformance MyViewController` 이다. 검사가 closure 입구인 `assumeIsolated` 에서 일어나고 그 아래로 같은 runtime 함수들이 이어진다. 이 제안서가 컴파일러에게 시키는 일은 이 손 작업과 같은 검사를 witness thunk 에 자동으로 넣는 것이다. 제안서가 function value 변환을 설명하면서 `MainActor.assumeIsolated` 를 쓰는 closure 로 풀어 쓰는 것도 같은 맥락이다.

차이는 두 가지다. 먼저 모든 witness 마다 `nonisolated` 를 붙이고 안을 감싸는 수고가 사라진다. 그리고 손으로 쓰는 방법에서는 `callFromAnywhere` 처럼 같은 모듈의 코드도 isolation 없이 `vc.respondToUIEvent()` 를 부를 수 있다. `nonisolated` 라서 컴파일러가 막지 않기 때문이다. 이 제안서의 방식은 구현이 main actor 에 묶인 채로 남으므로 앞의 `InModule.swift` 처럼 같은 모듈의 잘못된 호출은 계속 error 로 막힌다. 제안서가 "프로그래머가 자신의 코드에서 정적 data-race 안전을 잃는다" 고 지적한 부분이다.

### Sendable과 @Sendable이란?

함수 값 이야기에는 `Sendable` 이 계속 나온다. 먼저 isolation domain 부터 보자. isolation domain 은 "같은 규칙으로 보호받는 영역"이다. main actor 는 하나의 domain 이고, actor 인스턴스마다 domain 이 하나씩 있으며, isolation 이 없는 코드는 어느 domain 에도 묶이지 않은 채 아무 thread 에서나 돈다.

`Sendable` 은 값을 domain 사이로 안전하게 넘길 수 있다는 표시다. 회의 인쇄물과 공용 화이트보드로 비유하면 쉽다. 인쇄물은 사람마다 한 장씩 복사해 나누어 주니 누가 낙서를 해도 남에게 영향이 없다. 그래서 어느 방으로 가져가도 안전하다. 이것이 `Sendable` 이다. 공용 화이트보드는 한 장을 여럿이 같이 쓰니 두 사람이 동시에 지우고 쓰면 엉킨다. 이것이 `Sendable` 이 아닌 값이다. 같은 방 안에서만 쓰기로 해야 한다.

`@Sendable` 은 함수와 closure 에 붙이는 같은 종류의 표시다. `@Sendable` 함수는 어느 domain 으로 보내도 안전한 함수라서, 캡처하는 값도 `Sendable` 이어야 하고 isolation 을 안에서 가정하지 못한다. 반대로 `@Sendable` 이 없는 함수는 지금 있는 domain 안에서만 쓰기로 한 함수다.

### isolation 을 지우는 함수 값

두 번째 경계는 함수 값이다. 라이브러리 API 가 `() -> Void` 를 받으면 그 타입에는 `@MainActor` 가 없다. `@MainActor` 함수를 그 자리에 넘기면 컴파일러는 타입에서 isolation 이 지워지는 것을 허용한다. closure 가 `@Sendable` 이 아니니 다른 isolation domain 으로 못 나간다는 이유다. 그런데 그 라이브러리가 Swift 5 모드라서 컴파일러가 라이브러리의 구현을 지켜보지 못하면, "못 나간다" 는 보장이 라이브러리 안에서 깨질 수 있다. 제안서가 `track(view.renderToUIEvent)` 로 든 예가 이것이다. 앞에서 만든 `track(_:)` 가 실제로 그렇게 동작한다.

```swift
import NotMyLibrary

@MainActor
final class Screen {
  var renders = 0
  func render() {
    renders += 1
    print("render, renders = \(renders)")
  }
}

@MainActor
func updateUI(_ screen: Screen) {
  track(screen.render)   // @MainActor 함수를 그냥 () -> Void 자리에 넘긴다
}

@main
struct App {
  @MainActor static func main() {
    let screen = Screen()
    screen.render()
    print("track 에 넘긴다")
    updateUI(screen)
    print("끝")
  }
}
```

컴파일 진단은 모든 모드에서 0 줄이다. 그래도 검사는 들어간다. 검사 개수는 Swift 5 가 0, Swift 5 + flag 가 1, Swift 6 이 1, Swift 6 + `-disable-dynamic-actor-isolation` 이 0 이다. 들어간 자리는 `updateUI` 가 `track(_:)` 를 부르기 전에 `screen.render` 를 감싸는 thunk 다.

```text
sil shared [transparent] [reabstraction_thunk] @reabstraction thunk helper from @escaping @callee_guaranteed () -> () to @escaping @callee_guaranteed () -> () with global actor constraint Swift.MainActor : $@convention(thin) (@guaranteed @callee_guaranteed () -> ()) -> () {
```

"reabstraction thunk" 은 함수 값의 표현을 다른 모양으로 바꿔 주는 thunk 이고, 여기서는 "global actor constraint Swift.MainActor" 가 말하듯 main actor 를 확인하는 일을 겸한다. 제안서가 보여 준 `MainActor.assumeIsolated { view.renderToUIEvent() }` 로 감싸는 변환을 컴파일러가 이 thunk 로 실현한 것이다.

실행 결과는 Swift 5 와 Swift 6 + disable 에서 끝까지 간다.

```text
render, renders = 1
track 에 넘긴다
render, renders = 2
끝
```

`render, renders = 2` 는 `track` 이 만든 다른 thread 에서 실행된 것이다. 같은 프로그램을 Swift 6 이나 Swift 5 + flag 로 빌드해서 lldb 로 돌리면 `track 에 넘긴다` 줄 다음에 `EXC_BREAKPOINT` 로 멈춘다. backtrace 에서 #5 가 `_checkExpectedExecutor`, #6 이 위의 `reabstraction thunk helper ... with global actor constraint Swift.MainActor`, #7 이 `closure #1 in track(_:)` 이다. 라이브러리의 `track` 안 closure 가 thunk 를 부르다 멈췄다는 뜻이고, 책임이 어디 있는지 backtrace 가 알려 준다.

반대로 Swift 6 로 빌드한 라이브러리에 같은 모양으로 넘기면 검사가 들어가지 않는다.

```swift
// Swift 6 언어 모드로 빌드하는 라이브러리
public func track6(_ callback: @escaping () -> Void) {
  callback()
}
```

```swift
import StrictLibrary

@MainActor
final class Screen {
  func render() {}
}

@MainActor
func updateUI(_ screen: Screen) {
  track6(screen.render)   // Swift 6 라이브러리에 넘긴다
}
```

Swift 5 와 Swift 5 + flag 와 Swift 6 모두 검사 개수가 0 이다. Swift 6 로 빌드된 라이브러리는 컴파일 때 이미 isolation 을 검사받았으니 런타임에 다시 확인할 필요가 없다는 판단이다. 제안서가 "더 많은 생태계가 Swift 6 로 옮겨 갈수록 동적 검사가 사라진다" 고 한 설계를 이 측정이 보여 준다.

대조 실험으로 같은 `StrictLibrary` 소스를 Swift 5 모드로 빌드해서 같은 `track6` 호출을 컴파일했다. 클라이언트 쪽 코드는 바꾸지 않았다. 검사 개수는 Swift 5 가 0, Swift 5 + flag 가 1, Swift 6 이 1 이고 진단은 어느 모드에서도 나오지 않는다. 검사가 들어간 자리는 `Track.swift` 때와 같은 `reabstraction thunk helper ... with global actor constraint Swift.MainActor` 다. 클라이언트 코드가 같은데 라이브러리를 어느 모드로 빌드했느냐만으로 검사 유무가 갈린다. 이 규칙의 근거는 Holly 의 리뷰 답변이다. 함수 값이 인자로 넘어가고 callee 가 Swift 6 로 빌드되지 않은 import 라이브러리에 있을 때만 검사를 넣는다는 것이다(리뷰 #15).

![검사는 Swift 6 로 검사받지 않은 코드와 맞닿는 자리에만 들어간다. Swift 5 라이브러리 track 으로 넘기는 화살표에는 main actor 확인 thunk 가 있고 검사가 1개(Swift 6 모드 또는 Swift 5 + flag)이며, Swift 6 라이브러리 track6 로 넘기는 화살표에는 검사가 없다.](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-09-17-SE-0423/se-0423-checks-at-boundaries.png)

### Objective-C 로 내보낸 메서드

세 번째 경계는 Objective-C 다. 클래스나 그 메서드에 `@objc` 를 붙이면 컴파일러는 Objective-C 가 부를 수 있는 입구를 따로 만든다. 이 입구도 thunk 라서 거기에 검사를 넣는다. John McCall 이 1차 리뷰에서 이유를 설명했다(리뷰 #13). Objective-C 의 메서드 호출은 본래 매우 동적이고, method table(클래스가 메서드를 찾아보는 표)의 한 selector(메서드 이름표)에는 진입점을 하나만 둘 수 있으며, 부르는 쪽이 대개 Objective-C 라서 Swift concurrency 와 협조하게 할 수도 없다는 것이다. 그러니 이 입구에서는 검사를 하는 것이 맞다는 결론이다. 제안서 본문은 클래스나 그 동기 멤버가 actor-isolated 이면서 `@objc` 또는 `@objcMembers` 로 표시된 경우에 컴파일러가 만드는 thunk 에 새 precondition 검사가 들어간다고 적는다. `@objcMembers` 는 클래스의 멤버 전체를 한 번에 `@objc` 로 내보내는 표시다. hisekaldma 가 "thunk 가 무엇이냐" 고 물은 대목에 Holly 는 이렇게 답했다(리뷰 #5). `@objc` thunk 는 Swift 구현을 부르는 wrapper 이고, Swift 에서 직접 부를 때는 검사 비용을 치르지 않고 Objective-C 를 거쳐 부를 때만 검사가 들어간다.

```swift
import Foundation

@MainActor
final class Box: NSObject {
  var pokes = 0
  @objc func poke() {
    pokes += 1
    print("poke, pokes = \(pokes)")
  }
}

@main
struct App {
  @MainActor static func main() {
    let box = Box()
    box.poke()                          // Swift 에서 직접: 검사 없음
    box.perform(#selector(Box.poke))    // Objective-C 경로, main thread
    print("다른 thread 에서 Objective-C 경로로 부른다")
    let done = DispatchSemaphore(value: 0)
    Thread.detachNewThread {
      box.perform(#selector(Box.poke))  // Objective-C 경로, 다른 thread
      done.signal()
    }
    done.wait()
    print("끝")
  }
}
```

#### NSObject와 perform으로 Objective-C 경로로 메서드 부르기

1. [`NSObject`](https://developer.apple.com/documentation/objectivec/nsobject-swift.class){:target="_blank"} 는 Objective-C 의 모든 클래스의 뿌리다. Swift 클래스가 `NSObject` 를 상속하면 Objective-C 런타임에 등록되어, 메서드를 이름으로 찾아 부르는 Objective-C 방식의 호출이 가능해진다. `@objc` 는 그 메서드를 Objective-C 에 노출한다는 표시다.
2. [`#selector(Box.poke)`](https://developer.apple.com/documentation/objectivec/selector){:target="_blank"} 는 `Box` 의 `poke` 메서드의 Objective-C 이름표(selector)를 만든다. 메서드 이름을 문자열로 쓰는 대신 컴파일러가 확인해 주는 표현이다.
3. [`perform(_:)`](https://developer.apple.com/documentation/objectivec/nsobjectprotocol/perform%28_:%29){:target="_blank"} 은 selector 로 지정한 메서드를 Objective-C 의 메시지 전달 방식으로 부른다. Swift 의 직접 호출과 달리 `@objc` thunk 를 거친다. 이 실험에서는 Swift 에서 부르는 길과 Objective-C 로 부르는 길을 나란히 놓으려고 썼다.

검사 개수는 Swift 5 가 0, Swift 5 + flag 가 2, Swift 6 이 2, Swift 6 + disable 이 0 이다. 두 개가 들어간 함수는 이렇다.

```text
sil private [thunk] @@objc main.Box.poke() -> () : $@convention(objc_method) (Box) -> () {
sil private [thunk] @@objc main.Box.init() -> main.Box : $@convention(objc_method) (@owned Box) -> @owned Box {
```

`poke()` 와 `init()` 의 `@objc` thunk 두 개다. `init()` 은 `@MainActor` 클래스의 생성자도 main actor 에 묶인 동기 함수라서 Objective-C 입구에 검사가 붙는다. 첫 줄의 `box.poke()` 는 Swift 의 직접 호출이라 어느 thunk 도 거치지 않는다.

Swift 5 와 Swift 6 + disable 로 실행하면 끝까지 간다.

```text
poke, pokes = 1
poke, pokes = 2
다른 thread 에서 Objective-C 경로로 부른다
poke, pokes = 3
끝
```

Swift 6 과 Swift 5 + flag 로 lldb 에서 돌리면 세 번째 `poke` 직전에 `thread #2` 에서 `EXC_BREAKPOINT` 로 멈춘다. backtrace 의 #5 `_checkExpectedExecutor`, #6 `@objc Box.poke()`, #7 `closure #1 in static App.main()` 이다. main thread 에서 `perform` 으로 부른 두 번째 `poke` 는 같은 thunk 를 지나면서도 검사를 통과했다. 검사는 호출 경로가 아니라 "지금 thread 가 맞는가" 를 본다.

### Swift 6 라이브러리 호출 자리

리뷰를 거치며 제안서에 더해진 규칙이 하나 더 있다. John McCall 은 1차 리뷰에서 검사가 `@objc` 와 function value 로 한정되고, 직접 호출과 protocol 요구사항과 class method 는 isolated witness 라는 특수한 경우를 빼면 검사가 없다는 점을 짚었다(리뷰 #13). 그리고 호출하는 쪽에서 검사하는 방법이 대안이 될 수 있다고 했다. 컴파일러가 Swift 6 가 아닌 언어 모드로 호출자를 컴파일할 때 검사를 호출 자리에 넣으면, 호출자가 나중에 Swift 6 로 올라올 때 그 검사는 사라질 수 있다는 것이다. Holly 는 그 아이디어가 꽤 설득력 있다고 답했고(리뷰 #15), 호출 자리가 `@preconcurrency` 로 가려지는 경우를 예로 들었다(리뷰 #18). 2차 리뷰의 Revision history 에는 Swift 6 라이브러리에서 import 한 동기 actor-isolated 함수를 직접 호출하는 자리에 동적 검사를 넣는다는 항목이 적혀 있고, 모든 동적 검사를 끄는 flag 도 이때 더해졌다.

제안서의 예는 이렇다.

```swift
// ModuleA built with -swift-version 6
@MainActor public func onMain() { ... }

// ModuleB built with -swift-version 5 -strict-concurrency=minimal
import ModuleA

@preconcurrency @MainActor func callOnMain() {
  onMain()
}

func notIsolated() {
  callOnMain()
}
```

`callOnMain()` 은 `@preconcurrency` 가 붙어 있어서 isolation 없는 `notIsolated()` 가 minimal 검사 아래에서 아무 진단 없이 부를 수 있다. 그러면 `onMain()` 이 main actor 밖에서 실행되는 구멍이 생긴다. 이 예는 `onMain()` 을 부르는 자리가 Swift 6 로 빌드된 라이브러리를 향하는 경우다.

이 예를 6.4 에서 그대로 돌렸다. ModuleA 는 `-emit-library -static -emit-module` 로, ModuleB 는 같은 폴더를 `-I .`, `-L .` 로 가리키고 `-l` 로 이어서 빌드한다.

```bash
cd swift6lib
xcrun swiftc -parse-as-library -swift-version 6 -emit-library -static -emit-module \
    -module-name ModuleA ModuleA.swift -o libModuleA.a
xcrun swiftc -parse-as-library -swift-version 5 -I . -L . -lModuleA ModuleB.swift -o mb
```

ModuleB 를 Swift 5, Swift 5 + flag, Swift 5 + `-strict-concurrency=complete`(Swift 5 complete), Swift 6 으로 빌드해서 `_checkExpectedExecutor` 를 세면 모두 0 개다. 실행도 끝까지 간다.

```text
onMain, mainCounter = 1
onMain, mainCounter = 2
끝
```

두 번째 줄은 `Thread.detachNewThread` 안에서 `notIsolated()` 를 부른 결과다. 종료 코드는 0 이다. 진단은 Swift 5 complete 와 Swift 6 에서 `ModuleB.swift:10:3` 에 warning 이 하나 나온다.

```text
ModuleB.swift:10:3: warning: call to main actor-isolated global function 'callOnMain()' in a synchronous nonisolated context [#ActorIsolatedCall]
 3 | import ModuleA
 4 | 
 5 | @preconcurrency @MainActor func callOnMain() {
   |                                 `- note: calls to global function 'callOnMain()' from outside of its actor context are implicitly asynchronous
 6 |   onMain()
 7 | }
 8 |

   |      `- note: add '@MainActor' to make global function 'notIsolated()' part of global actor 'MainActor'

```

6.4 에서 이 예를 측정하면 검사는 0개이고 프로그램은 끝까지 돈다. 진단은 `notIsolated()` 가 `callOnMain()` 을 부르는 자리의 warning 으로만 나온다. 이 글에서 `_checkExpectedExecutor` 가 실제로 들어간 곳은 앞의 세 경계였다.

### async 함수는 검사하지 않는 이유

세 경계 모두 "동기" 함수만 대상이다. 제안서의 Detailed design 은 이렇게 설명한다. `async` 함수는 필요하면 자기 actor 로 건너가는 일을 callee 가 스스로 하므로 런타임 검사가 필요 없고, `async` 함수는 C, C++, Objective-C 에서 바로 부를 수도 없다. John McCall 도 비슷하게 정리했다(리뷰 #13). 동기 함수는 부르는 쪽이 isolation 을 이미 만들어 두었다고 믿고 들어가야 하니 입구에서 확인할 필요가 있고, `async` 함수는 들어간 뒤 스스로 건너가는 길이 있다.

```swift
public protocol Loader {
  func load() async -> Int
}

@MainActor
final class Screen: @preconcurrency Loader {
  var value = 7
  func load() async -> Int { value }
}

@main
struct App {
  static func main() async {
    let l: any Loader = await MainActor.run { Screen() }
    print(await l.load())
  }
}
```

#### MainActor.run으로 main actor 에서 값 만들기

[`MainActor.run(resultType:body:)`](https://developer.apple.com/documentation/swift/mainactor/run%28resulttype:body:%29){:target="_blank"} 은 closure 를 main actor 위에서 실행하고 그 결과를 돌려주는 비동기 함수다. `Screen()` 이 main actor 에 묶인 클래스의 생성자라서 main actor 밖인 `main()` 에서 만들려면 이렇게 건너가야 한다. `any Loader` 는 "`Loader` 를 지키는 어떤 타입" 을 담는 상자(existential)다.

Swift 5, Swift 5 + flag, Swift 6 모두 컴파일 진단이 0 줄이고 `_checkExpectedExecutor` 개수도 0 이다. 실행하면 `7` 이 출력된다. `load()` 가 `async` 라서 `l.load()` 를 부를 때 callee 쪽이 main actor 로 건너가고, 동기 witness 처럼 입구에서 검사할 필요가 없다는 제안서 설명이 측정으로 맞았다.

대조로 `@preconcurrency` 를 뺀 판(`AsyncNoPreconcurrency.swift`)도 돌렸다. `final class Screen: Loader` 로 바꾼 한 줄 말고는 같다. 이 판도 모든 모드에서 진단이 0줄이고 검사가 0개다. async 요구사항을 main actor 의 구현이 채우는 것은 정적으로 원래 허용되는 모양이라, 여기서는 `@preconcurrency` 가 억누를 진단이 없다. 그런데 앞의 `NoEffect.swift` 와 달리 `@preconcurrency` 를 붙인 판에서도 "has no effect" warning 은 나오지 않는다. 그래서 이 표시가 필요한지는 warning 의 유무가 아니라 witness 가 동기인지로 판단해야 한다.

### 검사 끄기

제안서는 동적 검사를 끄는 flag 도 넣었다. `-disable-dynamic-actor-isolation` 이다. 제안서는 끄는 것을 권하지 않는다고 하면서, 내가 고칠 수 없는 코드가 isolation 을 어겨서 프로그램이 멈추는 경우의 임시 방편이라고 한다. 예로 든 것은 non-Sendable 함수 인자를 main actor 밖으로 넘기는 경우다.

앞의 실험에서 이 flag 를 주면 검사 개수가 0 이 되고 프로그램이 끝까지 돌았다. `Preconcurrency.swift` 와 `Track.swift` 와 `ObjcThunk.swift` 모두 그랬다. 제안서는 이것을 `-enforce-exclusivity=unchecked` 에 비유한다. exclusivity(같은 변수에 겹치는 접근을 못 하게 하는 규칙)의 런타임 검사를 Swift 5 모드에 단계적으로 들여올 때 같이 제공한 탈출구와 같은 성격이다. 검사를 끈다고 data race 가 사라지는 것이 아니라, 멈추는 대신 조용히 race 가 나는 이전 상태로 돌아가는 것이다.

---

### 런타임 검사는 어떻게 동작하나

앞의 backtrace 를 아래에서 위로 따라가면 검사가 하는 일이 한눈에 보인다.

1. witness thunk 같은 자리에 컴파일러가 [`_checkExpectedExecutor`](https://github.com/swiftlang/swift/blob/main/stdlib/public/Concurrency/Executor.swift){:target="_blank"} 호출을 넣는다. "이 코드가 main actor 의 executor 위에서 돌고 있는가" 를 묻는 함수다.
2. 이것이 `swift_task_isCurrentExecutorWithFlagsImpl` 을 부른다. 현재 executor 가 기대한 executor 와 같은지 따지는 runtime 함수다.
3. 기대한 executor 가 main actor 의 것이면 `_swift_task_checkIsolatedSwift` 가 불리고, 이것이 libdispatch 의 `dispatch_assert_queue` 를 부른다.
4. `dispatch_assert_queue` 는 현재 코드가 지정한 queue 위에서 도는지 확인하고 아니면 `_dispatch_assert_queue_fail` 로 프로세스를 멈춘다.

앞에서 본 것처럼 main actor 의 executor 는 main dispatch queue 라서, 검사는 결국 "지금 main queue 위인가" 를 묻는 `dispatch_assert_queue` 로 끝난다. 그래서 stderr 에는 아무것도 나오지 않고, 크래시 리포트에도 `EXC_BREAKPOINT` 와 `SIGTRAP` 만 남는다. 멈춘 자리의 backtrace 가 진단의 전부다.

릴리스(-O) 빌드에서도 같다. `-O` 로 빌드한 같은 프로그램도 종료 코드가 133 이고, backtrace 는 이렇게 줄어든다.

```text
    frame #0: libdispatch.dylib`_dispatch_assert_queue_fail + 120
    frame #1: libdispatch.dylib`dispatch_assert_queue$V2.cold.1 + 116
    frame #2: libdispatch.dylib`dispatch_assert_queue + 108
    frame #3: libswift_Concurrency.dylib`_swift_task_checkIsolatedSwift + 48
    frame #4: libswift_Concurrency.dylib`swift_task_isCurrentExecutorWithFlagsImpl(...) + 356
    frame #5: appO`protocol witness for ViewDelegateProtocol.respondToUIEvent() in conformance MyViewController + 76
    frame #6: appO`closure #1 in fireEventFromBackground(_:) + 80
```

`_checkExpectedExecutor` 가 inline 되어 frame 에서 사라지고 #4 바로 아래에 witness thunk 가 온다. -O 의 SIL 에서는 `_checkExpectedExecutor` 를 부르는 `function_ref` 가 0개였다. 검사가 사라진 것이 아니라 호출 모양만 바뀐 것이다.

pitch 에서 ktoso 는 이 메커니즘이 `SerialExecutor`(actor 의 일감을 한 번에 하나씩 돌리는 executor 의 protocol)의 동등성 검사를 그대로 쓰고, main queue 를 target 으로 삼는 custom executor(개발자가 직접 구현해 actor 에 붙이는 executor)같은 복잡한 경우도 다룰 수 있다고 설명했다(pitch #2). 이 runtime 진입점은 오래된 runtime 에도 있어서 배포 대상 OS 에 제약이 없다는 것이 제안서의 입장이고, ktoso 는 `assumeIsolated` 의 back-deploy 문제는 `@backDeployed`(새 OS 의 API 를 옛 OS 에서도 쓰게 소스 형태로 함께 배포하는 속성) 쪽 사정이지 이 runtime 이 아니라고 보탰다(pitch #4).

## 다른 선택지는 왜 안 됐나

제안서의 Alternatives considered 는 두 가지를 적고, 리뷰 스레드는 검사 위치와 범위를 놓고 더 길게 오갔다. 아래는 포럼의 논의를 제안서에 반영된 순서대로 정리한 것이다.

---

### 모든 동기 isolated 함수 입구에서 검사하기

가장 단순한 안은 모든 동기 isolated 함수의 입구에서 늘 검사하는 것이다. 제안서의 이전 판이 이 안이었다. 이 방법은 빠뜨릴 일이 없다. 단점은 Swift 6 에서 컴파일 때 isolation 이 완전히 검사되는 코드도 런타임 검사 비용을 계속 낸다는 것이다. 지금 방식은 검사받지 않은 코드와 닿는 경계에만 검사를 넣으므로 생태계가 Swift 6 로 옮겨 갈수록 비용이 줄어든다. 대신 어떤 호출 경로를 놓칠 가능성이 생기고, 새로 발견되는 패턴마다 특별 규칙이 필요해질 수 있다고 제안서는 인정한다.

pitch 에서 George 는 모든 isolated 메서드 호출에 이 비용이 붙는 것이냐고 물었다(pitch #5). Holly 는 "동기 메서드에 한해서라면 그렇다" 고 답했다(pitch #6). 바로 위에 적은 제안서의 이전 판이 그 설계였다. 같은 질문에서 George 는 protocol witness 안에서 `assumeIsolated` 를 하는 얇은 wrapper 로 만들면 되지 않느냐고도 물었다(pitch #5). 최종 설계에 가장 가까운 모양이다. Holly 가 위험한 경로로 꼽은 것은 public 함수, `@objc`, protocol conformance, 함수 참조였고(pitch #6), 이 글의 경계들이 그 목록을 좁힌 것이다. 이것이 "왜 이 경계들인가" 의 답이다. Karl 은 기존의 `-enable-actor-data-race-checks`(actor isolation 을 모든 입구에서 런타임에 확인하는 실험용 컴파일러 옵션)가 매우 무디다고 했다(pitch #10). `@MainActor` 함수가 다른 `@MainActor` 함수를 부르는 것처럼 정적으로 증명되는 곳에도 검사가 들어가고 retain/release(객체의 참조 횟수를 올리고 내리는 메모리 관리 연산)도 늘어난다는 지적이다. Holly 는 이 pitch 가 그 flag 를 그대로 켜자는 것이 아니고 제안서에도 구현으로 올리지 않았다고 답했다(pitch #12).

John McCall 은 1차 리뷰에서 검사 전략을 세 가지로 정리했다(리뷰 #13).

| 전략 | 비용 |
| --- | --- |
| 무조건 검사한다 | 코드 크기와 실행 시간 비용이 항상 든다 |
| 호출 경로를 둘로 만들어, caller 가 isolation 을 확인해 둔 경우는 검사 없는 경로로 간다 | 실행 비용은 적지만 코드 크기가 크게 는다 |
| 검사하지 않고 동적 안전 없음을 감수한다 | 비용 없음, 안전 없음 |

그리고 어느 방식이 맞는지는 호출 방법별로 달라진다고 했다. 직접 호출, 불투명한 함수 값, Objective-C dispatch, protocol 요구사항, 재정의 가능한 class method 가 그 목록이다. Objective-C dispatch 와 함수 값은 검사를 넣을 곳이 정해져 있다. 나머지는 callee 쪽에 진입점을 여럿 만들면 코드가 너무 커지니, 가능하다면 caller 쪽에서 검사하는 것이 낫다는 것이 그의 요지였다.

Holly 는 호출 자리에서 검사하는 안이 꽤 설득력 있다고 답했고(리뷰 #15), 컴파일되는 호출 자리라면 검사를 빼도 되느냐고 스스로 묻고 답은 아마 아니라며 직접 호출이 컴파일되더라도 중간의 `@preconcurrency` 함수가 검사 없이 불릴 수 있다는 예를 들었다(리뷰 #18). John 은 `@MainActor` 만 붙은 함수는 호출 자리에서 isolation 이 강제되니 내부에 검사가 필요 없을 것이라고 정리하며 "함수 값으로 쓰일 때 `@preconcurrency` 가 isolation 을 지우니 thunk 에서 검사하면 된다" 고 보탰다(리뷰 #19). 2차 리뷰의 Swift 6 라이브러리 호출 자리 규칙이 이 논의의 결과다. 2차 리뷰는 추가 의견 없이 끝났다.

### @preconcurrency(unsafe) 로 warning 만 내기

제안서가 거절한 두 번째 안이다. 기존 바이너리에서 동적 검사가 버그를 드러냈을 때, `@preconcurrency(unsafe)` 같은 표시로 assertion 실패를 warning 으로 낮추자는 안이다. 제안서는 런타임에서 이미 드러난 data race 를 허용하는 것이 옳은 해결인지 불분명하다고 판단했다. 대신 막다른 길에서는 앞에서 본 `-disable-dynamic-actor-isolation` 이 있다.

### 이름과 gating

pitch 에서 ktoso 는 `: @preconcurrency P` 형태로 conformance 에 표시를 요구하는 것이 구 protocol 의 가정을 새 세계에 연착륙시키는 옳은 방법이라고 평했다(pitch #2). 동시에 "dynamic actor isolation" 이라는 이름이 너무 넓다고 했다. `assumeIsolated` 같은 다른 동적 방법들도 같은 이름 아래 들어갈 수 있으니, 실제로 다루는 global actor 와 conformance 에 가까운 이름이 낫겠다는 제안이었다. feature 와 flag 이름은 `DynamicActorIsolation` 그대로 수락되었다. 최종 제목에는 "from non-strict-concurrency contexts" 가 붙었다. 이름은 넓게 남았고, gating 은 `@preconcurrency` 표시와 Swift 6 모드라는 두 입구로 좁혀졌다.

### 성능 비용

George 의 질문과 Holly 의 답(pitch #5, #6)에서 나온 성능 이야기를 한 번에 정리한다. 검사는 동기 actor-isolated 메서드에만 들어가고, Holly 는 구체적인 수치를 모아 제안서에 넣겠다고 했다. 제안서의 최종 본문에는 수치가 들어가지 않았다. 대신 설계가 비용을 줄이는 쪽으로 갔다. 검사가 닿는 곳은 이 경계들로 한정되고, thunk 안에서만 일어나서 Swift 에서 직접 부르는 길은 비용이 없다는 것이 이 글의 앞 측정이다. 릴리스(-O) 빌드에서도 같은 프로그램이 종료 코드 133 으로 멈추니 검사는 디버그 빌드 전용이 아니다. Swift 6 라이브러리로 넘기는 `track6` 에는 아예 검사가 없었다.

### @escaping과 @Sendable의 차이

pitch 에서 Holly 가 든 예 하나가 이 제안서의 필요를 가장 잘 보여 준다(pitch #8).

```swift
// In NotMyLibrary
public func takesClosure(_ closure: () -> Void) { ... }

import NotMyLibrary

@MainActor func mustRunOnMainActor() {}

@MainActor func useAPI() {
  takesClosure(mustRunOnMainActor)
}
```

컴파일러 눈에는 완전히 안전한 코드다. `() -> Void` 에는 actor isolation 이 없지만 closure 가 `@Sendable` 이 아니라서 다른 isolation 영역으로 못 나가기 때문이다. 그러나 `NotMyLibrary` 가 strict concurrency 검사를 하지 않으면, 그 함수 값을 모르고 background thread 로 넘겨 부를 수 있다.

Karl 은 closure 가 non-escaping 이라 그럴 수 없지 않느냐고 반문했다(pitch #9). Holly 는 `@escaping` 이어도 `@Sendable` 이 아니니 타입 검사기가 허용한다고 답했고(pitch #11), `@Sendable` 이 아닌 값은 검사된 `Sendable` 타입에 저장할 수 없고 non-`Sendable` 타입에 저장해도 그 값이 isolation 경계를 못 넘는다는 것이 안전성의 이유라고 설명했다. 이 규칙은 더 최적화하려고 바꾸지 않겠다는 입장이었다. 이 글의 `Track.swift` 가 그 사고의 실물이다. `track` 이 `Thread.detachNewThread` 로 closure 를 다른 thread 에서 불렀고, 정적 검사는 이를 못 막았으며, 동적 검사가 막았다.

### 함수 값 강제 변환과 unsafeBitCast

1차 리뷰에서 John McCall 은 isolation 을 지우는 명시적 변환이 이미 있다고 짚었다(리뷰 #7).

```swift
func test(operation: @MainActor () -> Int) {
  let fn = operation as () -> Int
  fn()
}
```

이 변환이 동적으로 안전하다고 생각했는데 문서화되지 않았을 것 같고, 이 제안서가 다루기 좋은 자리일 것 같다는 이야기였다. Holly 는 현재 컴파일러가 이 코드에 동적 검사를 넣지 않고 Swift 6 모드에서는 변환 자체를 오류로 진단한다고 답했다(리뷰 #8). wadetregaskis 는 이런 변환을 허용한다면 크래시 가능성이 있으니 `as!` 를 쓰게 해야 하지 않느냐고 했고(리뷰 #9), John 은 그럴 거면 `as` 보다 명시적인 `assumeIsolated` 가 맞겠다고 했다(리뷰 #12). tgoyne 은 `-enable-actor-data-race-checks` 와 [`unsafeBitCast`](https://developer.apple.com/documentation/swift/unsafebitcast%28_:to:%29){:target="_blank"} 로 실제로 isolation 이 없는 closure 에 동적 검사를 붙이는 방법을 소개했다(리뷰 #11). John 은 그 예에서는 isolation 이 지워지는 지점이 비트 재해석이라 이 제안서의 규칙이 검사를 붙이지 못하고 그 구멍은 남는다고 정리했다(리뷰 #13 각주).

이 변환을 6.4 에서 돌려 봤다. isolation 이 없는 함수에서 하면 Swift 5 에서는 warning 이다.

```swift
func takesOperation(_ operation: @escaping @MainActor () -> Int) -> () -> Int {
  operation as () -> Int
}
```

```text
coerce/CoerceNonisolated.swift:2:3: warning: converting function value of type '@MainActor () -> Int' to '() -> Int' loses global actor 'MainActor'; this is an error in the Swift 6 language mode
1 | func takesOperation(_ operation: @escaping @MainActor () -> Int) -> () -> Int {
2 |   operation as () -> Int
  |   `- warning: converting function value of type '@MainActor () -> Int' to '() -> Int' loses global actor 'MainActor'; this is an error in the Swift 6 language mode
3 | }
4 | 
```

Swift 6 에서는 error 이고 타입에 `@Sendable` 이 붙어서 나온다.

```text
coerce/CoerceNonisolated.swift:2:3: error: converting function value of type '@MainActor @Sendable () -> Int' to '() -> Int' loses global actor 'MainActor'
1 | func takesOperation(_ operation: @escaping @MainActor () -> Int) -> () -> Int {
2 |   operation as () -> Int
  |   `- error: converting function value of type '@MainActor @Sendable () -> Int' to '() -> Int' loses global actor 'MainActor'
3 | }
4 | 
```

Swift 6 에서 global actor 에 묶인 함수 타입은 암묵적으로 `Sendable` 이다([SE-0434](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0434-global-actor-isolated-types-usability.md){:target="_blank"}). `@MainActor @Sendable` 함수는 어디로든 보낼 수 있지만, 동기로 부르는 일은 main actor 위에서만 된다. isolation 이 없는 문맥에서 이 변환을 허용하면, main actor 위에서만 불러야 할 함수를 그 자리, 곧 main actor 밖에서 바로 부를 수 있게 된다. 그래서 이 변환은 isolation 이 없는 문맥에서 막힌다.

같은 변환을 `@MainActor` 함수 안으로 옮기면 어느 모드에서도 진단이 없다.

```swift
@MainActor
func takesOperation(_ operation: @escaping @MainActor () -> Int) -> () -> Int {
  operation as () -> Int
}
```

Swift 5, Swift 5 complete, Swift 6 모두 진단 0 줄이고 `_checkExpectedExecutor` 도 0 개다. main actor 안에서 non-`Sendable` 함수로 바꾼 값은 그 actor 밖으로 못 나가니 허용된다. 리뷰 당시 Holly 가 말한 "Swift 6 에서는 error" 는 위 isolation 이 없는 문맥의 경우와 같다. 이 변환을 동적 검사로 풀지는 이 제안서의 범위가 아니다.

### XCTestCase 를 상속할 때

cal 은 `@MainActor final class MyTests: XCTestCase` 가 Swift 5.10 에서 "superclass 와 isolation 이 다르다" 는 warning 이 되었다며, 이것도 `@preconcurrency` 로 풀 수 있는지 물었다(리뷰 #14). 상속하는 클래스에 `@preconcurrency` 를 붙이는 모양이다. Holly 의 답은 안 된다는 것이었다(리뷰 #16). subclass 에 isolation 을 더하면 global actor 클래스가 암묵적으로 `Sendable` 이 되는 문제가 따라온다. superclass 의 non-`Sendable` 상태를 isolation 경계 너머로 몰래 보낼 수 있어서 동시 접근을 만든다. 이 제안서 밖에서 그 제약을 완화하는 별도 제안서를 준비 중이라고 했다. 이 제안서가 다루는 대상은 protocol conformance 이고 상속이 아니다.

### 수락

1차 리뷰가 끝나고 한 달여 뒤인 2024년 4월 10일, Ben Cohen 은 1차 리뷰 스레드에 제안서가 수정되었다고 알리고(리뷰 #20) 2차 리뷰를 열었다. 호출 자리의 검사와 끄는 flag 가 더해진 판이다. 2차 리뷰는 4월 19일까지였고 추가 피드백 없이 끝났으며, 2024년 4월 30일에 Language Steering Group 이 수락했다. 결과는 Ben Cohen 이 공지했다.

---

## 기대 효과

앞에서 직접 돌려 본 것에서 나오는 효과만 정리한다.

- 조용한 data race 가 재현 가능한 crash 로 바뀐다. 같은 `Preconcurrency.swift` 가 Swift 5 에서는 `count = 2` 를 찍고 정상 종료하지만, Swift 6 에서는 다른 thread 의 첫 호출에서 멈추고 종료 코드 133 이 나온다. 간헐적으로만 나타나던 상태 오염이 항상 같은 자리에서 멈추는 문제로 바뀐다.
- 멈춘 자리의 backtrace 가 부른 쪽을 바로 보여 준다. `fireEventFromBackground(_:)` 안의 closure(#7), `track(_:)` 안의 closure, `App.main()` 안의 closure 처럼 문제가 있는 호출이 프레임에 남는다. 문서의 약속을 어긴 라이브러리를 찾는 일이 빨라진다.
- 검사가 경계에만 있어서 Swift 6 로 옮겨 갈수록 사라진다. `track` 에는 검사가 1개, Swift 6 로 빌드한 `track6` 에는 0개였다. 모든 isolated 함수 입구를 검사하는 안이었다면 Swift 6 로 모두 옮긴 앱도 계속 비용을 냈을 것이다.
- `@preconcurrency` conformance 가 앱 안의 정적 안전을 지킨다. `nonisolated` 와 `assumeIsolated` 로 손수 감싸던 때는 같은 모듈의 잘못된 호출도 컴파일러가 막지 못했지만, 이 방식은 `InModule.swift` 의 `s.greet()` 를 계속 error 로 막는다.

## 마이그레이션

이 검사는 Swift 6 언어 모드에서는 기본으로 켜진다. Swift 5 모드의 프로젝트는 flag 로 먼저 켜 보면 어떤 라이브러리가 약속을 어기는지 미리 볼 수 있다. 컴파일러 옵션은 `-enable-upcoming-feature DynamicActorIsolation` 이다. SwiftPM 에서는 타깃의 `swiftSettings` 에 넣는다.

```swift
.target(
    name: "MyApp",
    swiftSettings: [
        .enableUpcomingFeature("DynamicActorIsolation")
    ]
)
```

#### enableUpcomingFeature로 타깃마다 기능 미리 켜기

[`.target(name:swiftSettings:)`](https://developer.apple.com/documentation/packagedescription/target){:target="_blank"} 는 Package.swift 에서 빌드 타깃 하나를 선언하고 그 타깃에만 적용할 컴파일러 설정을 준다. [`enableUpcomingFeature(_:_:)`](https://developer.apple.com/documentation/packagedescription/swiftsetting/enableupcomingfeature%28_:_:%29){:target="_blank"} 는 upcoming feature 하나를 그 타깃에서 켠다. 첫 인자가 feature 이름이고 두 번째 인자는 적용할 빌드 조건이며, 여기서는 이름만 넘겨서 모든 빌드에 적용했다. 타깃마다 따로 켤 수 있으니 모듈 하나씩 옮기기 좋다.

순서는 이렇게 잡을 수 있다.

1. 테스트나 디버그 빌드에서 flag 를 켜고 앱을 돌려 본다. 평소 쓰는 화면과 delegate callback 을 모두 지나간다.
2. 멈추면 lldb 나 Xcode 의 backtrace 에서 `_checkExpectedExecutor` 바로 아래 프레임을 본다. `protocol witness for ... in conformance ...` 이면 conformance 를 부른 라이브러리 함수가, `reabstraction thunk helper ... with global actor constraint` 이면 함수 값을 받은 API 가, `@objc` thunk 이면 Objective-C 쪽 호출이 원인이다.
3. 부른 쪽이 내 코드이거나 고칠 수 있는 라이브러리이면 그쪽을 고친다. main actor 에서 부르게 하는 가장 간단한 방법은 [`DispatchQueue.main`](https://developer.apple.com/documentation/dispatch/dispatchqueue/main){:target="_blank"} 의 `async` 로 부르는 코드를 main queue 로 넘기는 것이다.
4. 고칠 수 없는 라이브러리라서 당장 크래시를 못 없애면 마지막 수단으로 `-disable-dynamic-actor-isolation` 으로 검사를 끈다. 이 선택은 조용한 data race 로 돌아가는 것이므로 라이브러리 수정이나 교체를 기다리는 동안만 쓴다.

Xcode 27 의 빌드 설정에는 Upcoming Features 분류에 "Dynamic Actor Isolation" 항목이 있고 내부 이름은 `SWIFT_UPCOMING_FEATURE_DYNAMIC_ACTOR_ISOLATION` 이다. Swift Compiler 설정의 정의 파일(`Swift.xcspec`)에서 읽으면 이 항목은 언어 모드가 4, 4.2, 5 일 때만 보인다. YES 로 두면 `-enable-upcoming-feature DynamicActorIsolation` 이 컴파일러에 전달되고, 기본값은 `$(SWIFT_UPCOMING_FEATURE_6_0)` 이다. 설명문은 "Enable actor isolation checking at runtime for synchronous isolated functions. This is always enabled when in the Swift 6 language mode." 이다. 끄는 flag 에 해당하는 전용 설정은 없으므로 `-disable-dynamic-actor-isolation` 은 Other Swift Flags 에 넣는다.

마이그레이션에서 한 가지를 분명히 해 둔다. Swift 5 모드에서 conformance 에 `@preconcurrency` 만 붙이고 flag 를 켜지 않으면 검사 개수는 0 이다. 진단은 사라지지만 런타임 보호도 없다. 앞의 표에서 Swift 5 와 Swift 5 complete 의 줄이 그 상태다. 경고를 지우려고 `@preconcurrency` 를 붙였다면 flag 를 같이 켜야 멈춤이라는 안전장치가 생긴다.

## 정리

- Swift 6 의 정적 검사가 닿지 않는 경계에서 isolation 위반이 생기면, 조용히 data race 를 내는 대신 런타임에 멈추게 한다. 6.4 에서 `Preconcurrency.swift` 를 돌려 Swift 5 는 끝까지 가고 Swift 6 은 `EXC_BREAKPOINT`(종료 코드 133)로 멈추는 것을 직접 봤다.
- 6.4 에서 검사가 들어가는 곳은 `@preconcurrency` witness, 함수 값, `@objc` thunk 세 곳이다. 리뷰를 거치며 제안서에 더해진 Swift 6 라이브러리 호출 자리 규칙은 측정에서 검사가 0개였고 프로그램이 끝까지 돌았다. `async` 함수에는 넣지 않는다.
- 검사는 thunk 안에만 들어가서 Swift 에서 직접 부르는 길에는 비용이 없고, Swift 6 로 빌드된 쪽으로 넘기는 호출(`track6`)에는 아예 들어가지 않는다.
- 리뷰를 거치며 호출 자리 검사와 `-disable-dynamic-actor-isolation` 이 더해졌고, `XCTestCase` 상속이나 `unsafeBitCast` 같은 구멍은 이 제안서의 범위 밖으로 남았다.
- Swift 5 프로젝트는 `DynamicActorIsolation` flag 로 먼저 켜 보고, 멈추면 backtrace 로 부른 쪽을 찾는다.
