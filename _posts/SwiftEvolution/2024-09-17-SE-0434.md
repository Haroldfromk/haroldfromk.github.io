## 한 줄 요약

global actor 에 묶인 타입을 덜 답답하게 쓰게 해 주는 규칙 다섯 가지다. 값 타입의 `Sendable` var 저장 속성에는 `(unsafe)` 없이 `nonisolated` 를 쓸 수 있고, 정의한 모듈 안에서는 `nonisolated` 로 추론된다. global actor 에 묶인 함수 타입은 `@Sendable` 로 추론되며, 그런 closure 는 non-Sendable 값을 붙잡을 수 있다. 그리고 non-Sendable 부모를 둔 클래스에 global actor 를 붙인 자식 클래스가 허용되는 대신, 그 자식은 `Sendable` 이 아니다.

---

## 어떤 문제였나

`@MainActor` 를 붙이는 순간 타입은 안전해지지만 쓰기는 불편해진다. 이 제안서의 Motivation 은 그 불편을 세 군데에서 집는다. 값 타입의 var 속성을 `nonisolated` 로 읽을 수 없는 점, `@MainActor` closure 를 Task 에 넘기면 막히는 점, `@MainActor` 를 붙인 자식 클래스를 만들 수 없는 점이다. 셋은 서로 다른 규칙이지만 뿌리가 같다. global actor 에 묶인 타입은 자동으로 `Sendable` 이 되는데, 이 자동 규칙이 어떤 자리에서는 너무 엄격하고 어떤 자리에서는 구멍이 된다.

---

### global actor 에 묶인 타입이란?

actor 는 자기 안의 상태를 한 번에 한 코드만 만지게 하는 타입이고, global actor 는 프로그램 전체에 하나뿐인 actor 에 이름을 붙여 둔 것이다. 대표가 main thread 에 대응하는 [`@MainActor`](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 다. 타입 선언에 `@MainActor` 를 붙이면 그 타입의 모든 저장 속성과 메서드가 main actor 의 창구 안에 들어간다. 안에 있는 것을 쓰려면 이미 main actor 위에 있거나, 비동기 코드에서 `await` 로 줄을 서야 한다. 제안서는 이런 타입을 GAIT(global-actor-isolated type)라고 줄여 부른다. 이 글에서도 가끔 그렇게 쓴다. 이 글에서 isolation 은 어떤 코드나 값이 어느 실행 영역(main actor, 다른 actor, 어느 쪽에도 묶이지 않은 영역)에 속하는지를 가리키는 말이다.

`nonisolated` 는 이 규칙에서 빠지겠다는 표시다. 선언에 붙이면 그 선언은 main actor 의 창구 밖에 놓이고, 어느 곳에서든 `await` 없이 쓸 수 있다. 대신 안에서 창구 안의 상태를 만질 수 없다. actor, isolation, `nonisolated` 의 기초는 [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/)에, 전역 변수가 이 규칙에 걸리는 이야기는 [SE-0412 글](https://haroldfromk.github.io/posts/SE-0412/)에 있다.

global actor 에 묶인 타입에는 한 가지 성질이 더 따라온다. 타입이 암묵적으로 `Sendable` 이 된다. 상태가 전부 main actor 의 창구 뒤에 있으니, 객체 자체를 여러 곳에 나눠 들고 있어도 상태를 만지려면 어차피 줄을 서야 하기 때문이다. 이 글의 세 번째 문제가 이 암묵적 `Sendable` 이 왜 항상 맞지는 않은지에서 나온다.

---

### Sendable 과 @Sendable 이란?

[`Sendable`](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 은 동시 실행 영역 사이에 안전하게 넘길 수 있는 타입에 붙이는 표시다. `Int` 나 `let` 만 가진 struct 가 그렇다. 이 표시가 없는 타입을 이 글에서는 non-Sendable 이라고 부른다. 바뀌는 상태를 가진 평범한 class 가 대표적이고, 그런 값을 두 곳이 동시에 만지면 data race 가 날 수 있다.

`@Sendable` 은 함수 타입에 붙이는 같은 종류의 표시다. `@Sendable` closure 는 여러 곳에서 동시에 실행될 수 있다는 뜻이라서, 컴파일러는 closure 가 붙잡는 값(캡처한 값)까지 `Sendable` 인지 검사한다. 글 뒤쪽의 closure 예제들이 이 검사에서 갈린다.

---

### Swift 언어 모드와 upcoming feature flag 란?

이 글의 모든 측정은 Xcode 27 의 Swift 6.4 컴파일러 하나로 했다. 같은 컴파일러가 `-swift-version 5` 를 받으면 Swift 5 모드의 규칙으로, `-swift-version 6` 을 받으면 Swift 6 모드의 규칙으로 코드를 검사한다. Swift 5 모드에 `-strict-concurrency=complete` 를 더하면 concurrency 검사를 Swift 6 와 같은 범위로 넓히되 위반을 warning 으로 보여 준다. 이 글에서 "Swift 5" 는 Swift 5 모드 그대로, "complete" 는 Swift 5 모드에 이 옵션을 준 상태, "flag" 는 거기에 `-enable-upcoming-feature GlobalActorIsolatedTypesUsability` 까지 준 상태, "Swift 6" 은 Swift 6 모드를 가리킨다. 단계별 설명은 [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/)과 [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/)에 있다.

모든 진단은 `-emit-sil` 로 뽑았다. 타입 검사까지만 하는 `-typecheck` 는 SIL 단계에서 나오는 진단을 빼먹는다. 샘플은 전부 아래 한 줄짜리 `Common.swift` 와 함께 컴파일했다.

`Common.swift`

```swift
final class NonSendable {
  var value = 0
}
```

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 Common.swift X.swift
```

`-o /dev/null` 은 결과 파일을 버리고, `-parse-as-library` 는 파일을 최상위 코드가 없는 일반 소스로 다루라는 옵션이며, `-wmo` 는 파일 둘을 한 모듈로 같이 컴파일하라는 옵션이다. 진단 끝에 붙는 `[#RegionIsolation]: <https://...>` 같은 참조 줄은 이 글에서 모두 뺐다. 진단 원문 그대로이고 note 까지 줄이지 않았다.

### 옛 우회: nonisolated(unsafe)

제안서 Motivation 의 첫 문제다. `@MainActor` 구조체의 var 속성을 `==` 구현 같은 `nonisolated` 문맥에서 읽고 싶을 때, 지금까지 쓸 수 있는 유일한 방법은 속성을 `nonisolated(unsafe)` 로 선언하는 것이었다.

`VarPropUnsafe.swift`

```swift
@MainActor struct S {
  nonisolated(unsafe) var x: Int = 0
}

extension S: Equatable {
  static nonisolated func ==(lhs: S, rhs: S) -> Bool {
    return lhs.x == rhs.x
  }
}
```

`nonisolated(unsafe)` 는 "이 선언은 isolation 검사에서 빼 달라, 안전은 내가 책임진다" 는 표시다. 이 코드는 6.4 의 네 모드 모두 진단이 0개다. 컴파일은 되지만 이름에 `unsafe` 가 붙었으니 보는 사람은 이 속성이 위험한가 의심하게 된다. 제안서는 여기서 출발한다. `x` 는 `Int` 이고 `Int` 는 `Sendable` 이다. `Sendable` 값을 여러 곳에서 쓰는 것은 data race 가 아니다. 문제가 생긴다면 `x` 가 저장된 메모리에서 생기는데, `x` 는 값 타입 `S` 의 일부라서 `x` 에 접근하는 것은 곧 `S` 값 전체에 접근하는 것이다. `S` 값 전체에 대한 접근이 이미 안전하게 검사되고 있다면 `x` 부분에 접근하는 것도 안전하다. 그러니 `(unsafe)` 를 요구할 이유가 없다는 것이 제안서의 논리다.

#### Equatable 의 == 와 static nonisolated 로 conformance 구현하기

[`Equatable`](https://developer.apple.com/documentation/swift/equatable){:target="_blank"} 은 `==` 로 두 값이 같은지 비교할 수 있다는 약속이다. `==` 는 두 값을 받는 static 함수이고, protocol 의 요구사항이 isolation 표시 없는 nonisolated 함수라서 구현도 nonisolated 여야 한다. `@MainActor` 구조체가 `Equatable` 을 따르려면 `static nonisolated func ==` 를 써야 하고, 그 안에서 `lhs.x` 를 읽어야 하니 `x` 가 `nonisolated` 여야 했다. 위 코드의 `nonisolated(unsafe)` 가 그 때문에 들어갔다.

### 막히던 Task closure

둘째 문제다. 제안서는 `@MainActor` 함수 타입 parameter 를 Task 안에서 부르는 코드를 든다.

`Closure.swift`

```swift
func test(globallyIsolated: @escaping @MainActor () -> Void) {
  Task {
    await globallyIsolated()
  }
}
```

#### Task 로 일을 비동기로 시작하기

[`Task`](https://developer.apple.com/documentation/swift/task){:target="_blank"} 는 비동기로 실행할 일을 하나 시작하는 타입이다. `Task { ... }` 의 중괄호가 그 일이고, 시작한 곳의 isolation 을 이어받는다. 일이 안에서 `await` 로 `@MainActor` closure 를 부르면 main actor 의 줄을 서게 된다. Task 에 넘기는 closure 는 [SE-0430 글](https://haroldfromk.github.io/posts/SE-0430/)에서 본 `sending` parameter 이므로, 이 closure 가 붙잡는 값은 다른 isolation 으로 보내도 되는 값이어야 한다.

제안서는 이 코드에 `capture of 'globallyIsolated' with non-sendable type '@MainActor () -> Void' in a @Sendable closure` 라는 error 를 달아 두었다. 6.4 에서 측정하면 이렇다. Swift 5 모드는 진단이 0개다. complete 는 warning 하나를 낸다.

```text
Closure.swift:2:3: warning: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure; this is an error in the Swift 6 language mode [#RegionIsolation::SendingClosureRisksDataRace]
1 | func test(globallyIsolated: @escaping @MainActor () -> Void) {
2 |   Task {
  |   `- warning: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure; this is an error in the Swift 6 language mode [#RegionIsolation::SendingClosureRisksDataRace]
3 |     await globallyIsolated()
  |           `- note: closure captures 'globallyIsolated' which is accessible to code in the current isolation context
4 |   }
5 | }
```

flag 와 Swift 6 은 0개다. 같은 코드가 모드에 따라 이렇게 갈린다.

| 모드 | Closure.swift 의 진단 |
| --- | --- |
| Swift 5 | 0개 |
| complete | 2:3 warning |
| flag | 0개 |
| Swift 6 | 0개 |

complete 의 warning 은 `Task` 의 operation parameter 가 `sending` 이라서 나온다. closure 가 붙잡은 `globallyIsolated` 는 `@MainActor () -> Void` 라는 non-Sendable 함수 값이고, 현재 isolation 에서 닿을 수 있는 값이라서 Task 로 보내면 위험하다는 진단이다. flag 를 켜면 이 함수 값이 `@Sendable` 로 추론되어 위험할 것이 없어진다.

`@MainActor () -> Void` 는 main actor 에서만 실행되는 함수다. 제안서가 드는 이유는 global actor 에 묶인 함수는 non-Sendable 이어도 모두 그 global actor 의 isolation 으로 실행된다는 것이다. 부르는 쪽이 어디에 있든 `await` 로 main actor 에 보내서 실행하니, 이 함수를 여러 곳에서 동시에 부른다고 data race 가 날 일이 없다. 그래도 `@Sendable` 이 아니라는 이유로 Task 에 넘길 수 없다면, 이 함수 값은 main actor 위에서만 쓸 수 있는 함수가 된다. 이미 main actor 위에 있다면 `@MainActor` 표시가 필요 없으니, 제안서의 말로 이것은 쓸모 있는 조합이 아니다.

### 자식 클래스를 막던 규칙

셋째 문제다. 이 코드는 Swift 5.10 에서 warning 으로 추가되었고 Swift 6 모드에서 error 가 되는 진단에 걸렸다.

```swift
class NotSendable {}

@MainActor
class Subclass: NotSendable {}
// error: main actor-isolated class 'Subclass' has different actor isolation from nonisolated superclass 'NotSendable'
```

부모는 isolation 이 없는 nonisolated 클래스인데 자식만 `@MainActor` 로 묶으려 하면 막았다는 뜻이다. 이유는 global actor 가 암묵적 `Sendable` 을 끌고 오기 때문이다. 자식이 `Sendable` 이 되면 여러 isolation 으로 마음대로 건너갈 수 있는데, 부모가 물려준 상태는 main actor 의 보호 밖에 있다. 제안서는 이 구멍을 `withDiscardingTaskGroup` 예제로 보인다. 그 예제를 코드로 옮겼다.

`SubclassSmuggle.swift`

```swift
func computeCount() async -> Int { 1 }

class NotSendable {
  var mutableState = 0
  func mutate() async {
    let count = await computeCount()
    mutableState += count
  }
}

@MainActor
class Subclass: NotSendable {}

func test() async {
  let c = Subclass()
  await withDiscardingTaskGroup { group in
    group.addTask {
      await c.mutate()
    }

    group.addTask { @MainActor in
      await c.mutate()
    }
  }
}
```

#### withDiscardingTaskGroup 으로 자식 task 여럿 돌리기

[`withDiscardingTaskGroup`](https://developer.apple.com/documentation/swift/withdiscardingtaskgroup%28returning:isolation:body:%29){:target="_blank"} 은 자식 task 를 여러 개 만들어 동시에 돌리고, 결과는 모으지 않고 버리는 함수다. `group.addTask { ... }` 로 자식 task 를 추가한다. 위 코드는 자식 task 두 개가 같은 `c` 를 잡고 `c.mutate()` 를 부른다. 하나는 일반 closure 이고 하나는 `@MainActor in` 으로 main actor 에서 돈다.

문제는 `NotSendable.mutate()` 가 isolation 표시 없는 `async` 메서드라는 점이다. 두 task 가 동시에 `c.mutate()` 를 부르면 `mutableState += count` 가 서로 다른 곳에서 겹쳐 실행될 수 있다. `Subclass` 가 `@MainActor` 이니 암묵적 `Sendable` 로 `c` 를 두 task 에 나눠 줄 수 있다면, 부모 클래스가 물려준 상태는 아무도 지켜 주지 않는 채 data race 가 난다. 제안서가 "보호받지 못하는 가변 상태를 isolation 경계 너머로 몰래 넘기기" 라고 부르는 문제다. 5.10 에서 warning 으로 추가되어 Swift 6 모드에서 error 가 되는 그 진단은 이 구멍을 입구에서 막으려는 조치였고, 이 제안서는 입구를 열되 `Sendable` 이 되는 길을 막는 쪽으로 바꾼다.

---

## 무엇이 바뀌나

제안서의 Proposed solution 은 다섯 가지다. 값 타입의 `Sendable` 저장 속성은 `(unsafe)` 없이 `nonisolated` 로 선언할 수 있고, 정의한 모듈 안에서는 `nonisolated` 로 추론된다. global actor 에 묶인 함수와 closure 는 `@Sendable` 로 추론된다. global actor 에 묶인 closure 는 non-Sendable 값을 붙잡을 수 있다. non-Sendable 부모를 둔 클래스에 global actor 를 붙인 자식 클래스는 허용되되 `Sendable` 이 아니다. 아래에서 하나씩 6.4 의 네 모드로 확인한다.

---

### 값 타입 var 속성의 nonisolated 추론

옛 우회에서 본 코드에서 `nonisolated(unsafe)` 를 지우고 그냥 `var` 로 두면 어떻게 될까. 제안서의 첫 예제 그대로다.

`VarProp.swift`

```swift
@MainActor struct S {
  var x: Int = 0
}

extension S: Equatable {
  static nonisolated func ==(lhs: S, rhs: S) -> Bool {
    return lhs.x == rhs.x
  }
}
```

이 코드는 6.4 의 네 모드 모두 진단이 0개다. `x` 는 `S` 를 정의한 모듈 안에서 `nonisolated` 로 추론되었고, `==` 는 그것을 isolation 없이 읽는다. 명시적으로 쓰고 싶다면 `nonisolated var x` 라고 써도 된다. `unsafe` 가 필요 없다.

`VarPropExplicit.swift`

```swift
@MainActor struct S {
```

### 모듈 경계와 명시적 nonisolated

추론은 속성을 정의한 모듈 안에서만 일어난다. 다른 모듈에서 읽으려면 속성에 `nonisolated` 를 직접 써야 한다. 제안서가 든 이유는 호환성이다. 모듈 밖에서 본 저장 속성은 앞으로 computed property 로 바뀔 수 있고, 그때 새 접근자가 global actor 에 묶여야 할 수도 있다. 모듈 안에서는 그런 일이 일어나지 않았다는 것을 컴파일러가 알지만, 밖에서는 알 수 없다. 모듈 밖에서 `nonisolated` 로 쓰게 두면 속성을 바꾸는 순간 그 코드가 깨진다.

두 모듈로 확인했다. `ModA` 가 속성 둘을 공개한다.

`ModA.swift`

```swift

  public var x: Int = 0
  public nonisolated var y: Int = 0
  public init() {}
}
```

`ModB` 가 그것을 nonisolated 함수에서 읽는다.

`ModB.swift`

```swift

  p.x + p.y
}
```


Holly Borla 는 속성의 초기값이 isolation 을 요구하지 않아야 한다는 조건이 더 필요하다고 답했고, 공개 API 에서 추론으로 이것을 처리하는 것에는 반대했다(pitch #4). 경고를 내자는 생각은 원래 Holly Borla 가 다른 스레드에서 낸 것이고 gwendal.roue 가 #2 에서 그 글을 인용했다. Holly Borla 는 #6 에서 경고가 여전히 좋은 생각이라고 다시 답했다. 조건은 네 가지다. `let` 이고, 타입이 `Sendable` 이고, 초기값이 isolation 을 요구하지 않고, 그런데도 global actor 가 추론된 static 변수다. 경고는 명시적 `nonisolated` 나 명시적 global actor 로 끌 수 있다. 이 논의는 제안서에 들어오지 않았고, gwendal.roue 가 GitHub issue 72456 으로 따로 열었다(pitch #9).

### global actor 함수 타입의 Sendable 추론

함수 타입 규칙이다. `@MainActor () -> Void` 는 `@MainActor @Sendable () -> Void` 로 추론된다. 앞의 `Closure.swift` 가 flag 와 Swift 6 에서 조용해진 이유다. 타입이 실제로 어떻게 달라졌는지 보려고 함수 값을 `Int` 에 일부러 틀리게 대입해서 컴파일러가 타입을 적게 했다.

`ClosureType.swift`

```swift
func types() {
  let f: @MainActor () -> Void = {}
  let g: @MainActor @Sendable () -> Void = f
  let check: Int = f
  _ = (g, check)
}
```

### mangling 이란?

컴파일러는 함수 이름에 module 이름과 매개변수 타입 같은 정보를 붙여서 하나의 긴 문자열로 바꾸어 라이브러리에 넣는다. 이 규칙이 mangling 이고, 라이브러리 안에 들어간 그 이름이 symbol 이다. linker 는 앱이 부르는 함수와 라이브러리에 있는 함수를 symbol 로 짝지어 이어 준다. ABI 는 이미 빌드된 바이너리끼리 서로를 부르기 위한 약속이고 symbol 이름도 그 일부다. 그래서 함수 타입이 달라져 symbol 이 바뀌면, 옛 symbol 로 함수를 찾던 이미 빌드된 client 앱은 새 라이브러리에서 그 함수를 찾을 수 없어 깨진다.

`@Sendable` 은 함수 타입의 일부라서 mangling 에 들어간다. 그래서 `@Sendable` 추론은 symbol 을 바꾼다. 제안서의 ABI compatibility 절이 이 이야기를 한다.

`Mangle.swift`

```swift
public func takes(_ f: @escaping @MainActor () -> Void) {}
```

모드별로 라이브러리를 만들고 심볼 이름을 읽었다.

```bash
xcrun swiftc -emit-library -module-name M -parse-as-library -swift-version 5 Mangle.swift -o libM.dylib
nm libM.dylib | grep takes
xcrun swift-demangle '$s1M5takesyyyyScMYccF'
```

Swift 5 모드의 결과다.

```text
_$s1M5takesyyyyScMYccF
$s1M5takesyyyyScMYccF ---> M.takes(@Swift.MainActor () -> ()) -> ()
```

flag 를 켠 Swift 5 모드(`-swift-version 5 -strict-concurrency=complete -enable-upcoming-feature GlobalActorIsolatedTypesUsability`)와 Swift 6 모드는 같은 결과다.

```text
_$s1M5takesyyyyYbScMYccF
$s1M5takesyyyyYbScMYccF ---> M.takes(@Swift.MainActor @Sendable () -> ()) -> ()
```

`ScM` 앞에 `Yb` 가 붙었다. `Yb` 가 `@Sendable` 표시다. 같은 함수가 모드에 따라 다른 symbol 로 나온다. 영향은 resilient library(library evolution 으로 ABI 를 유지하는 라이브러리)의 effectively-public API 중에서 global actor 에 묶였지만 `Sendable` 이 아닌 함수 타입을 쓰는 것 전체에 미친다. parameter 자리만이 아니다. `@Sendable` 을 직접 써서 선언해도 symbol 은 `$s1M5takesyyyyYbScMYccF` 로 같으니, 옛 symbol 을 지키려면 `@_silgen_name` 처럼 이름을 직접 고정하는 수단이 필요하다. 제안서는 API 가 이미 `@preconcurrency` 이면 mangling 이 global actor 와 `@Sendable` 을 둘 다 뺀다고 설명한다.

### region 이란?

region 은 컴파일러가 non-Sendable 값들이 어느 isolation 에 속하는지 묶어서 추적하는 단위다. 같은 region 에 있는 값들은 서로 이어져 있어서, 하나를 다른 isolation 으로 보내면 나머지도 같이 간 것으로 본다. 어느 isolation 에도 묶이지 않고 방금 만들어진 값들은 disconnected region 에 있다. disconnected region 의 값은 다른 isolation 으로 보낼 수 있지만, 보낸 뒤 원래 자리에서 다시 쓰면 컴파일러가 막는다. 자세한 규칙은 [SE-0414 글](https://haroldfromk.github.io/posts/SE-0414/)에 있다.

### non-Sendable 값을 붙잡는 global actor closure

`@Sendable` closure 는 원래 non-Sendable 값을 붙잡을 수 없다. 여러 곳에서 동시에 실행될 수 있으니 non-Sendable 값을 같이 만질 수 있기 때문이다. 그런데 `@MainActor` closure 는 main actor 에서만 실행되므로 같은 값을 동시에 만질 방법이 없다. 제안서는 그래서 `@Sendable` 이라도 non-Sendable 을 붙잡는 것을 허용한다. 그 값은 main actor 의 region 으로 넘어가면 된다. 그 값은 앞에서 본 region 으로 말하면 main actor 의 region 에 속하게 된다.

`ClosureCapture.swift`

```swift
func test() {
  let ns = NonSendable()

  let closure = { @MainActor in
    print(ns)
  }

  Task {
    await closure()
  }
}
```

6.4 의 측정이다. Swift 5 모드, flag, Swift 6 은 진단이 0개이고, complete 는 `Task` 에 대한 warning 하나다.

```text
   |   `- warning: passing closure as a 'sending' parameter risks causing data races between main actor-isolated code and concurrent execution of the closure; this is an error in the Swift 6 language mode [#RegionIsolation::SendingClosureRisksDataRace]
 9 |     await closure()
   |           `- note: closure captures 'closure' which is accessible to main actor-isolated code
10 |   }
```

closure 를 만들 때 `ns` 를 붙잡는 것은 어느 모드에서도 문제 삼지 않는다. complete 에서 나오는 warning 은 closure 가 `@Sendable` 로 추론되지 않아서 생기는 앞의 `Closure.swift` 와 같은 종류의 진단이다.

### global actor 자식 class 와 Sendable

세 번째 규칙이다. non-Sendable 부모의 자식에 `@MainActor` 를 붙이는 것이 허용된다.

`Subclass.swift`


#### Task.detached 로 isolation 을 이어받지 않는 Task 만들기

[`Task.detached`](https://developer.apple.com/documentation/swift/task/detached%28name:priority:operation:%29-795w1){:target="_blank"} 는 만든 곳의 isolation 과 우선순위를 이어받지 않는 독립된 Task 를 만든다. 그래서 closure 가 붙잡는 값은 이 Task 로 보내도 되는 값이어야 한다.

제안서의 주석은 `Capture of 'self' with non-sendable type 'IsolatedSubclass' in a @Sendable closure` 를 적는다. 6.4 에서 측정하면 이렇다. Swift 5 모드는 진단이 0개이고, complete 와 flag 는 8:10 warning, Swift 6 은 같은 줄 error 다. Swift 6 의 결과다.


`self` 는 `IsolatedSubclass` 의 인스턴스이고 `Sendable` 이 아니다. 그러니 `Task.detached` 로 보낼 수 없다는 진단이다.

### override 가 지키는 부모의 isolation

자식이 부모의 메서드를 override 하는 경우다. 제안서는 override 가 부모 메서드의 isolation 을 따라야 한다고 한다.

`SubclassOverride.swift`

```swift
class Base {
  func test() {}
}

@MainActor
class IsolatedSubclass: Base {
  var mutable = 0
  override func test() {
    super.test()
    mutable += 0
  }
}
```

```text
SubclassOverride.swift:10:5: error: main actor-isolated property 'mutable' can not be mutated from a nonisolated context
 5 | @MainActor
 6 | class IsolatedSubclass: Base {
 7 |   var mutable = 0
   |       `- note: mutation of this property is only permitted within the actor
 8 |   override func test() {
 9 |     super.test()
10 |     mutable += 0
   |     `- error: main actor-isolated property 'mutable' can not be mutated from a nonisolated context
11 |   }
12 | }
```

네 모드 모두 같다. 부모의 `test()` 는 nonisolated 이니 override 한 `test()` 도 nonisolated 이고, 그 안에서 `@MainActor` 에 묶인 `mutable` 을 고칠 수 없다. 자식이 `@MainActor` 이니 메서드도 main actor 에 묶일 것 같지만 그렇게 되지 않는다.

이유를 제안서는 두 가지로 든다. 부모 메서드의 구현이 자신이 nonisolated 라는 사실에 기댈 수 있다는 것, 예를 들어 비동기 호출 뒤에 원래 isolation 으로 돌아오는 코드가 그렇다. 그리고 자식의 메서드를 isolation 을 보존하지 않고 부르는 방법이 여럿 있다는 것이다.

- 부모 타입으로 upcast 한 뒤 부른다 (upcast 는 자식 참조를 부모 타입의 참조로 바꾸는 것이다)
- 부모의 conformance 로 만든 existential 에 담아 부른다 (conformance 는 타입이 protocol 의 요구사항을 구현한다는 약속이고, existential 은 `P` 처럼 protocol 타입 자리에 구체 타입을 숨겨 담은 값이다)
- 부모의 conformance 가 필요한 generic parameter 에 자식을 넘겨 부른다 (generic parameter 는 `T: P` 처럼 타입을 매개변수로 받는 자리다)

pitch 에서 Holly Borla 가 세 번째를 코드로 보였다. #13 에서는 `generic` 이 async 였고, #18 에서 async 가 필요 없다며 고친 동기 함수 형태를 다시 보였다. 아래는 #18 의 형태다. `Super: P` 의 요구사항 구현이 `mutable` 을 고치고, 자식 `Sub` 이 `@MainActor` 일 때다.

`SubclassGeneric.swift`

```swift
protocol P {
  func requirement()
}

class Super: P {
  var mutable = 0
  func requirement() {
    mutable += 1
  }
}

@MainActor class Sub: Super {
}

func generic<T: P>(_ t: T) {
  t.requirement()
}

@MainActor func test(s: Sub) async {
  Task.detached {
    generic(s)
  }

  s.mutable += 2
}
```

`generic(_:)` 는 `Sub` 를 `P` 로 받아서 `requirement()` 를 부른다. 이 호출은 main actor 를 거치지 않는다. `Task.detached` 안에서 `generic(s)` 를 부르는 동안 `test(s:)` 는 main actor 에서 `s.mutable += 2` 를 한다. 두 곳이 같은 `mutable` 을 동시에 만지는 data race 다. Swift 6 의 결과다.

```text
SubclassGeneric.swift:20:8: error: passing closure as a 'sending' parameter risks causing data races between main actor-isolated code and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
18 | 
19 | @MainActor func test(s: Sub) async {
20 |   Task.detached {
   |        `- error: passing closure as a 'sending' parameter risks causing data races between main actor-isolated code and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
21 |     generic(s)
   |             `- note: closure captures main actor-isolated 's'
22 |   }
23 | 
```

Swift 5 모드는 진단이 0개이고, complete 와 flag 는 20:8 warning 이다. `Sub` 가 `Sendable` 이 아니니 `Task.detached` 가 붙잡을 수 없다. Holly Borla 는 이 상황을 두고 "upcast 나 상속한 conformance 처럼 안전하지 않은 것을 하나씩 막는 별도 규칙을 만드는 대신 자식 타입이 `Sendable` 이 되지 못하게 막으면, 훨씬 이해하기 쉬운 규칙이 되고 안전성은 기존 규칙에서 따라 나온다" 고 정리했다(pitch #13).

## 기대 효과

바뀌는 것은 크게 넷이다.

첫째, `nonisolated(unsafe)` 를 덜 쓰게 된다. 값 타입의 var 속성을 protocol conformance 에서 읽으려고 `unsafe` 를 달던 코드가 `unsafe` 없는 `var` 로 정리된다. `unsafe` 는 컴파일러가 더 이상 보호하지 않겠다는 표시라서, 정말 위험한 곳과 구별하기 어려워지던 것이 줄어든다.

둘째, `@MainActor` closure 를 Task 에 넘기기 쉬워진다. 앞의 `Closure.swift` 가 flag 를 켜면 진단 없이 통과한다. `@MainActor @Sendable` 을 같이 쓰던 습관도 이제 필요 없지만, 써도 경고가 없다.

셋째, isolation 이 없는 부모 위에 `@MainActor` 자식을 만들 수 있다. 앞의 `Subclass.swift` 가 진단 없이 통과한다. `NSObject` 를 상속한 클래스나 직접 만든 기반 클래스를 둔 코드에서 이 제약이 풀렸다.

넷째, 안전성은 그대로다. 자식이 `Sendable` 이 되지 않으니 부모에서 물려받은 가변 상태가 몰래 넘어가는 구멍은 열리지 않는다. 앞의 `SubclassSmuggle.swift` 의 네 진단이 그것이다. 반대로 말하면 `@MainActor` 자식을 `Sendable` 자리에 넘기던 코드는 이제 걸린다.

## 다른 선택지는 왜 안 됐나

이 제안서는 논의가 길었던 쪽이 자식 클래스 규칙이다. 제안서 본문에 Alternatives 로 올라간 것 하나와, pitch 와 리뷰에서 오간 선택지 셋을 본다.

---

### 자식 class 의 Sendable 을 명시적으로 빼는 방법

제안서의 Alternatives Considered 에 있는 유일한 항목이다. 자식 클래스가 조용히 `Sendable` 을 잃게 하는 대신 컴파일러가 명시적 opt-out 을 요구할 수도 있었다. `~Sendable` 같은 표기를 conformance 절에 쓰는 방식이다. 자식이 `Sendable` 이 아니라는 것이 코드에 드러난다는 장점이 있다.

제안서는 세 가지 이유로 이것을 택하지 않았다. 첫째, 프로그래머는 `Sendable` 이 필요한 자리에 쓰기 전까지 그 클래스가 `Sendable` 이 아니라는 사실을 알 필요가 없다. 둘째, 쓰는 순간에는 진단에 note 를 달아 이유를 설명할 수 있다. 셋째, global actor 가 항상 `Sendable` 을 뜻하는 것도 아니다. 뒤의 `@MainActor` protocol 이 그런 예이고, 그러니 isolated 자식 클래스에 opt-out 문법을 요구하면 "`@MainActor` 가 언제 `Sendable` 을 뜻하는가" 에 대한 단순한 규칙이 남지 않는다.

pitch 의 첫 글은 `@~Sendable` attribute 와 `~Sendable` protocol 을 제안 목록에 넣고 있었다. Sima Nerush 가 pitch 막바지에 그 부분을 뺐다고 알렸다(pitch #26). 쓸 곳이 분명하지 않다는 이유였다.

수락 공지가 이 항목과 이어진다. John McCall 은 리뷰 중에 자식 클래스의 `Sendable` 을 조용히 빼는 설계에 대한 질문이 나왔고, Language Steering Group 이 원문 그대로 수락하되 이 결정을 설명하는 문단을 Alternatives 에 넣어 달라고 요청했다고 적었다(수락 #1). 그 문단이 위의 내용이고, 문단을 쓰느라 공지가 늦어졌다. [PR 2495](https://github.com/swiftlang/swift-evolution/pull/2495/files){:target="_blank"} 가 그 변경이다.

---

### 부모 subobject 를 region 으로 추적하는 방법

pitch 에서 가장 오래 이어진 논쟁이다. Nickolas_Pohilets 는 자식을 `Sendable` 로 막는 것이 불필요하게 엄격하다고 했다(pitch #10). 대신 자식 안의 부모 몫(superclass subobject)을 non-Sendable 객체로 보고, 그것이 자식의 global actor 와 연결된 region 에 속한다고 추적하자는 제안이었다. upcast 해도 그 region 이 따라간다는 것이다. 그는 이 규칙이 필요해도 required initializer 가 있는 부모의 자식에는 isolation 을 붙이지 못하게 막아야 한다는 구멍도 함께 보였다.

Holly Borla 는 이 제안이 어떻게 성립하는지 묻는 것으로 답했다(pitch #11). `Sendable` 인 인스턴스의 일부를 non-Sendable subobject 로 보는 것이 가능한지가 핵심이었다. region 분석은 `Sendable` 부분에 닿는 순간 끊기기 때문이다. 이어서 앞에서 본 generic 예제(이때는 `generic` 이 async 였다)로 upcast 없이도 부모 몫에 닿는 길이 있다고 보였고(pitch #13), 자식을 `Sendable` 로 만들지 않는 쪽이 별도 규칙을 만드는 것보다 이해하기 쉽다고 정리했다. Nickolas_Pohilets 는 이 예제에서 `generic(_:)` 가 nonisolated 이면서 async 라 현재 task 의 region 을 요구하고 자식은 main actor 에 묶여 있으니 다른 이유로 막혀야 한다고 반박했고(pitch #14), 두 사람은 region 분석이 `Sendable` 값을 어떻게 다루는지를 놓고 몇 번 더 오갔다. Holly Borla 는 `generic` 이 async 일 필요가 없다고 동기 함수 형태를 다시 보이고, 인스턴스 자체는 main actor region 에 있지 않으며, 타입에 global actor 가 붙었다는 것은 상태와 메서드가 global actor 로 보호된다는 뜻이며, `Sendable` 값은 region 분석에 들어가지도 않는다고 설명했다(pitch #18). 자식 인스턴스는 region 분석에서 하나의 값이고, 부모가 nonisolated 메서드로 non-Sendable 상태를 돌려주면 자식이 `Sendable` 일 때 그 값이 disconnected region 에 놓인다는 점도 짚었다(pitch #23).

John McCall 은 Holly Borla 의 설명을 풀어 쓰며 동의했다(pitch #16). 그 규칙이 동작하게 만들 수는 있을 것 같지만, 깨지기 쉽고 로직이 많이 필요하며 부모 클래스를 두는 의미를 상당히 꺾는다는 것이다. 클래스 참조를 부모 타입으로 자유롭게 바꿀 수 없다는 것은 객체지향에서 부자연스럽다고도 했다. 그리고 Holly Borla 의 접근이 나중에 이 규칙을 허용하는 길을 막지 않는다고 덧붙였다. 구체적인 필요가 있느냐는 질문에 Nickolas_Pohilets 는 자식을 다른 isolation 으로 보내야 하는 좋은 예가 없고 수요도 낮을 것이라고 인정했다(pitch #17). 대신 자기 규칙을 따라가다 보면 부수 효과로 얻는 장점이 있다고 했다. 부모의 메서드를 자식의 isolation 으로 의미 있게 override 할 수 있게 된다는 것이다. 그리고 자식이 `Sendable` 이 될 수 없는 이유가 isolation 검사의 허점을 가리고 있을지 모른다고 걱정했다. required initializer 가 있는 부모 아래에 isolated 자식을 두는 경우를 그 예로 물었는데, Holly Borla 는 그런 자식은 가능하고 override 하는 init 은 부모 init 과 같은 isolation 이어야 한다고 답했다(pitch #23).

결과가 지금의 규칙이다. 자식은 `Sendable` 이 아니다. 부모 몫을 region 으로 추적하는 규칙은 들어오지 않았다.

---

### @MainActor protocol 은 왜 Sendable 이 아닌가

앞에서 Alternatives 의 셋째 이유로 나온 이야기다. tcldr 이 pitch 에서 `@MainActor protocol P: AnyObject {}` 가 `static let` 에 쓰일 때 나오는 진단을 가져왔다(pitch #3). `@MainActor` class 는 되는데 `@MainActor` protocol 은 `Sendable` 이 아니라고 나온다는 것이다. Holly Borla 는 protocol 에 붙은 global actor 가 하는 일이 두 가지뿐이라고 설명했다(pitch #4). protocol 의 요구사항 모두에 global actor 를 붙이고, conformance 를 타입의 본 선언에 쓴 경우에 그 타입에 global actor 를 추론하게 하는 것이다. extension 에서 conformance 를 쓰거나 다른 파일에서 쓰면 타입 전체에 global actor 를 추론할 수 없고, 그 타입의 가변 상태는 보호받지 못할 수 있다. 그러니 `@MainActor` protocol 을 따르는 타입이 non-Sendable 일 수 있다. `Sendable` 을 요구하려면 protocol 에 명시적으로 `Sendable` 을 써야 한다. tcldr 은 이 설명을 받고 자기가 protocol 의 global actor 가 conformance 하는 타입도 같은 actor 에 묶는다고 오해했다고 알렸다(pitch #7).

6.4 에서 측정해서 확인했다. protocol 이 `Sendable` 을 따로 쓰지 않으면 값을 Task 로 보낼 수 없다.

`ProtoPlain.swift`

```swift
@MainActor protocol P: AnyObject {}

func send(_ p: P) {
  Task.detached {
    _ = p
  }
}
```

Swift 6 의 결과다.

```text
ProtoPlain.swift:4:8: error: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
2 | 
3 | func send(_ p: P) {
4 |   Task.detached {
  |        `- error: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
5 |     _ = p
  |         `- note: closure captures 'p' which is accessible to code in the current isolation context
6 |   }
7 | }
```

Swift 5 모드는 진단이 0개이고, complete 와 flag 는 같은 줄의 warning 이다. protocol 에 `Sendable` 을 직접 쓴 판이다.

`ProtoSendable.swift`

```swift
@MainActor protocol P: AnyObject, Sendable {}

func send(_ p: P) {
  Task.detached {
    _ = p
  }
}
```

이쪽은 네 모드 모두 진단이 0개다.

이 설명이 이 제안서에 필요한 것은 앞의 Alternatives 때문이다. global actor 가 어떤 선언에서는 `Sendable` 을 의미하고 다른 선언에서는 의미하지 않는데, 자식 클래스에서만 opt-out 문법을 요구하면 규칙이 더 복잡해진다.

tcldr 은 수락 공지 뒤에 비슷한 이야기를 다시 꺼냈다(수락 #2). non-Sendable GAIT 안에서 `nonisolated` 멤버가 global actor 위라고 가정할 수 있으면 `RandomAccessCollection` 같은 protocol 을 따르기 쉬울 것이라는 아이디어였다. 곧바로 글 안에서 자기 생각을 거두었다. `@MainActor` 를 너무 많이 붙여 온 탓이라는 결론이었다.

---

### actor 인스턴스에 묶인 closure

Nickolas_Pohilets 는 같은 논리가 actor 인스턴스에 묶인 closure 에도 적용되니 모든 isolated closure 가 암묵적 `@Sendable` 이어도 된다고 했다(pitch #10). Holly Borla 는 인스턴스에 묶인 closure 가 `@Sendable` 이 되려면 closure 의 타입이 그 isolation 을 보존해야 하고, 타입 시스템에서 그것을 표현하는 길은 `@isolated(any)` 뿐이라고 답했다(pitch #11). pitch 에서는 `@isolated(any)` 타입이 `@Sendable` 을 함의하는 것으로 설명했다. 제안서 Motivation 의 closure 문단 마지막 문장도 같은 이야기다. actor 인스턴스에 묶인 closure 를 그 actor 밖에서 쓸 수 있는 문맥이 없어서 지금은 그런 closure 를 작성할 수 없다는 것이다.

최종 [SE-0431](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0431-isolated-any-functions.md){:target="_blank"} 은 Alternatives Considered 의 "Implying `@Sendable`" 에서 그 함의를 뺐다. 그래서 6.4 에서 `@isolated(any)` 함수 값은 `@Sendable` 이 아니고, 이 제안서가 만든 `@Sendable` 추론의 대상도 아니다. 이 측정은 그 결과를 보이려는 것이다. `@isolated(any)` 자체는 [SE-0431 글](https://haroldfromk.github.io/posts/SE-0431/)에서 자세히 다룬다. `@isolated(any)` 함수 값을 Task 가 붙잡는 코드다.

`IsolatedAny.swift`

```swift
func run(_ c: @escaping @isolated(any) () -> Void) {
  Task {
    await c()
  }
}
```

complete 와 flag 에서는 2:3 warning, Swift 6 에서는 error 다. Swift 6 의 결과다.

```text
IsolatedAny.swift:2:3: error: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
1 | func run(_ c: @escaping @isolated(any) () -> Void) {
2 |   Task {
  |   `- error: passing closure as a 'sending' parameter risks causing data races between code in the current isolation context and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]
3 |     await c()
  |           `- note: closure captures 'c' which is accessible to code in the current isolation context
4 |   }
5 | }
```

같은 코드에 `@Sendable` 을 직접 붙인 판이다.

`IsolatedAnySendable.swift`

```swift
func run(_ c: @escaping @isolated(any) @Sendable () -> Void) {
  Task {
    await c()
  }
}
```

이쪽은 네 모드 모두 진단이 0개다. `@isolated(any)` 가 `@Sendable` 을 함의하지 않으니 Task 로 보내려면 `@Sendable` 을 직접 써야 한다.

---

그 밖에 리뷰에서 곁가지로 나온 이야기가 하나 있다. ben-cohen 은 `@main` 이 기본으로 main actor 에서 시작해야 한다고 했고(리뷰 #3), xwu 가 같은 생각이라고 거들었다(리뷰 #4). 이 제안서의 범위 밖이어서 여기서 다루지 않았다.

## 마이그레이션

기존 코드를 바꿔야 하는 곳은 많지 않다. 제안서의 Source compatibility 절은 이 제안서가 기존 코드의 해석을 바꾸지만 소스 호환성 테스트에서 문제가 없었다고 적는다. 영향은 `@Sendable` 추론에서 온다.

1. Swift 5 모드의 프로젝트는 `-strict-concurrency=complete` 에 `-enable-upcoming-feature GlobalActorIsolatedTypesUsability` 를 더해서 먼저 켜 본다. 앞의 측정에서 flag 를 켜면 `Closure.swift` 와 `LocalFunc.swift` 가 조용해졌다. 반대로 flag 없이 complete 만 켜면 `@MainActor` closure 를 Task 에 넘기는 곳마다 `sending` warning 이 나온다. 이미 Swift 6 모드이면 따로 켤 것이 없다.
2. `nonisolated(unsafe) var` 은 정리한다. 속성이 `Sendable` 타입이고 같은 모듈 안에서만 읽는다면 그냥 `var` 로 두면 된다. 다른 모듈에서도 읽어야 하면 `nonisolated var` 로 쓴다. 앞의 `VarProp.swift` 와 `VarPropExplicit.swift` 가 그 두 형태다. 타입이 non-Sendable 인 속성은 이 규칙에 들어오지 않으니 `nonisolated(unsafe)` 를 그대로 두는 것이 맞다.
3. resilient library 의 effectively-public API 에서 global actor 에 묶였지만 `Sendable` 이 아닌 함수 타입을 쓰는 곳은 symbol 이 바뀐다는 점을 본다. 앞의 `Mangle.swift` 에서 `Yb` 가 붙었다. `@Sendable` 을 직접 써도 `Yb` 는 같으니, 이미 빌드된 client 가 옛 symbol 을 찾아야 한다면 제안서가 말한 `@_silgen_name` 처럼 이름을 직접 고정하는 수단이 필요하다.
4. 자식 클래스를 `Sendable` 자리에 넘기던 코드를 찾는다. 부모가 isolation 이 없는 non-Sendable 클래스이면 `@MainActor` 자식은 이제 `Sendable` 이 아니다. 앞의 `SubclassSmuggle.swift` 와 `SubclassCapture.swift` 의 진단이 그 모양이다. 고칠 길은 값을 main actor 안에서만 쓰도록 구조를 바꾸거나, 부모 자체를 `@MainActor` 로 바꾸는 것이다. 부모가 non-final class 라면 `Sendable` 을 따르게 할 수 없고(`non-final class 'Base' cannot conform to the 'Sendable' protocol`), `@unchecked Sendable` 로 표시하는 길은 안전을 작성자가 책임진다는 뜻이다.
5. 자식의 `Sendable` 을 명시적으로 쓴 코드는 warning 을 본다. 앞의 `SubclassExplicit.swift` 의 warning 이 앞으로의 언어 모드에서 error 가 된다고 말하니 미리 지운다.

## 정리

- 이 제안서는 global actor 에 묶인 타입의 사용성을 다섯 가지 규칙으로 고친다. 값 타입의 `Sendable` var 저장 속성에는 `(unsafe)` 없이 `nonisolated` 를 쓸 수 있고 같은 모듈 안에서는 `nonisolated` 로 추론되며, global actor 함수 타입은 `@Sendable` 로 추론되며, 그 closure 는 non-Sendable 값을 붙잡을 수 있고, non-Sendable 부모의 `@MainActor` 자식은 허용되되 `Sendable` 이 아니다.
- 6.4 에서 `VarProp.swift` 는 네 모드 모두 진단이 0개다. 추론은 속성 타입이 `Sendable` 일 때만 일어나고, property wrapper 와 `lazy` 는 computed property 라서 isolation 이 남으며, class 의 `var` 는 대상이 아니고 `let` 만 통과한다. 모듈 밖에서는 명시적 `nonisolated` 가 있어야 읽는다.
- `@Sendable` 추론은 flag 나 Swift 6 에서 일어난다. 6.4 의 Swift 5 와 complete 에서는 `@MainActor () -> Void` 가 그대로이고, flag 를 켜면 `@MainActor @Sendable () -> Void` 로 읽히며 mangling 에 `Yb` 가 붙는다. `@MainActor @Sendable` 중복 표기는 경고가 없다.
- `@MainActor` closure 가 non-Sendable 값을 붙잡는 것은 허용되지만, 값이 main actor region 으로 넘어간 뒤 쓰면 region 규칙이 error 로 막는다. parameter 로 받은 값은 호출한 쪽이 들고 있어서 보낼 수 없다.
- 자식 클래스는 6.4 의 네 모드 모두 진단 없이 선언된다. 대신 `Sendable` 이 아니어서 `withDiscardingTaskGroup` 이나 `Task.detached` 로 보내는 코드가 막히고, 명시적 `Sendable` 은 모든 모드에서 warning 이다. override 는 부모의 isolation 을 따른다.
- `@MainActor` protocol 은 `Sendable` 을 뜻하지 않는다. 그래서 자식의 opt-out 문법(`~Sendable`)은 들어오지 않았고, 부모 subobject 를 region 으로 추적하는 규칙도 들어오지 않았다.
