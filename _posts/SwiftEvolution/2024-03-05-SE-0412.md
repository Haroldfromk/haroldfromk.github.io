## 한 줄 요약

전역 변수와 static 변수는 둘 중 하나여야 한다. global actor 에 묶여 있거나, 바뀌지 않으면서 `Sendable` 인 값이어야 한다. 둘 다 아니면 Swift 6 언어 모드에서 error 다. 개발자가 lock 같은 장치로 직접 동기화를 책임지는 경우에는 `nonisolated(unsafe)` 를 붙여 "여기는 컴파일러가 검사하지 말라" 고 명시적으로 빠져나온다.

---

## 어떤 문제였나

Swift 5.5 가 actor 와 `Sendable` 을 들여온 뒤로 공유 상태의 대부분은 컴파일러가 지켜 주게 되었다. actor 안의 상태는 한 번에 한 코드만 만질 수 있고, task 사이를 오가는 값은 `Sendable` 이어야 한다. 그런데 이 장치들이 닿지 않는 곳이 하나 남아 있었다. 전역 변수다.

리뷰 스레드에서 Karl 이 정리한 말이 이 제안서의 위치를 잘 보여 준다(리뷰 #4). data race 를 없애는 일은 결국 shared mutable state(여럿이 함께 쓰면서 값이 바뀌는 상태)를 다루는 일이고, Swift 프로그램에서 그런 상태는 크게 다섯 곳에 있다. 전역 변수, 클래스, C/C++/ObjC 코드, actor, unsafe pointer 다. 이 중 actor 는 안전하고 unsafe pointer 는 이름부터 unsafe 라고 밝히고 있다. 전역 변수를 닫으면 목록에서 한 줄이 지워진다. 이 제안서가 하는 일이 그 한 줄이다.

왜 전역 변수만 따로 막아야 했을까. 제안서의 Motivation 이 이유를 순서대로 든다. 지역 변수는 다른 곳에서 캡처하지 않는 한 그 함수 안에서만 닿으니 저절로 격리된다. struct 같은 value type 의 저장 프로퍼티는 exclusivity 규칙(같은 변수를 겹쳐서 접근하지 못하게 하는 규칙)이 지킨다. class 의 저장 프로퍼티는 그 class 의 인스턴스를 격리하거나 `Sendable` 검사로 넘기는 것을 막거나 actor 로 만들면 지킬 수 있다. 전부 "그 값에 닿는 길을 좁히는" 방법이다. 전역 변수는 어느 함수에서나 이름만 쓰면 닿으니 길을 좁힐 수가 없다.

---

### 전역 변수와 static 변수란?

이 글에서 전역 변수는 파일 맨 바깥에 선언한 `var` 와 `let` 이다. 여기에 타입 안에 선언한 `static var` 와 `static let` 도 포함한다. 제안서는 이 둘을 묶어 "static duration 을 가진 저장소", 즉 프로그램이 시작해서 끝날 때까지 하나만 있는 저장 공간이라고 부른다.

비유하면 건물 로비에 놓인 공용 게시판이다. 층마다 있는 개인 사물함(지역 변수)은 열쇠를 가진 사람만 쓰지만, 로비 게시판은 건물 안 누구나 아무 때나 글을 붙이고 뗄 수 있다. 어느 함수에서든, 어느 스레드에서든 이름만 부르면 닿는다.

제안서는 초기화에 대해서도 한 줄을 적어 둔다. 전역 변수는 처음 쓰일 때 초기화되는 lazy 방식이고, 이 초기화는 이미 thread-safe 하게 보장되어 있다. 여러 스레드가 동시에 처음 접근해도 초기화 코드는 한 번만 돈다. 그래서 문제는 초기화가 아니라 초기화가 끝난 뒤의 읽기와 쓰기다. 이 제안서가 다루는 것도 그 부분이다.

---

### data race 란?

data race 는 두 스레드가 같은 메모리에 동시에 접근하는데 그중 하나 이상이 값을 쓰고 있고, 순서를 정해 주는 장치가 없는 상황이다. 겉으로는 평범한 코드인데 결과가 실행할 때마다 달라진다.

`count += 1` 한 줄은 실제로는 세 단계다. 값을 읽고, 1 을 더하고, 결과를 다시 쓴다. 공용 게시판에 "현재 방문자 수: 10" 이라고 적혀 있다고 하자. 두 사람이 동시에 와서 둘 다 10 을 읽고, 각자 11 을 적는다. 방문자는 둘인데 게시판은 11 이다. 한 번의 증가가 사라졌다.

---

### 실제로 값이 사라지는 모습

말로만 하면 와닿지 않아서 직접 돌려 봤다. 10 만 번 반복하면서 두 변수를 올리는 프로그램이다. 하나는 `main.swift` 의 최상위 `var` 에 `nonisolated(unsafe)` 를 붙여 컴파일러 검사를 끈 것이고, 다른 하나는 `Mutex` 로 감싼 값이다. `nonisolated(unsafe)` 는 뒤에서 자세히 다루고, 여기서는 "컴파일러 검사를 끈 상태" 라고만 알아 두면 된다.

```swift
import Dispatch
import Synchronization

nonisolated(unsafe) var unsafeCount = 0
let safeCount = Mutex(0)

DispatchQueue.concurrentPerform(iterations: 100_000) { _ in
    unsafeCount += 1
    safeCount.withLock { $0 += 1 }
}
print("unsafeCount:", unsafeCount)
print("safeCount:", safeCount.withLock { $0 })
```

#### DispatchQueue.concurrentPerform과 Mutex로 값이 사라지는지 보기

1. [`DispatchQueue.concurrentPerform(iterations:execute:)`](https://developer.apple.com/documentation/dispatch/dispatchqueue/concurrentperform%28iterations:execute:%29){:target="_blank"} 는 `execute` closure 를 `iterations` 번 실행하되, 여러 스레드에 나눠서 동시에 돌린다. closure 에는 몇 번째 반복인지 알려 주는 `Int` 가 들어오는데 여기서는 쓰지 않아 `_` 로 받았다. 모든 반복이 끝나야 이 함수가 돌아온다. 일부러 data race 를 만들기 위해 썼다.
2. [`Mutex`](https://developer.apple.com/documentation/synchronization/mutex){:target="_blank"} 는 값을 안에 품고 한 번에 한 스레드만 그 값에 닿게 하는 lock 이다. `Mutex(0)` 은 0 을 품은 lock 을 만든다. Swift 6 의 `Synchronization` 모듈에 있고 macOS 15, iOS 18 이상에서 쓸 수 있다.
3. [`withLock`](https://developer.apple.com/documentation/synchronization/mutex/withlock%28_:%29){:target="_blank"} 은 lock 을 잡고 closure 를 실행한 뒤 푼다. closure 는 품고 있는 값에 대한 `inout` 참조를 받아서 `$0 += 1` 처럼 안전하게 바꿀 수 있다. closure 가 돌려준 값이 `withLock` 의 반환값이 되어서 마지막 줄에서 값을 읽을 때도 썼다.

네 번 돌린 결과다. `swiftc -swift-version 6 -O` 로 빌드했다.

```text
unsafeCount: 83082
safeCount: 100000
unsafeCount: 90265
safeCount: 100000
unsafeCount: 88371
safeCount: 100000
unsafeCount: 89435
safeCount: 100000
```

10 만 번을 더했는데 `unsafeCount` 는 매번 8 만 3 천에서 9 만 사이에 머문다. 대략 10% 에서 17% 의 증가가 사라졌고, 실행마다 숫자가 다르다. 반면 `Mutex` 로 감싼 쪽은 네 번 모두 정확히 10 만이다.

같은 코드를 `-sanitize=thread` 로 빌드해서 실행하면 Thread Sanitizer(실행 중 data race 를 찾아 주는 도구)가 바로 알려 준다.

```text
WARNING: ThreadSanitizer: Swift access race (pid=56448)
  Modifying access of Swift variable at 0x0001001ec008 by thread T4:
  ...
  Location is global 'unsafeCount' at 0x0001001ec008 (race_tsan+0x100008008)
```

"Location is global 'unsafeCount'" 가 핵심이다. 레이스가 난 자리가 전역 변수라는 뜻이다. 이 사고가 일어나는 자리가 바로 이 제안서가 막으려는 곳이다.

`nonisolated(unsafe)` 를 빼고 `-swift-version 6` 으로 컴파일하면 어떻게 될까. 6.4 에서 실제로 돌려 보면 error 가 아니라 warning 하나만 나오고 빌드가 된다.

```text
main.swift:8:5: warning: main actor-isolated var 'unsafeCount' can not be mutated from a nonisolated context
```

이 실험이 `main.swift` 라서 그렇다. `main.swift` 의 최상위 변수는 SE-0343 규칙으로 이미 `@MainActor` 에 묶여 있고(뒤의 "스크립트 모드의 최상위 변수" 절에서 다룬다), 그 변수를 `DispatchQueue.concurrentPerform` 의 closure 에서 바꾸는 것은 isolation 위반이다. 다만 Dispatch 의 closure 가 `@preconcurrency` 로 선언되어 있어서 error 가 warning 으로 내려간다. `main.swift` 가 아닌 파일의 전역 `var` 였다면 이 제안서의 error 가 선언에서 나온다. 이 글의 실험은 `main.swift` 한 파일로 돌렸기 때문에 "MainActor warning" 이고, 일반 소스 파일의 전역 `var` 는 "SE-0412 error" 라고 나눠서 기억하면 된다.

### Swift 언어 모드란?

이 글에서 "Swift 5 모드" 와 "Swift 6 모드" 는 컴파일러 버전이 아니라 언어 모드를 가리킨다. 컴파일러는 Xcode 27 에 들어 있는 Swift 6.4 하나인데, 같은 컴파일러가 `-swift-version 5` 를 받으면 Swift 5 의 규칙으로, `-swift-version 6` 을 받으면 Swift 6 의 규칙으로 코드를 검사한다. Xcode 에서는 빌드 설정의 Swift Language Mode 가 이 옵션이다.

비유하면 같은 시험관이 채점 기준표를 두 벌 갖고 있는 것이다. 옛 기준표(Swift 5 모드)로는 기존 코드가 그대로 합격하도록 data race 검사를 느슨하게 두었고, 새 기준표(Swift 6 모드)에서는 같은 검사를 error 로 올린다. 이 글에서 "Swift 6 에서 error" 라고 쓰면 6.4 컴파일러에 `-swift-version 6` 을 준 결과다. Swift 5 모드에서도 일부 검사를 미리 켜 볼 수 있는데, 그 스위치가 아래에서 설명할 upcoming feature flag 와 `-strict-concurrency` 다.

### global actor 와 isolation 이란?

actor 는 자기 안의 상태를 한 번에 한 코드만 만지게 해 주는 타입이다. 은행 창구에서 번호표를 뽑고 한 명씩 들어가는 것과 같다. 이렇게 상태를 보호받는 것을 actor isolation(격리)이라고 한다. global actor 는 프로그램 전체에 하나뿐인 actor 를 이름으로 가리키는 장치이고, 대표가 main thread 에 대응하는 `@MainActor` 다. 어떤 변수나 함수에 `@MainActor` 를 붙이면 "이것은 main actor 의 창구 안에 있다" 는 표시가 되어서, 다른 곳에서 그것을 쓰려면 창구에 줄을 서야 한다. 비동기 코드에서는 그 줄서기가 `await` 다.

이 글에는 "nonisolated context" 라는 말이 자주 나온다. 어느 actor 에도 속하지 않은 코드, 예를 들어 아무 표시도 없는 평범한 동기 함수 안을 가리킨다. 창구 밖에 서 있는 코드이니 창구 안의 변수를 바로 만질 수 없다. 두 개념의 자세한 설명은 이 시리즈의 [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/)에 있다.

---

### Sendable 이란?

[`Sendable`](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 은 "이 타입의 값은 task 나 actor 의 경계를 넘겨 주고받아도 안전하다" 는 표시다. 회의에서 나눠 주는 인쇄물과 벽에 걸린 공용 화이트보드의 차이로 보면 쉽다. 인쇄물은 사람마다 복사본을 들고 있으니 각자 낙서해도 서로 영향이 없다. `Int` 나 값만 담은 `struct` 가 이쪽이다. 화이트보드는 하나뿐인 것을 여럿이 같이 쓰므로 두 사람이 동시에 지우고 쓰면 엉망이 된다. 내용을 바꿀 수 있는 `class` 인스턴스가 이쪽이어서 기본적으로 `Sendable` 이 아니다. 이 제안서가 요구하는 "immutable 이면서 `Sendable`" 은 "바뀌지 않는 인쇄물" 이라는 뜻이다. 누가 어디서 읽어도 같은 내용이니 안전하다.

### Swift 5 모드에서는 조용했던 코드

문제는 이런 코드가 지금까지 아무 경고 없이 컴파일되었다는 점이다. 이 제안서의 규칙을 시험해 볼 파일 하나를 만들었다. 전역 변수와 static 변수를 여러 모양으로 선언해 둔 파일이다.

```swift
import Dispatch

class Counter { var n = 0 }

var value = 1                       // 1. 전역 var
let shared = Counter()              // 2. non-Sendable let
let limit = 10                      // 3. Sendable let: OK
@MainActor var title = "home"       // 4. global actor: OK

struct Config {
    static var verbose = false      // 5. static var
    static let counter = Counter()  // 6. static non-Sendable let
}

nonisolated(unsafe) var cache: [String: Int] = [:]   // 7. opt-out

func f() { value = 2 }

func local() async {
    nonisolated(unsafe) var v = 1
    let task = Task { v = 2; return v }
    print(await task.value)
}
```

#### MainActor와 Task로 격리와 비동기 작업 표현하기

- [`@MainActor`](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 는 main thread 에 대응하는 global actor 다. 선언에 붙이면 그 선언은 main actor 에 묶이고, 쓰려는 쪽도 main actor 위에 있어야 한다. 아래에서 자세히 본다.
- [`Task`](https://developer.apple.com/documentation/swift/task){:target="_blank"} 는 비동기 작업 하나를 만든다. `Task { ... }` 로 closure 를 넘기면 바로 돌기 시작하고, 변수에 담아 둔 `task.value` 를 `await` 하면 closure 가 돌려준 값을 기다려 받는다. 여기서는 `local()` 이 지역 변수를 다른 실행 맥락으로 넘기는 상황을 만들려고 썼다.

이 글의 진단은 모두 이런 명령으로 뽑았다. `-emit-sil` 은 타입 검사 뒤 단계까지 컴파일해서 진단을 빠짐없이 내고, `-o /dev/null` 은 결과 파일을 버린다. `-parse-as-library` 는 이 파일을 최상위 코드가 없는 일반 소스 파일로 다루라는 옵션이다. 앱에서 `main.swift` 가 아닌 파일과 같은 조건이 된다. 이 옵션 없이 파일 하나를 그냥 컴파일하면 스크립트 모드가 되어 결과가 달라지는데, 뒤의 "스크립트 모드의 최상위 변수" 절에서 보여 준다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 5 Globals.swift
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 6 Globals.swift
```

Swift 5 모드에서는 진단이 한 줄도 나오지 않는다. 같은 파일을 Swift 6 모드로 검사하면 error 가 네 개 나온다. 다음 절에서 하나씩 본다.

## 무엇이 바뀌나

규칙은 한 문장이다. 전역 변수와 static 변수는 global actor 로 isolate 되어 있거나, immutable 이면서 `Sendable` 이어야 한다. 제안서는 이 요구를 declaration 시점에, 즉 변수를 선언한 자리에서 타입 검사기가 확인한다고 한다. 변수를 쓰는 자리를 일일이 따지는 것이 아니라 선언을 보고 판정한다.

앞의 `Globals.swift` 의 `func f() { value = 2 }` 가 그 증거다. 이 변수를 바꾸는 `f()` 에는 진단이 하나도 붙지 않고, error 는 변수를 선언한 5 번째 줄(5:5)에만 나온다. 제안서 Motivation 의 예는 달랐다. 거기서는 `f()` 안의 `value = 2` 자리에 "reference to var 'value' is not concurrency-safe because it involves shared mutable state" 라는 use-site warning 이 붙는 모양으로 적혀 있다. 6.4 에서 실제로 돌려 보면 같은 모듈 안의 전역 변수는 선언에서만 error 가 나고 쓰는 자리는 조용하다. 다른 모듈에서 import 한 전역 변수는 사정이 다르다. 내 컴파일에서는 그 선언을 검사할 수 없어서, 쓰는 자리에서 막는다. 아래 "다른 모듈과 C 의 전역 변수" 절의 error 가 바로 그것이다.

![전역 변수나 static 변수 하나가 판정되는 흐름: global actor 에 묶였으면 통과, 아니면 let 이면서 Sendable 인지 보고, 그것도 아니면 nonisolated(unsafe) 인지 본다. 셋 다 아니면 Swift 6 모드에서 error 다.](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-03-05-SE-0412/se-0412-global-rule.png)

판정은 위에서 아래로 갈림길 세 개를 지난다. 첫째, `@MainActor` 같은 global actor 에 묶였는가. 둘째, 그렇지 않다면 `let` 이면서 `Sendable` 인가. 셋째, 그것도 아니라면 `nonisolated(unsafe)` 로 직접 책임지겠다고 표시했는가. 어느 쪽에도 해당하지 않으면 error 이고, 이 error 가 Swift 6 모드에서 새로 생기는 것이다.

### 규칙이 보는 선언 일곱 가지

앞 절에서 만든 파일을 `-parse-as-library -swift-version 6` 으로 검사한 결과를 선언별로 모았다.

| 선언 | Swift 6 결과 |
| --- | --- |
| 1. `var value = 1` | error |
| 2. `let shared = Counter()` (non-Sendable class) | error |
| 3. `let limit = 10` | 통과 |
| 4. `@MainActor var title = "home"` | 통과 |
| 5. `static var verbose = false` | error |
| 6. `static let counter = Counter()` | error |
| 7. `nonisolated(unsafe) var cache` | 통과 |

error 네 개의 원문이다. 1 번은 이렇다.

```text
Globals.swift:5:5: error: var 'value' is not concurrency-safe because it is nonisolated global shared mutable state [#MutableGlobalVariable]
```

2 번은 변수가 `let` 인데도 걸린다. 값을 못 바꿔도 `Counter` 는 class 라서, 인스턴스 안의 `n` 을 바꿀 수 있기 때문이다.

```text
Globals.swift:6:5: error: let 'shared' is not concurrency-safe because non-'Sendable' type 'Counter' may have shared mutable state [#MutableGlobalVariable]
```

5 번과 6 번은 같은 규칙을 static 프로퍼티에 적용한 것이다.

```text
Globals.swift:11:16: error: static property 'verbose' is not concurrency-safe because it is nonisolated global shared mutable state [#MutableGlobalVariable]
Globals.swift:12:16: error: static property 'counter' is not concurrency-safe because non-'Sendable' type 'Counter' may have shared mutable state [#MutableGlobalVariable]
```

`let limit = 10` 은 `Int` 가 `Sendable` 이고 바꿀 수 없어서 어디서 읽어도 안전하다. `@MainActor var title` 은 `var` 인데도 통과한다. main actor 에 묶여서 "누가 만지는가" 가 정해지기 때문이다.

컴파일러는 error 에 note 를 붙여서 고칠 방향까지 알려 준다. 1 번 변수에 붙은 세 개는 이렇다.

```text
note: convert 'value' to a 'let' constant to make 'Sendable' shared state immutable
note: add '@MainActor' to make var 'value' part of global actor 'MainActor'
note: disable concurrency-safety checks if accesses are protected by an external synchronization mechanism
```

이 셋이 판정 흐름의 세 갈림길에 하나씩 대응한다. 첫째는 `let` 으로 바꿔서 immutable 로 만들라는 것, 둘째는 `@MainActor` 에 묶으라는 것, 셋째는 이미 외부 동기화로 지키고 있다면 검사를 끄라는 것이다. 2 번처럼 이미 `let` 인 변수에는 첫 번째 note 가 없다. 바꿀 수 없다는 조건은 이미 채웠는데 타입이 문제이기 때문이다. 진단 문서는 [Mutable global variable Docs](https://docs.swift.org/compiler/documentation/diagnostics/mutable-global-variable){:target="_blank"} 에 있다.

### global actor 에 묶기

`@MainActor var title = "home"` 처럼 global actor 에 묶으면 변수는 `var` 로 남아도 된다. 대신 그 변수를 쓰는 쪽도 같은 actor 위에 있어야 한다. 묶인 변수를 일반 동기 함수에서 읽으면 어떻게 되는지 해 봤다.

```swift
@MainActor var title = "home"
func read() { print(title) }
func readAsync() async { print(await title) }
```

위 세 줄은 `Local.swift` 의 7~9 줄이다. Swift 6 결과다.

```text
Local.swift:8:21: error: main actor-isolated var 'title' can not be referenced from a nonisolated context
note: add '@MainActor' to make global function 'read()' part of global actor 'MainActor'
```

동기 함수 `read()` 는 main actor 위에서 돈다는 보장이 없어서 안 된다. 해결은 두 갈래다. 함수에도 `@MainActor` 를 붙여서 같은 actor 위로 올리거나, `readAsync()` 처럼 비동기 함수에서 `await` 로 읽는 것이다. `await` 는 "main actor 로 건너가서 읽고 돌아온다" 는 뜻이라 이 경우에는 통과한다.

여기서 알아 둘 점이 있다. global actor 에 묶는다고 문제가 사라지는 것이 아니다. "누가 언제 만질 수 있는가" 를 사람 머릿속 약속에서 타입 시스템으로 옮기는 것이다. 어느 스레드에서든 부르던 코드는 이제 main actor 를 거쳐야 하고, 그 비용을 치르는 대신 data race 는 컴파일 단계에서 막힌다.

### 바뀌지 않는 Sendable 값으로 만들기

더 쉬운 길은 변수를 `let` 으로 만들고 타입을 `Sendable` 로 만드는 것이다. 값이 바뀌지 않으니 어디서 읽어도 같은 값이다. `let limit = 10` 이 그 예다.

그런데 카운터나 캐시처럼 값이 바뀌어야 하는 전역이 필요할 때는 어떻게 할까. 바뀌는 부분을 lock 안에 넣고, 그 lock 을 품은 타입을 `Sendable` 로 만들어 `let` 으로 두면 된다. 리뷰에서 Alejandro 가 짚은 부분이다(리뷰 #7). atomic, lock, concurrent 자료구조는 `let` 이면서 `Sendable` 이니 이 규칙에 그대로 들어맞는다. 다만 Alejandro 가 붙인 조건이 하나 있다. lock 이 감싸고 있는 값 자체도 `Sendable` 이어야 한다. lock 은 한 번에 한 곳만 값에 접근하게 해 줄 뿐이고, 값이 lock 밖으로 새어 나가면 그때부터는 다시 공유 상태가 되기 때문이다. 실제로 해 보았다.

```swift
import Synchronization
final class Logger: Sendable {
    private let lines = Mutex<[String]>([])
    func log(_ s: String) { lines.withLock { $0.append(s) } }
}
let logger = Logger()
enum Settings { @MainActor static var theme = "light" }
```

#### Mutex로 Sendable class 안의 배열 지키기

`Logger` 는 `final class` 이고 `Sendable` 을 선언했다. class 가 `Sendable` 이 되려면 조건이 있다. 먼저 `final` 이어야 한다. 하위 클래스가 나중에 변경 가능한 프로퍼티를 더할 수 있기 때문이다. 상속 쪽은 상위 클래스가 없거나 `NSObject` 여야 한다. 저장 프로퍼티는 모두 `let` 이고 그 타입도 `Sendable` 이어야 하는데, `Mutex` 가 `Sendable` 이라서 `lines` 가 통과한다. 안쪽에서는 [`withLock`](https://developer.apple.com/documentation/synchronization/mutex/withlock%28_:%29){:target="_blank"} 으로 lock 을 잡고 배열에 추가한다. 이미 설명한 `Mutex` 와 같은 모양이다.

`let logger = Logger()` 는 6.4 의 Swift 6 모드에서 진단이 하나도 없다. 값이 바뀌는 것은 맞지만 바뀌는 길이 전부 lock 을 거치기 때문이다. `enum Settings` 의 `@MainActor static var theme` 도 통과한다. static 변수도 같은 규칙이라 global actor 에 묶으면 된다.

pitch 에서 Joe Groff 가 가리킨 장기 방향이 이것이다(pitch #10). noncopyable 타입(복사할 수 없는 타입)이 생기면 mutex 로 감싼 값을 "immutable 처럼" 보이는 타입으로 만들어 `let` 에 둘 수 있게 된다. 그 방향이 Swift 6 의 `Mutex`(SE-0433) 로 이어졌다. 위 예제의 `Mutex` 가 그 결과물이다.

### nonisolated(unsafe) 로 빠져나오기

모든 전역을 `@MainActor` 나 `let` 으로 바꿀 수 있는 것은 아니다. Karl 이 pitch 에서 이 질문을 던졌다(pitch #5). mutex 로 직접 지키고 있는 mutable 전역은 어떻게 하느냐는 것이다. 그 전역은 어느 actor 에도 속하지 않지만, 직렬화된 곳에서만 접근한다고 개발자가 책임질 수 있다. 이런 경우의 출구가 필요하다는 이야기였다. John McCall 이 SE-0306 과 SE-0313 에 있던 `nonisolated(unsafe)` 를 다시 꺼내자고 답했고(pitch #17), 그것이 제안서에 들어갔다.

앞 절 파일의 7 번 `nonisolated(unsafe) var cache` 와 아래의 `nonisolated(unsafe) let shared = Counter()` 둘 다 진단이 없다.

```swift
class Counter { var n = 0 }
nonisolated(unsafe) let shared = Counter()
func bump() { shared.n += 1 }
```

이 세 줄은 `Local.swift` 의 11~13 줄이다.

`unsafe` 는 말 그대로다. 컴파일러가 확인을 포기한다는 뜻이고, 런타임 안전을 보장해 주지 않는다. 앞에서 본 race 실행 결과가 정확히 `nonisolated(unsafe)` 를 붙인 변수에서 나온 것이었다. 붙이는 순간 그 변수의 안전은 컴파일러가 아니라 붙인 사람의 몫이 된다.

리뷰에서는 이 출구에 안전망을 더하자는 의견이 나왔다. filip-sakel 은 `nonisolated(unchecked)` 라는 이름으로 런타임에 data race 를 잡아 주는 assertion 을 켜면 어떻겠느냐고 물었다(리뷰 #3). Sophia 는 그런 동적 검사가 이미 exclusivity enforcement 로 있다고 답했다(리뷰 #5). exclusivity enforcement 는 같은 변수에 겹치는 접근이 생기면 런타임에 잡아내는 장치다. 제안서도 이를 짚으면서, 동기화를 잘못 구현하면 exclusivity 검사나 Thread Sanitizer 가 잡아낼 수 있다고 적는다.

### 지역 변수에도 쓰는 nonisolated(unsafe)

리뷰에서 가장 큰 변화를 이끈 의견은 Doug Gregor 의 것이었다(리뷰 #11). 제안서는 `nonisolated(unsafe)` 를 "any form of storage" 에 붙일 수 있다고 하면서도 전역 변수 얘기만 했는데, 캡처된 지역 변수에도 같은 상황이 있다는 것이다. 한 번만 실행되는 `@Sendable` closure 에서 지역 변수를 바꾸는 패턴이다. 개발자는 안전하다는 것을 알지만 컴파일러는 모른다.

Doug 의 예를 파일로 만들어 돌려 봤다.

```swift
func runOnce(_ body: @escaping @Sendable () -> Void) { body() }

func myFunc() {
    var myValue = 17
    runOnce { myValue = 19 }
    print(myValue)
}

func myFunc2() {
    nonisolated(unsafe) var myValue = 17
    runOnce { myValue = 19 }
    print(myValue)
}
```

Swift 6 결과다. `myFunc` 만 걸리고 `myFunc2` 는 진단이 없다.

```text
Local2.swift:5:15: error: mutation of captured var 'myValue' in concurrently-executing code [#SendableClosureCaptures]
```

[`@Sendable`](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} closure 는 다른 스레드에서 실행될 수 있어서, 캡처한 `var` 를 바꾸는 것을 컴파일러가 막는다. `myFunc2` 처럼 지역 변수에 `nonisolated(unsafe)` 를 붙이면 "이 변수는 내가 안전함을 안다" 고 알려서 이 진단을 끌 수 있다.

Doug 의 질문에 Sophia 는 구현 PR 을 바로 올려서 답했다(리뷰 #14). "이제 가능하다" 는 한 줄이었다. 이 내용은 제안서 revision history 에 "clarified `nonisolated(unsafe)` for local variables" 로 들어갔다.

제안서 본문에는 `Task { value = 2 }` 를 쓰는 지역 변수 예가 있다. 앞 절의 `Globals.swift` 에 있는 `local()` 이 그 모양인데, 6.4 컴파일러에서는 `nonisolated(unsafe)` 를 빼고 `var v = 1` 로만 써도 진단이 나오지 않는다. 그 사이에 [SE-0414 region-based isolation](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0414-region-based-isolation.md){:target="_blank"} 이 들어와서, `Task` closure 로 지역 변수를 넘기는 것이 안전한 경우를 컴파일러가 구분할 수 있게 되었기 때문이다. region-based isolation 은 값이 어느 영역(region)에서만 접근되는지를 흐름을 따라 추적하는 분석이다. 값을 다른 task 로 넘겨 버리고 그 뒤로 이쪽에서 건드리지 않으면 안전하다고 보고, 넘긴 뒤에도 만지면 막는다. 넘기는 쪽 인자 자리가 `sending` 이고, 이것은 [SE-0430 sending](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0430-transferring-parameters-and-results.md){:target="_blank"} 에서 들어왔다.

차이를 눈으로 보려고 `local()` 을 두 모양으로 돌려 봤다. 먼저 `Task` 를 만든 뒤 지역 변수를 건드리지 않는 모양이다. 진단이 0 줄이다.

```swift
func local() async {
    var v = 1
    let task = Task { v = 2; return v }
    print(await task.value)
}
```

이번에는 `Task` 를 만든 직후에 `print(v)` 한 줄을 더했다.

```swift
func local() async {
    var v = 1
    let task = Task { v = 2; return v }
    print(v)
    print(await task.value)
}
```

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 6 Region.swift
```

```text
Region.swift:3:16: error: sending value of non-Sendable type '() async -> Int' risks causing data races [#RegionIsolation::SendingRisksDataRace]
note: Passing value of non-Sendable type '() async -> Int' as a 'sending' argument to initializer 'init(name:priority:operation:)' risks causing races in between local and caller code
note: access can happen concurrently
```

`v` 를 품은 closure 가 `Task` 로 넘어간 뒤에 `local()` 이 `print(v)` 로 같은 `v` 를 읽으면, 두 곳이 동시에 같은 변수에 접근할 수 있다. 컴파일러는 이것을 `sending` 인자의 data race 위험으로 잡는다. 정리하면 "Task 에 넘긴 뒤 이쪽에서 다시 건드리지 않으면 통과하고, 건드리면 error" 다. 값이 지역 변수라서 전역 변수의 규칙과는 다른 층의 문제지만, `nonisolated(unsafe)` 로 컴파일러를 끄는 쪽이 아니라 코드 모양으로 안전을 증명하는 길이 따로 있다는 점이 눈에 띈다. 그래서 이 글에서는 `nonisolated(unsafe)` 를 확실히 보여 주는 `@Sendable` closure 예로 설명했다.

### 스크립트 모드의 최상위 변수

스크립트 모드는 파일의 첫 줄부터 위에서 아래로 바로 실행되는 최상위 코드를 허용하는 컴파일 방식이다. `main.swift` 가 그렇고, `swiftc` 에 파일 하나만 주면 그 파일도 이 모드가 된다. `main.swift` 같은 top-level code 가 있는 파일에서는 사정이 조금 다르다. SE-0343 때문에 이런 파일의 최상위 변수는 이미 암묵적으로 `@MainActor` 에 묶여 있다. 제안서가 "top-level global variables are already implicitly isolated" 라고 적은 대목이다. pitch 에서 wadetregaskis 가 이 점을 헷갈려 했고, Sophia 는 이렇게 정리했다(pitch #8, #12). 파일이 하나뿐인 컴파일이면 모든 전역이 최상위라서 해당되는 것은 static 멤버뿐이고, 파일이 여러 개가 되면 `main.swift` 가 아닌 파일의 전역이 이 제안서의 대상이 된다.

```swift
var counter = 0
func inc() { counter += 1 }
```

이 `main.swift` 를 Swift 6 로 검사하면 이렇게 나온다.

```text
main.swift:2:14: error: main actor-isolated var 'counter' can not be mutated from a nonisolated context
note: add '@MainActor' to make global function 'inc()' part of global actor 'MainActor'
```

`counter` 가 이미 main actor 에 묶여 있다는 증거다. 이번 제안서가 새로 막는 것이 아니라 SE-0343 이 이미 해 둔 일이고, 앞 절의 `read()` 와 같은 종류의 error 다.

앞 절의 `Globals.swift` 도 `-parse-as-library` 를 빼고 파일 하나로 컴파일하면 스크립트 모드가 된다. 6.4 에서 실제로 돌려 보면 진단이 달라진다.

```bash
xcrun swiftc -emit-sil -o /dev/null -swift-version 6 Globals.swift
```

```text
Globals.swift:8:16: error: top-level code variables cannot have a global actor
Globals.swift:11:16: error: static property 'verbose' is not concurrency-safe because it is nonisolated global shared mutable state [#MutableGlobalVariable]
Globals.swift:12:16: error: static property 'counter' is not concurrency-safe because non-'Sendable' type 'Counter' may have shared mutable state [#MutableGlobalVariable]
Globals.swift:17:12: error: main actor-isolated var 'value' can not be mutated from a nonisolated context
```

1 번 `var value` 와 2 번 `let shared` 의 error 는 사라졌다. 최상위 변수라서 이미 `@MainActor` 에 묶인 것으로 취급되기 때문이다. 대신 그 변수를 일반 함수 `f()` 에서 바꾸는 17 번째 줄(17:12)에 main actor 위반이 나온다. 이미 `@MainActor` 를 직접 붙인 4 번 `title` 은 8:16 에서 "top-level code variables cannot have a global actor" 가 된다. 스크립트 모드의 최상위 변수는 암묵적으로 main actor 에 묶여 있어서 따로 붙일 수 없다는 뜻이다. static 멤버인 5 번과 6 번(11:16, 12:16)은 그대로 남는다. `Local.swift` 도 같다. 7 번째 줄의 `@MainActor var title` 에 같은 error(7:16)가 하나 더 붙는다. Sophia 가 "파일이 하나뿐인 컴파일이면 해당되는 것은 static 멤버뿐" 이라고 한 말(pitch #12)이 이 결과로 그대로 확인된다.

이 암묵적 `@MainActor` 가 곤란한 경우도 있다. Alejandro 가 물었다(리뷰 #7). lock 이나 atomic 전역까지 main actor 에 묶이면 어떻게 하느냐는 것이다. Sophia 의 답은 그런 전역을 struct 안의 `static` 으로 옮기라는 것이었다(리뷰 #9). 암묵적 `@MainActor` 는 최상위 변수에만 붙기 때문이다.

제안서는 이 자리에서 생기는 문법 모호함도 하나 적는다. `nonisolated` 는 contextual keyword(그 자리에서만 키워드로 읽히고 다른 곳에서는 평범한 식별자로 쓸 수 있는 단어)라서, 스크립트 모드에서 `nonisolated(unsafe)` 를 변수 선언 바로 앞줄에 따로 적으면 `nonisolated` 라는 함수에 `unsafe` 를 인자로 넘기는 호출로도 읽힌다. 인자가 라벨 없는 `unsafe` 하나이고 변수 선언 앞에 있으면 키워드로 읽도록 정했다. 대가로, 정말 그런 이름의 함수를 그 자리에서 부르던 스크립트는 깨진다. 제안서의 Source compatibility 절에 이 점이 적혀 있다.

### 다른 모듈과 C 의 전역 변수

전역 변수가 다른 모듈에 있으면 어떻게 될까. 그 모듈이 아직 이 규칙을 모르면 선언부터 위반일 수 있고, 내 코드가 고칠 수 있는 것도 아니다. 두 경우를 직접 만들어 봤다. 하나는 Swift 5 모드로 빌드한 모듈이고, 다른 하나는 C 헤더로 만든 모듈이다.

```swift
public var legacyCount = 0
public class Box { public var n = 0; public init() {} }
public let legacyBox = Box()
```

```c
extern int gCounter;
```

모듈을 만드는 과정은 이렇다. Swift 쪽은 Swift 5 모드로 모듈을 만들고, C 쪽은 헤더 옆에 `module.modulemap` 을 둔다.

```text
module CLegacy { header "c.h" export * }
```

```bash
xcrun swiftc -emit-module -module-name Legacy -swift-version 5 -parse-as-library \
    -emit-module-path mod/Legacy.swiftmodule mod/Legacy.swift
```

이 모듈을 쓰는 쪽은 `-I` 로 모듈 위치를 알려 준다. Swift 모듈은 `-I mod`, C 모듈은 `-I cmod` 다.

```bash
xcrun swiftc -emit-sil -o /dev/null -swift-version 6 -I mod UseLegacy.swift
xcrun swiftc -emit-sil -o /dev/null -swift-version 6 -I cmod UseC.swift
```

그냥 `import` 한 뒤 Swift 6 로 쓰면 둘 다 error 다.

```swift
import Legacy
func use() async { legacyCount += 1; print(legacyBox.n) }
```

```text
UseLegacy.swift:2:20: error: reference to var 'legacyCount' is not concurrency-safe because it involves shared mutable state
```

이 파일에서 error 가 나는 것은 mutable 전역인 `legacyCount` 하나다. non-Sendable 인 `legacyBox` 를 읽는 쪽은 6.4 컴파일러가 진단을 내지 않았다.

```swift
import CLegacy
func use() async { gCounter += 1 }
```

```text
UseC.swift:2:20: error: reference to var 'gCounter' is not concurrency-safe because it involves shared mutable state
```

이번에는 import 에 [`@preconcurrency`](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} 를 붙여 본다.

```swift
@preconcurrency import Legacy
func use() async { legacyCount += 1; print(legacyBox.n) }
```

```swift
@preconcurrency import CLegacy
func use() async { gCounter += 1 }
```

6.4 의 Swift 6 모드에서 두 파일 모두 진단이 나오지 않는다. 이 `@preconcurrency import` 는 SE-0337 에서 온 장치다. 아직 동시성 정보가 없는 모듈을 들여오면서 그 모듈의 선언에 대한 isolation 검사를 가라앉힌다.

제안서와 6.4 의 결과는 두 군데가 다르다. 제안서는 C 와 C++ 선언이 암묵적으로 `@preconcurrency` 로 들어오는 것으로 적고, `@preconcurrency import` 를 쓰더라도 사용하는 자리에서 warning 이 남는다고 한다. 6.4 에서 실제로 돌려 보면 첫째, `import CLegacy` 로 평범하게 들여온 C 전역 변수도 위의 `UseC.swift` 처럼 error 가 된다. 암묵적으로 가라앉지 않으니 `@preconcurrency import` 를 직접 써 줘야 한다. 둘째, 그렇게 쓰고 나면 사용하는 자리의 warning 도 없이 진단이 아예 나오지 않는다. 이 글의 나머지는 6.4 의 결과를 기준으로 한다.

이 규칙은 리뷰 중에 모양이 바뀌었다. 처음 제안서는 C 의 mutable 전역 변수를 암묵적으로 `nonisolated(unsafe)` 로 간주한다고 적었다. pitch 에서 John McCall 이 낸 방향이었다(pitch #23). ordinary C 전역 변수를 쓰는 API 는 드물고, 그런 API 는 `strtok`(문자열을 구분자로 잘라 가며 내부 전역 상태를 기억하는 C 함수)처럼 원래 조심해서 써야 하는 것들이라는 이유였다. 그런데 Doug Gregor 가 이것을 `@preconcurrency` 로 설명하자고 했다(리뷰 #11). 제안서의 설명으로는 C 와 C++ 선언이 원래 `@preconcurrency` 로 들어오니, "C 는 특별 취급" 대신 "`@preconcurrency` 로 들어온 선언은 검사를 가라앉힌다" 는 Swift 의 일반 규칙으로 말하면 C 를 포함하면서도 더 일관된다. Sophia 가 이 제안을 받아 revision 을 썼고(리뷰 #14), 리뷰 중 두 번의 수정 가운데 하나가 이것이다.

이 설계에는 우려도 있었다. wadetregaskis 는 C++ 라이브러리를 들여온 Swift 개발자가 컴파일러가 안전을 보장한다고 착각하기 쉽다고 했고(리뷰 #2), benlings 는 가져올 때 이름에 `unsafe` 를 붙이거나 `@preconcurrency(unsafe) import` 같은 표시를 요구하자고 했다(리뷰 #8). Sophia 는 어떤 안도 실제 안전을 더해 주지는 못한다고 답했다(리뷰 #6). 이름이 몰래 바뀌면 오히려 혼란스럽다고도 했다(리뷰 #10). 그래서 C 쪽에서 `__attribute__((swift_attr("@MainActor")))` 로 isolation 을 붙이거나, 안전한 Swift API 로 감싸 쓰는 방법이 남았다.

`errno` 같은 thread-local 변수(스레드마다 따로 한 벌씩 갖는 전역 변수)는 pitch 에서 따로 다뤘다. ktoso 는 `errno` 값이 `await` 를 거치면 다른 스레드에서 읽혀서 엉뚱한 값이 되고, 심지어 중간의 malloc(C 의 메모리 할당 함수)이 값을 덮어쓸 수도 있다고 설명했다(pitch #21). Doug Gregor 는 모델을 하나 제안했다(pitch #26). `Sendable` 타입의 thread-local 은 동기 코드 안에서는 자유롭게 접근하게 하고, non-Sendable 타입은 값이 경계를 넘어갈 수 있으니 금지하며, 비동기 함수에 `inout` 으로 넘기는 것도 막자는 내용이다. 이 제안서의 범위는 아니고 별도 문제로 남았다.

제안서의 Alternatives considered 에 세 가지가 있고, pitch 에서 같은 이야기가 더 길게 오갔다.

### 접근마다 자동으로 lock 걸기

전역 변수를 읽고 쓸 때마다 컴파일러가 알아서 lock 을 거는 방법이 있다. 메모리 안전은 지켜지지만 thread safety 는 아니라는 것이 제안서의 지적이다. 이런 코드를 보자.

```swift
global = global * 2
```

읽기와 쓰기가 각각 lock 으로 보호되어도, 읽고 나서 쓰기 전에 다른 스레드가 값을 바꿀 수 있다. 앞의 게시판 비유로 말하면, 게시판을 읽는 순간과 숫자를 고쳐 적는 순간이 각각 한 사람씩 들어가게 되어 있어도 그 사이에 다른 사람이 끼어들 수 있다. 개발자는 한 줄로 썼으니 한 덩어리로 실행될 것이라 믿는다. 그 믿음을 깨지 않으려면 "읽기-계산-쓰기" 전체를 한 번에 lock 으로 묶어야 하고, 그건 개발자가 직접 해야 한다.

제안서는 두 가지를 더 말한다. 옛 언어 모드에서 소스 호환을 지키려고 암묵적 lock 을 넣을 수는 있겠지만, Swift 는 그동안 "옛 언어 모드는 concurrency-unsafe" 라고 정리해 왔다. 또 non-Sendable 타입에는 통하지 않는다. 값이 격리된 채로만 쓰이도록 따로 보장해야 하는데, 그것은 non-Sendable 값을 isolation 경계 너머로 안전하게 보내는 별도 pitch 가 다루는 일이고, 이렇게 기본적인 문제의 해결책으로 들고 오기에는 너무 고급 기능이라고 적었다.

---

### 모든 전역을 기본 @MainActor 로

isolation 이 필요한 전역은 알아서 `@MainActor` 로 간주하는 방법도 있다. 제안서는 이렇게 하는 대신 개발자가 선택하게 하는 편이 낫다고 본다. 어떤 전역은 `let` 으로 충분할 수도 있기 때문이다. 기본값이 main actor 라면 그 질문을 아예 하지 않게 된다.

이 대안은 나중에 다른 모양으로 들어왔다. [SE-0466 default actor isolation](https://haroldfromk.github.io/posts/SE-0466/) 이 Swift 6.2 에서 모듈 단위로 기본 isolation 을 고르게 해 준다. 6.4 에서 `Globals.swift` 를 이 옵션으로 돌려 봤다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -swift-version 6 -default-isolation MainActor Globals.swift
```

진단이 0 줄이다. 전역 `var` 와 static 이 모두 기본으로 `@MainActor` 에 묶이기 때문이다. 정리하면 모든 전역을 언어가 강제로 main actor 에 두는 기본값은 거절되었고, 모듈이 스스로 고르는 기본값으로는 나중에 들어왔다.

---

### 접근 제어로 쓰임새 분석

컴파일러가 쓰임새를 분석해서 안전한 전역은 annotation 없이 통과시키자는 의견이 pitch 에서 나왔다. wadetregaskis 가 낸 안이다(pitch #2, #9). 실제로 안전하게 쓰이는데 개발자에게 선언을 요구하는 것은 progressive disclosure(필요할 때까지 어려운 개념을 드러내지 않는다는 원칙)에 어긋난다는 논지였다. 예를 들어 전역 `callCount` 를 `@MainActor` 함수 안에서만 올린다면, 변수 자체에 `@MainActor` 가 없어도 의도가 읽힌다는 것이다.

John McCall 은 기술적으로는 가능하지만 본질적으로 global analysis 라고 답했다(pitch #4). 그 변수를 쓰는 모든 코드를 한 번의 컴파일러 실행이 본 상태여야 한다. `public` 변수는 불가능하고, `package` 는 가능한지 의문이며, `internal` 도 빌드 성능에 큰 부담이다. 실현 가능해 보이는 것은 `private` 과 `fileprivate` 뿐인데, 그 좁은 경우를 위한 특례 규칙의 가치는 크지 않다고 했다.

제안서의 Future directions 에는 타입에 기반한 추론이 남아 있다. 어떤 mutable 전역 변수의 타입이 global actor 에 묶여 있다면, 그 변수도 같은 global actor 에 속한다고 추론해 줄 수 있다는 방향이다. 지금처럼 변수마다 `@MainActor` 를 일일이 적지 않아도 되는 여지다.

리뷰 자체는 순조로웠다. Doug Gregor 는 이 제안서를 "짧고, 핵심만 짚고, 중요하다" 고 평했다. 리뷰 중에 두 번의 revision(지역 변수의 `nonisolated(unsafe)`, `@preconcurrency` 기반 import 규칙)이 있었고 기간은 12 월 12 일까지 연장되었다. Doug 은 수정된 제안서가 좋다고 했고(리뷰 #18), Language Steering Group 이 12 월 15 일에 수락했다. 결과는 Holly Borla 가 공지했다.

## 개선했을 때의 기대 효과

앞에서 직접 돌려 본 것에서 나오는 효과만 정리한다.

- 전역 `var` 로 열어 둔 상태는 실제로 값을 잃었다. 10 만 번 중 대략 1 만에서 1 만 7 천 번의 증가가 사라졌고 Thread Sanitizer 가 그 자리를 전역 변수로 짚었다. `main.swift` 가 아닌 파일의 전역 `var` 였다면 Swift 6 에서 이 코드는 `nonisolated(unsafe)` 없이는 컴파일되지 않는다. (이 글의 실험은 `main.swift` 라서 `nonisolated(unsafe)` 를 빼면 MainActor warning 이 나왔다.) 같은 버그가 "빌드가 안 되는 코드" 아니면 "unsafe 라고 적힌 코드" 둘 중 한 모양으로만 남는다. 둘째 모양은 `grep nonisolated(unsafe)` 로 찾을 수 있어서 코드 리뷰에서 걸러낼 수도 있다.
- 같은 파일을 Swift 5 로 검사하면 진단이 0 줄이지만 Swift 6 로 검사하면 error 가 네 개 나오고, 각 error 마다 고칠 방향을 가리키는 note 가 붙는다. 전역 변수 하나하나에 대해 "`let` 으로 바꿀 수 있나, `@MainActor` 에 묶을 수 있나, 정말 직접 지키고 있나" 를 차례로 묻게 된다.

## Swift 6 언어 모드와 마이그레이션

이 규칙은 Swift 6 언어 모드에서는 기본으로 켜진다. Swift 5 모드에서 미리 써 보려면 upcoming feature flag 를 켠다. 컴파일러 옵션으로는 `-enable-upcoming-feature GlobalConcurrency` 다. SwiftPM 에서는 타깃의 `swiftSettings` 에 넣는다. [`.target(name:swiftSettings:)`](https://developer.apple.com/documentation/packagedescription/target){:target="_blank"} 는 Package.swift 에서 빌드 타깃 하나를 선언하고, `swiftSettings` 로 그 타깃에만 적용할 컴파일러 설정을 주는 API 다.

```swift
.target(
    name: "MyApp",
    swiftSettings: [
        .enableUpcomingFeature("GlobalConcurrency")
    ]
)
```

#### enableUpcomingFeature로 타깃마다 기능 미리 켜기

[`enableUpcomingFeature(_:_:)`](https://developer.apple.com/documentation/packagedescription/swiftsetting/enableupcomingfeature%28_:_:%29){:target="_blank"} 는 Swift 의 upcoming feature 하나를 그 타깃에서 켠다. 첫 인자가 feature 이름이고 두 번째 인자는 적용할 빌드 조건이다. 여기서는 이름만 넘겨서 모든 빌드에 적용했다. 타깃마다 따로 켤 수 있어서 모듈 하나씩 옮겨 가기 좋다.

켜는 정도에 따라 같은 `Globals.swift` 의 결과가 어떻게 달라지는지 컴파일해서 비교했다.

| 선언 | Swift 5 기본 | Swift 5 + GlobalConcurrency | Swift 5 + `-strict-concurrency=complete` | Swift 6 |
| --- | --- | --- | --- | --- |
| `var value` | 진단 없음 | warning | warning | error |
| `let shared` (non-Sendable) | 진단 없음 | 진단 없음 | warning | error |
| `static var verbose` | 진단 없음 | warning | warning | error |
| `static let counter` (non-Sendable) | 진단 없음 | 진단 없음 | warning | error |

`GlobalConcurrency` 만 켜면 전역 `var` 와 `static var` 두 개만 warning 이 된다. 메시지 끝에 "this is an error in the Swift 6 language mode" 가 붙어서 어디까지 다가왔는지 알려 준다. non-Sendable 타입을 담은 `let` 은 이 flag 로는 걸리지 않고, `-strict-concurrency=complete` 를 켜면 네 개가 모두 warning 으로 나온다. `-strict-concurrency` 는 Swift 5 모드에서 동시성 검사를 얼마나 엄격하게 할지 정하는 옵션이다. `minimal` 은 명시적으로 동시성을 쓴 코드만 검사하는 기본값이고, `targeted` 는 그 중간이며, `complete` 는 Swift 6 모드와 같은 범위의 검사를 warning 으로 보여 준다. `GlobalConcurrency` 는 이 제안서의 전역 변수 검사 하나만 켜는 flag 이고, 6.4 에서 돌려 보면 mutable 전역 두 개만 warning 이 되고 non-Sendable `let` 은 `complete` 에서만 잡힌다. 한 번에 다 켜기 부담스러우면 `GlobalConcurrency` 로 `var` 부터 정리하고 `complete` 로 올라가는 순서를 잡을 수 있다.

실무에서 정리하는 순서를 제안하면 이렇다.

1. UI 상태를 담은 전역이나 static 은 `@MainActor` 로 묶는다.
2. 값이 바뀌지 않는데 `var` 로 써 둔 것은 `let` 으로 바꾼다.
3. 카운터와 캐시처럼 바뀌는 값은 `Mutex` 나 actor 로 감싸서 `let` 으로 둔다.
4. 정말 외부 동기화가 있는 것만 `nonisolated(unsafe)` 를 붙이고, 왜 안전한지 주석을 단다.
5. 다른 모듈의 전역은 `@preconcurrency import` 로 임시로 덮는다.

Swift 6 의 `Mutex` 는 macOS 15, iOS 18 이상이라서 배포 타깃이 더 낮으면 쓸 수 없다. 그런 경우에는 pitch 에서 언급된 [`OSAllocatedUnfairLock`](https://developer.apple.com/documentation/os/osallocatedunfairlock){:target="_blank"} 이나 actor 를 쓴다.

## 정리

- 전역 변수와 static 변수는 global actor 에 묶이거나, 바뀌지 않는 `Sendable` 값이어야 하고, Swift 6 모드에서 이를 어기면 error 가 된다. 판정은 변수를 선언한 자리에서 한다.
- 막힌 변수의 출구는 세 개다. `let` 으로 바꾸기, `@MainActor` 로 묶기, 직접 동기화를 책임지겠다는 표시인 `nonisolated(unsafe)`. 마지막은 컴파일러가 검사하지 않으니 실제로 data race 가 난다는 것을 직접 돌려서 봤다.
- 리뷰를 거치며 `nonisolated(unsafe)` 가 지역 변수에도 쓸 수 있게 되었고, C 전역 변수의 처리는 `@preconcurrency import` 규칙으로 정리되었다.
- Swift 5 모드에서는 `GlobalConcurrency` 나 `-strict-concurrency=complete` 로 미리 켜서 warning 으로 확인할 수 있다.

앱에서 이 에러를 가장 먼저 만나는 자리는 싱글턴(앱 전체에서 인스턴스를 하나만 만들어 공유하는 객체)이다. `static let shared = SomeManager()` 의 타입이 non-Sendable class 면 Swift 6 에서 error 가 난다. 대부분은 그 타입이나 변수에 `@MainActor` 를 붙이는 것으로 정리된다.
