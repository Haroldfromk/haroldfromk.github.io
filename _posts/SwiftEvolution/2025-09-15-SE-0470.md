## 한 줄 요약

`@MainActor` 타입이 `nonisolated` 프로토콜을 따를 수 있게 하는 제안이다. 상속 목록에 `class C: @MainActor P` 처럼 isolation 을 적으면 그 conformance 는 main actor 안에서만 쓸 수 있는 "isolated conformance" 가 되고, 컴파일러가 세 규칙으로 그 conformance 가 main actor 밖으로 새어 나가는 길을 막는다. 이 글은 세 규칙을 컴파일러 진단으로 하나씩 확인하고, `@MainActor` 타입에서 이 철자를 자동으로 추론하는 upcoming feature `InferIsolatedConformances` 와 수정안의 추론 규칙까지 측정한다.

## 어떤 문제였나

SE-0466 글에서 본 것처럼 Swift 6 언어 모드에서 isolation 을 적지 않은 코드는 `nonisolated` 다. 그런데 앱 코드의 모델 타입은 `@MainActor` 인 경우가 많고, 표준 라이브러리의 프로토콜(`Equatable`, `Hashable`, `Codable`)과 직접 만든 프로토콜은 대부분 `nonisolated` 다. 이 둘이 만나는 자리가 이 제안이 풀려는 문제다.

이 글의 뼈대는 이렇다. 먼저 문제를 세 장면으로 본다. 컴파일러가 거부하는 장면, 거부를 피하려고 `nonisolated` 로 빼는 장면, `MainActor.assumeIsolated` 로 덮었다가 런타임에 죽는 장면이다. 그다음 바뀌는 것을 철자, 세 규칙, 동적 캐스트, 추론, 기본 MainActor 모드, 빌드 설정의 순서로 측정한다. 이어서 포럼 스레드 여섯 개를 따라가고, 소스 호환과 마이그레이션을 정리한다.

앞 글들의 내용은 짧게 짚고 간다.

- [SE-0414 글](https://haroldfromk.github.io/posts/SE-0414/): region based isolation. 값이 어느 "region" 에 속하는지를 따라서 non-`Sendable` 값을 다른 isolation 으로 넘겨도 되는지 판단한다. 이 글의 Rule 3 이 이 위에 서 있다
- [SE-0430 글](https://haroldfromk.github.io/posts/SE-0430/): `sending` 매개변수와 결과. 값이 호출 뒤에 호출자 쪽에서 다시 쓰이지 않음을 약속한다
- [SE-0449 글](https://haroldfromk.github.io/posts/SE-0449/): `nonisolated` 를 타입과 extension 에 붙이는 문법. 이 글에서는 conformance 앞에 붙는 `nonisolated` 가 나온다
- [SE-0466 글](https://haroldfromk.github.io/posts/SE-0466/): 모듈의 기본 isolation 을 `@MainActor` 로 바꾸는 옵션. 이 글의 추론 기능이 그 모드와 함께 켜진다
- [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/): `MainActor.assumeIsolated` 같은 동적 isolation 검사
- [SE-0337 글](https://haroldfromk.github.io/posts/SE-0337/): `@preconcurrency` 로 검사를 런타임으로 미루는 길

### conformance란?

이 글의 모든 이야기가 conformance 라는 낱말 위에 있어서 먼저 풀어 둔다. 프로토콜은 "이런 메서드와 속성을 갖춰라" 라는 요구사항 목록이고, conformance 는 "이 타입이 그 목록을 갖췄다" 는 선언이다. `struct Point: Equatable` 이라고 쓰면 `Point` 와 `Equatable` 짝에 대한 conformance 가 하나 생긴다. 이때 요구사항을 실제로 채우는 구현을 witness 라고 부른다. `Equatable` 의 요구사항은 `==` 이고, `Point` 안에 쓴(또는 컴파일러가 합성한) `==` 가 그 witness 다.

컴파일러는 conformance 마다 "요구사항별로 어느 구현을 부르는가" 를 적은 표를 만들어 둔다. 제네릭 함수 `func isEqual<T: Equatable>(_ a: T, _ b: T)` 는 `T` 가 무엇인지 모르는 채로 컴파일된다. 호출하는 쪽이 `T = Point` 를 정하면서 `Point: Equatable` conformance 를 같이 넘기고, 함수 안의 `a == b` 는 그 표를 거쳐 `Point.==` 로 간다. 비유하면 conformance 는 "이 사람은 운전할 수 있다" 는 면허증이고, 제네릭 함수는 면허증만 보고 운전을 맡기는 대리 기사 호출 앱이다. 면허증은 호출한 쪽에서 앱으로 넘어가고, 앱은 그 면허증을 가지고 어디서든 운전을 시킬 수 있다.

문제는 이 면허증을 어디서든 쓸 수 있다는 가정이다. witness 가 `@MainActor` 의 상태를 읽는다면, main actor 밖에서 그 witness 를 부르는 순간 data race 가 된다. 이 제안은 그 면허증에 "main actor 안에서만 유효" 라는 도장을 찍고, 도장이 찍힌 면허증이 새어 나가지 못하게 하는 규칙을 정한다.

### @MainActor 타입과 프로토콜의 충돌

제안서 Introduction 의 예제다. `@MainActor` 클래스가 `Equatable` 을 따르게 하려는 가장 평범한 코드다.

#### emit-sil 로 SIL 단계까지 진단받기

이 글의 진단은 모두 `-emit-sil` 로 뽑았다. `-emit-sil` 은 타입 검사 뒤 SIL(컴파일러 중간 표현) 단계까지 컴파일해서 그 단계의 진단까지 낸다. 타입 검사까지만 하는 `-typecheck` 는 SIL 단계의 진단(초기화 검사, region 검사)을 빼먹는다. `-o /dev/null` 은 결과 파일을 버리고, `-parse-as-library` 는 최상위 코드가 없는 일반 소스 파일로 다루라는 옵션이며, `-wmo` 는 모든 파일을 한 모듈로 같이 컴파일하게 한다. 이 옵션들의 자세한 이야기는 [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/)에 있다. 컴파일러는 `Apple Swift version 6.4 (swiftlang-6.4.0.34.1)` 이다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 Motivation.swift
```

이 글에서 "기본" 이라고 하면 이 명령처럼 Swift 6 언어 모드에 아무 옵션도 더하지 않은 판이다. 다른 판은 옵션을 앞에 더해서 부른다. 이 글의 진단 실험은 대부분 파일 하나를 이 명령으로 컴파일한 것이다. 그 밖에 `-print-ast` 로 AST 를 찍거나, 실행 파일을 만들어 돌리거나, lldb 와 `swift build` 를 쓰는 곳에서는 그 명령을 따로 적는다. 진단 아래의 `[#...]` 줄은 컴파일러가 진단 끝에 붙이는 문서 링크이고, `[exit N]` 은 컴파일러의 종료 코드다.

`Motivation.swift`

```swift
@MainActor
class MyModelType: Equatable {
  var name: String

  init(name: String) {
    self.name = name
  }

  static func ==(lhs: MyModelType, rhs: MyModelType) -> Bool {
    lhs.name == rhs.name
  }
}
```

`MyModelType` 은 `@MainActor` 클래스이고 `Equatable` 을 따른다. `==` 는 클래스를 따라 `@MainActor` 이고 `name` 을 읽는다. 기본 Swift 6 모드의 진단이다.

오류 문장은 "`MyModelType` 의 `Equatable` conformance 가 main actor 격리 코드로 넘어가서 data race 가 날 수 있다" 이다. `Equatable` 은 `nonisolated` 프로토콜이라서 요구사항 `==` 도 `nonisolated` 인데, 이 타입의 `==` 는 `@MainActor` 라서 요구사항을 만족시킬 수 없다는 것이 세 번째 note 이고, 네 번째 note 는 그 `==` 를 `nonisolated` 로 빼라는 고치는 법이다.

### nonisolated 로 빼는 우회

이 제안이 나오기 전의 대표적인 해법은 note 의 마지막 길이다. `==` 를 `nonisolated` 로 만들면 요구사항과 isolation 이 같아진다. [SE-0449 글](https://haroldfromk.github.io/posts/SE-0449/)이 다룬 `nonisolated` 문법을 멤버에 붙이는 것이다.

`Workaround.swift`

```swift
@MainActor
class MyModelType: Equatable {
  var name: String

  init(name: String) {
    self.name = name
  }

  nonisolated static func ==(lhs: MyModelType, rhs: MyModelType) -> Bool {
    lhs.name == rhs.name
  }
}
```

### assumeIsolated 로 덮는 우회

`nonisolated` 로 뺀 `==` 가 main actor 의 상태를 읽어야 한다면 남는 길은 "나는 지금 main actor 에 있다" 고 컴파일러에게 약속하는 것이다. [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/)에서 본 `MainActor.assumeIsolated` 가 그 약속이다.

`AssumeIsolated.swift`

```swift
@MainActor
final class MyModelType: Equatable {
  var name: String

  init(name: String) {
    self.name = name
  }

  nonisolated static func ==(lhs: MyModelType, rhs: MyModelType) -> Bool {
    MainActor.assumeIsolated {
      lhs.name == rhs.name
    }
  }
}

@main
struct Program {
  static func main() async {
    let a = MyModelType(name: "a")
    let b = MyModelType(name: "a")
    print("on main:", a == b)
    let r = await Task.detached { a == b }.value
    print("detached:", r)
  }
}
```

`MyModelType` 에는 이제 conformance 에 isolation 표시가 없다. `==` 는 `nonisolated` 이고, 본문에서 `MainActor.assumeIsolated` 로 main actor 안이라고 가정한 채 `name` 을 읽는다. `main` 에서 `a == b` 를 한 번 비교하고, `Task.detached` 안에서 한 번 더 비교한다. 컴파일은 오류 없이 된다.

#### MainActor.assumeIsolated로 main actor 가정하기

[`MainActor.assumeIsolated(_:file:line:)`](https://developer.apple.com/documentation/swift/mainactor/assumeisolated%28_:file:line:%29){:target="_blank"} 는 지금 실행 중인 코드가 main actor 에서 돌고 있다고 가정하고, 클로저를 main actor isolation 으로 실행한다. 클로저가 돌려주는 값을 그대로 돌려준다. 컴파일러는 가정을 믿어 주고, 대신 실행 시점에 정말 main actor 인지를 확인해서 아니면 프로그램을 멈춘다. `assumeIsolated` 를 호출하는 함수의 호출자가 isolation 을 지켜 줘야 하는데, 그 약속은 타입에 적히지 않는다.

#### Task.detached로 새 Task 만들기

[`Task.detached(name:priority:operation:)`](https://developer.apple.com/documentation/swift/task/detached%28name:priority:operation:%29-9xki7){:target="_blank"} 는 부모 Task 의 isolation 과 우선순위를 물려받지 않는 새 Task 를 만든다. 위 코드에서는 main actor 밖에서 `a == b` 를 부르는 길을 만들려고 썼다.

컴파일 결과 실행 파일을 `~/se470/assume` 으로 만들고 lldb 로 돌렸다. 실행 파일 만들기는 이렇다.

```bash
xcrun swiftc -parse-as-library -swift-version 6 AssumeIsolated.swift -o ~/se470/assume
```

## 무엇이 바뀌나

제안의 핵심은 두 가지다. 하나는 conformance 를 선언할 때 프로토콜 앞에 isolation 을 적을 수 있다는 것(`class C: @MainActor P`)이고, 다른 하나는 그렇게 만든 isolated conformance 가 isolation 도메인 밖으로 새어 나가지 못하게 컴파일러가 세 규칙으로 막는다는 것이다. 이어서 이 철자를 컴파일러가 알아서 붙여 주는 추론 규칙(upcoming feature)과 수정안이 바뀌는 순서로 하나씩 돌려 본다.

### @MainActor conformance

제안서가 첫 번째로 보여 주는 코드다. Motivation 의 `MyModelType` 에서 상속 목록의 `Equatable` 앞에 `@MainActor` 를 붙였다. 나머지는 그대로다.

`Explicit.swift`

```swift
@MainActor
class MyModelType: @MainActor Equatable {
  var name: String

  init(name: String) {
    self.name = name
  }

  static func ==(lhs: MyModelType, rhs: MyModelType) -> Bool {
    lhs.name == rhs.name
  }
}

@MainActor
func hasMatchingOnMain(_ value: MyModelType, in modelValues: [MyModelType]) -> Bool {
  modelValues.contains(value)
}

nonisolated func hasMatching(_ value: MyModelType, in modelValues: [MyModelType]) -> Bool {
  modelValues.contains(value)
}
```

`MyModelType: @MainActor Equatable` 이 isolated conformance 선언이다. 읽는 법은 "`MyModelType` 은 `Equatable` 을 따르는데, 그 conformance 는 main actor 에 isolated 되어 있다" 이다. 타입이 `@MainActor` 인 것과 conformance 가 `@MainActor` 인 것은 따로 적는 두 가지다. 아래 `OtherIsolation.swift` 에서 보듯 타입이 `@MainActor` 가 아니어도 conformance 만 main actor 에 묶을 수 있다.

#### Sequence.contains로 원소 포함 여부 확인하기

[`Sequence.contains(_:)`](https://developer.apple.com/documentation/swift/sequence/contains%28_:%29){:target="_blank"} 는 원소가 `Equatable` 일 때 시퀀스 안에 같은 값이 있는지 `==` 로 비교해서 `Bool` 을 돌려준다. `==` 가 곧 `Equatable` conformance 의 witness 라서, 이 호출은 conformance 를 쓰는 대표적인 자리다.

`hasMatchingOnMain` 은 `@MainActor` 함수라서 `modelValues.contains(value)` 가 conformance 를 쓰는 것이 문제 없다. 그런데 `nonisolated func hasMatching` 도 같은 `contains` 호출을 하는데, 이 파일을 컴파일한 결과는 이렇다.

### 데이터 레이스가 생기는 길

isolated conformance 를 도입하면 새로 열리는 data race 의 길이 있다. 제안서는 이 길을 Data-race safety issues 절에서 정리한다. 요지는 이렇다. conformance 는 값처럼 여기저기 넘겨진다. 제네릭 함수로 넘어가기도 하고, `any P` 속에 들어가기도 하고, key path 에 담기기도 한다. 그렇게 넘겨진 conformance 가 main actor 밖에서 호출되면 data race 가 난다. 그래서 제안은 conformance 가 새어 나가는 길마다 규칙을 하나씩 둔다.

![SE-0470 의 세 규칙. 위쪽에 상자 네 개가 왼쪽에서 오른쪽으로 이어진다. main actor 타입 C: @MainActor P, 제네릭 함수 f<T: P>(_:), main 밖으로 보냄(Task.detached 등), main 밖에서 호출(데이터 레이스) 순서이고 마지막 상자만 점선이다. 상자 사이 이음선 세 곳에 규칙 표지가 하나씩 붙어 있고 점선으로 아래 상자와 이어진다. 첫 번째 이음선(타입에서 제네릭 함수로)에는 Rule 2 가 붙는다. T: Sendable 이나 T: SendableMetatype 자리에는 isolated conformance 를 넘길 수 없다. 두 번째 이음선(제네릭 함수에서 main 밖으로 보냄)에는 Rule 3 이 붙는다. conformance 에 기대는 값은 main actor region 에 묶여 sending 으로 보낼 수 없다. 세 번째 이음선(main 밖으로 보냄에서 main 밖에서 호출로)에는 Rule 1 이 붙는다. conformance 는 main actor isolation 안에서만 쓰고 nonisolated 와 @concurrent 에서는 금지한다. 맨 아래 문구는 세 규칙이 길 위의 세 곳을 하나씩 막는다는 것이다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-09-15-SE-0470/se-0470-rules.png)

맨 왼쪽 상자가 `@MainActor` conformance 를 가진 타입이고, 오른쪽으로 갈수록 conformance 가 main actor 에서 멀어진다. 타입을 제네릭 함수에 넘기고, 그 함수가 값을 `Task.detached` 같은 곳으로 main 밖에 보내고, 마지막에 main 밖에서 실제로 호출하는 길이다. main actor 안에서 제네릭 함수에 넘기는 것 자체는 막히지 않는다. 규칙 표지는 이음선마다 하나씩 붙어서, 길을 따라 Rule 2, Rule 3, Rule 1 순서다. 이 글은 번호 순서(Rule 1 부터 3)로 6.4 컴파일러로 확인한다. 세 규칙의 정확한 문구는 이렇다.

- Rule 1: isolated conformance 는 그 isolation 과 같은 도메인 안에서만 쓸 수 있다. `nonisolated` 와 `@concurrent` 컨텍스트, 다른 actor 에서는 쓸 수 없다
- Rule 2: `Sendable` 이나 `SendableMetatype` 제약이 붙은 제네릭 타입 매개변수에는 isolated conformance 를 쓸 수 없다. 제약이 붙은 자리는 "다른 isolation 으로 보낼 수 있는 값" 을 받겠다는 뜻이기 때문이다
- Rule 3: isolated conformance 에 기대는 값은 그 conformance 의 global actor region 에 속한다. 그래서 `sending` 으로 다른 isolation 에 넘길 수 없다

### Rule 1 isolation 도메인 안에서의 사용

Rule 1 은 가장 직관적이다. main actor 의 conformance 는 main actor 에서만 쓴다. 제안서의 예제를 그대로 옮긴 파일이다.

`Rule1.swift`

```swift
protocol P {
  func f()
}

struct S: @MainActor P {
  func f() {}
}

struct WrapsP<T: P>: P {
  var value: T
  init(_ value: T) { self.value = value }
  func f() { value.f() }
}

func badFunc() -> WrapsP<S> { WrapsP(S()) }

func badFunc2() -> any P {
  S()
}

func acceptsP<T: P>(_ value: T) { }

func badFunc3() {
  acceptsP(S())
}

@MainActor func goodFunc() -> any P {
  S()
}

protocol P2 {
  associatedtype A: P
}

struct S2: P2 {
  typealias A = S
}
```

- 35:12 `S2: P2`: `S2` 의 conformance 가 `S` 의 main actor conformance 에 기댄다. `S2` 도 `@MainActor` 로 isolate 하라는 note 가 달린다. associated type 으로 conformance 가 전파되는 경로다
- 15:31 `badFunc`: 시그니처가 아니라 본문의 `WrapsP(S())` 에서 난다
- 18:3 `badFunc2`: `S()` 를 `any P` 로 돌려주는 자리
- 24:3 `badFunc3`: `acceptsP(S())` 의 제네릭 인자

`goodFunc` 는 진단이 없다. 첫 번째 진단의 note 두 줄이 흥미롭다. "이 conformance 도 main actor 로 isolate 하라" 는 note 는 이 제안의 철자가 해법으로 다시 나온 것이고, "conformance 가 `S` 의 main actor conformance 에 의존한다" 는 note 는 컴파일러가 의존 관계를 추적한다는 뜻이다.

#### any P로 conformance 를 값에 담아 넘기기

`any P` 는 existential 타입이다. `S` 값을 `any P` 로 감싸면 `S: P` conformance 도 같이 박스 안에 들어가서, 박스를 받은 쪽이 그 conformance 를 쓰게 된다. `@MainActor func goodFunc() -> any P` 처럼 함수에 붙이는 `@MainActor` 는 함수 본문을 main actor isolation 으로 돌리므로, 이 안에서는 main actor conformance 를 쓸 수 있다.

key path 에서도 같은 규칙이 적용되는지 본다. key path 는 요구사항 `name` 을 프로토콜 요구사항으로 가리키므로 conformance 를 쓴다.

`Rule1KeyPath.swift`

```swift
protocol HasName {
  var name: String { get }
}

@MainActor final class Named: @MainActor HasName {
  var name: String = "n"
}

@MainActor
func useName() {
  let named = Named()
  Task.detached {
    _ = named[keyPath: \HasName.name]
  }
}
```

#### keyPath 서브스크립트로 key path 가 가리키는 값 읽기

`value[keyPath: \T.name]` 은 [`KeyPath`](https://developer.apple.com/documentation/swift/keypath){:target="_blank"} 가 가리키는 속성을 값에서 읽는 서브스크립트다. `\HasName.name` 처럼 프로토콜 요구사항을 가리키는 key path 는 읽을 때 그 프로토콜의 conformance 로 `name` 을 찾아간다.

[SE-0418 글](https://haroldfromk.github.io/posts/SE-0418/)이 다룬 key path 의 `Sendable` 추론과는 별개의 길이지만, key path 도 conformance 를 들고 있다는 점은 같은 맥락이다.

앞에서 지나간 `contains` 경로로 돌아온다. Explicit 파일에서 `hasMatching` 은 진단이 없었다. 비슷한 경로를 몇 가지 더 모았다.

```swift
    print("==", Thread.isMainThread ? "main" : "not main")
    return lhs.name == rhs.name
  }
}

  modelValues.contains(value)
}

struct Program {
  static func main() async {
    let a = MyModelType(name: "a")
    let list = [MyModelType(name: "b"), a]
    print("main:", viaContains(a, in: list))
    let r = await Task.detached { viaContains(a, in: list) }.value
    print("detached:", r)
  }
}
```

### Rule 2 Sendable 제약과 isolated conformance

Rule 1 은 "쓰는 곳" 을 막는다. 그런데 제네릭 함수 안에서는 쓰는 곳이 호출자 쪽에서 정해지지 않는다. 제네릭 함수가 conformance 를 받아서 `Task.detached` 같은 데로 보내 버리면 어떻게 될까. 이 질문이 Rule 2 다. 먼저 제안서의 예다.

`Rule2Generic.swift`

```swift
protocol Q {
  static func g()
}

nonisolated func callQGElsewhere<T: Q>(_: T.Type) {
  Task.detached {
    T.g()
  }
}
```

`callQGElsewhere<T: Q>` 는 `T` 의 타입 객체를 받고, `Task.detached` 클로저에서 `T.g()` 를 부른다. `T.g()` 는 `Q` conformance 의 정적 요구사항을 부르므로 conformance 가 클로저로 건너간다. 만약 호출자가 `T` 에 `@MainActor` conformance 를 넘기면, 클로저가 main actor 밖에서 그 conformance 의 `g()` 를 부르게 된다.


### SendableMetatype이란?

이 warning 의 열쇠는 `T.Type` 이 `Sendable` 하지 않다는 사실이다. `T.Type` 은 제네릭 타입 `T` 의 타입 값이다. 값이 다른 isolation 으로 건너가도 되는지는 그 타입이 `Sendable` 이냐로 정해진다. 그런데 metatype(`T.Type`)은 conformance 를 들고 있으므로, 건너가도 안전한지는 "conformance 가 isolated 인가" 에 달려 있다.

[`SendableMetatype`](https://developer.apple.com/documentation/swift/sendablemetatype){:target="_blank"} 는 이 질문의 답을 표시하는 marker protocol 이다. 규칙은 이렇다.

- `T: SendableMetatype` 이면 `T.Type` 은 `Sendable` 이다. metatype 을 다른 isolation 으로 보내도 된다는 뜻이다
- `Sendable` 은 `SendableMetatype` 을 상속한다. 그래서 `T: Sendable` 도 `T.Type` 을 보낼 수 있다
- 구체 타입은 모두 암묵적으로 `SendableMetatype` 이다. isolated conformance 가 아닌 한 `T.Type` 을 보내도 안전하기 때문이다
- 그 대신 `T: SendableMetatype` 자리에는 isolated conformance 를 가진 타입을 넣을 수 없다. isolated conformance 를 가진 metatype 은 보낼 수 없기 때문이다

리뷰 중에 이 규칙의 모양이 바뀌었다. 제안서 Revision History 에 따르면 리뷰에 올라온 초안은 제네릭 함수 안에서 구체적인 conformance 를 isolated 일 수 있는 것으로 따지는 모델이었다. 리뷰에서 "제네릭 매개변수의 metatype 이 Sendable 한가" 를 기준으로 삼는 모델로 바꿨고, 이 모델은 이전 초안에서 쓰던 것으로 되돌아간 것이다(리뷰 #13 Doug, PR #2763). 이 글의 진단 문구가 `T.Type` 의 non-Sendable 을 말하는 것이 그 결과다. 제네릭 함수 안에서 `Task.detached` 가 `T.g()` 를 캡처하면, 컴파일러는 `T.Type` 이 Sendable 인지로 판단한다.

그러면 `callQGElsewhere` 를 어떻게 고치는가. 제안서의 답은 `T: Q & SendableMetatype` 으로 제약을 명시하는 것이다. 그러면 함수 안에서는 `T.Type` 이 Sendable 이 되고, 호출자는 isolated conformance 를 가진 타입을 넘길 수 없게 된다.

`Rule2Fixed.swift`

```swift
protocol Q {
  static func g()
}

nonisolated func callQGElsewhere<T: Q & SendableMetatype>(_: T.Type) {
  Task.detached {
    T.g()
  }
}

struct MyTypeThatConformsToQ: Q {
  static func g() {}
}

func use() {
  callQGElsewhere(MyTypeThatConformsToQ.self)
}

@MainActor final class C: @MainActor Q {
  static func g() {}
}

@MainActor func isolationWithStatics() {
  callQGElsewhere(C.self)
}
```

`callQGElsewhere<T: Q & SendableMetatype>` 으로 바꿨다. 구체 타입 `MyTypeThatConformsToQ` 는 일반 conformance 라서 `use()` 에서 문제없이 넘어간다. `C` 는 `@MainActor Q` 이고, `isolationWithStatics` 가 `callQGElsewhere(C.self)` 를 부른다.

이 절에서 Rule 2 가 막는 길은 제네릭 제약이다. 이제 제네릭 제약이 아닌 경로를 본다. `any Sendable & P` 로 지우는 경로다.

### Rule 3 global actor 의 region

Rule 1 과 2 가 conformance 를 막는 규칙이라면, Rule 3 은 conformance 에 기대는 값을 막는다. `any P` 같은 존재 타입 값은 안에 conformance 를 들고 있으므로, 그 값을 다른 isolation 으로 보내면 conformance 도 같이 가 버린다. 그래서 Rule 3 은 이런 값을 global actor 의 region 에 묶는다. 값을 isolation 사이로 보낼 때 쓰는 `sending` 이 그 region 을 따진다([SE-0414 글](https://haroldfromk.github.io/posts/SE-0414/)과 [SE-0430 글](https://haroldfromk.github.io/posts/SE-0430/)).

먼저 `sending` 이 main actor 의 callee 로 넘어가는 경우다.

`Rule3.swift`

```swift
protocol P {
  func f()
}

final class C: @MainActor P {
  @MainActor func f() {}
}

struct WrapsP<T: P> {
  var value: T
  init(_ value: T) { self.value = value }
}

@MainActor func acceptSending(_ value: sending any P) { }
@MainActor func acceptSendingWrap(_ value: sending WrapsP<C>) { }
@MainActor func acceptSendingC(_ value: sending C) { }

@MainActor func passSending() {
  let c1 = C()
  let ap1: any P = c1
  acceptSending(ap1)

  let c2 = C()
  let wp2 = WrapsP(c2)
  acceptSendingWrap(wp2)

  let c3 = C()
  acceptSendingC(c3)
}

@MainActor func badSendingReturn() -> sending any P {
  C()
}
```

```text
[exit 0]
```

`acceptSending`, `acceptSendingWrap`, `acceptSendingC` 는 모두 `@MainActor` 함수라서 값이 main actor 에서 main actor 로 건너간다. 진단이 없다. 그런데 `badSendingReturn() -> sending any P { C() }` 에는 "main 에서 main 으로" 와는 다른 이유로 진단이 없다. 본문의 `C()` 는 이름 없이 새로 만든 값이라 새 region 에 놓이고, main actor 에 묶인 값이 아니기 때문이다. 이름을 붙이면 달라지는지 변형 파일로 본다.

### 동적 캐스트

conformance 가 값에 따라붙으면 `as?` 같은 동적 캐스트도 영향을 받는다. `value as? any P` 는 런타임에 `value` 의 타입이 `P` 를 따르는지 찾아본다. 이때 `P` conformance 가 isolated 이면 호출한 곳의 isolation 이 맞아야 쓸 수 있다. 제안서는 "캐스트가 지금 실행 중인 executor 를 확인해서 isolated conformance 를 쓸 수 있을 때만 성공한다" 고 쓴다.

`DynamicCast.swift`

```swift
import Foundation

protocol P {
  func f()
}

@MainActor
final class C: @MainActor P {
  func f() { print("  f() on", Thread.isMainThread ? "main" : "not main") }
}

final class D: P, Sendable {
  func f() { print("  f() on", Thread.isMainThread ? "main" : "not main") }
}

nonisolated func tryP(_ label: String, _ value: Any) {
  if let p = value as? any P {
    print(label, "as? any P succeeded")
    p.f()
  } else {
    print(label, "as? any P failed")
  }
}

@main
struct Program {
  static func main() async {
    let c: any Sendable = C()
    let d: any Sendable = D()
    tryP("main C", c)
    tryP("main D", d)
    await Task.detached {
      tryP("detached C", c)
      tryP("detached D", d)
    }.value
  }
}
```

`C` 는 `@MainActor P`, `D` 는 일반 `P` 이면서 `Sendable` 이다. 두 값을 `any Sendable` 로 들고 있다가 main 에서 한 번, `Task.detached` 안에서 한 번 `tryP` 로 캐스트한다. `Thread.isMainThread` 로 `f()` 가 어느 스레드에서 도는지도 찍는다. 빌드는 `xcrun swiftc -parse-as-library -swift-version 6 DynamicCast.swift -o ~/se470/dynamiccast` 이다.

```text
main C as? any P succeeded
  f() on main
main D as? any P succeeded
  f() on main
detached C as? any P failed
detached D as? any P succeeded
  f() on not main
[exit 0]
```

네 번의 캐스트가 이렇게 갈린다.

- main 에서 `C` 의 `as? any P`: 성공하고 `f()` 가 main 에서 돈다
- main 에서 `D` 의 `as? any P`: 성공
- `Task.detached` 에서 `C` 의 `as? any P`: 실패. 캐스트가 지금 main actor 가 아니라는 것을 알고 isolated conformance 를 쓰지 않았다
- `Task.detached` 에서 `D` 의 `as? any P`: 성공하고 `f()` 가 main 이 아닌 곳에서 돈다. 일반 conformance 는 어디서든 쓸 수 있다

같은 `C` 값, 같은 `as? any P` 인데 호출한 곳의 isolation 에 따라 결과가 갈린다. 제안서가 말하는 "동적 캐스트의 isolation 확인" 이 이것이다. 동적 캐스트에 관련해 제안서가 따로 설명하는 것이 있다. 옛 런타임에서는 캐스트가 isolation 을 확인하지 않아서 항상 성공한다. ABI 절에서 한 문장으로 다시 만난다.

제안서에는 `value is any Sendable & P` 라는 예도 있다. 이 모양을 그대로 컴파일해 본다.

`DynamicCastSendable.swift`

```swift

  func f()
}

  value is any Sendable & P
}
```

### conformance isolation 추론

지금까지는 `@MainActor` 를 직접 적었다. 그런데 `@MainActor` 타입 안에서 모든 conformance 에 `@MainActor` 를 적는 것은 번거롭고, 제안서는 이 부분을 upcoming feature `InferIsolatedConformances` 로 덜어 준다. `@MainActor` 타입(또는 다른 global actor 타입)이 `nonisolated` 프로토콜을 따를 때, 컴파일러가 그 conformance 를 같은 global actor 에 isolate 한다. 명시적으로 `nonisolated` 라고 쓰면 추론하지 않는다.

여기에 수정안(2025-07 에 수락)이 규칙 두 개를 더했다. 아래 두 경우에는 `@MainActor` 가 아니라 `nonisolated` 로 추론한다.

- 프로토콜이 `SendableMetatype` 을 상속한다(`Sendable` 을 거쳐 간접적으로 상속하는 경우도 포함). isolated conformance 는 이런 프로토콜에서 쓸 수 없으니 추론할 이유가 없다
- conformance 의 요구사항을 채우는 witness 가 전부 `nonisolated` 다. 요구사항이 아예 없는 프로토콜과 `@Observable` 이 만드는 conformance 도 여기에 든다

![InferIsolatedConformances 의 추론 순서. 위에서 아래로 네 단계가 이어지고 먼저 맞는 단계의 결과가 적용된다. 첫 단계는 isolation 을 직접 적은 경우(@MainActor P, nonisolated P)로 적은 대로 따른다. 둘째 단계는 프로토콜이 SendableMetatype 을 상속하는 경우(Sendable 을 거치는 것 포함)로 nonisolated 로 추론한다. 셋째 단계는 모든 witness 가 nonisolated 인 경우(요구사항이 없는 경우와 @Observable 포함)로 nonisolated 로 추론한다. 마지막 단계는 위에 해당하지 않는 경우로, main actor 멤버가 요구사항을 채워서 @MainActor 로 추론한다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-09-15-SE-0470/se-0470-inference.png)

그림은 컴파일러가 conformance 마다 위에서 아래로 내려가며 처음 맞는 단계의 결과를 쓰는 순서다. 직접 적은 isolation 이 가장 우선이고, `SendableMetatype` 상속과 모든 witness 가 `nonisolated` 인 경우가 `nonisolated` 로 가며, 그 밖의 모든 경우가 `@MainActor` 로 추론된다. 이 순서를 한 파일에 담았다.

`Infer.swift`

```swift
protocol P {
  func f()
}

protocol Q {
  static func g()
}

protocol SP: Sendable {
  func h()
}

@MainActor
final class MyModelType: P {
  func f() {}
}

@MainActor
final class OptOut: nonisolated Q {
  nonisolated static func g() {}
}

@MainActor
final class AllNonisolated: Q {
  nonisolated static func g() {}
}

@MainActor
final class SendableProto: SP {
  nonisolated func h() {}
}

nonisolated func useP(_ m: MyModelType) -> any P { m }
nonisolated func useQ(_ t: OptOut.Type) -> any Q.Type { t }
nonisolated func useQ2(_ t: AllNonisolated.Type) -> any Q.Type { t }
nonisolated func useSP(_ s: SendableProto) -> any SP { s }
```

프로토콜 세 개와 타입 네 개다. `P` 와 `Q` 는 일반 프로토콜이고, `SP` 는 `Sendable` 을 상속한다. `MyModelType: P` 는 아무것도 적지 않았고 witness `f()` 는 `@MainActor` 다. `OptOut: nonisolated Q` 는 conformance 에 `nonisolated` 를 적었고([SE-0449 글](https://haroldfromk.github.io/posts/SE-0449/)이 다룬 문법을 conformance 에 쓴 것이다), `AllNonisolated: Q` 는 아무것도 안 적었지만 witness `g()` 가 `nonisolated` 다. `SendableProto: SP` 는 `Sendable` 을 상속하는 프로토콜을 따른다. 아래 네 `use` 함수는 각 conformance 를 `nonisolated` 함수에서 쓴다.

#### nonisolated 로 conformance 의 isolation 추론 막기

`nonisolated Q` 처럼 프로토콜 앞에 붙은 `nonisolated` 는 conformance 가 isolation 에 묶이지 않는다는 표시다. 타입이나 멤버에 붙이던 `nonisolated` 와 같은 낱말이지만 conformance 에도 쓴다. `Q` 의 `static func g()` 는 정적 요구사항이고, 이 요구사항의 witness 는 `nonisolated static func` 으로 적었다.

#### enable-upcoming-feature 로 upcoming feature 켜기

`-enable-upcoming-feature InferIsolatedConformances` 는 이 글의 중심 옵션이다. 컴파일러에 upcoming feature 의 이름을 주면 그 기능이 켜진다. 기능이 켜지는 것은 이 컴파일 한 번에 한해서이고, 소스는 그대로다. 프로젝트에 적용하는 법은 뒤의 "SwiftPM 과 Xcode 설정" 절에서 본다.

컴파일러가 추론한 isolation 이 소스에 보이는 것은 아니다. `-print-ast` 로 AST 를 찍어 본다.

수정안이 막은 경우를 본다. 수정안 피치에서 Doug 는 `Sendable` 을 상속하는 프로토콜은 `nonisolated` conformance 로 추론해야 한다고 하고(isolated conformance 를 쓸 수 있는 곳이 없기 때문이다), witness 가 전부 `nonisolated` 인 경우도 `nonisolated` 로 추론하자고 했다. 후자의 이유는 둘이다(수정안 피치 #1). 첫째, `Observable` 같은 매크로는 요구사항을 채우려고 `nonisolated` 멤버를 만드는데, 매크로는 확장하는 타입이 actor isolated 인지 모르고 conformance 가 `nonisolated` 여야 한다는 기대로 쓰였다. 둘째, 틀린 isolation 이 추론되면 그 영향이 문제가 생긴 곳에서 멀리 떨어진 곳, 이를테면 다른 모듈이나 패키지에서 드러난다. 피치가 든 예는 `InferIsolatedConformances` 를 켠 상태의 `class D: Q` 이고, 기본 MainActor 모드의 이야기가 아니다. 위 `AllNonisolated` 와 `SendableProto` 가 이 두 규칙의 코드다. 이제 `Sendable` 을 상속하는 프로토콜에 `@MainActor` 를 직접 적으면 어떻게 되는지 본다.

```swift
}
```

#### Observable 매크로로 변경 관찰 코드 만들기

[`@Observable`](https://developer.apple.com/documentation/observation/observable%28%29){:target="_blank"} 는 클래스에 붙이면 저장 속성의 접근과 변경을 추적하는 코드를 확장해 주는 매크로다. 위 출력처럼 `access(keyPath:)`, `withMutation(keyPath:_:)` 같은 `nonisolated` 멤버와 속성별 getter, setter 가 생성되고, [`Observable`](https://developer.apple.com/documentation/observation/observable){:target="_blank"} 프로토콜의 conformance 도 매크로가 붙인다.

#### ObservationRegistrar로 관찰 기록 관리하기

[`ObservationRegistrar`](https://developer.apple.com/documentation/observation/observationregistrar){:target="_blank"} 는 어떤 속성을 누가 읽었고 언제 바뀌었는지를 기록하는 타입이다. 매크로가 만든 `_$observationRegistrar` 저장 속성이 이것이고, 생성된 `access` 와 `withMutation` 이 이 기록기를 부른다.

요구사항이 없는 `protocol Empty` 는 upcoming feature 를 켜도 `nonisolated` 로 추론된다. "모든 witness 가 `nonisolated` 다" 라는 규칙에서 witness 가 하나도 없는 경우다. `useEmpty` 가 `nonisolated` 함수에서 `any Empty` 를 만드는데도 진단이 없는 것이 그 결과다.

### 기본 MainActor 모드와 함께

SE-0466 에서 본 `-default-isolation MainActor` 모드는 모듈의 모든 선언에 `@MainActor` 를 암묵적으로 붙인다. 이 제안은 그 모드와 함께 쓰이도록 설계되었다. 피치 스레드에서 Doug 가 이렇게 정리했다(#36).

- 기본 MainActor 모드만 있을 때: `class MyClass: SomeProtocol` 이 `@MainActor class MyClass` 와 `@MainActor func satisfiesRequirement...` 로 해석된다. `SomeProtocol` 의 요구사항이 `nonisolated` 라면 컴파일되지 않는다
- 이 제안의 추론과 함께: 같은 코드가 `@MainActor class MyClass: @MainActor SomeProtocol` 로 해석된다. conformance 를 main actor 코드 밖에서 쓰지 않는 한 문제가 없고, 모듈의 코드가 모두 기본 main actor 이니 대부분 괜찮다

이 상황을 코드로 본다. 프로토콜은 `nonisolated` 로 명시했고, 클래스에는 아무것도 붙이지 않았다.

`DefaultMain.swift`

```swift
nonisolated protocol P {
  func f()
}

final class MyModelType: P {
  func f() {}
}

nonisolated func useP(_ m: MyModelType) -> any P { m }
```

기본 모드에서는 이 파일이 문제없이 컴파일된다.

```text
[exit 0]
```

진단이 없다. `MyModelType` 은 기본으로 `nonisolated` 이고 `f()` 도 `nonisolated` 라서 `nonisolated` conformance 다. 이번에는 `-default-isolation MainActor` 로 컴파일한다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 -default-isolation MainActor DefaultMain.swift
```

이 파일에서 `nonisolated protocol P` 를 일부러 쓴 이유가 있다. 모듈 기본이 `@MainActor` 이면 `protocol P` 에 아무것도 안 적어도 `P` 자신이 main actor 가 된다. 이런 프로토콜은 제안과 상관없이 요구사항이 `@MainActor` 이므로 conformance 도 `@MainActor` 로 일치한다. isolated conformance 가 필요한 경우는 프로토콜이 다른 모듈에서 오거나 `nonisolated` 로 적힌 경우다.

### SwiftPM 과 Xcode 설정

upcoming feature 를 실제 프로젝트에 켜는 방법이다. SwiftPM 패키지 쪽부터 본다.

`Package.swift` 는 tools-version 6.2, macOS 15 이상, 실행 타깃 `App` 하나이고, `swiftSettings` 에 `.enableUpcomingFeature("InferIsolatedConformances")` 를 둔다.

`Pkg/Package.swift`

```swift
// swift-tools-version: 6.2
import PackageDescription

let package = Package(
  name: "Pkg",
  platforms: [.macOS(.v15)],
  targets: [
    .executableTarget(
      name: "App",
      swiftSettings: [.enableUpcomingFeature("InferIsolatedConformances")]
```

#### swiftSettings 로 타깃에 컴파일러 설정 더하기

[`swiftSettings`](https://developer.apple.com/documentation/packagedescription/target/swiftsettings){:target="_blank"} 는 타깃 선언의 매개변수로, 그 타깃의 Swift 컴파일에만 쓰이는 설정 목록을 받는다.

Xcode 프로젝트에서는 빌드 설정으로 켠다. Xcode 27 의 컴파일러 스펙(`Swift.xcspec`)에 `SWIFT_UPCOMING_FEATURE_INFER_ISOLATED_CONFORMANCES` 라는 설정이 있다. 정의는 이렇다.

```text
{
    Name = "SWIFT_UPCOMING_FEATURE_INFER_ISOLATED_CONFORMANCES";
    Type = Enumeration;
    Values = (
        YES,
        MIGRATE,
        NO,
    );
    DefaultValue = "$(SWIFT_APPROACHABLE_CONCURRENCY)";
    CommandLineArgs = {
        YES = ( "-enable-upcoming-feature", "InferIsolatedConformances" );
        MIGRATE = ( "-enable-upcoming-feature", "InferIsolatedConformances:migrate" );
        NO  = ();
    };
    DisplayName = "Infer Isolated Conformances";
    Category = "Upcoming Features";
    Description = "Infer conformances of global-actor isolated types as isolated to the same actor unless isolation is explicitly specified as `nonisolated`.";
},
```

값은 `YES`, `MIGRATE`, `NO` 셋이다. `YES` 는 앞의 SwiftPM 설정이 만든 컴파일러 옵션과 같은 `-enable-upcoming-feature InferIsolatedConformances` 를 넣고, `MIGRATE` 는 `:migrate` 를 붙인다. 기본값이 `$(SWIFT_APPROACHABLE_CONCURRENCY)` 이므로 이 값을 따로 정하지 않으면 "Approachable Concurrency" 설정을 따라간다.

`SWIFT_APPROACHABLE_CONCURRENCY` 는 Boolean 이고 기본값이 `NO` 다. 정의에는 조건이 하나 붙어 있다(`Swift.xcspec` 568 행).

```text
Condition = "$(EFFECTIVE_SWIFT_VERSION) == '4' || $(EFFECTIVE_SWIFT_VERSION) == '4.2' || $(EFFECTIVE_SWIFT_VERSION) == '5'";
```

이 조건은 실제로 적용되는 언어 버전이 4, 4.2, 5 일 때만 참이다. 즉 이 설정은 Swift 4 와 5 언어 모드에서만 쓰이고 Swift 6 모드에서는 대상이 아니다.

설정의 나머지 내용은 이렇다. 설명은 "더 다가가기 쉬운 Swift Concurrency 로 가는 기능들을 한꺼번에 켠다" 이고, 포함되는 기능은 `DisableOutwardActorInference`, `GlobalActorIsolatedTypesUsability`, `InferIsolatedConformances`, `InferSendableFromCaptures`, `NonisolatedNonsendingByDefault` 다섯 가지다. [SE-0466 글](https://haroldfromk.github.io/posts/SE-0466/)에서 본 Xcode 27 새 앱 템플릿이 이 설정을 `YES` 로 넣는다. 그 템플릿으로 만든 프로젝트에서는 이 글의 추론이 이미 켜져 있다.

### 이름과 기본값

피치 초반에는 이름과 기본값을 놓고 이야기가 오갔다. AlexanderM 은 "Actor-isolated conformances" 라는 이름을 제안했다(피치 #2, AlexanderM). Jon_Shier 는 isolated conformance 가 기본이면 안 되는지, 그리고 isolated 타입이 nonisolated 프로토콜을 올바르게 따를 수 있는 경우가 있는지 물었다(피치 #3, Jon_Shier).

Doug 의 답은 두 갈래였다. 기본으로 삼으면 isolation 이 눈에 보이지 않게 되어 적절하지 않고, 또 isolated 타입이라도 불변 상태에 기대는 conformance 는 문제가 없다는 것이다. 예로 든 것이 `nonisolated let recordID` 를 가진 `Person` 이다(피치 #4, Doug). 이 "기본으로 하지 말고, 필요하면 추론으로 돕자" 는 구도가 뒤에 `InferIsolatedConformances` 가 upcoming feature 로 들어온 배경이다.

### Sendable 과의 관계

가장 오래 이어진 이야기는 Rule 2 의 멘탈 모델이다. Andropov 는 두 번 어렵다고 적었고(피치 #11, #13, Andropov), 이어서 "global actor 로 isolate 된 타입은 Sendable 인데 conformance 가 sendable 이 아니라는 것이 말이 되는가" 를 물었다(#15, Andropov). vns 는 `foo` 안에서 타입이 지워지면 isolation 을 들고 다닐 것이 없다고 짚었다(#12, vns). Nickolas_Pohilets 는 Sendable conformance 를 isolated 와 nonisolated 요구사항을 가르는 문법으로 쓰는 것에 의문을 제기하면서, vision 문서의 `T: isolated P` 와 `T: nonisolated P` 를 인용했다(#16, #18, Nickolas_Pohilets).

Doug 는 이렇게 정리했다. `T: P` 는 `T: SendableMetatype` 이나 `T: Sendable` 이 아니면 isolated conformance 로 채울 수 있다. 이미 `Sendable` 제약을 더하면 호출부가 깨지는 것은 지금도 그렇다. 이 내용을 Alternatives Considered 에 더하겠다고 했다(#20, Doug). 이 글의 "Rule 2" 절에서 본 규칙이 이 문장에 해당한다.

리뷰 단계에서는 John_McCall 이 판을 바꾸는 제안을 했다. `SendableMetatype` 이 하는 일은 이제 isolated conformance 를 넘겨주지 못하게 막는 것뿐이니, `where T: nonisolated P` 를 도입하고 타입이 Sendable 이면 nonisolated 를 암묵적으로 두자는 것이다. 클라이언트가 nonisolated 요구사항을 isolated conformance 로 채우지 못하게 해야 한다는 점도 말했다(리뷰 #2, John_McCall). 8675309 가 같은 혼란에 동의했다(리뷰 #3, 8675309).

Doug 는 이 제안의 일부를 받아 모델을 고쳤다. 리뷰 #13 에서 "metatype `T.Type` 은 `T: MetatypeSendable` 일 때만 Sendable" 로 바꾸는 PR #2763 을 알렸고, 그 결과가 이 글의 "SendableMetatype이란?" 에서 본 모양이다. 한편 수락 공지는 `nonisolated` 를 제네릭 요구사항에 쓰는 대안에 열린 질문이 있다는 점을 적고, 지금의 더 좁은 `SendableMetatype` 접근을 따르되 이후 패치를 허용하기로 했다(수락 공지 #1, xwu).

### 철자

처음 제안서는 `class C: isolated P` 였다. 8675309 는 `isolated XYZ` 가 `nonisolated` 프로토콜을 따르는 것이 혼란스럽다고 했고(피치 #24, 8675309), Nickolas_Pohilets 는 길더라도 `@MainActor S: nonisolated P` 가 낫다고 했다(#26, Nickolas_Pohilets). Doug 는 2025-03-11 에 `isolated P` 를 `@MainActor P` 로 바꿨다(#29, Doug). Nickolas_Pohilets 가 두 철자가 공존해도 되지 않느냐고 물었지만(#32), Doug 는 문법을 둘 두고 싶지 않다고 답했다(#33, Doug). 이 글의 Spelling.swift 에서 `isolated P` 가 파서를 통과하지만 효과가 없는 것은 이 결정의 흔적이다.

여러 isolation 이 섞이는 경우도 나왔다. AlexisQapa 가 conformance 마다 isolation 이 다른 경우를 물었고(#28), bbrk24 는 한 타입이 nonisolated 인 `P` 와 서로 다른 isolation 의 `Q`, `R` 을 가질 수 있느냐고 물었다. Doug 는 된다고 답했다(#49, bbrk24, #51, Doug).

actor 인스턴스에 isolate 되는 conformance 도 물었다. bbrk24 는 self-isolated actor conformance 를 물었고(#30), Doug 는 이것이 Future Directions 이고 type-check 하는 방법을 아직 모른다고 했다(#31, Doug). 그래서 제안서의 Future Directions 에는 actor-instance isolated conformance 가 `isolated P` 로 남아 있다.

### 추론을 어떻게 켤 것인가

추론은 이 제안에서 가장 의견이 많았던 부분이다. Andropov 는 `@MainActor` 가 추론될 때 `isolated` 도 추론하는 미래 방향을 짚었다(피치 #25, Andropov). xwu 는 같은 소스가 플래그에 따라 다른 의미가 되는 것이 frozen 과 non-frozen enum 의 경우와 비슷하다고 했다(#35, xwu). Doug 는 이것이 SE-0466 에 이미 있는 성질이라고 답하고 `MyClass` 예제를 들었다(#36, Doug). 이 글의 "기본 MainActor 모드와 함께" 가 그 예제를 코드로 옮긴 것이다.

bjhomer 는 기본으로 추론하고 `nonisolated SomeProtocol` 로 빠져나오는 방식을 요청했다(#37, bjhomer). Doug 는 upcoming feature 로 단계를 나눠야 한다고 답하면서, 지금 있는 conformance 대부분은 `@preconcurrency` 나 `assumeIsolated` 로 덮여 있을 것이라고 추측했다(#38, Doug). hborla 는 불일치가 오류일 때만, 그리고 불일치한 witness 가 모두 같은 global actor 일 때만 추론하자는 좁은 안을 냈고 단점도 적었다(#39, hborla). Slava_Pestov 는 다른 파일을 봐야 하는 비용을 우려했고(#40), Doug 는 연관 conformance 와의 재귀 때문에 witness 에서 추론하지 않는다고 답했다(#41, Doug). 컴파일러가 스스로 추론한 것을 두고 불평하면 성가실 것이라는 이야기도 있었다(#42, Andropov, #43, Doug).

수정안 피치에서 Doug 는 항목을 이렇게 나열했다(수정안 피치 #1, Doug).

- `Sendable` 을 상속하는 프로토콜은 nonisolated conformance 로 추론한다
- SE-0466 의 추론이 `Sendable` 을 상속하는 프로토콜을 따른다고 선언한 타입에 `@MainActor` 를 붙이지 않도록 한다
- witness 가 전부 `nonisolated` 이면 nonisolated conformance 로 추론한다. 이유는 `@Observable` 같은 매크로가 `nonisolated` 멤버를 만든다는 점과, 틀린 추론의 영향이 원인에서 멀리 떨어진 곳에서 나타난다는 점이다
- global actor 타입의 `Equatable`, `Hashable`, `Codable` 합성 멤버가 추론된 isolation 을 갖게 해서 `@MainActor class C: Codable` 이 isolated conformance 를 얻게 한다

Andropov 는 `nonisolated P` 를 명시하게 하고 오류와 fix-it 를 주자고 했고(수정안 피치 #2, Andropov), Doug 가 답했다(#3). 이 글의 ObservableConf 와 SendableConf 가 이 항목들에 해당하는 코드다.

수정안 리뷰에서 xwu 가 의미 있는 문제를 짚었다. 라이브러리 A 의 v1.1 이 기본 구현이 있는 새 요구사항 `destroy()` 를 더하는데 `MyType.destroy()` 가 `@MainActor` 라면 conformance 가 `@MainActor` 로 바뀐다. 대안은 둘이다. `nonisolated` 명시를 필수로 하거나, 기본 구현이 없는 요구사항만 보는 것이다. xwu 는 뒤쪽에 기울었다(수정안 리뷰 #4, xwu). Doug 는 두 번째 안이 `AsyncIteratorProtocol` 의 `next()` 와 `next(isolation:)` 처럼 서로를 기본 구현으로 삼는 대체 요구사항에서 깨진다고 답했다(#5, Doug). 수정안 수락 공지는 요구사항이 늘면 추론된 isolation 이 바뀔 수 있고 깨끗한 휴리스틱이 없다는 점을 적고 원안대로 받아들였다(수정안 수락 공지 #1, xwu). 제안서의 Alternatives Considered 가 이 점을 단점으로 적는다.

### 동적 캐스트

xwu 는 existential 을 열 때는 어떻게 되는지 물었고(피치 #44, xwu), Doug 는 `as?` 에 검사가 둘 있다고 답했다. 현재 executor 와, 프로토콜이 `SendableMetatype` 을 함의하지 않는지다(#45, Doug). Nickolas_Pohilets 가 `isIsolatingCurrentContext()` 를 물었고(#48), Doug 는 커스텀 executor 와 SerialExecutor 의 isIsolated 제안을 들어 답했다(#51, Doug).

리뷰에서는 Nickolas_Pohilets 가 두 가지를 보였다. 하나는 배포 대상과 런타임 버전, 커스텀 executor 와 `assumeIsolated()` 의 조합을 표로 정리한 것이고(리뷰 #5), 다른 하나는 제네릭 함수를 거치면 `Sendable` 캐스트 제한을 우회할 수 있다는 것이다(#6). Doug 는 back-deployment 는 범위 밖이고 구현은 오래된 런타임에서 캐스트를 항상 허용하며, 택하지 않은 대안이 `assumeIsolated {}` 를 끼워 넣는 것이었다고 답했다(#8, Doug). 런타임은 `any P` 와 `any P & Sendable` 을 구분하지 못하므로 marker protocol 캐스트 문제는 고치지 않는다고도 했다(#10, Doug). 이 글의 "동적 캐스트" 절에서 본 `DynamicCastSendable` 이 그 지점이다.

수락 공지(#1, xwu)는 세 항목을 적었다.

- `nonisolated` 를 제네릭 요구사항에 쓰는 대안에 열린 질문이 있고, 더 좁은 `SendableMetatype` 접근을 따르되 패치는 가능하다
- 이 기능 이전의 런타임에서 캐스트는 틀리게 성공하거나 틀리게 실패한다. 운영 그룹은 "성공" 을 올바른 방향으로의 순이동으로 보고, 도구가 opt-in 진단을 줄 것을 기대한다
- 제안은 isolated conformance 를 가진 구체 타입을 `any Sendable & P` 로 캐스트하는 것을 거부한다. 제네릭 함수를 거치면 `Sendable` 이 얽힌 런타임 캐스트가 성공하는 기존 문제가 있다. 이것은 Sendable conformance 가 런타임 메타데이터에 기록되어야 닫을 수 있고, 이 제안의 범위 밖이며 승인을 막는다고 보지 않는다

이 글 "동적 캐스트" 절의 두 실행 결과는 이 문장들을 읽을 때 옆에 두고 볼 만하다.

## 기대 효과

데이터 레이스를 컴파일 시점에 막으면서 main actor 타입의 conformance 가 자연스러워진다. 구체적으로는 이렇다.

- `@MainActor` 클래스가 `nonisolated` 프로토콜을 따를 때 `nonisolated` witness 를 억지로 만들거나 `assumeIsolated` 로 덮지 않아도 된다
- 그 conformance 를 main actor 밖에서 쓰는 곳은 대부분 컴파일러가 막아 주므로, 안전하지 않은 호출이 런타임 크래시가 아니라 빌드 오류가 된다. 모든 길을 막는 것은 아니다. 앞 절에서 본 `contains` 를 거치는 길(`ContainsRun`)과 `any Sendable & P` 로 캐스트하는 길(`AnyBad`)은 main actor 밖에서 실행해도 진단 없이 컴파일되었다
- `InferIsolatedConformances` 를 켜면 conformance 마다 `@MainActor` 를 적지 않아도 된다
- `-default-isolation MainActor` 와 함께 쓰면 모듈 대부분의 코드가 별다른 표기 없이 main actor 안에서 consistent 하게 동작한다

## 다른 선택지는 왜 안 됐나

제안서가 검토한 대안과 이유를 정리한다.

- `Sendable` 대신 "Non-Sendable conformance" 라는 용어를 쓰는 안. region 기반 isolation 은 non-Sendable 값을 건네게 하지만 isolated conformance 는 건널 수 없고, global actor 타입은 보통 Sendable 이며, opt-in 방향이 거꾸로이고, 진단이 isolation 용어로 나오며, 정착된 철자도 없다
- `T: isolated P` 와 `T: nonisolated P` 요구사항을 두는 안. 나중에 일반화할 수 있다. 이 제안에서는 `T: SendableMetatype` 을 nonisolated P 로, 나머지를 isolated P 로 읽는다. 단점은 복잡도다
- 추론하지 않고 `nonisolated` 를 필수로 쓰게 하는 안. 소스 호환성과 `@Observable` 같은 매크로를 생각하면 추론이 필요하다. 단점은 프로토콜에 기본 구현이 있는 요구사항이 늘면 추론된 isolation 이 바뀔 수 있다는 것이고, 이는 이후 언어 모드에서 deprecate 할 수 있다

## Swift 6 모드와 마이그레이션

소스 호환성은 두 갈래로 나뉜다. 새 문법으로 isolated conformance 를 직접 쓴 코드는 기존 소스가 아니므로 깨질 것이 없다. 그 코드가 Rule 1 을 어기면 Swift 5 모드에서는 warning, Swift 6 모드에서는 error 다. Rule 2 를 어긴 `Rule2Generic` 은 Swift 6 모드에서도 warning 으로 나온다. 반면 기존 소스의 의미를 바꾸는 것은 `InferIsolatedConformances` 를 켰을 때뿐이다. 같은 `@MainActor class C: P` 가 `nonisolated` conformance 에서 `@MainActor` conformance 로 바뀐다. 먼저 새 문법의 Rule 1 위반을 모드별로 컴파일해 본다.

`Swift5.swift`

```swift
protocol P { func f() }

@MainActor final class A: @MainActor P {
  func f() {}
}

func use(_ a: A) -> any P { a }
```

```text
=== Swift5.swift [-swift-version 5]
Swift5.swift:7:29: warning: main actor-isolated conformance of 'A' to 'P' cannot be used in nonisolated context; this is an error in the Swift 6 language mode [#IsolatedConformances]
=== Swift5.swift [-swift-version 5 -strict-concurrency=complete]
Swift5.swift:7:29: warning: main actor-isolated conformance of 'A' to 'P' cannot be used in nonisolated context; this is an error in the Swift 6 language mode [#IsolatedConformances]
=== Swift5.swift [-swift-version 6]
Swift5.swift:7:29: error: main actor-isolated conformance of 'A' to 'P' cannot be used in nonisolated context [#IsolatedConformances]
```

Swift 5 모드에서도 `7:29` 에 "Swift 6 언어 모드에서는 오류다" 라는 warning 이 나오고, Swift 6 모드에서는 같은 자리가 오류다. strict concurrency 를 켜지 않은 plain Swift 5 에서도 warning 이 나온다. 이 파일은 Rule 1 의 예이고, Rule 2 는 이 표에 나오지 않는다.

ABI 는 깨지지 않는다. isolated conformance 정보는 기존 런타임 메타데이터로 확장되고, 오래된 런타임에서는 `as?` 가 항상 성공한다. 오래된 런타임에서 캐스트가 틀리게 성공하는 경우는 위 수락 공지의 두 번째 항목이 다룬 것이다.

`InferIsolatedConformances` 를 켤 때 기존 코드의 동작을 어떻게 지킬지는 `:migrate` 가 돕는다. 이 upcoming feature 는 migratable 이다. 컴파일러가 알려 주는 기능 목록에서 이 줄을 확인한다.

```bash
xcrun swiftc -print-supported-features
```

```text
{ "name": "InferIsolatedConformances", "migratable": true, "categories": ["IsolatedConformances"], "enabled_in": "7" }
```

`"migratable": true` 라서 `:migrate` 가 되고, `"enabled_in": "7"` 이므로 Swift 7 언어 모드에서는 기본으로 켜진다.

`Migrate.swift`

```swift
protocol Describable {
  func describe() -> String
}

@MainActor
final class Counter: Describable {
  let id = 1
  nonisolated func describe() -> String { "Counter" }
}

protocol Named {
  var name: String { get }
}

@MainActor
final class Item: Named {
  nonisolated let name = "item"
}

nonisolated func show(_ d: any Describable) -> String { d.describe() }
nonisolated func useElsewhere(_ c: Counter) -> String { show(c) }
```

기본 모드에서 컴파일한다.

```text
[exit 0]
```

진단이 없다. `Counter` 와 `Item` 은 지금 `nonisolated` conformance 다. 이제 기능만 켜서 컴파일한다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 -enable-upcoming-feature InferIsolatedConformances Migrate.swift
```

```text
[exit 0]
```

이것도 진단이 없다. witness 가 모두 `nonisolated` 라서 추론 결과가 `nonisolated` 이고, 기능을 켜도 의미가 바뀌지 않기 때문이다. 이제 migrate 모드로 컴파일한다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 -enable-upcoming-feature InferIsolatedConformances:migrate Migrate.swift
```

추론을 켜면 실제로 동작이 바뀌는 코드는 이쪽이다. witness 가 `@MainActor` 인 `Counter` 가 `nonisolated` 프로토콜을 따르고, 이를 `nonisolated` 함수에서 쓴다. Swift 6 모드에서는 선언 쪽 warning 이 이미 오류라서, 변화를 단계별로 보려고 Swift 5 모드로 컴파일한다.

```swift
protocol Describable {
  func describe() -> String
}

@MainActor

}

nonisolated func show(_ d: any Describable) -> String { d.describe() }
nonisolated func useElsewhere(_ c: Counter) -> String { show(c) }
```

## 정리

- `@MainActor class C: @MainActor P` 처럼 conformance 가 global actor 에 isolate 된다. 그 isolation 도메인 안에서만 쓸 수 있다
- 규칙은 셋이다. isolation 도메인 안에서만 쓴다(Rule 1), `Sendable` 과 `SendableMetatype` 제약에는 쓸 수 없다(Rule 2), isolated conformance 에 기댄 값은 그 global actor 의 region 에 묶인다(Rule 3)
- `as?` 는 런타임에 현재 executor 를 확인한다
- `InferIsolatedConformances` 는 `@MainActor` 타입의 conformance 를 `@MainActor` 로 추론한다. `SendableMetatype` 을 상속하는 프로토콜이나 witness 가 모두 `nonisolated` 인 경우는 `nonisolated` 로 추론한다
- `-default-isolation MainActor` 는 이 추론을 켠다. Xcode 의 Approachable Concurrency 가 같은 설정을 한꺼번에 켠다
- 새 문법의 Rule 1 위반은 Swift 5 모드에서 warning, Swift 6 모드에서 error 이고, Rule 2 위반은 6.4 에서 Swift 6 모드에서도 warning 이다. 기존 소스의 의미를 바꾸는 것은 `InferIsolatedConformances` 를 켤 때뿐이고, `:migrate` 가 `nonisolated` 를 적을 곳을 알려 준다
