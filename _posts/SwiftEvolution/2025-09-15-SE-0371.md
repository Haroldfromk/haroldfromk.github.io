## 한 줄 요약

actor 와 global actor 에 묶인 클래스의 `deinit` 앞에 `isolated` 를 적으면, 그 `deinit` 이 해당 actor 에서 돈다. 지금까지 `deinit` 은 마지막 release 가 일어난 스레드에서 그대로 실행되는 `nonisolated` 함수라서 actor 의 상태를 만질 수 없었다. 이 제안은 그 제한을 풀되 기본값은 그대로 두고, 필요한 `deinit` 만 직접 `isolated` 로 바꾸게 한다. 이 글은 `isolated deinit` 이 컴파일러와 런타임에서 실제로 어떻게 움직이는지를 하나씩 돌려 보면서 정리한다.

---

## 어떤 문제였나

[SE-0327](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0327-actor-initializers.md){:target="_blank"} 은 actor 의 `deinit` 을 `nonisolated` 로 정했다. 이유는 간단하다. 객체가 사라지는 순간은 마지막 참조가 release 되는 순간이고, 그 release 는 어느 스레드에서든 일어날 수 있다. 그래서 `deinit` 은 그 스레드에서 바로 실행된다. `deinit` 에 들어온 시점에는 객체를 참조하는 곳이 없으니 actor 의 격리 없이도 data race 는 없다. 문제는 컴파일러가 이 사실을 [`Sendable`](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 이 아닌 저장 프로퍼티까지 풀어 주지는 않는다는 점이다.

이 글은 먼저 문제를 컴파일러 진단으로 본다. 그다음 바뀌는 것을 철자와 isolation 계산 규칙, 상속, 런타임, task local, `self` 의 탈출, Objective-C, 기본 MainActor 모드 순서로 측정한다. 포럼 스레드는 여덟 개이고 시간순으로 따라간다. 마지막에 마이그레이션과 ABI 를 본다.

앞 글에서 다룬 것 중 이 글에서 다시 나오는 것은 이렇다.

- [SE-0466 글](https://haroldfromk.github.io/posts/SE-0466/): 모듈 단위로 기본 isolation 을 `@MainActor` 로 바꾸는 모드. 이 모드에서 `deinit` 이 어떻게 되는지를 마지막 장에서 본다
- [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/): Objective-C 에서 온 코드의 isolation 을 런타임에 검사하는 규칙. Objective-C 와 섞이는 장에서 같은 검사가 나온다
- [SE-0414 글](https://haroldfromk.github.io/posts/SE-0414/): region 기반 isolation. 스레드 논쟁 중 한 곳에서 언급된다

### 이 글의 진단 명령

진단은 전부 같은 명령으로 뽑았다.

```bash
xcrun swiftc -emit-sil -o /dev/null -parse-as-library -wmo -swift-version 6 X.swift
```

#### -emit-sil

SIL 까지 내려가는 옵션이다. `-typecheck` 는 타입 검사에서 멈추기 때문에 SIL 단계에서 나오는 진단(초기화 순서, `sending` 검사 같은 것)을 놓친다. `deinit` 은 `self` 의 탈출 검사가 SIL 쪽에 있어서 이 옵션이 필요하다. 코드의 isolation 이 어떻게 잡혔는지 읽을 때도 SIL 출력을 쓴다.

#### -o /dev/null

결과 파일은 필요 없고 진단만 보면 되므로 버린다.

#### -parse-as-library

`@main` 을 쓰는 파일과 최상위 코드가 없는 파일을 같은 방식으로 컴파일하기 위한 옵션이다.

#### -wmo

모듈 전체를 한 번에 컴파일한다. 파일이 하나뿐이어도 SIL 최적화 경로를 실제 빌드와 맞추려고 붙였다.

### 컴파일러가 말하는 문제

`@MainActor` 클래스가 `Sendable` 이 아닌 객체를 들고 있고, `deinit` 에서 그것을 만진다.

`Motivation.swift`

```swift
final class NonSendableAhmed {
  var state: Int = 0
}

@MainActor
final class Maria {
  let friend: NonSendableAhmed
  var count = 0

  init() {
    self.friend = NonSendableAhmed()
  }

  deinit {
    friend.state += 1
    count += 1
  }
}
```

```text
Motivation.swift:15:5: error: cannot access property 'friend' with a non-Sendable type 'NonSendableAhmed' from nonisolated deinit
 1 | final class NonSendableAhmed {
   |             `- note: class 'NonSendableAhmed' does not conform to the 'Sendable' protocol
 2 |   var state: Int = 0
 3 | }
   :
12 |   }
13 |
14 |   deinit {
   |   `- note: add 'isolated' to run isolated to 'MainActor', which may be later than 'nonisolated deinit'
15 |     friend.state += 1
   |     `- error: cannot access property 'friend' with a non-Sendable type 'NonSendableAhmed' from nonisolated deinit
16 |     count += 1
17 |   }
[exit 1]
```

오류는 `friend` 한 군데에만 난다. `count` 는 `Int` 라서 `Sendable` 이고, `deinit` 안에서는 아무도 경쟁하지 않으니 읽고 써도 된다. `friend` 가 막히는 이유는 `NonSendableAhmed` 가 `Sendable` 이 아니기 때문이다. `deinit` 이 어느 스레드에서 돌지 모르는 상황에서, 이 객체를 다른 곳도 쥐고 있을 수 있다는 가정을 컴파일러가 버리지 못한다.

주목할 곳은 note 의 두 번째 줄이다. 컴파일러가 `add 'isolated' to run isolated to 'MainActor', which may be later than 'nonisolated deinit'` 라고 직접 `isolated` 를 권한다. "나중일 수 있다" 는 말이 이 제안의 값이다. `isolated` 를 붙이면 `deinit` 이 main actor 에서 돌지만, 마지막 release 가 어디서 일어났느냐에 따라 시점이 뒤로 밀릴 수 있다.

고쳐서 다시 돌린다.

`Isolated.swift`

```swift
final class NonSendableAhmed {
  var state: Int = 0
}

@MainActor
final class Maria {
  let friend: NonSendableAhmed
  var count = 0

  init() {
    self.friend = NonSendableAhmed()
  }

  isolated deinit {
    friend.state += 1
    count += 1
  }
}
```

```text
[exit 0]
```

진단이 없다. `deinit` 앞에 `isolated` 한 단어를 더했다.

### UIKit 과 AppKit 의 서브클래스

이 제한이 가장 아픈 곳은 UI 코드다. `UIView` 와 `UIViewController` 는 `@MainActor` 로 표시되어 있어서 서브클래스도 main actor 에 묶인다. 그런데 `deinit` 은 어디서든 돌 수 있어서, 뷰가 들고 있는 다른 UI 객체를 정리할 수 없다. 첫 리뷰에서 OneSadCookie 는 이 기능으로 가장 필요한 것으로 `UIView` 와 `UIViewController` 서브클래스의 destructor 를 꼽았다(첫 리뷰 #9, OneSadCookie).

지금까지의 우회로는 세 가지가 있었다.

- 저장 프로퍼티를 `@unchecked Sendable` 로 표시하거나 `nonisolated(unsafe)` 로 열어 두고 `deinit` 에서 만진다. 컴파일러의 검사를 끄는 방식이다. 제안서 Motivation 이 이 유혹을 직접 적는다. `UIView` 서브클래스의 `deinit` 은 main 에서 불린다고 알려져 있어서 검사를 끄고 싶어지는데, 이러면 제대로 `Sendable` 이 아닌 타입이 다른 곳에서도 잘못 표시된 채로 쓰이고 data race 로 이어질 수 있다
- `deinit` 안에서 [`MainActor.assumeIsolated(_:file:line:)`](https://developer.apple.com/documentation/swift/mainactor/assumeisolated%28_:file:line:%29){:target="_blank"} 를 부른다. 두 번째 리뷰에서 Fritzt 가 UIKit 과 AppKit 을 상속할 때 지금 이 우회를 쓰고 있다고 적었다(두 번째 리뷰 #5, Fritzt). main 이 아닌 곳에서 마지막 release 가 일어나면 그 자리에서 멈춘다
- `deinit` 에서 `Task { @MainActor [publisher, connection] in ... }` 처럼 필요한 값만 캡처한 [`Task`](https://developer.apple.com/documentation/swift/task){:target="_blank"} 를 만든다. 두 번째 리뷰에서 moreindirection 이 이 모양을 boilerplate 라고 부르며 `isolated deinit` 으로 바뀌기를 바랐다(두 번째 리뷰 #27, moreindirection)

두 번째 우회가 정말 멈추는지 재 보았다. `deinit` 에서 `assumeIsolated` 로 main actor 의 상태를 만지는 `Screen` 을 배경 task 에서 놓는다.

`Assume.swift`

```swift
import Foundation

final class Counter {
  var value = 0
}

@MainActor
final class Screen {
  let counter = Counter()
  nonisolated init() {}
  deinit {
    MainActor.assumeIsolated {
      counter.value += 1
    }
  }
}

@main struct Program {
  static func main() async {
    await Task.detached {
      var screen: Screen? = Screen()
      screen = nil
      _ = screen
    }.value
    print("done")
  }
}
```

진단은 `[exit 0]` 이다. 컴파일러는 `assumeIsolated` 안이 main actor 라고 믿어 주기 때문에 이 코드를 통과시킨다. 실행은 lldb 로 했다. 명령은 `timeout 20 xcrun lldb --batch -o run -k bt -k quit -- ./assume` 이고, 주소를 뺀 스택은 이렇다.


`Screen.deinit` 이 배경에서 돌고 있고, `assumeIsolated` 가 현재 큐가 main 인지 `dispatch_assert_queue` 로 검사하다가 실패해서 멈춘다. `Screen.__deallocating_deinit` 은 release 를 부른 스레드에서 그대로 `deinit` 을 부른 것이다. 이 우회는 마지막 release 가 어디서 일어나는지를 호출하는 쪽이 알아서 지켜야 한다는 뜻이고, 그 약속은 컴파일러가 확인해 주지 않는다. 아래 마이그레이션 장에서 같은 코드를 `isolated deinit` 으로 바꿔서 다시 돌린다.

첫 pitch 스레드에는 실제 사례도 올라와 있다. jaredsinclair 는 2024-03-11 에 CoreData 의 `NSFetchedResultsController` 를 예로 들었다. 이 클래스는 `Sendable` 도 아니고 어떤 actor 에도 묶여 있지 않은데, UI 를 만지는 `@MainActor` 클래스가 그것을 들고 있는 경우가 많다. `NSFetchedResultsControllerDelegate` 를 구현하는 객체는 관행대로 `deinit` 에서 controller 의 `delegate` 를 `nil` 로 되돌려야 하는데, 이 문장이 strict concurrency 에서는 `NSFetchedResultsController` 가 `Sendable` 이 아니라서 경고 없이 컴파일되지 않는다. 그는 제안이 받아들여지면 이 문장을 약간의 수정으로 main actor 에서 컴파일하고 실행할 수 있게 되리라고 이해했다(첫 pitch #28, jaredsinclair). 그의 팀은 그동안 lock, 제네릭, `@unchecked Sendable` 을 섞어서 경고를 피해 왔다고 한다.

## 무엇이 바뀌나

바뀌는 것을 한 문장으로 하면, actor 와 global actor 에 묶인 클래스의 `deinit` 에 `isolated` 를 적을 수 있게 되었다. 그런데 이 한 문장 아래에 계산해야 할 것이 몇 가지 있다. 철자를 적는 방법, 상속에서 isolation 이 어떻게 이어지는지, 마지막 release 가 엉뚱한 스레드에서 일어났을 때 런타임이 무엇을 하는지, task local 이 어떻게 되는지, `deinit` 안에서 `self` 를 밖으로 내보내면 어떻게 되는지가 그것이다. Objective-C 와 섞이거나 SE-0466 의 기본 MainActor 모드에서 돌 때의 모양도 다르다.

### 철자와 isolation 계산 규칙

`deinit` 에 쓸 수 있는 철자는 세 가지다. `isolated deinit` 은 클래스가 이미 가진 isolation 을 그대로 쓴다. `@MainActor deinit` 처럼 global actor 를 직접 적을 수도 있다. `nonisolated deinit` 은 지금까지의 동작이다. 먼저 틀린 쪽을 본다.

`Rules.swift` (일부)

```swift
@globalActor actor AnotherActor {
  static let shared = AnotherActor()
}

class Plain {
  isolated deinit {}
}

@MainActor
class Base {
  isolated deinit {}
}

class Removed: Base {
  deinit {}
}

class Changed: Base {
  @AnotherActor deinit {}
}
```

```text
Rules.swift:6:3: error: deinit is marked isolated, but containing class 'Plain' is not isolated to an actor
Rules.swift:46:3: error: nonisolated deinitializer 'deinit' has different actor isolation from main actor-isolated overridden declaration
Rules.swift:38:12: note: overridden declaration is here
Rules.swift:50:17: error: global actor 'AnotherActor'-isolated deinitializer 'deinit' has different actor isolation from main actor-isolated overridden declaration
Rules.swift:38:12: note: overridden declaration is here
[exit 1]
```

오류가 세 개다. 첫 번째는 isolation 이 없는 클래스 `Plain` 에 `isolated deinit` 을 적은 것이다. `isolated` 는 "클래스의 isolation 을 쓴다" 는 뜻이라서, 쓸 isolation 이 없으면 의미가 없다. 두 번째와 세 번째는 `Base` 의 `isolated deinit` 을 서브클래스에서 `nonisolated` 로 되돌리거나 다른 actor 로 바꾼 것이다. 이 둘은 아래 상속 규칙에서 다시 본다.

이번에는 같은 파일에서 틀린 세 곳을 빼고 컴파일되는 것만 남긴 `RulesOK.swift` 를 컴파일러에 물었다. 진단은 없고 `[exit 0]` 이다. 클래스마다 SIL 에서 `deinit` 의 isolation 을 읽은 결과는 이렇다.

| 클래스 | 적은 철자 | `deinit` 의 isolation |
|---|---|---|
| `PlainMain` (isolation 없음) | `@MainActor deinit` | `global_actor MainActor` |
| `Same` (`@MainActor`) | `@MainActor deinit` | `global_actor MainActor` |
| `Exotic` (`@MainActor`) | `@AnotherActor deinit` | `global_actor AnotherActor` |
| `Baz` (actor) | `@MainActor deinit` | `global_actor MainActor` |
| `Bar` (actor) | `isolated deinit` | `actor_instance. name: 'self'` |
| `Opted` (`@MainActor`) | `nonisolated deinit` | nonisolated, isolated 함수 없음 |
| `Derived: Base` | `isolated deinit` | `global_actor MainActor` |
| `Implicit: Base` | 없음 | `global_actor MainActor` |

`PlainMain` 이 눈에 띈다. 클래스 자체에는 isolation 이 없어도 `@MainActor deinit` 만 따로 적을 수 있다. `Baz` 는 actor 인데 `deinit` 만 main actor 에 둔 것이고, 이것도 허용된다. `Exotic` 처럼 클래스의 isolation 과 다른 global actor 를 `deinit` 에 적는 것도 된다. `Bar` 는 actor 의 `isolated deinit` 인데, SIL 에서는 `self` 에 묶인 isolation 으로 읽힌다.

한 가지 짚을 것이 `nonisolated deinit` 이다. `Opted` 는 `@MainActor` 클래스인데 `deinit` 만 `nonisolated` 라고 적었고, 결과는 isolated 함수가 생기지 않는 지금까지의 `deinit` 이다. 이 철자는 철자를 적지 않은 평범한 `deinit` 과 같은 결과를 낸다. 제안서도 이 철자를 허용하되 아무 일도 하지 않는다고 적는다. SE-0466 의 기본 MainActor 모드에서도 같은지는 마지막 장에서 따로 쟀다. [SE-0449 글](https://haroldfromk.github.io/posts/SE-0449/)의 `nonisolated` 가 같은 줄기에 있는 문법이다.

### 상속 규칙과 합성된 deinit

서브클래스는 `deinit` 에 isolation 을 더할 수는 있어도 빼거나 바꿀 수는 없다. 위의 `Removed` 와 `Changed` 가 그 오류다. 반대로 `RulesOK.swift` 의 `AddsIsolation: PlainMainFree` 는 부모가 `nonisolated` 인데 서브클래스가 `@MainActor deinit` 을 적은 것이고 통과한다.

일반 함수의 override 규칙과 방향이 반대라는 점이 헷갈린다. 일반 메서드는 서브클래스의 override 가 부모의 isolation 을 그대로 따라야 한다. `deinit` 은 부모의 `deinit` 을 서브클래스의 `deinit` 이 끝에서 부르기 때문에, 컴파일러가 묻는 질문이 "서브클래스의 `deinit` 이 `super.deinit()` 을 부를 수 있는가" 다. 서브클래스가 main actor 에서 도는데 부모가 `nonisolated` 면 부를 수 있다. `nonisolated` 함수는 어디서든 부를 수 있기 때문이다. 서브클래스가 `nonisolated` 인데 부모가 main actor 면 부를 수 없다. `Removed` 의 오류가 그것이다.

`deinit` 을 쓰지 않은 서브클래스는 어떻게 되는가. `Implicit: Base` 는 `deinit` 을 쓰지 않았는데 SIL 에서 `global_actor MainActor` 이고 `__isolated_deallocating_deinit` 이 만들어진다. 컴파일러가 합성하는 `deinit` 이 부모 `deinit` 의 isolation 을 물려받기 때문이다. 부모가 `isolated deinit` 이면 서브클래스는 아무것도 안 적어도 이어진다.

### 런타임, 인라인이냐 나중이냐

`isolated deinit` 의 실행은 마지막 release 가 어디서 일어났느냐에 따라 달라진다. SIL 에서 `isolated deinit` 을 가진 클래스를 열어 보면 `deinit` 관련 함수가 둘이다.

- `__isolated_deallocating_deinit`: 사용자가 쓴 `deinit` 본문. isolation 이 붙어 있다
- `__deallocating_deinit`: 런타임이 부르는 진입점. 이쪽은 언제나 `nonisolated` 이고, 안에서 `swift_task_deinitOnExecutor` 를 부른다

모든 클래스의 `__deallocating_deinit` 이 nonisolated 로 나오고, `swift_task_deinitOnExecutor` 가 호출 대상으로 보인다. 이 함수가 현재 executor 를 확인한다. 이미 맞는 executor 위라면 `deinit` 을 그 자리에서 바로 실행한다. 아니라면 task 없이 job 을 하나 예약하고, release 를 부른 쪽은 기다리지 않고 돌아간다.

![마지막 release 가 main 에서 일어나면 isolated deinit 이 그 자리에서 돌고, 배경에서 일어나면 release 는 job 만 예약하고 돌아가며 deinit 은 나중에 main 에서 돈다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-09-15-SE-0371/se-0371-hop.png)

실제로 돌려서 순서를 본다.

`Run.swift` (일부)

```swift
import Foundation

func here() -> String { Thread.isMainThread ? "main" : "background" }

@MainActor
final class IsolatedModel {
  let name: String
  nonisolated init(_ name: String) { self.name = name }
  isolated deinit {
    print("  isolated deinit \(name) on", here())
  }
}

@MainActor
final class PlainModel {
  let name: String
  nonisolated init(_ name: String) { self.name = name }
  deinit {
    print("  plain deinit \(name) on", here())
  }
}

actor Counter {
  var count = 0
  isolated deinit {
    print("  actor isolated deinit on", here(), "count:", count)
  }
}
```

`here()` 는 [`Thread.isMainThread`](https://developer.apple.com/documentation/foundation/thread/ismainthread-swift.type.property){:target="_blank"} 로 지금 스레드가 main 인지 알려 주는 도우미다. `Run.swift` 는 이 타입 세 개를 네 가지 방식으로 해제한다. 빌드는 `xcrun swiftc -parse-as-library -swift-version 6 Run.swift -o run` 이다. 배경 task 에서 `IsolatedModel` 을 놓는 경우부터 본다.

```text
$ ./run background
before release on background
after release on background
  isolated deinit A on main
done
```

순서가 핵심이다. `release` 가 부른 쪽은 `after release` 를 먼저 출력하고, `deinit` 은 그다음에 main 에서 돈다. release 가 `deinit` 을 기다리지 않았다는 증거다. 여덟 번 돌려도 같은 순서였다. 두 번째 리뷰에서 ksluder 가 "정말 synchronous 인가, scope 가 끝난 뒤의 assert 는 맞는가" 를 물었는데(두 번째 리뷰 #2, ksluder), 이 출력이 답이다. synchronous 는 `deinit` 본문이 `await` 를 못 쓴다는 뜻이고, release 한 쪽이 끝날 때까지 기다린다는 뜻은 아니다.

main 에서 놓으면 모양이 달라진다.

```text
$ ./run main
before release on main
  isolated deinit B on main
after release on main
done
```

`deinit` 이 `after release` 보다 앞에 찍힌다. executor 가 이미 맞아서 그 자리에서 실행된 것이다. 이 차이가 제안서가 "인라인이냐 나중이냐" 로 구분하는 두 경로다.

`isolated deinit` 이 아닌 `PlainModel` 은 배경에서 놓으면 배경에서 `deinit` 이 돈다.

```text
$ ./run plain
before release on background
  plain deinit C on background
after release on background
done
```

`@MainActor` 클래스인데도 `deinit` 은 배경 스레드다. `isolated` 를 적지 않으면 이렇다는 것이 이 제안의 기본값이다.

마지막으로 actor 다.

```text
$ ./run actor
before release on main
  actor isolated deinit on main count: 0
after release on main
done
```

default actor 의 `isolated deinit` 은 main 에서 놓으니 main 에서 돌았다. 이 출력에는 한 가지가 더 있다. `Counter` 는 `@MainActor` 가 아니라 평범한 default actor 인데, 마지막 release 가 main 스레드에서 일어났는데도 `deinit` 이 main 에서 돌았고 그 자리에서 실행되었다. 제안서 Runtime 절은 default actor 를 해제할 때, 그 actor 에서 돌고 있는 job 이 없다면 executor 를 옮길 필요가 없다고 적고 거의 모든 사용에서 그렇다고 덧붙인다. 첫 리뷰에서 Nickolas_Pohilets 가 같은 설명을 했고, 런타임이 그 actor 의 lock 을 현재 스레드에서 조건부로 잡아 보고 잡히면 그 스레드에서 `deinit` 을 실행한다는 것이다(첫 리뷰 #4, Nickolas_Pohilets). 두 번째 리뷰에서 ktoso 도 default actor 는 inline 으로 `deinit` 이 돌 수 있다고 정리했다(두 번째 리뷰 #7, ktoso). `Counter` 는 도는 job 이 없었으니 lock 이 잡혔고, main 스레드가 release 하는 그 호출 안에서 `deinit` 이 끝난 것이다. 출력에서 `deinit` 이 `after release` 보다 앞에 찍힌 이유가 이 경로다.

#### swift_task_deinitOnExecutor

`__deallocating_deinit` 이 부르는 런타임 함수다. 직접 호출하는 API 가 아니고 컴파일러가 넣는 호출이다. 현재 executor 와 `deinit` 이 필요로 하는 executor 를 비교해서, 같으면 `__isolated_deallocating_deinit` 을 바로 호출하고 다르면 job 을 예약한다.

#### 동시에 잠기는 actor

default actor 의 lock 을 잡는 경로에는 걱정되는 점이 하나 있다. 제안서는 이렇게 적는다. 이전 executor 가 다른 default actor 였다면 그 lock 은 잡힌 채로 남는다. 그래서 여러 actor 가 동시에 잠길 수 있다. 그런데 제안서는 이것이 deadlock 으로 이어지지 않는 이유를 둘로 든다.

- lock 은 조건부로 잡으며 기다리지 않는다. 잡히지 않으면 인라인을 포기하고 job 을 예약한다
- 객체는 두 번 deinitialize 되지 않는다. 그래서 `deinit` 호출이 만드는 그래프에 순환이 없다

첫 번째는 한 스레드가 두 lock 을 쥐고 기다리는 상태를 만들지 않는다는 뜻이고, 두 번째는 A 의 `deinit` 이 B 의 `deinit` 을 부르고 B 의 `deinit` 이 다시 A 의 `deinit` 을 부르는 사슬이 성립하지 않는다는 뜻이다.

#### task executor preference

`isolated deinit` 이 나중에 도는 경로에서 예약되는 job 은 task 밖에서 실행된다. 그래서 task executor preference 는 이 job 에 적용되지 않는다. 제안서 Interaction with task executor preference 절이 그렇게 적는다. 앞에서 본 task local 이 비워지는 것과 같은 뿌리의 사실이다. job 에는 이를 붙잡아 둘 task 가 없다.

#### 큐 기반 executor 와 빠른 경로

두 번째 리뷰에서 ktoso 는 인라인 경로가 항상 열리지 않는 경우를 하나 들었다. 어떤 큐 위에서 도는 custom actor 가 있고, 지금 그 큐 위에서 일을 하고 있는 쪽에서 그 actor 의 `isolated deinit` 이 걸린 객체를 놓는 경우다. SE-0424 의 custom isolation checking 은 "지금 이 executor 인가" 를 물어서 true 를 받을 수는 있어도, dispatch 에는 false 를 돌려주는 API 가 없고 조건이 맞지 않으면 crash 만 한다. 그래서 같은 큐인지를 판별하지 못하는 상황이면 빠른 경로를 못 타고 job 을 예약한다고 그는 설명했다. 반대로 `assumeIsolated` 는 false 일 때 crash 하는 성질 덕분에 이 상황을 정확하게 알아낸다는 주석도 달았다(두 번째 리뷰 #6, ktoso).

이 설명을 세 가지 구성으로 재 보았다. 먼저 `DispatchSerialQueue` 를 executor 로 쓰는 global actor 다.

`QueueActor.swift` (일부)

```swift
let sharedQueue = DispatchSerialQueue(label: "shared.queue")

@globalActor
actor QueueActor {
  static let shared = QueueActor()
  nonisolated var unownedExecutor: UnownedSerialExecutor {
    sharedQueue.asUnownedSerialExecutor()
  }
}

@QueueActor
final class Model {
  nonisolated init() {}
  isolated deinit {
    print("  isolated deinit body")
  }
}
```

이 `Model` 을 세 군데에서 놓는다. `sibling` 은 같은 큐를 executor 로 쓰는 다른 actor 안에서, `rawqueue` 는 어떤 actor 도 아닌 `sharedQueue.async` 블록 안에서, `outside` 는 배경 task 에서 놓는다. 빌드는 `xcrun swiftc -parse-as-library -swift-version 6 QueueActor.swift -o queue` 이다.

```text
$ ./queue sibling
  isolated deinit body
  released, after the release statement
done
$ ./queue rawqueue
  isolated deinit body
  released, after the release statement
done
$ ./queue outside
  released, after the release statement
  isolated deinit body
done
```

`sibling` 과 `rawqueue` 는 인라인이다. `deinit` 본문이 `released` 보다 먼저 찍혔다. `outside` 는 job 으로 나중에 돌았다. 6.4 컴파일러와 macOS 27 런타임에서 `DispatchSerialQueue` 로 만든 executor 는 이 인라인 경로를 탔다.

이번에는 `DispatchSerialQueue` 대신 `SerialExecutor` 를 직접 구현한 executor 두 개가 같은 큐를 공유하게 하고, 한쪽의 actor 에서 다른 쪽 executor 에 묶인 객체를 놓는다.

`QueueExec.swift` (일부)

```swift
let sharedQueue = DispatchQueue(label: "shared.queue")

final class QueueExecutor: SerialExecutor {
  func enqueue(_ job: consuming ExecutorJob) {
    let unowned = UnownedJob(job)
    sharedQueue.async { unowned.runSynchronously(on: self.asUnownedSerialExecutor()) }
  }
  func asUnownedSerialExecutor() -> UnownedSerialExecutor {
    UnownedSerialExecutor(ordinary: self)
  }
}

let executorA = QueueExecutor()
let executorB = QueueExecutor()

actor ActorB {
  nonisolated var unownedExecutor: UnownedSerialExecutor {
    executorB.asUnownedSerialExecutor()
  }

  func release(_ box: Box) {
    var model: Model? = box.take()
    model = nil
    _ = model
    print("  released, after the release statement")
  }
}
```

`Model` 은 `@ActorA` 로 `executorA` 에 묶여 있고 `ActorB` 는 `executorB` 위에서 돈다. 둘은 같은 큐로 일을 보내지만 executor 객체가 다르다. 진단은 `[exit 0]` 이다.

```text
$ ./qexec
  released, after the release statement
  isolated deinit body
done
```

이쪽은 `released` 가 먼저이고 `deinit` 은 job 으로 나중에 돌았다. 같은 큐라는 사실이 executor 객체로는 드러나지 않아서 현재 executor 가 같다고 판정하지 못하고, 인라인 경로를 놓친 것이다. 실행 순서에 기대지 말라는 ktoso 의 결론이 이 부분에 근거한다. 빠른 경로는 최적화이고, 어느 경우에 타는지는 executor 의 구현에 달려 있다.

### task local 비우기

`deinit` 에서 task local 값을 읽으면 어떻게 되는가. 이 질문 하나에 제안이 한 번 반려되고, 수락 때 수정이 붙었다. 결론은 수락 때의 수정이다. `isolated deinit` 에 들어갈 때 task local 은 언제나 비워진다. job 으로 나중에 도는 경우만이 아니라 인라인으로 도는 경우에도 그렇다.

`LocalsShort.swift` (일부)

```swift
import Foundation

enum Trace {
  @TaskLocal static var id = "none"
}

@MainActor
final class IsolatedModel {
  nonisolated init() {}
  isolated deinit {
    print("  isolated deinit on", here(), "Trace.id =", Trace.id)
    Trace.$id.withValue("inside") {
      print("  inside withValue Trace.id =", Trace.id)
    }
  }
}

final class PlainModel {
  deinit {
    print("  plain deinit on", here(), "Trace.id =", Trace.id)
  }
}
```

[`TaskLocal`](https://developer.apple.com/documentation/swift/tasklocal){:target="_blank"} 는 task 에 값을 붙이는 property wrapper 이고, `Trace.$id.withValue(_:operation:)` 는 그 값을 클로저 범위 안에서만 바꾼다. 배경에서 `withValue("release")` 범위 안에 `model = nil` 을 두고 돌린다. 빌드는 `xcrun swiftc -parse-as-library -swift-version 6 LocalsShort.swift -o locals` 이다.

```text
$ ./locals hop
  isolated deinit on main Trace.id = none
  inside withValue Trace.id = inside
done
```

release 한 쪽에서는 `Trace.id` 가 `release` 였는데 `deinit` 안에서는 기본값 `none` 이다. job 이 task 없이 실행되니 값이 따라오지 않는 것이다. 이번에는 main 에서 놓는다.

```text
$ ./locals inline
  isolated deinit on main Trace.id = none
  inside withValue Trace.id = inside
done
```

인라인이어서 같은 task 안인데도 `none` 이다. 런타임이 `isolated deinit` 에 들어가면서 task local 을 비웠기 때문이다. `deinit` 본문 안에서 쓴 `withValue` 의 값은 그 범위 안에서 보인다.

`isolated` 가 아닌 평범한 `deinit` 은 다르다.

```text
$ ./locals plain
  plain deinit on main Trace.id = release
done
```

`nonisolated` `deinit` 은 release 한 task 에서 그대로 돌아서 값이 보인다. 그래서 "task local 을 늘 비운다" 는 규칙은 `isolated deinit` 에만 걸린다. 같은 코드에 `isolated` 를 붙이면 보이던 값이 사라지는 곳이 생긴다는 뜻이다.

같은 코드에 priority 도 같이 찍는 `Locals.swift` 로 재면 이렇다. 이 파일은 위 `LocalsShort.swift` 에서 `print` 두 곳에 `"priority:", Task.currentPriority` 가 더 붙은 것이다.

```text
$ ./locals hop
  isolated deinit on main Trace.id = none priority: TaskPriority(rawValue: 33)
  inside withValue Trace.id = inside
done
$ ./locals hop-high
  isolated deinit on main Trace.id = none priority: TaskPriority(rawValue: 33)
  inside withValue Trace.id = inside
done
$ ./locals inline
  isolated deinit on main Trace.id = none priority: TaskPriority.medium
  inside withValue Trace.id = inside
done
$ ./locals plain
  plain deinit on main Trace.id = release priority: TaskPriority.medium
done
```

`hop` 은 `.utility` 로, `hop-high` 는 `.high` 로 띄운 배경 task 에서 놓은 것이다. 나중에 도는 두 경우 모두 `deinit` 안의 `Task.currentPriority` 는 `TaskPriority(rawValue: 33)` 이었고, 인라인과 평범한 `deinit` 은 `medium` 이었다.

#### 제안서가 권하는 쓰는 법

제안서의 Task-local values 절은 값을 비우는 이유와 대안을 같이 적는다. 이 동작은 인라인으로 돌 때와 hop 으로 돌 때의 `isolated deinit` 이 똑같이 움직이게 하면서, task local 을 복사하는 런타임 비용을 내지 않으려는 것이다. 그리고 마지막 release 가 일어나는 지점은 예측하기 어렵고 최적화로도 바뀐다. 그래서 debug 빌드와 release 빌드에서 동작이 달라질 수 있다. 제안서는 개발자가 마지막 release 시점의 task local 집합에 기대지 말라고 하고, 대신 객체의 저장 프로퍼티로 의존성을 주입하라고 권한다. 이 권고는 `nonisolated deinit` 에도 똑같이 적용되지만 이 제안은 그쪽 동작을 바꾸지 않는다고 덧붙인다. 마지막으로 UIKit 클래스가 `retain` 과 `release` 를 override 해서 main 으로 옮기는 기존 hop 은 task local 을 알지 못할 가능성이 크다고 적는다.

반려 공지가 이 규칙의 씨앗이었다. 워크그룹은 task local 을 복사하는 것이 비싸고 실용적이지 않다고 보았지만, `deinit` 이 마지막 release 를 하는 task 에 따라 다른 값이 아니라 일관된 view 를 받는 것에는 가치가 있다고 인정했다. 그래서 복사하지 말고 `deinit` 에 들어가기 전에 비우라고 요구했다(반려 #1, Jumhyn).

#### 포럼에서 갈린 두 시각

수락 전에 스레드에서 이 규칙을 두고 나온 이야기를 두 가지만 옮긴다. 첫 번째는 수정 논의에서 Nickolas_Pohilets 가 task local 이 유용한 경우를 두 가지로 든 것이다. 대부분은 task 트리의 뿌리에서 값을 설정한 경우다. 마지막 release 가 어느 잎 task 에서 일어나든 값이 트리 전체에 있으니 상관이 없다. 가끔은 디버깅처럼 추상화를 깨고 마지막 release 가 어느 task 에서 일어났는지 알고 싶은 경우다. 그리고 `deinit` 에서 task local 에 기대는 것이 취약하다는 점은 이미 평범한 `deinit` 에서도 마찬가지이니, 그게 큰 문제라면 isolation 을 더하는 이 제안이 아니라 모든 `deinit` 에서 task local 을 막는 쪽을 논의해야 한다고 했다(수정 논의 #6, Nickolas_Pohilets). 두 번째는 ktoso 가 distributed tracing 쪽에서 본 시각이다. tracing span 같은 값을 task local 로 들고 있는 코드는 `deinit` 시점에 task local 이 있다고 믿을 수 없고, 값이 필요하면 `defer { span.end() }` 나 `withSpan {}` 처럼 명시적으로 끝내야 한다는 것이다(수정 논의 #7, ktoso).

서브 pitch 에서는 task local 보다 비동기 쪽 이야기가 따로 나왔다. 컴파일러가 만들어 주는 unstructured `Task` 는 footgun 이라서 unstructured `Task` 는 명시적으로 만들어야 한다는 FranzBusch 의 글이 있다. 그는 async `deinit` 이 필요한 곳은 `~Copyable` 타입이라고도 했다(서브 pitch #3, FranzBusch). ktoso 는 암묵적으로 미뤄지는 해제가 걱정이라며 전용 worker 를 둘 수 있을지를 물었다(서브 pitch #2, ktoso). Nickolas_Pohilets 는 task local 을 정의되지 않은 채 두는 안이 ObjC 상위 클래스의 `release` override 가 task local 을 모른다는 점과도 맞는다고 보았다(서브 pitch #26, Nickolas_Pohilets).

이 규칙에 이르는 길이 이 제안의 큰 줄거리다. 스레드 장에서 다시 본다.

### deinit 안에서 self 를 놓아주지 않기

`deinit` 은 객체가 죽는 중이다. 여기서 `self` 를 Task 같은 곳에 넘겨서 `deinit` 보다 오래 살게 하면 해제된 객체를 쓰는 것이 된다. 제안서는 이 경우를 막는다.

`Escape.swift` (일부)

```swift
func logClicks(_ count: Int) async {
  print("logged clicks:", count)
}

actor Clicker {
  var count: Int = 0

  func click(_ times: Int) {
    for _ in 0..<times {
      self.count += 1
    }
  }

  isolated deinit {
    let moreClicks = 10
    Task { await self.click(moreClicks) }
    print("deinit end, count:", count)
  }
}
```

```text
Escape.swift:16:10: error: capture of 'self' in a closure that outlives deinit
Escape.swift:16:12: warning: no 'async' operations occur within 'await' expression [#UnnecessaryEffectMarker]
[exit 1]
```

`Task { ... }` 안에서 `self` 를 잡은 것이 오류다. 이 진단은 Swift 6 언어 모드에서 오류이고, Swift 5 모드에서는 경고다. 같은 파일을 `-swift-version 5` 로 진단하면 16:10 의 메시지가 `capture of 'self' in a closure that outlives deinit; this is an error in the Swift 6 language mode` 로 바뀐 경고가 된다.

옆의 두 번째 경고가 왜 붙는지도 이유가 있다. `Task` 의 클로저는 `deinit` 의 isolation 을 물려받는다. 그래서 `await self.click(moreClicks)` 의 `await` 는 같은 actor 안의 동기 호출이 되어서 쉬어 갈 곳이 없다는 경고가 나온 것이다.

고치는 방법은 필요한 값만 캡처하는 것이다. `SafeClicker` 가 그렇다.

```swift
actor SafeClicker {
  var count: Int = 3

  isolated deinit {
    Task { [count] in
      await logClicks(count)
    }
  }
}
```

진단은 비어 있고, 실행하면 이렇다.

```text
$ ./escape safe
logged clicks: 3
done
```

`[count]` 로 값을 복사해서 넘기니 `self` 가 `deinit` 밖으로 나가지 않는다. 이 실행 파일은 `-swift-version 5` 모드로 빌드했다. `Escape.swift` 에 `Clicker` 도 같이 들어 있어서 Swift 6 모드로는 컴파일되지 않기 때문이다.

경고를 무시하고 돌리면 어떻게 되는지도 같은 파일로 쟀다. 인자 없이 실행하면 `Clicker` 가 만들어졌다 해제된다.

```text
$ ./escape
Object 0x... of class Clicker deallocated with non-zero retain count 3. This object's deinit, or something called from it, may have created a strong reference to self which outlived deinit, resulting in a dangling reference.
deinit end, count: 0
```

종료 코드는 134 다. 객체가 해제될 때 retain count 가 0 이 아니면 런타임이 죽는다.

컴파일러가 모르는 탈출도 있다. `@unchecked Sendable` 상자에 `self` 를 넣는 경우다.

`Escape2.swift` (일부)

```swift
final class Box: @unchecked Sendable {
  var items: [AnyObject] = []
}
let box = Box()

actor Clicker {
  var count: Int = 0

  isolated deinit {
    box.items.append(self)
    print("deinit end")
  }
}
```

진단은 `[exit 0]` 이다. 상자 안으로 `self` 를 넣는 것은 컴파일러가 따라가지 못한다. 실행하면 런타임이 이렇게 죽는다.

```text
Object 0x... of class Clicker deallocated with non-zero retain count 2. ...
deinit end
```

종료 코드는 134 다. 이 검사가 `isolated deinit` 에만 있는지도 확인해 보았다. `isolated` 가 없는 평범한 클래스의 `deinit` 에서 같은 일을 한다.

`PlainEsc.swift`

```swift
final class Box: @unchecked Sendable { var items: [AnyObject] = [] }
let box = Box()
final class K { deinit { box.items.append(self); print("deinit end") } }
@main struct P { static func main() { _ = K(); print("done") } }
```

```text
Object 0x... of class K deallocated with non-zero retain count 2. ...
deinit end
```

이것도 종료 코드 134 다. 이 검사는 모든 `deinit` 에 있고 `isolated deinit` 이 새로 만든 것이 아니다. 정리하면 눈에 보이는 클로저 캡처는 Swift 6 에서 컴파일 오류, 눈에 안 보이는 탈출은 런타임 crash 다.

#### 제안서가 든 ViewModel 예

제안서 Future Directions 는 같은 함정을 `@MainActor` 클래스로 보여 준다. `deinit` 에서 `Task` 가 암묵적으로 `self` 를 잡으면 런타임 fatal error 가 되므로, 필요한 프로퍼티만 캡처 목록에 넣어야 한다.

```swift
actor Service {
  func shutdown() {}
}

@MainActor
class ViewModel {
  let service: Service

  deinit {
    // Incorrect:
    _ = Task { await service.shutdown() }

    // Corrected version:
    _ = Task { [service] in await service.shutdown() }
  }
}
```

첫 `Task` 는 `service` 를 `self.service` 로 읽으니 `self` 를 잡고, 두 번째는 `service` 만 복사한다. 이 코드는 제안서의 것을 그대로 옮긴 것이고, 이 글에서 따로 돌려 보지는 않았다. 제안서는 거의 모든 프로퍼티를 복사해야 한다면 객체를 task 의 문맥으로 재사용하는 async `deinit` 이 더 효율적일 것이라고 이어 적는다. 이 이야기는 다른 선택지 장의 Future Directions 에서 다시 본다.

### Objective-C 와 섞일 때

Objective-C 의 `dealloc` 과 [`NSObject`](https://developer.apple.com/documentation/objectivec/nsobject-swift.class){:target="_blank"} 가 섞이면 이야기가 복잡해진다. [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/)에서 본 `_checkExpectedExecutor` 가 여기서도 나온다.

#### Swift 만으로 NSObject 를 상속할 때

먼저 Swift 만으로 `NSObject` 를 상속한 경우다.

`ObjC.swift` (일부)

```swift
@MainActor
class Base: NSObject {
  nonisolated override init() { super.init() }
  isolated deinit { print("  Base deinit on", here()) }
}

@MainActor
final class Derived: Base {
  isolated deinit { print("  Derived deinit on", here()) }
}
```

배경에서 `Derived` 를 놓는다.

```text
$ ./objc
released on background
  Derived deinit on main
  Base deinit on main
done
```

`Derived` 의 `deinit` 에 이어 `Base` 의 `deinit` 이 main 에서 돈다. 이 두 클래스의 SIL 을 `-emit-sil` 로 뽑아 `swift-demangle` 에 넣으면 클래스마다 함수가 세 개씩 나온다.

```text
sil hidden @oc.Base.__isolated_deallocating_deinit
sil hidden @oc.Base.__deallocating_deinit
sil private [thunk] @@objc oc.Base.__deallocating_deinit
sil hidden @oc.Derived.__isolated_deallocating_deinit
sil hidden @oc.Derived.__deallocating_deinit
sil private [thunk] @@objc oc.Derived.__deallocating_deinit
```

`__isolated_deallocating_deinit` 에 사용자가 쓴 본문이 들어 있고, Swift 쪽 `__deallocating_deinit` 이 `swift_task_deinitOnExecutor` 로 executor 를 맞춘 뒤 그것을 부른다. `@objc` 가 붙은 thunk 는 Objective-C 런타임이 `dealloc` 메시지로 들어올 때의 입구다. `Derived.__isolated_deallocating_deinit` 은 본문을 실행한 다음 부모의 `deinit` 을 이 한 줄로 부른다. `-Onone` 과 `-O` 모두 같은 모양이었다.

```text
%36 = objc_super_method %0, #Base.deinit!deallocator.foreign : (Base) -> () -> (), $@convention(objc_method) (Base) -> ()
%37 = upcast %0 to $Base
%38 = apply %36(%37) : $@convention(objc_method) (Base) -> ()
```

그래서 경로는 이렇게 이어진다. 배경에서 `Derived` 의 마지막 release 가 일어나면 `Derived` 의 `@objc` thunk 가 `Derived.__deallocating_deinit` 으로 가고, 그것이 `swift_task_deinitOnExecutor` 로 main 으로 옮긴다. main 에서 `Derived.__isolated_deallocating_deinit` 이 돌고, `Base` 의 `@objc` thunk 와 `Base.__deallocating_deinit` 을 거치지만 이미 main 이라서 빠른 경로로 지나간다. 실제로 executor 를 옮기는 것은 가장 아래 서브클래스뿐이다.

![Swift 계층과 Objective-C 계층에서 deinit 이 main 으로 가는 경로](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-09-15-SE-0371/se-0371-objc.png)

`-emit-objc-header` 로 내보낸 헤더에서 `@interface Base : NSObject` 와 `@interface Derived : Base` 에는 `init` 만 있고 `dealloc` 이나 isolation 에 관한 정보가 없다. 제안서 Exporting to Objective-C 절은 Objective-C 코드가 Swift 클래스를 상속할 수 없으니 `deinit` isolation 이 `*-Swift.h` 에 더하는 정보가 없다고 적는다. 측정이 그것과 같았다.

#### Objective-C 에서 시작한 클래스를 상속할 때

까다로운 쪽은 Objective-C 에서 시작한 클래스를 Swift 가 상속할 때다. 아래 `Legacy.h` 는 클래스와 `dealloc` 에 `@MainActor` 를 `swift_attr` 로 달았다.

`Legacy.h`

```objc
#import <Foundation/Foundation.h>
__attribute__((swift_attr("@MainActor")))
@interface Legacy : NSObject
- (void)dealloc __attribute__((swift_attr("@MainActor")));
@end
__attribute__((swift_attr("@MainActor")))
@interface LegacyPlain : NSObject
@end
```

`Legacy.m` 의 `dealloc` 은 `NSLog` 로 main 인지 찍고 `[super dealloc]` 을 부른다. 이 구현은 `release` 를 override 하지 않는다. 모듈은 `module Legacy { header "Legacy.h" export * }` 로 열었고, 빌드는 `clang -fno-objc-arc -c objcmod/Legacy.m` 으로 만든 `Legacy.o` 를 `xcrun swiftc -I objcmod ... Legacy.o` 에 같이 넘겼다.

이 `Legacy` 를 Swift 에서 상속해 `isolated deinit` 을 적는다.

`ImportOK.swift`

```swift
import Foundation
import Legacy

final class NonSendableLog { var lines: [String] = [] }

final class Sub: Legacy {
  let log = NonSendableLog()
  isolated deinit { log.lines.append("bye") }
}
```

진단은 없다(`[exit 0]`). `Sub` 의 `deinit` 이 isolated 로 검사되어서 `Sendable` 이 아닌 `log` 를 만져도 된다. 그런데 SIL 을 열면 `__isolated_deallocating_deinit` 도 `swift_task_deinitOnExecutor` 도 한 번도 안 나온다. 대신 `@objc Sub.__deallocating_deinit` thunk 가 `_checkExpectedExecutor` 를 부르고 `Sub.__deallocating_deinit` 을 부른다. 타입 검사에서는 isolated 인데 실행 시 executor 를 옮겨 주는 hop 이 없는 모양이다.

제안서 Importing Objective-C code 절은 이 구성을 이렇게 설명한다. `dealloc` 에 isolation 을 달았다는 것은 `dealloc` 이 그 executor 에서만 불려야 한다는 뜻이다. 그런 클래스는 `retain` 과 `release` 를 override 해서 이를 지킨다고 가정하며, Swift 서브클래스의 `deinit` 은 그 `dealloc` 의 override 로 만들어진다. 그래서 부모에서 성립하는 사전 조건이 서브클래스에도 성립하니, 서브클래스에서 isolation thunk 를 만들지 않는 것은 코드 크기와 성능을 위한 최적화다.

그러면 어떻게 도는가. main 에서 놓으면 문제가 없다.

```text
$ ./importrun main
2026-11-27 00:07:03.650 importrun[...] Legacy dealloc main=1
main mode: true
Sub deinit main: true
done
```

여기서 `NSLog` 줄이 `main mode: true` 보다 먼저 찍힌 것은 `NSLog` 가 stderr 로 바로 쓰고 `print` 는 버퍼링되는 stdout 으로 가기 때문이라서 두 스트림이 섞인 순서다. 실제 해제는 `main mode: true` 뒤의 `keep = nil` 에서 일어난다.

배경에서 놓으면 죽는다.

```text
$ ./importrun
(exit 133)
```

stdout 이 버퍼링되어 있어서 죽기 전에 찍은 글도 나오지 않고, stderr 만 따로 보아도 비어 있었다. lldb 로 보면 `EXC_BREAKPOINT` 이다. 명령은 `timeout 20 xcrun lldb --batch -o run -k bt -k quit -- ./importrun` 이다. 스택은 주소를 빼고 이렇다.

```text
thread #3, name = 'Task 2', queue = 'com.apple.root.default-qos.cooperative', stop reason = EXC_BREAKPOINT
  libdispatch.dylib  _dispatch_assert_queue_fail
  libdispatch.dylib  dispatch_assert_queue$V2.cold.1
  libdispatch.dylib  dispatch_assert_queue
  libswift_Concurrency.dylib  _swift_task_checkIsolatedSwift
  libswift_Concurrency.dylib  swift_task_isCurrentExecutorWithFlagsImpl(...)
  libswift_Concurrency.dylib  _checkExpectedExecutor(_filenameStart:...)
  importrun  @objc importrun.Sub.__deallocating_deinit + 112
  importrun  closure #1 in static Program.main()
```

`@objc Sub.__deallocating_deinit` 에서 `_checkExpectedExecutor` 가 호출되고, 현재 큐가 main 이 아니라서 `dispatch_assert_queue` 가 실패한다. 이 부분이 [SE-0423 글](https://haroldfromk.github.io/posts/SE-0423/)에서 본 런타임 검사와 같은 장치다. 이 실험의 `Legacy.m` 은 `release` 를 override 하지 않아서 배경 release 를 main 으로 돌려 주는 장치가 없고, 그래서 이 검사에서 죽는다. 제안서가 `dealloc` 에 isolation 을 다는 Objective-C 클래스는 `retain` 과 `release` 를 override 하라고 한 이유가 이 경로다.

참고로 이 글의 `importrun` 같은 실험에는 `nonisolated(unsafe) var keep: Sub?` 라는 전역 변수가 나온다. [SE-0412 글](https://haroldfromk.github.io/posts/SE-0412/)에서 다룬 전역 변수 규칙을 끄는 표시이고, 여기서는 배경 task 에서 바로 건드리려고 썼다.

#### dealloc 에 표시를 다는 기준

`LegacyPlain` 처럼 클래스에만 `@MainActor` 를 달고 `dealloc` 에는 달지 않은 경우를 보자.

`ImportPlain.swift` (일부)

```swift
final class SubPlain: LegacyPlain {
  let log = NonSendableLog()
  deinit { log.lines.append("bye") }
}
```

```text
ImportPlain.swift:8:12: error: cannot access property 'log' with a non-Sendable type 'NonSendableLog' from nonisolated deinit
  note: class 'NonSendableLog' does not conform to the 'Sendable' protocol
  note: add 'isolated' to run isolated to 'MainActor', which may be later than 'nonisolated deinit'
[exit 1]
```

클래스에만 isolation 이 있으면 `deinit` 은 `nonisolated` 로 남고, 앞의 Motivation 과 같은 오류가 난다. 제안서도 이 경우를 같이 적는다. 클래스에 단 표시는 Objective-C 코드의 동작을 바꾸지 않으므로 이렇게 `nonisolated` `deinit` 으로 가져온다.

`dealloc` 까지 표시한 `Legacy` 에서는 반대 방향이 막힌다. `Legacy` 를 상속하면서 `deinit {}` 만 쓰면 오류다.

```text

.../objcmod/Legacy.h:4:1: note: overridden declaration is here
[exit 1]
```

note 가 가리키는 곳이 `Legacy.h` 의 `dealloc` 줄이다. 다른 global actor 를 적어도 같다.

`deinit` 을 쓰지 않은 서브클래스는 어떻게 되는지도 쟀다.

#### 어떤 Objective-C 클래스가 dealloc 에 표시를 다는가

제안서는 `dealloc` 에 isolation 을 다는 기준도 적는다. `retain` 과 `release` 를 override 해서 isolation 을 구현한 Objective-C 클래스는 `dealloc` 에 표시를 달아야 한다. Swift 서브클래스가 isolation 의 이익을 다 받게 되고, 서브클래스가 다른 actor 에서 `deinit` 과 `[super dealloc]` 을 돌리지 못하게도 막는다. 반대로 `dealloc` 안에서 executor 를 바꾸는 클래스는 표시를 달면 안 된다. 그 `dealloc` 은 어느 스레드에서든 불릴 수 있고, 서브클래스가 다른 actor 에 isolate 하는 것을 막지도 않는다. 그런 경우에 서브클래스의 isolation thunk 를 생략하면 잘못된 것이다.

제안서가 보이는 패턴은 이렇게 `dealloc` 이 일을 `dealloc_impl` 로 넘기는 모양이다.

```objc
- (void)dealloc_impl { ... }

static void dealloc_impl_helper(void *ctx) {
    [(MyClass*)ctx dealloc_impl];
}

- (void)dealloc {
    dispatch_async_f(dispatch_get_main_queue(), self, dealloc_impl_helper);
}
```

이 글의 `Legacy` 는 `release` 를 override 하지 않으면서 `dealloc` 에 표시를 달았다. 표시가 약속하는 것을 구현이 지키지 않는 구성이어서, 배경 release 에서 죽은 것이다.

macOS 27 SDK 의 AppKit 과 Foundation 헤더를 `swift_attr` 로 훑어보니 `dealloc` 에 이 표시를 단 곳은 없었다. 그러면 `NSView` 서브클래스는 어떤가. `NSViewSub.swift` 의 `final class MyView: NSView` 에 `isolated deinit` 을 쓰고 SIL 을 열었다.

`NSViewSub.swift`

```swift
import AppKit

final class NonSendableLog { var lines: [String] = [] }

final class MyView: NSView {
  let log = NonSendableLog()
  isolated deinit { log.lines.append("bye") }
}
```

```text
sil hidden @nv.MyView.__isolated_deallocating_deinit
sil hidden @nv.MyView.__deallocating_deinit
  function_ref @swift_task_deinitOnExecutor
sil [available 15.4] @swift_task_deinitOnExecutor
sil private [thunk] @@objc nv.MyView.__deallocating_deinit
```

`MyView.__deallocating_deinit` 은 `swift_task_deinitOnExecutor` 를 부르고(이 심볼은 `[available 15.4]` 다), `@objc MyView.__deallocating_deinit` thunk 에는 `_checkExpectedExecutor` 가 없었다. `_checkExpectedExecutor` 는 init thunk 쪽에만 있었다. `Legacy` 와 달리 `dealloc` 표시가 없는 SDK 클래스의 서브클래스는 `isolated deinit` 의 hop 을 스스로 가지고 있다. 제안서가 말하는 isolation 이 Swift 에서 시작된 계층이라서 클래스마다 thunk 가 만들어지는 경우다.

#### 런타임을 건드리는 주의점

제안서 Interaction with ObjC runtime 절에 주의할 것이 하나 더 있다. Objective-C 와 호환되는 모든 Swift 클래스는 `dealloc` 을 합성하는데, 이것은 `__deallocating_deinit` 으로 가는 thunk 다. 보통 `__deallocating_deinit` 이 `super.deinit` 을 부를 때는 `objc_msgSuper` 로 `dealloc` 메시지를 보낸다. 이러면 Objective-C 와의 호환성이 최대이지만 런타임 비용이 따른다. 제안서는 isolated `deinit` 이 Swift 기반 클래스의 isolated `deinit` 을 부를 때 이 Objective-C 런타임을 건너뛰고 `__isolated_deallocating_deinit` 을 직접 부른다고 쓴다. 그래서 호환성은 Swift 와 Objective-C 의 경계에서만 지켜진다.

이것이 실무에서 어디까지 영향을 주는지도 제안서가 구분한다. 런타임에서 Objective-C 서브클래스를 만드는 KVO 는 괜찮다. 가장 아래 파생 클래스의 `dealloc` 을 swizzling 하는 것도 괜찮다. 하지만 중간 Swift 클래스의 `dealloc` 을 swizzling 하는 것은 기대대로 동작하지 않을 수 있다. 그래서 중간 클래스의 `dealloc` 에 끼워 넣는 swizzling 은 설계 단계에서 보장 범위 밖이다.

마지막으로 distributed actor 의 원격 proxy 는 `deinit` 이 아예 isolated 가 아니다.

### 기본 MainActor 모드에서

[SE-0466 글](https://haroldfromk.github.io/posts/SE-0466/)의 `-default-isolation MainActor` 모드를 켜면 isolation 을 안 적은 선언이 `@MainActor` 가 된다. 이때 `deinit` 은 이 제안과 맞물려서 한 번 더 갈린다. 사용자가 `deinit` 을 쓰지 않은 클래스는 컴파일러가 합성하는 `deinit` 이 isolated 가 되고, 직접 쓴 평범한 `deinit` 과 `nonisolated deinit` 은 `nonisolated` 로 남는다.

`Default.swift`

```swift
final class Log { var lines: [String] = [] }

final class Screen {
  let log = Log()
  deinit {
    log.lines.append("closed")
  }
}

final class IsolatedScreen {
  let log = Log()
  isolated deinit {
    log.lines.append("closed")
  }
}
```

```text
Default.swift:6:9: error: main actor-isolated property 'lines' can not be mutated from a nonisolated context
  note: mutation of this property is only permitted within the actor
```

`-default-isolation MainActor` 로 컴파일한 결과다. `Log` 는 `@MainActor` 로 추론되어 `lines` 가 main actor 의 상태이고, 직접 쓴 `Screen` 의 `deinit` 이 nonisolated 라서 만질 수 없다. `IsolatedScreen` 에는 오류가 없다. `IsolatedScreen` 만 남긴 `DefaultOK.swift` 는 `[exit 0]` 이다.

#### 철자 세 가지를 나란히 놓기

`deinit` 을 쓰지 않은 클래스, 평범한 `deinit` 을 쓴 클래스, `nonisolated deinit` 을 쓴 클래스를 한 파일에 넣고 두 모드에서 SIL 의 isolation 주석을 읽었다.

`NI.swift`

```swift
final class A { deinit {} }
final class B { nonisolated deinit {} }
final class C {}
```

기본 모드에서는 세 클래스 모두 `__isolated_deallocating_deinit` 이 없고 `__deallocating_deinit` 이 `nonisolated` 다. `-default-isolation MainActor` 모드의 결과는 이렇다.

| 클래스 | `deinit` | `__isolated_deallocating_deinit` | `__deallocating_deinit` |
|---|---|---|---|
| `A { deinit {} }` | `nonisolated` | 없음 | `nonisolated` |
| `B { nonisolated deinit {} }` | `nonisolated` | 없음 | `nonisolated` |
| `C {}` (합성) | `global_actor MainActor` | `global_actor MainActor` | `nonisolated` |

`C` 만 `swift_task_deinitOnExecutor` 를 부르는 `__deallocating_deinit` 을 갖는다. 그러니 `nonisolated deinit` 은 어느 모드에서든 철자를 안 적은 평범한 `deinit` 과 같은 결과를 낸다. 위의 철자 절에서 말한 "효과 없는 철자" 가 MainActor 모드에서도 성립한다는 측정이다.

#### 합성된 deinit

`deinit` 을 안 쓴 클래스는 SIL 로 읽었다.

`Implicit.swift`

```swift
final class Log { var lines: [String] = [] }

@MainActor
final class ExplicitMain { var lines: [String] = [] }
```

| 모드 | `Log.deinit` | `ExplicitMain.deinit` | `__isolated_deallocating_deinit` |
|---|---|---|---|
| 기본 | `unspecified` | `unspecified` | 없음 |
| MainActor | `global_actor MainActor` | `global_actor MainActor` | 있음, `swift_task_deinitOnExecutor` 호출 |

기본 모드에서는 `deinit` 을 쓰지 않으면 isolation 이 `unspecified` 이고 `__isolated_deallocating_deinit` 이 안 만들어진다. MainActor 모드에서는 쓰지 않은 `deinit` 이 isolated 가 되고, 이때 `@MainActor` 를 직접 단 `ExplicitMain` 도 같이 바뀐다. 눈에 안 보이는 `deinit` 이 isolated 가 된다는 점이 중요하다. 실제 영향은 아래와 같다.

`DefaultRun.swift` (일부)

```swift
nonisolated final class Probe: Sendable {
  let name: String
  init(_ name: String) { self.name = name }
  deinit { print("  Probe \(name) released on", here()) }
}

final class Holder: Sendable {
  let probe: Probe
  nonisolated init(_ name: String) { probe = Probe(name) }
}
```

`Holder` 는 `deinit` 을 쓰지 않았고, `Probe` 의 `deinit` 은 어디서 release 되느냐에 따라 도는 곳이 달라진다. 배경 task 에서 `Holder` 를 놓는다.

```text
# -default-isolation MainActor
after release on background
  Probe implicit released on main
done

# 기본 모드
  Probe implicit released on background
after release on background
done
```

MainActor 모드에서는 `Holder` 의 합성 `deinit` 이 isolated 라서 main 으로 넘어가고, 그 안에서 `Probe` 가 해제된다. 그래서 `Probe` 의 `deinit` 이 main 에서 돈다. 기본 모드에서는 배경 스레드 그대로다. 같은 코드가 모드에 따라 `deinit` 시점이 달라지는 것이다.

#### 비용과 일관성

이 설계에는 비용 논거가 붙는다. 제안서가 든 수치로는 `deinit` 선언이 7만 7천 5백 개쯤, 클래스가 220 만 개쯤이어서 직접 `deinit` 을 쓴 클래스는 3.5% 다. 제안서는 이 수치를 isolation 을 모든 동기 `deinit` 에 암묵적으로 전파하는 안을 기각하는 근거로 쓴다. 대부분의 `deinit` 은 컴파일러가 합성한 것이고 저장 프로퍼티를 release 할 뿐이라서, 그것까지 isolated 로 만들면 큰 성능 비용을 낸다는 것이다. 첫 리뷰의 중심 논점도 같은 곳이었다.

같은 자리에 6.4 의 MainActor 모드에서 잰 사실을 놓는다. 이 모드에서 합성 `deinit` 은 isolated 이고, 직접 쓴 `deinit {}` 는 `nonisolated` 다(`NI.swift`). 첫 리뷰에서 inamiy 가 걱정한 것은 암시적 `deinit` 과 명시적 `deinit {}` 의 동작이 갈리는 점이었고(첫 리뷰 #8, inamiy), Douglas_Gregor 는 `init` 처럼 기본을 nonisolated 로 하자고 했다(첫 리뷰 #10, Douglas_Gregor). 이 모드에서는 그 갈림이 방향을 바꾸어 나타난다. 쓰지 않은 쪽이 isolated 이고 `deinit {}` 를 쓴 쪽이 `nonisolated` 다. 두 철자의 차이는 `nonisolated deinit` 과 `isolated deinit` 을 직접 적어서 가를 수 있다.

### 첫 pitch 와 첫 리뷰

2022-06 의 첫 pitch 에서 Nickolas_Pohilets 가 올린 원안은 지금과 달랐다. 명시적 `deinit` 이 있으면 isolation 을 일반 규칙으로 계산해서 기본으로 isolated 였고(`@MainActor` 클래스의 `deinit {}` 는 main 에서, `nonisolated deinit` 으로 끌 수 있다), 쓰지 않은 `deinit` 은 isolated 로 만들지 않았다. 마지막 release 가 엉뚱한 곳이면 task local 과 priority 를 복사해서 hop 하는 설계였고, 런타임 함수 이름은 `swift_task_performOnExecutor` 였다. 첫 pitch 본문의 `Clicker` 예제는 이 글의 `self` 탈출 장에서 본 그 예제다(첫 pitch #1, Nickolas_Pohilets).

이어진 첫 리뷰에서 ktoso 가 먼저 짚은 것은 이렇다. 쓰지 않은 기본 `deinit` 에는 hop 이 없어서 좋다고 했다. 반면 사용자가 쓴 `deinit` 이 기본으로 hop 하는 것을 비판했다. 그는 `deinit` 은 `init` 을 본뜬 모델이어야 하고 `init` 은 opt-in 이라고 하며 `deinit async` 를 제안했다. 그리고 task local 을 미리 복사하는 것도 걱정했다(첫 리뷰 #3, ktoso).

Nickolas_Pohilets 는 복사가 드물다고 답했다. 명시적 `deinit` 이 있는 클래스는 3.5% 뿐이고, default actor 는 현재 스레드에서 lock 을 잡는다는 것이다(첫 리뷰 #4, Nickolas_Pohilets). inamiy 는 암시적 `deinit` 과 명시적 `deinit {}` 의 동작이 갈리는 점을 지적하고 `nonisolated deinit` 철자를 제안했다(첫 리뷰 #8, inamiy). 위에서 본 철자가 여기서 나왔다.

가장 무게가 실린 글은 Douglas_Gregor 의 것이다. 그는 `init` 처럼 기본을 nonisolated 로 뒤집자고 했다. 많은 `@MainActor` 클래스가 필요 없는 main hop 을 치르게 되고, task local 에 의존하는 `deinit` 은 이미 의미가 깨진 것이라는 이유였다. `deinit async` 에도 흥미를 보였다(첫 리뷰 #10, Douglas_Gregor).

### 반려와 수정

Jumhyn 은 2022-09-02 에 이 제안을 수정하라며 돌려보냈다. 요구는 세 가지였다. 기본은 nonisolated 로 하고 `isolated deinit` 으로 opt-in 할 것, task local 은 복사하지 말고 비울 것, `deinit async` 를 더 논의할 것(반려 #1, Jumhyn).

2023년 1월 수정 논의에서 Nickolas_Pohilets 는 첫 번째 요구는 받아들이고 `isolated deinit` 과 `@MainActor deinit` 철자를 정했다. 두 번째는 반박했다. 복사 대신 비우는 것은 조기 최적화이고, 부모 task 가 설정한 값은 믿을 수 있다는 논리였다. 로거나 에러 추적기를 task local 로 주입했다면 `deinit` 에서 다시 주입하는 것을 잊기 쉽고, 에러가 드물면 두 문제가 오래 발견되지 않는다고 했다(수정 논의 #1, Nickolas_Pohilets).

이에 John_McCall 이 길게 답했다. 마지막 release 시점에 어떤 thread 나 task 문맥이 있다고 믿는 것 자체가 매우 취약하다는 것이다. `@MainActor` 클래스는 `Sendable` 이라서 main actor 밖으로 참조가 새기 쉽고, 한 번이라도 새면 그 참조가 마지막이 될 경합이 거의 확실히 생긴다. 최적화는 그 가정으로 해도 되지만 그 가정이 깨지면 망가지는 코드를 쓰도록 권장해서는 안 된다고 했다(수정 논의 #5, John_McCall).

#### 두 번째 pitch

2023-05 의 두 번째 pitch 는 세 가지를 바꾸었다. 동기 `deinit` 의 isolation 을 `isolated` 키워드로 opt-in 하게 했고, task local 은 기본으로 복사하되 성능을 위해 `@resetTaskLocals` 속성으로 끌 수 있게 했으며, async `deinit` 을 넣었다. async `deinit` 은 마지막 release 를 한 코드와 동시에 실행된다고 했다(두 번째 pitch #1, Nickolas_Pohilets).

반응은 짧았다. mickeyl 과 Fritzt 는 환영했고, Fritzt 는 `UIView` 와 `UIViewController` 에서 파생한 클래스의 빈틈을 메우는 것이라서 특히 `isolated deinit` 이 좋다고 했다(두 번째 pitch #2, #3). tourultimate 는 동기 `deinit` 은 기본이 nonisolated 이고 async `deinit` 은 기본이 isolated 인 것이 맞느냐고 물었다(두 번째 pitch #4, tourultimate). Nickolas_Pohilets 는 그렇다고 답했다. async `deinit` 이 isolation 없는 클래스 안에 있으면 그것도 nonisolated 이고, 기본을 isolated 로 둔 이유는 사람들이 프로퍼티 하나하나를 `await` 하는 것을 막으려는 것이다(두 번째 pitch #5, Nickolas_Pohilets).

#### 서브 pitch

2024-02 의 서브 pitch 에서 Nickolas_Pohilets 는 task local 정책을 세 갈래로 정리해서 이 주제만 다시 논의하자고 했다.

1. 아무것도 안 한다. 빠른 경로에서는 보이고 느린 경로와 async deinit 에서는 안 보인다
2. 늘 보이게 한다. 빠른 경로는 그대로, 느린 경로와 async deinit 은 복사한다
3. 늘 안 보이게 한다. 빠른 경로에 stop-node 를 넣고 나머지는 그대로 둔다

비용 표도 함께 올렸다. 빠른 경로에서 값을 허용하는 쪽은 객체당 15에서 20ns 이고, 비우는 쪽은 20ns 다. 느린 경로에서 복사하지 않으면 enqueue 에 115ns, dequeue 에 140ns 가 들고, 복사하면 값당 enqueue 30에서 35ns, dequeue 20ns 가 더 든다. 그는 객체 트리를 지울 때 느린 경로는 뿌리 하나만 타고 나머지는 빠른 경로를 타니, 늘 복사하는 편이 늘 비우는 편보다 싸다고 주장했다. 그래도 기본값 선택이 다른 선택지를 막지는 않는다고 했다(서브 pitch #1, Nickolas_Pohilets).

서브 pitch 중간에는 async `deinit` 을 두고 두 가지 비판이 나왔다. 하나는 Karl 의 글이다. 그는 C++ 의 P1662(Adding async RAII support to coroutines)를 끌어왔다. 소멸자를 비동기로 만들면 타입 시스템이 둘로 갈라진다는 논문의 논지다. 비동기 소멸자를 가진 타입이 멤버로 들어가면 그 타입도 비동기 소멸자를 가져야 하고, 지역 변수나 `std::vector` 의 `resize()` 와 `pop_back()` 같은 동기 문맥에는 놓을 수 없다는 것이다. 그는 Swift 에서도 `deinit` 을 structured concurrency 로 들이면 같은 분열이 생기니 unstructured 여야 동기처럼 보일 수 있다고 정리했다. 그리고 nonisolated 와 isolated `deinit` 은 바깥에서 둘 다 동기 호출처럼 보이므로 나중에 서로 바뀌기도 쉽다고 덧붙였다(서브 pitch #27, Karl).

다른 하나는 Nickolas_Pohilets 가 task local 을 정의하지 않은 채 두는 이유를 하나 더 든 글이다. 제안은 Objective-C 상위 클래스가 `release` 를 override 해서 isolation 을 구현하게 허용하는데, 그런 구현은 task local 을 모르니 복사도 초기화도 하지 않을 것이라는 이야기다(서브 pitch #26, Nickolas_Pohilets).

이 스레드의 결말은 Jumhyn 의 글에 있다. Language Steering Group 은 보장을 안 하는 task local 설계를 두 번째 리뷰에 올리기로 결정했다(서브 pitch #24, Jumhyn).

### 두 번째 리뷰

2024년 7월의 두 번째 리뷰는 의견이 갈렸다.

먼저 task local 쪽이다. 보장하지 않는 설계에 대해 jrose 는 명시되지 않은 task local 동작은 Hyrum's Law 위반이니 왜 늘 새 task 처럼 비우지 않느냐고 물었다(두 번째 리뷰 #3, jrose). ktoso 는 LSG 결정의 배경을 설명했다. "늘 비운다" 로 하면 평범한 `deinit` 에서는 task local 이 가끔 보이는데 `isolated deinit` 에서는 안 보이는 불일치가 생긴다는 것이다. 그래서 보장하지 않는 쪽을 택했다(두 번째 리뷰 #4, ktoso). 같은 글에서 그는 실행 순서와 시점에 기대는 것은 취약하다고도 했다. 이 말은 task local 이 아니라 `deinit` 이 도는 순서와 시점에 대한 것이다(두 번째 리뷰 #6, ktoso). Nickolas_Pohilets 는 막거나 복사하는 것이 가능하니 일단 정의하지 않은 채로 두자고 했다(두 번째 리뷰 #10, Nickolas_Pohilets). 결과적으로 수락 때 이 부분이 뒤집힌 것이 위의 "늘 비운다" 이다.

이름도 한 번 흔들렸다. ksluder 는 정말 synchronous 인지 물었고, Jumhyn 과 Nickolas_Pohilets 는 "synchronous" 가 `deinit async` 를 이 제안의 범위 밖으로 둔다는 뜻일 뿐이라고 답했다(두 번째 리뷰 #8, #9). 제안서에 `GAITs` 라는 약어가 있었는데, woolsweater 가 이 약어를 풀어 쓰자고 물었고(두 번째 리뷰 #28, woolsweater) ktoso 가 그 수정의 PR #2538 을 올렸다(두 번째 리뷰 #29, ktoso). 이 글에서는 그 약어 대신 "global actor 에 isolated 된 타입" 이라고 적었다.

반대 의견은 서버 쪽에서 나왔다. johannesweiss 는 -1 이었다. 이 기능이 backpressure 없는 GC 방식의 지연 해제라서 메모리가 터질 수 있다는 것이다(두 번째 리뷰 #12, johannesweiss). FranzBusch 도 -1 이었다. 서버에서 원격 DoS 가 가능하다고 보았고, 서버 코드에서는 쓰지 말라고 권고하겠다고 했다(두 번째 리뷰 #15, FranzBusch). 서로 다른 처지라서 이 지점은 합의가 안 되었다. 그래도 johannesweiss 는 -1 이면서 문서가 필요하다는 점을 남겼고(두 번째 리뷰 #17), `deinit async` 는 가능성이 낮다고 보았다(두 번째 리뷰 #13). Fritzt 는 opt-in 이라는 점을 들어 이를 방어했다(두 번째 리뷰 #16, Fritzt).

찬성 쪽에서 grynspan 은 이 기능이 필요하다면서도 기본값이 nonisolated 인 것은 아쉽다고 했고 `deinit async` 를 설명했다(두 번째 리뷰 #18, grynspan). taylorswift 는 이 기능이 주로 컴파일러를 달래는 데 쓰이고, region 기반 isolation([SE-0414 글](https://haroldfromk.github.io/posts/SE-0414/))이 그 필요를 약화시킬 수 있다고 했다(두 번째 리뷰 #25, taylorswift). Nickolas_Pohilets 의 답은 이렇다. actor 의 `deinit` 이 돌고 있는 동안에도 그 actor 에 isolate 된 job 이 돌면서 `ClientBootstrap` 을 쓰고 있을 수 있으니 컴파일러가 맞게 막은 것이고 RBI 가 바꾸는 것은 없다. 다만 이것은 재현하는 방법을 아직 모르는 아주 드문 경우라고 했다(두 번째 리뷰 #26, Nickolas_Pohilets).

JJJ 는 별도 블록을 제안했다. `isolatedDeinitialization {}` 같은 것이다(두 번째 리뷰 #30, JJJ).

## 기대 효과

- 컴파일러가 `isolated` 를 권하는 곳에서 한 단어로 `Sendable` 이 아닌 프로퍼티와 actor 상태를 정리할 수 있다
- `Task { @MainActor [publisher, connection] in ... }` 처럼 `deinit` 에서 값을 복사해서 옮기던 boilerplate 가 줄어든다
- `NSFetchedResultsController` 처럼 `Sendable` 도 아니고 어떤 actor 에도 묶이지 않은 객체를 `@MainActor` 클래스의 `deinit` 에서 만지는 코드가 main actor 안에서 컴파일되고 실행될 수 있다
- `UIView` 와 `UIViewController` 서브클래스의 `deinit` 이 main actor 의 상태를 직접 정리할 수 있다
- 기본값이 그대로 `nonisolated` 라서 기존 코드의 동작이 바뀌지 않고, 필요한 곳만 켠다
- `deinit` 안에서 `self` 를 탈출시키는 코드를 컴파일러와 런타임이 막아서, 해제된 객체를 쓰는 사고가 줄어든다
- SE-0466 의 기본 MainActor 모드에서 `deinit` 이 왜 isolated 인지 설명할 근거가 생긴다

## 다른 선택지는 왜 안 됐나

대안은 제안서의 Alternatives considered 에서 온 것과 스레드에서 나온 것이 섞여 있다. 하나씩 이유를 본다.

#### 기본을 isolated 로 하기

처음 제안이 그랬지만 첫 리뷰에서 뒤집혔다. 많은 `@MainActor` 클래스가 필요 없는 hop 을 치르고, 기본 `deinit` 에 task local 복사 비용이 붙는다는 이유다(첫 리뷰 #10, Douglas_Gregor). 제안서가 말하는 비용 논거는 앞 장에서 숫자와 함께 보았다.

#### 모든 동기 deinit 에 isolation 전파하기

제안서의 Alternatives 에는 "isolation 을 동기 `deinit` 에 암묵적으로 전파하기" 가 있다. 서브클래스가 부모의 isolation 을 물려받는 이야기가 아니라, 클래스의 isolation 이 그 클래스의 모든 동기 `deinit` 으로 퍼지는 안이다. 기각한 이유는 셋이다. 소스를 깨는 변경이고, 비용이 크고(3.5% 의 직접 쓴 `deinit` 에 비해 대부분 합성된 `deinit` 이 release 만 하는데 그것이 isolated 가 된다), 암시적인 `deinit` 만 예외로 하면 전파 규칙이 복잡해진다는 것이다.

#### task local 을 복사하기

서브 pitch 가 비용으로 복사를 옹호했지만, 마지막 release 시점의 문맥에 기대는 코드가 취약하다는 이유로 수락 때 늘 비우는 쪽이 되었다(수정 논의 #5, John_McCall). 제안서 Alternatives 는 복사에 성능 비용이 따르는데 대부분의 사용자에게 이득이 없을 것이라고 쓰고, 정의하지 않은 채 두면 나중에 사용자 피드백으로 바꿀 여지가 남는다고 쓴다.

#### task local 을 정의하지 않기

두 번째 리뷰의 원안이다. jrose 가 Hyrum's Law 위반이라고 지적했다(두 번째 리뷰 #3, jrose). 제안서도 같은 이유를 적는다. 아무 약속을 하지 않으면 사용자가 구현 세부에 기대게 되고, 나중에 바꾸기 어려워진다는 것이다. 이 안은 수락 #1 에서 수정으로 바뀌었다(수락 #1, Jumhyn). ktoso 가 짚은 불일치(두 번째 리뷰 #4)는 "늘 비운다" 쪽의 약점이었고, 정의하지 않는 설계를 지지하는 논거로 나온 것이다.

#### swift_release() 안에서 hop 하기

release 가 일어나는 곳 자체를 바꾸는 안이다. `UIView` 와 `UIViewController` 는 `release` 를 override 해서 main 으로 옮기는 방식으로 hop 을 구현한다. 그런데 Swift 에는 release 를 위한 vtable 이나 witness table 슬롯이 없고, 슬롯을 더하면 isolated `deinit` 이 필요 없는 많은 코드에도 영향이 간다. 이 제안은 `deinit` 진입점에서 executor 를 확인하는 쪽을 택했다.

#### deinit async

제안 범위 밖이다. 직접 써 보면 이렇다.

`AsyncDeinit.swift`

```swift
actor Service {
  func shutdown() {}
}

@MainActor
final class ViewModel {
  let service = Service()
  deinit async {
    await service.shutdown()
  }
}
```

```text
AsyncDeinit.swift:8:10: error: deinitializers cannot have a name
AsyncDeinit.swift:9:19: error: call to actor-isolated instance method 'shutdown()' in a synchronous nonisolated context [#ActorIsolatedCall]
AsyncDeinit.swift:2:8: note: calls to instance method 'shutdown()' from outside of its actor context are implicitly asynchronous
AsyncDeinit.swift:9:5: error: 'await' in a function that does not support concurrency
[#ActorIsolatedCall]: <https://docs.swift.org/compiler/documentation/diagnostics/actor-isolated-call>
[exit 1]
```

`deinit async` 는 문법 오류다. 첫 오류가 "deinit 에 이름을 붙일 수 없다" 로 나오고, 이어서 `await` 가 동시성을 지원하지 않는 함수 안에 있다는 오류가 따라온다. 스레드에서 `deinit async` 를 두고 갈린 이유는 johannesweiss 의 질문에 있다. `async` 인 것은 어딘가에서 `await` 되어야 하는데, 참조가 scope 를 벗어나는 곳에는 `await` 가 없고 `async` `deinit` 이 있는 객체가 `async` 문맥에서만 scope 를 벗어난다는 보장도 없다(두 번째 리뷰 #13, johannesweiss). grynspan 은 호출한 쪽이 async 함수이고 컴파일러가 안전함을 증명할 수 있으면 암묵적인 suspension point 로, 아니면 unstructured 하되 detached 가 아닌 child task 로 만들자고 상상했다. 그게 너무 비결정적이면 async `deinit` 을 가진 값을 소비하거나 복사하는 함수는 항상 `async` 이어야 하고 동기 함수는 borrow 만 하게 하자고도 했다(두 번째 리뷰 #18, grynspan).

#### 그 밖에 안 받아들여진 것

- 소금 철자 `@unstructured isolated deinit`: 수락에서 받아들여지지 않았다(수락 #1, Jumhyn)
- 별도 블록 `isolatedDeinitialization {}`: JJJ 의 제안이고 반영되지 않았다(두 번째 리뷰 #30, JJJ)

#### Future Directions 다섯 가지

제안서가 나중으로 남긴 방향은 다섯 가지다. 이 제안에는 들어가지 않았다.

**암시적 async deinit.** 제안서는 거의 모든 인스턴스 프로퍼티를 복사해서 task 로 넘겨야 한다면, 원래 객체를 task 클로저의 문맥으로 재사용하고 `deinit` 을 비동기로 만드는 쪽이 효율적이라고 쓴다. `__deallocating_deinit` 을 unstructured task 를 시작하는 thunk 로 쓰면 되지만 이 제안의 범위는 아니다. 앞의 ViewModel 예가 `deinit async { await service.shutdown() }` 로 줄어드는 모양이다. 이 방향이 풀어야 할 문제는 johannesweiss 의 질문(두 번째 리뷰 #13)이고, 가능한 설계의 하나가 grynspan 의 구상(두 번째 리뷰 #18)이다.

**linear type.** 순차적인 async 정리는 suspension point 라서 `await` 가 필요한데, 암묵적으로 불리는 `deinit` 보다 명시적인 메서드 호출이 그 역할에 맞는다. 문제는 그 정리 메서드를 모든 경로에서 정확히 한 번 부르는 것을 컴파일러가 확인해 주지 못한다는 점이다. 이동 전용 타입은 최대 한 번을 보장하고, linear 타입은 정확히 한 번을 보장한다. 제안서의 스케치는 이렇다.

```swift
@linear // like @moveonly, but consumption is mandatory
struct Connection {
  // acts as a named explicit async deinit
  consuming func close() async {
    ...
  }
}

func communicate() async {
  let c = Connection(...)
  // error: value of linear type is not consumed
}
```

`close()` 가 이름 있는 명시적 async `deinit` 의 역할을 하고, 소비하지 않으면 오류가 난다. 서브 pitch 에서 FranzBusch 가 async `deinit` 이 필요한 곳은 `~Copyable` 타입이라고 한 것(서브 pitch #3)과 이어지는 방향이다.

**executor 접근의 devirtualization 과 inlining.** 지금은 `@MainActor deinit` 의 진입점이 `MainActor.shared.unownedExecutor` 에 접근하는 호출을 두 번 만들고, 두 번째는 동적 dispatch 까지 쓴다. 제안서는 이것을 정적으로 참조하는 `swift_task_getMainExecutor()` 호출 한 번으로 바꿀 수 있다고 쓴다.

**확장된 스택 trace.** isolated `deinit` 에 breakpoint 를 건 개발자는 마지막 release 에 이른 call stack 을 보고 싶을 것이다. executor 전환이 일어나면 지금은 release 한 쪽의 스택이 디버거에 보이지 않는다.

**동기 scheduling API.** 이 제안이 넣는 런타임 함수는 `deinit` 용에 맞춘 호출 규약이지만, 시그니처가 조금 다른 비슷한 함수로는 actor 에 임의의 일을 동기적으로 예약하는 API 를 만들 수 있다. 제안서가 보인 모양은 이렇다.

```swift
extension Actor {
  /// Adds a job to the actor queue that calls `work` passing `self` as an argument.
  nonisolated func enqueue(_ work: __owned @Sendable @escaping (isolated Self) -> Void)

  /// If actor's executor is already the current one - executes work immediately
  /// Otherwise adds a job to the actor's queue.
  nonisolated func executeOrEnqueue(_ work: __owned @Sendable @escaping (isolated Self) -> Void)
}
```

`enqueue` 는 actor 의 큐에 job 을 넣고, `executeOrEnqueue` 는 이미 그 executor 면 즉시 실행하고 아니면 큐에 넣는다. 지금까지 본 `swift_task_deinitOnExecutor` 의 인라인 또는 job 예약 경로를 일반 API 로 내놓은 것이다.

## Swift 6 모드와 마이그레이션

새 철자가 하나 생기는 변화라서 기존 코드가 깨질 일은 적다. 그래도 언어 모드마다 진단이 달라지는 곳, 런타임 ABI, 공개 API 의 호환, 옮기는 순서를 나눠서 본다.

---

### 소스 호환

새 철자 `isolated deinit` 이 생기는 것이라서 이전에 안 되던 코드가 된다. 기존 `deinit` 은 그대로 `nonisolated` 다. 이미 `@MainActor` 클래스에서 `deinit` 을 `assumeIsolated` 나 Task 로 우회해 둔 코드는 그대로 돈다.

---

### 언어 모드

`deinit` 의 `self` 탈출은 언어 모드에 따라 진단이 달라진다. Motivation 과 Escape 를 세 가지 모드로 컴파일했다.

| 코드 | Swift 5 | Swift 5 + complete 검사 | Swift 6 |
|---|---|---|---|
| Motivation (nonisolated deinit 에서 `friend` 접근) | 진단 없음 | 경고, 끝에 "this is an error in the Swift 6 language mode" | 오류 |
| Escape (클로저가 `self` 를 캡처) | 경고, 끝에 "this is an error in the Swift 6 language mode" | 같은 경고 | 오류 |

Swift 5 모드에서 `deinit` 의 접근은 조용히 통과하고, complete 검사를 켜면 경고로 알려 주고, 6 모드에서 오류가 된다. 이 경고는 6 로 올릴 때 어디가 막히는지를 미리 보여 준다.

---

### ABI 와 back deployment

새 런타임 함수 `swift_task_deinitOnExecutor` 가 생긴다. SIL 에서 이 함수 선언은 `[available 15.4]` 로 표시되어 있고, 구현은 Swift 6.2 에 들어갔다. 배포 대상을 낮추면 어떻게 되는지 `-target arm64-apple-macosx14.0` 으로 쟀다. 먼저 `@MainActor` 클래스다.

`BD.swift`

```swift
@MainActor final class A { isolated deinit { print("d") } }
@main struct P { static func main() async { _ = await A() } }
```

```text
BD.swift:2:49: warning: no 'async' operations occur within 'await' expression [#UnnecessaryEffectMarker]
[exit 0]
```

경고 하나만 나오고 컴파일이 된다. 경고는 `await A()` 의 `await` 에 대한 것이라 `isolated deinit` 과 무관하다. 오브젝트 파일의 심볼을 `nm` 으로 보면 `_swift_task_deinitOnExecutorMainActorBackDeploy` 가 `T`, 즉 이 파일 안에 정의되어 있고, `_swift_task_deinitOnExecutor` 는 `U`, 즉 정의되지 않은 외부 심볼이다. `@MainActor` 클래스의 오브젝트 파일에는 back deployment 용 구현이 들어가 있다.

global actor 를 직접 만든 클래스와 actor 는 같은 타깃에서 오류가 난다.

`BD2.swift`

```swift
@globalActor actor G { static let shared = G() }
@G final class B { isolated deinit { print("b") } }
actor C { var x = 0; isolated deinit { print("c", x) } }
```

```text
BD2.swift:2:20: error: isolated deinit is only available in macOS 15.4.0 or newer
BD2.swift:2:16: note: add '@available' attribute to enclosing class
BD2.swift:3:22: error: isolated deinit is only available in macOS 15.4.0 or newer
BD2.swift:3:7: note: add '@available' attribute to enclosing actor
[exit 1]
```

note 가 권하는 것은 `@available` 을 클래스나 actor 에 다는 것이다. 정리하면 15.4 보다 낮은 배포 대상에서 `@MainActor` 의 `isolated deinit` 은 컴파일되고, 다른 global actor 와 actor 는 availability 를 요구한다.

---

### API 와 라이브러리

공개 클래스의 `deinit` isolation 을 바꾸는 것은 API 변화다. 제안서는 이렇게 정리한다.

| 변경 | open @objc | open non-@objc | non-open |
|---|---|---|---|
| isolation 제거 | breaking | 가능 | 가능 |
| isolation 추가 | breaking | breaking | 가능 |
| actor 변경 | breaking | breaking | 가능 |

`open` 이면서 `@objc` 인 클래스는 어느 쪽으로 바꿔도 breaking 이다. isolation 을 제거하면 `__isolated_deallocating_deinit` 심볼이 사라져서 클라이언트의 링크가 실패하기 때문이다. Objective-C 클래스에서 `dealloc` 의 isolation 표시를 retain 과 release 의 override 와 함께 없애는 것도 breaking 이다. 제안서는 기존 서브클래스가 isolated 로 타입 검사를 받았지만 thunk 없이 컴파일되어 있어서, 없앤 뒤에는 `deinit` 이 엉뚱한 executor 에서 불릴 수 있다고 쓴다.

반대로 Objective-C `dealloc` 에 isolation 을 다는 것도 breaking 이다. 이미 있는 서브클래스가 다른 actor 에 isolate 한 `deinit` 을 가졌다면, 다시 컴파일하지 않은 바이너리는 그 actor 에서 `[super dealloc]` 을 부르고 있고, 다시 컴파일하면 컴파일 오류가 난다. nonisolated `deinit` 이나 같은 actor 에 isolate 한 `deinit` 을 가진 서브클래스는 ABI 호환이 유지된다. 제안서는 지금은 UIKit 클래스의 서브클래스가 모두 nonisolated `deinit` 이라서 UIKit 이 표시를 달 수 있다고 덧붙인다.

실제 `.swiftinterface` 를 뽑아 보았다.

`Lib.swift`

```swift
@MainActor
open class Screen {
  public init() {}
  isolated deinit {}
}

public actor Store {
  isolated deinit {}
}
```

```bash
xcrun swiftc -emit-module -module-name Lib -swift-version 6 -enable-library-evolution -emit-module-interface-path Lib.swiftinterface Lib.swift -parse-as-library
```

`Lib.swiftinterface` (일부)

```text
// swift-interface-format-version: 1.0
// swift-compiler-version: Apple Swift version 6.4 (swiftlang-6.4.0.34.1 clang-2100.3.34.1)
// swift-module-flags: -target arm64-apple-macosx27.0.0 -enable-objc-interop -enable-library-evolution -language-mode 6 -module-name Lib
@_Concurrency::MainActor open class Screen {
  @_Concurrency::MainActor public init()
  @objc isolated deinit
}
@_hasMissingDesignatedInitializers public actor Store {
  @objc isolated deinit
  ...
}
extension Lib::Screen : Swift::Sendable {}
```

`isolated deinit` 이 그대로 interface 에 실리고 `open class Screen` 도 `open` 이 유지된다. `#if compiler` 같은 가드는 없다. `@objc` 는 `.swiftinterface` 가 `deinit` 에 늘 붙이는 표시다.

---

### 옮기는 방법

- 평범한 `deinit` 에서 isolated 상태를 만지는 코드는 `isolated deinit` 으로 바꾼다. 컴파일러 note 가 이 철자를 그대로 권한다
- `Task { ... }` 로 값을 복사해서 옮기던 코드는 `isolated deinit` 안에서 바로 쓰도록 바꾼다. 다만 `deinit` 이 나중에 돈다는 점은 감수해야 한다
- 파일 핸들처럼 시점이 중요한 자원에는 쓰지 않는다. 제안서 Motivation 의 주의다. `isolated deinit` 은 시점이 불확정이므로, with 형태의 API, 명시적인 `close()`, `~Copyable` 타입으로 해제를 직접 제어하는 편이 맞다

#### 우회를 isolated deinit 으로 바꾸기

UIKit 장에서 재 본 `assumeIsolated` 우회가 바꾸기 전이다. `Assume.swift` 의 `Screen` 은 배경에서 마지막 release 가 일어나면 `assumeIsolated` 가 `dispatch_assert_queue` 에서 멈추고, 실행 파일은 종료 코드 133 으로 끝난다.

```text
$ ./assume
(exit 133)
```

같은 `Screen` 에서 `deinit` 을 `isolated deinit` 으로 바꾸고 `assumeIsolated` 를 걷어낸다.

`MigrateAfter.swift` (일부)

```swift
@MainActor
final class Screen {
  let counter = Counter()
  nonisolated init() {}
  isolated deinit {
    counter.value += 1
    print("  deinit on", here(), "value:", counter.value)
  }
}
```

진단은 `[exit 0]` 이고, 같은 방식으로 배경 task 에서 놓은 실행 결과는 이렇다.

```text
$ ./migrate
  released on background
  deinit on main value: 1
done
```

release 는 배경에서 끝나고 `deinit` 은 main 에서 돌아 `counter.value` 가 올라갔다. 죽던 코드가 도는 코드가 되었다. 바꾸면서 잃는 것은 시점이다. 우회 코드에서는 `deinit` 이 release 한 그 자리에서 돌았지만, 바꾼 뒤에는 `released on background` 뒤에 main 에서 돈다. 이 차이가 괜찮은 자원인지가 바꾸는 기준이다.

---

## 정리

- actor 와 global actor 에 묶인 클래스의 `deinit` 앞에 `isolated` 를 적으면 그 isolation 에서 `deinit` 이 돈다. 철자는 `isolated deinit`, `@MainActor deinit`, 효과 없는 `nonisolated deinit` 이다. 기본값은 지금까지처럼 `nonisolated` 다
- isolation 이 없는 클래스의 `isolated deinit` 은 오류다. 서브클래스는 `deinit` 에 isolation 을 더할 수는 있지만 빼거나 바꿀 수는 없고, 검사는 `super.deinit()` 을 부를 수 있는지로 한다. 쓰지 않은 `deinit` 은 부모의 isolation 을 물려받는다
- 런타임은 `__deallocating_deinit` 에서 `swift_task_deinitOnExecutor` 를 불러 executor 를 확인한다. 이미 맞으면 인라인으로, 아니면 task 없는 job 을 예약하고 release 한 쪽은 기다리지 않는다. default actor 는 lock 을 잡을 수 있으면 인라인이다
- task local 은 `isolated deinit` 에 들어갈 때 인라인이든 나중이든 늘 비워진다. `deinit` 안의 `withValue` 는 그 범위 안에서 보인다. 평범한 `deinit` 은 release 한 task 의 값이 보인다
- `deinit` 안의 클로저 캡처로 `self` 가 밖으로 나가면 Swift 6 에서 컴파일 오류, 5 모드에서 경고다. 컴파일러가 못 보는 탈출은 `isolated` 가 아닌 `deinit` 에서도 런타임에서 종료 코드 134 로 죽는다
- Objective-C `dealloc` 에 `@MainActor` 를 단 클래스의 서브클래스는 타입 검사에서는 isolated 이지만 executor 를 옮겨 주는 thunk 가 없다. `release` 를 override 하지 않은 상태에서 배경에서 놓으면 `_checkExpectedExecutor` 가 죽는다. 표시가 없는 SDK 클래스의 서브클래스는 `swift_task_deinitOnExecutor` 로 스스로 옮긴다
- SE-0466 의 기본 MainActor 모드에서 쓰지 않은 `deinit` 은 isolated 가 되고, 직접 쓴 평범한 `deinit` 과 `nonisolated deinit` 은 `nonisolated` 로 남는다
- 시점이 불확정이라서 파일 핸들 같은 자원에는 쓰지 않는다. 포럼에서는 서버 쪽에서 DoS 와 메모리 압박 우려가 나왔고, 수락 공지는 opt-in 이라서 신중한 코드베이스는 lint 로 막을 수 있다고 정리했다
- `deinit async` 는 문법 오류이고 Future Directions 에 남았다. 공개 API 의 `deinit` isolation 을 바꾸는 것은 breaking 이다. macOS 14 같은 낮은 배포 대상에서 `@MainActor` 클래스는 컴파일되고, 다른 global actor 와 actor 는 `@available` 을 요구한다
