## 한 줄 요약

`@preconcurrency` 하나로 두 가지 문제를 푼다. 라이브러리는 기존 선언에 동시성 annotation 을 붙여도 기존 사용자의 소스와 ABI 를 깨지 않고, 앱은 아직 annotation 이 없는 모듈을 import 하면서도 자기 코드부터 strict checking 을 켤 수 있다. 제안서는 여기에 "모듈마다 하나씩 옮겨 가는" 단계적 마이그레이션 흐름까지 정의한다.

## 어떤 문제였나

Swift 5.5 는 data race 를 언어 차원에서 없애려고 `Sendable` 과 `@MainActor` 를 도입했다. 그런데 완전히 강제하지는 않았다. 강제하면 아직 동시성을 모르는 모듈과 함께 쓰기가 너무 힘들었기 때문이다. 제안서의 Introduction 이 바로 이 이야기로 시작한다. 검사를 느슨하게 둔 채로는 data race 를 막을 수 없고, 엄격하게 하면 생태계 전체가 한꺼번에 움직여야 한다. 이 제안서는 그 사이를 이을 도구를 만든다.

문제는 두 방향에서 온다. 하나는 라이브러리를 만드는 쪽이 이미 배포한 API 에 뒤늦게 동시성 정보를 붙이려는 경우이고, 다른 하나는 앱을 만드는 쪽이 자기 코드는 준비되었는데 import 한 모듈이 아직 준비되지 않은 경우다. 먼저 이 글에서 계속 나올 개념 몇 가지를 정리한다.

---

### Sendable 이란?

data race 는 두 곳의 코드가 같은 메모리를 동시에 건드리는데, 그중 하나 이상이 값을 쓰고 있고 순서를 정해 주는 장치가 없는 상황이다. 결과가 실행할 때마다 달라지고 재현도 어렵다.

[`Sendable`](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 은 "이 타입의 값은 task 나 actor 의 경계를 넘겨도 안전하다" 는 표시다. 비유하면 회의에서 나눠 주는 인쇄물과 벽에 걸린 공용 화이트보드의 차이다. 인쇄물은 사람마다 복사본을 들고 있으니 각자 낙서해도 서로 영향이 없다. `Int` 나 값만 담은 `struct` 가 이쪽이다. 화이트보드는 하나뿐인 것을 여럿이 함께 쓰므로, 두 사람이 동시에 지우고 쓰면 엉망이 된다. 내용을 바꿀 수 있는 `class` 인스턴스가 이쪽이다. Sendable 인 타입만 경계를 넘겨 주고받게 하면, 화이트보드를 아무 경고 없이 여러 곳에 넘기는 일을 컴파일러가 막아 준다.

제안서가 말하는 "Sendable checking" 은 이 검사를 뜻한다. 경계를 넘기는 API 는 입력이 Sendable 이어야 한다고 요구하고, 컴파일러는 값의 타입이 정말 Sendable 인지 확인한다. 그래서 모듈 A 가 모듈 B 의 타입을 경계 너머로 보내려면, B 의 타입이 Sendable 인지 아닌지를 A 의 컴파일러가 알 수 있어야 한다. B 가 동시성 이전에 만들어졌다면 그 정보가 없다.

---

### actor isolation 과 global actor 란?

actor 는 자기 안의 상태를 한 번에 한 코드만 만지게 해 주는 타입이다. 은행 창구에 번호표를 뽑고 한 명씩 들어가는 것과 같다. 이렇게 상태를 보호받는 것을 actor isolation 이라고 한다.

actor 의 상태에 바깥에서 닿으려면 순서를 기다려야 해서 `await` 가 필요하다. 여기서 task 는 동시에 실행될 수 있는 작업 한 단위이고, `async` 함수는 실행 도중에 멈췄다가 이어질 수 있는 함수이며, `await` 는 그렇게 멈출 수 있는 지점을 표시한다. actor 밖에서 `await` 로 actor 안의 값을 읽으면, 그 값은 actor 의 경계를 넘어 밖으로 나온다. 값이 actor 나 task 의 경계를 넘는 바로 그 순간이 Sendable 검사가 일어나는 자리다. 뒤에 나오는 `await canvas.origin` 이 이 경우이고, 꺼내 온 값이 Sendable 이 아니면 컴파일러가 막는다.

global actor 는 프로그램 전체에 하나뿐인 actor 를 이름으로 가리키는 장치다. 대표가 `@MainActor` 이고 main thread 위의 작업에 대응한다. UIKit 의 화면 관련 메서드가 "main thread 에서만 불러라" 라고 문서에 적어 두었던 규칙을, `@MainActor` 가 붙으면 컴파일러가 검사할 수 있다. `@MainActor` 가 붙은 함수는 main actor 위에서 실행되는 코드가 바로 부를 수 있다. 그 밖에서는 `await` 를 붙여 main actor 로 넘어가서 불러야 하는데, 동기 함수는 `await` 를 쓸 수 없으므로 부를 수 없다. 그래서 동기 함수가 `@MainActor` 함수를 부르려면, 그 호출이 main actor 위에서 일어난다는 것을 컴파일러가 알 수 있어야 한다.

---

### Swift 언어 모드란?

컴파일러 버전과 언어 모드는 다른 개념이다. Swift 6.4 컴파일러는 `-swift-version 5` 로 Swift 5 언어 모드를, `-swift-version 6` 으로 Swift 6 언어 모드를 고를 수 있고, 같은 컴파일러가 모드에 따라 같은 코드에 다른 규칙을 적용한다. 컴파일러를 새 버전으로 올려도 언어 모드를 그대로 두면 옛 규칙으로 컴파일되므로, 컴파일러 업데이트와 소스 호환성 문제를 떼어 놓는 장치다. 이 글에서 "Swift 5 모드" 와 "Swift 6 모드" 는 이 언어 모드를 가리킨다.

동시성 검사에서 Swift 5 모드의 기본값은 minimal checking 이다. Sendable 위반은 대부분 진단하지 않고, 동시성 annotation 을 어긴 호출 중 actor isolation 위반만 error 로 낸다. Swift 6 모드에서는 모든 코드를 완전히 검사하고 위반을 error 로 낸다. 그 중간 단계는 뒤의 concurrency checking mode 절에서 다룬다.

### 라이브러리가 annotation 을 붙이면 깨지는 것

제안서의 Motivation 첫 번째 주제다. UIKit 같은 라이브러리의 많은 메서드는 늘 main thread 에서만 쓰도록 되어 있었지만, 그 사실을 컴파일러에게 말할 방법이 없었다. 이제 `@MainActor` 가 있으니 라이브러리는 이 사실을 선언에 적고 싶다. 그런데 그렇게 하면 이 사실을 아직 모르는 기존 사용자 코드가, 올바르게 쓰고 있는데도 컴파일 error 를 맞는다.

제안서의 예를 그대로 돌려 봤다. 라이브러리 쪽 코드는 `LibA.swift` 다. Swift 6 모드로 빌드했고 `@preconcurrency` 는 붙이지 않았다. 뒤에서 `@preconcurrency` 를 붙인 `LibB.swift` 와 비교하려고 A, B 로 나눠 불렀다.

```swift
@MainActor
public func doSomethingThenFollowUp(_ body: @escaping @Sendable () -> Void) {
    Task.detached {
        body()
    }
}
```

제안서 원문 코드에는 `@escaping` 이 없다. 여기서는 `Task.detached` 안에서 `body` 를 부르려면 closure 가 함수보다 오래 살아남는(escaping) 것이어야 해서 `@escaping` 을 추가했다.

#### Task.detached로 다른 task 에서 closure 실행하기

[`Task.detached(name:priority:operation:)`](https://developer.apple.com/documentation/swift/task/detached%28name:priority:operation:%29-795w1){:target="_blank"} 는 지금 있는 actor 나 task 와 무관한 새 task 를 만들어 `operation` closure 를 실행한다. 호출한 쪽의 actor isolation 을 물려받지 않는다는 점이 `Task { }` 와 다르다. 이 예에서는 main actor 에서 불린 함수가 "다른 일을 한 다음 사용자가 넘긴 `body` 를 별도 task 에서 부르는" 흐름을 만드는 데 썼다. closure 가 다른 task 로 넘어가므로 `body` 는 `@Sendable` 이어야 한다. [`@Sendable`](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} 은 "이 closure 가 캡처하는 값이 경계를 넘겨도 안전해야 한다" 는 표시이고, `@MainActor` 는 앞에서 설명한 대로 main actor 위의 코드가 바로 부를 수 있고, 그 밖의 동기 코드는 부를 수 없다는 뜻이다. Swift 의 attribute 목록은 같은 문서에 모여 있다.

사용하는 쪽은 `Button.swift` 다. 라이브러리가 이 annotation 을 갖기 전부터 이렇게 쓰던 코드다.

```swift
import Lib

class MyButton {
    var clickedCount = 0

    func onClicked() { // 시스템이 항상 main thread 에서 부른다
        doSomethingThenFollowUp {
            self.clickedCount += 1
        }
    }
}
```

제안서 원문은 `clickedCount += 1` 이지만 클래스의 escaping closure 안에서 프로퍼티를 쓸 때는 `self.` 를 명시해야 해서 붙였다. 이것은 언어 모드와 상관없이 필요하고 Swift 5 모드에서도 빠지면 error 다.

Swift 5 모드는 기본값이 minimal checking 이라서 (앞의 Swift 언어 모드란? 절 참고) Sendable 위반은 대부분 진단하지 않는다. 그래도 error 가 하나 나온다.

```text
error: call to main actor-isolated global function 'doSomethingThenFollowUp' in a synchronous nonisolated context [#ActorIsolatedCall]
```

이 error 는 Sendable 검사가 아니라 actor isolation 검사에서 나온다. `@MainActor` 함수를 동기이면서 어느 actor 에도 속하지 않은 (nonisolated) 문맥에서 부르는 것은 Swift 5.5 부터 error 였고, minimal 이라고 숨겨지지 않는다. 반면 Sendable closure 캡처 진단은 Swift 5 모드에서는 나오지 않았다. Swift 6 모드에서는 그 진단이 하나 더 붙는다.

```text
error: capture of 'self' with non-Sendable type 'MyButton' in a '@Sendable' closure [#SendableClosureCaptures]
```

요점은 이 코드가 틀리지 않았다는 것이다. `onClicked` 는 예전부터 main thread 에서만 불렸고, 그래서 `doSomethingThenFollowUp` 을 부르는 것도 안전했다. 다만 "main actor 에서 불린다" 는 사실을 컴파일러에게 증명할 annotation 이 `onClicked` 에 없고, `MyButton` 이 Sendable 이라는 선언도 없다. 라이브러리가 올바른 정보를 더했을 뿐인데 사용자의 올바른 코드가 소스 호환성을 잃는다. 제안서가 말하는 source break 이다.

### name mangling 과 ABI 란?

source break 는 다시 컴파일하면 고칠 수 있다. 문제는 이미 컴파일된 바이너리까지 깨지는 ABI break 다. 이를 이해하려면 컴파일된 바이너리가 함수를 어떻게 찾는지 알아야 한다. 컴파일된 바이너리 안에서 함수는 이름으로 찾는다. 그런데 Swift 는 같은 이름의 함수를 인자 타입으로 구분하므로, 컴파일러는 `doSomethingThenFollowUp` 이라는 이름에 모듈 이름과 인자 타입 정보를 덧붙여 하나의 긴 문자열로 만든다. 이것이 name mangling 이다. 편지 주소에 번지수와 동 이름을 빠짐없이 적는 것과 같다. 주소가 하나라도 달라지면 우편물이 도착하지 않는다.

ABI 는 이미 컴파일된 코드끼리 서로를 호출하기 위해 지켜야 하는 약속(이름, 인자를 넘기는 방식, 메모리 배치 같은 것)이다. 라이브러리를 새 버전으로 바꿨는데 예전에 컴파일된 앱이 그대로 돌아간다면 ABI 가 유지된 것이다.

문제는 `@Sendable` 과 `Sendable` 제약이 mangled name 에 들어간다는 점이다. 제안서에 따르면 Sendable 은 호출 규약 (calling convention, 인자와 반환값을 어디에 어떻게 넘기는지에 대한 약속) 에는 아무 영향이 없는데도 (타입별 동작 목록인 witness table 을 추가 인자로 넘기지 않는다) 이름에는 영향을 준다. 직접 컴파일해서 `nm` 으로 심볼을 뽑고 `swift demangle` 로 읽어 봤다. `nm` 은 바이너리에 든 심볼 이름을 뽑아 주는 도구이고, `swift demangle` 은 mangling 된 이름을 사람이 읽는 모양으로 되돌린다.

`@preconcurrency` 가 없는 `LibA` 일 때:

```text
$s3Lib23doSomethingThenFollowUpyyyyYbcF -> Lib.doSomethingThenFollowUp(@Sendable () -> ()) -> ()
```

`@preconcurrency` 를 붙인 `LibB` 일 때:

```text
$s3Lib23doSomethingThenFollowUpyyyycF -> Lib.doSomethingThenFollowUp(() -> ()) -> ()
```

두 이름의 차이는 `Yb` 두 글자이고, 그것이 `@Sendable` 표시다. `@MainActor` 는 이름에 들어가지 않는다. 같은 함수를 annotation 없이 컴파일한 것, `@MainActor` 만 붙인 것, `LibB` 의 이름이 모두 `$s3Lib23doSomethingThenFollowUpyyyycF` 로 같았다. 선언의 `@MainActor` 는 이름에 안 들어가고 이름을 바꾸는 것은 `@Sendable` (`Yb`) 뿐이다. 라이브러리가 `@Sendable` 을 붙이는 순간 심볼 이름이 바뀌니, 예전 이름으로 링크된 바이너리는 함수를 찾지 못한다. 그래서 필요한 것은 "검사는 새 규칙으로 하되, 코드를 만들 때는 이 annotation 이 없는 것처럼 이름을 짓는" 장치다. 제안서가 이 요구를 이렇게 적는다. 타입 검사 단계에서는 제약을 강제하되, 코드 생성 단계에서는 제약이 없는 것처럼 만들어야 한다.

### 내 코드가 먼저 준비된 경우

반대 방향의 문제다. 이번에는 내가 앱을 만드는 쪽이다. 내 코드에 actor 와 async 를 쓰면서 strict checking 을 켰는데, import 한 모듈은 아직 아무 annotation 이 없다.

Geometry 라는 모듈 (`Geometry.swift`) 이 있고 Swift 5 모드로 빌드한 상태다.

```swift
public class Point {
    public var x = 0
    public var y = 0
    public init() {}
}
```

내 앱 코드 `Client1.swift` 는 Swift 6 모드이고, Geometry 의 `Point` 를 actor 안에 두고 밖에서 읽거나 `@Sendable` closure 로 캡처한다.

```swift
import Geometry

actor Canvas {
    var origin = Point()
}

func read(_ canvas: Canvas) async {
    let p = await canvas.origin
    print(p.x)
}

func capture() {
    let p = Point()
    let work: @Sendable () -> Void = {
        print(p.x)
    }
    work()
}
```

`await canvas.origin` 은 actor 안에 있는 `Point` 를 밖으로 꺼내는 호출이다. 값이 actor 의 경계를 넘어 나오므로 `Point` 가 Sendable 이어야 하는데 아니라서 첫 error 가 난다. `capture()` 는 `@Sendable` closure 가 다른 task 로 넘어갈 수 있기 때문에 같은 이유로 캡처한 `p` 를 검사한다.

Swift 6 모드에서 나온 진단이다.

```text
error: non-Sendable type 'Point' of property 'origin' cannot exit actor-isolated context [#NonSendableExitingActor]
note: class 'Point' does not conform to the 'Sendable' protocol
warning: add '@preconcurrency' to treat 'Sendable'-related errors from module 'Geometry' as warnings [#AddPreconcurrencyImport]
error: capture of 'p' with non-Sendable type 'Point' in a '@Sendable' closure [#SendableClosureCaptures]
```

세 번째 줄 warning 은 `import Geometry` 줄에 붙는다. fix-it (컴파일러가 진단과 함께 내미는 자동 수정안) 이 `@preconcurrency import` 를 제안하는 것이다. 이 장면이 제안서가 설계한 흐름의 출발점이다.

제안서의 Motivation 은 여기서 더 어려운 질문을 던진다. 내가 `Point` 를 보고 "이건 아마 Sendable 일 것" 이라고 판단해 진단을 끄고 지나갔다고 하자. 시간이 지나 Geometry 의 관리자가 구현을 살펴보고 "아니다, 보내면 안 된다" 고 확정했다. 내가 새 버전으로 빌드하면 어떻게 되어야 할까.

진단을 계속 숨기는 것은 옳지 않다. 관리자의 확정이 내 추측보다 정확하기 때문이다. 반대로 빌드를 막는 것도 곤란하다. Geometry 의 새 버전이 내 코드에 버그를 넣은 게 아니라, 원래 있던 버그를 드러냈을 뿐이다. 어제 빌드되던 프로젝트가 업데이트 하나로 깨지면 사용자들은 업데이트를 미루고 관리자를 압박하게 되어 생태계의 진행이 느려진다. 제안서의 결론은 warning 이다. 버그는 알려 주고 빌드는 막지 않는다. 숨겨진 버그보다 진단된 버그가 낫다는 것이다. 이 논리가 이후 모든 규칙의 바탕에 있다.

## 무엇이 바뀌나

제안서는 기능 하나가 아니라 여러 기능이 함께 움직여 만드는 마이그레이션 흐름을 먼저 정의한다. 5단계로 요약되며, 이 흐름이 제안서의 뼈대다.

---

### 마이그레이션 다섯 단계

![내 모듈은 처음부터 끝까지 strict checking 을 켜 두고, 다른 모듈 문제는 @preconcurrency import 로 잠시 가뒀다가, 그 모듈이 준비되면 숨은 버그가 warning 으로 나오고, 다 고치면 import 의 표시를 지운다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2022-03-14-SE-0337/se-0337-migration-steps.png)

1. 동시성 checking 을 켠다. 제안서는 Swift 6 모드로 바꾸거나 `-warn-concurrency` 플래그를 주거나 async/await 나 actor 를 쓰기 시작하면 된다고 쓴다. 동시성 규칙 위반이 error 나 warning 으로 나타난다. (6.4 의 Swift 5 모드 기본값은 async/await 나 actor 를 써도 이것이 켜지지 않는다. 뒤의 checking mode 절에서 본다.)
2. 문제를 풀기 시작한다. 다른 모듈의 타입 때문이라면 fix-it 이 `@preconcurrency import` 를 제안한다. 이 import 가 문제를 침묵시키거나 warning 으로 낮춘다.
3. 내 모듈에서 풀 수 있는 문제를 풀었으면 더 큰 빌드에 통합한다.
4. 언젠가 그 모듈이 `Sendable` 같은 annotation 을 붙인 새 버전을 낸다. 내 코드가 새 제약을 어기고 있으면 warning 이 뜬다. 이것이 내 코드에 있던 잠재 data race 이니 고친다.
5. 다 고쳤거나 고칠 게 없으면, 제안서의 설계로는 `@preconcurrency import` 가 불필요하다는 warning 이 뜬다 (6.4 에서는 나오지 않았다. 뒤에서 본다). 속성을 지운다. 그 뒤로 그 모듈 때문에 생기는 Sendable 검사 실패는 `@preconcurrency import` 를 제안하지 않고, Swift 6 모드에서는 빌드를 막는 error 가 된다.

그림에서 회색 선은 내 모듈이 처음부터 끝까지 strict checking 상태에 있다는 뜻이다 (Swift 6 모드나 `complete` 를 가정한다). 청록색 구간은 `@preconcurrency import` 라는 임시 표시가 붙어 있는 기간이다. 경계는 내 코드가 아니라 다른 모듈에 있다. 그 모듈이 따라올 때까지 경계에서만 기다리고, 내 코드는 앞서 간다. 그림의 5단계에 있는 warning 은 제안서의 설계이고 6.4 에서는 나오지 않았다.

이 흐름을 받치는 장치는 세 가지다. Swift 6 모드에서는 모든 코드를 Sendable 과 동시성 위반에 대해 완전히 검사하고, `@preconcurrency` 가 낮추지 않은 위반은 error 로 낸다. 옛 언어 모드에서는 `-warn-concurrency` 가 같은 위반을 warning 으로 낸다. 선언에 붙는 `@preconcurrency` 는 "이 선언은 동시성 이전부터 있었다" 는 표시이고, import 에 붙는 `@preconcurrency` 는 "이 모듈의 아직 준비 안 된 타입 때문에 생기는 Sendable 진단은 가볍게 다뤄라" 는 표시다. 이어지는 절에서 하나씩 본다.

---

### 복구 동작

제안서는 먼저 "진단을 warning 으로 낮추거나 숨긴다" 는 말이 컴파일러에게 구체적으로 무슨 뜻인지를 정한다. 그런 경우 컴파일러는 아래처럼 행동한다고 가정하고 계속 타입 검사를 진행한다 (우선순위 순서).

- Sendable 을 따르지 않는 nominal 타입 (`struct`, `class`, `enum`, `actor` 처럼 이름을 붙여 선언한 타입) 이 따르는 것처럼 취급한다.
- `@Sendable` 이나 global actor 가 붙은 함수 타입이 그것이 없는 것처럼 취급한다.

error 를 그냥 "무시" 하는 것이 아니라, 그 error 를 만든 요구 자체를 없는 것으로 치고 나머지 코드를 검사한다. 이래야 error 하나가 연쇄적으로 다른 error 를 만들지 않는다.

뒤의 선언 절에서 쓸 `LibB` (`@preconcurrency` 를 붙인 라이브러리) 로 앞의 `Button.swift` 를 Swift 6 모드에서 컴파일하면 이 동작이 그대로 보인다. 진단은 `#ActorIsolatedCall` 과 `#SendableClosureCaptures` 두 개의 warning 뿐이었고, 그 두 요구를 없는 것으로 치고 검사를 이어 간 덕분에 다른 진단이 연달아 붙지 않았다.

---

### concurrency checking mode 란?

컴파일러는 코드의 영역(scope)마다 두 가지 checking mode 중 하나를 적용한다.

- Strict: Sendable 이나 global actor annotation 이 빠진 것을 진단한다. Swift 6 에서 `@preconcurrency` 없이 쓰면 대개 error 이고, Swift 5 모드이거나 `@preconcurrency` 가 관여하면 warning 이다.
- Minimal: 같은 진단을 warning 으로만 낸다. 선언에 붙은 `@preconcurrency` 가 이 모드에서는 많은 진단을 아예 숨긴다.

최상위 scope 의 모드는 이렇게 정해진다. Swift 6 모드이거나, 이전 언어 모드에서 `-warn-concurrency` 를 줬거나, 파싱 중인 파일이 module interface (`.swiftinterface`, 모듈의 공개 API 를 소스 모양으로 적은 파일) 이면 Strict 이고, 나머지는 Minimal 이다.

하위 scope 는 부모가 Minimal 일 때 아래 중 하나에 해당하면 Strict 가 된다. 아니면 부모를 따른다.

- global actor attribute 를 명시한 closure
- 타입이 `async` 이거나 `@Sendable` 인 closure 나 autoclosure (`@autoclosure` 로 인자 표현식이 자동으로 감싸진 closure)
- `nonisolated` (어느 actor 에도 묶이지 않았다는 표시이고, 자세한 이야기는 [(Deep Dive) nonisolated는 왜 필요한가](https://haroldfromk.github.io/posts/%28Deep-Dive%29-nonisolated%EB%8A%94-%EC%99%9C-%ED%95%84%EC%9A%94%ED%95%9C%EA%B0%80/) 에 있다) 나 global actor attribute 를 명시한 선언
- `async` 나 `@Sendable` 로 표시된 함수, 메서드, initializer, accessor, 변수, subscript
- `actor` 선언

Minimal 인 부모 안에서도 동시성을 쓴 부분은 따로 엄격해진다는 이야기다. 동시성을 쓰지 않는 옛 코드는 기존처럼 두고, 동시성을 쓴 곳만 엄격하게 본다. 한편 C 에서 가져온 선언은 항상 Minimal scope 에 속한다.

지금 컴파일러에서는 이 모드가 `-strict-concurrency=minimal|targeted|complete` 옵션으로 나뉘어 있다. 이 이름들이 제안서의 용어와 어떻게 이어지는지 `Client1.swift` (앞의 Geometry 예) 로 실험했다.

- Swift 5 모드 기본값 (minimal) 에서는 진단이 하나도 나오지 않는다. async 함수 `read` 안에서도 마찬가지다.
- `-swift-version 5 -strict-concurrency=targeted` 에서는 async 함수 `read` 안의 `canvas.origin` 진단이 warning 으로 나오고, `import Geometry` 줄에는 `@preconcurrency` 를 권하는 warning 이 붙는다. 동기 함수 `capture()` 의 `@Sendable` closure 캡처 진단은 나오지 않는다.
- `-strict-concurrency=complete` 에서는 둘 다 나온다.

targeted 결과는 아래와 같다.

```text
warning: non-Sendable type 'Point' of property 'origin' cannot exit actor-isolated context; this is an error in the Swift 6 language mode
warning: add '@preconcurrency' to suppress 'Sendable'-related warnings from module 'Geometry'
```

complete 결과는 아래와 같다.

```text
warning: non-Sendable type 'Point' of property 'origin' cannot exit actor-isolated context; this is an error in the Swift 6 language mode
warning: capture of 'p' with non-Sendable type 'Point' in a '@Sendable' closure; this is an error in the Swift 6 language mode
warning: add '@preconcurrency' to suppress 'Sendable'-related warnings from module 'Geometry'
```

두 결과 모두 마지막 줄은 `import Geometry` 줄에 붙는다.

첫 번째 항목이 중요하다. 제안서는 async 함수나 actor 처럼 동시성을 쓴 scope 는 Minimal 안에서도 Strict 가 된다고 설계했지만, 6.4 의 Swift 5 모드 기본값은 그렇게 동작하지 않는다. 그 규칙은 `targeted` 부터 켜진다. 하위 scope 규칙은 `Scope.swift` 로 따로 실험했다.

```swift
class Counter {
    var value = 0
}

func minimalScope() {
    let c = Counter()
    let a: @Sendable () -> Void = { print(c.value) }
    a()
}

func strictScope() async {
    let c = Counter()
    let a: @Sendable () -> Void = { print(c.value) }
    a()
}

actor Store {
    func run() {
        let c = Counter()
        let a: @Sendable () -> Void = { print(c.value) }
        a()
    }
}
```

Swift 5 모드 기본값에서는 세 곳 모두 진단이 없다. async 함수와 actor 메서드 안에서도 그렇다. `targeted` 에서는 async 함수 `strictScope` 와 actor 메서드 `run` 에서만 아래 warning 이 나오고 동기 함수 `minimalScope` 는 조용하다. `complete` 에서는 세 곳 모두 나온다.

```text
warning: capture of 'c' with non-Sendable type 'Counter' in a '@Sendable' closure; this is an error in the Swift 6 language mode
```

제안서의 하위 scope 규칙대로라면 `@Sendable` 타입의 closure 는 동기 함수 안에서도 Strict 이므로 `minimalScope` 도 진단되어야 한다. 그래서 targeted 는 "동시성을 쓴 scope 만 엄격하게 본다" 는 모양이어서 제안서의 하위 scope 규칙과 비슷하지만 같지 않다. 그리고 `targeted` 라는 이름은 제안서에 없다. 제안서가 정의한 Strict 와 Minimal 두 모드 뒤에 컴파일러에 생긴 단계다. Xcode 에서는 build setting `SWIFT_STRICT_CONCURRENCY` (Strict Concurrency Checking: Minimal / Targeted / Complete) 가 이 옵션에 대응한다.

### 선언에 붙이는 @preconcurrency

라이브러리 관리자가 기존 선언에 동시성 정보를 더하려면 보통 세 가지 중 하나를 해야 한다. 함수 타입에 `@Sendable` 이나 global actor attribute 를 붙이거나, generic signature (제네릭 선언의 타입 매개변수와 그 제약 목록) 에 `Sendable` 제약을 더하거나, 선언에 global actor attribute 를 붙인다. 이 중 어느 것이든 그 자체로는 옛 코드의 source break 나 ABI break 가 될 수 있다.

`@preconcurrency` 는 이런 선언에 붙인다. "이 선언은 모듈이 동시성을 완전히 도입하기 전부터 있었다" 는 뜻으로, `enum`, enum `case`, `struct`, `class`, `actor`, `protocol`, `var`, `let`, `subscript`, `init`, `func` 에 쓸 수 있다. 붙이면 효과가 네 가지다.

- 이름이 앞에서 본 목록의 기능이 없는 것처럼 mangling 된다.
- 사용하는 scope 가 Minimal 이면 그 불일치에 대한 진단을 숨긴다.
- 사용하는 scope 가 Strict 이면 (Swift 6 이후 포함) 그런 진단을 error 에서 warning 으로 낮춘다.
- ABI checker (라이브러리 버전 사이의 ABI 변화를 검사하는 도구) 는 digest (ABI 를 요약한 목록) 를 만들 때 이 기능들을 지운다.

Objective-C 선언은 가져올 때 모두 `@preconcurrency` 가 붙은 것처럼 취급한다.

앞의 `doSomethingThenFollowUp` 에서 `@MainActor` 와 `@Sendable` 을 `@preconcurrency` 와 함께 붙인 `LibB.swift` 로 같은 `Button.swift` 를 컴파일했다.

```swift
@preconcurrency @MainActor
public func doSomethingThenFollowUp(_ body: @escaping @Sendable () -> Void) {
    Task.detached {
        body()
    }
}
```

결과는 아래와 같다.

- Swift 5 모드: 진단 0개
- Swift 6 모드: error 였던 두 줄이 warning 이 된다.

```text
warning: call to main actor-isolated global function 'doSomethingThenFollowUp' in a synchronous nonisolated context [#ActorIsolatedCall]
warning: capture of 'self' with non-Sendable type 'MyButton' in a '@Sendable' closure [#SendableClosureCaptures]
```

- Swift 5 + `-strict-concurrency=complete`: 같은 두 줄이 warning 으로 나온다.

Minimal 에서는 완전히 숨고, Strict 에서는 error 대신 warning 이 되는 것이다. 옛 코드는 깨지지 않고, 새 규칙에 어긋난다는 사실은 사라지지 않는다.

Swift 6 이후에도 선언의 `@preconcurrency` 가 warning 으로 낮춘다는 이 규칙은 제안서의 2026-04-24 개정 ([commit d580e824](https://github.com/swiftlang/swift-evolution/commit/d580e824){:target="_blank"}, "Update SE-0337 to reflect `@preconcurrency` working on decls in Swift 6") 에서 본문에 들어갔다. 처음 수락된 본문은 선언의 `@preconcurrency` 효과를 Swift 5 모드 위주로 썼고, 이 개정이 실제 컴파일러 동작에 맞춰 Swift 6 이후 동작을 같이 적었다.

사용처의 모드에 따라 같은 함수의 타입이 달라 보이는 것도 이 절에서 눈여겨볼 점이다. 제안서의 예를 `Infer.swift` 로 옮겨 돌렸다. 아래 결과는 `@preconcurrency` 를 붙인 `LibB.swift` 로 만든 `Lib` 에 대해 컴파일한 것이다. `fn` 을 `@Sendable` 도 global actor 도 없는 `plain` 에 대입해서, `fn` 의 타입에 그것들이 보이는지를 드러낸다.

```swift
import Lib

func minimal() {
    let fn = doSomethingThenFollowUp
    let plain: (@escaping () -> Void) -> Void = fn
    _ = plain
}

func strict() async {
    let fn = doSomethingThenFollowUp
    let plain: (@escaping () -> Void) -> Void = fn
    _ = plain
}
```

Swift 5 모드에서 동기 함수 `minimal()` 은 진단이 없다. `async` 인 `strict()` 의 같은 코드는 warning 두 개를 낸다. `@preconcurrency` 가 없는 `LibA.swift` 로 같은 파일을 컴파일하면 `minimal()` 도 같은 warning 두 개를 낸다. 그러니 minimal 의 침묵은 `@preconcurrency` 가 만든 결과다.

```text
warning: converting non-Sendable function value to '@Sendable () -> Void' may introduce data races
warning: converting function value of type '@MainActor (@escaping @Sendable () -> Void) -> ()' to '(@escaping () -> Void) -> Void' loses global actor 'MainActor'; this is an error in the Swift 6 language mode
```

타입을 출력해 보면 minimal scope 에서 `fn` 의 타입은 `(@escaping () -> Void) -> ()`, strict scope 에서는 `@MainActor (@escaping @Sendable () -> Void) -> ()` 다. 제안서의 `minimal()` 과 `strict()` 예와 같은 결과다. Swift 6 모드에서는 최상위 scope 가 Strict 이므로 두 함수 모두 `@MainActor @Sendable (@escaping @Sendable () -> Void) -> ()` 로 보이고, `minimal()` 과 `strict()` 두 곳 모두 `error: converting non-Sendable function value to '@Sendable () -> Void' may introduce data races` 가 난다. 동시성을 모르는 코드에게는 동시성 이전 시절의 타입 그대로 보이고, 동시성을 아는 코드에게는 새 annotation 이 보인다. 같은 선언이 두 얼굴로 쓰이는 것이 이 기능의 핵심이다.

---

### Sendable 의 세 가지 상태

import 규칙을 읽으려면 타입이 Sendable 인지에 대해 세 가지 상태를 구분해야 한다. 타입이 프로토콜을 따른다고 선언하는 것을 conformance 라고 하는데, 아래 상태는 이 선언이 있는지와 유효한지로 나뉜다.

| 상태 | 뜻 |
| --- | --- |
| explicitly Sendable | 실제로 `Sendable` 을 따른다. 직접 선언했든 SE-0302 의 추론 규칙으로 따르게 되었든 같다 |
| explicitly non-Sendable | `Sendable` conformance 를 선언했지만 unavailable 이거나 만족하지 못하는 제약이 있다. 또는 Strict scope 에서 선언된 타입이다 |
| implicitly non-Sendable | `Sendable` conformance 가 아예 선언되지 않았다 |

각주 [2] 가 덧붙인다. Swift 6 모드나 `-warn-concurrency` 로 컴파일한 모듈의 타입은 implicit 상태가 없다. 모두 explicitly Sendable 이거나 explicitly non-Sendable 이다. implicit 은 아직 동시성을 모르는 옛 모듈에서만 생긴다. 그 모듈의 관리자가 "이 타입은 보내면 안 된다" 고 확정하려면 unavailable conformance 를 쓴다.

```swift
@available(*, unavailable)
extension Point: Sendable {}
```

#### @available로 Sendable conformance 를 막기

[`@available`](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/){:target="_blank"} 에 `*` 와 `unavailable` 을 주면 모든 플랫폼에서 그 선언을 쓸 수 없다는 뜻이다. 이것을 `Sendable` conformance 에 붙이면 "`Point` 는 `Sendable` 이 아니다" 라고 명시적으로 선언하는 셈이 된다. 이런 conformance 가 있으면 `Point` 가 Sendable 로 추론되는 것도 막힌다. 이 절의 표에서 implicit 과 explicit non-Sendable 이 달라지는 것은 바로 이 선언의 유무 때문이다.

---

### import 에 붙이는 @preconcurrency

`@preconcurrency` 를 `import` 에 붙이면, 그 모듈에서 온 타입 때문에 생기는 동시성 위반을 약하게 다룬다. 아직 동시성 annotation 이 없는 모듈을 쓸 때 쓰고, 제안서는 내가 필요한 타입들이 모두 annotation 을 얻으면 컴파일러가 알려 주도록 설계했다 (6.4 에서는 이 알림이 나오지 않았다. 아래에서 본다). 내가 갖고 있던 잘못된 가정이 고쳐질 때까지 프로젝트가 컴파일되게 해 주는 임시 탈출구이기도 하다. 제안서의 규칙은 다음과 같다.

- implicitly non-Sendable 타입이 Sendable 을 요구하는 자리에 쓰였을 때:
  - 그 타입이 `@preconcurrency import` 를 통해 보이면, 진단은 Swift 6 이전에는 숨겨지고 Swift 6 이후에는 warning 으로 나온다.
  - 아니면 진단은 평소대로 나오고, 별도로 `@preconcurrency import` 를 쓰라는 진단이 붙는다.
- explicitly non-Sendable 타입이 Sendable 을 요구하는 자리에 쓰였을 때:
  - `@preconcurrency import` 를 통해 보이면 Swift 6 이후에도 error 대신 warning 이다.
  - 아니면 진단은 평소대로 나온다.
- `@preconcurrency` 가 쓰이지 않았으면 지우라는 warning 이 나온다고 제안서는 쓴다. 6.4 에서는 이 warning 이 나오지 않았다.

이 규칙을 실제로 확인하려고 Geometry 를 세 가지 상태로 만들고, 사용하는 쪽의 `import` 를 두 가지로 바꿔 돌렸다. 앞의 `Client1` 이 `import Geometry` 쪽이고, `@preconcurrency import Geometry` 쪽은 첫 줄만 다르다. 결과는 아래 표와 같다 (모두 Swift 6.4).

| Geometry 상태 | 사용하는 쪽 | Swift 5 모드 | Swift 6 모드 |
| --- | --- | --- | --- |
| Point 에 Sendable 표시 없음 (implicit) | `import Geometry` | 진단 없음 | error 2개 + "add @preconcurrency" warning |
| 같음 | `@preconcurrency import Geometry` | 진단 없음 | 진단 없음 |
| unavailable Sendable (explicit non-Sendable) | `import Geometry` | warning 2개 (`...; this is an error in the Swift 6 language mode`) | error 2개 |
| 같음 | `@preconcurrency import Geometry` | warning 2개 | warning 2개 |
| `public struct Point: Sendable` | `@preconcurrency import Geometry` | 진단 없음 | 진단 없음 |

explicit non-Sendable 에 `@preconcurrency import` 를 붙인 칸의 Swift 6 모드 warning 은 이렇다.

```text
warning: non-Sendable type 'Point' of property 'origin' cannot exit actor-isolated context
warning: capture of 'p' with non-Sendable type 'Point' in a '@Sendable' closure
```

표에서 눈에 띄는 것은 두 번째 줄이다. 제안서 문장은 implicit 타입이 `@preconcurrency import` 로 보이면 "Swift 6 이후에는 warning" 이라고 말한다. 그런데 6.4 컴파일러는 Swift 6 모드에서도 이 경우 warning 을 내지 않고 진단이 하나도 없다. 제안서 본문과 지금 컴파일러의 동작에 이만큼의 차이가 있다. 이 동작은 뒤의 리뷰 절에서 haikuty 가 요청한 쪽, 곧 warning 도 남기지 않는 쪽과 가깝다.

세 번째와 네 번째 줄은 제안서와 맞는다. 관리자가 "아니다" 라고 확정한 타입은 import 에 `@preconcurrency` 를 붙였든 안 붙였든 진단이 돌아오고, 붙였을 때만 error 가 아닌 warning 이다. 앞 절에서 말한 "숨기지 않고, 막지도 않는다" 가 그대로 구현된 것이다. 다섯 번째 줄은 관리자가 `Point` 를 `struct` 로 바꾸고 Sendable 로 확정한 경우로, 가정이 사실이 되었으니 진단이 없다.

다섯 번째 줄은 `@preconcurrency import` 가 쓸모없어진 경우이기도 하다. 제안서의 규칙대로면 여기서 지우라는 warning 이 나와야 하지만 나오지 않았다. `Client2` 와 `Client3` 처럼 `@preconcurrency import` 를 쓴 파일을 Geometry 세 가지 상태, Swift 5 와 6 모드, `complete`, `-warn-concurrency` 로 돌려 봤을 때도 6.4 에서는 그 warning 이 나오지 않았다.

"쓸모없는 `@preconcurrency import` 면 지우라" 는 규칙에 해당하는 진단 문구는 컴파일러 진단 문자열 목록 (`share/swift/diagnostics/en.strings`) 에 `remove_predates_concurrency_import` 라는 항목으로 있고, 문구는 `'@preconcurrency' on module %0 has no effect` 다. 하지만 이 글의 샘플은 그 진단을 내지 않았다. 제안서 각주 [4] 는 "unused" 의 정의를 일부러 정확히 하지 않았다고 쓴다. 같은 타입을 가져오는 `@preconcurrency import` 가 둘이면 그중 어느 쪽을 지우라고 권해야 할지를 정교하게 정하기 어려워서다.

리뷰에서 nonsensery 가 규칙 목록의 도입 문장이 헷갈린다고 물었다. 문장대로 읽으면 "import 가 `@preconcurrency` 인데 `@preconcurrency import` 를 쓰라는 진단이 나온다" 처럼 보이기 때문이다. Doug Gregor 는 목록 자체가 아니라 도입 문장이 문제라고 답하며 문구를 고치겠다고 했다. 이 부분은 "`@preconcurrency` 를 import 에 쓸 수 있고, 그러면 이렇게 동작한다" 로 읽으면 된다. 현재 본문에도 도입 문장은 그대로다.

### Sendable 을 물려받는 프로토콜과 Error

SE-0302 는 `Error` 와 `CodingKey` 에만 특별 규칙을 하나 두었다. 이 프로토콜들이 `Sendable` 을 상속하게 되면 기존에 이 프로토콜을 따르던 타입이 갑자기 Sendable 로 취급되어 깨지므로, 이들을 통해 Sendable 이 된 타입의 error 는 Swift 6 이전에는 warning 으로 낮춘다는 규칙이었다.

이 제안서는 이 개별 규칙을 일반화한다. `@preconcurrency` 가 붙고 `Sendable` 을 상속하는 모든 프로토콜에 같은 규칙을 적용한다. 표준 라이브러리의 두 프로토콜도 이 방식으로 바뀐다.

```swift
@preconcurrency protocol Error: Sendable { ... }
@preconcurrency protocol CodingKey: Sendable { ... }
```

#### Error 와 CodingKey 의 Sendable 상속

[`Error`](https://developer.apple.com/documentation/swift/error){:target="_blank"} 는 `throw` 로 던질 수 있는 타입이 따르는 프로토콜이다. 던져진 error 는 다른 task 나 actor 로 넘어갈 수 있어서 Sendable 이어야 안전하다. [`CodingKey`](https://developer.apple.com/documentation/swift/codingkey){:target="_blank"} 는 `Codable` 이 인코딩과 디코딩에 쓰는 키 타입 (보통 `enum CodingKeys`) 이 따르는 프로토콜이다. 둘 다 오래전부터 있던 프로토콜이라 `Sendable` 상속을 뒤늦게 얹으면 이를 따르던 기존 타입이 깨질 수 있어서 `@preconcurrency` 가 필요하다.

각주 [3] 는 2026-04 개정에서 추가되었다. 원래 SE-0302 의 규칙과 달리 이 완화는 Swift 6 이후를 포함한 모든 언어 모드에 적용되고, stored property 가 non-Sendable 이라거나 non-final class 가 따른다는 등, 상속한 Sendable 요구에서 오는 모든 진단을 다룬다.

직접 확인한 `Err.swift` 다.

```swift
class MutableStorage {
    var counter = 0
}

struct ProblematicError: Error {
    var storage: MutableStorage
}

@preconcurrency protocol Job: Sendable {}

struct MyJob: Job {
    var storage: MutableStorage
}

protocol StrictJob: Sendable {}

struct MyStrictJob: StrictJob {
    var storage: MutableStorage
}
```

Swift 6 모드의 결과는 이렇다. `ProblematicError` 와 `MyJob` 은 warning 이고, `@preconcurrency` 가 없는 `StrictJob` 을 따르는 `MyStrictJob` 은 error 다.

```text
warning: stored property 'storage' of 'Sendable'-conforming struct 'ProblematicError' has non-Sendable type 'MutableStorage'
error: stored property 'storage' of 'Sendable'-conforming struct 'MyStrictJob' has non-Sendable type 'MutableStorage'
```

`MyJob` 도 `ProblematicError` 와 같은 꼴의 warning 이 나온다. Swift 5 (minimal) 에서는 `ProblematicError` 와 `MyJob` 은 진단이 없고, `MyStrictJob` 만 `...; this is an error in the Swift 6 language mode` 가 붙은 warning 이다. `Job` 처럼 새로 만든 프로토콜에 `@preconcurrency` 를 붙인 것은 이 규칙이 일반화되었음을 보려는 실험이다. 실제로 이 장치가 쓰이는 자리는 이미 있던 프로토콜이 나중에 `Sendable` 을 상속하게 되는 경우다. `Error` 에만 있던 특혜를 같은 처지의 모든 프로토콜에 열어 준 셈이다.

## 개선했을 때의 기대 효과

근거가 있는 것만 정리한다.

라이브러리 쪽은 실측 mangled name 비교가 증거다. `@preconcurrency` 를 annotation 과 함께 붙이면 심볼 이름이 `$s3Lib23doSomethingThenFollowUpyyyycF` 로 유지되어 ABI 가 깨지지 않는다. annotation 이 없던 원래 선언, `@MainActor` 만 붙인 선언, `@preconcurrency` 를 붙인 `LibB` 가 모두 이 이름이었다. 다만 순서에 주의할 점이 있다. 제안서의 Effect on ABI stability 는, 이미 `@Sendable` 같은 기능을 붙여 배포한 선언에 나중에 `@preconcurrency` 를 붙이면 그때 ABI 가 깨진다고 쓴다. 기능과 `@preconcurrency` 를 같은 시점이나 그 이전에 붙여야 한다.

앱 쪽은 Swift 6 모드에서 그냥 `import Geometry` 했을 때 error 2줄과 `@preconcurrency` 를 권하는 warning 1줄이던 것이, `@preconcurrency import Geometry` 로 바꾸면 0줄이 된다. 그리고 Geometry 가 `Point` 를 explicit non-Sendable 로 확정하면 warning 으로 돌아온다. 빌드는 계속되면서 버그는 드러난다.

실행해서 돌려 본 패키지가 있다. Geometry 는 `.swiftLanguageMode(.v5)`, Lib 는 Swift 6 에 `@preconcurrency`, App 은 Swift 6 에 `@preconcurrency import Geometry` 로 구성했다. App 의 `main.swift` 는 이렇다.

```swift
@preconcurrency import Geometry
import Lib

actor Canvas {
    var origin = Point()
}

let canvas = Canvas()
let p = await canvas.origin
print("origin:", p.x, p.y)

await MainActor.run {
    doSomethingThenFollowUp {
        print("follow up")
    }
}
try await Task.sleep(for: .milliseconds(100))
```

#### MainActor.run과 Task.sleep으로 main actor 호출 보여 주기

[`MainActor.run(resultType:body:)`](https://developer.apple.com/documentation/swift/mainactor/run%28resulttype:body:%29){:target="_blank"} 은 주어진 closure 를 main actor 위에서 실행하고, 끝날 때까지 `await` 로 기다린다. 이 예에서는 `@MainActor` 인 `doSomethingThenFollowUp` 을 main actor 위에서 부른다는 점을 코드에 드러내려고 썼다. Swift 6 모드의 top-level code 는 이미 main actor 위에서 실행되지만, 어디서 부르는지가 눈에 보이게 하려는 것이다. [`MainActor`](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 자체는 앞에서 설명한 global actor 이고, `@MainActor` attribute 가 가리키는 대상이다. [`Task.sleep(for:tolerance:clock:)`](https://developer.apple.com/documentation/swift/task/sleep%28for:tolerance:clock:%29){:target="_blank"} 는 현재 task 를 주어진 시간 동안 멈춘다. 여기서는 `doSomethingThenFollowUp` 이 만든 별도 task 가 `"follow up"` 을 출력할 시간을 벌려고 100ms 를 기다린다. 프로그램이 먼저 끝나면 그 출력이 사라지기 때문이다. `sleep` 은 기다리는 동안 task 가 취소되면 `CancellationError` 를 던지므로 `try` 가 필요하다.

`swift build` 후 `swift run App` 출력이다.

```text
origin: 0 0
follow up
```

경계를 넘는 `Point` 읽기와 `@MainActor` 함수 호출이 모두 컴파일되고 의도대로 돈다. 다만 컴파일되고 돈다고 안전하다는 뜻은 아니다. `Point` 는 여전히 여러 곳이 공유할 수 있는 class 이고, `@preconcurrency import` 는 그 위험을 가렸을 뿐 없애지 않았다.

## 다른 선택지는 왜 안 됐나

제안서는 두 가지 대안을 검토하고 받아들이지 않았다. 하나는 버전 기준으로 자동 적용하는 방식이고, 다른 하나는 Objective-C 쪽의 예외를 없애는 방식이다. 그 뒤에는 리뷰 스레드에서 나온 반론과 답을 정리한다.

---

### concurrency epoch

모듈의 발전이 `@available` 로 표현할 수 있는 버전에 묶여 있다면, 어떤 버전에서 공개 API 에 동시성 annotation 을 소급해서 붙이고, 그 뒤 새 API 는 처음부터 annotation 을 갖고 태어날 가능성이 높다. 그렇다면 "이 버전 이전의 API 에는 자동으로 `@preconcurrency` 를 적용한다" 는 기준 버전을 모듈이 정하게 하자는 아이디어다. 관리자가 수많은 선언에 일일이 `@preconcurrency` 를 붙이지 않아도 된다.

제안서는 이 안을 세 가지 이유로 거절한다. Darwin (macOS 와 iOS 의 기반이 되는 Apple 의 OS 층) 전용 모듈에만 쓸모가 있고, Swift 나 OS 와 버전이 묶인 모듈에만 쓸모가 있으며, 버전 단위가 너무 거칠다. 마지막 이유의 예는, 개발 주기 초반에 추가된 API 가 주기 후반에 동시성 annotation 을 받으면 자동으로 `@preconcurrency` 가 붙었다고 착각하기 쉽다는 것이다. 게다가 `@preconcurrency` 는 어차피 관리자가 고치고 있는 선언 바로 옆에 붙이면 되므로, 수고를 덜어 주는 폭이 크지 않다.

---

### Objective-C 선언은 언제나 @preconcurrency

모든 Objective-C 선언이 암묵적으로 `@preconcurrency` 이므로, 새로 만든 Objective-C 동시성 API 라 해도 Minimal 모드 코드에서 검사를 강제할 방법이 없다. 제안서는 이 한계를 받아들인다. 거대한 기존 Objective-C 라이브러리를 점검하는 과정을 단순하게 유지하는 쪽이 낫다고 보았기 때문이다.

실제로 이 한계가 닿는 곳은 UIKit 처럼 Objective-C 헤더로 가져오는 프레임워크다. 헤더에서 `@MainActor` 로 가져온 선언은 `@preconcurrency` 가 붙은 것으로 취급되므로, Minimal 인 코드에서는 main actor 를 어긴 호출이 아무 진단 없이 지나간다. `@MainActor` 라는 사실이 선언에 있는데도 숨겨져 있는 것이고, Strict 인 코드에서야 warning 이나 error 로 드러난다.

### 리뷰에서 나온 이야기

리뷰 스레드에서 가장 길게 오간 이야기는 haikuty 의 문제 제기였다. 많은 팀이 warnings-as-errors 를 정책으로 쓰는데, Swift 6 에서 `@preconcurrency import` 가 진단을 error 에서 warning 으로 낮출 뿐 없애지 않으면, 그런 팀은 warning 때문에 여전히 빌드가 깨져 이 마이그레이션 경로를 쓸 수 없다는 것이다. 수락 당시 제안서 본문 2단계가 "silences these warnings" 라고 쓴 것과도 어긋나 보인다고 지적했다. 이 문구는 2026-04 개정 (commit d580e824) 에서 "silences or downgrades" 로 바뀌어 지금 본문에 있다.

Doug Gregor 의 답은 이렇다. Swift 6 의 의도는 unsafe 코드가 명시적으로 개입하지 않은 잠재 data race 를 조용히 받아들이지 않는 것이다. 그래서 `@preconcurrency` 가 진단을 완전히 숨길 수 없고 warning 으로 남긴다. 완전한 침묵이 필요하면 다른 모듈의 타입에 직접 `@unchecked Sendable` (컴파일러의 검증을 건너뛰고 개발자가 책임지고 Sendable 을 선언하는 conformance) 를 쓰는 길이 있다. 타입이 Sendable 이 되어 경고가 사라지고, 명시적이므로 괜찮다. warnings-as-errors 팀은 이 conformance 를 계속 관리해야 하지만 그 정도는 감수할 만하다는 입장이다.

haikuty 는 40명 이상의 팀과 80만 줄 이상의 코드, GRDB 나 Apollo-iOS 같은 큰 서드파티 패키지 이야기를 하며, 모든 타입에 `@unchecked Sendable` 을 쓰는 것은 비현실적이라고 맞섰다. 이때 xwu 가 간단한 해법을 제시했다. 그런 큰 팀은 Swift 6 컴파일러를 쓰되 언어 모드는 Swift 5 로 유지하면 된다는 것이다. haikuty 도 이 점을 잊고 있었다며 수긍했다. 이 대화가 곧 마이그레이션 순서의 실무를 말해 준다. 언어 모드를 올리는 것과 컴파일러를 올리는 것은 별개이고 (앞의 Swift 언어 모드란? 절), 큰 코드베이스는 둘을 따로 움직일 수 있다.

lukasa 는 이 제안서를 "한 가지 개념을 여러 곳에 같은 뜻으로 쓰는, Swift 다운 설계" 라고 평가했다. 한편 라이브러리 관리자가 annotation 을 붙이면서 `@preconcurrency` 를 깜빡하기 쉽다는 우려도 남겼다. 이는 ABI checker 같은 도구로 보완할 수 있다는 의견이었다. 제안서는 그대로 수락되었다 (2022-01-28).

앞에서 본 2026-04 개정은 이 스레드의 걱정과 이어진다. 개정의 중심은 선언의 `@preconcurrency` 가 Swift 6 이후에도 진단을 낮춘다는 규칙을 본문에 넣은 것이다. import 쪽 규칙은 "Swift 6" 를 "Swift 6 and later" 로 고치고 각주 번호를 단 정도로 바뀌었다. 그리고 6.4 컴파일러가 implicit 타입의 `@preconcurrency import` 를 Swift 6 모드에서도 조용히 넘기는 것은, haikuty 가 바란 방향에 오히려 가깝다.

## Swift 6 언어 모드와 마이그레이션

제안서의 `-warn-concurrency` 는 지금 `StrictConcurrency` upcoming feature (다음 언어 모드의 기능을 미리 켜는 옵션) 와 `-strict-concurrency=complete` 로 이어진다. `-swift-version 5 -enable-upcoming-feature StrictConcurrency` 로 `Client1` 을 컴파일하면 `complete` 와 같은 warning 3줄이 나왔다. Swift 6 언어 모드에서는 이 feature 가 기본으로 켜진다.

SwiftPM 에서는 타깃마다 언어 모드를 따로 고를 수 있다. 샘플 패키지의 `Package.swift` 다.

```swift
// swift-tools-version: 6.0
import PackageDescription

let package = Package(
    name: "SE0337",
    platforms: [.macOS(.v15)],
    targets: [
        .target(name: "Geometry", swiftSettings: [.swiftLanguageMode(.v5)]),
        .target(name: "Lib"),
        .executableTarget(name: "App", dependencies: ["Geometry", "Lib"]),
    ]
)
```

#### Package 와 target 선언

[`Package`](https://developer.apple.com/documentation/packagedescription/package){:target="_blank"} 는 SwiftPM 패키지 하나를 기술하는 최상위 값이다. `targets` 에 모듈 단위인 target 을 나열한다. [`Target`](https://developer.apple.com/documentation/packagedescription/target){:target="_blank"} 의 `.target` 은 다른 target 이 가져다 쓰는 라이브러리 모듈이고, `.executableTarget` 은 `main.swift` 가 있는 실행 파일 모듈이다. 위 예에서 Geometry 와 Lib 는 `.target`, App 은 `.executableTarget` 이며 `dependencies` 로 앞의 둘을 가져다 쓴다. [`platforms`](https://developer.apple.com/documentation/packagedescription/package/platforms){:target="_blank"} 의 `.macOS(.v15)` 는 이 패키지의 최소 배포 대상을 macOS 15 로 정한다.

#### swiftLanguageMode로 타깃마다 언어 모드 고르기

[`swiftLanguageMode(_:_:)`](https://developer.apple.com/documentation/packagedescription/swiftsetting/swiftlanguagemode%28_:_:%29){:target="_blank"} 는 타깃의 `swiftSettings` 배열에 넣어서 그 타깃을 컴파일할 Swift 언어 모드를 정한다. `.v5` 는 Swift 5 모드이고, 정하지 않으면 tools version 6.0 이상의 패키지는 Swift 6 모드가 기본이다. 위 예에서 Geometry 는 "아직 동시성을 모르는 옛 라이브러리" 를 흉내 내려고 `.v5` 로 두었고 Lib 와 App 은 Swift 6 기본이다. 같은 방식으로 아직 옮기지 못한 타깃만 `.v5` 로 남기면 된다. upcoming feature 를 따로 켜려면 [`enableUpcomingFeature(_:_:)`](https://developer.apple.com/documentation/packagedescription/swiftsetting/enableupcomingfeature%28_:_:%29){:target="_blank"} 에 `"StrictConcurrency"` 를 넘기면 된다. Swift 5 모드를 유지한 채 그 타깃에만 엄격한 검사를 더하는 용도다.

실무에서의 마이그레이션 순서를 정리하면 이렇다. Swift 5 모드에서 targeted 로 시작해 complete 로 올리고, 마지막에 Swift 6 모드로 옮긴다. 이 과정에서 만나는 아직 준비되지 않은 의존 모듈에 `@preconcurrency import` 를 붙인다. 이 표시는 임시 탈출구이므로 가끔 `@preconcurrency` 를 지워 보고 진단이 돌아오는지 본다. 제안서는 불필요해졌다는 warning 이 지울 때를 알려 준다고 했지만 6.4 에서는 그 warning 이 나오지 않으므로, 지워 보고 진단이 돌아오는지를 직접 본다.

## 정리

- 동시성 annotation 이 늦게 붙는 라이브러리 때문에 source 와 ABI 가 깨지지 않도록, 선언에 붙이는 `@preconcurrency` 가 이름은 옛 모양으로 짓고 사용처의 진단은 모드에 따라 숨기거나 warning 으로 낮춘다.
- 내 코드가 먼저 준비된 경우를 위해 `@preconcurrency import` 가 아직 준비 안 된 모듈의 Sendable 진단을 가라앉힌다. 그 모듈이 "아니다" 라고 확정하면 warning 으로 돌아오니 버그는 숨지 않고 빌드도 막히지 않는다.
- 이 모든 것이 "내 모듈부터 엄격하게, 경계는 임시 표시로, 모듈이 준비되면 표시를 지운다" 는 다섯 단계 흐름 위에 놓인다.
- 제안서가 쓴 Strict 와 Minimal 두 모드는 지금 컴파일러에서 `-strict-concurrency` 의 `minimal`, `targeted`, `complete` 로 나뉘어 있고, 제안서 본문과 6.4 의 동작은 세 군데 다르다. implicit 타입은 `@preconcurrency import` 아래에서 Swift 6 모드에도 진단이 없고, 쓸모없는 `@preconcurrency import` 를 지우라는 warning 이 나오지 않으며, Swift 5 모드의 minimal 은 async 함수나 actor 안에서도 진단을 내지 않는다.

RunWay 같은 앱에서는 서드파티 SDK 를 `@preconcurrency import` 로 가두고 내 모듈부터 Swift 6 로 옮기면 된다. 직접 만든 패키지를 공개할 때는 기존 API 에 동시성 annotation 과 `@preconcurrency` 를 같이 붙여, 이미 쓰고 있는 사람들의 소스와 바이너리를 지킨다.
