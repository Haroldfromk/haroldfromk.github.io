Udemy에서 Hummingbird 강의를 들으면서 라우팅, Fluent, JWT 인증, Docker로 Railway 배포까지 한 바퀴 돌았다. 그런데 강의에서 WebSocket은 다루지 않았다. 백엔드를 이번에 처음 시작한 입장에서 REST 다음으로 궁금했던 게 실시간 통신이라, 연습 삼아 직접 만들어보기로 했다.

이 시리즈는 클로드 코드와 함께 만들면서 정리한 것이다. 백엔드는 이번에 막 시작한 참이라 막히는 지점마다 물어보며 진행했고, 그 과정에서 걸린 것들을 그대로 남겨두려 한다.

만들 건 단체 채팅방 하나다. 1:1도 아니고 방 여러 개도 아니다. 로그인도 넣지 않고 이름만 적고 들어간다. 메시지도 저장하지 않는다. 이번 시리즈에서 확인하고 싶은 건 연결이 어떻게 맺어지고, 한 명이 보낸 글이 어떻게 나머지 전부에게 퍼지는지, 그 두 가지뿐이라 나머지는 전부 덜어냈다.

## 처음 생각한 구조가 틀렸다

시작하기 전에 머릿속으로 그린 그림은 이랬다. 앱에서 `URLSession`으로 메시지를 POST로 보내고, 받을 때는 GET으로 가져온다. 그 GET을 Combine 같은 걸로 계속 흘려보내면 실시간처럼 보이지 않을까 싶었다.

지금까지 배운 게 REST뿐이었으니 자연스러운 상상이었는데, WebSocket은 그렇게 동작하지 않았다.

![요청을 보내야 답이 오는 방식과, 한 번 연결하면 서버가 먼저 말을 거는 방식의 차이](/assets/img/chatbird/rest-and-socket.svg){: width="720" height="300"}

왼쪽이 내가 생각했던 방식이다. 앱이 "새 메시지 있어요?"라고 물어야만 서버가 답한다. 문제는 언제 새 메시지가 올지 앱이 알 수 없다는 것이다. 그래서 계속 물어보는 수밖에 없는데, 대부분은 "없어요"가 돌아온다. 채팅이 만들어지긴 하지만 헛걸음이 많고, 물어보는 간격만큼 반응도 늦다.

오른쪽이 WebSocket이다. 처음 붙을 때 딱 한 번 요청을 보내는데, 이때 "앞으로 이 연결은 HTTP 말고 다른 방식으로 쓰자"고 서로 합의한다. 합의가 끝나면 그 연결은 끊기지 않고 계속 열린 채로 남는다. 그 뒤로는 GET도 POST도 없다. 열린 길 위로 양쪽이 아무 때나 글자를 던지면 된다.

여기서 제일 큰 차이는 **서버가 먼저 말을 걸 수 있다**는 점이다. 앱이 아무것도 묻지 않았는데 다른 사람이 보낸 메시지가 그냥 도착한다. 내가 Combine으로 흉내내려고 했던 게 원래 이 프로토콜에 들어있는 기능이었던 셈이다.

그래서 앱 쪽에도 Combine은 필요 없다. `URLSessionWebSocketTask`가 이미 "받으면 알려주는" 동작을 갖고 있어서, 받은 걸 화면에 꽂아주기만 하면 된다.

## 메시지가 건너가는 길

두 번째로 헷갈렸던 건 웹페이지와 서버를 같은 것으로 본 부분이었다. 브라우저에 뜨는 채팅 화면이 곧 Hummingbird라고 생각했는데 그렇지 않다.

Hummingbird는 서버고, 웹페이지는 그 서버가 내려준 HTML을 브라우저가 받아서 띄운 화면이다. 즉 브라우저 화면은 iOS 앱과 같은 지위의 손님이다. 둘 다 서버에 각자 연결을 하나씩 맺고 있을 뿐이다.

![브라우저 탭과 iOS 앱이 각각 서버에 연결을 맺고, 한 명이 보낸 메시지를 서버가 나머지 모두에게 다시 보내주는 구조](/assets/img/chatbird/broadcast-path.svg){: width="720" height="320"}

그래서 브라우저에서 보낸 글이 앱으로 직접 가는 일은 없다. 서버까지 갔다가, 서버가 자기한테 붙어 있는 연결 명단 전체에 다시 뿌린다. 이걸 브로드캐스트라고 부른다.

그림에서 보낸 사람 본인도 다시 받는 걸로 그렸는데, 일부러 그렇게 잡았다. 보낸 사람만 빼고 보내려면 서버가 "이 연결은 방금 보낸 그 사람인가"를 매번 가려내야 한다. 그냥 명단 전체에 뿌리면 그 판단이 통째로 사라진다. 화면에 내 말풍선을 띄우는 일도 서버가 되돌려준 걸 받아서 처리하면 되니, 보낸 직후와 받은 직후를 따로 다룰 필요도 없어진다.

## 프로젝트 준비하기

`hummingbird init`으로 서버를 만들었다. 만드는 중에 database support를 고르라고 하는데 postgres, fluent, no 세 가지가 나온다. no를 골랐다.

메시지를 남기려면 DB가 필요하지만, 그러면 시작하자마자 모델을 정의하고 표를 만드는 코드부터 써야 한다. 이번에 확인하려는 건 연결과 브로드캐스트라 그 앞에 다른 게 끼는 게 싫었다. 나중에 지난 대화 불러오기를 붙이고 싶어지면 그때 의존성을 추가하면 된다.

만들어진 기본 코드는 라우터에 `GET /` 하나가 전부다.

```swift
// App+build.swift
func buildRouter() throws -> Router<AppRequestContext> {
    let router = Router(context: AppRequestContext.self)
    router.addMiddleware {
        LogRequestsMiddleware(.info)
    }
    router.get("/") { _,_ in
        return "Hello!"
    }
    return router
}
```

서버를 띄우고 브라우저로 들어가면 `Hello!`만 뜬다.

## 소켓이란 무엇인가?

이제 연결 경로를 만들 차례인데, 그 전에 소켓이라는 말을 짚고 가야겠다. 나는 이게 WebSocket에만 들어있는 특별한 장치인 줄 알았는데 아니었다.

두 컴퓨터가 네트워크로 대화하려면 양쪽에 글자를 넣고 빼는 창구가 하나씩 있어야 한다. 이 창구를 소켓이라고 부른다. 콘센트처럼 뭔가를 꽂아서 통하게 하는 자리라는 뜻에서 온 이름이다.

지금까지 만든 REST API도 전부 이 창구 위에서 돌아갔다. 요청할 때마다 창구를 열고, 요청을 넣고, 응답을 받고, 볼일이 끝났으니 정리한다. WebSocket이 하는 일은 여기서 마지막 정리를 하지 않는 것이다. 그래서 이름에 소켓이 들어간다. 웹에서 쓰는, 닫지 않는 소켓이라는 뜻이다.

![앱과 서버 양쪽 아래에 소켓이라는 창구가 있고, 그 위에 HTTP와 WebSocket이라는 대화 규칙이 얹혀 있는 층 구조](/assets/img/chatbird/socket-layers.svg){: width="720" height="312"}

층으로 그리면 이렇다. 소켓은 맨 아래에 늘 깔려 있고, 그 위에서 어떤 규칙으로 말을 주고받을지가 HTTP냐 WebSocket이냐의 차이다. 양쪽이 같은 규칙을 쓰고 있어야 말이 통한다.

말로만 보면 잘 안 와닿아서 직접 눌러볼 수 있게 만들었다. 방식을 바꿔가며 서버에 메시지를 도착시켜 보면 된다.

REST 쪽은 물어볼 때마다 창구를 새로 열고 대부분 헛걸음으로 끝난다. 그사이 도착한 메시지는 앱이 물어보기 전까지 서버에 쌓여 있다. WebSocket 쪽은 창구를 연 횟수가 1에서 늘지 않고, 서버에 도착한 메시지가 앱으로 곧장 넘어간다.

그럼 REST는 왜 굳이 창구를 정리할까. 열어두면 서버가 그만큼 자리를 계속 잡아먹기 때문이다. 손님이 천 명이면 창구도 천 개가 열린 채로 남는다. 게시판 글을 한 번 읽고 마는 일에는 그 값을 치를 이유가 없고, 채팅은 치를 만하다. 그 판단의 차이일 뿐이다.

## 브라우저에서 먼저 확인할 화면 만들기

원래 계획은 iOS 앱부터 만드는 거였는데, 순서를 바꿨다. 단체 채팅방은 여러 명이 동시에 들어와야 확인이 되는데, 시뮬레이터를 여러 개 띄우는 것보다 브라우저 탭을 여러 개 여는 게 훨씬 빠르기 때문이다.

그래서 서버가 채팅 화면을 직접 내려주도록 했다. 강의에서는 JSON을 돌려주는 API만 만들어봐서 서버가 HTML 파일까지 내려줄 수 있다는 걸 몰랐는데, Hummingbird에는 폴더 안의 파일을 그대로 내려주는 `FileMiddleware`가 이미 들어있었다. 별도 의존성을 추가할 필요도 없이 본체에 포함되어 있다.

```swift
// App+build.swift
router.addMiddleware {
    LogRequestsMiddleware(.info)
    // public 폴더 안의 파일을 그대로 내려준다.
    // "/" 로 들어오면 public/index.html 을 찾아서 보여준다.
    FileMiddleware("public", searchForIndexHtml: true)
}
```

`searchForIndexHtml`을 켜두면 `/`로 들어왔을 때 `public/index.html`을 찾아준다. 이걸 넣고 나니 `Hello!`를 돌려주던 `router.get("/")`은 도달할 일이 없어졌다. 미들웨어가 먼저 파일을 찾아서 응답해버리기 때문이다. 그래서 그 라우트는 지웠다.

`public/index.html`은 빌드 도구 없이 HTML 한 파일로 만들었다. 이름을 적고 연결하면 말풍선이 쌓이는 화면이다.

여기서부터는 먼저 밝혀둘 게 있다. 나는 자바스크립트를 거의 모른다. 이 페이지는 클로드 코드에 시켜서 만들었고, 내가 한 일은 어떤 화면이 필요한지 말하고 결과를 확인한 것뿐이다. 그래서 문법을 설명하지는 않고, WebSocket을 쓰는 부분이 나중에 Swift에서 쓸 것과 어떻게 대응되는지만 짚으려 한다. 어차피 이 페이지는 서버가 제대로 도는지 확인하는 도구고, 진짜 목적지는 iOS 앱이다.

핵심은 아래 부분이다.

```javascript
// public/index.html
socket = new WebSocket(`ws://${location.host}${SOCKET_PATH}`);

socket.onopen = () => {
  setStatus("연결됨", "on");
  // 생략
};

socket.onmessage = (event) => {
  const message = decodeMessage(event.data);
  addBubble(message, message.sender === myNickname);
};

socket.onclose = () => {
  setStatus("연결 끊김", "off");
  // 생략
};
```

`new WebSocket(...)` 한 줄이 앞에서 말한 "한 번만 하는 요청"이다. 이게 성공하면 `onopen`이 불리고, 그때부터 연결이 열린 채로 남는다. 그 뒤로 서버가 뭔가 보낼 때마다 `onmessage`가 불린다. 내가 요청을 보내지 않아도 불린다는 게 REST와 다른 지점이다.

이름만 다를 뿐 앱에서도 같은 일을 하게 된다.

| 하는 일 | 브라우저 | 앱 (Swift) |
|---|---|---|
| 연결 만들기 | `new WebSocket(주소)` | `URLSession.shared.webSocketTask(with:)` |
| 연결됨 | `onopen` | `resume()` 이후 첫 응답 |
| 메시지 받기 | `onmessage` | `receive`의 성공 결과 |
| 메시지 보내기 | `send()` | `send(.string(...))` |
| 연결 끊김 | `onclose` | `cancel(with:reason:)` |

한 가지 큰 차이가 있다. 브라우저의 `onmessage`는 한 번 등록해두면 메시지가 올 때마다 알아서 계속 불린다. 그런데 Swift의 `receive`는 한 번 부르면 딱 한 개만 가져다준다. 그래서 앱에서는 하나를 받아 처리한 뒤에 `receive`를 **다시 불러줘야** 다음 메시지도 들어온다. 이 차이 때문에 앱 쪽 코드가 브라우저보다 한 겹 더 필요해진다.

주소를 `location.host`로 잡은 건 이 페이지를 내려준 서버와 같은 곳에 붙기 위해서다. 포트를 바꾸거나 나중에 배포해도 이 줄은 그대로 둘 수 있다.

주고받는 글자 모양은 일단 제일 단순하게 잡았다. `해롤드: 안녕하세요`처럼 이름과 내용을 콜론으로 붙인 한 줄짜리 글자다. 이러면 서버는 받은 글자를 그대로 다시 뿌리기만 하면 되고, 누가 보냈는지 알아내는 일은 받는 쪽에서 콜론 앞을 잘라내면 끝난다.

```javascript
// public/index.html
function encodeMessage(nickname, text) {
  return `${nickname}: ${text}`;
}

function decodeMessage(raw) {
  const at = raw.indexOf(":");
  if (at === -1) return { sender: "", text: raw };
  return { sender: raw.slice(0, at).trim(), text: raw.slice(at + 1).trim() };
}
```

나중에 JSON으로 바꾸고 싶어지면 이 두 함수만 고치면 되도록 따로 빼뒀다.

지금 이 페이지에서 연결 버튼을 누르면 빨간 불이 켜지면서 연결이 끊겼다고 나온다. 서버에 WebSocket 경로가 아직 없으니 당연한 결과다. 반대로 말하면 연결 실패를 감지하는 부분은 제대로 동작한다는 뜻이다.

## iOS 앱은 화면부터

앱은 아직 통신 코드를 넣지 않고 화면만 세웠다. 이름을 적는 화면, 채팅방, 말풍선, 입력창, 연결 상태를 알려주는 띠까지다. 가짜 데이터를 넣어두면 화면 흐름은 전부 확인할 수 있다.

통신을 담당할 자리는 껍데기만 만들어뒀다.

```swift
// ChatSocketClient.swift
final class ChatSocketClient {
    /// 서버에서 메시지가 도착했을 때 불린다.
    var onMessageReceived: ((ChatMessage) -> Void)?
    /// 연결 상태가 바뀔 때마다 불린다.
    var onStateChanged: ((ConnectionState) -> Void)?

    private var task: URLSessionWebSocketTask?

    func connect(nickname: String) {
        // 생략
    }

    func send(text: String) {
        // 생략
    }

    private func receiveNext() {
        // 생략
    }
}
```

`receiveNext`라는 이름을 붙인 건 앞에서 말한 차이 때문이다. 하나를 받아 처리한 뒤에 이 함수를 다시 불러줘야 그다음 메시지가 들어오니, 그걸 잊지 않으려고 이름에 남겨뒀다.

앱에서 붙을 주소도 상수 하나로 빼뒀다.

```swift
// ChatSocketClient.swift
static let defaultServerURL = URL(string: "ws://127.0.0.1:8080/chat")!
```
