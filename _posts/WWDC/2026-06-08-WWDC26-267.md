## 한 줄 요약

XCTest 를 한 번에 갈아엎지 말고, **새 테스트만 Swift Testing 으로 쓰면서 기존 helper 는 test framework interoperability 로 그대로 재사용하라**는 세션이다. 그 과정에서 두 framework 가 섞여 생기는 문제를 얼마나 엄격하게 다룰지는 mode 로 고른다.

세션은 Swift Testing 기초 복습, 마이그레이션 전략, interoperability 와 mode, 자주 나오는 변환 패턴, 그리고 옮기고 나서 얻는 두 가지 도구 (parameterized test, exit test) 순서로 진행된다.

## Swift Testing 기초

Swift Testing 은 Xcode 16 에서 처음 나온 테스트 라이브러리다. Swift concurrency 를 전제로 만들어져서 test case 를 병렬로 돌리고 결과를 빨리 돌려준다. 세션은 XCTest 와 비교하면서 기본 구성 요소를 먼저 훑는다.

```swift
import Testing

@testable import DemoApp

@Test func `Default climate: tropical`() async throws {
    let fruit = Fruit(name: "Coconut")
    #expect(fruit.climate == .tropical)
}
```

`Fruit` 은 세션에 정의가 없어서 `name` 과 `climate` property 를 가진 struct 로 직접 만들었다.

#### Test 와 expect 로 테스트 만들기

- `@Test`: 함수를 테스트로 선언한다. XCTest 처럼 `XCTestCase` class 안에 넣거나 이름을 `test` 로 시작할 필요가 없다
- `#expect`: 조건이 참이기를 기대한다. 실패하면 양쪽 값을 풀어서 보여 준다
- 함수 이름의 backtick: Swift 의 raw identifier 다. 공백과 문장부호를 넣을 수 있어서 긴 테스트 이름을 문장처럼 쓸 수 있다

`#expect` 하나가 XCTest 의 assertion 여러 개를 대신한다.

| XCTest | Swift Testing |
|---|---|
| `XCTFail` | `Issue.record(...)` |
| `XCTAssert`, `XCTAssertTrue`, `XCTAssertFalse` | `#expect(...)` |
| `XCTAssertNil`, `XCTAssertNotNil` | `#expect(...)` |
| `XCTAssertEqual`, `XCTAssertNotEqual` | `#expect(...)` |
| `XCTAssertIdentical`, `XCTAssertNotIdentical` | `#expect(...)` |
| `XCTAssertGreaterThan`, `XCTAssertLessThanOrEqual` 등 비교 계열 | `#expect(...)` |

조건 없이 무조건 실패시키는 `XCTFail` 만 [`Issue.record`](https://developer.apple.com/documentation/testing/issue){:target="_blank"} 로 바뀐다.

다만 **XCTest 를 계속 써야 하는 경우**가 있다.

- UI automation 테스트: 관련 API 가 XCTest 에만 있다
- performance 테스트: 마찬가지다
- Objective-C exception 을 던지는 코드의 테스트: Objective-C 로 쓴 XCTest 여야 한다. Swift 코드는 Swift 로 쓴 XCTest 를 포함해서 이 exception 을 안전하게 처리할 수 없다

기초가 더 필요하면 WWDC24 의 [Meet Swift Testing](https://developer.apple.com/videos/play/wwdc2024/10179/){:target="_blank"} 을 보라고 안내한다.

## 마이그레이션 전략

세션의 전략은 "조금씩" 이다. 오래된 테스트는 작은 수정에도 위험이 따른다. 테스트가 깨진 건지 테스트 대상이 깨진 건지 헷갈리는 상황이 생기기 때문이다. 그래서 다음 원칙을 세운다.

- 기존 XCTest 대부분은 **그대로 둔다**
- 준비됐을 때 몇 개씩 옮기고, **자주 고치는 테스트부터** 옮긴다
- **새 테스트는 Swift Testing 으로** 쓴다

이것이 가능한 이유는 한 test target 에 두 framework 의 테스트가 같이 들어갈 수 있기 때문이다. 같은 파일에 있어도 된다. 제약은 하나다. `@Test` 함수는 `XCTestCase` class 안에 넣을 수 없다.

데모 앱은 동네 새들에게 과일 배달을 훈련시키는 앱이다. `Fruit` 에 최근 climate 정보를 추가했는데 아직 테스트가 없다. XCTest suite 가 있는 파일을 그대로 열어서 `import Testing` 을 추가하고, 파일 끝에 위의 `@Test` 함수를 붙인다. suite 밖에 둬도 되고, 테스트가 늘어나면 나중에 suite 로 묶으면 된다. Test navigator 에 새 테스트가 바로 나타나고 실행하면 통과한다.

---

### helper 를 쓰는 테스트

문제는 준비 과정이 긴 테스트다. 과일 배열의 이름이 모두 고유한지 확인하는 테스트가 있다. 원래는 assertion 을 만들기 위한 코드가 테스트 본문에 여러 줄 들어 있었고, 실패했을 때 왜 실패했는지 읽기 어려웠다. 그래서 여러 단계짜리 assertion 을 helper 함수로 뽑아냈다.

```swift
func testUniqueFruitNames() async throws {
    assertUnique(Market.fruits + [Fruit.lychee])
}

// TestHelpers.swift

func assertUnique(_ fruits: [Fruit], file: StaticString = #filePath, line: UInt = #line) {
    var uniqueNames = Set<String>()
    for name in fruits.map(\.name) {
        if !uniqueNames.insert(name).inserted {
            XCTFail("Duplicate name: \(name)", file: file, line: line)
        }
    }
}
```

`file` 과 `line` 을 받아서 `XCTFail` 에 넘기는 것은 실패 위치를 helper 안이 아니라 **helper 를 부른 줄**로 표시하기 위해서다.

`Market.fruits` 는 세션에 정의가 없어서, lychee 를 포함한 과일 세 개짜리 배열로 만들었다. 거기에 lychee 를 하나 더 붙이니 이 테스트는 실패하는 것이 정상이다.

이제 Swift Testing 으로 새 테스트를 쓰면서 이 helper 를 부르고 싶다. 그런데 helper 가 결국 부르는 `XCTFail` 은 Swift Testing 의 API 가 아니다. 여기서 test framework interoperability 가 나온다.

## test framework interoperability

test framework interoperability 는 **한 framework 의 테스트 본문 안에서 다른 framework 의 API 를 안전하게 부를 수 있게** 해 주는 기능이다.

---

### cross-framework issue 란?

방향은 두 가지다.

![가운데 위쪽 화살표에는 XCTFail in Swift Testing, 아래쪽 화살표에는 Issue.record in XCTest 라고 적혀 있고, XCTest 아이콘과 Swift Testing 아이콘 사이를 양방향으로 잇는 그림](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-267/wwdc26-267-interop-directions.png)

출처: WWDC26 - Migrate to Swift Testing

- **XCTest API 를 Swift Testing 테스트 안에서** 부른다. `XCTFail` 을 감싼 `assertUnique` 를 `@Test` 함수에서 재사용하는 경우다
- **Swift Testing API 를 XCTest 안에서** 부른다. `XCTestCase` 의 메서드에서 `#expect` 나 `Issue.record` 를 쓰는 경우다

어느 쪽이든 **issue 를 보고한 API 와 그 API 가 불린 테스트가 서로 다른 framework 에 속한다.** 세션은 이것을 cross-framework issue 라고 부른다. 식당으로 치면 한식당 주방에 들어온 양식 주문서다. 처리할 사람이 없으면 이 주문서는 조용히 버려진다. interoperability 를 끄고 돌려 보면 실제로 그렇다. Swift Testing 테스트 안에서 `XCTFail` 이 불려도 아무 메시지 없이 테스트가 통과한다. Xcode 27 은 interoperability 를 기본으로 켜서 이 주문서를 처리한다.

---

### limited mode

같은 본문을 가진 Swift Testing 테스트를 하나 더 만든다.

```swift
@Test func `Unique fruit names`() async throws {
    assertUnique(Market.fruits + [Fruit.lychee])
}
```

이 테스트는 세션 Code 탭에는 없고 영상 화면에 나온 것을 옮겼다. 위의 XCTest 와 똑같이 실패할 것 같지만, 돌려 보면 **통과**한다. 대신 메시지가 두 개 붙는다.

![Xcode 에서 Unique fruit names 테스트 옆에 통과 표시가 있고, 그 아래 보라색 삼각형 경고 두 개 (Duplicate name: Lychee, XCTFail 을 Issue.record 로 바꾸라는 안내) 가 펼쳐진 화면](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-267/wwdc26-267-limited-warnings.png)

출처: WWDC26 - Migrate to Swift Testing

보라색 삼각형은 warning 이다. 에러가 아니라서 테스트는 통과한다. 첫 번째는 Lychee 가 중복이라는 원래의 실패 내용이고, 두 번째는 `XCTFail` 을 Swift Testing 의 `Issue.record` 로 바꾸라는 안내다.

이것이 **limited mode** 다. XCTest 쪽에서 온 cross-framework issue 를 warning 으로 낮춰서 보고한다. `swift test` 로 돌려도 같은 결과가 나온다.

```
Test "Unique fruit names" recorded a warning at FruitTests.swift:17:1: Issue recorded
Test "Unique fruit names" recorded a warning at FruitTests.swift:17:1: An API was misused
Replace XCTest API such as 'XCTAssert' with a Swift Testing equivalent such as '#expect'.
Test "Unique fruit names" passed after 0.001 seconds with 2 warnings.
```

### interoperability mode

mode 는 네 가지다. 세션은 이렇게 한 장으로 정리한다.

![interoperability mode 표. Swift Testing 테스트 안의 XCTFail 은 None 에서 무시, Limited 에서 보라색 경고, Complete 에서 빨간 에러, Strict 에서 fatal error 이고, XCTest 안의 Issue.record 는 None 을 뺀 모든 mode 에서 빨간 에러다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-267/wwdc26-267-interop-modes.png)

출처: WWDC26 - Migrate to Swift Testing

| mode | Swift Testing 안의 XCTest API 실패 | XCTest 안의 Swift Testing API 실패 |
|---|---|---|
| none | 보고하지 않음 | 보고하지 않음 |
| limited | warning (테스트 통과) | error |
| complete | error (테스트 실패) | error |
| strict | fatal error (그 자리에서 중단) | error |

각 mode 의 쓰임새는 이렇다.

- **limited**: Xcode 27 이전에 만든 test plan 이 물려받는 mode 다. 기존 프로젝트가 갑자기 실패하지 않게 한다
- **complete**: 새 프로젝트의 기본값이다. `XCTFail` 이 만든 error 를 그대로 유지하고, 옮기라는 warning 도 같이 보여 준다. limited 보다 한 단계 위라고 보면 된다. 놓치기 쉬운 warning 을 error 로 올린다
- **strict**: complete 보다 한 단계 더 위다. XCTest 쪽 cross-framework issue 가 생기면 fatal error 로 테스트를 멈춘다. 데모에서는 helper 안의 `XCTFail` 을 부르는 바로 그 줄에서 멈췄다. **XCTest API 를 Swift Testing API 로 바꿔야 할 자리를 찾는 용도**다
- **none**: interoperability 를 끈다. 양방향 모두 보고하지 않는다. cross-framework issue 는 실제 버그를 드러낼 수 있으니, 써야 한다면 잠깐만 쓰라고 한다

표의 오른쪽 열이 중요하다. **Swift Testing API 가 만든 issue 는 none 을 뺀 모든 mode 에서 error 다.** 그래서 helper 를 Swift Testing API 로 써 두면 어느 framework 의 테스트에서 불러도 제대로 실패한다. 세션의 권장은 complete 또는 strict 다.

Xcode 에서는 Test Plan 의 Settings 중 Test Execution 영역에서 mode 를 바꾼다. 데모에서는 설정 검색창에 interoperability 를 입력해서 찾았다.

> Test Plan 설정 화면, 보라색 warning 표시, strict mode 에서 debugger 가 멈추는 위치는 Xcode 화면에서만 볼 수 있다. 같은 동작을 Swift package 에서 `swift test` 로 확인한 결과가 아래에 있다.

### Swift package 에서의 mode

Swift package 에서도 같은 기능을 쓴다. 기본 mode 는 `swift-tools-version` 에 따라 갈린다.

- `swift-tools-version: 6.3` 이하: Swift 6.4 toolchain 이 **limited** 를 쓴다
- `swift-tools-version: 6.4` 이상: **complete** 를 쓴다

환경 변수로 언제든 덮어쓸 수 있다. 값은 mode 이름을 소문자로 쓴다.

```bash
SWIFT_TESTING_XCTEST_INTEROP_MODE=strict swift test
```

위의 `Unique fruit names` 테스트로 네 가지를 모두 돌려 봤다. 세션 설명과 전부 일치했다.

| 설정 | 결과 |
|---|---|
| tools-version 6.3, 환경 변수 없음 | warning 2개, 테스트 통과 |
| tools-version 6.4, 환경 변수 없음 | issue 1개와 warning 1개, 테스트 실패 |
| `complete` | tools-version 6.4 와 같음 |
| `strict` | fatal error 로 test process 가 signal 5 로 종료 |
| `none` | 아무 메시지 없이 통과 |

strict 의 메시지는 이렇게 나온다.

```
Fatal error: Replace XCTest API such as 'XCTAssert' with a Swift Testing equivalent such as '#expect'.
This is a fatal error because strict interop mode is active (SWIFT_TESTING_XCTEST_INTEROP_MODE=strict)
```

### helper 를 Swift Testing API 로 바꾸기

strict mode 가 알려 준 자리를 고친다. 아직 이 helper 를 부르는 XCTest 가 남아 있지만 괜찮다. 앞에서 본 것처럼 Swift Testing API 가 만든 issue 는 XCTest 안에서도 error 로 보고된다.

```swift
import Testing

func assertUnique(_ fruits: [Fruit], sourceLocation: SourceLocation = ...) {
    var uniqueNames = Set<String>()
    for name in fruits.map(\.name) {
        if !uniqueNames.insert(name).inserted {
            Issue.record("Duplicate name: \(name)", sourceLocation: sourceLocation)
        }
    }
}
```

#### Issue.record 와 sourceLocation 으로 실패 위치 넘기기

바꾼 곳은 세 군데다.

- `import XCTest` 를 `import Testing` 으로 바꾼다
- `XCTFail(...)` 을 `Issue.record(...)` 로 바꾼다
- `file` 과 `line` 두 parameter 를 `sourceLocation` 하나로 바꾼다. [`SourceLocation`](https://developer.apple.com/documentation/testing/sourcelocation){:target="_blank"} 은 파일, 줄, 열을 한 값으로 묶은 타입이다

세션 코드는 기본값을 `...` 로 줄여 놓았다. 빌드할 때는 `#_sourceLocation` 을 넣었다. 호출한 위치를 `SourceLocation` 으로 만들어 주는 macro 다.

고친 뒤 전체 테스트를 다시 돌리면 **두 테스트가 모두 실패**한다. 원하던 결과다.

```
FruitTests.swift:7: error: -[DemoAppTests.FruitTests testUniqueFruitNames] : Issue recorded: Duplicate name: Lychee
Test "Unique fruit names" recorded an issue at FruitTests.swift:17:17: Issue recorded
Duplicate name: Lychee
```

첫 줄은 XCTest 가 `Issue.record` 를 자기 실패로 받은 것이고, 아래는 Swift Testing 테스트의 실패다. 테스트의 의미는 바꾸지 않고 XCTest API 만 Swift Testing API 로 갈아 끼웠다.

---

### 지원하는 API

interoperability 가 모든 API 를 이어 주는 것은 아니다. 지원 범위는 다음과 같다.

| XCTest | Swift Testing |
|---|---|
| `XCTFail` | `Issue.record(...)` |
| 그 밖의 모든 `XCTAssert...` assertion | `#expect(...)`, `try #require(...)` |
| (assertion 실패를 known 으로 표시) | `withKnownIssue { ... }` |
| (XCTest 의 test case 를 skip) | `Test.cancel(...)` |

아래 두 줄은 Swift Testing API 가 XCTest 쪽에 작용하는 경우다. `withKnownIssue` 로 감싼 `XCTAssertEqual(1, 2)` 를 `XCTestCase` 안에서 돌려 보니 `Expected failure` 로 기록되고 테스트는 통과했다.

## 자주 나오는 변환 패턴

옮기다 보면 반복해서 만나는 패턴이 있다. 세션은 두 가지를 짚는다.

---

### 테스트 건너뛰기

XCTest 에서는 `XCTSkip` 계열 API 로 테스트를 건너뛴다. Swift Testing API 로 바꾸면 `Test.cancel` 이다.

```swift
let isFall = false

// XCTest
func testSwallowFallMigration() async throws {
    try XCTSkipIf(!isFall, "Wrong season for migration")
    // ...
}

// Test.cancel interoperability from Swift Testing
func testSwallowFallMigration() async throws {
    if !isFall {
        try Test.cancel("Wrong season for migration")
    }
    // ...
}

// ✅ Prefer test trait in Swift Testing
@Test(.enabled(if: isFall, "Wrong season for migration"))
func `Swallow fall migration`() async throws {
   // ...
}
```

#### enabled trait 로 실행 조건을 본문 밖에 두기

세 버전은 단계다.

- 첫 번째는 원래의 XCTest 다
- 두 번째는 `XCTestCase` 안에 그대로 둔 채 API 만 `Test.cancel` 로 바꾼 것이다. interoperability 덕분에 XCTest 에서도 skip 으로 처리된다
- 세 번째는 Swift Testing 으로 완전히 옮긴 것이다. `Test.cancel` 은 Swift Testing 에서도 동작하지만, 세션은 **trait** 를 권한다

trait 는 테스트 함수나 suite 에 붙이는 annotation 이다. [`.enabled(if:)`](https://developer.apple.com/documentation/testing/trait/enabled%28if:_:sourcelocation:%29){:target="_blank"} 나 `.disabled` 를 쓰면 실행 조건이 테스트 본문 밖으로 나온다. 본문은 검증만 남고, 왜 안 도는지는 선언만 봐도 알 수 있다.

두 XCTest 버전은 함수 이름이 같아서 하나의 이름을 바꿔 한 class 에 넣고 돌렸다. 세 가지 모두 skip 으로 보고됐다.

```
Test Case '-[DemoAppTests.MigrationTests testSwallowFallMigrationSkip]' skipped (0.001 seconds).
Test Case '-[DemoAppTests.MigrationTests testSwallowFallMigration]' skipped (0.001 seconds).
Test "Swallow fall migration" skipped: "Wrong season for migration"
```

---

### 실패하면 멈추기

XCTest 에서는 `continueAfterFailure` 를 `false` 로 두면 첫 실패에서 테스트가 멈춘다. Swift Testing API 로는 `#require` 를 쓴다.

```swift
func testExample() async throws {
    #expect(Fruit.banana.climate == .temperate)

    try #require(Fruit.banana == Fruit.plantain)
    XCTFail("This is never reached")
}
```

#### require 로 실패 시 테스트 중단하기

[`#require`](https://developer.apple.com/documentation/testing/require%28_:_:sourcelocation:%29-5l63q){:target="_blank"} 는 실패하면 에러를 던져서 테스트를 그 자리에서 끝낸다. 그래서 `try` 가 붙는다. `continueAfterFailure` 는 테스트 전체에 걸리는 스위치였지만, Swift Testing 에서는 **어느 expectation 이 테스트를 멈추고 어느 것은 계속 가는지를 줄마다 고른다.**

위 코드를 `XCTestCase` 안에서 돌리면 `#expect` 실패가 기록되고 다음 줄로 넘어가서, `#require` 실패가 기록된 뒤 멈춘다. 마지막 `XCTFail` 은 출력에 나오지 않았다.

더 많은 변환 사례는 Apple 문서 [Migrating a test from XCTest](https://developer.apple.com/documentation/testing/migratingfromxctest){:target="_blank"} 에 있다. Xcode 의 Coding Assistant 도 이 문서를 알고 있어서 마이그레이션 전략을 세우거나 작업을 검토하는 데 쓸 수 있고, 일부를 자동화하는 skill 도 있다고 한다.

---

### 전략 요약

세션이 중간에 한 번 정리하는 내용이다.

- 준비되기 전까지 XCTest 를 고쳐야 한다는 압박을 느끼지 않는다
- 새 테스트를 Swift Testing 으로 쓰는 데 집중한다
- interoperability 에 기대서 XCTest API 를 감싼 helper 도 재사용한다
- 그 과정에서 드러나는 XCTest 쪽 cross-framework issue 는 Swift Testing API 로 바꿔서 없앤다
- complete 나 strict mode 로 올려서 앞으로 생길 cross-framework issue 를 놓치지 않는다

## 옮기고 나서 얻는 것

마지막 부분은 XCTest 를 쓰지 않는 사람에게도 해당한다. Swift Testing 으로 옮기면 쓸 수 있는 도구 두 가지다.

---

### parameterized test

parameterized test 는 인자를 바꿔 가며 반복하는 테스트다. 인자 하나하나가 독립된 test case 가 되고, 다른 Swift Testing 테스트처럼 기본으로 병렬 실행된다.

데모의 테스트는 모든 새가 날개를 40번부터 100번까지 칠 수 있는지 확인한다. 조합이 너무 많아서 테스트를 따로 쓸 수 없으니, 원래 XCTest 에서는 중첩 loop 로 조합을 만들었다. Swift Testing 으로 옮긴 직후의 모습이다.

```swift
struct BirdTests {

    @Test func `Birds flap wings successfully`() async throws {
        for bird in Aviary.birds {
            for count in (40...100) {
                try await bird.flapWings(count: count)
            }
        }
    }

}
```

돌려 보면 두 가지가 걸린다. 조합이 많아서 오래 걸리고, 실패는 하는데 **어느 새가 실패했는지 알 수 없다.** XCTest 였다면 에러를 직접 catch 하거나 debugger 를 붙여야 했다.

```swift
struct BirdTests {

    @Test(arguments: Aviary.birds, 40...100)
    func `Birds flap wings successfully`(bird: Bird, count: Int) async throws {
        try await bird.flapWings(count: count)
    }

}
```

#### arguments 로 조합마다 test case 만들기

loop 를 본문에서 지우고, `bird` 와 `count` 를 함수 parameter 로 받는다. 입력은 `@Test(arguments:)` 에 collection 두 개로 준다. Swift Testing 은 **첫 번째의 모든 원소와 두 번째의 모든 원소를 짝지어** test case 를 만든다.

데모에서는 테스트가 거의 즉시 끝났다. Test navigator 에서는 테스트 왼쪽에 펼침 화살표가 생기고, 누르면 모든 조합이 따로 나온다.

![Xcode Test navigator 에 Birds flap wings successfully 테스트 아래로 새 이름과 횟수 조합이 한 줄씩 길게 나열된 화면. 대부분 통과 표시이고 편집기에는 Insufficient Airspeed 에러가 표시돼 있다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-267/wwdc26-267-parameterized-navigator.png)

출처: WWDC26 - Migrate to Swift Testing

실패한 결과만 필터링하면 원인이 바로 보인다. 데모에서는 swallow 가 43번 미만으로는 날개를 못 치는 것이었다. 결과가 빨라졌고, **어느 입력이 실패했는지가 분명해졌다.**

`Bird` 와 `Aviary` 는 세션에 정의가 없다. 새 세 마리를 만들고 그중 swallow 만 43번 미만에서 에러를 던지게 해서 같은 상황을 재현했다. 결과는 이렇다.

```
Test "Birds flap wings successfully (loop)" recorded an issue: Caught error: FlapError(bird: "Swallow", count: 40)
Test "Birds flap wings successfully" recorded an issue with 2 arguments bird → Swallow, count → 40
Test "Birds flap wings successfully" recorded an issue with 2 arguments bird → Swallow, count → 41
Test "Birds flap wings successfully" recorded an issue with 2 arguments bird → Swallow, count → 42
Test "Birds flap wings successfully" with 183 test cases failed after 0.003 seconds with 3 issues.
```

loop 버전은 첫 실패에서 에러가 던져져 끝나기 때문에 40 하나만 보인다. parameterized 버전은 183개 (3마리 × 61가지) 를 전부 돌려서 실패한 세 조합을 인자와 함께 알려 준다. 이 예제는 동작이 너무 가벼워서 속도 차이는 드러나지 않았다.

### exit test

exit test 는 **crash 해야 맞는 코드**를 테스트한다. macOS, Linux, FreeBSD, Windows 에서만 지원한다. iOS 는 목록에 없다.

`Bird` 의 initializer 에는 이름이 비어 있으면 프로그램을 멈추는 검사가 있다.

```swift
// In `Bird.init(...)`
if name.isEmpty {
    preconditionFailure("Bird name cannot be empty")
}
```

Xcode 의 Editor 메뉴에서 Code Coverage 를 켜면 이 줄이 빨갛게 표시된다. 어떤 테스트도 이 코드를 실행하지 않는다는 뜻이다. 보통의 테스트로는 실행할 방법이 없다. 실행하는 순간 test process 가 같이 죽기 때문이다.

```swift
extension BirdTests {

    @Test func `Bird with empty name crashes`() async throws {
        await #expect(processExitsWith: .failure) {
            _ = Bird(name: "")
        }
    }

}
```

#### expect processExitsWith 로 crash 검증하기

exit test 는 `#expect` 에 기대하는 process 종료 조건과 본문을 주는 형태다. 여기서는 `.failure`, 곧 비정상 종료를 기대한다.

![왼쪽 Main test process 안에 exitTest 와 다른 테스트 a, b 가 있고, exitTest 의 본문이 오른쪽 Exit test process 로 분리돼 그 안에서 preconditionFailure 가 발생하는 그림](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-267/wwdc26-267-exit-test-process.png)

출처: WWDC26 - Migrate to Swift Testing

동작은 그림과 같다.

1. Swift Testing 이 exit test 의 본문을 **child process 에서** 실행한다
2. 그 코드는 격리돼 있어서 crash 해도 다른 테스트에 영향을 주지 않는다
3. exit test 는 child process 가 끝나기를 기다렸다가 exit status 를 보고 성공과 실패를 판단한다

child process 를 기다려야 하니 `await` 가 붙는다. 더 자세한 사용법은 [Exit testing](https://developer.apple.com/documentation/testing/exit-testing){:target="_blank"} 문서에 있다.

`swift test` 로 돌렸을 때 이 테스트는 통과했다. 데모에서는 통과 후 coverage 표시가 초록색으로 바뀌는 것까지 보여 준다.

## 정리

핵심만 다시 모으면 이렇다.

- **다 옮기지 않는다**: XCTest 는 그대로 두고 새 테스트만 Swift Testing 으로 쓴다. 한 target, 한 파일에 같이 둘 수 있다
- **XCTest 를 남겨야 하는 것**: UI 테스트, performance 테스트, Objective-C exception 테스트
- **cross-framework issue**: issue 를 보고한 API 와 테스트의 framework 가 다른 경우다. Xcode 27 부터 기본으로 처리된다
- **mode 네 가지**: none, limited, complete, strict. 기존 test plan 과 tools-version 6.3 이하 package 는 limited, 새 프로젝트와 6.4 이상은 complete 다
- **limited 의 함정**: Swift Testing 테스트 안의 `XCTFail` 은 warning 이라 **테스트가 통과한다.** 초록불을 믿으면 안 된다
- **helper 는 Swift Testing API 로**: `Issue.record` 와 `#expect` 는 어느 mode 든 양쪽 framework 에서 error 다
- **패턴**: `XCTSkip` 은 `.enabled` trait 로, `continueAfterFailure = false` 는 `#require` 로 바꾼다
- **얻는 것**: parameterized test 로 조합별 결과와 병렬 실행, exit test 로 crash 경로의 coverage

실제 프로젝트에 가져갈 점도 적어 둔다.

- 기존 test plan 을 가진 프로젝트를 Xcode 27 로 열면 limited 로 시작한다. XCTest helper 를 `@Test` 에서 부르고 있다면 통과로 보이는 테스트에 warning 이 숨어 있을 수 있다. 먼저 complete 로 올려서 확인하는 것이 순서다
- CI 에서 `swift test` 를 쓰는 package 는 `SWIFT_TESTING_XCTEST_INTEROP_MODE=strict` 로 한 번 돌리면 바꿔야 할 자리가 바로 나온다
- RunWay 처럼 iOS 가 대상인 앱에서는 exit test 를 쓸 수 없다. `precondition` 경로를 검증하려면 그 로직을 macOS 에서도 빌드되는 Swift package 로 빼야 한다
- 페이스 계산이나 거리 변환처럼 입력 조합이 많은 순수 함수는 parameterized test 가 가장 잘 맞는 자리다
