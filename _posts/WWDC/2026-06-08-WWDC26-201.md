## 한 줄 요약

App Attest 는 Secure Enclave 에 묶인 key 를 Apple 이 보증해 주는 attestation 과, 그 key 로 요청마다 서명하는 assertion 으로 이루어진다. server 는 이것을 검증해서 요청이 진짜 Apple 기기에서 도는 수정되지 않은 내 앱에서 왔는지를 판단한다. 올해는 macOS 27 지원, key access control property, authenticator data 의 extensions (launch validation category 와 bundle version) 가 더해졌다. 세션이 여러 번 강조하는 것은 이 신호들을 사용자를 바로 차단하는 스위치로 쓰지 말고 risk assessment 의 재료로 쓰라는 점이다.

## App Attest 가 막으려는 위협

앱은 Apple platform 의 안전한 환경에서 동작하도록 만들어 배포한다. 하지만 사기를 치려는 쪽은 앱이 의도한 기능 밖에서 앱을 악용할 방법을 늘 찾는다. 세션은 두 가지 시나리오를 든다.

첫째는 변조된 앱이 그럴듯해 보이는 요청을 server 에 보내 민감한 data 에 접근하는 경우다. 학생이 퀴즈를 풀고 답을 제출하는 시험 감독 앱을 만들었다고 하자. 누군가 앱을 reverse engineering 해서, 조작한 답안을 server 에 제출하는 수정본을 만들 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-threat-requests.png)
출처: WWDC26 - Secure your apps with App Attest

둘째는 내가 배포하지 않은 내용을 앱에 넣는 경우다. source code 나 resource bundle 을 직접 고치고, 앱을 다시 서명한 다음, 수정본을 기기에서 실행한다. dragon slayer game 에 능력치를 올려 주는 cheat menu 를 심어서, 조작된 점수를 server 에 제출하고 leaderboard 맨 위로 올라가는 식이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-threat-modify.png)
출처: WWDC26 - Secure your apps with App Attest

App Attest 는 이런 위협을 다루려고 만든 것이다. server 가 수정된 client 에서 온 요청을 거절할 수 있게 해 준다.

## App Attest 의 세 가지 보호

App Attest 가 앱을 지키는 방식은 세 갈래다. 정품 hardware 인지 확인하고, 앱이 수정되었는지 알려 주고, server 로 가는 payload 를 보호한다.

---

### App Attest 란?

App Attest 는 [DeviceCheck](https://developer.apple.com/documentation/devicecheck){:target="_blank"} framework 에 들어 있는 service 다. 앱이 기기에서 key 를 만들고, Apple 이 그 key 에 대한 attestation 을 발급하고, 개발자의 server 가 그것을 검증하는 구조로 되어 있다. 앱 쪽 API 는 [DCAppAttestService](https://developer.apple.com/documentation/devicecheck/dcappattestservice){:target="_blank"} 하나에 모여 있고, 전체 그림은 문서의 [Establishing your app's integrity](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity){:target="_blank"} 에 있다.

---

### 정품 Apple hardware

App Attest 는 앱이 진짜 Apple hardware 에서 돌고 있다는 것을 확인하게 해 준다. 방법은 attestation 을 발급하는 것이다. attestation 은 사용자 기기에서 도는 앱이 유효하다는 것에 대한 cryptographic 증명이다. server 가 이것을 검증하면, 앱이 안전한 Apple 기기에서 돌고 있다고 믿을 근거가 생긴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-genuine-hardware.png)
출처: WWDC26 - Secure your apps with App Attest

### 앱 수정의 탐지

App Attest 는 사용자 기기에 있는 앱이 수정되었는지를 알 수 있게 해 준다. 앱과 관련된 세 가지 정보를 드러낸다. relying party, launch validation category, bundle version 이다.

앱은 relying party identifier 로 식별된다. Apple developer provisioning profile 의 Team Identifier 와 앱의 bundle identifier 를 이어 붙인 것이다. 누군가 앱을 수정하고 내 Team Identifier 와 맞지 않는 provisioning profile 로 다시 서명하면, App Attest 가 드러내는 앱 identity 가 달라지므로 허가받지 않은 수정을 알아챌 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-detect-rpid.png)
출처: WWDC26 - Secure your apps with App Attest

iOS 27 에서 새로 생긴 것이 launch validation category 다. 사용자 기기에서 앱이 어떤 경로로 검증되어 실행되었는지를 알려 준다. 앱을 App Store 로 배포했는데 App Attest 가 TestFlight 라고 알려 온다면 이상한 일이다. slide 는 정상 앱에 `4 (App Store)`, 수정본에 `2 (TestFlight)` 를 적어 놓았다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-detect-launch.png)
출처: WWDC26 - Secure your apps with App Attest

bundle version 도 함께 알려 준다. 누군가 내가 모르는 bundle version 으로 앱을 다시 서명했다면 App Attest 를 통해 드러난다. slide 의 예는 내가 배포한 `2.0.1` 과 수정본의 `4.1.2` 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-detect-bundle.png)

### payload 의 보호

마지막으로 앱에서 server 로 가는 payload 를 보호할 수 있다. App Attest 는 앞서 발급받은 attestation 의 cryptographic 속성을 써서 assertion 을 만든다. server 는 앱이 보낸 payload 에 붙은 assertion 을 검증해서, payload 가 전송 중에 변조되지 않았음을 확인한다.

## 지원 platform 과 isSupported

App Attest 는 모든 Apple platform 에서 지원된다. 세션에 따르면 이전에는 지원되지 않던 macOS 가 macOS 27 부터 포함된다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-availability.png)
출처: WWDC26 - Secure your apps with App Attest

표는 platform 마다 앱, app extension, App Clip 의 세 칸으로 되어 있다. 다섯 platform 모두 앱에서는 쓸 수 있다. app extension 은 iOS 에서만 일부 지원되고 나머지 platform 에서는 지원되지 않는다. App Clip 은 iOS 에서 지원된다. 주요 OS 에서 모두 쓸 수 있다고 해도 그 platform 의 모든 앱 형태에서 쓸 수 있는 것은 아니라는 뜻이다. 세션이 드는 예는 Action extension 과 SSO extension 이다. 이 둘에서는 쓸 수 있고, 다른 종류의 app extension 에서는 쓸 수 없다.

그래서 App Attest 를 쓰는 code 는 `isSupported` 로 감싼다.

```swift
import DeviceCheck

func makeKey() async throws -> String? {
  guard DCAppAttestService.shared.isSupported else { return nil }
  let keyID = try await DCAppAttestService.shared.generateKey()
  return keyID
}
```

세션 snippet 은 `generateKey()` 를 부르는 한 줄이다. 세션이 말로 설명한 `isSupported` 확인을 내가 앞에 붙이고 함수로 감쌌다.

#### isSupported

[isSupported](https://developer.apple.com/documentation/devicecheck/dcappattestservice/issupported){:target="_blank"} 는 현재 기기와 실행 환경에서 App Attest service 를 쓸 수 있는지를 알려 주는 Bool property 다.

`isSupported` 의 값은 fraud signal 로도 쓸 수 있다. 지원되는 platform 에만 앱을 배포했는데 어떤 사용자에게서 지원되지 않는다는 응답이 갑자기 늘어난다면 변조를 의심해 볼 수 있다. 이 값을 risk assessment 에 넣는다. 그리고 App Attest 가 지원되지 않을 때 사용자가 앱 기능을 계속 쓰게 할지는 개발자가 정해야 한다.

macOS 에 대해서는 하나 확인한 것이 있다. Xcode 27.0 의 macOS SDK header 에는 `DCAppAttestService` 가 macOS 11.0 부터 available 로 표시되어 있고, 위 code 는 deployment target 을 macOS 26 으로 낮춰도 type check 를 통과한다. API 자체는 전부터 있었고, 달라지는 것은 실행했을 때의 `isSupported` 값이라고 이해하면 된다. macOS 27.0.1 에서 서명된 앱 bundle 이 아닌 command line tool 로 `isSupported` 를 찍어 보면 `false` 가 나온다.

## key 생성

App Attest 흐름의 첫 단계는 key ID 를 만드는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-keygen.png)
출처: WWDC26 - Secure your apps with App Attest

1. 앱이 App Attest 에 key 생성을 요청한다.
2. App Attest 가 앱을 대신해 Secure Enclave 에 묶인 key pair 를 만든다. private key 는 Secure Enclave 안에 머문다.
3. App Attest 가 public key 의 hash 를 앱에 돌려준다. 이것이 key ID 다.
4. 앱이 key ID 를 Keychain 에 저장한다.

#### generateKey()

[generateKey(completionHandler:)](https://developer.apple.com/documentation/devicecheck/dcappattestservice/generatekey%28completionhandler:%29){:target="_blank"} 는 Secure Enclave 에 새 key pair 를 만들고 그 key 의 identifier 를 돌려주는 method 다. Swift 에서는 `async throws -> String` 형태로 부른다.

key 를 다룰 때의 원칙은 세 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-keygen-practices.png)
출처: WWDC26 - Secure your apps with App Attest

- account 가 있는 앱이면 사용자마다 key 하나, 아니면 기기에 설치된 앱 전체에 key 하나를 만든다. 사용자들 사이에 key 를 공유하지 않는다.
- 앱이 만든 key ID 는 [Keychain](https://developer.apple.com/documentation/security/keychain-services){:target="_blank"} 에 저장한다.
- key ID 는 앱이 설치되어 있는 동안 유효하다. 앱 update 에는 살아남지만, 사용자가 앱을 다시 설치하거나 기기를 복원하면 (iCloud backup 에서의 복원 포함) key 가 무효가 된다.

그리고 key 는 기기마다 따로다. 사용자의 여러 기기 사이에 sync 되지 않는다. 이렇게 만든 key 가 attestation 과 assertion 의 바탕이 된다.

## attestation

key ID 가 생겼으면 앱은 App Attest 에 그 key 를 attest 해 달라고 요청할 수 있다. 여기서부터 server 두 곳이 등장한다. 개발자의 server 와 Apple 의 server 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-attestation-flow.png)
출처: WWDC26 - Secure your apps with App Attest

1. 앱이 Keychain 에서 key ID 를 꺼낸다.
2. 앱이 자기 server 에 이 key ID 의 attestation 을 하겠다고 요청한다.
3. server 가 attestation 에 넣을 challenge 를 앱에 내려 준다.
4. 앱이 key ID 와 server challenge 를 넘기며 attestation API 를 부른다.
5. App Attest 가 key ID 에 해당하는 key pair 와 기기의 attestation data 를 가져온다. 이 data 는 Secure Enclave 에서 나온 것이고, boot 시점부터의 기기 hardware 속성 snapshot 을 담고 있다. 수정할 수 없다.
6. App Attest 가 Apple service 에 요청을 보낸다. Apple 은 기기 data 를 검증하고 attestation 을 돌려준다.
7. App Attest 가 attestation object 를 앱에 돌려준다.
8. 앱이 attestation 을 server 에 보낸다. server 는 이것을 검증하고, 저장하고, 앱의 사용자와 연결해 둔다.

앱 쪽 code 는 다음과 같다.

```swift
import DeviceCheck
import CryptoKit
import Foundation

func attest(keyId: String, challenge: Data) async throws -> Data {
  let clientDataHash = Data(SHA256.hash(data: challenge))
  let attestation = try await DCAppAttestService.shared.attestKey(keyId, clientDataHash: clientDataHash)
  return attestation
}
```

세션 snippet 은 `attestKey(keyId: keyId, clientDataHash: clientDataHash)` 로 적혀 있고 `keyId` 와 `clientDataHash` 의 값은 `...` 로 비워 두었다. 이 호출을 그대로 type check 하면 `extraneous argument label 'keyId:' in call` 이라는 error 가 난다. 첫 argument 에는 label 이 없고, slide 에 적힌 signature `func attestKey(_ keyId: String, clientDataHash: Data) async throws -> Data` 가 SDK 와 일치한다. 그래서 label 을 뺐다. `clientDataHash` 를 server challenge 의 SHA-256 hash 로 만드는 줄은 문서의 설명을 따라 내가 채운 것이다.

#### attestKey(_:clientDataHash:)

[attestKey(_:clientDataHash:completionHandler:)](https://developer.apple.com/documentation/devicecheck/dcappattestservice/attestkey%28_:clientdatahash:completionhandler:%29){:target="_blank"} 는 key ID 에 해당하는 key 가 유효하다는 것을 Apple 에 증명해 달라고 요청하고 attestation object 를 돌려주는 method 다. network 요청이 따라붙는다.

attestation 을 받고 다룰 때의 원칙은 네 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-attestation-practices.png)
출처: WWDC26 - Secure your apps with App Attest

- attestation 의 시작은 server 가 통제한다. 그래야 앱 전체의 요청이 초당 요청 수의 안전한 상한 안에 머물도록 할 수 있다.
- attestation 은 실패할 수 있고, 그럴 때 앱은 나중에 다시 시도해야 한다. global rate limit 에 걸리지 않도록 exponential back-off 를 구현한다. Apple 의 attestation server 로 통제할 수 없는 요청 급증이 가지 않도록, retry logic 을 앱에 hard-code 하지 않는다.
- attestation 은 사용자 흐름 밖에서 받는다. 가능하면 background task 에서 수행한다.
- attestation 은 앱이 아니라 항상 server 가 검증한다. 앱이 변조되었다면 그 앱이 한 검증은 믿을 수 없다.

### attestation object 의 구조

attestation API 가 돌려주는 object 는 세 부분으로 되어 있다. format, attestation statement, authenticator data 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-attestation-object.png)
출처: WWDC26 - Secure your apps with App Attest

format 은 Apple 의 anonymized attestation 임을 나타내는 고정 문자열이다.

attestation statement 에는 certificate chain 과 receipt 가 들어 있다. 그림에서 Intermediate 와 Leaf 가 certificate chain 이고 그 아래가 Receipt 다. certificate chain 은 attest 된 key 가 진짜 Apple hardware 에서 만들어졌다는 것을 증명한다. leaf certificate 안에는 nonce, key ID, relying party identifier 가 들어 있고, 검증 절차는 문서 [Validating apps that connect to your server](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server){:target="_blank"} 를 따른다.

receipt 는 App Store receipt 와 비슷한 형식이다. parsing 방법은 문서를 따르고, receipt 안에 들어 있는 relying party ID, attest 된 key, server challenge 를 검증한다. server 는 이 receipt 를 저장해 두어야 한다. 뒤에 나오는 fraud metric 을 조회할 때 쓰기 때문이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-acl-policy.png)
출처: WWDC26 - Secure your apps with App Attest

macOS 에서 App Attest 는 만드는 key 마다 full security mode 와 System Integrity Protection 을 요구하는 policy 를 건다. full security mode 는 가장 높은 수준의 보안을 보장하고 기기의 운영체제가 온전한지를 검증한다. [System Integrity Protection](https://support.apple.com/en-us/102149){:target="_blank"} 은 허가받지 않은 code 의 실행을 막고 system path 를 보호한다. 둘 다 Mac 에서 기본으로 켜져 있다. key access control property 를 검증하면 사용자 기기에서 어떤 보안 조건이 강제되었는지를 확신할 수 있다.

---

### authenticator data 와 extensions

attestation object 의 마지막 부분인 authenticator data 는 앱과 attestation 에 대한 정보를 담는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-authdata.png)
출처: WWDC26 - Secure your apps with App Attest

slide 에 적힌 항목은 relying party ID hash, flags, counter, AAGUID, key ID hash, encoded key, 그리고 extensions 다. 앞의 여섯 개를 풀고 검증하는 방법은 문서 [Attestation Object Validation Guide](https://developer.apple.com/documentation/devicecheck/attestation-object-validation-guide){:target="_blank"} 를 따른다.

iOS 27 부터 authenticator data 의 끝에 extensions 라는 새 구조가 붙는다. Web Authentication 표준의 authenticator data 형식을 따른다 ([W3C Web Authentication 의 Authenticator Data](https://www.w3.org/TR/webauthn-3/#sctn-authenticator-data){:target="_blank"}).

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-extensions.png)
출처: WWDC26 - Secure your apps with App Attest

extensions 는 attestation 과정에서 기기가 수집한, 앱의 추가 보안 속성을 담는다. 이번에 추가된 extension identifier 는 두 개다.

- launch validation category: 앱이 예상하지 못한 환경에서 실행되고 있는지를 알 수 있게 해 준다.
- bundle version: 내가 배포한 version 의 앱이 사용자 기기에서 돌고 있는지를 확인하게 해 준다.

server 는 이 속성들을 지켜보고, 예상 밖의 값이 있는지 확인하고, 사용자에 대한 전체 risk assessment 에 반영한다.

---

### macOS 에서의 변조 시나리오

attestation 은 변조의 흔적을 찾는 데 특히 쓸모가 있다. App Attest 를 붙인 macOS 앱이 있다고 하자. 누군가 System Integrity Protection 을 끄고, 앱을 수정해서 다른 provisioning profile 로 다시 서명하고, system path 에 있는 App Attest framework 까지 수정한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-unauthorized.png)
출처: WWDC26 - Secure your apps with App Attest

이때 server 가 받는 attestation 에는 key access control property 를 통해 System Integrity Protection 이 꺼져 있다는 것이 드러난다. Team Identifier, launch validation category, bundle version 이 바뀌어 있을 수도 있다. server 는 수정본과의 통신을 거절할 수 있고, 이 사실을 그 사용자에 대한 risk assessment 에 반영할 수 있다.

---

## assertion

server 가 attestation 을 검증하고 public key 를 저장했다면, 앱은 그 attest 된 key 로 이후의 통신을 보호할 수 있다. 이것이 assertion 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-assertion-flow.png)
출처: WWDC26 - Secure your apps with App Attest

1. 앱이 server 에 보낼 data 를 준비한다.
2. server 가 payload 에 넣을 challenge 를 앱에 내려 준다.
3. 앱이 key ID 를 꺼내고, key ID 와 server challenge 를 넘기며 assertion API 를 부른다.
4. App Attest 가 encode 된 assertion object 를 앱에 돌려준다.
5. 앱이 assertion object 를 payload 에 넣어 server 로 보낸다.
6. server 가 assertion 을 검증하고 payload 내용을 받아들이거나 거절한다.

```swift
import DeviceCheck
import CryptoKit
import Foundation

func makeAssertion(keyId: String, payload: Data) async throws -> Data {
  let clientDataHash = Data(SHA256.hash(data: payload))
  let assertion = try await DCAppAttestService.shared.generateAssertion(keyId, clientDataHash: clientDataHash)
  return assertion
}
```

세션 snippet 은 `generateAssertion(keyId: String, clientDataHash: Data)` 로 적혀 있다. argument 자리에 type 이름이 들어가 있어서 호출이라기보다 signature 를 옮겨 적은 것에 가깝다. attestation 과 마찬가지로 첫 argument 에는 label 이 없고, slide 의 `func generateAssertion(_ keyId: String, clientDataHash: Data) async throws -> Data` 가 SDK 와 일치한다. server challenge 가 포함된 payload 의 SHA-256 hash 를 넘기는 줄은 문서의 설명을 따라 내가 채웠다.

#### generateAssertion(_:clientDataHash:)

[generateAssertion(_:clientDataHash:completionHandler:)](https://developer.apple.com/documentation/devicecheck/dcappattestservice/generateassertion%28_:clientdatahash:completionhandler:%29){:target="_blank"} 은 attest 된 key 로 client data 의 hash 에 서명한 assertion object 를 돌려주는 method 다.

assertion 을 만들 때 생각할 점은 세 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-assertion-practices.png)
출처: WWDC26 - Secure your apps with App Attest

- 필요할 때 그 자리에서 만든다. assertion 은 기기 안에서 만들어지고 Apple server 를 거치지 않는다. 앱 lifecycle 가운데 server payload 에 넣어야 하는 바로 그 시점에 만들면 된다.
- CPU 를 쓴다. assertion 을 만드는 일에는 cryptographic 연산이 들어간다. 짧은 간격으로 연달아 만들거나 앱 lifecycle 안에서 너무 많이 만들지 않도록 주의한다.
- server 는 assertion 안의 counter 를 검증한다.

---

### counter 와 replay 방지

server 는 assertion 에 들어 있는 counter 값을 검증하고, 그 값이 반드시 증가하는지를 확인해야 한다. 사용자와 연결된 assertion 들의 counter 를 server 가 기록해 두는 것이다. 이것이 replay attack 에 대한 보호가 된다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-counter.png)
출처: WWDC26 - Secure your apps with App Attest

앱이 assertion 을 넣을 때마다 assertion object 안의 counter 값은 커져야 한다. counter 가 그대로이거나 줄어든 것이 보이면, server 에 기록된 counter 값을 모르는 변조된 앱일 수 있다.

---

### assertion object 의 구조

assertion 은 두 부분으로 된 구조다. signature 와 authenticator data 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-assertion-object.png)
출처: WWDC26 - Secure your apps with App Attest

signature 는 authenticator data, server challenge, 그리고 attestation object 에서 얻은 public key 로 검증한다. 절차는 문서를 따른다. authenticator data 는 attestation 때와 비슷하게 assertion 시점의 앱에 대한 정보를 담는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-assertion-authdata.png)
출처: WWDC26 - Secure your apps with App Attest

assertion 의 authenticator data 는 relying party ID hash, flags, counter 로 되어 있고, iOS 27 부터는 여기에도 끝에 extensions 가 붙는다. attestation object 의 extensions 와 같은 방식으로 다룬다. assertion 은 요청이 유효한 앱에서 왔다는 것을 요청마다 확인하는 데 쓸모가 있다.

---

## 흔한 실수

server 는 앱에서 오는 의심스러운 활동을 조심스럽게 다뤄야 한다. 세션은 두 가지 상황을 짚는다.

---

### 기존 사용자의 새 attestation

이미 attestation 이 있는 사용자에게서 새 attestation 이 오는 경우다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-new-attestations.png)
출처: WWDC26 - Secure your apps with App Attest

- 새 key 를 곧바로 거절하지 않는다. 앱을 다시 설치하거나 기기를 복원하는 것 같은 정당한 상황에서도 key 가 바뀐다.
- 같은 이유로, 그 사용자의 이전 attestation 에 있던 key 를 즉시 무효로 만들지도 않는다.
- fraud metric 과 함께 쓰면, server 가 가진 사용자별 attestation 목록 자체가 fraud 나 abuse 의 신호가 된다.

---

### 거절의 처리

server 가 attestation 이나 assertion 을 거절했을 때 앱은 이것을 부드럽게 처리해야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-rejections.png)
출처: WWDC26 - Secure your apps with App Attest

- 그 사용자에게는 App Attest 에 묶인 기능을 낮춰서 제공한다.
- 감시 수준을 높인 채로 제한된 접근을 허용한다.
- 종합적인 risk assessment 없이 사용자를 바로 차단하지 않는다.

---

### risk assessment

세션은 risk assessment 가 무슨 뜻인지를 따로 설명한다. 그 내용은 business, 배포하는 앱의 종류, 앱에서 fraud 가 일어났을 때의 영향에 따라 달라진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-risk.png)
출처: WWDC26 - Secure your apps with App Attest

App Attest 를 근거로 어떤 사용자의 사기 행위가 의심된다면, 사용자 비활성화나 정지에 대한 자기 business 의 지침을 따른다. 제대로 평가하지 않고 사용자를 차단하면 신뢰가 깎이고 정당한 사용자가 피해를 볼 수 있다. 항상 잘 정의된 risk assessment 절차를 따른다.

---

## fraud metric

App Attest 의 마지막 부분은 fraud metric 이다. 의심스러운 attestation 활동을 찾아내는 도구다.

변조된 기기도 attestation 을 통과할 수 있다. 그런 기기는 broker 처럼 행동할 수 있다. 다른 기기에서 도는 수정된 앱들을 대신해서 유효한 attestation 을 만들어 주는 것이다. 그러면 그 수정된 앱들이 server 에 변조된 요청을 보낼 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-broker.png)
출처: WWDC26 - Secure your apps with App Attest

---

### fraud metric 이란?

fraud metric 은 특정 기기에서 지난 30일 동안 내 앱과 연결되어 attest 된 고유한 key 의 대략적인 개수다. 기기 하나가 key 를 유난히 많이 attest 하고 있다면 broker 일 가능성이 있다. 사용자가 변조되었을 수 있는 기기의 attestation 과 연결되어 있는지를 판단하는 데 쓰고, 사용자의 risk assessment profile 에 넣는다. 자세한 내용은 문서 [Assessing fraud risk](https://developer.apple.com/documentation/devicecheck/assessing-fraud-risk){:target="_blank"} 에 있다.

---

### fraud metric 의 조회

fraud metric 은 앱이 아니라 server 가 조회한다. 내 server 와 App Attest data server 사이에서 오간다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-fraud-access.png)
출처: WWDC26 - Secure your apps with App Attest

1. server 가 사용자와 연결된 attestation 에서 receipt 를 꺼낸다.
2. 그 receipt 를 넣어 App Attest data server 에 POST 요청을 보낸다.
3. data server 가 fraud metric 이 담긴 receipt 를 돌려준다. 다음 조회부터는 이 새 receipt 를 쓴다.

---

### receipt 의 구조

receipt 는 App Store receipt 와 비슷한 구조이고 세 부분으로 되어 있다. signature, certificate chain, receipt payload 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-receipt.png)
출처: WWDC26 - Secure your apps with App Attest

signature 는 receipt payload 에 대한 서명이다. certificate chain 은 Apple 의 certificate authority 까지 이어진다. receipt payload 에는 metric 과 연결된 attest 된 key 에 대한 정보와 fraud metric 자체가 들어 있다. slide 에 적힌 payload 항목은 attested public key, client hash, token, receipt type, creation time, risk metric, not before, expiration time 이다. 각 부분의 검증은 문서를 따른다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-receipt-fields.png)
출처: WWDC26 - Secure your apps with App Attest

세션이 따로 짚는 항목은 마지막 세 개다.

- risk metric: fraud metric 의 개수다.
- not before: receipt 를 새로 고칠 수 있는 가장 이른 시점이다. receipt 는 새로 고쳐야 한다.
- expiration time: receipt 가 만료되는 시점이다. 이 뒤로는 새로 고칠 수 없다.

---

### fraud metric 을 쓸 때의 원칙

fraud metric 을 다룰 때 생각할 점은 두 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-fraud-practices.png)
출처: WWDC26 - Secure your apps with App Attest

- App Attest key 가 바뀌는 사용자 행동은 모두 fraud metric 을 올린다. 앱을 다시 설치하거나 기기를 복원하면 key 를 새로 만들고 다시 attest 하게 되고, 이것이 metric 에 더해진다.
- fraud metric 으로 사용자를 곧바로 차단하지 않는다. 사기 행위를 조사하게 만드는 신호로 다룬다. 값을 지켜보고, 분석해서 baseline 을 잡고, 급증을 의심스러운 활동의 지표로 찾아낸다.

---

## 세션의 마무리

세션은 다음 걸음으로 네 가지를 적는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-201/wwdc26-201-next.png)
출처: WWDC26 - Secure your apps with App Attest

- 최신 SDK 로 앱을 다시 build 해서 App Attest API 의 새 기능을 쓸 수 있게 한다.
- 앱에서 attestation 의 보안이 도움이 될 영역을 찾는다. 인증 흐름이 그렇고, 유료 content 를 다루는 민감한 payload 는 assertion 으로 강화할 수 있다.
- server 가 attestation 을 검증하고, receipt 를 저장하고, assertion counter 를 추적하도록 준비한다.
- fraud metric 을 risk assessment pipeline 에 넣는다.

App Attest 는 앱의 무결성을 검증하고, 앱과 server 사이의 통신을 보호하고, fraud 의 징후를 찾는 도구를 준다. 모두 Apple hardware 의 보안에 기대고 있다.

## 정리

세션에 나온 요소를 누가 만들고 누가 확인하는지로 나누면 다음과 같다.

| 요소 | 만드는 곳 | server 가 확인할 것 | 올해 달라진 점 |
| --- | --- | --- | --- |
| key ID | 앱이 `generateKey()` 로 요청, key 는 Secure Enclave 에 | 사용자와의 연결 | macOS 27 지원 |
| attestation | 앱이 `attestKey` 로 요청, Apple server 가 발급 | certificate chain, relying party ID, challenge, receipt | leaf certificate 의 key access control property |
| authenticator data | attestation 과 assertion 안에 포함 | 각 항목과 extensions | iOS 27 의 extensions (launch validation category, bundle version) |
| assertion | 앱이 `generateAssertion` 으로 기기 안에서 생성 | signature, 증가하는 counter | extensions 가 여기에도 붙음 |
| fraud metric | server 가 receipt 로 App Attest data server 에 조회 | risk metric 의 baseline 과 급증 | 세션에서 달라졌다고 말한 것은 없음 |

실제 프로젝트에 가져갈 점은 다음과 같다.

- App Attest 호출은 `isSupported` 로 감싸고, 지원되지 않을 때 기능을 어디까지 열어 줄지를 미리 정한다. 그 값 자체도 server 에 신호로 보낸다.
- key ID 는 Keychain 에 두고, account 기반 앱이면 사용자마다 따로 만든다.
- attestation 은 server 가 시작시키고, 사용자 흐름 밖에서 받고, 실패하면 exponential back-off 로 다시 시도한다. retry 간격을 앱에 고정해 두지 않는다.
- 검증은 전부 server 에서 한다. 앱 안에서 attestation 을 검증하는 code 는 의미가 없다.
- server 는 attestation 의 receipt 를 저장해 둔다. fraud metric 을 조회하려면 필요하다.
- assertion 의 counter 를 사용자별로 기록하고, 증가하지 않는 값은 의심한다.
- 새 key, 거절, fraud metric 의 급증은 모두 차단의 근거가 아니라 조사의 신호다. 재설치와 기기 복원만으로도 key 가 바뀌고 metric 이 오른다.
- App Store 로만 배포하는 앱이라면 launch validation category 와 bundle version 을 내가 배포한 값과 비교하는 검사를 server 에 더한다.
