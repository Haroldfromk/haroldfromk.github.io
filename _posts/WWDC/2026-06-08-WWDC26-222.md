## 한 줄 요약

iOS 27 에서 MetricKit 이 Swift 중심의 새 API 로 다시 만들어졌다. `MetricManager` 의 `AsyncSequence` 두 개로 metric 과 diagnostic 을 받고, report 는 `Codable` 이라 그대로 JSON 으로 보낼 수 있다. 가장 큰 변화는 **앱이 알려 준 state 별로 metric 을 나눠 받을 수 있다**는 점이다.

세션은 네 부분이다. MetricKit 소개와 iOS 27 의 변화, metric report 받기, diagnostic report 받기, state 로 context 붙이기 순서다.

## MetricKit 의 자리와 iOS 27 의 변화

세션은 성능 개선을 한 번 하고 끝나는 일이 아니라 도는 과정으로 본다. data 를 모으고, 분석해서 문제를 찾고, 문제마다 원인을 가려내고, 고치고, 다시 처음으로 돌아가 결과를 지켜본다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-workflow.png)

출처: WWDC26 - Meet the new MetricKit

MetricKit 은 이 중 **collect** 를 맡는다. 개발자의 기기가 아니라 실제 사용자의 기기에서, 실제 사용 중에 일어난 일을 모아 준다는 것이 Instruments 와 다른 점이다.

---

### metric 과 diagnostic 이란?

MetricKit 이 주는 data 는 두 종류다.

| 종류 | 답하는 질문 | 예 |
|---|---|---|
| metric | 이 영역의 성능이 전체적으로 좋아지고 있는가 나빠지고 있는가 | launch time, hang time, peak memory |
| diagnostic | 어느 code path 가 문제를 일으켰는가 | crash 의 backtrace, hang 의 call stack |

metric 은 앱의 건강 상태를 계속 알려 주는 신호다. 세션은 둘로 묶어 설명한다.

- launch time, hang, animation metric 은 앱이 얼마나 빠르게 반응하고 매끄럽게 느껴지는지를 말한다. launch 가 느리면 사람들은 앱을 떠난다
- CPU, GPU, disk write, network transfer 같은 resource 소비 metric 은 앱이 얼마나 무겁게 일하고 기기에 어떤 영향을 주는지를 말한다

---

### metric 의 형태

metric 이 숫자 하나로 오는 것은 아니다. time to first draw 같은 launch metric 은 histogram 으로 온다. 하루 동안 앱을 열 때마다 걸린 시간을 구간별로 센 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-histogram.png)

출처: WWDC26 - Meet the new MetricKit

이 예에서는 대부분의 launch 가 510 에서 540 millisecond 사이에 몰려 있고 바깥에 몇 개가 있다. 평균 하나로는 보이지 않는 분포가 보인다.

MetricKit 이 준 값에서 내가 필요한 지표를 직접 만들 수도 있다. 세션의 예는 hang rate 다. 앱을 30분 쓰는 동안 hang time 이 모두 3초였다면 시간당 6초라는 hang rate 가 나온다.

이 값을 모든 기기에 걸쳐 모으면 앱의 성능이 어느 쪽으로 가고 있는지를 숫자로 볼 수 있다.

### iOS 27 에서 달라진 것

세션은 framework 를 바닥부터 다시 만들었다고 말한다. context 가 풍부하고 표현력 있는 Swift 중심의 API 다. 그리고 이 세션에서 다루는 새 기능은 모두 **새 API 에서만** 쓸 수 있다. 기존 [MXMetricManager](https://developer.apple.com/documentation/metrickit/mxmetricmanager){:target="_blank"} 에는 들어오지 않는다.

새로 생긴 것은 세 가지다.

- **state 별 metric**: 각 metric 을 앱의 state 에 따라 나눠 준다. tab 이 세 개인 앱의 hang time 을 tab 1, tab 2, tab 3 가 활성일 때로 나눠 볼 수 있다
- **Metal frame rate metric**: game 의 render 성능을 보는 metric 이다. 자세한 내용은 [Find and fix performance issues in your Metal games](https://developer.apple.com/videos/play/wwdc2026/388/){:target="_blank"} 세션에서 다룬다
- **memory exception diagnostic**: 앱이나 extension 이 memory limit 을 넘겨 종료됐을 때 무슨 일이 있었는지 알려 준다

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-contextualized.png)

출처: WWDC26 - Meet the new MetricKit

## metric report 받기

사람들이 하루 동안 앱을 쓰면 MetricKit 은 launch, hang, memory, CPU 같은 metric 을 계속 모아서 **하루에 한 번** report 로 앱에 전달한다.

---

### metric report 의 구조

report 안에는 entry 가 여러 개 있다. 하루 전체를 덮는 entry 가 하나 있고, 보통 몇 시간씩인 더 작은 구간의 entry 가 따로 있다. 작은 구간은 그 구간에 해당하는 metric 이 있을 때만 들어온다.

각 entry 안에서 metric 은 metric group 으로 묶인다. group 은 system 의 한 측면을 나타내고 `.cpu`, `.memory`, `.display`, `.gpu` 같은 것이 있다. group 안에 개별 metric 이 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-report-structure.png)

출처: WWDC26 - Meet the new MetricKit

iOS 27 SDK 의 interface 를 열어 보면 [MetricGroup](https://developer.apple.com/documentation/metrickit/metricgroup){:target="_blank"} 에는 세션이 든 네 개 말고도 `diskIO`, `networkTransfer`, `animation`, `applicationResponsiveness`, `appLaunch`, `appRuntime`, `appTermination`, `frameStatistics` 등이 있다.

---

### MetricManager 로 report 기다리기

```swift
import MetricKit

let manager = MetricManager()

for await report in manager.metricReports {
    processReport(report)
}
```

> 세션의 코드 조각은 top level 에 놓인 형태다. 빌드를 확인할 때는 `async` 함수 안에 넣었고, `processReport(_:)` 는 세션에 정의가 나오지 않아 빈 함수로 채웠다. 뒤의 조각들도 같은 방식으로 확인했다.
{: .prompt-warning }

#### MetricManager 의 metricReports 로 metric 받기

[MetricManager](https://developer.apple.com/documentation/metrickit/metricmanager){:target="_blank"} 가 새 API 의 진입점이다. [metricReports](https://developer.apple.com/documentation/metrickit/metricmanager/metricreports){:target="_blank"} 는 [MetricReport](https://developer.apple.com/documentation/metrickit/metricreport){:target="_blank"} 를 내놓는 `AsyncSequence` 라서 `for await` 로 기다리면 된다. delegate 를 등록하던 `MXMetricManager` 와 달리 subscriber protocol 이 없다.

세션이 붙인 주의 사항이 두 가지 있다.

- 이 설정은 **앱이 시작할 때** 한다. 늦게 구독하면 그 사이의 data 를 잃을 수 있다
- `MetricManager` 는 **계속 살려 둔다**. 그래야 뒤에 준비되는 report 가 stream 으로 계속 전달된다

`for await` 는 끝나지 않는 loop 이므로 세션은 이 일을 detached task 나 전용 service class 에서 하라고 한다.

---

### report 를 server 로 보내기

metric 은 기기 한 대의 값으로는 의미가 약하다. 여러 기기의 값을 모아야 앱의 상태가 보인다. 그래서 보통은 report 를 server 로 보낸다.

```swift
import MetricKit

for await report in manager.metricReports {
    let jsonData = try JSONEncoder().encode(report)
    sendToServer(jsonData)
}
```

`MetricReport` 는 `Codable` 이다. [JSONEncoder](https://developer.apple.com/documentation/foundation/jsonencoder){:target="_blank"} 를 만들어 report 전체를 encode 하면 끝이다. 기존 API 의 `jsonRepresentation()` 처럼 정해진 형태의 `Data` 만 받는 것이 아니라 일반적인 Swift type 이므로, 필요하면 다른 encoder 를 쓰거나 일부만 골라 보낼 수 있다.

---

### 특정 metric 만 꺼내기

report 를 통째로 보내지 않고 특정 group 이나 값만 볼 수도 있다.

```swift
import MetricKit

for await report in manager.metricReports {
    let intervalEntries = report.intervalEntries
    let fullDayEntry = intervalEntries.fullDayEntry
    
    for entry in intervalEntries {
        let memoryMetrics = entry.values.filter { $0.metricGroup == .memory }
        
        for metric in memoryMetrics {
            switch metric {
            case .peakMemory(let peak):
                processPeakMemory(peak)
            default: break
            }
        }
    }
}
```

> 세션 코드 그대로 빌드된다. `fullDayEntry` 는 만들고 쓰지 않아서 warning 이 하나 나온다.
{: .prompt-warning }

#### intervalEntries 와 MetricResult 로 값 꺼내기

세 단계로 내려간다.

1. `report.intervalEntries` 를 돈다. 하루 전체 entry 와 작은 구간 entry 가 함께 들어 있다. 하루 전체만 필요하면 `fullDayEntry` 로 바로 꺼낸다
2. [IntervalEntry](https://developer.apple.com/documentation/metrickit/metricreport/intervalentry){:target="_blank"} 의 `values` 를 `metricGroup` 으로 걸러서 관심 있는 group 만 남긴다
3. [MetricResult](https://developer.apple.com/documentation/metrickit/metricresult){:target="_blank"} 를 `switch` 한다. metric 종류마다 case 가 있고 associated value 로 그 metric 의 값이 온다

`MetricResult` 가 enum 이라는 점이 기존 API 와의 큰 차이다. 예전에는 `MXMetricPayload` 의 optional property 를 하나씩 확인했다면, 이제는 report 에 실제로 들어 있는 metric 만 배열로 오고 pattern matching 으로 고른다. SDK 를 보면 `.peakMemory` 의 associated value 는 [PeakMemoryMetric](https://developer.apple.com/documentation/metrickit/peakmemorymetric){:target="_blank"} 이고 `value` 는 `Measurement<UnitInformationStorage>` 다.

### 모은 metric 분석하기

여기까지가 workflow 의 collect 단계다. 다음은 analyze 인데, 세션은 이것을 data science 문제라고 부른다. MetricKit 이 해 주는 일이 아니다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-server.png)

출처: WWDC26 - Meet the new MetricKit

- report 를 받아서 관심 있는 dimension 에 따라 집계하는 server 를 직접 둔다
- 어떤 통계 분석이 맞는지는 만들고 싶은 data 와 찾고 싶은 insight 에 따라 직접 정한다
- 집계한 결과로 baseline, 곧 앱이 지금 어느 정도인지를 먼저 잡는다
- 그 뒤로 집계 metric 을 지켜보면서 좋아지는지 나빠지는지를 본다

## diagnostic report 받기

metric 으로 문제가 있다는 것을 알았다면 다음은 triage 다. 원인을 가려내는 이 단계에서 diagnostic 이 쓰인다.

crash 나 hang 같은 일이 생기면 system 이 기기에서 diagnostic 을 잡는다. diagnostic report 는 이 내용을 묶어서 MetricKit 을 통해 **바로** 앱에 전달한다. 하루에 한 번인 metric report 와 다르다.

---

### crash diagnostic 의 내용

많은 diagnostic 이 backtrace 를 담고 있다. 그 일이 일어난 순간의 call stack 이다. 세션이 가장 중요하다고 꼽는 crash diagnostic 에는 세 가지가 더 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-crash.png)

출처: WWDC26 - Meet the new MetricKit

| 항목 | 내용 |
|---|---|
| backtrace | crash 시점의 call stack |
| termination reason | 앱이 왜 종료됐는지 |
| exception type | 어떤 종류의 실패인지 |
| termination category | 이 crash 가 metric 에서 어떻게 집계됐는지. iOS 27 에 새로 생겼다 |

termination category 가 metric 과 diagnostic 을 잇는다. 비정상 종료 metric 이 올라가고 있을 때 어느 diagnostic 이 그 숫자에 해당하는지 바로 짝지을 수 있다. SDK 의 `CrashDiagnostic.TerminationCategory` 에는 `badAccess`, `abnormal`, `illegalInstruction`, `watchdog`, `taskTimeout`, `fileLock` 이 정의돼 있다.

backtrace 를 읽는 방법도 세션이 짚는다. symbolicate 된 backtrace 는 system 의 thread start 에서 시작해 아래로 내려가면서 앱의 코드로 들어온다. 끝까지 따라 내려간 곳이 crash 지점이다. 세션의 예에서는 앱의 `submitReport()` 함수에서 실행이 멈췄고, 고칠 곳이 그 함수로 좁혀진다.

---

### diagnosticReports 로 diagnostic 받기

```swift
import MetricKit

let manager = MetricManager()

for await report in manager.diagnosticReports {
    processReport(report)
}
```

[diagnosticReports](https://developer.apple.com/documentation/metrickit/metricmanager/diagnosticreports){:target="_blank"} 도 같은 `MetricManager` 의 `AsyncSequence` 다. metric 과 똑같이 앱이 시작하자마자 detached task 나 전용 service class 에서 듣기 시작한다.

[DiagnosticReport](https://developer.apple.com/documentation/metrickit/diagnosticreport){:target="_blank"} 도 `Codable` 이라서 server 로 보내는 코드는 metric 과 같은 모양이다.

```swift
import MetricKit

for await report in manager.diagnosticReports {
    let jsonData = try JSONEncoder().encode(report)
    sendToServer(jsonData)
}
```

---

### diagnostic 종류별로 처리하기

```swift
import MetricKit

for await report in manager.diagnosticReports {
    switch report.result {
    case .crash(let crash):
        let backtrace = crash.callStackTree
        let reason = crash.terminationReason
        let category = crash.terminationCategory
        processCrash(backtrace: backtrace, reason: reason, category: category)
    case .hang(let hang):
        processHangDiagnostic(hang)
    default: break
    }
}
```

#### DiagnosticResult 로 종류 가르기

`report.result` 는 [DiagnosticResult](https://developer.apple.com/documentation/metrickit/diagnosticresult){:target="_blank"} enum 이다. metric 쪽의 `MetricResult` 와 같은 설계다. `.crash` 에서는 [CrashDiagnostic](https://developer.apple.com/documentation/metrickit/crashdiagnostic){:target="_blank"} 이 오고 여기서 [callStackTree](https://developer.apple.com/documentation/metrickit/callstacktree){:target="_blank"}, `terminationReason`, `terminationCategory` 를 꺼낸다. `.hang` 에서는 [HangDiagnostic](https://developer.apple.com/documentation/metrickit/hangdiagnostic){:target="_blank"} 이 온다.

SDK 에는 이 둘 말고 `.cpuException`, `.diskWriteException`, `.appLaunch`, 그리고 iOS 27 의 `.memoryException` 이 있다. `.memoryException` 의 [MemoryExceptionDiagnostic](https://developer.apple.com/documentation/metrickit/memoryexceptiondiagnostic){:target="_blank"} 도 `callStackTree` 를 갖는다.

## state 로 context 붙이기

지금까지의 metric 과 diagnostic 은 앱 전체에 대한 그림이다. 개별 문제를 파고들려면 그때 앱이 어떤 상태였는지가 필요하다. 사용자가 어떤 흐름에 있었는지, 앱이 어떻게 설정돼 있었는지 같은 것이다.

---

### 섞인 metric 의 한계

세션의 예제는 경비 처리 앱이다. 영수증을 scan 하고, 경비를 제출하고, category 와 예산별로 지출을 본다. 기능은 Reports tab 과 Spending tab 에 나뉘어 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-expense-app.png)

출처: WWDC26 - Meet the new MetricKit

이 앱의 scroll hitch metric 을 본다. 하루 동안 5분을 scroll 했고 그중 hitch time 이 4.5초였다. hitch rate 로는 15 ms/s 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-scroll-hitch.png)

출처: WWDC26 - Meet the new MetricKit

문제는 이 숫자가 앱 전체의 평균이라는 점이다. 사용자가 두 tab 을 오가며 쓴 시간이 다 섞여 있어서, 어느 화면이 느린지는 이 숫자로 알 수 없다.

---

### state 란?

앱의 설정이나 동작을 설명하는, **내가 정의한 정보**다. 앱이 state 를 알려 주면 MetricKit 은 metric 을 그 state 별로 나눠서 집계한다. state 를 알리는 일은 MetricKit 이 아니라 [StateReporting](https://developer.apple.com/documentation/statereporting){:target="_blank"} 이라는 별도 framework 로 한다.

경비 앱에서 사용자는 Reports tab 에서 경비를 추가하고, 앱을 떠났다가, 식비 예산을 보려고 Spending tab 으로 돌아온다. 앱은 이렇게 state 가 바뀔 때마다 transition 을 알리고, MetricKit 은 그것을 metric 과 diagnostic 에 겹친다.

결과는 이렇게 달라진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-by-state.png)

출처: WWDC26 - Meet the new MetricKit

| | hitch rate |
|---|---|
| state 없이 섞인 값 | 15 ms/s |
| Spending tab | 1 ms/s |
| Reports tab | 71 ms/s |

Spending tab 은 문제가 없고 Reports tab 이 심하게 끊긴다. 15 ms/s 라는 평균만 봤다면 내릴 수 없는 결론이다. 최적화할 곳이 정확히 정해진다.

---

### domain 이란?

state 가 속하는 범위다. domain 은 앱의 한 기능이나 영역을 나타내고, **한 domain 에서는 한 번에 하나의 state 만** 활성일 수 있다. domain 을 나누면 여러 state 를 동시에 유지할 수 있다.

세션의 예는 실험이다. 경비 앱에 실험적인 변경을 넣었는데, 켜면 database 에서 경비를 작은 batch 로 가져오고 끄면 큰 batch 로 가져온다. tab state 와 batch size state 를 서로 다른 domain 에 두면 MetricKit 은 tab 별 metric 과 batch size 별 metric 을 각각 준다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-domains.png)

출처: WWDC26 - Meet the new MetricKit

state 는 transition model 을 따른다. 앱은 지금 옮겨 가는 state 만 알리고, 그 state 에 얼마나 머물렀는지는 MetricKit 이 잰다. start 와 end 를 짝지어 부르는 방식이 아니다. 앱은 언제든 지금 어떤 조건에 있는지만 말한다.

---

### StateReporter 로 transition 알리기

```swift
import MetricKit
import StateReporting

let domain = StateReportingDomain("com.metrickitsample.tabs")
let manager = MetricManager(enabledStateReportingDomains: [domain])

// Report transitions throughout the app

let reporter = StateReporter.reporter(for: domain.rawValue)
reporter.reportTransition(to: "Reports")
```

#### StateReportingDomain 과 StateReporter 로 state 알리기

순서는 세 단계다.

1. [StateReportingDomain](https://developer.apple.com/documentation/metrickit/statereportingdomain){:target="_blank"} 을 만든다. 이름은 보통 reverse DNS 형태의 문자열이다
2. `MetricManager` 를 만들 때 `enabledStateReportingDomains` 로 그 domain 을 등록한다. 등록한 domain 의 state 만 metric 과 겹쳐진다
3. [StateReporter](https://developer.apple.com/documentation/statereporting/statereporter){:target="_blank"} 를 domain 이름으로 얻고, state 에 들어갈 때 `reportTransition(to:)` 를 부른다. state 는 문자열 label 로 식별한다

`StateReportingDomain` 은 MetricKit 의 type 이고 `StateReporter` 는 StateReporting 의 type 이라서, reporter 를 얻을 때는 `domain.rawValue` 로 문자열을 넘긴다. SDK 를 보면 `reportTransition(to:)` 의 label 은 optional 이다.

---

### state 에 metadata 붙이기

state 마다 세부 정보를 더할 수 있다. 경비 앱이라면 화면에 있는 항목에 대한 정보다. 거래 목록이 small, medium, large 중 어느 크기인지, 정렬돼 있는지 같은 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-metadata.png)

출처: WWDC26 - Meet the new MetricKit

```swift
import StateReporting

@ReportableMetadata
struct ViewConfiguration {
    let listSize: String
    let isSorted: Bool
}

let reporter = StateReporter.reporter(
    for: domain.rawValue,
    stableMetadata: ViewConfiguration.self
)

reporter.reportTransition(
    to: "Reports",
    stableMetadata: ViewConfiguration(listSize: "large", isSorted: false)
)
```

#### ReportableMetadata macro 로 구조화된 정보 정의하기

[@ReportableMetadata](https://developer.apple.com/documentation/statereporting/reportablemetadata%28%29){:target="_blank"} macro 를 struct 에 붙이면 [ReportableMetadata](https://developer.apple.com/documentation/statereporting/reportablemetadata){:target="_blank"} protocol 을 따르게 된다. 그 type 을 `reporter(for:stableMetadata:)` 에 넘겨 reporter 를 만들고, transition 을 알릴 때 label 과 함께 값을 넘긴다.

SDK 의 interface 에서 확인한 점을 덧붙인다.

- macro 는 `metadataDictionary` 라는 member 를 만든다. 값의 type 은 `ReportableMetadataValue` 이고 문자열, 날짜, 정수, 실수, `Bool` 로 만들 수 있다. 그러니 struct 의 property 는 이런 단순한 type 이어야 한다
- 인자 이름이 `stableMetadata` 인 것은 `volatileMetadata` 가 따로 있기 때문이다. `reporter(for:stableMetadata:volatileMetadata:)` 와 `reportVolatileMetadataUpdate(_:)` 가 있다. 세션은 stable 쪽만 다루고 둘의 차이는 설명하지 않는다

### state entry 읽기

state 를 알리기 전의 metric report 는 앱 전체에 대한 넓은 metric 만 준다. report 의 `stateEntries` 가 state 를 반영한 metric 을 담는 곳인데, state 를 알린 적이 없으면 비어 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-state-entries.png)

출처: WWDC26 - Meet the new MetricKit

state 를 알리기 시작하면 [StateEntry](https://developer.apple.com/documentation/metrickit/metricreport/stateentry){:target="_blank"} 가 채워진다. state 하나에 `StateEntry` 하나이고, 그 state 에 머문 시간 동안의 metric 이 집계돼 있다. SDK 를 보면 `StateEntry` 는 `state` 와 `values` 를 갖고, `values` 는 interval entry 와 같은 `[MetricResult]` 다. 앞에서 본 `switch` 를 그대로 쓸 수 있다.

server 로 보낼 때는 domain 별로 묶어서 encode 할 수 있다.

```swift
import MetricKit

for await report in manager.metricReports {
    let encoder = JSONEncoder()
    
    let formatKey = MetricReport.encodingFormatKey
    encoder.userInfo[formatKey] = MetricReport.EncodingFormat.byStateReportingDomain
    
    let jsonData = try encoder.encode(report)
    sendToServer(jsonData)
}
```

#### encodingFormatKey 로 domain 별로 묶어 encode 하기

encoder 의 `userInfo` 에 [encodingFormatKey](https://developer.apple.com/documentation/metrickit/metricreport/encodingformatkey){:target="_blank"} 를 key 로, [EncodingFormat](https://developer.apple.com/documentation/metrickit/metricreport/encodingformat){:target="_blank"} 의 `byStateReportingDomain` 을 값으로 넣는다. 이렇게 encode 하면 state entry 와 interval entry 둘 다 report 에 있는 domain 과 state 별로 묶인 형태가 된다. server 쪽에서 domain 을 기준으로 집계하기 쉬운 모양이다.

### state 를 정의할 때의 best practice

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-222/wwdc26-222-best-practices.png)

출처: WWDC26 - Meet the new MetricKit

- **domain 은 좁게 잡는다.** 앱의 영역마다 자기 state 를 갖고, 그 state 별로 data 를 이해할 수 있게 한다
- **state 는 안정적이고 의미 있는 단계여야 한다.** 잠깐 스치는 UI event 를 state 로 삼지 않는다
- **state 가 무엇을 뜻하는지 신중하게 정한다.** regression 이 보였을 때 그 state 만으로 어디를 고칠지 알 수 있어야 한다
- **state 의 수를 계획한다.** 너무 많으면 data 가 지나치게 잘게 쪼개져서 전체 그림을 읽기가 오히려 어려워진다. overhead 를 줄이려고 state 수에는 상한도 있다
- **출시 전에 Points of Interest instrument 로 확인한다.** 알린 state 가 기대한 대로인지 Instruments 에서 본다

상한이 몇 개인지는 세션에 나오지 않는다. 다만 SDK 의 `MetricReport.Environment` 에 `hasExceededStateLimit` 이라는 property 가 있어서, 상한을 넘겼는지는 report 에서 알 수 있는 것으로 보인다.

## 정리

세션이 마지막에 주는 행동 목록은 이렇다.

- `MetricManager` 로 성능 metric 을 모아서 앱의 건강 상태를 지켜본다
- diagnostic 을 분석해서 고칠 곳을 구체적으로 찾는다
- 앱의 중요한 state 를 알려서 data 에 context 를 붙인다
- memory diagnostic, Metal frame rate metric 같은 새 data 를 살펴본다
- `MXMetricManager` 를 쓰고 있다면 새 `MetricManager` API 로 옮긴다

기존 API 와 달라진 점을 한 표로 모으면 이렇다.

| | 기존 | iOS 27 의 새 API |
|---|---|---|
| 진입점 | `MXMetricManager.shared` 와 subscriber | `MetricManager` instance |
| 받는 방법 | delegate method | `metricReports`, `diagnosticReports` 를 `for await` |
| report 의 형태 | payload class 와 JSON 표현 | `Codable` 인 struct 와 enum |
| 값 꺼내기 | property 를 하나씩 확인 | `MetricResult`, `DiagnosticResult` 를 `switch` |
| context | 없음 | StateReporting 의 domain 과 state |

실제 프로젝트에 가져갈 점도 적어 둔다.

- 구독은 앱 시작 시점에 하고 `MetricManager` 를 놓지 않는다. `App` 의 `init` 에서 만든 service 가 manager 를 들고 `Task.detached` 로 stream 두 개를 듣는 구조가 세션의 설명과 맞는다
- 새 기능은 전부 새 API 에만 있고 새 API 는 iOS 27 부터다. 더 낮은 버전을 지원하는 앱은 `if #available` 로 갈라서 `MXMetricManager` 를 한동안 같이 유지해야 한다
- MetricKit 은 모아 주기만 한다. report 를 받을 server 와 집계 방식은 직접 정해야 하고, state 를 넣기 전에 baseline 부터 잡는 것이 순서다
- state 는 tab 이나 주요 화면처럼 오래 머무는 단위부터 시작한다. domain 하나에 state 몇 개로 시작해서 Points of Interest 로 확인하고 늘린다
- A/B 실험 flag 를 별도 domain 의 state 로 알리면 실험이 성능에 준 영향을 MetricKit 으로 볼 수 있다
