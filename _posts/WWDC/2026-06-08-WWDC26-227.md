## 한 줄 요약

agent 에게 화면 하나를 만들어 달라고 하지 말고 **여러 개를, 각각 이름 붙은 preview 로** 만들어 달라고 한다. 그 결과를 보고 고르고 섞는 것은 사람의 일이다. 세션은 이 원칙을 layout 탐색, sample content, animation tuning 세 단계에 똑같이 적용한다.

발표자가 디자이너라는 점이 이 세션의 성격을 정한다. API 설명은 없고, agent 에게 무엇을 어떻게 시켜야 prototype 이 좋아지는지를 prompt 예시로 보여 준다.

## prototyping 과 두 가지 도구

세션은 앱을 만들어 내는 일이 이렇게 쉬웠던 적이 없기 때문에, 의도를 갖고 design 하는 것이 눈에 띄기 위한 조건이 됐다고 말한다. prototyping 은 여러 design idea 를 빠르게 시도해 보는 과정이고 그래서 전보다 더 중요해졌다는 것이다.

목표는 agent 가 처음 만들어 준 다듬어지지 않은 화면에서 출발해 목적이 분명하고 고유한 design 으로 가는 것이다.

### coding agent 와 Xcode preview

세션이 전제로 삼는 Xcode 기능은 둘이다.

- **coding agent**: 만들고 싶은 것을 말로 설명하면 코드로 만들어 준다. new conversation 버튼을 누르고 원하는 코드 변경이나 기능을 적으면 된다
- **Xcode preview**: 고칠 때마다 build 하고 실행하지 않아도 UI 를 보고 조작할 수 있다. Swift file 에 preview 가 정의돼 있어야 하고, show canvas 버튼으로 연다. preview 를 정의하는 방법은 [Previews in Xcode](https://developer.apple.com/documentation/swiftui/previews-in-xcode){:target="_blank"} 문서에 있다

둘을 합치면 핵심 화면과 순간을 빠르게 prototype 할 수 있다. 세션이 강조하는 장점은 agent 가 **실제 native 코드**를 만든다는 점이다. prototype 이 그림으로 끝나지 않고 그 코드를 앱 개발로 그대로 가져갈 수 있다.

---

### 협업자로서의 agent

본론에 들어가기 전에 세션이 못 박는 말이 있다. 비판적 사고를 이 도구에 넘기지 말라는 것이다. 앱을 쓰는 사람에게 무엇이 가장 좋은 경험인지 판단하는 일은 내 몫이고, agent 는 그 답을 찾는 과정을 돕는 협업자다. 최종 결정권은 항상 나에게 있다. 이 말은 세션 마지막에도 그대로 반복된다.

## UI 가능성 탐색하기

예제는 독서 모임을 관리하는 앱이다. 정기적으로 만나는 book club 을 위한 앱을 만든다고 하자.

---

### 모호한 prompt 가 만드는 문제

일단 시작하고 싶은 마음에 "정기적으로 만나는 book club 을 관리하는 UI 를 만들어 줘" 라고 쓰기 쉽다. 결과는 빨리 나오고 그럴듯하다. 하지만 세션은 이 prompt 가 네 가지 문제를 만든다고 짚는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-vague-problems.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

| 문제 | 내용 |
|---|---|
| 임의의 layout | 동작은 하겠지만 이런 앱을 구성하는 많은 방법 중 하나일 뿐이다 |
| AI 가 고른 기능 | prompt 에 기능이 없으니 agent 가 추측한다. 원하지 않은 투표나 사진 gallery 가 들어온다 |
| 갇힘 | 잘못된 출발점에 묶인다. 다른 기능 구성에나 어울렸을 navigation 요소를 계속 끌고 가게 된다 |
| feature creep | 원하는 기능을 다 보여 주도록 고쳐 갈수록 화면이 투박해진다 |

핵심은 세 번째다. 처음 받은 화면이 기준점이 돼 버리면 그 뒤의 수정은 전부 그 화면을 고치는 일이 된다. 더 나은 구조가 있었는지는 알 수 없게 된다.

### 탐색 단계의 prompt 요령

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-tips-explore.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

- **구체적으로 쓴다.** 앱이 가질 기능과 큰 방향을 처음부터 생각해서 적는다. 내 앱이 어떤 문제를 풀어야 하는지는 agent 보다 내가 더 잘 안다
- **style 의 단서를 준다.** 앱이 불러일으켰으면 하는 분위기나 느낌이 있다면 prompt 에 쓴다. book club 이라면 coffee shop 의 따뜻한 분위기와 색감인지, 종이의 질감과 아름다운 typography 인지 같은 것이다
- **여러 안을 요청한다.** 세션이 가장 중요하다고 꼽는 항목이다. 서로 다른 방향을 여럿 놓고 비교해 볼 수 있는 가장 좋은 때가 초반이다

세션이 보여 주는 개선된 prompt 는 세 문단이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-prompt-variations.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

1. 반복되는 book club 모임을 기록하는 mobile 앱의 interface 를 **서로 다른 variation 열 개**로 만들어 달라고 한다
2. 기능을 구체적으로 적는다. 다음 모임이 언제인지와 읽기 목표 보기, 읽고 있는 책에 comment 달기, 서로의 진도 확인하기, 지난 책 보기다
3. variation 마다 **자기만의 Swift preview 와 고유한 이름**을 주라고 한다

세 번째 문단이 이 세션 전체에서 반복되는 장치다. preview 가 따로 있어야 canvas 에서 하나씩 넘겨 가며 볼 수 있고, 이름이 있어야 다음 prompt 에서 "Cozy 의 typography" 처럼 가리킬 수 있다.

### 마음에 드는 요소 섞기

대개는 한 안이 통째로 마음에 들기보다 여러 안의 서로 다른 요소가 마음에 든다. 그럴 때는 어떤 variation 이 유망한지, 그리고 어떤 요소를 다른 것과 섞고 싶은지를 적은 prompt 를 이어서 보낸다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-prompt-remix.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

세션의 두 번째 prompt 는 이런 내용이다.

1. 새 file 에 새로운 variation 을 여러 개 만든다. racetrack 요소와 크게 보이는 책 표지를 넣고, 일부는 Cozy 의 typography 로, 일부는 grid 에서 detail 로 가는 navigation 으로, 일부는 Editorial 의 typography 로 만든다
2. 이번에도 variation 마다 Swift preview 를 주고 고유하고 설명적인 이름을 붙인다

agent 는 언급한 요소만 써서 새로운 hybrid 를 만든다. 순위표 idea 와 지금 읽는 책의 표지가 들어간 안들이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-remix-result.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

세션은 이 과정을 세 단어로 줄인다. **go wide, remix, repeat.** 넓게 벌리고, 섞고, 반복한다. 지치지 않고 새로운 안을 내놓는 것이 agent 의 가장 큰 힘 중 하나라는 것이다.

발표자가 실제로 밟은 경로는 네 단계였다. Cozy 에서 출발한 design 에 racetrack 을 넣고, 중립적인 색으로 바꾸고, 중복을 줄여 단순하게 만들었다. 구조가 잡혔으니 이제 interaction 과 세부를 다듬을 차례다.

## 앱이 쓰이고 있는 것처럼 만들기

개발 초기에 여러 사람에게 앱을 써 보게 하고 feedback 을 받는 것은 좋은 방법이다. 하지만 사람들이 자기 content 를 넣어 써 볼 수 있는 상태가 되려면 아직 먼 앱이 많다.

---

### lived in 이란?

누군가 실제로 한동안 써 온 것처럼 content 가 채워진 상태를 말한다. agent 가 앱을 쓰는 사람의 역할을 대신 맡아서 그 상태를 만들어 줄 수 있다. book club 앱이라면 회원들의 이름, 읽은 책 목록, 책을 두고 오간 대화 같은 것이다.

내가 가져온 image 까지 더하면, 내용이 느슨하게 채워진 빈 template 이 실제 사용에 가까운 화면으로 바뀐다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-lived-in.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

placeholder 로 채운 화면은 무엇이든 정돈돼 보인다. 긴 제목, 많은 회원, 빈 목록이 들어와야 design 의 약한 곳이 드러난다.

---

### sample content 단계의 prompt 요령

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-tips-content.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

- **preview 를 하나가 아니라 여러 개 요청한다.** 앞 단계와 같은 원칙이다
- **edge case 는 직접 멈춰서 생각한다.** 모임이 아직 잡히지 않았을 때 detail 영역은 어떻게 보이는가 같은 질문이다
- **구체적으로 쓴다.** interface 의 어느 state 를 바꿔 가며 볼 것인지 명시해서 agent 가 빠뜨릴 위험을 줄인다. 그리고 sample content 가 앱의 사용자층에 그럴듯하도록 충분한 context 를 준다. 이 앱이라면 토론 내용이 책에 관한 것이어야 한다
- **끝없이 늘어날 수 있는 요소를 시험한다.** 회원 수, 대화의 길이, 지난 책의 수 같은 것이다. 긴 입력도 여기에 든다. text 가 잘려도 되는가, 여러 줄로 넘어가야 하는가를 정해야 한다

여기에 하나가 더 붙는다. agent 가 쓴 예제 content 를 **재사용할 수 있고 읽기 쉬운 형태로 별도 file 에** 두게 한다. 그래야 내가 들어가서 고칠 수 있다.

세션의 prompt 는 이렇다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-prompt-content.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

1. 새 Swift file 을 만들어 이 design 의 variation 들을 보여 준다. 긴 text 와 짧은 text, 많은 회원과 적은 회원, 그리고 내가 생각하지 못했을 다른 UI state 를 다룬다
2. variation 들이 재사용 가능한 model 을 공유하게 해서 내가 읽고 고칠 수 있게 하고, 나중의 다른 view 도 쓸 수 있게 한다
3. variation 마다 Swift preview 를 주고 설명적인 이름을 붙인다

첫 문단의 마지막 구절이 눈에 띈다. 내가 떠올린 edge case 를 적되 agent 에게도 더 찾아보라고 여지를 준다.

### content 가 드러낸 문제와 수정

Xcode 는 variation 마다 preview tab 을 보여 주고, 발표자는 그것을 넘겨 가며 네 가지를 발견한다.

| 발견한 것 | 고친 방법 |
|---|---|
| 비어 있는 상태의 UI 가 없다. 새 책을 지정할 방법도 계정을 관리할 방법도 없다 | 계정 관리와 call to action control 을 추가 |
| 다음 모임 설명이 아주 길면 책 표지를 침범한다 | 잘리도록 허용. 책 제목은 표지와 중복이라 아예 뺌 |
| 참가자가 많으면 leaderboard 가 너무 길어져서 토론까지 scroll 이 길다 | 내 상대 순위는 항상 보이게 하고 expand control 로 전체 목록을 펼침 |
| 다양한 책 표지가 들어오니 화면이 표지에 반응하는 것이 보기 좋다 | detail page 가 표지의 색에 맞춰 바뀌게 함 |

앞의 셋은 문제를 찾은 것이고 마지막은 idea 를 얻은 것이다. 실제 같은 content 는 결함만 보여 주는 것이 아니라 design 의 방향도 준다.

세션은 한계도 분명히 한다. 실제로 앱을 써 본 사람들의 feedback 을 이길 수 있는 것은 없다. 이 방법은 feedback 단계를 앞당겨 시작하는 수단이다.

## 핵심 순간 조율하기

여기까지는 navigation, control, 서체, 색 같은 정적인 요소였다. SwiftUI 로는 interaction, animation, transition 까지 다룰 수 있고, 이쪽은 맞추기가 더 어렵다.

### 움직임의 종류

세션은 animation style 두 가지와 그 밖의 동적 요소 세 가지를 든다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-animation-styles.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

| 종류 | 내용 | 세션의 예 |
|---|---|---|
| ease | 물체가 부드럽게 가속하거나 감속하거나 둘 다 한다. 걸리는 시간을 정한다 | |
| spring | spring 에 끌리는 물체의 움직임을 흉내 낸다. stiffness, damping, mass 세 값을 조절한다 | |
| friction 과 inertia | 끌어서 움직일 때 요소가 얼마나 무겁게 느껴지는가 | Music 에서 sheet 를 닫을 때의 무게감 |
| device motion | accelerometer 나 gyroscope 에 앱이 어떻게 반응하는가 | Wallet 의 Apple Cash card 가 보여 주는 parallax |
| haptics | 중요한 순간이나 특별한 mode 를 어떻게 전달하는가 | Find My 에서 물건에 가까워질 때의 haptic |

SwiftUI 에서 ease 는 [easeInOut](https://developer.apple.com/documentation/swiftui/animation/easeinout){:target="_blank"} 계열이고 spring 은 [spring](https://developer.apple.com/documentation/swiftui/animation/spring){:target="_blank"} 계열의 [Animation](https://developer.apple.com/documentation/swiftui/animation){:target="_blank"} 이다. book club 앱의 핵심 순간은 animation 에 관한 것이라서 세션은 이 둘에 집중한다.

---

### tuning panel 이란?

animation 의 값은 조금만 달라져도 느낌이 달라진다. 맞는 값을 빨리 정하려면 어떻게 해야 할까.

한 가지 방법은 preview 를 띄워 두고 코드의 상수를 고치는 것이다. 잘 통할 때도 있지만, 관심 있는 상수가 코드의 여러 곳에 흩어져 있으면 오가는 일이 번거롭다.

그래서 세션이 권하는 것이 tuning panel 이다. **내 interface 의 특정 parameter 를 조절하는 일만 하는 전용 UI** 다. 세션의 간단한 예는 화면의 요소를 목표 지점으로 던져 보면서 spring 의 성질을 살피는 화면이고, menu 버튼을 누르면 값을 바꿔 볼 수 있는 panel 이 올라온다.

요점은 이 panel 을 직접 만들지 말고 agent 에게 만들게 하라는 것이다. 예전이라면 조율용 UI 를 만드는 비용이 조율로 얻는 이득보다 커서 건너뛰던 일이다.

---

### tuning panel 단계의 prompt 요령

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-tips-tuning.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

- **무엇을 바꿔 가며 볼지 자세히 쓴다.** animation style 을 비교하려는 것인지 spring curve 의 세부를 보려는 것인지, 요소가 여럿인지, view hierarchy 에 들어오고 나가는 transition 이 있는지
- **animation 을 phase 로 나눠 달라고 한다.** panel 이 이해하기 쉬워지고, 나와 agent 가 animation 의 특정 부분을 가리키는 공통의 말을 갖게 된다
- **animation 말고 다른 용도로도 쓴다.** 앱의 state 를 바꾸거나, 색, font style, 시각적 offset 을 바꿔 보는 데도 panel 이 쓸모 있다
- **더 넓은 창에서 나란히 놓이는 layout 을 지정한다.** UI 와 panel 을 옆에 두면 값을 바꾸고 결과를 보는 사이에 화면을 오갈 필요가 없다

phase 의 예로 세션은 book club 앱의 transition 을 든다. phase 1 에서 view 가 detail page 로 전환되고, phase 2 에서 content 의 각 줄이 시차를 두고 차례로 들어온다.

---

### transition 을 실제로 조율하기

발표자는 이 transition 이 어딘가 어색하다고 느낀다. delay 와 시차를 둔 등장 timing 이 원인인 것 같다. 그래서 이런 prompt 를 쓴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-prompt-tuning.png)

출처: WWDC26 - Create UI prototypes using agents in Xcode

1. 책 grid 와 detail 화면 사이의 animation 을 관리하는 전용 view 를 만든다. animation 에는 phase 가 둘 있다
2. phase 1 은 책 grid 와 detail page 사이의 transition 이고, phase 2 는 detail page 가 나타날 때 실행되는 animation 들이다
3. animation curve, parameter, timing, delay 에 여러 선택지를 주고, 각 phase 를 이 view 에서 따로 재생할 수 있게 한다
4. 별도 file 에, compact 보다 넓은 폭에서는 UI 와 control panel 을 나란히 보여 주는 view 를 만든다. iPad 같은 경우다. 여기에 Swift preview 를 준다

agent 가 준 view 는 처음에는 spring 예제처럼 panel 을 켜고 끄는 형태로 보인다. panel 이 UI 를 가려서 불편하다. canvas 의 resize control 을 눌러 preview 를 넓히면 네 번째 문단에서 요청한 대로 UI 와 panel 이 나란히 놓인다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-resize-control.png)

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-227/wwdc26-227-tuning-side.png)

panel 에는 phase 를 하나씩 따로 재생하는 control 이 있어서 각 parameter 가 animation 에 주는 영향을 바로 볼 수 있다. 발표자는 delay 와 stagger 값을 줄이고, animation style 을 bouncy preset 으로 바꾼다. SwiftUI 의 [bouncy](https://developer.apple.com/documentation/swiftui/animation/bouncy){:target="_blank"} 에 해당하는 것으로 보인다. 책 표지가 전환된 뒤 이어지는 animation 들이 매끄러워진다.

세션은 이것을 agent 로 prototype 할 때 가장 강력한 흐름 중 하나라고 부른다. view 의 여러 구성을 다루거나 animation 과 interaction 의 값을 고르는 중이라면 언제든 tuning panel 을 만들어서 feedback loop 를 줄이라는 것이다.

## 정리

세션의 세 단계에 공통된 틀을 표로 모으면 이렇다.

| 단계 | agent 에게 시키는 것 | 내가 하는 것 |
|---|---|---|
| UI 탐색 | 기능을 명시한 variation 여러 개 | 마음에 드는 요소를 골라 섞으라고 다시 요청 |
| lived in | edge case 를 담은 sample content 와 state 별 preview | edge case 를 직접 떠올리고, 드러난 문제를 판단 |
| 핵심 순간 | phase 로 나눈 tuning panel | 값을 움직여 보고 느낌으로 결정 |

세 단계 모두에 들어가는 문장은 하나다. variation 마다 Swift preview 와 이름을 준다.

실제 프로젝트에 가져갈 점을 적는다.

- 새 화면을 agent 에게 맡길 때 첫 prompt 에 기능 목록을 적고 안을 여러 개 받는다. 화면 하나만 받으면 그 화면이 기준점이 된다
- variation 은 preview 이름으로 구분하게 한다. [Preview](https://developer.apple.com/documentation/swiftui/preview%28_:body:%29){:target="_blank"} macro 의 첫 인자가 이름이라서 canvas 에서 이름으로 고를 수 있고, 다음 prompt 에서 그 이름으로 가리킬 수 있다
- sample data 는 view 안에 흩어 두지 말고 별도 file 의 model 로 받는다. preview 용 fixture 로 계속 쓸 수 있다
- 긴 text, 많은 항목, 빈 상태는 preview 로 따로 만들어 둔다. agent 덕분에 이 preview 들을 만드는 비용이 거의 없어졌다
- animation 값을 정할 때 상수를 고치고 다시 보는 것을 반복하고 있다면 tuning panel 을 만들게 한다. 조율이 끝나면 정한 값만 코드에 남기고 panel 은 지우면 된다
