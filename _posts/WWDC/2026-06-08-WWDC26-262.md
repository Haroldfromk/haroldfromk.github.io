### optional 과 some any 의 괄호

지금까지 `some` 이나 `any` 를 optional 과 같이 쓰려면 `(any Vehicle)?` 처럼 괄호를 쳐야 했다. 연산자 우선순위 규칙에서 나온 제약인데, 괄호 없는 `any Vehicle?` 가 뜻할 수 있는 것은 사실상 하나뿐이다. Swift 6.4 부터는 괄호 없이 쓸 수 있다.

```swift
protocol Vehicle {}
struct Lander: Vehicle {}

func park(_ vehicle: any Vehicle?) {}
func makeVehicle() -> some Vehicle? { Lander() as Lander? }
```

이 부분은 세션 Code 탭에 코드가 없어서 위 예제를 직접 만들어 빌드했다.

### Task 가 삼킨 에러 경고와 defer 안의 await

`Task { }` 안에서 에러가 던져졌는데 그 Task 를 어디에도 저장하지 않으면, 에러는 아무에게도 전달되지 않고 사라진다. Swift 6.4 는 이 상황에 경고를 낸다.

```swift
Task {
    try lander.fly(to: moon)
}
```

실제로 빌드하면 이런 경고가 나온다.

```
warning: unstructured throwing task created by 'init(name:priority:operation:)' is not used,
which may accidentally ignore errors thrown inside the task [#NoUseUnstructuredThrowingTask]
```

고치는 방법은 두 가지다. Task 안에서 에러를 처리하거나,

```swift
Task {
    do {
        try lander.fly(to: moon)
    }
    catch {
        lander.abort()
    }
}
```

Task 를 변수에 담아 두고 나중에 결과를 확인한다.

```swift
let landingTask = Task {
    try lander.fly(to: moon)
}

defer {
    await orbiter.rendezvous(with: lander)
}

try await orbiter.justHangOut(waitingFor: landingTask)
```

두 번째 코드에는 변화가 하나 더 들어 있다. **`defer` 블록 안에서 `await` 를 쓸 수 있게 됐다.** 예전에는 defer 안에서 async 함수를 부를 수 없어서, 정리 작업이 async 면 함수의 모든 종료 지점에 같은 코드를 반복해야 했다.

빌드할 때는 `lander`, `moon`, `orbiter` 타입을 빈 struct 로 만들어 붙였다.

### weak let 과 Sendable 이 아니라는 선언

`weak var` property 가 하나 있다는 이유로 class 에 `@unchecked Sendable` 을 붙이는 경우가 있었다. `var` 는 언제든 바뀔 수 있으니 compiler 가 안전하다고 볼 수 없었기 때문이다. 이제 `weak let` 으로 선언할 수 있다. 값을 바꿀 수 없으니 Sendable 검사를 그대로 받을 수 있다.

```swift
final class Spacecraft: Sendable {
    ...
    weak let dockedAt: SpaceStation?
    ...
}

class Mission: ~Sendable { ... }

class CrewedMission: Mission, @unchecked Sendable { ... }
```

반대 방향도 생겼다. `~Sendable` 은 **"이 타입은 Sendable 이 아니다"** 를 명시하는 문법이다. 실제로 `Mission` 을 Sendable 이 필요한 자리에 넘기면 `type 'Mission' does not conform to the 'Sendable' protocol` 에러가 난다. 그러면서도 subclass 가 Sendable 이 되는 것은 막지 않아서, 위의 `CrewedMission` 처럼 하위 타입에서 따로 채택할 수 있다.

`...` 자리는 세션 코드에서 생략된 부분이다. 빌드할 때는 `SpaceStation` class 와 initializer 를 채워 넣었다.

### 두 번째 memberwise initializer

struct 에 `private` property 가 하나라도 있으면 자동으로 만들어지는 memberwise initializer 도 `private` 이 됐다. 다른 파일에서는 쓸 수 없어서 결국 initializer 를 손으로 써야 했다.

```swift
struct Briefing {
    internal var topic: String
    internal var scheduledAt: Date
    private  var attendees: [Person] = []
}
```

이제 이런 struct 에는 initializer 가 두 개 생긴다. 모든 property 를 받는 `private` 버전과, `private` property 를 뺀 `internal` 버전이다.

```swift
// Generated memberwise initializers:
// extension Briefing {
//     private init(topic: String, scheduledAt: Date, attendees: [Person] = []) { ... }
//     internal init(topic: String, scheduledAt: Date) { ... }
// }
```

다른 파일에서 `Briefing(topic: "Launch", scheduledAt: .now)` 를 호출해서 빌드되는 것을 확인했다. 두 번째 initializer 가 만들어지려면 `private` property 에 기본값이 있어야 한다는 점은 코드에서 읽을 수 있다.

### anyAppleOS availability

Apple 플랫폼이 늘어나면서 `@available` 줄도 같이 길어졌다. 작년에 OS 버전 번호가 하나로 맞춰졌고, 올해는 플랫폼 이름까지 하나로 줄일 수 있게 됐다.

```swift
// before
extension Mission {
    @available(macOS 27, iOS 27, watchOS 27, tvOS 27, visionOS 27, *)
    func showStatus() { ... }

    @available(macOS 27, iOS 27, watchOS 27, visionOS 27, *)
    @available(tvOS, unavailable)
    func launch() { ... }

    #if os(macOS) || os(iOS) || os(watchOS) || os(tvOS) || os(visionOS)
    func makeLiveActivityWidget() -> some Widget { ... }
    #endif
}
```

```swift
// after
extension Mission {
    @available(anyAppleOS 27, *)
    func showStatus() { ... }

    @available(anyAppleOS 27, *)
    @available(tvOS, unavailable)
    func launch() { ... }

    #if os(anyAppleOS)
    func makeLiveActivityWidget() -> some Widget { ... }
    #endif
}
```

쓰는 방법은 세 가지다.

- 모든 플랫폼의 조건이 같으면 `anyAppleOS` 하나로 끝낸다
- 예외가 있으면 `anyAppleOS` 로 기본값을 잡고, 예외만 플랫폼별 attribute 로 덧붙인다
- `#if os(anyAppleOS)` 로 조건부 컴파일에도 쓴다

SDK 의 표준 라이브러리 interface 도 이미 `@available(anyAppleOS 27.0, *)` 로 적혀 있었다.

### diagnose attribute 로 경고 조절

API 가 deprecated 됐는데 새 API 로 바로 옮길 수 없을 때가 있다. 프로젝트 전체 설정을 건드리지 않고 그 함수 하나에서만 경고를 끄고 싶다면 `@diagnose` 를 쓴다.

```swift
@diagnose(DeprecatedDeclaration, as: ignored, reason: "Flying with surplus hardware")
func makeApolloSoyuzMission() -> Mission {
    CrewedMission(
        rocket: makeSaturnIRocket(),
        payload: makeApolloCSM(),
        crew: [.daniellePoole, .nathanMorrison]
    )
}

@diagnose(StrictMemorySafety, as: warning)
func uplinkCommand(from receiver: inout Receiver, to computer: inout Computer) {
    let commandSize = receiver.receiveInt()
    receiver.withReceivedData(byteCount: commandSize) {
        computer.receiveUplinkedCommand($0)
    }
}

@diagnose(ErrorInFutureSwiftVersion, as: error)
func fetchPosition() -> (x: Double, y: Double, z: Double) {
    return self.rotation
}
```

#### diagnose 로 선언 하나의 경고 동작 바꾸기

`@diagnose(<경고 그룹>, as: <동작>)` 형태다. 첫 인자는 경고 메시지 끝에 `[#DeprecatedDeclaration]` 처럼 붙어 나오는 warning group 이름이고, 동작은 세 가지다.

- `ignored`: 그 선언 안에서는 해당 경고를 내지 않는다. `reason:` 으로 이유를 남길 수 있다
- `warning`: 기본으로 꺼져 있는 경고를 그 선언에서만 켠다. 예제는 보안이 중요한 함수에서 strict memory safety 검사를 켜서 unsafe API 사용을 점검한다
- `error`: 경고를 에러로 올린다. 예제는 "다음 Swift 버전에서 에러가 될 경고" 를 지금 에러로 만든다

deprecated 함수를 부르는 함수 세 개 (attribute 없음, `as: ignored`, `as: error`) 를 만들어 빌드해 보니, 차례대로 경고, 조용함, 에러가 나왔다. 위 세션 코드의 타입들 (`CrewedMission`, `Receiver` 등) 은 세션에 정의가 없어서 같은 attribute 를 단순한 함수에 붙여 확인했다.

### module selector

두 module 이 같은 이름의 타입을 가지면 충돌이 난다. 세션의 예시는 실제 110m 짜리 로켓을 뜻하는 `Rocket` module 의 `SaturnV` 와, 기념품 가게 장난감을 뜻하는 `GiftShopToys` module 의 `SaturnV` 다.

```swift
import Rocket
import GiftShopToys

let rocket1 = SaturnV()            // could mean `Rocket::SaturnV` or `GiftShopToys::SaturnV`
let rocket2 = Rocket.SaturnV()     // prefers `Rocket::Rocket.SaturnV`
let rocket3 = Rocket::SaturnV()    // correctly finds `Rocket::SaturnV`
```

`rocket1` 은 어느 쪽인지 알 수 없어서 에러다. 지금까지의 해결책은 `Rocket.SaturnV` 처럼 module 이름을 점으로 붙이는 것이었는데, **module 안에 module 과 같은 이름의 타입이 있으면** 이 방법이 깨진다. Swift 는 module 이름보다 타입 이름을 먼저 찾기 때문에, `Rocket.SaturnV` 를 "`Rocket` 타입의 member `SaturnV`" 로 해석하고 그런 member 가 없다는 에러를 낸다.

Swift 6.3 의 해결책은 점을 `::` 로 바꾸는 것이다.

#### 콜론 두 개로 module 지정하기

`::` 왼쪽의 이름은 **항상 module 이름**으로 해석된다. 그래서 `Rocket::SaturnV` 는 타입 `Rocket` 을 무시하고 module `Rocket` 으로 바로 간다.

method 나 property 이름에도 쓸 수 있다. 한 타입이 서로 다른 module 의 extension 에서 같은 이름의 method 를 받았을 때 쓴다.

```swift
// Module Chemistry
public protocol Flammable { ... }

extension Flammable {
    /// Set `self` on fire.
    public func fire() { ... }
}

// Module HumanResources
import Chemistry

public protocol Employee { ... }

extension Employee {
    /// Remove `self` from job.
    public func fire() { ... }
}

public class LaunchPadTechnician: Employee, Flammable { ... }

// Module main
import HumanResources
import Chemistry

let launchPadTechnician = LaunchPadTechnician(...)

launchPadTechnician.HumanResources::fire()
```

불을 붙이는 `fire()` 와 해고하는 `fire()` 가 같은 이름이다. 세션의 표현대로 잘못 부르면 누군가의 하루를 망친다.

Swift package 에 module 네 개 (`Rocket`, `GiftShopToys`, `Chemistry`, `HumanResources`) 를 만들어 확인했다. `Rocket::SaturnV()` 는 `Rocket` module 의 타입을 찾았고, `HumanResources::fire()` 는 `Employee` 쪽 구현을 불렀다.

세션이 정리한 쓰임새는 이렇다.

- 내가 고칠 수 없는 두 module 이 충돌할 때 쓴다. SwiftUI 와 데이터베이스 package 가 둘 다 `View` 라는 타입을 가진 경우가 예다
- macro expansion 처럼 자동 생성되는 코드에서 방어적으로 쓴다. 생성된 코드는 그 파일에 무엇이 import 돼 있을지 알 수 없다
- **일부러 이름이 충돌하게 API 를 설계하고 module selector 로 구분하는 것은 권하지 않는다.** 코드는 모호하지 않아도 에러 메시지와 문서가 헷갈리게 된다

### 표준 라이브러리

task cancellation, dictionary 변환, 파일 경로 세 가지가 소개됐다.

비용이 큰 작업을 시작하기 전에는 Task 가 취소됐는지 확인하는 것이 맞다. 그런데 취소된 뒤에도 끝까지 해야 하는 일이 있다. 파일이 깨지지 않게 쓰던 데이터를 마저 쓰는 경우가 그렇다.

```swift
extension Radio {
  func send(_ data: [UInt8]) {
    if Task.isCancelled { return }
    // ...
  }
}

extension EmergencyTransponder {
  func sendSOS() {
    withTaskCancellationShield {
        radio.send(makeSOSPacket())
    }
  }
}
```

세션 Code 탭의 원본은 `func send(_ data: [UInt8] {` 로 닫는 괄호가 빠져 있어서 그 부분만 고쳤다.

#### withTaskCancellationShield 로 취소 확인 막기

shield 안에서는 `Task.isCancelled` 같은 취소 확인이 **항상 false** 를 돌려준다. Task 가 이미 취소됐어도 `radio.send` 는 중간에 포기하지 않고 SOS packet 을 끝까지 보낸다. SDK 에는 sync 버전과 async 버전이 모두 들어 있다.

세션이 덧붙인 주의점은 **이 구간을 짧게 유지하라**는 것이다. 이미 시작한 일을 마무리하거나 되돌리는 데만 쓴다. 긴 작업을 통째로 감싸면 취소가 의미 없어진다.

다음은 dictionary 다. `mapValues` 는 closure 에 값만 넘겨준다. 새 값을 계산할 때 key 도 필요하면 dictionary 를 손으로 다시 만들어야 했다. 세션은 key 와 값을 같이 넘겨주는 `mapKeyedValues` 를 소개했다.

마지막은 파일 경로다. 플랫폼마다 경로 표현이 조금씩 달라서 문자열로 직접 다루면 실수하기 쉽다. 세션은 Swift System 의 타입을 바탕으로 한 `FilePath` 가 표준 라이브러리에 들어왔다고 설명했다.

> `mapKeyedValues` 와 표준 라이브러리의 `FilePath` 는 Xcode 27.0 에서 빌드되지 않았다. `mapKeyedValues` 는 SDK 에 선언이 없었고, `FilePath` 는 `import System` 을 해야 쓸 수 있는 기존 타입만 있었다. 빌드를 확인하지 못해서 두 API 의 코드는 싣지 않는다.

### Swift Testing

Swift 6.4 의 Swift Testing 은 테스트 동작을 더 세밀하게 조절할 수 있게 됐다. 치명적이지 않은 문제를 드러내는 방법, 실행 중에 테스트를 건너뛰는 방법, flaky test 를 반복하는 방법, XCTest 와 섞어 쓰는 방법 네 가지다.

```swift
@Test(arguments: allRockets)
func testBurn(rocket: Rocket) throws {
    // solid-fuel rocket engines can't be stopped
    if rocket.engineType == .solid {
        try Test.cancel("\(rocket.name) has solid fuel")
    }

    rocket.burn(for: .seconds(150))
    let remaining = rocket.propellantKg / rocket.totalPropellantKg

    if remaining < 0.10 {
        Issue.record(
            "\(rocket.name) remaining fuel is below 10% reserve target",
            severity: .warning
        )
    }

    #expect(remaining > 0.02, "\(rocket.name) propellant critically low - abort")
}
```

빌드할 때는 `Rocket` 을 값 타입으로 만들었기 때문에 함수 첫 줄에 `var rocket = rocket` 을 추가했다.

#### Issue.record 의 severity 로 경고 남기기

[`Issue.record`](https://developer.apple.com/documentation/testing/issue){:target="_blank"} 에 `severity: .warning` 을 주면 테스트를 실패시키지 않고 문제만 기록한다. 조사할 가치는 있지만 CI 를 막을 정도는 아닌 상황에 쓴다. 위 예제에서는 남은 연료가 10% 아래면 경고, 2% 아래면 실패다.

실행해 보면 경고가 기록되고 테스트는 통과로 끝난다.

```
Test testBurn(rocket:) recorded a warning ... Atlas remaining fuel is below 10% reserve target
Test testBurn(rocket:) with 2 test cases passed after 0.001 seconds with 1 warning.
```

#### Test.cancel 로 실행 중에 테스트 취소하기

`try Test.cancel("이유")` 는 그 지점에서 테스트를 취소한다. parameterized test 에서 특히 쓸모가 있다. 인자 중 일부만 실행하면 안 될 때, 그 인자의 test case 만 취소하고 나머지는 그대로 돌릴 수 있다. 끝까지 돌리거나 실패 처리하는 것보다 의도가 분명하다. 위 실행 결과에서도 고체 연료 로켓은 취소되고 전체 테스트는 통과했다.

flaky test 는 `swift test` 의 새 옵션으로 다룬다.

```bash
swift test --repeat-until fail --maximum-repetitions 20
```

`--repeat-until` 은 `pass` 또는 `fail` 을 받고, `--maximum-repetitions` 로 최대 횟수를 정한다. `pass` 로 주면 실패한 테스트만 다시 돌리기 때문에 이미 통과한 테스트에 시간을 쓰지 않는다. `swift test --help` 에 따르면 두 옵션은 Swift Testing 테스트에만 적용된다.

마지막은 XCTest 상호운용이다. XCTest API 로 만든 helper 가 많은 프로젝트는 Swift Testing 으로 옮기기가 부담스러웠다. `@Test` 함수 안에서 `XCTAssertEqual` 을 부르면 실패해도 아무 일도 일어나지 않았기 때문이다.

```swift
func checkedTransmitAndReceive(on radio: Radio,
                               packet: Packet,
                               expectedByteCount: Int) throws -> [UInt8] {
    try radio.transmit(bytes: packet.data)
    let bytes = try radio.receive()
    XCTAssertEqual(bytes.count, expectedByteCount)
    return bytes
}

@Test
func pingTest() throws {
    let radio = Radio()
    let bytes = try checkedTransmitAndReceive(on: radio, packet: .ping, expectedByteCount: 8)
    #expect(bytes == [0x00, 0x00, 0xf0, 0x37, 0x0f, 0xc7, 0x00, 0x01])
}
```

Swift 6.4 에서는 양방향으로 이어진다.

- Swift Testing 에서 부른 XCTest assertion 실패가 test issue 로 보고된다
- `XCTestCase` 안에서 부른 `#expect` 도 동작한다

그래서 helper 를 Swift Testing API 로 만들어 두면 어느 쪽에서 불러도 같은 결과가 나온다.

주의할 점은 기본 동작이다. 기존 프로젝트가 이미 이렇게 섞어 쓰고 있을 수 있어서, Swift Testing 에서 부른 XCTest assertion 실패는 **기본으로 warning** 이다. 테스트 실패로 올리려면 Xcode build setting 에서 켠다. 같은 구조의 테스트를 만들어 돌려 보니 실제로 이렇게 나왔다.

```
Test xctestFromSwiftTesting() recorded a warning at T.swift:32:1: Issue recorded
Test xctestFromSwiftTesting() recorded a warning at T.swift:32:1: An API was misused
Replace XCTest API such as 'XCTAssert' with a Swift Testing equivalent such as '#expect'.
Test xctestFromSwiftTesting() passed after 0.001 seconds with 2 warnings.
```

반대 방향인 `XCTestCase` 안의 `#expect` 실패는 바로 테스트 실패로 잡혔다. `Radio` 와 `Packet` 은 세션에 정의가 없어서, 위 코드 대신 `XCTAssertEqual` 을 부르는 단순한 helper 로 같은 동작을 확인했다.

마이그레이션 전략은 [Migrate to Swift Testing](https://developer.apple.com/videos/play/wwdc2026/267/){:target="_blank"} 세션이 따로 다룬다.

### Subprocess 1.0

작년에 공개된 [Subprocess](https://github.com/swiftlang/swift-subprocess){:target="_blank"} package 가 1.0 이 됐다. 다른 프로그램을 실행하고 그 출력을 받아 오는 API 다. 실사용 피드백을 반영해 바뀐 점은 다음과 같다.

- execution 타입이 단순해졌다
- 에러 처리가 개선됐다
- process 출력을 stream 으로 받는 편의 API 가 생겼다
- 플랫폼별 process file descriptor 와 termination status 를 지원해서, 플랫폼마다 다른 의미를 더 정확히 반영한다

`run` 을 호출할 때 output 을 `.sequence` 로 주면 표준 출력이 `AsyncBufferSequence` 로 execution 객체에 담겨 온다. 각 stream 은 한 번만 만들어진다는 것이 보장된다.

```swift
import Subprocess

let result = try await Subprocess.run(.name("ls"),
                                      input: .none,
                                      output: .sequence,
                                      error: .string(limit: 4096)) { execution in
    var swiftFiles: [String] = []
    for try await line in execution.standardOutput.strings() where line.hasSuffix(".swift") {
        swiftFiles.append(line)
    }
    return swiftFiles
}

for swiftFile in result.closureResult {
    print("Swift file: \(swiftFile)")
}
```

#### strings 로 출력을 한 줄씩 읽기

`strings()` 는 byte 로 들어오는 출력을 줄 단위 문자열로 바꿔 준다. grapheme cluster 경계를 지키기 때문에 한글이나 emoji 같은 multi-byte 문자가 buffer 경계에서 잘리는 것을 걱정하지 않아도 된다.

> 위 코드는 세션 코드를 고친 것이다. 세션 Code 탭의 원본은 `standardOtput` 오타와 변수 이름 불일치가 있었고, 결과를 `result.closureOutput` 으로 읽는데 1.0.2 에서 실제 이름은 `closureResult` 였다. 또 원본처럼 filter 한 sequence 를 closure 밖으로 돌려준 뒤 읽으면 `Bad file descriptor` 로 실행 중에 죽었다. 그래서 closure 안에서 다 읽고 배열을 돌려주는 형태로 바꿨고, 이 버전이 `Swift file: main.swift` 를 출력하는 것을 확인했다.

### Foundation

Foundation 소식은 새 타입 하나와 내부 재작성이다.

`ProgressManager` 는 진행률 보고를 위한 새 타입이다. 세션이 든 특징은 세 가지다.

- async/await 방식의 concurrency 와 잘 맞게 설계됐다
- 진행률을 **조합하는 쪽**과 **보고하는 쪽**이 깔끔하게 나뉜다
- 추가 metadata 를 붙이는 구조적이고 type-safe 한 방법이 있다

```swift
let mission = ProgressManager(totalCount: 100)
try await rocket.launch(mission.subprogress(assigningCount: 100))

extension Rocket {
    func launch(_ progress: consuming Subprogress? = nil) async throws {
        let stage = progress?.start(totalCount: 3)
        try await ignite(); stage?.complete(count: 1)
        try await liftoff(); stage?.complete(count: 1)
        try await stageSeparation(); stage?.complete(count: 1)
    }
}
```

#### ProgressManager 와 Subprogress 로 진행률 나눠 맡기기

위쪽 (조합) 은 전체를 100 으로 잡고 그중 얼마를 하위 작업에 맡길지 `subprogress(assigningCount:)` 로 정한다. 아래쪽 (보고) 은 받은 `Subprogress` 를 `start(totalCount:)` 로 시작해서 자기 기준의 단계 수 (여기서는 3) 로 `complete(count:)` 를 부른다. 하위 작업은 자기가 전체의 몇 퍼센트인지 몰라도 된다.

`Subprogress` 는 noncopyable 타입이라 parameter 에 `consuming` 이 붙는다. 한 번 넘기면 호출한 쪽에서는 다시 쓸 수 없어서, 같은 몫을 두 군데에 맡기는 실수를 compiler 가 막는다.

세션 Code 탭의 원본은 첫 줄의 변수가 `manager` 인데 다음 줄에서 `mission` 으로 쓰고 있어서 `mission` 으로 맞췄다. `Rocket` 의 세 단계 함수를 빈 async 함수로 만들어 실행했고, 끝난 뒤 `mission.fractionCompleted` 가 1.0 인 것을 확인했다. Code 탭에는 `Observations` 로 진행률을 관찰하는 코드와 `deltaV` 같은 metadata 를 붙이는 코드도 있었는데, 오타가 있고 필요한 선언이 빠져 있어서 빌드하지 못했다. 그 둘은 싣지 않는다.

두 번째는 Swift-Foundation 이다. 2년 전에 시작한, Foundation 을 Swift 로 다시 써서 안전하고 일관된 cross-platform 코드로 옮기는 작업이다. 올해 진행된 부분은 이렇다.

- `Data` 의 더 많은 부분이 Swift 로 바뀌었다. span 접근, 동등 비교, 순회, 변경이 빨라졌다
- Apple 플랫폼에서 `Data` 와 `NSData` 사이의 bridging 이 빨라졌다
- `NSURL` 과 `CFURL` 이 하나의 Swift 구현으로 합쳐져서 더 빠르고 메모리를 덜 쓴다

Foundation 처럼 크고 오래된 라이브러리를 옮길 수 있는 이유는 Swift 의 언어 interoperability 다. 새 API 를 Swift 로 추가할 수 있고, 기존 API 의 겉모습을 바꾸지 않고 구현만 Swift 로 갈아 끼울 수 있다.

## Apple 플랫폼 밖의 Swift

세 번째 덩어리는 Swift 를 다른 언어, 다른 에디터, 다른 실행 환경으로 넓히는 이야기다. Apple 은 Weather 같은 앱, 실시간 스팸 전화 감지 같은 서비스, kernel, firmware 의 가장 낮은 층까지 Swift 를 쓰고 있고, Swift 를 소프트웨어 stack 의 모든 층에서 쓸 수 있는 언어로 만드는 것이 목표라고 한다.

### C 로 내보내는 Swift 함수

C 를 Swift 로 가져오는 것은 원래 쉬웠다. Swift 6.4 는 반대 방향, **Swift 로 쓴 함수를 C 에 내보내는 것**을 지원한다. Objective-C 에서 Swift 로 옮길 때 쓰던 `@objc` 와 같은 역할을 C 에 대해 하는 `@c` attribute 다.

`@c` 는 C 와 호환되는 타입만 다루는 함수에 붙일 수 있다. C 에서 Swift 로 import 할 수 있는 타입이면 반대로 내보낼 때도 쓸 수 있다. 정수, pointer, import 한 C struct, raw value 가 정수인 enum 이 그렇다. C 와 맞지 않는 타입을 넘기려고 하면 compiler 가 막는다.

세션의 데모는 로켓 발사 일정 앱에서 launch window 를 다루는 C 코드를 Swift 로 옮기는 과정이다. 이 부분은 Code 탭에 코드가 없어서 영상 화면의 코드를 옮겨 빌드했다. 먼저 C header 에 이런 선언이 있다.

```c
struct launch_window { unsigned start_time; unsigned end_time; };

/// Get the length of the launch window
unsigned launch_window_duration(struct launch_window window);
```

`struct launch_window` 의 정의는 영상에 나오지 않아서 field 이름에 맞춰 직접 썼다. 이제 C 구현 파일을 지우고 Swift 로 구현한다.

```swift
import CLaunch

@c @implementation public func launch_window_duration(_ window: launch_window) -> UInt32 {
    window.end_time - window.start_time
}

@c public func mean_launch_window_length(
    _ windows: UnsafePointer<launch_window>,
    _ count: UInt32
) -> Float {
    let buffer = UnsafeBufferPointer<launch_window>(start: windows, count: Int(count))
    let sum = buffer.reduce(0) { acc, window in
        return acc + launch_window_duration(window)
    }
    return Float(sum) / Float(buffer.count)
}
```

#### c 와 implementation 으로 C 함수 구현하기

두 함수의 차이는 `@implementation` 유무다.

- `@c @implementation`: **header 에 이미 선언된 C 함수의 구현**을 Swift 로 제공한다. 선언은 원래 header 에 있으니 새로 만들지 않는다. `launch_window_duration` 이 이 경우다
- `@c` 만: **header 에 없는 새 함수**를 내보낸다. Swift compiler 가 생성하는 C interop header 에 선언을 넣어 주기 때문에 C 코드에서 바로 부를 수 있다. 평균을 구하는 `mean_launch_window_length` 가 이 경우다

Swift package 에 C target 과 Swift target 을 나눠 만들어 빌드했다. C 에서 부르는 것도 된다. Swift file 을 `-emit-clang-header-path` 로 compile 하면 생성된 header 에 `mean_launch_window_length` 의 선언이 `SWIFT_EXTERN float mean_launch_window_length(struct launch_window const * _Nonnull windows, uint32_t count)` 로 들어간다. C 의 `main` 에서 원래 header 와 이 header 를 include 하고 window 둘 (10 ~ 40, 100 ~ 150) 을 넘기면 `launch_window_duration` 은 30, 평균은 40.0 이 나온다. 생성된 header 가 원래 header 를 다시 include 하므로 원래 header 에는 `#pragma once` 같은 include guard 가 있어야 한다.

세션은 여기에 safe interop 을 얹는다. C 함수를 Swift 에서 부를 때 배열 pointer 와 개수를 따로 넘기는 대신 [`Span`](https://developer.apple.com/documentation/swift/span){:target="_blank"} 을 넘길 수 있는 안전한 wrapper 가 제공된다. Swift 의 Span 은 C 로 자동 bridging 되고, C++ interoperability 는 이제 C++20 의 `std::span` 과도 이어진다. 화면에 나온 선언은 이런 모양이다.

```cpp
#include <span>

int sum(std::span<const int> const numbers [[clang::noescape]]);
```

이 선언은 Swift 에서 Span 을 받는 함수로 import 돼서 `sum([1, 2, 3, 4].span)` 처럼 부를 수 있다. Xcode 27.0 에서 `-cxx-interoperability-mode=default -Xcc -std=c++20` 만 주고 빌드하면 추가 flag 없이 이 호출이 compile 되고 10 이 찍힌다. C++ 쪽 정의에도 `[[clang::noescape]]` 를 똑같이 붙여야 한다. 선언에만 붙이면 clang 이 "conflicting types for 'sum'" 으로 막는다.

### Swift-Java 와 Android

[Swift-Java](https://github.com/swiftlang/swift-java){:target="_blank"} 는 Swift 와 Java 사이의 interoperability 를 맡는 package 다. 올해 추가된 것은 다음과 같다.

### WebAssembly 와 JavaScriptKit

open source toolchain 은 Swift 를 WebAssembly (Wasm) 로 compile 할 수 있다. Wasm 은 브라우저가 실행할 수 있는 binary 형식이다. native 앱, backend 서버, 웹 frontend 를 같은 언어로 쓸 수 있다는 뜻이다.

Swift 와 JavaScript 를 잇는 것은 open source 프로젝트 [JavaScriptKit](https://github.com/swiftwasm/JavaScriptKit){:target="_blank"} 이다. 예전에는 이름을 문자열로 찾는 동적 lookup 이 많았고 타입이 맞기를 바랄 수밖에 없었다. 최근 작업으로 bridging 이 더 안전하고 빨라졌다. 세션 화면의 코드는 보통의 Swift 코드처럼 보이지만 JavaScript 를 거쳐 WebGL 을 호출한다.

사례는 노트 앱 Goodnotes 다. iOS 앱에 더해 웹 버전을 만들었는데, 핵심 로직을 다른 언어로 다시 쓰고 버그를 잡고 두 codebase 를 유지하는 비용이 너무 컸다. 그래서 검증된 기존 Swift 코드를 Wasm 으로 compile 해서 웹에 올렸다.

그림처럼 View Model, 데이터와 sync, 렌더러를 Swift 로 한 번만 쓰고, 화면에 그리는 층만 플랫폼별로 갈아 끼운다. Goodnotes 의 benchmark 에서는 JavaScriptKit 의 safe bridging 이 dynamic bridging 보다 **35배에서 40배** 빨랐다고 한다.

### Embedded Swift

Embedded Swift 는 제약이 큰 환경에 맞게 언어를 덜어 낸 subset 이다. 사람들이 실제로 어떻게 쓰는지 보면서 쓸 수 있는 범위를 다시 넓히고 있다. 올해 추가된 것은 세 가지다.

- **existential type**: 같은 protocol 을 따르는 여러 타입을 한 배열에 담거나 함수에 넘길 수 있다 (`any Shape` 같은 타입)
- **untyped throws**: typed throws 는 에러 타입을 알 때는 좋지만 한 가지 타입으로 제한된다. existential 을 다루는 같은 구조를 써서 타입을 정하지 않은 `throws` 도 지원한다
- **coredump debugging**: debugger 가 변수를 보여 주려면 타입 layout 에 대한 metadata 가 필요한데, Embedded Swift 는 크기를 줄이려고 이것을 binary 에 넣지 않는다. 게다가 embedded 환경은 crash 순간의 메모리 dump 만 남는 경우가 많다. Swift 6.4 는 필요한 metadata 를 DWARF debug info 에 저장해서, binary 크기는 그대로 두고 coredump debugging 을 개선했다

여전히 subset 이기 때문에 쓸 수 없는 기능이 있다. `EmbeddedRestrictions` warning group 이 그런 기능을 알려 준다. embedded 와 일반 Swift 를 모두 지원하는 라이브러리는 embedded 에서 못 쓰는 기능을 쓰는 함수도 내보내야 할 수 있는데, 앞에서 본 `@diagnose` 로 이 경고를 선언 단위로 조절할 수 있다.

## 성능 튜닝

마지막 덩어리가 세션에서 가장 길다. Swift 는 가장 단순하게 쓴 코드도 충분히 빠르게 돌도록 설계돼 있다. 하지만 계산이 많거나 embedded 처럼 자원이 빠듯하면 코드를 조금 복잡하게 만들어서라도 성능을 더 짜내야 할 때가 있다. 세션은 이 기능들이 **평소에는 필요 없다**는 점을 먼저 짚고, optimizer 를 직접 조절하는 방법과 ownership 을 차례로 다룬다.

---

### inlining 제어

optimizer 의 강력한 기법 몇 가지는 코드를 복제해서 특정 상황에 맞게 다듬는 방식이다. 잘 맞으면 빨라지지만, 안 맞으면 프로그램이 더 크고 느려진다.

대표가 inlining 이다. 함수 호출을 그 함수의 본문으로 바꿔 넣고, 호출한 자리에 맞게 다시 최적화한다.

```swift
func histogram<Values>(of values: Values) -> [256 of Int] where Values: Sequence<UInt8> {
    var result = makeInts(randomized: false)

    for value in values {
        result[Int(value)] += 1
    }

    return result
}

func makeInts(randomized: Bool) -> [256 of Int] {
    if randomized {
        InlineArray { _ in Int.random(in: (.min)...(.max)) }
    } else {
        InlineArray(repeating: 0)
    }
}
```

`histogram` 은 `makeInts(randomized: false)` 를 부른다. inlining 하면 `makeInts` 의 `if randomized` 가 `histogram` 안으로 들어오고, 인자가 `false` 로 고정이니 optimizer 는 조건문을 통째로 지우고 `InlineArray(repeating: 0)` 한 줄만 남길 수 있다. 호출 비용도 사라지고 분기도 사라진다.

optimizer 는 함수와 호출 지점을 분석해서 inlining 이 이득일지 판단하는데, 가끔 틀린다. 그래서 직접 정할 수 있는 attribute 가 있다.

```swift
@inline(always)
func makeInts(randomized: Bool) -> [256 of Int] {
    if randomized {
        InlineArray { _ in Int.random(in: (.min)...(.max)) }
    } else {
        InlineArray(repeating: 0)
    }
}
```

#### inline always 로 inlining 강제하기

`@inline(never)` 는 예전부터 있었다. inlining 이 절대 이득이 아닐 때 금지한다. Swift 6.4 에 짝이 되는 `@inline(always)` 가 생겼다. optimizer 가 확신하지 못해도 inlining 하게 만든다.

그래도 못 하는 경우가 있다. override 될 수 있는 class method 는 실제로 어떤 구현이 불릴지 compile 시점에 알 수 없다. 그래서 class method 에 쓸 때는 `final` 과 같이 쓰라고 권한다.

---

### specialization 제어

또 하나의 중요한 최적화가 specialization 이다. generic 함수를 **특정 타입 전용으로 복제**해서 generic 을 다루는 비용을 없애고, 추가 최적화의 길을 연다. 위의 `histogram` 을 `[UInt8]` 전용으로 복제하면 `Values` 가 무엇이든 동작해야 한다는 부담이 사라진다.

문제는 optimizer 가 그 타입으로 불릴 것을 알아야 한다는 점이다. 라이브러리처럼 함수가 어떻게 쓰일지 compiler 가 볼 수 없는 경우가 있다.

```swift
@specialized(where Values == [UInt8])
func histogram<Values>(of values: Values) -> [256 of Int] where Values: Sequence<UInt8> {
    var result = makeInts(randomized: false)

    for value in values {
        result[Int(value)] += 1
    }

    return result
}
```

#### specialized 로 타입 전용 버전 요청하기

Swift 6.3 의 `@specialized` 는 attribute 안에 `where` 절을 써서 generic parameter 의 일부 또는 전부를 고정한다. Swift 는 그 조건에 맞는 전용 버전을 만들어 둔다. 느린 generic 코드가 한두 가지 타입으로 자주 불린다면 그 타입을 우선하라고 알려 주는 방법이다.

`@inline(always)` 와 `@specialized` 를 붙인 코드는 그대로 빌드됐다. 실제로 얼마나 빨라지는지는 측정하지 않았다.

### ownership

성능 튜닝에서 올해 가장 크게 바뀐 부분이 ownership system 이다. 세션은 새 기능을 소개하기 전에 배경부터 다시 정리한다.

Swift 의 성능 문제 상당수는 **불필요한 복사**에서 나온다. 데이터가 한 곳에 있는데 다른 곳에서도 필요하니, 새 저장 공간에 복사한다. 두 "곳" 은 앱의 model 층과 view 층처럼 클 수도 있고, for 문의 `in` 양쪽에 있는 두 변수처럼 작을 수도 있다. 구조는 같다.

복사가 필요 없는 조건은 두 가지다. 저장 공간이 계속 살아 있다는 것, 그리고 양쪽이 exclusivity 규칙을 지켜서 같이 보고 있는 데이터를 바꾸지 않는다는 것이다. 이 조건이 맞으면 복사하지 않고 기존 저장 공간에 접근만 허락하면 된다.

가장 쉬운 방법은 데이터를 object 에 넣고 object 를 넘기는 것이다. 대부분 이걸로 충분하지만 문제가 완전히 사라지지는 않는다. object 는 reference counting 을 하고, 넘길 때마다 count 가 바뀐다. retain 과 release 는 큰 값을 복사하는 것보다는 싸도, 성능에 가장 민감한 코드에서는 여전히 느릴 수 있다.

object 를 못 쓰면 `UnsafePointer` 를 넘겨야 했다.

### borrow 와 mutate 란?

그래서 몇 년 전부터 Swift 는 저장 공간을 안전하게 공유하는 데 필요한 보장을 언어 안에 정리했다. 그것이 **borrow** 다.

비유하면 도서관 책을 열람실에서 같이 보는 것과 비슷하다. 책을 복사해 가지 않고 원본을 본다. 대신 보는 동안에는 누구도 책에 낙서할 수 없고, 다 본 뒤에야 주인이 책을 마음대로 다룰 수 있다.

출처: WWDC26 - What's new in Swift

- Component 2 가 빌려 쓰는 동안 **양쪽 모두 읽기만** 할 수 있다
- Component 2 가 먼저 사용을 끝내야 하고, 끝나면 Component 1 이 다시 모든 권한을 가진다

**mutate** 는 비슷하지만 더 엄격하다. 빌려 간 쪽이 값을 바꿀 수 있는 대신, 원래 주인은 그동안 저장 공간에 **아예 접근하지 못한다.**

막는 이유는 반쯤 바뀐 데이터를 읽거나, 상대가 언제 변경을 써 넣느냐에 따라 동작이 달라지는 일을 없애기 위해서다. borrow 든 mutate 든 양쪽이 규칙을 지키는지는 **compile 시점에 검증**된다. UnsafePointer 와 같은 효율을 내면서 안전은 compiler 가 책임지는 셈이다.

이 작업의 원칙은 평범한 Swift 코드를 쓰는 방식에 영향을 주지 않는 것이다. 그래서 ownership 기능은 여러 해에 걸쳐 조금씩 들어오고 있고 아직 끝나지 않았다. 올해 더해진 것들이 아래 내용이다.

### noncopyable 타입과 protocol

noncopyable 타입 (`~Copyable`) 은 복사할 수 없는 타입이고, non-escapable 타입 (`~Escapable`) 은 만들어진 scope 밖으로 내보낼 수 없는 타입이다. 둘 다 "복사하지 않고 빌려 쓴다" 를 타입으로 표현하는 도구다.

올해 넓어진 부분은 두 가지다.

- `Equatable`, `Comparable`, `Hashable` 을 noncopyable 타입에 쓸 수 있다. `Equatable` 과 `Comparable` 은 non-escapable 타입에도 쓸 수 있다
- associated type 이 noncopyable 이나 non-escapable 일 수 있다

성능과 안전을 위해 만든 타입도 평범한 Swift 타입이 가진 가장 기본적인 기능을 쓸 수 있게 된 것이다. 두 번째 항목은 protocol 설계의 폭을 넓힌다. 세션이 예로 든 것이 `Iterable` protocol 이다. element 타입은 noncopyable 일 수 있고, iterator 타입은 noncopyable 이면서 non-escapable 일 수 있다. 물론 copyable 한 타입을 써도 된다. protocol 이 요구하지 않을 뿐이다.

> 세션 Code 탭의 `Iterable` 선언은 설명용으로 줄인 것이라 그대로는 빌드되지 않았다 (`a method cannot return a ~Escapable result`). 실제 SDK 선언에는 `@lifetime` 표기가 붙어 있고 이름도 다르다. 세션의 `IterableIteratorProtocol`, `makeIterableIterator()`, `nextSpan(maximumCount:)` 는 SDK 에서 `BorrowingIteratorProtocol`, `makeBorrowingIterator()`, `nextSpan(maxCount:)` 다. 그래서 선언 코드는 싣지 않는다.
{: .prompt-warning }

### for 문과 Iterable

`Iterable` 은 예시로 끝나지 않고 Swift 6.4 에 실제로 들어왔다. for 문이 이 protocol 을 지원한다.

우리가 아는 `Sequence` 는 element 를 **복사해서** 꺼낸다. `Iterable` 은 for 문이 element 를 **빌려 쓰게** 한다. 그래서 다음이 가능해진다.

- noncopyable element 를 순회할 수 있다
- object 나 copy-on-write 타입을 순회할 때 reference counting 을 하지 않는다
- `AsyncSequence` 처럼 순회 중에 에러를 던질 수 있다

대신 borrow 이기 때문에, **순회하는 동안 그 Iterable 을 변경할 수 없다.** exclusivity 검사가 막는다. 세션은 이것이 나쁜 일만은 아니라고 한다. Sequence 에서는 순회 중 변경이 성능 함정인 경우가 많았다. 이 동작 차이 때문에 for 문은 `Sequence` 를 쓸 수 있으면 그쪽을 먼저 쓰고, 없을 때 `Iterable` 로 넘어간다.

동작 방식도 다르다. Sequence 처럼 iterator 를 만들지만, element 를 하나씩이 아니라 **묶음으로** 가져온다.

![IterableIterator 가 Next index 3 을 기억하고 있고, Element 0 부터 2 까지 세 개가 하나의 Span 으로 묶여 있는 모습](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-262/wwdc26-262-iterable-span.png)

출처: WWDC26 - What's new in Swift

for 문은 iterator 에게 element 의 span 을 요청해서 하나씩 지나가고, 다 보면 다음 span 을 요청한다. 더 줄 것이 없으면 빈 span 이 돌아오고 for 문이 끝난다. 전부를 큰 span 하나로 돌려줄 수 있는 타입에서는 특히 효율적이다.

noncopyable element 를 for 문으로 도는 코드를 직접 만들어 빌드했다.

```swift
struct Token: ~Copyable { var id: Int }

func ids(_ tokens: borrowing UniqueArray<Token>) -> Int {
    var sum = 0
    for token in tokens {
        sum += token.id
    }
    return sum
}
```

`Token` 은 복사할 수 없으니 예전 방식의 for 문으로는 꺼낼 수 없다. `UniqueArray` 는 아래에서 다시 나온다.

### borrow 와 mutate accessor

Swift 6.4 는 accessor 에도 큰 변화를 줬다. 왜 중요한지는 `UniqueBox` 라는 struct 로 설명한다. 큰 값에 대한 pointer 를 자동으로 관리하고, computed property 로 그 값에 접근하게 해 주는 타입이다.

```swift
@safe public struct UniqueBox<Value>: ~Copyable {
    private let valuePointer: UnsafeMutablePointer<Value>

    public init(_ value: consuming Value) {
        valuePointer = UnsafeMutablePointer.allocate(capacity: 1)
        valuePointer.initialize(to: value)
    }

    public var value: Value {
        get { valuePointer.pointee }
        set { valuePointer.pointee = newValue }
    }

    deinit {
        valuePointer.deinitialize(count: 1)
        valuePointer.deallocate()
    }
}
```

이 `value` property 에는 심각한 성능 문제가 있다. `UniqueBox` 에 `Int` 256개짜리 [`InlineArray`](https://developer.apple.com/documentation/swift/inlinearray){:target="_blank"} 를 넣었다고 하자. InlineArray 는 element 를 heap 이 아니라 값 안에 그대로 담기 때문에, 64-bit 기기에서 2KB 짜리 struct 다. 그런데 `get` 과 `set` 은 **값을 복사하는 방식**으로 동작한다. 배열의 `Int` 하나를 바꾸려면 2KB 를 통째로 꺼냈다가 다시 넣어야 한다.

이제 `get` 과 `set` 대신 `borrow` 와 `mutate` 를 쓸 수 있다.

```swift
@safe public struct UniqueBox<Value: ~Copyable>: ~Copyable {
    private let valuePointer: UnsafeMutablePointer<Value>

    public init(_ value: consuming Value) {
        valuePointer = UnsafeMutablePointer.allocate(capacity: 1)
        valuePointer.initialize(to: value)
    }

    public var value: Value {
        borrow { valuePointer.pointee }
        mutate { &valuePointer.pointee }
    }

    deinit {
        valuePointer.deinitialize(count: 1)
        valuePointer.deallocate()
    }
}
```

#### borrow 와 mutate accessor 로 제자리 접근 제공하기

- `borrow`: 복사 없이 공유 저장 공간에 대한 **읽기 전용 접근**을 준다
- `mutate`: 제자리에서 고칠 수 있는 **배타적 접근**을 준다. 값이 아니라 저장 위치를 돌려주기 때문에 `&` 를 붙인다

바꾸고 나면 `box.value[3] += 1` 은 원본 배열의 element 를 그 자리에서 바꾼다. 복사는 없다.

덤으로 첫 줄이 `UniqueBox<Value>` 에서 `UniqueBox<Value: ~Copyable>` 로 바뀐 것도 볼 수 있다. `get` 은 값을 복사해서 돌려주니 noncopyable 값을 담을 수 없었는데, 새 accessor 는 복사하지 않으니 noncopyable 값도 담을 수 있다.

두 버전 모두 빌드했고, 두 번째 버전에 `[256 of Int]` 를 넣어 `box.value[3] += 1` 이 빌드되는 것을 확인했다. 복사가 실제로 사라지는지를 측정하지는 않았다.

### 표준 라이브러리의 새 타입

`UniqueBox` 도 실제로 표준 라이브러리에 들어온 타입이다. unsafe 코드를 직접 쓰지 않게 해 주는 API 가 같이 추가됐다.

| API | 하는 일 |
|---|---|
| `UniqueBox` | 값 하나를 heap 에 두고 유일한 소유자로 관리한다 |
| `UniqueArray` | 보통의 Array 와 비슷하지만 noncopyable 이다. noncopyable element 를 담을 수 있고, 크기를 고정하지 않으면서 reference counting 비용을 피한다 |
| `withTemporaryAllocation` | `UnsafeMutableBufferPointer` 대신 `OutputSpan` 을 넘겨줘서 임시 메모리를 안전하게 다룬다 |
| `Continuation` | resume 을 한 번만 하는지 compile 시점에 검사한다. `CheckedContinuation` 보다 안전하고 `UnsafeContinuation` 만큼 효율적이다 |

네 가지 모두 SDK 에 선언이 있는 것을 확인했고, `UniqueBox` 와 `UniqueArray` 는 간단한 사용 코드를 빌드했다.

### Ref 와 MutableRef

마지막 한 쌍은 기존 API 의 개선판이 아니라 새 능력이다. `Ref` 는 Span 과 비슷한데 여러 값이 아니라 **값 하나**를 가리킨다. borrow 나 mutation 을 담는 그릇이라고 보면 된다. 변수에 저장하고, 함수에 넘기고 돌려받고, generic 타입에 쓸 수 있다.

- 읽기 접근에서 `Ref` 를 만든다
- 쓰기 접근에서 앞에 `&` 를 붙여 `MutableRef` 를 만든다

property 하나에 대한 `MutableRef` 를 돌려주는 method 처럼 전에는 쓸 수 없던 API 를 만들 수 있고, 성능 문제를 푸는 데도 쓴다.

```swift
func updateCount<Key: Hashable>(
    for key: Key,
    from sets: [Set<Key>],
    in counts: inout [Key: Int]
) {
    for set in sets {
        if set.contains(key) {
            counts[key, default: 0] += 1
        }
    }
}
```

이 함수는 loop 를 돌 때마다 같은 key 로 dictionary lookup 을 다시 한다. 반복되는 일은 loop 밖으로 빼서 한 번만 하는 것이 보통인데, dictionary lookup 을 "한 번 해 두고 열어 둔 채로 유지" 하는 방법이 지금까지는 하나뿐이었다. loop 를 내부 함수로 옮기고 lookup 을 `inout` parameter 로 넘기는 것이다.

```swift
    func updateCountImpl(count: inout Int) {
        for set in sets {
            if set.contains(key) {
                count += 1
            }
        }
    }

    updateCountImpl(count: &counts[key, default: 0])
```

동작은 하지만 알기 어려운 요령이다. `MutableRef` 를 쓰면 이렇게 된다.

```swift
func updateCount<Key: Hashable>(
    for key: Key,
    from sets: [Set<Key>],
    in counts: inout [Key: Int]
) {
    var countRef = MutableRef(&counts[key, default: 0])

    for set in sets {
        if set.contains(key) {
            countRef.value += 1
        }
    }
}
```

#### MutableRef 로 접근을 한 번만 열어 두기

loop 시작 전에 dictionary lookup 으로 `MutableRef` 를 한 번 만들고, 값을 바꿀 때는 `countRef.value` 를 쓴다. Ref 는 non-escapable 이라서 변수가 scope 를 벗어나면 접근이 끝난다는 것을 Swift 가 안다. 접근을 닫는 코드를 따로 쓸 필요가 없다.

세 버전 모두 세션 코드 그대로 빌드됐다.

- **Android**: Android workgroup 이 Swift 6.3 과 함께 첫 Swift SDK for Android 를 냈다. Android 앱과 iOS 앱이 Swift 코드를 공유할 수 있다

## 정리

핵심만 다시 모으면 이렇다.

- **작은 문법 개선**: `any P?` 괄호 제거, defer 안의 await, `weak let`, `~Sendable`, 두 번째 memberwise initializer. 따로 배울 것 없이 불편이 사라진다
- **Task 에러 경고**: 버려진 throwing Task 에 경고가 난다. 기존 프로젝트를 Swift 6.4 로 빌드하면 가장 먼저 눈에 띌 변화다
- **`anyAppleOS`**: availability 와 `#if os` 를 한 단어로 줄인다
- **`@diagnose`**: 경고를 선언 단위로 끄거나 켜거나 에러로 올린다
- **module selector `::`**: 이름 충돌을 module 이름으로 확실하게 푼다. 충돌을 일부러 만들라는 뜻은 아니다
- **Swift Testing**: warning severity, `Test.cancel`, 반복 실행, XCTest 양방향 상호운용. XCTest 쪽 실패는 기본이 warning 이라는 점을 기억해야 한다
- **`@c`**: Swift 함수를 C 로 내보낸다. C 코드를 함수 단위로 Swift 로 옮길 수 있다
- **ownership**: for 문 (`Iterable`), accessor (`borrow` / `mutate`), 표준 타입 (`UniqueBox`, `UniqueArray`, `Ref`, `MutableRef`) 까지 "복사 없이 안전하게 빌려 쓰기" 가 넓어졌다

RunWay 에 바로 쓸 수 있는 것을 꼽아 보면 다음과 같다.

- RunWay 는 iOS 와 watchOS 를 같이 지원해서 `@available(iOS 27, watchOS 27, *)` 같은 줄이 생긴다. `anyAppleOS` 로 줄일 수 있다
- `Task { try ... }` 로 띄워 두고 결과를 보지 않는 코드가 있으면 6.4 에서 경고가 난다. 에러를 삼키고 있던 자리를 찾는 기회가 된다
- 러닝 종료 시 기록을 저장하는 구간은 Task 가 취소돼도 끝까지 가야 한다. `withTaskCancellationShield` 가 맞는 자리다
- 테스트에서 "이상하지만 실패는 아닌" 값은 `severity: .warning` 으로 남길 수 있다
- ownership 기능은 지금의 RunWay 에는 필요 없다. 세션 말대로 평소에는 쓸 일이 없고, 측정해서 복사가 병목으로 드러났을 때 꺼내는 도구다

세션 코드와 실제 SDK 가 달랐던 부분도 한 번에 모아 둔다. Xcode 27.0 (Swift 6.4) 기준이다.

| 항목 | 결과 |
|---|---|
| `mapKeyedValues` | SDK 에 없어서 빌드 실패 |
| 표준 라이브러리 `FilePath` | `import System` 의 기존 타입만 있음 |
| `Iterable` 선언 | 세션 코드는 줄인 버전. 실제 이름은 `BorrowingIteratorProtocol`, `makeBorrowingIterator()`, `nextSpan(maxCount:)` |
| Subprocess 예제 | `closureOutput` 이 아니라 `closureResult`. sequence 는 closure 안에서 읽어야 함 |
| `ProgressManager` 의 관찰과 metadata 예제 | 선언이 빠져 있어 빌드하지 못함 |
