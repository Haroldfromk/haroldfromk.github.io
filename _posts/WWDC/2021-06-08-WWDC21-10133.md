## 한 줄 요약

여러 task 가 함께 쓰는 mutable state 는 actor 안에 넣어 보호한다. actor 는 자기 state 를 프로그램의 나머지와 격리하고 한 번에 하나의 code 만 그 state 를 만지게 하며, 이 규칙을 어기면 compiler 가 error 로 알려 준다.

## data race 문제

세션은 concurrent 프로그램에서 가장 다루기 어려운 문제인 data race 로 시작한다. data race 는 만들기는 쉬운데 찾아서 고치기는 어렵다는 것이 출발점이다.

---

### data race 란?

data race 는 두 thread 가 같은 data 에 동시에 접근하고, 그중 적어도 하나가 write 일 때 생기는 문제다. 둘 다 읽기만 하면 문제가 없고, 서로 다른 data 를 만져도 문제가 없다. 같은 data 를 한쪽이 고치는 동안 다른 쪽이 건드릴 때만 생긴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-race-counter.png)
출처: WWDC21 - Protect mutable state with Swift actors

---

### Counter 예제

세션이 드는 예는 숫자를 하나씩 올리는 `Counter` class 다. `increment()` 는 값을 1 올리고 새 값을 돌려준다. 이 counter 하나를 두 개의 detached task 가 함께 쓴다.

```swift
class Counter {
    var value = 0

    func increment() -> Int {
        value = value + 1
        return value
    }
}

func run() {
    let counter = Counter()

    Task.detached {
        print(counter.increment()) // data race
    }

    Task.detached {
        print(counter.increment()) // data race
    }
}
```

세션 page 의 snippet 은 top-level code 다. 여기서는 `run()` 함수로 감쌌다.

#### Task.detached

[Task.detached](https://developer.apple.com/documentation/swift/task/detached%28name:priority:operation:%29-9xki7){:target="_blank"} 는 지금 context 와 이어지지 않은 새 top-level task 를 만들어 operation 을 비동기로 실행하는 함수다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-race-tasks.png)
출처: WWDC21 - Protect mutable state with Swift actors

두 task 가 어떤 순서로 실행되느냐에 따라 결과가 달라진다. 1 다음 2 가 찍히거나 2 다음 1 이 찍히는 것은 기대한 결과다. 두 task 가 차례로 `increment()` 를 끝낸 경우이기 때문이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-race-result-ok.png)
출처: WWDC21 - Protect mutable state with Swift actors

문제는 그 밖의 결과도 나올 수 있다는 점이다. 두 task 가 모두 0 을 읽고 각자 1 을 쓰면 1 이 두 번 찍힌다. 두 `increment()` 가 다 끝난 뒤에야 return 문이 실행되면 2 가 두 번 찍힌다. 이런 결과는 counter 의 상태가 일관되지 않다는 뜻이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-race-result-bad.png)
출처: WWDC21 - Protect mutable state with Swift actors

data race 가 까다로운 이유를 세션은 두 가지로 든다. 하나는 문제를 일으키는 두 접근이 프로그램의 전혀 다른 곳에 있을 수 있어서, 한 곳만 봐서는 알 수 없다는 점이다. 다른 하나는 운영체제의 scheduler 가 실행할 때마다 작업을 다르게 끼워 넣을 수 있어서 결과가 매번 달라진다는 점이다.

원인은 shared mutable state 다. data 가 바뀌지 않거나, 여러 task 가 함께 쓰지 않으면 data race 는 생기지 않는다.

지금의 compiler 는 이 code 를 어떻게 볼까. Swift 5 language mode 에서는 아무 진단 없이 통과했다. Swift 6 language mode 에서는 첫 번째 `Task.detached` 줄에서 non-Sendable 값을 넘기면 data race 위험이 있다는 error 가 났다. 2021년에는 사람이 찾아야 했던 문제를 지금은 compiler 가 막는다.

---

### value semantics

data race 를 피하는 한 가지 방법은 value semantics 로 shared mutable state 를 없애는 것이다. value type 의 변수를 고치면 그 변수만 바뀐다. 그리고 `let` 으로 선언한 value type 은 정말로 바뀌지 않으므로 여러 task 가 함께 읽어도 안전하다.

```swift
var array1 = [1, 2]
var array2 = array1

array1.append(3)
array2.append(4)

print(array1)        // [1, 2, 3]
print(array2)        // [1, 2, 4]
```

`array2` 는 `array1` 의 복사본이라, 각각에 값을 덧붙여도 서로에게 영향이 없다. Swift 는 처음부터 value semantics 를 밀어 왔고, 표준 library 의 collection 을 비롯한 대부분의 type 이 value semantics 를 가진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-value-array.png)
출처: WWDC21 - Protect mutable state with Swift actors

### shared mutable state 가 필요한 경우

그러면 `Counter` 를 struct 로 바꾸면 되지 않을까. 세션은 이 시도를 단계별로 보여 준다.

먼저 struct 로 바꾸면 `increment()` 는 `mutating` 이 되어야 한다. 그런데 `counter` 는 `let` 이라 고칠 수 없으므로 compile error 가 난다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-struct-let-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

이 error 는 지금도 그대로 난다. `cannot use mutating member on immutable value: 'counter' is a 'let' constant` 라는 문구다.

여기서 `counter` 를 `var` 로 바꾸고 싶어진다. 하지만 그러면 두 task 가 같은 변수를 참조하면서 고치게 되어 다시 data race 다. 세션 화면에서는 compiler 가 concurrent 하게 실행되는 code 에서 capture 한 `var` 를 고칠 수 없다고 막는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-struct-var-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

지금 확인한 결과는 조금 다르다. Swift 5 language mode 에서는 이 code 가 진단 없이 통과했고, Swift 6 language mode 에서는 class 버전과 같은 종류의 error (non-Sendable 값을 넘기면 data race 위험) 가 났다. 화면의 문구와는 다르지만 Swift 6 mode 에서 막힌다는 점은 같다.

마지막으로 각 task 안에서 counter 를 local 변수로 복사하면 compile 이 된다.

```swift
struct Counter {
    var value = 0

    mutating func increment() -> Int {
        value = value + 1
        return value
    }
}

func run() {
    let counter = Counter()

    Task.detached {
        var counter = counter
        print(counter.increment()) // always prints 1
    }

    Task.detached {
        var counter = counter
        print(counter.increment()) // always prints 1
    }
}
```

여기서도 top-level code 를 `run()` 함수로 감쌌다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-struct-copy.png)
출처: WWDC21 - Protect mutable state with Swift actors

이제 data race 는 없다. 하지만 두 task 가 각자의 복사본을 올리므로 언제나 1 이 두 번 찍힌다. race 는 없어졌지만 원하던 동작도 아니다. 두 task 가 하나의 counter 를 함께 올리는 것이 목적이었기 때문이다. 결국 shared mutable state 가 꼭 필요한 경우가 있다는 것이 이 예의 결론이다.

---

### 기존 동기화 수단

shared mutable state 를 쓰려면 동기화가 필요하다. 세션은 지금까지 쓰던 수단으로 atomics, lock, serial dispatch queue 를 든다. 낮은 수준의 도구부터 높은 수준의 도구까지 있고 각각 장점이 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sync-options.png)
출처: WWDC21 - Protect mutable state with Swift actors

이 수단들의 공통된 약점은 규율이다. 매번 빠짐없이 정확하게 써야 하고, 한 번이라도 빠뜨리면 다시 data race 가 생긴다. actor 는 이 지점을 해결하려고 나온 기능이다.

## actor

Dario 는 여기서 actor 를 소개한다. actor 는 shared mutable state 를 위한 동기화 mechanism 이고, 동기화를 빠뜨릴 수 없게 언어가 보장한다는 점이 기존 수단과 다르다.

---

### actor 란?

actor 는 자기 state 를 프로그램의 나머지와 격리(isolate)하는 type 이다. 그 state 에 접근하려면 반드시 actor 를 거쳐야 하고, actor 는 한 번에 하나의 code 만 state 에 접근하도록 보장한다. 이것을 mutually-exclusive access 라고 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-actor-points.png)
출처: WWDC21 - Protect mutable state with Swift actors

lock 이나 serial dispatch queue 로 얻던 성질과 같다. 다른 점은 Swift 가 이것을 보장한다는 것이다. 동기화를 깜빡하면 실행 중에 문제가 생기는 것이 아니라 compile error 가 난다.

---

### actor type

actor 는 Swift 의 새로운 종류의 type 이다. struct, enum, class 가 할 수 있는 일을 거의 다 한다. property, method, initializer, subscript 를 가질 수 있고, protocol 을 따를 수 있고, extension 으로 넓힐 수 있다.

class 처럼 reference type 이다. actor 의 목적이 shared mutable state 를 표현하는 것이기 때문이다. 다른 type 과 구별되는 점은 instance data 를 격리하고 그 data 로의 접근을 동기화한다는 것 하나다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-actor-type.png)
출처: WWDC21 - Protect mutable state with Swift actors

`Counter` 를 actor 로 바꾸면 다음과 같다. 바뀐 것은 `class` 가 `actor` 가 된 것과 호출하는 쪽에 `await` 가 붙은 것뿐이다.

```swift
actor Counter {
    var value = 0

    func increment() -> Int {
        value = value + 1
        return value
    }
}

func run() {
    let counter = Counter()

    Task.detached {
        print(await counter.increment())
    }

    Task.detached {
        print(await counter.increment())
    }
}
```

여기서도 top-level code 를 `run()` 함수로 감쌌다. 이 code 는 Swift 5 mode 와 Swift 6 mode 에서 모두 통과했다.

#### actor

[Actor](https://developer.apple.com/documentation/swift/actor){:target="_blank"} 는 모든 actor type 이 따르는 protocol 이고, `actor` keyword 로 선언한 type 은 자동으로 이 protocol 을 따른다.

`increment()` 가 actor 위에서 실행되는 동안에는 다른 code 가 그 actor 에서 실행되지 않는다. 그래서 한 번 시작한 `increment()` 는 끝까지 실행되고, 두 task 의 결과는 1 과 2 또는 2 와 1 뿐이다. 1 이 두 번 찍히거나 2 가 두 번 찍히는 경우는 사라진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-actor-result.png)
출처: WWDC21 - Protect mutable state with Swift actors

### 밖에서의 비동기 접근

두 task 가 동시에 `increment()` 를 부르면 어떻게 될까. 하나가 먼저 actor 에 들어가고 다른 하나는 차례를 기다려야 한다. 이때 기다리는 쪽이 thread 를 붙잡고 멈춰 있으면 안 된다.

그래서 actor 밖에서 actor 와 주고받는 일은 비동기다. actor 가 바쁘면 부른 쪽 code 는 suspend 되고, 그 CPU 는 다른 일을 한다. actor 가 비면 code 가 깨어나 actor 위에서 이어서 실행된다. 호출에 붙은 `await` 는 이 지점에서 suspend 될 수 있다는 표시다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-actor-await.png)
출처: WWDC21 - Protect mutable state with Swift actors

`await` 와 suspend 에 관한 설명은 [Meet async/await in Swift](https://haroldfromk.github.io/posts/WWDC21-10132/){:target="_blank"} 글에 정리해 두었다.

### actor 안의 sync code

actor 안에서는 사정이 다르다. 이미 actor 위에서 실행 중인 code 는 actor 의 state 에 바로 접근할 수 있고, 같은 actor 의 sync method 도 `await` 없이 부를 수 있다.

```swift
extension Counter {
    func resetSlowly(to newValue: Int) {
        value = 0
        for _ in 0..<newValue {
            increment()
        }
        assert(value == newValue)
    }
}
```

`resetSlowly(to:)` 는 값을 0 으로 되돌린 다음 `increment()` 를 필요한 횟수만큼 부른다. `increment()` 호출에 `await` 가 없다. 이 code 는 통과했지만 `increment()` 의 결과를 쓰지 않는다는 warning 이 하나 나왔다.

#### assert

[assert](https://developer.apple.com/documentation/swift/assert%28_:_:file:line:%29){:target="_blank"} 는 debug build 에서 조건이 거짓이면 프로그램을 멈추는 함수다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-actor-sync.png)
출처: WWDC21 - Protect mutable state with Swift actors

actor 위의 sync code 는 중간에 끊기지 않고 끝까지 실행된다. 그래서 다른 code 가 끼어들어 state 를 바꿀 걱정 없이 위에서 아래로 차례대로 읽으면 된다. 마지막 줄의 `assert` 가 항상 참인 이유다.

## actor reentrancy

sync code 는 끊기지 않지만, actor 는 다른 actor 나 비동기 code 와도 일한다. actor 안에 `await` 가 들어오면 이야기가 달라진다. Dario 는 이 부분에 세션에서 가장 긴 시간을 쓴다.

---

### image downloader 예제

예제는 image 를 내려받아 cache 에 넣어 두는 actor 다. 같은 URL 을 두 번 내려받지 않으려는 것이 목적이다.

```swift
import Foundation

struct Image: Sendable {
    var data: Data
}

func downloadImage(from url: URL) async throws -> Image {
    let (data, _) = try await URLSession.shared.data(from: url)
    return Image(data: data)
}

actor ImageDownloader {
    private var cache: [URL: Image] = [:]

    func image(from url: URL) async throws -> Image? {
        if let cached = cache[url] {
            return cached
        }

        let image = try await downloadImage(from: url)

        // Potential bug: `cache` may have changed.
        cache[url] = image
        return image
    }
}
```

세션 page 의 snippet 은 `ImageDownloader` 만 있다. `Image` 와 `downloadImage(from:)` 는 세션에 나오지 않아 직접 채웠다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-reentrancy-code.png)
출처: WWDC21 - Protect mutable state with Swift actors

논리는 단순하다. cache 를 확인하고, 없으면 내려받고, cache 에 기록하고, 돌려준다. actor 안이므로 낮은 수준의 data race 는 없다. 여러 task 가 동시에 `image(from:)` 을 불러도 actor 의 동기화가 cache 를 한 번에 한 task 만 만지게 해서 cache 가 망가지지 않는다.

문제는 가운데의 `await` 다. `await` 는 이 함수가 여기서 suspend 될 수 있다는 뜻이고, suspend 된 동안 actor 는 다른 일을 받아 처리한다. 다시 깨어났을 때는 프로그램 전체의 상태가 바뀌어 있을 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-reentrancy-await.png)
출처: WWDC21 - Protect mutable state with Swift actors

---

### reentrancy 란?

reentrancy 는 actor 위에서 실행되던 code 가 `await` 에서 suspend 된 동안, 같은 actor 에 다른 code 가 들어와 실행될 수 있는 성질이다. actor 는 한 번에 하나의 code 만 실행하지만, suspend 된 함수가 끝날 때까지 actor 를 잠가 두지는 않는다.

---

### 슬픈 고양이 시나리오

세션은 두 task 가 같은 URL 의 image 를 거의 동시에 요청하는 상황을 그림으로 따라간다.

첫 번째 task 가 cache 를 확인한다. 아직 없으므로 server 에서 내려받기 시작하고, 시간이 걸리므로 suspend 된다. 그 사이에 server 에는 같은 URL 로 새 image 가 올라온다. 원래는 고양이 image 였는데 슬픈 고양이 image 로 바뀐다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-cat-overwrite.png)

### 해결 방법

첫 번째 해결은 `await` 뒤에 가정을 다시 확인하는 것이다. 깨어났을 때 cache 에 이미 값이 있으면 그 값을 유지하고 새로 받은 것은 버린다.

```swift
actor ImageDownloader2 {
    private var cache: [URL: Image] = [:]

    func image(from url: URL) async throws -> Image? {
        if let cached = cache[url] {
            return cached
        }

        let image = try await downloadImage(from: url)

        // Replace the image only if it is still missing from the cache.
        cache[url] = cache[url, default: image]
        return cache[url]
    }
}
```

한 file 에 세 버전을 같이 넣어 검사하느라 type 이름 뒤에 숫자를 붙였다. 세션에서는 세 버전 모두 `ImageDownloader` 다.

#### Dictionary 의 default subscript

[subscript(_:default:)](https://developer.apple.com/documentation/swift/dictionary/subscript%28_:default:%29){:target="_blank"} 는 key 에 해당하는 값이 있으면 그 값을, 없으면 넘겨준 기본값을 돌려주는 subscript 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-reentrancy-fix.png)
출처: WWDC21 - Protect mutable state with Swift actors

더 나은 해결은 중복 내려받기 자체를 피하는 것이다. 영상에서는 말로만 언급하고, code 는 세션 page 에 딸려 있다. cache 에 image 대신 "내려받는 중인 task" 를 넣어 두고, 두 번째 요청은 그 task 의 결과를 기다리게 한다.

```swift
actor ImageDownloader3 {

    private enum CacheEntry {
        case inProgress(Task<Image, Error>)
        case ready(Image)
    }

    private var cache: [URL: CacheEntry] = [:]

    func image(from url: URL) async throws -> Image? {
        if let cached = cache[url] {
            switch cached {
            case .ready(let image):
                return image
            case .inProgress(let task):
                return try await task.value
            }
        }

        let task = Task {
            try await downloadImage(from: url)
        }

        cache[url] = .inProgress(task)

        do {
            let image = try await task.value
            cache[url] = .ready(image)
            return image
        } catch {
            cache[url] = nil
            throw error
        }
    }
}
```

세 버전 모두 Swift 5 mode 와 Swift 6 mode 에서 통과했다.

#### Task 의 value

[value](https://developer.apple.com/documentation/swift/task/value-60t02){:target="_blank"} 는 task 가 끝난 뒤의 결과를 돌려주는 property 이고, task 가 아직 끝나지 않았으면 끝날 때까지 기다린다.

이 버전에서는 cache 를 확인하는 일과 `.inProgress` 를 기록하는 일 사이에 `await` 가 없다. 두 일이 한 덩어리의 sync code 로 실행되므로 두 번째 요청은 반드시 `.inProgress` 를 보게 된다.

---

### 설계 지침

세션은 reentrancy 를 결함으로 보지 않는다. actor 가 suspend 된 함수를 기다리며 잠겨 있지 않기 때문에 deadlock 이 생기지 않고, 프로그램이 계속 앞으로 나아간다. 대신 `await` 를 사이에 두고 가정이 유지되는지를 작성자가 확인해야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-reentrancy-points.png)
출처: WWDC21 - Protect mutable state with Swift actors

reentrancy 를 고려한 설계 지침은 세 가지다.

- actor state 를 고치는 일은 sync code 안에서 한다. 가장 좋은 것은 sync 함수 하나 안에 state 변경을 모두 넣는 것이다.
- state 를 잠시 일관되지 않은 상태로 두었다면 `await` 전에 되돌려 놓는다. suspend 된 동안 actor state 가 바뀔 수 있다고 생각하고 쓴다.
- `await` 는 suspend 될 수 있는 지점이다. suspend 되면 깨어나기 전에 프로그램 전체의 상태가 바뀔 수 있다. global state, 시계, timer, actor 에 대해 세운 가정은 `await` 뒤에 다시 확인한다.

---

## actor isolation

여기서부터는 Doug 가 맡는다. actor isolation 은 actor type 의 동작의 바탕이고, 이 장은 그 isolation 이 protocol conformance, closure, class 같은 다른 언어 기능과 어떻게 맞물리는지를 다룬다.

---

### protocol conformance

actor 도 다른 type 처럼 protocol 을 따를 수 있다. 단, actor 의 요구를 만족할 수 있는 경우에만 그렇다. 예제는 도서관 계정을 나타내는 `LibraryAccount` actor 다.

```swift
struct Author {
    var name: String
}

struct Book {
    var title: String
    var authors: [Author]
}

actor LibraryAccount {
    let idNumber: Int
    var booksOnLoan: [Book] = []

    init(idNumber: Int) {
        self.idNumber = idNumber
    }

    func selectRandomBook() -> Book? {
        booksOnLoan.randomElement()
    }
}

extension LibraryAccount: Equatable {
    static func ==(lhs: LibraryAccount, rhs: LibraryAccount) -> Bool {
        lhs.idNumber == rhs.idNumber
    }
}
```

`Author`, `init(idNumber:)`, `selectRandomBook()` 의 body 는 세션에 나오지 않거나 생략되어 있어 직접 채웠다.

#### Equatable

[Equatable](https://developer.apple.com/documentation/swift/equatable){:target="_blank"} 은 두 값이 같은지를 `==` 로 비교할 수 있는 type 이 따르는 protocol 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-equatable.png)
출처: WWDC21 - Protect mutable state with Swift actors

`==` 는 static method 다. static method 에는 `self` 가 없으므로 actor 에 격리되어 있지 않다. 대신 actor type 의 parameter 두 개를 받고, 이 method 는 두 actor 모두의 밖에 있다. 그래도 괜찮은 이유는 method 가 읽는 것이 `idNumber` 뿐이기 때문이다. `let` 으로 선언한 immutable state 는 actor 밖에서도 바로 읽을 수 있다.

`Hashable` 은 사정이 다르다. `hash(into:)` 를 평범하게 쓰면 compiler 가 막는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-hashable-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

이유는 이렇다. `hash(into:)` 는 instance method 라 actor 에 격리된다. 그런데 `Hashable` 을 따른다는 것은 이 method 를 actor 밖에서 부를 수 있다는 뜻이다. `hash(into:)` 는 async 가 아니므로 밖에서 부를 때 actor isolation 을 지킬 방법이 없다.

지금 확인해 보니 여전히 error 가 나고 문구만 달라졌다. conformance 가 actor-isolated code 로 넘어가서 data race 를 일으킬 수 있다는 내용이다. Swift 5 mode 와 Swift 6 mode 에서 모두 error 였다.

---

### nonisolated 란?

`nonisolated` 는 actor 의 member 를 actor 밖에 있는 것으로 다루게 하는 keyword 다. 문법상으로는 actor 안에 쓰여 있지만 actor 에 격리되지 않으므로, 밖에서 sync 로 부를 수 있다.

```swift
extension LibraryAccount: Hashable {
    nonisolated func hash(into hasher: inout Hasher) {
        hasher.combine(idNumber)
    }
}
```

#### nonisolated

[nonisolated](https://github.com/apple/swift-evolution/blob/main/proposals/0313-actor-isolation-control.md){:target="_blank"} 는 SE-0313 에서 들어온 keyword 로, 선언을 actor isolation 에서 빼낸다.

#### Hashable 의 hash(into:)

[hash(into:)](https://developer.apple.com/documentation/swift/hashable/hash%28into:%29){:target="_blank"} 는 값의 핵심 요소를 hasher 에 넣어 hash 값을 만드는 method 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-nonisolated.png)
출처: WWDC21 - Protect mutable state with Swift actors

이제 `hash(into:)` 는 `Hashable` 이 요구하는 sync method 를 만족한다. 대신 actor 밖에 있는 것으로 다뤄지므로 actor 의 mutable state 를 참조할 수 없다. `idNumber` 는 immutable 이라 괜찮다. 하지만 `booksOnLoan` 으로 hash 를 만들려고 하면 error 가 난다. 밖에서 mutable state 에 접근하면 data race 가 될 수 있기 때문이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-books-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

`hasher.combine(booksOnLoan.count)` 로 바꿔 확인해 보니 지금도 error 였다. actor-isolated property 를 nonisolated context 에서 참조할 수 없다는 내용이다.

---

### closure 의 isolation

closure 는 한 함수 안에서 정의되어 다른 함수로 넘겨지고 한참 뒤에 불릴 수 있는 작은 함수다. 함수와 마찬가지로 closure 도 actor-isolated 이거나 nonisolated 다.

```swift
extension LibraryAccount {
    func readSome(_ book: Book) -> Int {
        book.title.count
    }

    func read() -> Int {
        booksOnLoan.reduce(0) { total, book in
            total + readSome(book)
        }
    }
}
```

세션 page 의 snippet 은 closure 가 parameter 를 `book` 하나만 받고 body 가 `readSome(book)` 뿐이다. `reduce` 의 closure 는 누적값과 원소 두 개를 받으므로 그대로는 compile 되지 않았다. 그래서 `total, book` 을 받아 더하도록 고쳤다. `readSome(_:)` 의 body 는 생략되어 있어 직접 채웠다.

#### reduce

[reduce(_:_:)](https://developer.apple.com/documentation/swift/array/reduce%28_:_:%29){:target="_blank"} 는 초깃값에서 시작해 원소를 하나씩 closure 로 합쳐 값 하나를 만드는 method 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-closure.png)
출처: WWDC21 - Protect mutable state with Swift actors

closure 안에서 `readSome(_:)` 을 부르는데 `await` 가 없다. actor-isolated 함수 안에서 만든 closure 는 그 자체로 actor-isolated 이기 때문이다. 그리고 `reduce` 는 closure 를 sync 로 실행하므로, closure 가 다른 thread 로 빠져나가 concurrent 하게 실행될 일이 없다.

detached task 는 다르다.

```swift
extension LibraryAccount {
    func readLater() {
        Task.detached {
            await self.read()
        }
    }
}
```

세션 page 의 snippet 은 `await read()` 다. 그대로는 closure 안에서 `self` 를 명시하라는 error 가 나서, 영상 화면과 같이 `await self.read()` 로 썼다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-iso-detached.png)
출처: WWDC21 - Protect mutable state with Swift actors

detached task 는 actor 가 하고 있는 다른 일과 concurrent 하게 closure 를 실행한다. 그 closure 가 actor 위에 있다고 치면 data race 가 생긴다. 그래서 이 closure 는 nonisolated 이고, `read()` 를 부르려면 `await` 로 비동기 호출을 해야 한다. `await` 를 빼고 확인해 보니 actor-isolated method 를 actor 밖에서 부를 수 없다는 error 가 났다.

---

### actor 를 드나드는 data

지금까지는 code 가 actor 안에서 실행되는지 밖에서 실행되는지를 봤다. 이번에는 data 다. `Book` 이 어떤 종류의 type 인지에 따라 이야기가 달라진다.

`Book` 이 struct 라면 `LibraryAccount` 의 state 는 전부 actor 안에 담겨 있다. 아무 책이나 하나 골라 돌려주는 `selectRandomBook()` 을 밖에서 부르면 책의 복사본을 받는다. 복사본을 고쳐도 actor 에는 영향이 없고 그 반대도 마찬가지다.

```swift
func visit(_ account: LibraryAccount) async {
    guard var book = await account.selectRandomBook() else {
        return
    }
    book.title = "\(book.title)!!!" // OK: modifying a local copy
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-data-struct.png)
출처: WWDC21 - Protect mutable state with Swift actors

`Book` 을 class 로 바꾸면 달라진다. actor 자체는 여전히 잘 동기화되어 있다. 하지만 `selectRandomBook()` 이 돌려주는 것은 이제 actor 의 mutable state 로의 reference 다. actor 밖에서 그 reference 를 갖게 되므로, `visit(_:)` 에서 제목을 고치면 actor 가 가진 책이 actor 를 거치지 않고 바뀐다. data race 가 생길 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-data-class.png)
출처: WWDC21 - Protect mutable state with Swift actors

정리하면 value type 과 actor 는 concurrent 하게 써도 안전하지만 class 는 여전히 문제가 될 수 있다. 이 구분에 이름을 붙인 것이 Sendable 이다.

## Sendable

concurrent 하게 써도 안전한 type 과 그렇지 않은 type 을 가르는 기준이 Sendable 이다. Doug 는 Sendable type 의 종류, conformance 를 검사하는 방법, 함수에 적용하는 방법을 차례로 설명한다.

---

### Sendable 이란?

Sendable type 은 그 값을 여러 actor 사이에서 공유해도 안전한 type 이다. 값을 한 곳에서 다른 곳으로 복사했을 때, 양쪽이 각자의 값을 고쳐도 서로 간섭하지 않으면 Sendable 이 될 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-types.png)
출처: WWDC21 - Protect mutable state with Swift actors

세션이 드는 Sendable type 은 다음과 같다.

- value type: 복사본이 서로 독립이라 Sendable 이다.
- actor type: mutable state 로의 접근을 스스로 동기화하므로 Sendable 이다.
- 조심스럽게 구현한 class: class 와 모든 subclass 가 immutable data 만 가지면 Sendable 이 될 수 있다. 내부에서 lock 등으로 직접 동기화하는 class 도 그렇다.
- `@Sendable` 함수 type: 함수가 모두 Sendable 인 것은 아니어서, actor 사이로 넘겨도 안전한 함수를 나타내는 새 함수 type 이 있다.

대부분의 class 는 여기에 해당하지 않으므로 Sendable 이 될 수 없다.

---

### Sendable 검사

actor 를 포함한 모든 concurrent code 는 주로 Sendable type 으로 주고받아야 한다. 그래야 data race 가 없다. 세션은 이것을 Swift 가 "언젠가" 정적으로 검사하기 시작할 것이고, 그때가 되면 non-Sendable type 을 actor 경계 너머로 넘기는 것이 error 가 된다고 말한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-checking.png)
출처: WWDC21 - Protect mutable state with Swift actors

2021년에는 예고였던 이 검사가 지금은 들어와 있다. 앞의 `visit(_:)` 예에서 `Book` 을 class 로 바꿔 확인해 보았다. Swift 5 language mode 에서는 진단 없이 통과했고, Swift 6 language mode 에서는 `selectRandomBook()` 을 부르는 줄에서 non-Sendable 인 결과를 actor-isolated method 에서 nonisolated context 로 돌려줄 수 없다는 error 가 났다.

Sendable 은 protocol 이다. type 이 Sendable 을 따른다고 선언하는 방법은 다른 protocol 과 같고, 선언하면 Swift 가 그 type 이 정말 Sendable 로서 말이 되는지 검사한다.

```swift
class Author {
    var name: String
    init(name: String) { self.name = name }
}

struct Book: Sendable {
    var title: String
    var authors: [Author]
}
```

이 code 는 error 를 보여 주려는 예다. 세션 page 의 snippet 에는 `struct Book: Sendable` 만 있고 `Author` class 는 직접 채웠다.

#### Sendable

[Sendable](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 은 값을 concurrency domain 사이로 넘겨도 data race 위험이 없는 type 이 따르는 protocol 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-author-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

struct 가 Sendable 이 되려면 stored property 가 모두 Sendable type 이어야 한다. `Author` 가 class 면 `Author` 도, `Author` 의 array 도 Sendable 이 아니다. 그래서 compiler 가 `Book` 이 Sendable 일 수 없다고 알려 준다. 확인해 보니 Swift 5 mode 에서는 warning 이고 Swift 6 mode 에서는 error 였다.

---

### conditional conformance

generic type 은 type argument 에 따라 Sendable 여부가 달라진다. 이럴 때는 conditional conformance 로 Sendable 을 전파한다.

```swift
struct Pair<T, U> {
    var first: T
    var second: U
}

extension Pair: Sendable where T: Sendable, U: Sendable {
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-pair.png)
출처: WWDC21 - Protect mutable state with Swift actors

`Pair` 는 두 type argument 가 모두 Sendable 일 때만 Sendable 이다. 표준 library 의 array 도 같은 방식이어서, Sendable type 의 array 는 Sendable 이다.

세션은 concurrent 하게 공유해도 안전한 type 에는 Sendable conformance 를 붙이고, 그 type 들을 actor 안에서 쓰라고 권한다. 그렇게 해 두면 Swift 가 actor 에 대해 Sendable 을 강제하기 시작할 때 code 가 준비되어 있게 된다.

---

### @Sendable 함수

함수도 Sendable 일 수 있다. actor 사이로 함수 값을 넘겨도 안전하다는 뜻이다. `@Sendable` 은 특히 closure 에 중요한데, closure 가 할 수 있는 일을 제한해서 data race 를 막기 때문이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-functions.png)
출처: WWDC21 - Protect mutable state with Swift actors

`@Sendable` closure 의 제약은 세 가지다.

- mutable 한 local 변수를 capture 할 수 없다. 그 변수에서 data race 가 생길 수 있기 때문이다.
- capture 하는 것은 모두 Sendable type 이어야 한다. non-Sendable type 을 actor 경계 너머로 옮기는 통로가 되면 안 되기 때문이다.
- sync 인 `@Sendable` closure 는 actor-isolated 일 수 없다. actor-isolated 라면 밖에서 actor 위의 code 를 실행할 수 있게 되기 때문이다.

이 세션에서 이미 이 제약에 기대고 있었다. detached task 를 만드는 operation 은 `@Sendable` 함수를 받는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-detached.png)
출처: WWDC21 - Protect mutable state with Swift actors

지금의 문서를 확인해 보니 `Task.detached` 의 operation parameter 는 `@Sendable` 대신 `sending` 으로 선언되어 있다. 2021년의 signature 와는 다르다.

세션 처음의 struct `Counter` 예로 돌아가 보자. `var counter` 를 두 closure 가 고치려고 했던 code 다. closure 가 mutable 한 local 변수를 고치려 했으므로 data race 가 되는 code 였고, detached task 의 closure 가 `@Sendable` 이라 Swift 가 error 를 냈던 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-counter-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

actor isolation 에도 같은 원리가 쓰인다. `readLater()` 의 detached task closure 는 `@Sendable` 이므로 actor-isolated 가 아니라고 추론된다. 그래서 그 안에서 actor 와 주고받는 일은 비동기여야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-sendable-read-error.png)
출처: WWDC21 - Protect mutable state with Swift actors

Sendable type 과 `@Sendable` closure 는 mutable state 가 actor 사이에 공유되지 않는지, concurrent 하게 수정되지 않는지를 검사해서 actor isolation 을 지켜 준다.

---

## main actor

마지막 주제는 특별한 actor 하나다. 앱에서 가장 자주 만나는 동기화 문제인 main thread 를 actor 로 표현한 것이다.

---

### main thread 와의 상호작용

main thread 는 앱에서 중요한 자리다. UI rendering 이 일어나고, 사용자의 event 가 처리된다. UI 를 다루는 일은 보통 main thread 에서 해야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-main-thread.png)
출처: WWDC21 - Protect mutable state with Swift actors

그렇다고 모든 일을 main thread 에서 할 수는 없다. 느린 입출력이나 server 응답을 기다리는 일을 main thread 에서 오래 하면 UI 가 멈춘다. 그래서 UI 를 다룰 때는 main thread 에서 하고, 계산이 많거나 오래 기다리는 일은 빨리 main thread 밖으로 내보내야 한다.

지금까지는 code 가 main thread 에서 실행되도록 `DispatchQueue.main.async` 를 직접 불렀다.

```swift
import UIKit

struct Book: Sendable {
    var title: String
}

class BooksView: UIView {
    var checkedOutBooks: [Book] = []
}

let booksView = BooksView()

func checkedOut(_ booksOnLoan: [Book]) {
    booksView.checkedOutBooks = booksOnLoan
}

func notify(_ booksOnLoan: [Book]) {
    // Dispatching to the main queue is your responsibility.
    DispatchQueue.main.async {
        checkedOut(booksOnLoan)
    }
}
```

세션 page 의 snippet 은 `checkedOut(_:)` 과 `DispatchQueue.main.async` 호출뿐이다. `Book`, `BooksView`, `booksView`, `notify(_:)` 는 직접 채웠다. 이 code 는 Swift 5 language mode 에서만 통과했다. Swift 6 language mode 에서는 내가 채운 global `booksView` 선언에서 error 가 났다. `UIView` 가 main actor 에 속하기 때문이다.

#### DispatchQueue.main

[DispatchQueue.main](https://developer.apple.com/documentation/dispatch/dispatchqueue/main){:target="_blank"} 은 앱의 main thread 에 묶인 dispatch queue 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-main-dispatch.png)
출처: WWDC21 - Protect mutable state with Swift actors

이 방식에서는 main queue 로 보내는 책임이 작성자에게 있다. 그런데 구조를 보면 actor 와 닮았다. main thread 위에서 실행 중이면 UI state 에 안전하게 접근할 수 있고, main thread 밖이면 비동기로 주고받아야 한다. actor 가 일하는 방식 그대로다.

---

### main actor 란?

main actor 는 main thread 를 나타내는 actor 다. 보통의 actor 와 다른 점은 두 가지다.

- 동기화를 모두 main dispatch queue 로 한다. 그래서 runtime 관점에서 main actor 는 `DispatchQueue.main` 과 서로 바꿔 쓸 수 있다.
- main thread 에 있어야 하는 code 와 data 가 곳곳에 흩어져 있다. SwiftUI, AppKit, UIKit 같은 system framework 에도 있고, 내 view, view controller, data model 의 UI 쪽 부분에도 있다.

흩어져 있는 code 를 하나의 actor type 안에 모을 수는 없다. 그래서 선언마다 붙이는 attribute 를 쓴다.

---

### MainActor attribute

선언에 `@MainActor` 를 붙이면 그 선언은 main actor 에서 실행되어야 한다는 뜻이 된다.

```swift
import UIKit

struct Book: Sendable {
    var title: String
}

class BooksView: UIView {
    var checkedOutBooks: [Book] = []
}

@MainActor let booksView = BooksView()

@MainActor func checkedOut(_ booksOnLoan: [Book]) {
    booksView.checkedOutBooks = booksOnLoan
}

func notify(_ booksOnLoan: [Book]) async {
    // Swift ensures that this code is always run on the main thread.
    await checkedOut(booksOnLoan)
}
```

세션 page 의 snippet 은 `@MainActor func checkedOut(_:)` 과 `await checkedOut(booksOnLoan)` 한 줄이다. 나머지는 직접 채웠고, `booksView` 에도 `@MainActor` 를 붙였다. 이 code 는 Swift 5 mode 와 Swift 6 mode 에서 모두 통과했다.

#### MainActor

[MainActor](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 는 executor 가 main dispatch queue 와 같은 singleton actor 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-main-actor-func.png)
출처: WWDC21 - Protect mutable state with Swift actors

`checkedOut(_:)` 을 main actor 밖에서 부르려면 `await` 를 붙여야 한다. 그러면 호출이 main thread 에서 비동기로 실행된다. `DispatchQueue.main.async` 를 빠뜨릴 수 있었던 예전과 달리, main thread 에서 실행되어야 하는 code 를 표시해 두면 언제 main actor 로 넘어가야 하는지를 Swift 가 챙긴다.

type 에도 붙일 수 있다. type 에 `@MainActor` 를 붙이면 그 type 의 모든 member 와 subclass 가 main actor 위에 놓인다. 대부분의 code 가 main thread 에서 실행되어야 하는 UI code 에 잘 맞는다.

```swift
@MainActor class MyViewController: UIViewController {
    func onPress(_ sender: UIButton) {
        Task {
            await fetchLatestAndDisplay()
        }
    } // implicitly @MainActor

    nonisolated func fetchLatestAndDisplay() async {
        let books = [Book(title: "Dracula")]
        await checkedOut(books)
    }
}
```

세션 page 의 snippet 은 두 method 의 parameter 와 body 가 `...` 로 생략되어 있다. 여기서는 직접 채웠다. 위의 `Book` 과 `checkedOut(_:)` 선언과 같은 file 에 두고 검사했고, Swift 5 mode 와 Swift 6 mode 에서 모두 통과했다.

#### UIViewController

[UIViewController](https://developer.apple.com/documentation/uikit/uiviewcontroller){:target="_blank"} 는 UIKit 앱에서 view 계층 하나를 관리하는 object 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-main-actor-type.png)
출처: WWDC21 - Protect mutable state with Swift actors

`onPress` 는 따로 표시하지 않아도 main actor 위에 있다. 개별 method 는 `nonisolated` 로 빼낼 수 있고, 규칙은 보통 actor 에서 보던 것과 같다. main actor 를 UI 와 관련된 type 과 operation 에 쓰고 다른 state 는 자신의 actor 로 관리하면, 앱의 구조 안에서 concurrency 를 안전하게 쓸 수 있다는 것이 Doug 의 정리다.

---

## 세션의 마무리

Doug 는 세션 내용을 네 문장으로 줄인다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2021-06-08-WWDC21-10133/wwdc21-10133-summary.png)
출처: WWDC21 - Protect mutable state with Swift actors

- actor 로 mutable state 로의 접근을 동기화한다. actor 는 actor isolation 과, 밖에서는 비동기로만 접근하게 하는 규칙으로 state 를 보호한다.
- reentrancy 를 고려해 설계한다. `await` 는 그 사이에 세상이 움직여서 가정이 무효가 될 수 있다는 뜻이다.
- value type 과 actor 를 함께 써서 data race 를 없앤다. 스스로 동기화하지 않는 class 와 그 밖의 non-Sendable type 은 shared mutable state 를 다시 들여오므로 조심한다.
- UI 와 주고받는 code 에는 main actor 를 써서 main thread 에서 실행되어야 하는 code 가 항상 그렇게 실행되게 한다.

이어서 볼 세션으로는 두 개를 권한다. 앱에서 actor 를 실제로 쓰는 과정은 [Swift concurrency: Update a sample app](https://developer.apple.com/videos/play/wwdc2021/10194/){:target="_blank"} 에서, actor 를 포함한 concurrency model 의 구현은 [Swift concurrency: Behind the scenes](https://developer.apple.com/videos/play/wwdc2021/10254/){:target="_blank"} 에서 다룬다. actor 는 async/await, structured concurrency 와 함께 Swift concurrency model 의 핵심을 이룬다.

## 정리

세션에 나온 개념을 한 표로 모으면 다음과 같다.

| 개념 | 하는 일 | 기억할 점 |
|---|---|---|
| data race | 두 thread 가 같은 data 에 동시에 접근하고 하나가 write | 원인은 shared mutable state |
| value semantics | 복사본이 독립이라 공유 자체가 없어짐 | 공유가 꼭 필요한 state 에는 못 씀 |
| actor | state 를 격리하고 한 번에 하나의 code 만 접근시킴 | 밖에서는 `await`, 안에서는 sync |
| reentrancy | suspend 된 동안 같은 actor 에 다른 code 가 들어옴 | `await` 뒤에 가정을 다시 확인 |
| `nonisolated` | member 를 actor 밖에 있는 것으로 다룸 | mutable state 는 참조 못 함 |
| Sendable | concurrent 하게 공유해도 안전한 type 표시 | value type, actor, 조심스럽게 만든 class |
| `@Sendable` 함수 | actor 사이로 넘겨도 안전한 함수 | mutable capture 금지, capture 는 Sendable |
| main actor | main thread 를 나타내는 actor | `@MainActor` 를 함수나 type 에 붙임 |

실제 프로젝트에 가져갈 점은 다음과 같다.

- 여러 task 가 함께 고치는 state 는 class 와 lock 대신 actor 에 넣는다.
- actor 의 state 를 고치는 일은 `await` 가 없는 sync 구간에 모은다. `await` 앞에서 확인한 사실은 `await` 뒤에 다시 확인한다.
- 같은 일을 중복해서 시작하지 않으려면 결과가 아니라 진행 중인 `Task` 를 cache 에 넣는다.
- actor 를 드나드는 data 는 struct 같은 Sendable type 으로 만든다. class 를 돌려주면 Swift 6 language mode 에서 error 가 난다.
- `Hashable` 처럼 sync 요구를 가진 protocol 은 immutable property 만 쓰는 `nonisolated` method 로 만족시킨다.
- view controller 처럼 UI 를 다루는 type 에는 `@MainActor` 를 붙이고, main thread 가 필요 없는 method 만 `nonisolated` 로 빼낸다.
