## 한 줄 요약

Xcode 27 부터는 coding agent 에게 "앱을 Canadian French 로 번역해 줘" 라고 말하면 된다. 언어 추가, String Catalog 생성, 번역, plural variation 까지 agent 와 Xcode 가 나눠서 처리하고, 이때 **Xcode 가 string 마다 context 를 agent 에게 넘겨주는 것**이 핵심이다.

세션은 Landmarks 예제 앱을 Canadian French 로 번역하는 데모 하나로 진행된다. 번역 추가, 검토와 반복, best practice 세 부분이다.

## 번역에 context 가 필요한 이유

예전의 machine learning model 은 소프트웨어 localization 에서 약한 부분이 많았다. 요즘 LLM 은 일반 번역은 잘하지만 context 가 없으면 소프트웨어 번역에서 여전히 틀린다.

세션이 드는 예는 영어 단어 'book' 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-213/wwdc26-213-book.png)

출처: WWDC26 - Translate your app using agents in Xcode

왼쪽 화면의 Book 은 읽을 책이고, 오른쪽 호텔 화면의 Book 은 예약하기라는 동작이다. 영어로는 같은 글자지만 다른 언어에서는 전혀 다른 단어로 번역된다. 한국어로도 하나는 "책" 이고 하나는 "예약" 이다. string 만 덜렁 보고 번역하면 틀린 쪽을 고를 수 있다.

Xcode 는 String Catalog 를 도입한 뒤로 이 context 를 조금씩 쌓아 왔다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-213/wwdc26-213-string-context.png)

출처: WWDC26 - Translate your app using agents in Xcode

- 2년 전: String Catalog 가 string 이 코드의 **어디에서** 쓰이는지 추적하기 시작했다
- 작년: string 이 **어떻게** 쓰이는지까지 추적해서 설명 comment 를 자동으로 만들어 주기 시작했다
- 올해: 이 context 를 모아 coding agent 에게 넘긴다. Xcode 27 에서 agent 로 string 을 직접 번역할 수 있다

## agent 로 번역 추가하기

데모 앱은 세계 여러 곳의 landmark 를 소개하는 Landmarks 앱이다. SwiftUI 로 만들었기 때문에 UI 는 이미 localizable 하다. [Text](https://developer.apple.com/documentation/swiftui/text){:target="_blank"} 나 `Button` 같은 API 는 넘겨받은 string 을 자동으로 localization 대상으로 내놓는다.

시작은 toolbar 의 New Conversation 버튼을 눌러 agent 에게 앱을 Canadian French 로 번역해 달라고 요청하는 것이다. 그 뒤로는 agent 와 Xcode 가 단계별로 일을 나눈다.

---

### 프로젝트 준비 단계

agent 가 가장 먼저 하는 일은 Xcode 에게 프로젝트를 localization 할 수 있게 준비하라고 시키는 것이다. 화면의 transcript 에는 `Prepare Project For Localization` 이라는 단계로 나온다. Xcode 는 이 단계에서 세 가지를 한다.

1. project settings 에 언어를 추가한다. 여기서는 French (Canada), `fr-CA` 다
2. 지원하는 platform 의 모든 target 을 빌드한다. 프로젝트 안의 localizable string 을 빠짐없이 찾으려면 빌드가 필요하다
3. 새로 찾은 string 을 String Catalog 에 넣는다. 프로젝트에 String Catalog 가 하나도 없으면 Xcode 가 알아서 만든다

[Apple 문서](https://developer.apple.com/documentation/xcode/localizing-your-app-using-agents){:target="_blank"}에 따르면 이때 Info.plist 에 들어 있는 사람이 읽는 text 도 함께 localize 된다. 데모 화면에서도 `Landmarks-InfoPlist.xcstrings` 에 `CFBundleName`, `CFBundleDisplayName`, `NSLocationWhenInUseUsageDescription` 이 들어가 있다.

---

### String Catalog 와 table name

string 은 기본으로 `Localizable` 이라는 String Catalog 에 들어간다. string 이 많은 프로젝트라면 table name 을 지정해서 여러 catalog 로 나눌 수 있다.

```swift
Text("Hello, world!", comment: "A standard greeting")
```

#### Text 의 comment 로 번역 context 남기기

[Text](https://developer.apple.com/documentation/swiftui/text){:target="_blank"} 에 string literal 을 넘기면 그 string 은 localization key 가 된다. `comment` 는 화면에 나오지 않고 String Catalog 에 같이 저장되어 번역하는 쪽에 string 의 뜻을 알려 준다. table name 을 주지 않았으니 이 string 은 `Localizable.xcstrings` 로 간다.

```swift
Text("Hello, world!", tableName: "Greetings", comment: "A standard greeting")
```

#### tableName 으로 String Catalog 나누기

[init(_:tableName:bundle:comment:)](https://developer.apple.com/documentation/swiftui/text/init%28_:tablename:bundle:comment:%29){:target="_blank"} 의 `tableName` 에 `Greetings` 를 주면 이 string 은 `Greetings.xcstrings` 로 들어간다. 그 이름의 catalog 가 없으면 준비 단계에서 Xcode 가 만든다.

데모에서는 준비가 끝난 뒤 navigator 에 String Catalog 4개가 새로 생겼다. agent 는 번역할 string 을 고르는데, 프로젝트 전체를 번역해 달라고 했으므로 4개를 전부 읽는다.

---

### subagent 와 string context

실제 번역은 여기서 시작된다. agent 는 string 을 batch 로 나누고 batch 마다 subagent 에게 번역을 맡긴다. 화면에서는 agent 가 batch 9개를 만들고, 앱 이름이 들어 있는 InfoPlist 를 먼저 번역해서 뒤의 번역이 그 용어를 재사용하게 한 다음, `Localizable.xcstrings` 의 batch 를 3개씩 병렬로 돌린다.

Xcode 는 subagent 에게 번역할 string 마다 context 를 준다. 화면에서는 `Get String Context` 라는 단계로 보인다. 세션이 말하는 context 는 세 가지다.

- string 이 코드의 어디에서 쓰이는지
- 비슷한 용어를 쓰는 다른 string 목록
- 같은 string 이 다른 언어로 어떻게 번역되어 있는지

앞에서 본 'book' 문제가 여기서 풀린다. subagent 는 string 한 줄만 보는 것이 아니라 그 string 이 어느 화면의 어떤 view 에 들어가는지를 같이 본다.

---

### plural variation 이란?

plural variation 은 숫자에 따라 문장이 달라지는 string 을 숫자 범주별로 따로 번역해 두는 것이다. 세션은 subagent 하나가 `%lld items` 를 어떻게 처리했는지를 보여 준다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-213/wwdc26-213-plural.png)

출처: WWDC26 - Translate your app using agents in Xcode

`%lld` 는 runtime 에 숫자로 바뀌는 placeholder 다. 영어에서는 숫자에 따라 "1 item", "2 items" 로 달라져야 하므로 이 string 은 plural 로 나뉘어 있다. subagent 는 Canadian French 쪽도 똑같이 나눴다.

| 범주 | English | French (Canada) |
|---|---|---|
| one | `%lld item` | `%lld élément` |
| other | `%lld items` | `%lld éléments` |

언어마다 plural 범주의 개수가 다르다. 영어와 French 는 둘이지만 더 많은 언어도 있고 한국어처럼 나눌 필요가 없는 언어도 있다. 어떤 언어에 어떤 variation 이 필요한지는 Xcode 가 subagent 에게 알려 주기 때문에, agent 가 언어별 규칙을 틀리게 기억해서 범주를 빠뜨리는 일을 막을 수 있다.

---

### 번역된 앱 실행하기

번역이 끝나면 그 언어로 앱을 실행해 본다. 기기 언어를 바꿀 필요는 없다.

1. toolbar 에서 scheme 을 선택하고 Edit Scheme 으로 들어간다
2. Run 을 고르고 Options tab 으로 간다
3. App Language 를 French (Canada) 로 바꾼다
4. 빌드하고 실행한다

이렇게 하면 다음 debug run 만 그 언어로 뜬다.

### 용어 바꾸기

첫 번역에서 agent 는 'landmarks' 를 'lieux d'intérêt' 로 옮겼다. 잘 통하는 좋은 번역이다. 그런데 발표자는 Canadian French 를 쓰며 자랐고, Canada 관광 업계에서는 이 앱이 말하는 landmarks 와 비슷한 뜻으로 'attraits' (attractions) 를 자주 쓴다는 것을 안다. 더 편하고 Canada 의 French 화자에게 익숙한 말이다.

그래서 두 가지를 agent 에게 요청한다.

- 'landmarks' 의 번역을 'attraits' 로 바꾼다
- 앱 이름은 'Attraits phares' (Flagship attractions) 로 바꾼다

agent 는 관련된 string 을 전부 찾아서 고친다. 앱 이름도, "Draw a sketch of this landmark" 같은 문장도 함께 바뀐다. 처음 번역을 넣을 때와 같은 방식으로 요청하면 된다.

---

### 새 기능과 용어의 일관성

이미 localize 된 앱에 기능을 추가할 때도 같은 흐름을 쓴다. 발표자는 새 conversation 을 열고, featured landmark 아래에 "앱의 landmark 를 전부 찾아보라" 는 label 을 추가하고 localize 해 달라고 요청한다. agent 는 기능을 만든 다음 Canadian French 로 번역한다.

결과로 `Can you discover all %lld landmarks?` 라는 string 이 생겼고, 영어와 Canadian French 양쪽에 plural variation 이 들어갔다.

| 범주 | English | French (Canada) |
|---|---|---|
| one | `Can you discover all %lld landmark?` | `Pouvez-vous découvrir le %lld attrait?` |
| other | `Can you discover all %lld landmarks?` | `Pouvez-vous découvrir tous les %lld attraits?` |

눈여겨볼 부분은 'attraits' 다. 이 conversation 은 새로 연 것이라 agent 는 앞에서 용어를 바꾸던 대화를 읽지 않았다. 그런데도 기본으로는 고르지 않았을 'attraits' 를 썼다. Xcode 가 비슷한 용어를 쓰는 기존 string 과 그 번역을 context 로 넘겨줬기 때문이다. 대화 기록이 아니라 String Catalog 에 들어 있는 번역이 용어집 역할을 하는 셈이다.

## 번역 검토와 반복

번역을 프로젝트에 넣는 것은 일의 일부다. 다른 언어에서 runtime 에 화면이 기대한 대로 나오는지까지 봐야 한다. 이 장은 agent 에게 맡길 수 있는 검토와 사람에게 받아야 하는 검토를 나눠서 다룬다.

---

### agent 로 truncation 찾기

언어마다 성격이 다르다. Canadian French 문장은 평균적으로 영어보다 길다. 방금 번역한 label 이 UI 안에 잘리지 않고 들어가는지 확인해야 한다.

발표자는 agent 에게 새 기능의 UI 를 Canadian French 로 render 해서 truncation 을 찾아 달라고 요청한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-213/wwdc26-213-truncation.png)

출처: WWDC26 - Translate your app using agents in Xcode

agent 는 `LandmarksView` preview 를 `fr-CA` locale 로 render 하고 snapshot 을 찍어서 문제를 찾아냈다. label 이 "Pouvez-vous découvrir tous les 21 attr…" 에서 잘린다. 화면에 보이는 agent 의 설명으로는 `Text` 에 걸린 [lineLimit(1)](https://developer.apple.com/documentation/swiftui/view/linelimit%28_:%29){:target="_blank"} 때문에 영어 문장은 들어가지만 더 긴 French 문장은 폭을 넘는다.

여기서 무엇을 고칠지는 개발자가 판단한다. 세션이 드는 선택지는 셋이다.

- 구현의 단순한 bug 인지 확인한다
- 긴 text 를 받아들이도록 UI 를 다시 설계한다
- 그래도 안 되면 model 에게 더 짧은 번역을 요청한다

순서에 뜻이 있다. 번역을 줄이는 것은 마지막 수단이다.

같은 방법으로 다른 언어의 문제도 찾을 수 있다.

- Thai 처럼 글자가 세로로 큰 언어에서 text 의 위아래가 잘리는 문제
- Arabic 같은 right-to-left 언어에서 view 정렬이 틀어지는 문제

기능을 만들면서 바로 확인하고 고칠 수 있다는 점이 이 방식의 장점이다. text layout 과 formatting 문제를 다루는 API 는 [Build multilingual-ready apps](https://developer.apple.com/videos/play/wwdc2024/10185/){:target="_blank"} 와 [Get it right (to left)](https://developer.apple.com/videos/play/wwdc2022/10107/){:target="_blank"} 세션에서 다룬다.

### native speaker 피드백

agent 의 검토만으로는 부족하다. 세션이 짚는 이유는 이렇다. agent 로 코딩할 때 개발자의 가장 큰 강점은 코드를 이해한다는 것이다. agent 가 만든 코드가 요구에 맞는지, nuance 를 놓쳤는지, 엉뚱한 방향으로 가는지를 알아볼 수 있다.

내가 유창하지 않은 언어로 번역을 시킬 때는 그 강점이 사라진다. 결과가 맞는지 판단할 수가 없다.

그래서 TestFlight 를 쓴다. 새 기능을 App Store 에 내기 전에 사람들에게 테스트를 부탁하듯이, 추가하는 언어의 native speaker 에게 그 언어로 앱을 써 보게 한다. TestFlight 에서는 제안이나 localization 문제가 보이는 screenshot 을 피드백으로 쉽게 보낼 수 있어서 공개 전에 고칠 수 있다.

발표자가 'landmarks' 의 번역을 바꿀 수 있었던 것은 Canadian French 를 할 줄 알아서였다. 다른 언어에서는 그런 제안을 TestFlight 로 받아야 한다. TestFlight 로 피드백을 모으는 방법은 tech talk [Get started with TestFlight](https://developer.apple.com/videos/play/tech-talks/110343/){:target="_blank"} 에 있다.

## best practice

세션의 마지막 부분은 번역 기능을 제대로 쓰기 위한 조언이다. localizable 한 string, translation guidance, model 선택, agent 번역의 구분 네 가지를 다룬다.

---

### localizable 한 string

잘 localize 된 앱이라면 사용자에게 보이는 string 이 전부 번역되어 있어야 한다. 그러려면 먼저 그 string 들이 localizable 해야 한다. 준비 단계에서 Xcode 가 찾아내지 못한 string 은 agent 가 번역할 수도 없다.

SwiftUI 코드는 기본으로 localizable 하다. 그 밖의 코드에서 사람이 읽는 string 을 만들 때는 따로 API 를 써야 한다.

```swift
String(localized: "Hello, world!", comment: "A standard greeting")
```

#### String(localized:) 로 localizable 한 String 만들기

[String(localized:)](https://developer.apple.com/documentation/swift/string/init%28localized:%29){:target="_blank"} 계열의 initializer 는 넘긴 값을 localization key 로 삼아 현재 locale 의 번역을 찾아 `String` 을 만든다. `let title = "Hello, world!"` 처럼 그냥 `String` 으로 만들면 Xcode 는 이것을 번역 대상으로 보지 않는다. view model 이나 notification 본문처럼 SwiftUI view 밖에서 만드는 문장이 여기에 해당한다.

```swift
LocalizedStringResource("Hello World!", bundle: #bundle, comment: "A standard greeting")
```

#### LocalizedStringResource 로 번역을 나중에 찾기

[LocalizedStringResource](https://developer.apple.com/documentation/foundation/localizedstringresource){:target="_blank"} 는 번역된 결과가 아니라 "이 key 를 이 bundle 에서 찾아라" 라는 참조를 들고 다니는 타입이다. 번역은 실제로 보여 줄 때 찾는다. App Intents 처럼 string 을 다른 process 로 넘겨야 할 때 쓴다. [#bundle](https://developer.apple.com/documentation/foundation/bundle%28%29){:target="_blank"} 은 이 코드가 들어 있는 target 의 resource bundle 을 가리키는 macro 다.

> `#bundle` 줄은 Swift package 에서 빌드해 보면 target 에 resource 가 하나도 없을 때 `No resource bundle is available for this module` 에러가 난다. package 의 target 에 `Localizable.xcstrings` 를 넣고 `resources: [.process("Resources")]` 를 선언한 뒤에 빌드가 됐다. 앱 target 에서는 해당하지 않는다.
{: .prompt-warning }

localization 에 쓰는 API 전반은 [Code-along: Explore localization with Xcode](https://developer.apple.com/videos/play/wwdc2025/225/){:target="_blank"} 세션에서 다룬다. UIKit 과 AppKit 에서 쓰는 API 는 [Preparing your app's text for translation](https://developer.apple.com/documentation/xcode/preparing-your-apps-text-for-translation){:target="_blank"} 문서에 있다.

### translation guidance 란?

translation guidance 는 agent 가 번역할 때 따라야 할 내 앱만의 규칙을 적어 둔 글이다. string 이 전부 localizable 해졌다면 다음으로 생각할 것은 앱의 audience 다. 은행 앱과 어린이 앱은 말투도 용어도 다르다.

agent 는 기본으로 Xcode 에 들어 있는 언어별 style guide 를 쓴다. Apple 의 번역 경험이 여기에 담겨 있다. 여기에 개발자가 준 guidance 를 더해서 따른다. 세션이 드는 guidance 의 예는 세 가지다.

- glossary: 특정 단어를 어떤 번역으로 쓸지 정한 목록
- 번역하지 않을 단어 목록: 제품 이름이나 trademark
- 앱이 쓸 tone 을 평문으로 적은 설명

이 guidance 는 `AGENTS.md` 나 프로젝트에 이미 있는 비슷한 파일에 번역 섹션을 만들어서 준다. 다만 내용을 전부 거기에 쓰면 번역과 상관없는 작업을 할 때도 매번 context 에 올라간다. 그래서 세션은 `AGENTS.md` 에서는 `TRANSLATION.md` 라는 파일을 가리키기만 하고, guidance 는 전부 그 파일에 쓰라고 권한다. agent 는 번역 작업을 할 때만 그 파일을 읽는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-213/wwdc26-213-translation-md.png)

출처: WWDC26 - Translate your app using agents in Xcode

화면의 `TRANSLATION.md` 는 어린이 교육 앱의 예다. audience 가 아이 (4~12세) 와 보호자 둘이라는 설명으로 시작해서, 아이에게 보이는 string 은 informal 하게, 보호자에게 보이는 string 은 formal 하게 쓰라는 규칙과, 영어의 칭찬 관용구 ("You're on fire!" 같은 것) 를 글자 그대로 옮기지 말고 그 언어의 아이가 칭찬으로 알아들을 말로 바꾸라는 규칙이 적혀 있다.

이 구조를 내 프로젝트에 옮긴다면 `AGENTS.md` 쪽은 이 정도면 된다. 아래는 세션에 나온 것이 아니라 설명을 위해 내가 쓴 예다.

```markdown
## Translation Guidance

번역이나 localization 작업을 할 때는 먼저 TRANSLATION.md 를 읽는다.
```

Apple 문서에 따르면 `CLAUDE.md` 처럼 agent 가 자동으로 읽는 다른 설정 파일에서도 같은 방식으로 참조할 수 있다.

---

### model 선택

앱 번역은 복잡하고 오래 걸리는 작업이다. 프로젝트 전체에서 용어를 일관되게 쓰려면 더 그렇다. 세션은 model 을 고를 때 두 가지를 보라고 한다.

- context window 가 클 것
- 길게 이어지는 요청을 끝까지 해내는 데 강할 것

주의할 점도 둘 있다.

- 대부분의 model 이 학습한 데이터에는 어떤 언어가 다른 언어보다 적게 들어 있다. 그런 언어는 번역 품질이 떨어질 수 있다
- model 에 따라 특정 언어를 더 잘하거나 못할 수 있다

학습 데이터의 언어 분포는 model provider 의 문서를 확인하라는 것이 세션의 안내다.

---

### agent 번역 구분하기

Xcode 에서 localization 을 export 해서 번역 업체나 다른 도구로 넘기는 경우, 어떤 번역이 agent 가 넣은 것인지 구분할 수 있다. export 된 XLIFF 에서 `state-qualifier` 를 본다.

```xml
<trans-unit id="Grand Canyon" xml:space="preserve">
  <source>Grand Canyon</source>
  <target state="translated" state-qualifier="leveraged-mt">Grand Canyon</target>
  <note>Name of the ‘Grand Canyon’ landmark.</note>
</trans-unit>
```

`target` 의 `state-qualifier="leveraged-mt"` 가 agent 가 번역한 항목이라는 표시다. `note` 에는 String Catalog 의 comment 가 들어간다. Apple 문서에 따르면 String Catalog 파일 안에서는 같은 번역의 state 가 `machine_translated` 로 기록된다. 이 조각은 세션에 나온 XLIFF 를 그대로 옮긴 것이고, 직접 export 해서 확인한 것은 아니다.

사람이 검수한 번역과 agent 가 넣은 번역을 섞어 쓰는 프로젝트라면, 이 표시로 검수가 필요한 항목만 골라서 native speaker 에게 넘길 수 있다.

---

## 정리

세션의 흐름을 한 번에 적으면 이렇다.

1. agent 에게 번역을 요청한다
2. Xcode 가 언어를 추가하고, 모든 target 을 빌드해서 string 을 찾고, String Catalog 에 넣는다
3. agent 가 string 을 batch 로 나눠 subagent 에게 맡긴다
4. Xcode 가 subagent 에게 string 별 context (사용 위치, 비슷한 용어의 string, 다른 언어 번역) 와 필요한 plural variation 을 알려 준다
5. scheme 의 App Language 를 바꿔 실행해 본다
6. agent 에게 그 언어로 UI 를 render 하게 해서 truncation 같은 문제를 찾는다
7. native speaker 에게 TestFlight 로 피드백을 받는다

실제 프로젝트에 가져갈 점도 적어 둔다.

- 번역을 맡기기 전에 SwiftUI view 밖에서 만드는 string 이 `String(localized:)` 를 쓰는지 먼저 본다. 빌드로 찾지 못한 string 은 번역되지 않는다
- `comment` 는 agent 가 읽는 context 이기도 하다. 'book' 처럼 뜻이 갈리는 짧은 string 일수록 적어 둘 가치가 크다
- 용어를 한 번 바로잡아 두면 String Catalog 의 기존 번역이 다음 번역의 기준이 된다. 그래도 꼭 지켜야 하는 용어는 `TRANSLATION.md` 의 glossary 에 적어 두는 편이 확실하다
- 내가 모르는 언어의 번역은 내가 검증할 수 없다. agent 가 넣은 번역은 `leveraged-mt` 로 구분되니, 출시 전에 그 언어를 아는 사람의 확인을 받는다
