## 한 줄 요약

Swift 6 language mode 는 data isolation 을 compiler 가 끝까지 강제하는 mode 이고, 켤지 말지는 target 마다 고른다. 옮기는 순서는 target 하나를 잡아 Swift 5 mode 에서 complete checking 을 켜고, 나온 warning 을 없애고, Swift 6 mode 로 잠근 뒤 다음 target 으로 가는 것이다. warning 의 대부분은 global variable 을 `let` 으로 바꾸거나 함수와 protocol 에 `@MainActor` 를 붙이는 식의 작은 수정으로 사라지고, compiler 가 알 수 없는 약속은 `MainActor.assumeIsolated` 나 `@preconcurrency` 로 실행 시점 검사에 맡긴다.

## Coffee Tracker 와 WWDC21 의 refactoring

예제는 하루 동안 마신 커피를 기록하는 watchOS 앱 Coffee Tracker 다. 지금의 caffeine 수치를 watch face 에 보여 주는 complication 도 함께 들어 있다. Ben 은 Swift Concurrency 가 처음 나온 WWDC21 에서 바로 이 앱을 새 concurrency model 로 옮기는 세션 [Swift concurrency: Update a sample app](https://developer.apple.com/videos/play/wwdc2021/10194/){:target="_blank"} 을 맡았고, 이번 세션은 그 뒷이야기다.

그때의 교훈은 깔끔해 보이는 구조가 concurrency 의 복잡함을 가리고 있었다는 것이다. view 와 model 만 보면 type 은 잘 나뉘어 있었다. 그런데 code 가 어느 queue 에서 도는지를 따라가 보면 그림이 달랐다. 원래 앱에는 code 가 실행될 수 있는 queue 가 세 종류 있었다.

- UI 와 model 의 작업은 main queue 에서 돌았다.
- background 작업을 위한 dispatch queue 가 하나 있었다.
- HealthKit 이 결과를 돌려주는 completion handler 같은 callback 은 임의의 queue 에서 불렸다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-queue-before.png)
출처: WWDC24 - Migrate your app to Swift 6

type 은 가지런했지만, 어떤 code 가 어떤 queue 에서 왜 도는지는 type 사이를 가로질러 얽혀 있었고 군데군데 분명하지도 않았다.

Swift Concurrency 를 도입하면서 이 임시방편 구조가 다음처럼 바뀌었다. UI view 와 model 은 main actor 에서 돌고, background 작업은 전용 actor 가 맡는다. actor 끼리는 thread-safe 한 value type 을 async/await 로 주고받는다. 그 결과 concurrency 구조도 type 구조만큼 설명하기 쉬워졌다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-actors-after.png)
출처: WWDC24 - Migrate your app to Swift 6

하지만 걸리는 점이 하나 남아 있었다. data race 를 피하는 책임이 여전히 programmer 에게 많이 남아 있었다는 것이다. Ben 은 guideline 을 지켜 actor 사이에 value type 만 넘겼지만, 꼭 그래야 하는 것은 아니었다. class 같은 reference type 을 한 actor 에서 다른 actor 로 넘길 수도 있었다. reference type 은 shared mutable state 를 들고 다닐 수 있고, 그렇게 되면 두 actor 가 같은 state 에 동시에 접근하게 되어 actor 가 주는 mutual exclusion 이 깨진다. 즉 class instance 를 actor 사이로 보내면 여전히 data race 가 날 수 있고, 그 결과는 crash 이거나 더 나쁘게는 사용자 data 의 손상이다.

## Swift 6 language mode 와 data-race safety

위의 허점을 막는 것이 Swift 6 의 이점이다. Swift 6 language mode 는 data isolation 을 완전히 강제한다. task 와 actor 사이에 state 가 실수로 공유되는 일을 compiler 가 막아 주므로, refactoring 을 하거나 기능을 더할 때 새 concurrency bug 를 넣고 있는지 걱정하지 않아도 된다.

---

### data isolation 이란?

data isolation 은 mutable state 마다 그것을 만질 수 있는 영역이 정해져 있다는 뜻이다. actor 의 state 는 그 actor 안에서만, main actor 에 묶인 state 는 main actor 에서만 만질 수 있고, 영역을 넘어가는 값은 안전하게 넘길 수 있는 값이어야 한다. Swift 5 mode 에서는 이 규칙의 일부만 검사하거나 warning 으로만 알려 주지만, Swift 6 language mode 에서는 어긋나는 code 가 compile error 가 된다.

---

### Swift 6 로 옮길 시점

Swift 6 language mode 는 기존 project 든 새 project 든 직접 골라서 켜는 opt-in 이다. 켜면 concurrent code 의 실수를 compile 시점에 잡으므로 앱의 품질이 눈에 띄게 올라갈 수 있다. Ben 은 특히 다음 세 경우를 꼽는다.

- 재현하기 어려운 crash 를 겪고 있고, data race 의 가능성을 체계적으로 지워 나가고 싶을 때
- 반응성과 성능을 위해 concurrency 를 더 넣고 있는 중이고, 그 변경이 새 data race 를 만들지 않게 하고 싶을 때
- 공개 Swift package 를 관리할 때. 사용자들이 자기 code base 를 옮기려면 dependency 가 먼저 Swift 6 를 채택해 있는 편이 좋으므로 되도록 빨리 옮기기를 권한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-when-to-migrate.png)
출처: WWDC24 - Migrate your app to Swift 6

많이 쓰이는 package 들의 채택 상황은 [Swift Package Index](https://swiftpackageindex.com/){:target="_blank"} 에서 따라가 볼 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-package-index.png)

### 새 code 를 위한 안전

Ben 은 자기 앱에 지금 data race 가 실제로 있다고는 생각하지 않는다고 말한다. 대부분의 code 도 마찬가지일 것이다. 오래 다듬고, bug report 를 받고, Main Thread Checker 와 Thread Sanitizer 를 돌리면서 기존 code 의 data race 는 이미 대부분 털어 냈을 가능성이 높다.

data-race safety 의 진짜 가치는 앞으로 쓸 code 를 지키는 데 있다. 새 기능을 넣거나, concurrency 를 더 잘 쓰도록 기존 code 를 refactoring 할 때다. data-race safety 가 있으면 나중에 추적해야 할 data race, 혹은 crash 를 재현하지 못해 짐작으로 넣는 수정을 걱정하지 않고 concurrency 를 쓸 수 있다.

demo 의 설정도 여기에 맞춰져 있다. Coffee Tracker 가 잘 되어서 team 이 커졌고, 앱의 일부를 CoffeeKit 이라는 새 framework 로 떼어 냈다. team 은 새 기능을 넣고 싶어 하지만, 그 전에 Swift 6 로 옮겨서 기능을 넣는 동안 새 concurrency bug 가 들어오지 않게 하려 한다.

## migration 전략

Ben 은 Xcode 16 을 막 내려받아 project 를 연다. Swift 6 compiler 와 watchOS 11 SDK 가 들어 있는 상태다. 그대로 build 하면 아무 수정 없이 성공한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-build-succeeded.png)
출처: WWDC24 - Migrate your app to Swift 6

build 가 되는 것은 앱에 data race 의 가능성이 없어서가 아니다. Swift 6 language mode 를 아직 켜지 않았기 때문이다. 이전 release 들과 마찬가지로 Swift 6 에도 source compatibility 보장이 있어서, 아주 사소한 변화를 빼면 기존 앱은 새 compiler 로 항상 build 되어야 한다.

다음 단계는 data isolation 을 완전히 강제하는 Swift 6 mode 를 켜는 것이다. 그 준비로 compiler 진단을 켜기 전에 `MainActor` 와 `Sendable` 을 직접 훑으며 점검할 수도 있다. 하지만 그러면 새 compiler 가 주는 이점을 놓친다. compiler 진단은 고쳐야 할 곳으로 안내해 준다. Ben 은 이것을 code 의 잠재적인 bug 를 짚어 주는 pair programmer 에 빗댄다. 진단을 따라가면 migration 과정에 구조가 생긴다.

---

### target 별 네 단계

migration 은 target 하나씩 진행하고, 각 target 에서 다음 순서를 밟는다.

1. complete concurrency checking 을 켠다. module 단위의 설정이고, project 는 Swift 5 mode 에 그대로 두면서 Swift 6 의 data isolation 에서 실패할 code 전부에 warning 을 낸다.
2. 그 target 의 warning 을 모두 해결한다.
3. Swift 6 mode 를 켠다. 지금까지의 수정이 잠기고, 이후의 refactoring 이 안전하지 않은 상태로 되돌아가는 것을 막는다.
4. 다음 target 으로 가서 반복한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-steps.png)
출처: WWDC24 - Migrate your app to Swift 6

모든 target 이 끝나면 앱 전체를 돌아보며 refactoring 을 할 수 있다. 구조를 바꿔서 unsafe 로 빠져나갔던 곳을 되돌리거나, 진행하면서 눈에 띈 더 나은 구조로 고치는 것이다.

---

### refactoring 과 분리하기

refactoring 에 대해 Ben 이 주는 조언은 하나다. 큰 refactoring 과 data-race safety 를 켜는 일을 섞지 말고 한 번에 하나씩 하라는 것이다. 둘을 함께 하면 한꺼번에 바뀌는 것이 너무 많아져서 결국 되돌아가게 된다.

이 세션이 다루는 것도 이미 Swift Concurrency 로 refactoring 을 마친 앱에 Swift 6 를 켜는 단계뿐이다.

## concurrency 기능과 compiler 진단

complete checking 이 무엇을 켜는지 보기 전에, 그것을 켜지 않아도 만나는 진단이 있다. 앱에서 이미 Swift Concurrency 를 쓰고 있다면 concurrency 기능을 도입하는 자리에서 warning 이나 error 를 본 적이 있을 것이다.

예제는 새로 넣고 있는 delegate 다. CoffeeKit 에 추가하는 callback 을 받아서 caffeine 수치가 걱정스러울 만큼 낮아졌을 때 알려 주는 type 이다.

```swift
import CoffeeKit
import SwiftUI

class Recaffeinater: ObservableObject {
    @Published var recaffeinate: Bool = false
    var minimumCaffeine: Double = 0.0
}

extension Recaffeinater: CaffeineThresholdDelegate {
    public func caffeineLevel(at level: Double) {
        if level < minimumCaffeine {
            // TODO: alert user to drink more coffee!
        }
    }
}
```

세션 page 의 snippet 에 `import` 두 줄을 더했다. protocol 은 다른 module 인 CoffeeKit 에 있어야 세션과 같은 상황이 되므로, 아래의 protocol 선언만 담은 CoffeeKit module 을 Swift 5 mode 로 따로 만들어서 import 했다. 이 상태로는 세 설정 모두에서 진단이 없다.

```swift
public protocol CaffeineThresholdDelegate: AnyObject {
    func caffeineLevel(at level: Double)
}
```

#### ObservableObject

[ObservableObject](https://developer.apple.com/documentation/combine/observableobject){:target="_blank"} 는 `@Published` property 가 바뀌기 전에 알림을 내보내 SwiftUI view 가 다시 그려지게 하는 Combine 의 protocol 이다.

이 delegate 는 값을 SwiftUI view 로 publish 하므로 main actor 에 isolate 하고 싶다. 그래서 class 위에 `@MainActor` 를 붙여 모든 method 와 property 접근이 main thread 에서 이루어지게 한다.

```swift
@MainActor
class Recaffeinater: ObservableObject {
    @Published var recaffeinate: Bool = false
    var minimumCaffeine: Double = 0.0
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-recaffeinater.png)
출처: WWDC24 - Migrate your app to Swift 6

그러면 아래쪽의 protocol 구현에서 진단이 나온다. 세션 화면의 문구는 main actor 에 isolate 된 instance method `caffeineLevel(at:)` 을 nonisolated protocol requirement 를 만족하는 데 쓸 수 없다는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-protocol-fixit.png)
출처: WWDC24 - Migrate your app to Swift 6

지금의 compiler 는 같은 문제를 conformance 쪽에서 말한다. Swift 5 mode 에서는 minimal 과 complete 모두 아래 warning 이고, Swift 6 mode 에서는 같은 내용의 error 다.

```
warning: conformance of 'Recaffeinater' to protocol 'CaffeineThresholdDelegate' crosses into main actor-isolated code and can cause data races; this is an error in the Swift 6 language mode [#ConformanceIsolation]
```

이유는 이렇다. `CaffeineThresholdDelegate` protocol 은 자기가 어떻게 불릴지에 대해 아무 보장도 하지 않는다. CoffeeKit 안에 있고, CoffeeKit 은 아직 Swift 6 로 옮기지 않았다. 그런데 `Recaffeinater` 는 방금 main actor 로 제한했다. 이 type 의 method 는 main actor 에서 돌게 되는데, 항상 main actor 에서 불린다는 보장이 없는 protocol 을 그대로 conform 할 수는 없다.

이 진단은 complete checking 과 상관없이, type 하나를 main actor 에서 불리는지 검사받도록 골라 넣었기 때문에 나온 것이다. WWDC21 의 Coffee Tracker 세션에서 앱 여기저기에 concurrency 를 도입할 때 나오던 것과 같은 종류다. 해결은 complete checking 을 켠 다음 다른 warning 들과 함께 한다.

## watch extension 의 complete checking

target 의 build setting 에서 strict checking 을 켜면 그 module 전체가 race condition 가능성을 검사받는다. Swift 의 data isolation 은 target 단위로 켜고, 이 앱에는 중요한 target 이 둘 있다. UI 층이 있는 WatchKit extension 과, caffeine 을 추적하고 HealthKit 에 저장하는 business logic 이 있는 framework CoffeeKit 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-targets.png)
출처: WWDC24 - Migrate your app to Swift 6

---

### extension 부터 시작하는 이유

Ben 은 watch extension 부터 complete checking 을 켠다. 이유는 두 가지다.

첫째, 보통 UI 층이 concurrency checking 을 켜기에 더 쉬운 곳이다. UI 층의 많은 부분은 main thread 에서 돌고, SwiftUI 나 UIKit 처럼 그 자체가 main thread 에서 동작한다고 보장하는 API 를 쓴다.

둘째, strict concurrency 를 켜면 아직 Swift Concurrency 에 맞게 갱신되지 않은 다른 module 과 함께 일하게 되는 경우가 많다. 영영 갱신되지 않을 C library 일 수도 있고, 언젠가 Swift 6 로 갱신되겠지만 아직은 아닌 framework 나 package 일 수도 있다. 이 앱에서는 CoffeeKit 이 바로 그런 module 이다. 위에서 아래로 내려가는 순서가 왜 도움이 되는지는 `Recaffeinater` 의 warning 을 고치는 과정에서 드러난다. 아직 갱신되지 않은 module 을 쓰는 쪽의 기법을 먼저 익히고, 그 module 을 갱신하면 그 기법이 필요 없어지는 것까지 보게 된다.

extension target 의 build setting 에서 Swift concurrency checking 을 검색해 Complete 로 바꾼다. 이렇게 하면 compiler 가 concurrency-safe 하다고 확인할 수 없는 code 에 warning 을 내기 시작한다. warning 일 뿐이라 project 는 여전히 build 되고 실행된다. build 하면 앞에서 만든 warning 에 더해 몇 개가 더 보인다.

## global variable 의 shared mutable state

첫 번째 warning 은 Swift 6 에서 가장 흔하게 다루게 되는 종류로, `logger` 라는 변수를 가리킨다.

```swift
import os

var logger = Logger(
    subsystem:
        "com.example.apple-samplecode.Coffee-Tracker.watchkitapp.watchkitextension.ContentView",
    category: "Root View")
```

`import os` 를 더했다. 그리고 검사가 의미를 갖도록 이 변수를 쓰는 nonisolated 함수와 `@MainActor` 함수를 하나씩 붙였다. Swift 5 minimal 에서는 진단이 없고, complete 에서는 아래 warning, Swift 6 mode 에서는 같은 내용의 error 다.

```
warning: var 'logger' is not concurrency-safe because it is nonisolated global shared mutable state; this is an error in the Swift 6 language mode [#MutableGlobalVariable]
```

#### Logger

[Logger](https://developer.apple.com/documentation/os/logger){:target="_blank"} 는 unified logging system 에 log message 를 쓰는 type 이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-logger-warning.png)
출처: WWDC24 - Migrate your app to Swift 6

logger instance 가 global variable 로 선언되어 있다. global variable 은 shared mutable state 의 원천이다. program 의 어떤 code 든, 어떤 thread 에서 돌든 같은 변수를 읽고 쓸 수 있다. 그래서 data race 가 쉽게 생기는 곳이고 안전하게 만들어야 한다. 이 검사의 설계는 [SE-0412](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0412-strict-concurrency-for-global-variables.md){:target="_blank"} 에 있다. 방법은 몇 가지가 있고, issue 를 펼치면 compiler 가 그 선택지를 직접 권한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-logger-fixit.png)
출처: WWDC24 - Migrate your app to Swift 6

### let 으로 바꾸기

가장 쉬운 방법은 읽기 전용으로 만드는 것이다. `Logger` 는 `Sendable` type 이므로 `let` 으로 선언되어 있으면 여러 thread 에서 써도 data race 를 일으킬 수 없다.

```swift
let logger = Logger(
    subsystem:
        "com.example.apple-samplecode.Coffee-Tracker.watchkitapp.watchkitextension.ContentView",
    category: "Root View")
```

`var` 를 `let` 으로 바꾸고 다시 build 하면 issue 가 사라진다. 내 검사에서도 세 설정 모두 진단이 없다. 이 경우에는 이것이 맞는 수정이다.

---

### global actor 에 묶기

값을 나중에 바꾸고 싶어서 `let` 이 아니라 `var` 로 두고 싶다고 하자. 그럴 때는 global variable 을 global actor 에 묶을 수 있다. 여기는 UI 층이니 log 는 모두 main actor 에서 남길 것이다. 그러면 변수에 `@MainActor` 를 붙이면 된다.

```swift
@MainActor var logger = Logger(
    subsystem:
        "com.example.apple-samplecode.Coffee-Tracker.watchkitapp.watchkitextension.ContentView",
    category: "Root View")
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-logger-mainactor.png)
출처: WWDC24 - Migrate your app to Swift 6

세션의 앱에서는 logger 를 쓰는 곳이 전부 main actor 라서 이것으로도 warning 이 없어진다. 내 검사에서도 `@MainActor` 함수에서만 쓸 때는 진단이 없었다. nonisolated 함수에서 쓰는 곳이 하나라도 있으면 세 설정 모두에서 다음 error 가 난다.

```
error: main actor-isolated var 'logger' can not be referenced from a nonisolated context
```

### compiler 가 모르는 보호 장치

마지막 선택지는 compiler 가 강제할 수 없는 외부 장치가 이 변수를 지키고 있는 경우를 위한 것이다. 예를 들어 모든 접근을 dispatch queue 로 감싸고 있을 수 있다. 그럴 때는 `nonisolated(unsafe)` keyword 를 쓴다.

```swift
nonisolated(unsafe) var logger = Logger(
    subsystem:
        "com.example.apple-samplecode.Coffee-Tracker.watchkitapp.watchkitextension.ContentView",
    category: "Root View")
```

세 설정 모두 진단 없이 compile 된다. Swift 에서 unsafe 라는 말이 쓰이는 다른 곳과 마찬가지로, 이 변수의 안전은 쓰는 사람이 책임진다는 뜻이다. 이것은 최후의 수단이어야 하고, Swift 의 compile 시점 보장을 쓰는 편이 가장 좋다. 다만 compiler 가 모든 것을 알 수는 없으므로 그런 경우를 위해 열려 있는 문이다.

나중에 돌아와서 refactoring 하고 싶은 곳의 예이기도 하다. 변수를 actor 안으로 옮기면 compiler 가 안전하게 쓰이는지 검증할 수 있다. 당장은 `nonisolated(unsafe)` 로 표시해 두고 다음 warning 으로 넘어가는 식으로 쓸 수 있다. 다만 logger 는 그런 경우가 아니므로 Ben 은 `let` 선언으로 되돌린다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-logger-let.png)
출처: WWDC24 - Migrate your app to Swift 6

### global variable 의 초기화 시점

global 을 초기화하는 initializer 는 언제 실행될까. thread safety 를 이해하려면 알아야 하는 것 아닐까.

Swift 의 global variable 은 lazy 하게 초기화된다. 값은 처음 쓰일 때, 여기서는 Coffee Tracker 가 처음 log 를 남길 때 만들어진다. C 나 Objective-C 와 크게 다른 점이다. 그 언어들에서는 global variable 이 startup 때 초기화되고, 이것이 launch 시간에 아주 나쁠 수 있다. Swift 의 lazy 초기화는 그 문제를 피해서 앱이 쓸 수 있는 상태에 더 빨리 도달하게 한다.

그런데 lazy 초기화는 그 자체로 race 를 만들 수 있다. 두 thread 가 동시에 이 global 로 처음 log 를 남기려 하면 logger 가 두 개 만들어질까. 그렇지 않다. Swift 에서 global variable 은 atomic 하게 만들어진다고 보장된다. 두 thread 가 동시에 처음 접근하면 하나만 초기화를 하고, 다른 하나는 기다리며 block 된다.

## main actor 에 묶인 global instance 와 함수

다음 warning 들은 `WKApplication` 의 shared instance 에 접근하는 code 에 있다.

```swift
import WatchKit
import os

let scheduleLogger = Logger(
    subsystem:
        "com.example.apple-samplecode.Coffee-Tracker.watchkitapp.watchkitextension.scheduleLogger",
    category: "Scheduler")

func scheduleBackgroundRefreshTasks() {

    scheduleLogger.debug("Scheduling a background task.")

    // Get the shared extension object.
    let watchExtension = WKApplication.shared()

    // If there is a complication on the watch face, the app should get at least four
    // updates an hour. So calculate a target date 15 minutes in the future.
    let targetDate = Date().addingTimeInterval(15.0 * 60.0)

    // Schedule the background refresh task.
    watchExtension.scheduleBackgroundRefresh(withPreferredDate: targetDate, userInfo: nil) {
        error in

        // Check for errors.
        if let error {
            scheduleLogger.error(
                "An error occurred while scheduling a background refresh task: \(error.localizedDescription)"
            )
            return
        }

        scheduleLogger.debug("Task scheduled!")
    }
}
```

`import` 두 줄과 `scheduleLogger` 선언을 더했다. Swift 5 minimal 에서는 진단이 없고, complete 에서는 warning 이 두 개 나온다.

```
warning: call to main actor-isolated class method 'shared()' in a synchronous nonisolated context [#ActorIsolatedCall]
warning: call to main actor-isolated instance method 'scheduleBackgroundRefresh(withPreferredDate:userInfo:scheduledCompletion:)' in a synchronous nonisolated context [#ActorIsolatedCall]
```

내 검사에서는 Swift 6 mode 에서도 이 둘이 error 가 아니라 warning 으로 나왔다. 세션은 이 warning 을 Swift 6 mode 를 켜기 전에 고치므로 그때의 Swift 6 mode 결과는 화면에 없다.

#### WKApplication

[WKApplication](https://developer.apple.com/documentation/watchkit/wkapplication){:target="_blank"} 은 watchOS 앱의 중심 object 이고, `shared()` 로 그 하나뿐인 instance 를 얻는다.

#### scheduleBackgroundRefresh

[scheduleBackgroundRefresh(withPreferredDate:userInfo:scheduledCompletion:)](https://developer.apple.com/documentation/watchkit/wkapplication/schedulebackgroundrefresh%28withpreferreddate:userinfo:scheduledcompletion:%29){:target="_blank"} 는 지정한 시각 무렵에 앱을 background 에서 깨워 달라고 system 에 예약하는 method 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-wkapp-warning.png)
출처: WWDC24 - Migrate your app to Swift 6

`shared()` 는 main actor 에 isolate 된 method 다. 진단에 붙은 첫 번째 note 는 actor 에 isolate 된 state 로의 호출은 암묵적으로 asynchronous 하다는 점을 짚는다. 이 함수가 async 함수였다면 `await` 를 써서 main actor 의 이 instance 에 접근할 수 있다는 뜻이다. 이 함수는 asynchronous 가 아니므로 `async` 로 표시하거나 새 task 를 시작해야 한다.

compiler 는 다른 수정도 제안한다. 함수 자체를 main actor 에 올리는 것이다. 이 함수는 view 의 method 가 아니라 free function 이라서 기본으로 main actor 에 있지 않다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-wkapp-fixit.png)
출처: WWDC24 - Migrate your app to Swift 6

fix-it 을 적용하면 함수가 main actor 에 isolate 되고 build 가 성공한다.

```swift
@MainActor func scheduleBackgroundRefreshTasks() {
    // 내용은 위와 같다
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-wkapp-mainactor.png)
출처: WWDC24 - Migrate your app to Swift 6

내 검사에서도 `@MainActor` 를 붙이면 세 설정 모두 진단이 없다. 이때 `WKApplicationDelegate` 를 구현한 class 에서 이 함수를 부르는 code 를 더해 호출하는 쪽도 함께 확인했다.

이것이 통한 이유는 호출하는 쪽을 보면 알 수 있다. 이 함수는 두 군데에서 불리고, 둘 다 main actor 에 있는 method 다. main actor 가 아닌 곳에서 불리고 있었다면 compiler 가 error 로 알려 줬을 것이고, 그 호출자를 찾아가 어떤 context 에서 부르는지 볼 수 있었을 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-callers.png)
출처: WWDC24 - Migrate your app to Swift 6

호출자 하나는 SwiftUI view 이고, 다른 하나는 `WKApplicationDelegate` 의 구현이다. `WKApplicationDelegate` 를 option-click 하면 main actor 에 묶인 protocol 인 것이 보인다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-delegate-quickhelp.png)
출처: WWDC24 - Migrate your app to Swift 6

#### WKApplicationDelegate

[WKApplicationDelegate](https://developer.apple.com/documentation/watchkit/wkapplicationdelegate){:target="_blank"} 는 watchOS 앱의 launch 와 lifecycle event, background task 를 받는 delegate protocol 이다.

이 annotation 은 그 method 들이 main actor 에서만 불린다는 보장이다. WatchKit framework 가 부를 때 그렇고, Swift 6 mode 를 켜면 내 code 가 부를 때도 그렇다.

main actor 에서만 동작하도록 설계된 많은 delegate 와 protocol 이 이렇게 annotate 되어 있고, Xcode 16 과 함께 온 SDK 에서 특히 그렇다. 가장 중요한 것은 SwiftUI 의 [View](https://developer.apple.com/documentation/swiftui/view){:target="_blank"} protocol 이다. 예전에 strict concurrency checking 을 켜 본 적이 있다면 새 SDK 에서 필요한 것보다 더 많은 main actor annotation 을 붙였을 가능성이 높고, 그중 일부는 지울 수 있을 것이다.

## delegate callback 과 concurrency

delegate 나 completion handler 로 callback 을 받을 때는 그 callback 의 concurrency 보장이 무엇인지부터 알아야 한다.

어떤 callback 은 보장을 한다. 문서에 모든 callback 이 항상 main thread 에서 온다고 적혀 있는 식이다. 많은 UI framework 가 이 보장을 하고, watch extension 의 view 층에서 무언가를 main actor 로 표시할 때 warning 이 그리 많이 나오지 않는 이유 중 하나다.

반대로 어떤 delegate 는 어떻게 불릴지에 대해 아무 보장도 하지 않고, 임의의 thread 나 queue 에서 부른다고 말한다. 앱의 back end 쪽으로 들어오는 callback 이라면 이것이 자연스럽다. Coffee Tracker 가 HealthKit 에서 받는 callback 이 이쪽에 가깝다. 이런 경우에는 받는 쪽이 맞는 queue 나 actor 로 다시 dispatch 하거나, thread-safe 한 방식으로 일을 해야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-healthkit-doc.png)
출처: WWDC24 - Migrate your app to Swift 6

delegate 마다 규칙이 다르고 그 규칙이 문서에만 적혀 있는 방식의 문제는, 올바르게 하는 부담을 쓰는 사람에게 많이 지운다는 것이다. callback 이 불릴 때 내가 어디에 있을지, 다음 logic 을 하려면 어디에 있어야 하는지를 생각해야 한다. 확인하는 것을 잊거나 다시 dispatch 하는 것을 잊으면 쉽게 data race 가 난다.

더 나쁜 경우도 있다. 이미 자리 잡고 잘 돌아가는 callback 이 있고, 우연히 항상 main queue 에서 불렸지만 그것이 보장된 것은 아니었다고 하자. 나중에 그 framework 에 변경이 생겨 다른 queue 에서 들어오기 시작한다. 그런데 UI 층은 main queue 에서 온다는 것에 기대고 있었다.

---

### local reasoning 이란?

여기서 빠져 있는 것이 local reasoning 이다. UI 층에서 일하고 있을 때, 앱의 다른 곳에서 일어나는 변경, 예를 들어 작업하는 queue 를 바꾸는 일 때문에 내 code 가 쉽게 깨지지 않는다는 보장이다. 지금 보고 있는 code 만으로 옳은지 판단할 수 있다는 뜻이다.

Swift Concurrency 는 이 보장, 혹은 보장이 없다는 사실을 명시적으로 만들어서 문제를 다룬다.

- callback 이 어떻게 불리는지 명시하지 않으면 nonisolated 로 간주되고, 특정 isolation 이 필요한 data 에 접근할 수 없다.
- callback 이 isolation 을 보장한다면, 예를 들어 항상 main actor 에서 불린다면, delegate protocol 이나 callback 에 그렇게 annotate 할 수 있고 받는 쪽은 그 보장에 기댈 수 있다.

## 직접 관리하지 않는 code 와의 경계

이제 첫 번째 warning 으로 돌아간다. main actor 에 있는 delegate type 이 nonisolated protocol 을 conform 할 수 없다는 것이었다. compiler 가 제안하는 선택지가 몇 가지 있다.

---

### nonisolated method

첫 번째는 method 를 `nonisolated` 로 선언하는 것이다. main actor 에 isolate 된 type 의 method 지만 이 method 만은 main actor 에 isolate 되지 않는다는 뜻이다. 어디서 부를지 일부러 약속하지 않는 callback 이라면 이 길이 맞다.

```swift
extension Recaffeinater: CaffeineThresholdDelegate {
    nonisolated public func caffeineLevel(at level: Double) {
        if level < minimumCaffeine {
            // TODO: alert user to drink more coffee!
        }
    }
}
```

물론 이 type 은 view 를 위한 것이라 곧바로 main actor 로 돌아가서 일을 하고 싶을 것이다. 그렇게 하지 않으면 main actor 가 보호하는 property 에 접근하고 있으므로 새 error 가 난다. 세 설정 모두에서 다음과 같다.

```
error: main actor-isolated property 'minimumCaffeine' can not be referenced from a nonisolated context
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-nonisolated-error.png)
출처: WWDC24 - Migrate your app to Swift 6

### main actor 의 task

이 error 는 main actor 에서 task 를 시작하면 고칠 수 있다.

```swift
extension Recaffeinater: CaffeineThresholdDelegate {
    nonisolated public func caffeineLevel(at level: Double) {
        Task { @MainActor in
            if level < minimumCaffeine {
                // TODO: alert user to drink more coffee!
            }
        }
    }
}
```

세 설정 모두 진단 없이 compile 된다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-task-mainactor.png)
출처: WWDC24 - Migrate your app to Swift 6

화면은 편집하는 도중이라 앞의 error 표시가 아직 남아 있다.

---

### protocol 의 annotation

그런데 이 경우에 Ben 은 이 callback 이 main actor 에서 오게 되어 있다는 것을 안다. CoffeeKit 안의 model type 에서 오고, 그 type 자체가 main actor 에서 돌고 있다.

code base 전체를 직접 관리한다면 지금 바로 고치는 것이 한 방법이다. definition 으로 가면 CoffeeKit 안의 protocol 이 보이고, 여기에 `@MainActor` 를 붙이면 main actor 에서 불린다는 것을 보장할 수 있다.

하지만 code base 전체를 관리하지 못할 때도 있다. CoffeeKit 을 다른 team 이 맡고 있거나, 남이 관리하는 package 나 framework 일 수 있다. 여기서는 그런 경우라고 가정하고 delegate 구현으로 돌아간다.

### assumeIsolated 의 실행 시점 검사

code 를 확인했든 문서에서 읽었든, 호출이 특정 actor 에서 온다는 것을 확실히 알 때 그 사실을 compiler 에게 알려 주는 method 가 있다.

```swift
extension Recaffeinater: CaffeineThresholdDelegate {
    nonisolated public func caffeineLevel(at level: Double) {
        MainActor.assumeIsolated {
            if level < minimumCaffeine {
                // TODO: alert user to drink more coffee!
            }
        }
    }
}
```

세 설정 모두 진단 없이 compile 된다.

#### MainActor.assumeIsolated

[assumeIsolated(_:file:line:)](https://developer.apple.com/documentation/swift/mainactor/assumeisolated%28_:file:line:%29){:target="_blank"} 는 지금 실행 중인 code 가 이미 main actor 위에 있다고 가정하고 closure 를 동기로 실행하며, 가정이 틀리면 program 을 멈추는 method 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-assume-isolated.png)
출처: WWDC24 - Migrate your app to Swift 6

`Task` 와 달리 main actor 로 넘어가는 새 task 를 시작하지 않는다. 이 code 가 이미 main actor 에서 돌고 있다고 Swift 에게 말할 뿐이다.

어딘가의 code 가 이 함수를 main actor 가 아닌 곳에서 부르는 것은 여전히 가능하다. main thread 에서 불린다고 가정하는 오늘날의 Swift 함수들과 같은 사정이다. 이것을 막는 좋은 방법은 함수 안에 정말 main actor 에 있는지 확인하는 assertion 을 넣는 것이고, `assumeIsolated` 가 그 일을 한다. main actor 가 아닌 곳에서 불리면 trap 이 나고 program 이 멈춘다. trap 은 바라는 일이 아니지만 사용자 data 를 망가뜨릴 수 있는 race condition 보다는 낫다.

---

### preconcurrency conformance

main actor 에서 불린다고 가정하는 delegate protocol 을 conform 하는 이 pattern 은 흔해서 줄여 쓰는 방법이 있다. 앞의 수정을 되돌리고, conformance 에 `@preconcurrency` 를 쓴다.

```swift
extension Recaffeinater: @preconcurrency CaffeineThresholdDelegate {
    public func caffeineLevel(at level: Double) {
        if level < minimumCaffeine {
            // TODO: alert user to drink more coffee!
        }
    }
}
```

세 설정 모두 진단 없이 compile 된다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-preconcurrency.png)
출처: WWDC24 - Migrate your app to Swift 6

손으로 쓴 것과 같은 일을 한다. 이 type 이 isolate 된 actor 에서 불린다고 가정하고, 그렇지 않으면 trap 이 난다. 이 기능의 설계는 [SE-0423](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0423-dynamic-actor-isolation.md){:target="_blank"} 에 있다.

    subsystem:

## actor 사이로 보내는 배열

마지막으로 남은 진단들은 drink 의 배열을 서로 다른 actor 사이로 넘기는 데서 나온다. 첫 번째는 `self.currentDrinks` 를 `save` method 로 보내면 data race 가 날 수 있다는 것이다.

```swift
// Begin saving the drink data to disk.
private func drinksUpdated() async {
    logger.debug("A value has been assigned to the current drinks property.")

    // Begin saving the data.
    await store.save(currentDrinks)
}
```

이 method 가 들어 있는 `CoffeeData` 와 `save` 를 가진 `CoffeeDataStore`, 그리고 `Drink` 를 최소한으로 채워서 검사했다. Swift 5 minimal 에서는 진단이 없고, complete 에서는 아래 warning, Swift 6 mode 에서는 같은 내용의 error 다.

```
warning: sending 'self.currentDrinks' risks causing data races; this is an error in the Swift 6 language mode [#RegionIsolation::SendingRisksDataRace]
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-sending-warning.png)
출처: WWDC24 - Migrate your app to Swift 6

`save` 는 다른 actor 의 method 다. `CoffeeData` 는 main actor 에 있다. SwiftUI 의 `ObservableObject` 이므로 그래야 한다. 반면 `save` 는 background 에서 disk 저장과 불러오기를 하는 `CoffeeDataStore` actor 에 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-datastore.png)
출처: WWDC24 - Migrate your app to Swift 6

warning 으로 돌아가 보면, main actor 에 isolate 된 model 이 들고 있는 바로 그 drink 배열을 `save` 로 보내고 있다. `Drink` 가 reference type 이었다면 main actor 와 저장 actor 가 shared mutable state 에 동시에 접근할 수 있는 data race 의 조건을 만드는 셈이다.

### public type 과 Sendable

`Drink` 의 정의를 보면 struct 이고, immutable property 몇 개를 가지며 그것들이 모두 value type 이다.

```swift
// The record of a single drink.
public struct Drink: Hashable, Codable {

    // The amount of caffeine in the drink.
    public let mgCaffeine: Double

    // The date when the drink was consumed.
    public let date: Date

    // A globally unique identifier for the drink.
    public let uuid: UUID

    public let type: DrinkType?

    public var latitude, longitude: Double?

    // The drink initializer.
    public init(type: DrinkType, onDate date: Date, uuid: UUID = UUID()) {
        self.mgCaffeine = type.mgCaffeinePerServing
        self.date = date
        self.uuid = uuid
        self.type = type
    }

    // Calculate the amount of caffeine remaining at the provided time,
    // based on a 5-hour half life.
    public func caffeineRemaining(at targetDate: Date) -> Double {
        // Calculate the number of half-life time periods (5-hour increments)
        let intervals = targetDate.timeIntervalSince(date) / (60.0 * 60.0 * 5.0)
        return mgCaffeine * pow(0.5, intervals)
    }
}
```

세션 page 의 snippet 에는 `HKQuantitySample` 에서 만드는 `init(from:)` 도 있다. 내 검사용 file 에서는 HealthKit 에 기대는 그 initializer 만 빼고 넣었다.

이런 type 은 분명히 `Sendable` 이 될 수 있고, 그러면 drink 를 한 actor 에 저장해 두고 같은 배열을 다른 actor 로 보내도 아무 문제가 없다.

이것이 internal type 이었다면 Swift 가 자동으로 `Sendable` 로 여겼을 것이다. 하지만 이것은 public type 이다. CoffeeKit 밖의 Coffee Tracker extension 과 함께 쓴다. Swift 는 public type 의 sendability 를 자동으로 추론하지 않는다. type 을 `Sendable` 로 표시하는 것은 그 type 을 쓰는 쪽에 대한 보장이기 때문이다. 오늘은 mutable state 가 없지만 나중에 바꾸고 싶을 수도 있고, 그렇다면 sendability 를 미리 잠가 두고 싶지 않다. 그래서 Swift 는 public type 에는 [Sendable](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} conformance 를 명시적으로 적게 한다.

여기서는 그렇게 해도 좋다. 그리고 이것은 한 줄의 변경이 여러 warning 을 한꺼번에 없애는 예다. `Drink` 가 `Sendable` 이어야 했던 곳이 세 군데였다. 큰 project 라면 셋이 아니라 여러 project 에 걸친 수십 개일 수 있다.

```swift
public struct Drink: Hashable, Codable, Sendable {
    // 내용은 위와 같다
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-drink-sendable.png)
출처: WWDC24 - Migrate your app to Swift 6

다시 compile 하면 `Sendable` 이 아닌 type 이 하나 더 드러난다. `type` property 의 `DrinkType` 이다. 내 검사에서는 Swift 5 mode 의 minimal 과 complete 모두 아래 warning 이고, Swift 6 mode 에서는 error 다.

```
warning: stored property 'type' of 'Sendable'-conforming struct 'Drink' contains non-Sendable type 'DrinkType'; this is an error in the Swift 6 language mode
```

### Sendable 로 만들 수 없는 type

`DrinkType` 은 그냥 enum 이라서 `Sendable` 로 표시하면 된다. 그런데 그렇지 않았다면 어떨까. Objective-C type 이고, mutable state 를 reference type 에 담고 있어서 결코 `Sendable` 이 될 수 없는 것이었다면.

그때는 안전에 대해 몇 가지 선택을 해야 한다. 한 가지는 그 type 에 대해 따져 보고, mutable reference type 이기는 하지만 예를 들어 `NSCopying` 으로 만든 새 사본이라 안전하다고 판단하는 것이다. `Sendable` 은 아니지만 변수를 private 으로 만드는 식으로 그 class 를 보호할 수 있다고 보고, `Sendable` type 안에 그대로 저장하기로 할 수도 있다. 그럴 때 다시 `nonisolated(unsafe)` keyword 를 쓴다.

```swift
public struct Drink: Hashable, Codable, Sendable {
    // 다른 property 는 위와 같다

    nonisolated(unsafe)
    public let type: DrinkType?
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-unsafe-type.png)
출처: WWDC24 - Migrate your app to Swift 6

이렇게 하면 `Drink` 가 `Sendable` annotation 을 단 채로 compile 된다. 내 검사에서도 세 설정 모두 진단이 없다.

여기서는 그럴 필요가 없으므로 Ben 은 이것을 되돌리고 `DrinkType` 으로 가서 `Sendable` 을 붙인다.

```swift
// Define the types of drinks supported by Coffee Tracker.
public enum DrinkType: Int, CaseIterable, Identifiable, Codable, Sendable {
    // case 들
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-drinktype.png)
출처: WWDC24 - Migrate your app to Swift 6

`Drink` 와 `DrinkType` 이 둘 다 `Sendable` 이 되면 `store.save(currentDrinks)` 를 포함해 세 설정 모두 진단이 없다.

## Swift 6 mode 에서의 새 기능

보호를 받게 됐으니 Coffee Tracker 에 새 기능을 넣어 본다. 사용자들이 커피를 마신 위치를 기록해서 자기 caffeine 습관을 들여다보고 싶어 한다. 그래서 앱에 CoreLocation 을 넣는다.

### AsyncSequence 방식

CoffeeKit 의 `addDrink` method 에서 drink 를 추가하기 직전에 CoreLocation 으로 현재 위치를 가져온다. CoreLocation 에는 현재 위치를 흘려보내는 async sequence 가 있고 Swift Concurrency 와 아주 잘 맞는다. 충분한 정확도가 나올 때까지 위치 결과를 loop 로 돌다가 그 위치를 caffeine sample 에 넣으면 된다.

```swift
func addDrink() async {
    var drink = Drink()

    do {
        // Request authorization to access the user's location.
        for try await update in CLLocationUpdate.liveUpdates() {
            guard let coord = update.location else {
                logger.info("Update received but no location, \(update.location)")
                break
            }

            drink.latitude = coord.coordinate.latitude
            drink.longitude = coord.coordinate.longitude
        }
    } catch {
    }
}
```

세션 page 의 snippet 은 method 의 중간 조각이고 `do` 가 닫히지 않은 채로 끝난다. 그래서 함수와 `drink`, `catch` 를 채워서 문법이 맞게 만들었다. deployment target 이 watchOS 11 이면 세 설정 모두 진단 없이 compile 된다.

#### CLLocationUpdate.liveUpdates

[liveUpdates(_:)](https://developer.apple.com/documentation/corelocation/cllocationupdate/liveupdates%28_:%29){:target="_blank"} 는 위치 update 를 `AsyncSequence` 로 돌려주는 [CLLocationUpdate](https://developer.apple.com/documentation/corelocation/cllocationupdate){:target="_blank"} 의 type method 다.

Ben 은 이 code 에 timeout 을 더하고 싶을 것이고, 그것은 structured concurrency 와 cancellation 으로 할 수 있다고 덧붙인다.

이 접근에는 문제가 하나 있다. Coffee Tracker 의 최소 deployment target 을 올려야 한다. 아직 그럴 준비가 안 됐다. watchOS 10 으로 올리고 싶지 않지만 커피 마신 곳은 기록하고 싶은 사용자가 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-liveupdates-error.png)
출처: WWDC24 - Migrate your app to Swift 6

deployment target 을 watchOS 9 로 두고 검사하면 세 설정 모두에서 다음 error 가 난다.

```
error: 'CLLocationUpdate' is only available in watchOS 10.0 or newer
```

그래서 delegate callback 에 기반한 예전 CoreLocation API 를 써야 한다. 이쪽은 Swift Concurrency 보다 먼저 나온 것이라 쓰기가 조금 더 까다롭다.

Ben 은 넘어가기 전에 두 방식을 비교한다. async sequence 방식의 좋은 점은 평범한 synchronous code 처럼 보인다는 것이다. 위치를 요청하고, 들어오는 위치 update 를 충분히 정확한 것이 올 때까지 loop 로 돌고, 이 모든 것이 새 drink 를 배열에 더하는 함수 하나 안에 있다. delegate API 는 state 를 어딘가에 보관해 두고, delegate method 가 불리기를 기다리고, 거기서 위치와 함께 drink 값을 저장하는 일을 이어 가야 한다. 그래서 deployment target 을 올려서 새 API 를 쓰는 것은 해 볼 만한 일이다.

### delegate 방식

하지만 올리지 않기로 했다고 하자. 방금 넣은 code 를 지우고 file 맨 아래에 CoreLocation delegate object 를 만든다.

```swift
import CoreLocation

class CoffeeLocationDelegate: NSObject, CLLocationManagerDelegate {
  var location: CLLocation?
  var manager: CLLocationManager!

  var latitude: CLLocationDegrees? { location?.coordinate.latitude }
  var longitude: CLLocationDegrees? { location?.coordinate.longitude }

  override init () {
    super.init()
    manager = CLLocationManager()
    manager.delegate = self
    manager.startUpdatingLocation()
  }

  func locationManager (
    _ manager: CLLocationManager,
    didUpdateLocations locations: [CLLocation]
  ) {
      self.location = locations.last
  }
}
```

`import CoreLocation` 을 더했다. 세 설정 모두 진단 없이 compile 된다.

#### CLLocationManager

[CLLocationManager](https://developer.apple.com/documentation/corelocation/cllocationmanager){:target="_blank"} 는 위치 관련 event 의 전달을 시작하고 멈추는 object 다.

#### CLLocationManagerDelegate

[CLLocationManagerDelegate](https://developer.apple.com/documentation/corelocation/cllocationmanagerdelegate){:target="_blank"} 는 location manager 가 보내는 event 를 받는 protocol 이고, [locationManager(_:didUpdateLocations:)](https://developer.apple.com/documentation/corelocation/cllocationmanagerdelegate/locationmanager%28_:didupdatelocations:%29){:target="_blank"} 로 새 위치를 받는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-location-delegate.png)
출처: WWDC24 - Migrate your app to Swift 6

CoreLocation 에서 위치 update 를 받는 delegate class 의 기본 구현이다. CoreLocation 의 이 부분은 Swift Concurrency 보다 먼저 나왔으므로 규칙을 지키려면 일을 더 해야 한다.

이 delegate 는 이 세션에서 본 다른 callback 들과 조금 다르다. 어느 thread 에서 불릴지에 대한 정적인 보장이 없다. 지금까지는 항상 main thread 에서 불리는 delegate 와 임의의 thread 에서 불리는 delegate 를 이야기했다. `CLLocationManager` 의 문서가 하는 보장은 delegate 가 불리는 thread 가 `CLLocationManager` 를 만든 thread 로 정해진다는 것이다. 이것은 실행 시점에 정해지는 동적인 성질이라 Swift 가 도움 없이 자동으로 강제할 수 없다.

이 앱에서는 이 정보를 main actor 에 있는 model type 에서 쓴다. 그러니 가장 단순한 길은 이 delegate 도 main thread 에 있게 하는 것이다. Swift 가 그것을 강제하도록 돕는 방법은 간단하다. type 전체를 main actor 에 올린다.

```swift
@MainActor
class CoffeeLocationDelegate: NSObject, CLLocationManagerDelegate {
    // 내용은 위와 같다
}
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-location-mainactor.png)
출처: WWDC24 - Migrate your app to Swift 6

그러면 location manager 는 initializer 에서 main thread 에 만들어지고, delegate 호출도 main actor 로 들어온다.

물론 이렇게 하면 익숙한 error 가 나온다. 이 delegate callback 이 main actor 에 isolate 되어 있지 않다는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-location-error.png)
출처: WWDC24 - Migrate your app to Swift 6

지금의 compiler 는 `Recaffeinater` 때와 같은 문구로 말한다. Swift 5 mode 에서는 minimal 과 complete 모두 아래 warning 이고, Swift 6 mode 에서는 error 다.

```
warning: conformance of 'CoffeeLocationDelegate' to protocol 'CLLocationManagerDelegate' crosses into main actor-isolated code and can cause data races; this is an error in the Swift 6 language mode [#ConformanceIsolation]
```

다루는 pattern 은 이미 봤다. delegate method 를 `nonisolated` 로 표시하고, main actor 에서 돌아야 하는 code 를 `MainActor.assumeIsolated` 호출로 감싼다.

```swift
@MainActor
class CoffeeLocationDelegate: NSObject, CLLocationManagerDelegate {
  var location: CLLocation?
  var manager: CLLocationManager!

  var latitude: CLLocationDegrees? { location?.coordinate.latitude }
  var longitude: CLLocationDegrees? { location?.coordinate.longitude }

  override init () {
    super.init()
    manager = CLLocationManager()
    manager.delegate = self
    manager.startUpdatingLocation()
  }

  nonisolated func locationManager (
    _ manager: CLLocationManager,
    didUpdateLocations locations: [CLLocation]
  ) {
    MainActor.assumeIsolated { self.location = locations.last }
  }
}
```

세션 page 의 snippet 에는 `locations. last` 처럼 점 뒤에 공백이 들어가 있어서 붙여 썼다. 세 설정 모두 진단 없이 compile 된다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2024-06-10-WWDC24-10169/wwdc24-10169-location-fixed.png)
출처: WWDC24 - Migrate your app to Swift 6

build 가 성공한다. Swift 6 로 build 되는 상태를 유지한 채 앱에 현재 위치를 가져오는 기능이 들어갔다.

## 세션의 마무리

이 세션은 앱을 Swift 6 language mode 로 옮기는 기법 몇 가지를 빠르게 둘러본 것이고, 다루지 않은 상황이 많다. Ben 은 이어서 볼 자료를 알려 준다.

먼저 이전 세션이다. Swift 의 concurrency 기능으로 기존 앱을 현대화하는 내용이고, 이 code 를 Swift 6 로 옮기는 길의 많은 부분이 그때 한 refactoring 덕분에 쉬워졌다.

Swift 6 language mode 는 이전 migration 들에서 얻은 교훈을 바탕으로 Swift ecosystem 전체에 걸친 점진적 migration 을 위해 설계됐다. 그래서 data race 는 code 변경 하나씩으로 없애 갈 수 있다. 정적인 data-race safety 와 동적인 data-race safety 사이를 잇는 기법은 이 세션이 겉만 다뤘고, 이 전략들과 그 밖의 것을 모은 guide 가 [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/){:target="_blank"} 에 있다.

## 정리

세션에서 만난 진단과 그 해결을 한 표로 모으면 다음과 같다.

| 상황 | 진단 | 해결 |
| --- | --- | --- |
| global `var` | nonisolated global shared mutable state | `let` 으로 바꾼다. 바꿔야 하는 값이면 global actor 에 묶고, 외부 장치가 지키고 있을 때만 `nonisolated(unsafe)` |
| free function 에서 main actor API 호출 | synchronous nonisolated context 에서의 호출 | 함수에 `@MainActor` |
| `@MainActor` type 이 isolation 없는 protocol 을 conform | conformance 가 main actor code 로 넘어감 | 내 protocol 이면 protocol 에 `@MainActor`. 남의 것이면 `@preconcurrency` conformance 나 `nonisolated` 와 `MainActor.assumeIsolated` |
| actor 사이로 public type 의 값을 보냄 | sending 이 data race 를 일으킬 수 있음 | type 에 `Sendable` 을 명시 |
| `Sendable` type 안의 non-Sendable property | stored property 가 non-Sendable | property 의 type 을 `Sendable` 로. 불가능하고 안전을 직접 따졌을 때만 `nonisolated(unsafe)` |
| 만든 thread 로 callback 이 오는 delegate | 정적인 보장이 없음 | type 을 `@MainActor` 로 두고 callback 은 `nonisolated` 와 `MainActor.assumeIsolated` |

실제 프로젝트에 가져갈 점은 다음과 같다.

- 순서는 target 하나씩이다. Swift 5 mode 에서 complete checking 을 켜고, warning 을 없애고, Swift 6 mode 로 잠근 뒤 다음 target 으로 간다.
- UI 층 target 부터 시작한다. 갱신되지 않은 module 을 쓰는 쪽에 `@preconcurrency` 같은 임시 장치를 넣어 두면, 그 module 을 갱신했을 때 compiler 가 지우라고 알려 준다.
- 큰 refactoring 과 data-race safety 를 켜는 일은 섞지 않는다.
- warning 이 많이 나와도 쉬운 것부터 몰아서 처리하고, 여러 warning 의 뿌리가 되는 한 줄을 찾는다.
- 도중에 급한 일이 생기면 checking 을 다시 꺼도 된다. 그동안 한 수정은 그대로 유효하다.
- public type 은 `Sendable` 이 자동으로 추론되지 않는다. 쓰는 쪽에 대한 약속이므로 직접 적는다.
- `MainActor.assumeIsolated` 와 `@preconcurrency` conformance 는 가정이 틀리면 trap 이 난다. compiler 의 검사를 실행 시점 검사로 바꾸는 것이지 검사를 없애는 것이 아니다.
- `nonisolated(unsafe)` 는 검사를 아예 끈다. 쓴 곳은 Swift 6 mode 를 켠 뒤에 다시 돌아볼 목록으로 남긴다.
