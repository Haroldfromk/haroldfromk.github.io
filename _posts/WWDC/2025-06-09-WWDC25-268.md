## 한 줄 요약

앱은 모든 code 가 main thread 에서 도는 single-threaded 상태로 시작하고, concurrency 는 필요가 확인된 만큼만 들인다. 순서는 정해져 있다. 기다리는 시간이 길면 `async`/`await` 로 감추고, main thread 의 계산이 길면 `@concurrent` 로 background 에 넘기고, main actor 에 쌓인 data 때문에 task 들이 main thread 로 몰리면 그 data 를 actor 로 떼어 낸다. Swift 6.2 의 main actor 기본 isolation 과 Approachable Concurrency 설정이 이 순서를 그대로 따라가기 쉽게 만들어 준다.

## 필요한 만큼의 concurrency

concurrency 는 code 가 여러 일을 동시에 하게 해 준다. 앱에서는 두 가지 용도가 있다. 하나는 disk 에서 file 을 읽거나 network 요청을 보낼 때처럼 data 를 기다리는 동안 앱이 반응하도록 하는 것이고, 다른 하나는 큰 image 를 처리하는 것처럼 비싼 계산을 background 로 넘기는 것이다.

Swift 의 concurrency model 은 concurrent code 를 올바르게 쓰기 쉽도록 설계되어 있다. concurrency 가 들어오는 지점을 code 에 드러나게 하고, concurrent task 들 사이에 어떤 data 가 공유되는지를 밝혀낸다. compiler 는 이 정보를 써서 data race 가능성을 compile 시점에 잡아낸다. 그래서 고치기 어려운 data race 를 만들 걱정 없이 필요할 때 concurrency 를 들일 수 있다.

그렇다고 concurrency 를 많이 쓰라는 뜻은 아니다. 많은 앱은 concurrency 를 조금만 쓰면 되고, 전혀 필요 없는 앱도 있다. concurrent code 는 single-threaded code 보다 복잡하므로 필요할 때만 들인다. 세션이 slide 한 장에 크게 적은 문장도 이것이다. 필요한 concurrency 만 들인다.

앱이 거치는 길은 다음과 같다.

- 처음에는 모든 code 를 main thread 에서 돌린다. main thread 는 UI event 를 받고 그에 맞춰 UI 를 갱신하는 곳이다. 계산이 많지 않다면 전부 main thread 에 두어도 괜찮고, 이 상태로 꽤 멀리 갈 수 있다.
- 언젠가는 network 에서 content 를 받는 것 같은 asynchronous code 가 필요해진다. content 가 오기를 기다리는 동안 UI 가 멈추지 않게 할 수 있다.
- 그 작업이 너무 오래 걸리면 main thread 와 동시에 도는 background thread 로 옮긴다.
- 앱이 더 커져서 모든 data 를 main thread 에 두는 것이 성능을 떨어뜨리면, 항상 background 에서 도는 전용 data type 을 들인다.

Swift concurrency 는 이런 concurrent 작업을 표현하는 도구로 actor 와 task 를 준다. 큰 앱의 구조는 대체로 아래 그림처럼 된다. main actor 가 가운데 있고, 한 번의 작업을 맡는 task 와 network caching 이나 database 접근 같은 subsystem 을 맡는 actor 가 둘레에 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-arch.png)
출처: WWDC25 - Embracing Swift concurrency

다만 여기서 시작하는 것이 아니고, 모든 앱이 여기까지 갈 필요도 없다. 세션은 single-threaded 에서 concurrent 까지 한 걸음씩 가면서 걸음마다 언제 그 걸음을 내딛는지, 어떤 언어 기능을 쓰는지, 어떻게 써야 효과적인지, 왜 그렇게 동작하는지를 설명한다.

## single-threaded code

program 을 실행하면 code 는 main thread 에서 돌기 시작한다. 내가 추가하는 code 도 다른 곳에서 돌리겠다고 concurrency 를 명시적으로 들이기 전까지는 main thread 에 머문다. single-threaded code 는 한 번에 한 가지 일만 하므로 쓰기도 유지하기도 쉽다. 그리고 나중에 concurrency 를 들이더라도 Swift 가 main thread 의 code 를 보호해 준다.

세션의 첫 예는 global variable 하나와 함수 둘이 전부인 program 이다.

```swift
var greeting = "Hello, World!"

func readArguments() { }

func greet() {
  print(greeting)
}

readArguments()
greet()
```

세션 snippet 은 top-level code 로 되어 있다. 나는 다른 file 과 같은 방식으로 검사하려고 마지막 두 줄을 `@main` type 의 `static func main()` 안으로 옮겼다. 선언 부분은 그대로다.

---

### main actor 란?

main thread 와 그 위의 모든 data 를 대표하는 것이 [MainActor](https://developer.apple.com/documentation/swift/mainactor){:target="_blank"} 다. main actor 를 실행할 수 있는 thread 는 main thread 하나뿐이므로 main actor 안에는 concurrency 가 없다. data 나 code 가 main actor 에 있다는 것은 `@MainActor` 로 적는다.

Swift 는 main actor 의 code 가 main thread 에서만 실행되고 main actor 의 data 가 main thread 에서만 접근되도록 보장한다. 이런 code 를 두고 main actor 에 isolated 되어 있다고 말한다.

---

### 기본값이 된 main actor

Swift 6.2 부터는 module 단위로 main actor isolation 을 기본값으로 둘 수 있다. compiler 가 그 module 의 모든 선언에 `@MainActor` 를 대신 적어 주는 것과 같다.

```swift
import Foundation

struct Image {
}

final class ImageModel {
  var imageCache: [URL: Image] = [:]
}

final class Library {
  static let shared: Library = Library()
}
```

slide 는 이 세 type 위에 `@MainActor` 가 흐리게 붙어 있는 모습으로 이것을 그린다. 이 mode 에서는 static variable 같은 shared state 를 code 어디에서나 자유롭게 쓸 수 있고, concurrency 를 들이기 전까지는 동시 접근을 걱정할 필요가 없다.

이 차이는 compiler 로 바로 확인된다. 위의 두 file 을 Swift 6 language mode 에서 `-default-isolation MainActor` 없이 검사하면 둘 다 error 가 난다. 첫 예의 `greeting` 에는 `var 'greeting' is not concurrency-safe because it is nonisolated global shared mutable state` 가, `Library.shared` 에는 `static property 'shared' is not concurrency-safe because non-'Sendable' type 'Library' may have shared mutable state` 가 나온다. flag 를 켜면 둘 다 진단 없이 통과한다. [Migrate your app to Swift 6](https://haroldfromk.github.io/posts/WWDC24-10169/){:target="_blank"} 에서 global variable 마다 하나씩 고쳐야 했던 바로 그 error 다.

main actor 기본값은 build setting 으로 정한다. Swift Compiler - Concurrency 묶음의 Default Actor Isolation 을 MainActor 로 두는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-main-actor-default.png)
출처: WWDC25 - Embracing Swift concurrency

이 설정은 주로 앱의 main module 과 UI 를 다루는 데 집중하는 module 에 쓴다. 세션에 따르면 Xcode 26 으로 새로 만든 앱 project 에는 기본으로 켜져 있다. 세션의 code 는 끝까지 이 mode 가 켜져 있다고 가정하고, 이 글의 검사도 같은 조건이다. [Xcode 의 build setting 문서](https://developer.apple.com/documentation/xcode/build-settings-reference){:target="_blank"} 에는 이 설정의 이름이 `SWIFT_DEFAULT_ACTOR_ISOLATION` 으로 올라 있고, 언어 쪽 제안은 [SE-0466](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0466-control-default-actor-isolation.md){:target="_blank"} 이다.

### 동기 방식의 image 표시

image model 에 image 를 가져와 화면에 보여 주는 method 를 넣는다. 먼저 local file 에서 읽는 형태다.

```swift
import Foundation

class Image {
}

final class View {
  func displayImage(_ image: Image) {
  }
}

final class ImageModel {
  var imageCache: [URL: Image] = [:]
  let view = View()

  func fetchAndDisplayImage(url: URL) throws {
    let data = try Data(contentsOf: url)
    let image = decodeImage(data)
    view.displayImage(image)
  }

  func decodeImage(_ data: Data) -> Image {
    Image()
  }
}
```

file 을 읽고, decode 하고, UI 에 보여 준다. 이 앱에는 concurrency 가 전혀 없다. main thread 하나가 모든 일을 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-sync-pipeline.png)
출처: WWDC25 - Embracing Swift concurrency

함수 전체가 main thread 에서 한 덩어리로 실행된다. 그 안의 작업이 모두 충분히 빠르다면 이대로 괜찮다.

## asynchronous task

지금까지는 local file 만 읽을 수 있었다. network 에서 image 를 받으려면 다른 API 를 써야 한다. `Data(contentsOf:)` 자리에 URLSession 의 호출을 넣어 보면 두 가지를 알 수 있다.

```swift
  func fetchAndDisplayImage(url: URL) throws {
    let (data, _) = try URLSession.shared.data(from: url)
    let image = decodeImage(data)
    view.displayImage(image)
  }
```

첫째, 이 code 는 compile 되지 않는다. 지금 compiler 는 `'async' call in a function that does not support concurrency` 라는 error 를 내고, 세션 화면의 진단도 같은 문구다. 둘째, 만약 이런 호출을 main thread 에서 동기로 할 수 있었다면 data 를 다 받을 때까지 UI 가 얼어붙었을 것이다. slide 는 Fetch image 칸을 빨갛게 칠해 이 상황을 그린다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-fetch-blocks.png)
출처: WWDC25 - Embracing Swift concurrency

앱이 반응하도록 유지하는 것은 개발자의 몫이다. UI 가 끊기거나 멈출 만큼 main thread 를 오래 붙잡지 않도록 신경 써야 한다. 이런 hang 을 막기 위해 network 접근은 asynchronous 로 되어 있다.

### async 와 await

`fetchAndDisplayImage` 가 asynchronous 호출을 다룰 수 있게 하려면 함수를 `async` 로 만들고 URLSession 호출 앞에 `await` 를 적는다.

```swift
  func fetchAndDisplayImage(url: URL) async throws {
    let (data, _) = try await URLSession.shared.data(from: url)
    let image = decodeImage(data)
    view.displayImage(image)
  }
```

#### URLSession.data(from:)

[data(from:delegate:)](https://developer.apple.com/documentation/foundation/urlsession/data%28from:delegate:%29){:target="_blank"} 은 URL 의 내용을 내려받아 `Data` 와 `URLResponse` 의 tuple 로 돌려주는 [URLSession](https://developer.apple.com/documentation/foundation/urlsession){:target="_blank"} 의 async method 다.

`await` 는 함수가 suspend 될 수 있는 지점을 표시한다. suspend 는 기다리는 일이 일어날 때까지 현재 thread 에서 실행을 멈추는 것이고, 그 일이 일어나면 실행을 이어 간다. 함수를 두 조각으로 나누는 것이라고 생각하면 된다. image 를 받기 시작할 때까지 도는 조각과, image 를 받은 뒤에 도는 조각이다. 이렇게 나누면 두 조각 사이에 다른 일이 끼어들 수 있고, 그래서 UI 가 계속 반응한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-await-split.png)
출처: WWDC25 - Embracing Swift concurrency

그림에서 Fetch image 는 Background 줄에 있다. 실제로 URLSession 같은 library API 는 작업을 알아서 background 로 넘겨 준다. 내 code 에는 아직 concurrency 를 들이지 않았고, 들일 필요도 없었다. 일부를 asynchronous 로 만들고 대신 일을 넘겨 주는 library API 를 부른 것만으로 앱의 반응성이 좋아졌다. 내 code 가 한 일은 async/await 를 받아들인 것뿐이다. `async` 와 `await` 의 기본은 [Meet async/await in Swift](https://haroldfromk.github.io/posts/WWDC21-10132/){:target="_blank"} 에서 정리했다.

### task 란?

async 함수는 task 안에서 실행된다. task 는 다른 code 와 독립적으로 실행되는 단위이고, 특정한 작업 하나를 처음부터 끝까지 수행하도록 만든다. button 을 누르는 것 같은 event 에 반응해 task 를 만드는 것이 흔한 모습이다.

```swift
import Foundation

final class ImageModel {
  var url: URL = URL(string: "https://swift.org")!

  func onTapEvent() {
    Task {
      do {
        try await fetchAndDisplayImage(url: url)
      } catch let error {
        displayError(error)
      }
    }
  }

  func displayError(_ error: any Error) {
  }

  func fetchAndDisplayImage(url: URL) async throws {
  }
}
```

세션 snippet 은 `URL("https://swift.org")!` 로 되어 있다. 이 줄을 그대로 검사하면 compile 은 되지만 `'init(_:)' was deprecated in macOS 13.0: replaced by 'init(filePath:)'` 라는 warning 이 나온다. 문자열 literal 이 file path 로 해석된다는 뜻이라 나는 `URL(string:)` 으로 바꿨다. 나머지는 snippet 그대로다.

#### Task

[Task](https://developer.apple.com/documentation/swift/task){:target="_blank"} 는 asynchronous 작업의 단위다. `Task { }` 로 만들면 synchronous code 에서 async 함수를 부르는 새 task 가 시작된다.

여기서 task 는 image 를 받아 보여 주는 작업 전체를 맡는다. slide 는 task 의 쓰임을 두 줄로 정리한다. task 는 asynchronous 작업 하나를 끝에서 끝까지 구현하고, synchronous event 에 반응해 asynchronous 작업을 만들 때 task 를 쓴다.

### interleaving

한 앱 안에는 asynchronous task 가 여럿 있을 수 있다. image 를 받아 보여 주는 task 옆에, news 를 받아서 보여 주고 새로 고침을 기다리는 두 번째 task 를 둔다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-two-tasks.png)
출처: WWDC25 - Embracing Swift concurrency

각 task 는 자기 작업들을 처음부터 끝까지 순서대로 마친다. fetch 는 background 에서 일어나지만 task 의 나머지 작업은 모두 main thread 에서 돌고, main thread 는 한 번에 한 작업만 실행할 수 있다. task 들은 서로 독립적이므로 번갈아 가며 main thread 를 쓴다. main thread 는 각 task 의 조각을 실행할 준비가 되는 대로 실행한다.

thread 하나가 여러 task 사이를 오가는 것을 interleaving 이라고 부른다. interleaving 은 system resource 를 가장 효율적으로 써서 전체 성능을 높인다. 작업 하나를 기다리느라 thread 를 놀려 두는 대신, 어느 task 든 진행할 수 있게 되는 즉시 진행한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-interleave.png)
출처: WWDC25 - Embracing Swift concurrency

그래서 실행 순서는 무엇이 먼저 끝나느냐에 달려 있다. image 를 받는 일이 news 를 받는 일보다 먼저 끝나면 main thread 는 news 를 보여 주기 전에 image 의 decode 와 표시를 시작한다. news 가 먼저 오면 image 를 decode 하기 전에 news 를 먼저 보여 준다.

### 순서가 필요한 작업

여러 개의 asynchronous task 는 앱이 독립적인 작업 여러 개를 동시에 해야 할 때 알맞다. 반대로 정해진 순서대로 해야 하는 일은 task 하나 안에서 돌린다. task 하나는 code 를 순차적으로 실행하기 때문이다.

```swift
import Foundation

class Image {
  func applyImageEffect() async { }
}

final class ImageModel {
  func displayImage(_ image: Image) {
  }

  func loadImage() async -> Image {
    Image()
  }

  func onButtonTap() {
    Task {
      let image = await loadImage()
      await image.applyImageEffect()
      displayImage(image)
    }
  }
}
```

load, effect 적용, 표시가 한 task 안에 있으므로 이 순서가 바뀌지 않는다.

이 장을 한 문장으로 줄이면 asynchronous 만으로 충분한 경우가 많다는 것이다. network 요청처럼 latency 가 큰 작업이 있을 때는 asynchronous task 로 그 latency 를 감춘다. library 가 내 대신 concurrency 를 써 주는 asynchronous API 를 제공하므로, 내 code 는 계속 main thread 에 머물 수 있다.

## concurrency 의 도입

URLSession 은 network 접근을 background thread 에서 처리하므로 이미 내 대신 concurrency 를 들인 셈이다. 반면 내가 쓴 fetch 와 표시 작업은 main thread 에서 돈다. 그러다 decode 가 너무 오래 걸린다는 것을 알게 될 수 있다. 큰 image 를 decode 할 때 UI 가 멈추는 식으로 드러난다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-decode-hang.png)
출처: WWDC25 - Embracing Swift concurrency

asynchronous 이면서 single-threaded 인 구조는 앱 하나에 충분한 경우가 많다. 하지만 앱이 반응하지 않는다는 것을 느끼기 시작했다면 main thread 에서 너무 많은 일이 벌어지고 있다는 신호다. 이때 순서가 있다. 먼저 Instruments 같은 profiling 도구로 어디에서 시간을 많이 쓰는지 찾는다. concurrency 없이 더 빠르게 만들 수 있는 일이라면 그것부터 한다. 더 빠르게 만들 수 없을 때 concurrency 를 들인다. slide 는 이것을 profile 하고 최적화하는 것이 먼저라는 한 줄로 적는다.

concurrency 는 code 의 일부를 main thread 와 병렬로 background thread 에서 돌려 UI 를 막지 않게 해 준다. system 의 CPU core 를 더 많이 써서 일을 빨리 끝내는 데에도 쓸 수 있다.

---

### concurrent 함수

목표는 decode 를 main thread 에서 떼어 background thread 에서 일어나게 하는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-offload.png)
출처: WWDC25 - Embracing Swift concurrency

main actor 가 기본값인 mode 이므로 `fetchAndDisplayImage` 와 `decodeImage` 는 둘 다 main actor 에 isolated 되어 있다. main actor 의 code 는 main thread 에서만 접근할 수 있는 모든 data 와 code 를 자유롭게 쓸 수 있고, main thread 에는 concurrency 가 없으므로 그것이 안전하다. `decodeImage` 호출을 밖으로 넘기려면 `decodeImage` 에 `@concurrent` attribute 를 붙인다.

```swift
  func fetchAndDisplayImage(url: URL) async throws {
    let (data, _) = try await URLSession.shared.data(from: url)
    let image = await decodeImage(data, at: url)
    view.displayImage(image)
  }

  @concurrent
  func decodeImage(_ data: Data, at url: URL) async -> Image {
    Image()
  }
```

#### @concurrent

`@concurrent` 는 함수를 actor 밖의 concurrent thread pool 에서 실행하라고 Swift 에 알리는 attribute 로, [SE-0461](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0461-async-function-isolation.md){:target="_blank"} 에서 들어왔다. `async` 함수에만 붙일 수 있다.

`decodeImage` 가 `async` 가 되었으므로 부르는 쪽에는 `await` 가 생긴다. 그리고 `decodeImage` 가 어디서 도는지를 바꾸면, `decodeImage` 가 어떤 state 에 접근할 수 있는지에 대한 가정도 같이 바뀐다.

---

### main actor 와의 연결 끊기

`decodeImage` 의 구현을 들여다보면 그 가정이 깨지는 곳이 있다.

```swift
final class ImageModel {
  var cachedImage: [URL: Image] = [:]
  let view = View()

  func fetchAndDisplayImage(url: URL) async throws {
    let (data, _) = try await URLSession.shared.data(from: url)
    let image = await decodeImage(data, at: url)
    view.displayImage(image)
  }

  @concurrent
  func decodeImage(_ data: Data, at url: URL) async -> Image {
    if let image = cachedImage[url] {
      return image
    }

    // decode image
    let image = Image()
    cachedImage[url] = image
    return image
  }
}
```

구현은 cache 된 image data 가 담긴 dictionary 를 확인한다. 이 dictionary 는 main actor 에 저장되어 있어서 main thread 에서만 안전하게 다룰 수 있다. compiler 는 함수가 main actor 의 data 에 접근하려는 곳을 짚어 준다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-concurrent-error.png)
출처: WWDC25 - Embracing Swift concurrency

지금 compiler 로 검사하면 error 가 두 개 나온다. cache 를 읽는 줄에 `main actor-isolated property 'cachedImage' cannot be accessed from outside of the actor`, cache 에 쓰는 줄에 `main actor-isolated property 'cachedImage' can not be mutated from a nonisolated context` 다. 세션 화면에는 읽는 줄의 진단 하나만 보이고 문구도 조금 다르다. `Image` 를 `nonisolated class` 로 선언해서 검사하면 dictionary 가 non-Sendable 이라 main actor 밖으로 나갈 수 없다는 error 가 하나 더 붙는다.

concurrency 를 더할 때 bug 를 만들지 않으려면 바로 이 정보가 필요하다. main actor 와의 연결을 끊어 concurrency 를 안전하게 들이는 전략은 세 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-breaking-ties.png)
출처: WWDC25 - Embracing Swift concurrency

- main actor 의 code 를 항상 main actor 에서 도는 caller 쪽으로 옮긴다. 그 일이 synchronous 하게 일어나야 할 때 좋은 전략이다.
- concurrent code 에서 `await` 를 써서 main actor 에 asynchronous 하게 접근한다.
- code 가 main actor 에 있을 필요가 전혀 없다면 `nonisolated` keyword 를 붙여 어떤 actor 와도 떼어 놓는다.

여기서는 첫 번째 전략을 쓴다. image caching 을 main actor 에서 도는 `fetchAndDisplayImage` 로 옮긴다.

```swift
final class ImageModel {
  var cachedImage: [URL: Image] = [:]
  let view = View()

  func fetchAndDisplayImage(url: URL) async throws {
    if let image = cachedImage[url] {
      view.displayImage(image)
      return
    }

    let (data, _) = try await URLSession.shared.data(from: url)
    let image = await decodeImage(data)
    cachedImage[url] = image
    view.displayImage(image)
  }

  @concurrent
  func decodeImage(_ data: Data) async -> Image {
    // decode image
    Image()
  }
}
```

세션 page 의 snippet 에는 cache 에 저장하는 줄이 빠져 있고 slide 에는 있다. 나는 slide 를 따라 `cachedImage[url] = image` 를 넣었고, 이 형태는 진단 없이 통과한다.

async 호출을 하기 전에 cache 를 먼저 확인하는 것은 latency 를 없애는 데에도 좋다. image 가 cache 에 있으면 `fetchAndDisplayImage` 는 한 번도 suspend 되지 않고 synchronous 하게 끝난다. 결과가 UI 에 곧바로 전달되고, image 가 아직 없을 때만 suspend 된다. `decodeImage` 는 이제 url 이 필요 없으므로 parameter 에서 뺀다. 남은 일은 `decodeImage` 의 결과를 `await` 하는 것뿐이다.

### nonisolated code

`@concurrent` 함수는 실행될 때 항상 actor 에서 벗어난다. 함수가 자신을 부른 actor 에 그대로 머물기를 원한다면 `nonisolated` keyword 를 쓴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-where-run.png)
출처: WWDC25 - Embracing Swift concurrency

둘의 차이는 누가 실행 위치를 정하느냐다. `@concurrent` 는 항상 background 에서 돌고, `nonisolated` 는 부르는 쪽이 어디서 돌지를 고르게 한다. Swift 에는 concurrency 를 더 들이는 다른 방법들도 있는데, 세션은 그 내용을 [Beyond the basics of structured concurrency](https://developer.apple.com/videos/play/wwdc2023/10170/){:target="_blank"} 로 넘긴다.

이 구분은 library 를 만들 때 중요하다. decode API 를 여러 client 가 쓰는 library 의 일부로 제공한다면 `@concurrent` 가 늘 좋은 선택은 아니다. decode 에 걸리는 시간은 data 의 크기에 달려 있고, 작은 data 는 main thread 에서 decode 해도 괜찮다. library 는 nonisolated API 를 제공하고 일을 밖으로 넘길지는 client 가 정하게 하는 것이 가장 좋다. 세션은 Foundation 의 `JSONDecoder` 를 예로 든다.

```swift
import Foundation

nonisolated
public class MyDecoder {
  public func decode<T: Decodable>(_ type: T.Type, from data: Data) -> T {
    fatalError("not implemented")
  }
}

nonisolated struct Post: Decodable {
  var title: String
}

final class Model {
  func onMain(_ data: Data) -> Post {
    MyDecoder().decode(Post.self, from: data)
  }

  @concurrent
  func offMain(_ data: Data) async -> Post {
    MyDecoder().decode(Post.self, from: data)
  }
}
```

세션 snippet 은 class 선언 하나이고 이름이 `JSONDecoder` 다. Foundation 의 [JSONDecoder](https://developer.apple.com/documentation/foundation/jsondecoder){:target="_blank"} 와 헷갈리지 않게 이름을 `MyDecoder` 로 바꿨고, 양쪽에서 부를 수 있다는 것을 보려고 `Post` 와 `Model` 을 내가 더했다.

nonisolated code 는 어디서든 부를 수 있어서 유연하다. main actor 에서 부르면 main actor 에 머물고, background thread 에서 부르면 background thread 에 머문다. 그래서 범용 library 의 기본값으로 알맞다. slide 는 library module 쪽 build setting 의 Default Actor Isolation 이 nonisolated 로 되어 있는 모습을 함께 보여 준다.

검사하면서 알게 된 것이 하나 있다. 처음에 `Post` 를 `nonisolated` 없이 `struct Post: Decodable` 로 적었더니 `offMain` 에서 `main actor-isolated conformance of 'Post' to 'Decodable' cannot be used in @concurrent context` 라는 error 가 났다. main actor 가 기본값인 module 에서는 type 뿐 아니라 그 type 의 protocol conformance 도 main actor 에 묶이기 때문이다 ([SE-0470](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0470-isolated-conformances.md){:target="_blank"}). background 에서 decode 할 model type 은 `nonisolated` 로 선언해야 한다는 뜻이다. 이 부분은 세션에 없는 내용이고 내 검사 결과다.

### concurrent thread pool

일을 background 로 넘기면 그 일을 background thread 에 배정하는 것은 system 이 맡는다. concurrent thread pool 은 system 의 모든 background thread 를 담고 있고, 그 수는 정해져 있지 않다. watch 같은 작은 기기에는 pool 에 thread 가 하나나 둘뿐일 수 있고, core 가 많은 큰 system 에는 더 많다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-thread-pool.png)
출처: WWDC25 - Embracing Swift concurrency

task 가 어느 background thread 에서 도는지는 중요하지 않다. resource 를 가장 잘 쓰는 일은 system 에 맡기면 된다. 예를 들어 task 가 suspend 되면 원래 thread 는 준비된 다른 task 를 실행하기 시작한다. task 가 resume 될 때는 pool 의 thread 가운데 비어 있는 아무 thread 에서나 이어서 돌 수 있고, 그 thread 는 처음 시작한 thread 와 다를 수 있다. 그림에서 Fetch image 다음의 Decode image 가 다른 줄로 내려간 것이 그 모습이다. 이 pool 이 어떻게 동작하는지는 [Swift concurrency: Behind the scenes](https://haroldfromk.github.io/posts/WWDC21-10254/){:target="_blank"} 에서 자세히 다뤘다.

## data 공유

concurrency 가 생겼으므로 이제 서로 다른 thread 사이에 data 를 공유하게 된다. concurrent code 에서 mutable state 를 공유하는 것은 실수하기 쉽기로 악명이 높고, 그 실수는 고치기 어려운 runtime bug 로 이어진다. Swift 는 이런 실수를 compile 시점에 잡아 주므로 concurrent code 를 자신 있게 쓸 수 있다.

main actor 와 concurrent pool 사이를 오갈 때마다 thread 사이에 data 가 공유된다. 지금의 함수에서는 세 번이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-data-shared.png)
출처: WWDC25 - Embracing Swift concurrency

- UI 에서 얻은 URL 이 main actor 에서 background thread 로 넘어가 image 를 받는 데 쓰인다.
- image 를 받으면 data 가 나오고, 그것이 image decode 로 넘어간다.
- decode 가 끝나면 image 가 `self` 와 함께 main actor 로 되돌아온다.

Swift 는 이 값들이 concurrent code 에서 모두 안전하게 접근되도록 보장한다.

### value type 의 복사

UI 갱신이 그 URL 을 쓰는 task 를 추가로 만든다면 어떻게 될까. 다행히 `URL` 은 value type 이다. URL 을 background thread 로 복사하면 background thread 는 main thread 에 있는 것과 별개의 복사본을 갖는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-value-copies.png)
출처: WWDC25 - Embracing Swift concurrency

사용자가 UI 에서 새 URL 을 입력하면 main thread 의 code 는 자기 복사본을 마음대로 쓰거나 바꿀 수 있고, 그 변화는 background thread 에서 쓰는 값에 영향을 주지 않는다. 그래서 `URL` 같은 value type 은 공유해도 안전하다. 사실은 공유가 아니기 때문이다. 복사본 하나하나가 서로 독립적이다.

value type 은 처음부터 Swift 의 큰 부분이었다. string, integer, date 같은 기본 type 은 모두 value type 이다. dictionary 와 array 처럼 value type 을 담는 collection 도 value type 이다. value type 을 저장하는 struct 와 enum 도 마찬가지다.

```swift
import Foundation

struct Post {
  var author: String
  var title: String
  var date: Date
  var categories: [String]
}
```

### Sendable 이란?

concurrent 하게 공유해도 항상 안전한 type 을 Sendable type 이라고 부른다. [Sendable](https://developer.apple.com/documentation/swift/sendable){:target="_blank"} 은 protocol 이고, 여기에 conform 하는 type 은 공유해도 안전하다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-sendable-types.png)
출처: WWDC25 - Embracing Swift concurrency

slide 가 나열하는 것은 네 가지다.

- `URL` 같은 value type 은 Sendable 이다.
- `Array` 같은 collection 은 Sendable 에 대한 conditional conformance 를 정의한다. element 가 Sendable 이면 collection 도 Sendable 이다.
- struct 와 enum 은 instance data 가 모두 Sendable 일 때 Sendable 로 표시할 수 있다.
- main actor 의 type 은 암묵적으로 Sendable 이므로 따로 적지 않아도 된다.

```swift
import Foundation

struct ImageRequest: Sendable {
  var url: URL
}

@MainActor class ImageModel {}

nonisolated func needsSendable<T: Sendable>(_ value: T) {}

nonisolated func check(url: URL, urls: [URL], request: ImageRequest, model: ImageModel) {
  needsSendable(url)
  needsSendable(urls)
  needsSendable(request)
  needsSendable(model)
}
```

세션 snippet 에는 `extension URL: Sendable {}` 과 `extension Array: Sendable where Element: Sendable {}` 이 들어 있다. 이것은 Foundation 과 standard library 가 이미 선언해 둔 것을 설명하려고 적은 줄이라, 그대로 compile 하면 conformance 가 그 type 의 module 에 이미 선언되어 있다는 warning 이 난다. 그래서 그 두 줄은 빼고, 네 종류가 정말 Sendable 인지 확인하는 `needsSendable` 과 `check` 를 내가 더했다. 네 호출 모두 진단 없이 통과한다. 반대로 `nonisolated class` 로 선언한 type 을 같은 함수에 넘기면 `type 'MyImage' does not conform to the 'Sendable' protocol` 이라는 error 가 난다. `Sendable` 의 규칙은 [Protect mutable state with Swift actors](https://haroldfromk.github.io/posts/WWDC21-10133/){:target="_blank"} 에서 처음 정리했다.

---

### actor 를 드나드는 값

main actor 같은 actor 는 non-Sendable state 를 보호한다. 그 state 에 한 번에 task 하나만 접근하도록 하는 방식이다. actor 는 method 로 들어온 값을 저장할 수도 있고, 보호하고 있는 state 에 대한 reference 를 method 의 결과로 내보낼 수도 있다. 그래서 값이 actor 안으로 들어가거나 밖으로 나올 때마다 compiler 는 그 값을 concurrent code 로 보내도 안전한지 검사한다.

`decodeImage` 를 부르는 async 호출 한 줄을 보자. `decodeImage` 는 instance method 이므로 `self` 가 암묵적인 argument 로 넘어간다. 값 둘이 main actor 밖으로 나가고, 결과 값 하나가 main actor 안으로 돌아온다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-send-check.png)
출처: WWDC25 - Embracing Swift concurrency

- `self` 는 image model class 이고 main actor 에 isolated 되어 있다. main actor 가 mutable state 를 보호하므로 이 class 의 reference 를 background thread 로 넘겨도 안전하다.
- `Data` 는 value type 이라 Sendable 이다.
- 남는 것은 image type 이다. `Data` 처럼 value type 일 수도 있고, 그렇다면 Sendable 이다.

slide 의 두 번째 줄이 이 검사의 다른 절반을 적고 있다. non-Sendable 값은 보낸 뒤에 다시 쓰지 않을 때에만 보내는 것이 허용된다. 세션은 이 규칙을 설명하려고 image 를 class 로 바꾼다.

---

### class 와 reference

class 는 reference type 이다. 변수 하나를 다른 변수에 대입하면 둘은 memory 의 같은 object 를 가리킨다. 한 변수를 통해 object 를 바꾸면, 예를 들어 image 를 scale 하면, 그 변화는 같은 object 를 가리키는 다른 변수에서도 곧바로 보인다.

```swift
import Foundation

struct Color { }

nonisolated class MyImage {
  var width: Int
  var height: Int
  var pixels: [Color]
  var url: URL

  init() {
    width = 100
    height = 100
    pixels = []
    url = URL(string: "https://swift.org")!
  }

  func scale(by factor: Double) {
  }
}

func demo() {
  let image = MyImage()
  let otherImage = image // refers to the same object as 'image'
  image.scale(by: 0.5)   // also changes otherImage!
  _ = otherImage
}
```

세션 snippet 은 마지막 세 줄이 top-level 에 있다. 나는 그것을 `demo()` 함수 안으로 옮기고 쓰지 않는 변수 warning 을 없애려고 `_ = otherImage` 를 더했다. `URL(...)` 은 앞에서와 같은 이유로 `URL(string:)` 으로 바꿨다. `MyImage` 는 뒤의 예들에서도 같은 선언을 쓰고, method 이름만 `scaleImage(by:)` 와 `applyAnotherEffect()` 가 더해진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-ref-type.png)
출처: WWDC25 - Embracing Swift concurrency

그런데 지금의 `fetchAndDisplayImage` 는 image 값을 concurrent 하게 쓰지 않는다. `decodeImage` 는 background 에서 돌기 때문에 actor 가 보호하는 state 에 접근할 수 없다. 주어진 data 로 image 의 새 instance 를 만들 뿐이다. 이 image 는 다른 어떤 concurrent code 도 가리킬 수 없으므로 main actor 로 보내 UI 에 표시해도 안전하다. slide 의 주석이 말하듯 새로 만든 object 는 어디로든 보내도 안전하다.

### 동시 공유와 data race

여기에 concurrency 를 조금 넣어 보면 사정이 달라진다.

```swift
final class ImageModel {
  var cachedImage: [URL: MyImage] = [:]
  let view = View()

  func scaleAndDisplay(imageName: String) {
    let image = loadImage(imageName)
    Task { @concurrent in
      image.scaleImage(by: 0.5)
    }

    view.displayImage(image)
  }

  func loadImage(_ imageName: String) -> MyImage {
    // decode image
    return MyImage()
  }
}
```

`scaleAndDisplay` 는 main thread 에서 새 image 를 load 한다. `image` 변수는 고양이 사진이 담긴 image object 를 가리킨다. 그다음 함수는 concurrent pool 에서 도는 task 를 만들고, 그 task 는 `image` 의 복사본을 갖는다. 복사된 것은 reference 이므로 가리키는 object 는 같다. 마지막으로 main thread 는 image 를 표시하러 넘어간다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-race.png)
출처: WWDC25 - Embracing Swift concurrency

이제 문제가 생겼다. background thread 는 image 를 바꾸고 있다. width 와 height 를 다른 값으로 만들고 pixel 들을 scale 된 것으로 갈아 끼운다. 같은 순간에 main thread 는 예전 width 와 height 를 기준으로 pixel 들을 돌고 있다. 이것이 data race 다. UI 가 깨져 보이는 정도로 끝날 수도 있지만, pixel 배열의 범위 밖을 읽으려다 crash 가 날 가능성이 더 크다.

Swift concurrency 는 code 가 non-Sendable type 을 공유하려 할 때 compiler error 로 data race 를 막는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-send-error.png)
출처: WWDC25 - Embracing Swift concurrency

세션 화면의 진단은 concurrent task 로 보내는 `image` 가 main actor 쪽의 사용과 data race 를 일으킬 수 있다는 내용이다. 지금 compiler 는 같은 곳을 closure 단위로 짚는다. `Task` 줄에 `passing closure as a 'sending' parameter risks causing data races between main actor-isolated code and concurrent execution of the closure` 라는 error 가 난다. 문구는 달라도 가리키는 문제는 같다. concurrent task 가 image 를 capture 하고 있고, main actor 도 그 image 를 표시하는 데 쓴다.

고치려면 같은 object 를 concurrent 하게 공유하지 않도록 해야 한다. image effect 가 UI 에 보이기를 원한다면 scale 이 끝나기를 기다린 뒤에 image 를 표시하는 것이 올바른 해법이다. 세 작업을 모두 task 안으로 옮겨 순서대로 일어나게 한다.

```swift
  func scaleAndDisplay(imageName: String) {
    Task { @concurrent in
      let image = loadImage(imageName)
      image.scaleImage(by: 0.5)
      await view.displayImage(image)
    }
  }

  nonisolated
  func loadImage(_ imageName: String) -> MyImage {
    // decode image
    return MyImage()
  }
```

`displayImage` 는 main actor 에서 돌아야 하므로 concurrent task 에서 부를 때 `await` 를 쓴다. 앞에서 본 세 전략 가운데 두 번째다. `loadImage` 는 이제 background 에서 불리므로 `nonisolated` 가 붙었다. 세 번째 전략이다.

`scaleAndDisplay` 자체를 async 로 만들 수 있다면 새 task 를 만들지 않도록 code 를 줄일 수 있다. 세 작업은 `scaleAndDisplay` 를 부른 task 안에서 순서대로 수행된다.

```swift
  @concurrent
  func scaleAndDisplay(imageName: String) async {
    let image = loadImage(imageName)
    image.scaleImage(by: 0.5)
    await view.displayImage(image)
  }
```

두 형태 모두 지금 compiler 에서 진단 없이 통과한다.

---

### 보낸 뒤의 수정

image 를 main actor 로 보내 UI 에 표시하고 나면, main actor 는 그 image 의 reference 를 저장해 둘 수 있다. image object 를 cache 하는 경우가 그렇다. 그래서 UI 에 표시한 뒤에 image 를 바꾸려 하면 안전하지 않은 동시 접근이라는 compiler error 가 난다.

```swift
  @concurrent
  func scaleAndDisplay(imageName: String) async {
    let image = loadImage(imageName)
    image.scaleImage(by: 0.5)
    await view.displayImage(image)
    image.applyAnotherEffect()
  }
```

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-after-send-error.png)
출처: WWDC25 - Embracing Swift concurrency

지금 compiler 의 진단은 `await view.displayImage(image)` 줄의 `sending 'image' risks causing data races` 이고, 세션 화면과 같은 내용이다. 화면에는 그 아래 줄에 접근이 동시에 일어날 수 있다는 note 가 붙어 있다. 앞 절의 규칙 그대로다. non-Sendable 값은 보낸 뒤에 다시 쓰지 않을 때에만 보낼 수 있는데, 여기서는 보낸 뒤에 다시 썼다.

해법은 image 에 대한 변경을 main actor 로 보내기 전에 모두 끝내는 것이다.

```swift
  @concurrent
  func scaleAndDisplay(imageName: String) async {
    let image = loadImage(imageName)
    image.scaleImage(by: 0.5)
    image.applyAnotherEffect()
    await view.displayImage(image)
  }
```

compiler 가 이렇게 보낸 뒤의 사용 여부까지 따지는 것은 Swift 6 에서 들어온 region-based isolation 덕분이고, 그 배경은 [Eliminate data races using Swift Concurrency](https://haroldfromk.github.io/posts/WWDC22-110351/){:target="_blank"} 와 [Migrate your app to Swift 6](https://haroldfromk.github.io/posts/WWDC24-10169/){:target="_blank"} 의 sending 부분에 이어진다.

---

### model class 와 Sendable

data model 에 class 를 쓰고 있다면, model class 는 대개 main actor 에서 시작하게 된다. 그래야 그 일부를 UI 에 보여 줄 수 있다. 나중에 background thread 에서 다뤄야겠다고 정하면 `nonisolated` 로 만든다. 하지만 Sendable 로 만드는 것은 아마 맞지 않다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-model-classes.png)
출처: WWDC25 - Embracing Swift concurrency

그림의 Family, Parent, Child 처럼 서로를 가리키는 model object 들이 있을 때, model 의 일부는 main thread 에서 갱신되고 다른 일부는 background thread 에서 갱신되는 상황은 피해야 한다. model class 를 non-Sendable 로 두면 이런 동시 수정이 일어나지 못한다. 더 쉬운 길이기도 하다. class 를 Sendable 로 만들려면 대개 lock 같은 저수준 synchronization 장치를 써야 하기 때문이다. slide 의 제목이 이 태도를 그대로 말한다. non-Sendable class 는 괜찮다.

### closure 의 capture

class 와 마찬가지로 closure 도 shared state 를 만들 수 있다.

```swift
  @concurrent
  func scaleAndDisplay(imageName: String) async throws {
    let image = loadImage(imageName)
    try await perform(afterDelay: 0.1) {
      image.scale(by: 0.5)
    }
    await view.displayImage(image)
  }

  nonisolated
  func perform(afterDelay delay: Double, body: () -> Void) async throws {
    try await Task.sleep(for: .seconds(delay))
    body()
  }
```

#### Task.sleep(for:)

[sleep(for:tolerance:clock:)](https://developer.apple.com/documentation/swift/task/sleep%28for:tolerance:clock:%29){:target="_blank"} 은 주어진 시간만큼 현재 task 를 suspend 하는 static method 다. thread 를 막지 않고, 기다리는 동안 task 가 cancel 되면 error 를 던진다.

함수는 image object 를 만들고 `perform(afterDelay:)` 를 부르면서 image 를 scale 하는 closure 를 넘긴다. 이 closure 안에는 같은 image 를 가리키는 reference 가 하나 더 있다. 이것을 `image` 변수의 capture 라고 부른다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-closure.png)
출처: WWDC25 - Embracing Swift concurrency

non-Sendable class 와 똑같이, shared state 를 가진 closure 도 concurrent 하게 불리지 않는 한 안전하다. 위 code 는 진단 없이 통과한다. `perform` 의 `body` 가 Sendable 이 아니고 `perform` 이 `nonisolated` 라서, closure 는 그것을 넘긴 task 안에서만 불린다. 그래서 함수 type 은 concurrent 하게 공유해야 할 때에만 Sendable 로 만든다.

---

### Sendable 검사의 요약

Sendable 검사는 data 가 actor 와 task 사이를 지날 때마다 일어난다. 앱에 bug 를 일으킬 data race 가 없도록 보장하려고 있는 것이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-sendable-summary.png)
출처: WWDC25 - Embracing Swift concurrency

- 흔히 쓰는 type 의 다수는 Sendable 이고, concurrent task 사이에 자유롭게 공유할 수 있다.
- class 와 closure 는 concurrent 하게 공유하면 안전하지 않은 mutable state 를 담을 수 있으므로, 한 번에 task 하나에서만 쓴다.
- object 를 한 task 에서 다른 task 로 보내는 것은 여전히 가능하다. 다만 object 에 대한 수정은 보내기 전에 모두 끝낸다.

## actor

asynchronous task 를 background thread 로 옮기면 main thread 가 비어서 앱이 계속 반응한다. 그런데 main actor 에 data 가 많아서 그 task 들이 main thread 에 너무 자주 들러야 한다면, actor 를 들일 때가 된 것이다.

앱이 자라면서 main actor 의 state 도 함께 자란다. network 접근을 관리하는 것 같은 새 subsystem 이 생기고, 그러면 network manager 가 다루는 열린 connection 의 집합 같은 state 가 main actor 에 자리를 잡는다. network 에서 data 를 받을 때마다 그 state 에 접근해야 한다.

```swift
import Foundation

nonisolated class MyImage { }

struct Connection {
  func data(from url: URL) async throws -> Data { Data() }
}

final class NetworkManager {
  var openConnections: [URL: Connection] = [:]

  func openConnection(for url: URL) async -> Connection {
    if let connection = openConnections[url] {
      return connection
    }

    let connection = Connection()
    openConnections[url] = connection
    return connection
  }

  func closeConnection(_ connection: Connection, for url: URL) async {
    openConnections.removeValue(forKey: url)
  }

}

final class View {
  func displayImage(_ image: MyImage) {
  }
}

final class ImageModel {
  var cachedImage: [URL: MyImage] = [:]
  let view = View()
  let networkManager: NetworkManager = NetworkManager()

  func fetchAndDisplayImage(url: URL) async throws {
    if let image = cachedImage[url] {
      view.displayImage(image)
      return
    }

    let connection = await networkManager.openConnection(for: url)
    let data = try await connection.data(from: url)
    await networkManager.closeConnection(connection, for: url)

    let image = await decodeImage(data)
    view.displayImage(image)
  }

  @concurrent
  func decodeImage(_ data: Data) async -> MyImage {
    // decode image
    return MyImage()
  }
}
```

이런 subsystem 을 쓰기 시작하면 image 를 받아 보여 주는 task 가 복잡해진다. background thread 에서 돌려고 하지만 network manager 의 data 가 main thread 에 있으므로 main thread 로 건너가야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-contention.png)
출처: WWDC25 - Embracing Swift concurrency

그 결과가 contention 이다. 여러 task 가 동시에 main actor 에서 code 를 실행하려고 한다. 작업 하나하나는 짧을 수 있지만, 이런 task 가 많으면 합쳐져서 UI 가 끊기는 일이 생긴다.

앞에서는 code 를 `@concurrent` 함수에 넣어 main thread 에서 떼어 냈다. 여기서는 일의 전부가 network manager 의 data 에 접근하는 것이라 그 방법이 통하지 않는다. data 를 밖으로 옮겨야 하고, 그러려면 network manager 를 actor 로 만든다.

---

### actor 란?

main actor 처럼 actor 는 자신의 data 를 isolate 한다. 그 data 에는 그 actor 위에서 실행 중일 때에만 접근할 수 있다. main actor 말고도 [actor](https://developer.apple.com/documentation/swift/actor){:target="_blank"} type 을 직접 정의할 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-actor-types.png)
출처: WWDC25 - Embracing Swift concurrency

actor type 은 main actor 의 class 와 비슷하다. 그 class 처럼 data 를 isolate 해서 한 번에 thread 하나만 data 를 건드릴 수 있게 한다. actor type 은 Sendable 이기도 해서 actor object 를 자유롭게 공유할 수 있다. 다른 점은 두 가지다. main actor 와 달리 program 안에 actor object 가 여러 개 있을 수 있고 각각이 독립적이다. 그리고 actor object 는 main actor 처럼 thread 하나에 묶여 있지 않다.

code 의 변화는 한 단어다. 앞의 `NetworkManager` 선언에서 `final class` 를 `actor` 로 바꾼다.

```swift
actor NetworkManager {
  var openConnections: [URL: Connection] = [:]

  func openConnection(for url: URL) async -> Connection {
    if let connection = openConnections[url] {
      return connection
    }

    let connection = Connection()
    openConnections[url] = connection
    return connection
  }

  func closeConnection(_ connection: Connection, for url: URL) async {
    openConnections.removeValue(forKey: url)
  }

}
```

`ImageModel` 쪽 code 는 한 글자도 바뀌지 않고, file 전체가 진단 없이 통과한다. 부르는 쪽에 이미 `await` 가 있었기 때문이다. 달라지는 것은 실행 위치다. main actor 의 state 일부를 actor object 로 옮기면 더 많은 code 가 background thread 에서 실행될 수 있고, main thread 는 UI 를 반응하게 하는 데 쓸 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-actor-off-main.png)
출처: WWDC25 - Embracing Swift concurrency

그림에서 connection 을 얻고 놓는 칸이 Main thread 줄에서 Background 줄로 내려왔고, main thread 에는 UI 갱신이 들어갈 자리가 넓게 남았다. actor 의 내부 동작과 reentrancy 같은 주의점은 [Protect mutable state with Swift actors](https://haroldfromk.github.io/posts/WWDC21-10133/){:target="_blank"} 에 있다.

---

### actor 를 쓸 때와 쓰지 않을 때

actor 는 main actor 에 data 를 두는 것이 너무 많은 code 를 main thread 에서 돌게 만든다는 것을 알았을 때 쓴다. 그 시점에 network 관리 code 처럼 UI 와 무관한 부분 하나의 data 를 새 actor 로 떼어 낸다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-when-actors.png)
출처: WWDC25 - Embracing Swift concurrency

slide 는 쓸 때와 쓰지 않을 때를 함께 적는다.

- main actor 에 둔 data 때문에 thread 를 건너다니는 일이 너무 많을 때 쓴다.
- 여러 task 에서 오는 data 접근을 조율해야 할 때 쓴다.
- 앱의 class 대부분은 actor 가 될 것이 아니다.
- UI 와 맞닿은 class 는 main actor 에 남아야 UI state 와 직접 상호작용할 수 있다.
- model class 는 대체로 UI 와 함께 main actor 에 두거나 non-Sendable 로 둔다. model 에 대한 동시 접근을 부추기지 않기 위해서다.

## 세션의 마무리

세션은 single-threaded code 에서 시작했다. 필요가 커지면서 latency 를 감추려고 asynchronous task 를, background thread 에서 돌리려고 concurrent code 를, data 접근을 main thread 밖으로 옮기려고 actor 를 들였다. 시간이 지나면 많은 앱이 같은 길을 밟는다. 어떤 code 를 언제 main thread 에서 떼어 낼지는 profiling 도구로 찾고, 그 code 를 main thread 에서 올바르게 분리하는 일은 Swift concurrency 가 돕는다.

concurrency 를 들이기 쉽게 해 주는 권장 build setting 은 두 가지다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2025-06-09-WWDC25-268/wwdc25-268-settings.png)
출처: WWDC25 - Embracing Swift concurrency

- Approachable Concurrency 설정은 concurrency 를 다루기 쉽게 해 주는 upcoming feature 묶음을 켠다. 모든 project 에 권장한다.
- 앱의 main module 처럼 주로 UI 와 상호작용하는 Swift module 에는 Default Actor Isolation 을 main actor 로 두는 것도 권장한다. 따로 말하지 않는 한 code 를 main actor 에 둔다.

두 설정은 함께 작동해서 single-threaded 앱을 쓰기 쉽게 하고, 필요할 때 concurrency 를 들이는 길을 더 완만하게 만든다. slide 의 화면에는 Strict Concurrency Checking 이 Complete 인 것도 함께 보인다.

Approachable Concurrency 가 켜는 feature 는 [Xcode 의 build setting 문서](https://developer.apple.com/documentation/xcode/build-settings-reference){:target="_blank"} 에 `SWIFT_APPROACHABLE_CONCURRENCY` 항목으로 적혀 있다. `DisableOutwardActorInference`, `GlobalActorIsolatedTypesUsability`, `InferIsolatedConformances`, `InferSendableFromCaptures`, `NonisolatedNonsendingByDefault` 다섯 개다. 이 가운데 세션의 설명과 직접 닿는 것은 마지막 것이다. `nonisolated` async 함수가 자신을 부른 actor 에 머문다는 설명은 이 feature 가 켜져 있을 때의 동작이다.

Swift concurrency 는 앱을 더 낫게 만들려고 있는 도구다. 앱에서 성능 문제를 발견했을 때 asynchronous code 나 concurrent code 를 들이는 데 쓴다. 세션은 다음 걸음으로 세 가지를 적는다. Approachable Concurrency 설정을 켜고, 앱의 반응성을 높이기 위해 concurrency 를 들이고, concurrency 와 data-race safety 로 가는 길에 대한 질문은 [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/){:target="_blank"} 에서 찾는다. 이 세션의 개념을 예제 앱에 적용하는 과정은 짝이 되는 code-along 세션 [Code-along: Elevate an app with Swift concurrency](https://developer.apple.com/videos/play/wwdc2025/270/){:target="_blank"} 에 있다.

## 정리

세션이 그린 길을 걸음마다 신호와 도구로 나누면 다음과 같다.

| 걸음 | 넘어가는 신호 | 쓰는 것 | 달라지는 점 |
| --- | --- | --- | --- |
| single-threaded | 시작점 | main actor 기본 isolation | 모든 code 와 data 가 main thread 에 있다 |
| asynchronous | network 처럼 기다리는 시간이 긴 작업 | `async`, `await`, `Task` | 함수가 조각으로 나뉘고 main thread 에서 interleaving 된다 |
| concurrent | profile 로 확인한 main thread 의 긴 계산 | `@concurrent`, `nonisolated` | 그 함수가 concurrent thread pool 에서 돈다 |
| data 공유 | actor 와 task 사이를 지나는 값 | `Sendable`, 보내기 전의 수정 | compiler 가 값마다 안전을 검사한다 |
| actor | main actor 의 data 때문에 생기는 contention | `actor` | 그 data 와 그것을 다루는 code 가 main thread 밖으로 나간다 |

실제 프로젝트에 가져갈 점은 다음과 같다.

- 새 앱 target 은 Default Actor Isolation 을 MainActor 로, Approachable Concurrency 를 Yes 로 두고 시작한다. global variable 과 static property 에서 나던 error 가 처음부터 생기지 않는다.
- concurrency 를 들이기 전에 profile 부터 한다. concurrency 없이 빨라질 수 있는 일이면 그것이 먼저다.
- 기다림이 문제라면 `async`/`await` 만으로 끝난다. library 가 background 작업을 대신 해 준다.
- 계산이 문제라면 그 함수에 `@concurrent` 를 붙인다. compiler 가 짚어 주는 main actor 접근은 caller 로 옮기거나, `await` 로 접근하거나, `nonisolated` 로 떼어 낸다.
- library 의 API 는 `nonisolated` 로 두고, 밖으로 넘길지는 쓰는 쪽이 정하게 한다.
- main actor 기본 mode 에서 background 로 넘길 model type 은 `nonisolated` 로 선언한다. 그러지 않으면 type 과 그 protocol conformance 가 main actor 에 묶인다.
- model class 는 main actor 에 두거나 non-Sendable 로 둔다. Sendable 로 만들려고 lock 을 넣지 않는다.
- non-Sendable object 를 다른 actor 로 보낼 때는 수정을 모두 끝낸 뒤에 보내고, 보낸 뒤에는 건드리지 않는다.
- actor 는 UI 와 무관한 subsystem 의 data 가 main actor 에서 contention 을 일으킬 때에만 만든다.
