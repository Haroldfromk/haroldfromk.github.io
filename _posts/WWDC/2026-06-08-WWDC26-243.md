## 유연함의 대가

세션은 `DynamicInstructions` 가 편리한 이유와 debug 하기 어려운 이유가 같다는 말로 시작한다. `DynamicInstructions` 는 model 이 쓸 instructions 와 tool 을 정해 주는데, request 를 보낼 때마다 다시 평가된다. 그래서 model 은 항상 지금 상황에 맞는 context 를 받는다. 반대로 말하면 어느 request 에서 어떤 instructions 와 tool 이 실제로 들어갔는지는 code 만 봐서는 알기 어렵다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-dynamic.png)

## LLM 앱 개발의 세 가지 과제

기존 code 는 예측할 수 있지만 LLM 은 그렇지 않다. 세션은 이 차이를 세 가지로 나눈다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-mindset.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

| 과제 | 내용 | 따라오는 문제 |
|---|---|---|
| Probabilistic output | 같은 prompt 에 다른 응답이 나온다 | 출력을 고정된 문자열과 비교하는 unit test 가 성립하지 않는다. 응답의 품질과 의도를 평가해야 한다 |
| Model-to-model communication | 여러 model 이 이어서 일한다 | model 사이로 data 가 안정적으로 흐르게 하고, 중간에 틀어졌을 때 복구해야 한다 |
| Observability | 여러 단계 중 어디서 틀어졌는지 알기 어렵다 | 단계마다 model 이 무엇을 받았고 무엇을 결정했는지 볼 수 있어야 한다 |

두 번째 과제의 예로 recipe 앱이 나온다. model 하나가 사진에서 재료를 알아내고, 다른 model 이 그 결과로 recipe 를 만든다. 이 세션이 다루는 것은 세 번째인 observability 다.

### tool call loop 란?

가장 단순한 LLM 기능은 세 단계다. 사람이 prompt 를 보내고, model 이 reason 하고, 사람이 응답을 받는다. 요약, 글쓰기 보조, 질의응답 같은 기능은 이것으로 충분하다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-basic-pattern.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

model 이 갖고 있지 않은 정보가 필요해지면 tool call 이 들어간다. 현재 시각, database record, 검색 결과 같은 것이다. 이때의 흐름이 tool call loop 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-tool-loop.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

1. 사람이 prompt 를 보낸다.
2. model 이 reason 하고 tool 을 호출한다.
3. tool 이 동작을 수행한다.
4. model 이 tool 결과를 받아 최종 응답을 만든다. 이 응답이 loop 를 다시 시작시킬 수도 있다.

단계가 하나 늘 때마다 latency 가 늘고 실패할 수 있는 지점도 하나 는다. Foundation Models instrument 가 보여 주는 화면은 전부 이 loop 를 펼쳐 놓은 것이라서, 세션은 이 그림을 먼저 익히고 넘어간다.

## 대상 기능의 설계

demo 대상은 Craft 앱의 brainstorming 기능이다. 앱이 만들 거리를 몇 개 제안하고, 사용자가 model 과 대화하며 고른 뒤 하나를 정하면 그 craft 의 tutorial 을 만들어 준다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-design.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

이 기능은 instructions 두 벌로 이루어진다.

| instructions | 역할 | tool |
|---|---|---|
| `BrainstormingDynamicInstructions` | craft idea 제안 | `GenerateCraftIdeaTool`, `SwitchToTutorialModeTool` |
| `TutorialDynamicInstructions` | 고른 craft 의 tutorial 생성 | slide 에는 없음 |

둘 다 Private Cloud Compute 의 server model 을 쓴다. 설계의 핵심은 `SwitchToTutorialModeTool` 이다. 사용자가 craft 를 확정하면 model 이 이 tool 을 호출하고, 그 호출이 instructions 를 brainstorming 에서 tutorial 로 바꾼다. 뒤에 나오는 bug 는 바로 이 전환이 일어나지 않는 것이다.

type 이름은 slide 와 Xcode 화면이 조금 다르다. slide 는 `BrainstormingDynamicInstructions`, `GenerateCraftIdeaTool` 이고 Xcode 의 code 는 `BrainstormDynamicInstructions`, `GenerateCraftIdeasTool` 이다. 이 글의 code 는 Xcode 화면 쪽을 따랐다.

## trace 기록

기록 절차는 다른 Instruments template 과 같다. Xcode 의 Product 메뉴에서 Profile 을 고르면 앱이 빌드되고 Instruments 의 template chooser 가 뜬다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-template.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

template 목록에서 Foundation Models 를 고른다. 화면의 대상 기기는 iPad 다. Record 를 누르면 경고가 하나 뜬다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-warning.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

경고 제목은 "Recording may capture sensitive or personal information" 이다. 이 instrument 는 기기에서 오간 prompt 와 response 를 그대로 기록한다. 세션이 말하는 조건은 세 가지다.

- production 에서는 이 logging 이 꺼져 있다.
- trace 를 기록하는 동안에만 켜진다.
- 그래서 trace 파일 자체에 사용자 입력과 model 응답이 들어간다. 파일을 안전한 곳에 둬야 한다.

"Record Anyway" 를 누르면 기록이 시작된다. trace 파일을 issue 나 메신저에 그대로 붙이는 습관이 있다면 이 template 에서는 조심해야 한다.

## Instruments 화면 구성

Instruments 창은 세 영역으로 나뉜다.

| 영역 | 위치 | 보여 주는 것 |
|---|---|---|
| Track | 위 | timeline 위의 활동. track 하나에 lane 이 여러 개 들어갈 수 있다 |
| Detail view | 아래 | 지금 보고 있는 구간의 요약 |
| Inspector | 오른쪽 | timeline 의 막대나 detail view 의 행을 고르면 열리는 상세 정보 |

Foundation Models instrument 는 timeline 에 lane 6개를 갖고, detail view 는 tree 다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-session-inspector.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

화면에서 읽은 lane 이름은 위에서부터 Session, Request, Instructions, Model Inference, Tool, Model Loading 이다. 세션이 설명하는 lane 은 Instructions 와 Model Inference 둘이고, 나머지 넷은 이름과 화면으로만 확인했다.

| lane | 화면에서 본 것 |
|---|---|
| Session | 파란 막대 하나. 첫 prompt 인 "Please generate 3 craft ideas for me." 가 label 로 붙는다 |
| Request | 청록 막대. request 하나에 하나씩 |
| Instructions | 초록 막대. instructions 본문이 label 로 붙는다 |
| Model Inference | 노란 막대와 주황 막대 |
| Tool | tool call 시점의 가는 세로선 |
| Model Loading | 기록 앞쪽의 가는 세로선 |

이 프레임은 Request 막대를 고른 상태다. inspector 에 Duration 3.16 s, Instructions 1, Model Inferences 2, Tokens 1,175, Error Count 0 이 보인다.

### Instructions lane

Instructions lane 은 instructions 와 tool 한 벌이 얼마 동안 활성이었는지를 보여 준다. 한 벌이 여러 request 에 걸칠 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-instructions-lane.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

첫 번째 기록에서는 초록 막대가 session 처음부터 끝까지 하나다. inspector 에는 그 instructions 의 본문이 나오고 Duration 은 28.11 s 다. 설계대로라면 brainstorming 과 tutorial 두 벌이 보여야 하므로, 이 한 줄만으로 handoff 가 일어나지 않았다는 것을 알 수 있다. bug 의 위치가 "전환" 으로 좁혀진다.

### Model Inference lane

Model Inference lane 의 막대는 두 색이다.

| 색 | 뜻 |
|---|---|
| 노랑 | system 이 input prompt 를 처리하는 데 쓴 시간 |
| 주황 | 응답을 생성하는 데 걸린 시간 |

inference 하나는 노란 막대 뒤에 주황 막대가 붙은 모양이 된다. 노란 구간이 뒤에 나오는 Time to First Token 에 해당한다.

### 빠진 tool

원인은 Instructions node 에서 나온다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-tools-one.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

Instructions node 를 고르면 inspector 가 instructions 본문과 Tools 목록을 보여 준다. 본문의 마지막 문단은 "Use the switchToTutorialMode tool once the user explictly confirms the craft they want to make." 다. 그런데 Tools 목록에는 `generateCraftIdea(description, title)` 하나뿐이다. prompt 는 `switchToTutorialMode` 를 쓰라고 하는데 그 tool 이 구성에 들어 있지 않다.

model 은 없는 tool 을 호출할 수 없으므로 brainstorming 에서 tutorial 로 넘어갈 방법이 없다. 사용자는 같은 자리를 맴돈다.

### silent failure 란?

세션은 이 bug 를 silent failure 라고 부른다. model 은 계속 입력을 받고 tool 도 호출했지만 error 는 한 번도 나지 않았다. 잘못됐다는 신호가 어디에도 없어서 찾기 어려운 종류다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-second-request.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

Request 2 의 model inference 를 고른 프레임이 이 점을 잘 보여 준다. Prompt 는 "Paper butterfly" 이고 Response 는 Paper Butterfly 를 고른 것을 반기면서 tutorial mode 로 바꿔 줄지를 되묻는 문장이다. model 은 instructions 가 말한 전환을 하려 했지만 호출할 tool 이 없어서 말로만 응답한 것으로 읽힌다. 이 해석은 프레임을 보고 내가 붙인 것이고, 세션은 이 응답 문장을 따로 설명하지 않는다.

기존 code 라면 없는 함수를 부르는 것은 compile error 다. 여기서는 instructions 의 문장과 tool 목록이 따로 관리되므로, 둘이 어긋나도 build 는 통과하고 runtime 에도 error 가 나지 않는다.

## 수정과 재확인

원인이 정해졌으니 Xcode 로 돌아간다. `BrainstormDynamicInstructions` 정의를 보면 Instructions block 의 문장은 `switchToTutorialMode` tool 을 언급하지만 tool 은 `GenerateCraftIdeasTool` 하나만 나열되어 있다. 수정은 한 줄 추가다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-xcode-fix.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

아래는 수정 뒤의 모습을 옮긴 것이다. instructions 문장은 줄였고, `IdeaState` 와 두 tool 의 본문은 화면에 다 나오지 않아 직접 채웠다. tool 의 `name` 과 `description`, 인자 이름은 Instruments inspector 에 보인 값을 따랐다.

```swift
import FoundationModels
import Observation

@Observable
@MainActor
final class IdeaState {
    var ideas: [String] = []
    var chosenCraft: String?
}

struct GenerateCraftIdeasTool: Tool {
    let name = "generateCraftIdea"
    let description = "Record a single craft project idea (title + description) for the user to consider."
    let state: IdeaState

    @Generable
    struct Arguments {
        let title: String
        let description: String
    }

    func call(arguments: Arguments) async throws -> String {
        await MainActor.run { state.ideas.append(arguments.title) }
        return "Recorded: \(arguments.title)"
    }
}

struct SwitchToTutorialModeTool: Tool {
    let name = "switchToTutorialMode"
    let description = "Switch the session into tutorial-generation mode for the brainstormed idea the user has chosen."
    let state: IdeaState

    @Generable
    struct Arguments {
        let title: String
        let description: String
    }

    func call(arguments: Arguments) async throws -> String {
        await MainActor.run { state.chosenCraft = arguments.title }
        return "Switching to tutorial mode for \(arguments.title)"
    }
}

struct BrainstormDynamicInstructions: DynamicInstructions {
    var state: IdeaState

    var body: some DynamicInstructions {
        Instructions {
            """
            You are an expert crafting assistant.

            Call generateCraftIdea three times simultaneously in
            a single response.

            Use the switchToTutorialMode tool once the user explicitly \
            confirms the craft they want to make.
            """
        }
        GenerateCraftIdeasTool(state: state)
        SwitchToTutorialModeTool(state: state)
    }
}
```

`body` 의 마지막 줄인 `SwitchToTutorialModeTool(state: state)` 가 세션에서 추가한 줄이다. 영상의 code 는 `BrainstormDynamicInstructions` 에 `@MainActor` 가 붙어 있는데, Swift 6 language mode 에서는 그대로 두면 `DynamicInstructions` conformance 가 main actor 격리를 넘는다는 error 가 나서 이 글에서는 뺐다.

#### DynamicInstructions

`body` 안에 instructions 와 tool 을 선언형으로 나열하는 protocol 이다. `body` 는 request 마다 다시 평가되므로 상태에 따라 구성이 달라질 수 있다. 문서는 [DynamicInstructions](https://developer.apple.com/documentation/foundationmodels/dynamicinstructions){:target="_blank"} 에 있다.

#### Instructions

model 에게 역할과 행동 방식을 알려 주는 글이다. 여기에 tool 이름을 적는다고 그 tool 이 등록되지는 않는다. 이 세션의 bug 가 바로 그 차이에서 나왔다. 문서는 [Instructions](https://developer.apple.com/documentation/foundationmodels/instructions){:target="_blank"} 에 있다.

#### Tool

model 이 호출할 수 있는 동작을 정의하는 protocol 이다. `name` 과 `description`, `Arguments` 가 model 에게 전달되고, Instruments 의 Tools 목록에 보이는 것도 이 값들이다. 문서는 [Tool](https://developer.apple.com/documentation/foundationmodels/tool){:target="_blank"} 에 있다.

## 성능 metric

bug 를 고친 뒤에는 같은 trace 로 효율을 본다. tree 의 Info column 은 살펴볼 만한 node 를 빨리 골라내는 용도다. error, 긴 duration, 큰 token 수가 여기에 드러난다. 발표자는 Request 1 의 첫 model inference 가 예상보다 오래 걸렸다며 그 node 를 연다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-metrics-second.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

이 inference 의 값은 Total Duration 1.84s, Response Duration 1.42s, Time to First Token 0.42s, Total Tokens 603, Consumed Tokens 450, Generated Tokens 153, Cached Tokens 0, Cache Hit Rate 0%, Tokens per Second 107.67, Time per Output Token 9.3ms 다. 첫 번째 기록의 같은 inference 는 Consumed Tokens 가 341 이었다. tool 하나가 더 등록되면서 입력이 109 token 늘었다고 볼 수 있는데, 이 비교는 두 프레임의 숫자를 내가 맞대 본 것이고 세션이 언급한 내용은 아니다.

세션은 metric 세 가지를 정리한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-243/wwdc26-243-token-metrics.png)
출처: WWDC26 - Debug and profile agentic app experiences with Instruments

| metric | 재는 것 | 쓰임 |
|---|---|---|
| Time to First Token | prompt 를 받은 뒤 model 이 응답을 생성하기 시작할 때까지 | 값이 크면 사용자가 빈 화면을 보고 있다는 뜻이다. prompt 를 줄이면 줄어든다 |
| Tokens per Second | 응답 생성 속도 | prompt 구성끼리 비교하고, 변경 뒤 regression 을 잡는다 |
| Total Latency | request 를 보낸 때부터 최종 응답을 받을 때까지 | 사용자가 가장 직접 느끼는 값이다. streaming 으로 부분 결과를 먼저 보여 주면 체감이 줄어든다 |

slide 는 timeline 위에 Request 와 token T1 부터 Tn 까지를 놓고, Request 에서 T1 까지를 Time to First Token, token 이 나오는 구간을 Tokens per Second, 전체를 Total Latency 로 표시한다. Total Latency 를 줄이는 방법으로 나온 streaming 은 실제 시간을 줄이는 것이 아니라 체감 시간을 줄이는 방법이라는 점은 구분해 둘 만하다.

## 정리

| 보고 싶은 것 | 보는 곳 |
|---|---|
| instructions 가 언제 바뀌었는지 | Instructions lane 의 막대 수, session inspector 의 Instruction Changes |
| 어떤 tool 이 실제로 등록됐는지 | tree 의 Instructions node 를 고른 뒤 inspector 의 Tools |
| model 이 받은 것과 내놓은 것 | Model Inference node 의 Instructions, Prompt, Response |
| tool call 의 인자와 결과 | Tool Call node 의 inspector |
| 입력 처리와 생성 중 어디가 느린지 | Model Inference lane 의 노란 막대와 주황 막대, inspector 의 Duration |
| token 사용량 | Model Inference node 의 Metrics |

실제 프로젝트에 가져갈 점은 다음과 같다.

- instructions 문장에 tool 이름을 적었다면 그 tool 이 같은 `body` 에 실제로 나열되어 있는지 확인한다. 둘이 어긋나도 build 와 runtime 어디서도 error 가 나지 않는다.
- agentic 기능이 "틀리지는 않았는데 이상하게" 움직이면 먼저 Instructions lane 의 막대 수를 설계와 맞춰 본다. 전환이 일어났는지는 그것만으로 알 수 있다.
- model inference 마다 instructions, prompt, response 를 한 묶음으로 본다. response 가 글인지 tool call 인지에 따라 다음 단계가 달라진다.
- Foundation Models template 으로 만든 trace 파일에는 prompt 와 response 원문이 들어간다. 공유하기 전에 내용을 확인한다.
- Time to First Token 이 크면 prompt 길이부터 줄이고, Total Latency 가 문제면 streaming 을 먼저 검토한다.
- Tokens per Second 와 token 수는 prompt 를 바꿀 때마다 같은 node 에서 비교해 regression 을 본다.
