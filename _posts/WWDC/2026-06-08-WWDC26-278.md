## 달라진 adaptivity 요구 사항

앱은 이미 여러 환경에 놓인다. 화면 크기가 다르고, 다른 앱이나 자기 자신과 나란히 실행된다. iPad 에서는 앱이 resize 되고 외부 display 로 옮겨 가기를 기대하고, iPhone 에서는 portrait 와 landscape 를 모두 기대한다. iPhone 을 Mac 에 mirroring 하는 것도 그렇다.

---

### resize 되는 iPhone 앱

iOS 27 과 macOS 27 에서는 이 경험이 넓어졌다. 이런 환경에서 실행되는 앱은 그 platform 의 앱이 겪는 동적인 변화를 대부분 함께 겪는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-mirroring.png)
출처: WWDC26 - Modernize your UIKit app

- Mac 의 iPhone Mirroring 에서 iPhone window 를 자유롭게 resize 할 수 있다. 앱도 따라서 resize 된다.
- iPad 에서 실행되는 iPhone 전용 앱도 다른 iPad 앱처럼 완전히 resize 된다.

그래서 앱은 runtime 에 주어지는 어떤 scene 크기에도 맞춰야 한다. universal binary 라면 출발은 좋지만 할 일이 더 있다. 세션이 꼽는 것은 넷이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-legacy.png)
출처: WWDC26 - Modernize your UIKit app

- app lifecycle 대신 scene lifecycle 을 쓰는지 확인하기
- main screen 참조 없애기
- user interface idiom 검사 고치기
- interface orientation 검사 고치기

### scene lifecycle 로 옮기기

첫 단계는 app lifecycle 에서 scene lifecycle 로 옮기는 것이다. 대부분의 앱은 이미 쓰고 있다. adaptive 한 앱의 바탕이고, 이 세션의 나머지 작업도 여기에 기댄다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-scene-lifecycle.png)
출처: WWDC26 - Modernize your UIKit app

최신 SDK 로 build 할 때 `UIScene` lifecycle 은 필수다. 없으면 앱이 실행되지 않는다. 앱이 `UISceneDelegate` 를 쓰는지 확인한다. 아직 옮기지 않았다면 세션은 [Make your UIKit app more flexible](https://developer.apple.com/videos/play/wwdc2025/282/){:target="_blank"} (WWDC25) 와 문서 [Transitioning to the UIKit scene-based life cycle](https://developer.apple.com/documentation/uikit/transitioning-to-the-uikit-scene-based-life-cycle){:target="_blank"} 을 권한다.

## main screen 참조 없애기

iPhone 앱이 Mac 에 mirroring 되거나 iPad 에서 앱을 외부 display 로 옮기면 scene 에 연결된 screen 이 바뀐다. 그러면 code 안의 main screen 참조는 앱이 실행 중인 환경과 맞지 않는 정보를 준다.

---

### window scene 에서 screen 얻기

main screen 을 참조하지 않는다. 대신 window 의 window scene 에서 screen 을 그때그때 얻는다. view 나 view controller 가 가까이 없는 곳에서는 screen 이 필요한 method 에 참조를 넘긴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-local-screen.png)
출처: WWDC26 - Modernize your UIKit app

```swift
// Access the correct screen through a windowScene
let screen = window?.windowScene?.screen

// Pass in local screen references
@MainActor func generateThumbnail(_ image: UIImage, screen: UIScreen) -> UIImage {
    // existing code, replacing main screen with local screen reference
    let scale = screen.scale
    _ = scale
    return image
}
```

snippet 의 함수는 본문이 comment 뿐이다. `screen.scale` 을 읽는 줄과 `return` 을 내가 채웠고, `UIScreen` 의 property 가 main actor 에 묶여 있어서 `@MainActor` 를 붙였다. 첫 줄은 `UIView` subclass 의 method 안에 넣어 확인했다.

---

### scale 대신 displayScale

올바른 screen 을 얻는 것보다 더 좋은 것은 screen 참조를 아예 없애는 것이다. adaptive 한 앱에 더 잘 맞는 API 가 많다. 세션은 흔한 pattern 둘을 든다.

첫째는 screen 의 scale 이다. trait collection 의 `displayScale` 로 바꾼다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-display-scale.png)
출처: WWDC26 - Modernize your UIKit app

```swift
override func layoutSubviews() {
    super.layoutSubviews()

    // layoutSubviews will be called again automatically when displayScale changes
    let displayScale = traitCollection.displayScale
    // ...
}
```

view 와 view controller 는 trait collection 을 알아서 갱신하고, 화면에 보이는 hierarchy 에 들어 있지 않을 때도 그럴듯한 값을 준다.

흔히 override 하는 지점은 추적도 된다. `layoutSubviews`, `updateProperties`, `drawRect` 같은 layout 과 drawing method 안에서 어느 trait 을 읽었는지를 system 이 기록한다. 그 trait 이 바뀌면 method 를 다시 불러서 UI 가 갱신된다. 변화를 따로 지켜볼 필요가 없다. 자세한 내용은 문서 [Automatic trait tracking](https://developer.apple.com/documentation/uikit/automatic-trait-tracking){:target="_blank"} 에 있다.

#### displayScale

[displayScale](https://developer.apple.com/documentation/uikit/uitraitcollection/displayscale){:target="_blank"} 은 trait collection 이 속한 환경의 화면 배율이다.

---

### trait 변화를 직접 받기

automatic trait tracking 이 닿지 않는 곳에서는 `registerForTraitChanges` 로 변화를 받는다. 받는 view 의 특정 trait 이 바뀔 때 불리는 closure 를 건다. cache 를 무효로 하거나 그 view 에 딸린 data 를 고치는 데 쓴다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-register-traits.png)
출처: WWDC26 - Modernize your UIKit app

```swift
final class Cache { func invalidate() {} }

final class GalleryView: UIView {
    let cache = Cache()

    override init(frame: CGRect) {
        super.init(frame: frame)

        let displayScaleTrait: [UITrait] = [UITraitDisplayScale.self]
        registerForTraitChanges(displayScaleTrait) {
            (view: GalleryView, previousTraitCollection: UITraitCollection) in
            view.cache.invalidate()
        }
    }

    required init?(coder: NSCoder) { fatalError() }
}
```

snippet 은 가운데 네 줄이다. `GalleryView`, `Cache`, `init` 은 내가 채웠다. 자세한 내용은 문서 [Adapting your app when traits change](https://developer.apple.com/documentation/uikit/adapting-your-app-when-traits-change){:target="_blank"} 에 있다.

#### registerForTraitChanges

[registerForTraitChanges(_:handler:)](https://developer.apple.com/documentation/uikit/uitraitchangeobservable-67e94/registerfortraitchanges%28_:handler:%29){:target="_blank"} 은 주어진 trait 가운데 하나가 바뀔 때 부를 closure 를 등록한다. closure 는 바뀐 object 와 이전 trait collection 을 받는다.

---

### bounds 대신 effective geometry

둘째 pattern 은 screen 의 bounds 로 앱이 쓸 수 있는 공간을 재는 것이다. adaptive 한 환경에서는 scene 이 쓰는 공간이 화면 전체가 아닐 수 있다. screen bounds 참조가 남아 있다면 지금 없앤다.

앱이 쓸 수 있는 공간은 window scene 의 effective geometry 가 알려 준다. 변화를 지켜봐야 하면 scene delegate 에 `windowScene(_:didUpdateEffectiveGeometry:)` 를 구현한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-geometry.png)
출처: WWDC26 - Modernize your UIKit app

```swift
final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func windowScene(
        _ windowScene: UIWindowScene,
        didUpdateEffectiveGeometry previousEffectiveGeometry: UIWindowScene.Geometry
    ) {
        let geometry = windowScene.effectiveGeometry
        let availableSpace = geometry.coordinateSpace.bounds
        // ...
    }
}
```

snippet 은 method 하나다. 감싸는 `SceneDelegate` 는 내가 더했다.

#### effectiveGeometry

[effectiveGeometry](https://developer.apple.com/documentation/uikit/uiwindowscene/effectivegeometry){:target="_blank"} 는 window scene 의 지금 geometry 이고, [windowScene(_:didUpdateEffectiveGeometry:)](https://developer.apple.com/documentation/uikit/uiwindowscenedelegate/windowscene%28_:didupdateeffectivegeometry:%29){:target="_blank"} 는 그 값이 바뀐 뒤 불리는 delegate method 다.

---

### view 의 크기로 판단하기

view 와 view controller 안에서는 scene 의 bounds 를 볼 것도 없다. view controller 의 view 나 view 의 superview 가 가진 크기로 쓸 수 있는 공간을 정한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-view-bounds.png)
출처: WWDC26 - Modernize your UIKit app

```swift
override func viewDidLayoutSubviews() {
    super.viewDidLayoutSubviews()

    let availableSpace = view.bounds.size
    // ...
}
```

이렇게 하면 UI 가 어떻게 present 되는지에 덜 묶인다. view controller 가 split view controller 안처럼 다른 맥락에 놓여도 잘 맞는다.

### game 을 위한 UIRequiresFullscreen

game 은 resize 가 어렵다. 그래서 iOS 27 부터 resize 되는 환경의 iPhone 에서도 `UIRequiresFullscreen` 이 받아들여진다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-fullscreen.png)
출처: WWDC26 - Modernize your UIKit app

동작도 바뀌었다. 이제 앱을 resize 에서 완전히 빼 주지 않는다. 대신 supported interface orientations 를 따르는 discrete resizing 을 켠다. 사람이 scene 크기를 바꿀 때마다 system 이 scene 을 그 크기에 맞는 새 screen 구성으로 넘긴다. game 은 주어진 공간에서 늘 온전한 품질로 그려진다.

#### UIRequiresFullscreen

[UIRequiresFullscreen](https://developer.apple.com/documentation/bundleresources/information-property-list/uirequiresfullscreen){:target="_blank"} 은 앱이 화면 전체를 쓴다고 알리는 Info.plist key 다.

## idiom 과 orientation 검사 고치기

남은 두 legacy API 는 layout 을 정하는 근거로 쓰이던 값들이다.

---

### user interface idiom

user interface idiom trait 은 이제 layout 결정에 아무 뜻이 없다. 앱은 phone idiom 이든 pad idiom 이든 늘어난 공간을 의미 있게 써야 한다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-size-classes.png)
출처: WWDC26 - Modernize your UIKit app

iPhone 앱이 iPad 나 Mac 의 iPhone Mirroring 에서 실행되면 완전히 resize 되지만 idiom 은 여전히 phone 이다. 그러니 layout 결정에서 idiom 검사를 뺀다. menu 를 접거나 공간에 맞춰 layout 을 고치는 일은 size class 로 한다. 더 세밀하게 다뤄야 하면 앞에서처럼 둘러싼 view 의 크기를 쓴다.

---

### interface orientation

interface orientation 도 layout 결정에 쓸모가 없어졌다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-orientation.png)
출처: WWDC26 - Modernize your UIKit app

- iOS 27 에서 앱의 supported interface orientation 은 system 에 건네는 선호일 뿐이다. resize 되는 환경에서는 무시된다.
- Mac 의 iPhone Mirroring 에서 앱은 scene 의 가로세로 비율과 상관없이 늘 portrait orientation 으로 실행된다.
- orientation 검사도 size class 로 바꾼다.

이 생각의 전환은 iOS 8 에서 시작됐다. 세션은 WWDC 2014 에서 Bruce Nilo 가 한 말을 다시 꺼낸다. 기기 회전은 animation 이 붙은 bounds 변화일 뿐이라는 말이다. 여러 기기 크기, iPad 의 resize 되는 window, Mac 의 resize 되는 iPhone 앱이 있는 지금 더 잘 들어맞는다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-quote.png)
출처: WWDC26 - Modernize your UIKit app

### motion 과 location 의 body

orientation 과 이어지는 변화가 하나 더 있다. iOS 27 에서 `UIView` 는 Core Motion 과 Core Location 의 새 Body protocol 을 따른다. motion manager 와 location manager 를 motion data 를 그리는 view, 예를 들어 compass 나 map view 에 잇는다. 그러면 interface orientation 과 상관없이 data 가 늘 맞는 좌표 공간으로 온다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-body.png)
출처: WWDC26 - Modernize your UIKit app

```swift
final class CompassViewController: UIViewController {
    let motionManager = CMMotionManager()
    let locationManager = CLLocationManager()

    override func viewDidLoad() {
        super.viewDidLoad()

        motionManager.deviceMotionBody = view
        locationManager.headingBody = view
    }
}
```

snippet 은 `viewDidLoad` 뿐이다. class 와 두 manager 선언은 내가 더했다. SDK header 에서 `UIView` 가 `CMBodyIdentifiable` 과 `CLBodyIdentifiable` 을 따르는 것을 확인했다.

#### deviceMotionBody 와 headingBody

[deviceMotionBody](https://developer.apple.com/documentation/coremotion/cmmotionmanager/devicemotionbody){:target="_blank"} 는 device motion 의 기준이 되는 body 이고, [headingBody](https://developer.apple.com/documentation/corelocation/cllocationmanager/headingbody){:target="_blank"} 는 heading 의 기준이 되는 body 다.

## tab bar 와 sidebar

iPad 에서 tab bar 는 환경이 받쳐 주면 sidebar 로 펼쳐져서 앱의 구조를 더 많이 드러낸다. iPhone 에서는 어떤 크기에서든 아래쪽 tab bar 가 기본이다.

---

### iPhone 앱의 sidebar

iOS 27 부터 iPhone 앱도 sidebar 를 고를 수 있다. tab bar controller 의 `sidebar.preferredPlacement` 를 `.sidebar` 로 둔다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-sidebar.png)
출처: WWDC26 - Modernize your UIKit app

```swift
tabBarController.sidebar.preferredPlacement = .sidebar
```

iPad 와 달리 이것은 앱의 선택이다. sidebar 를 고르면 UI 에서 sidebar 와 tab bar 를 오가는 방법은 없다. sidebar 를 보일 공간이 있는지는 system 이 정한다. horizontal size class 가 regular 일 때가 그런 예다.

sidebar 를 보일 수 있는지는 `isAvailable` 로 안다. 지금 쓸 수 없다면 nested tab 뒤에 있는 UI 를 앱의 다른 곳에서 드러낸다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-sidebar-available.png)
출처: WWDC26 - Modernize your UIKit app

```swift
tabBarController.sidebar.isAvailable
```

tab group 관리는 [Make your UIKit app more flexible](https://developer.apple.com/videos/play/wwdc2025/282/){:target="_blank"} (WWDC25), tab bar 와 sidebar 의 통합은 [Elevate your tab and sidebar experience in iPadOS](https://developer.apple.com/videos/play/wwdc2024/10147/){:target="_blank"} (WWDC24) 에서 다룬다.

#### preferredPlacement 와 isAvailable

[preferredPlacement](https://developer.apple.com/documentation/uikit/uitabbarcontroller/sidebar-swift.class/preferredplacement){:target="_blank"} 는 sidebar 와 tab bar 가운데 하나만 보일 수 있을 때 무엇을 보일지 정한다. [isAvailable](https://developer.apple.com/documentation/uikit/uitabbarcontroller/sidebar-swift.class/isavailable){:target="_blank"} 은 지금 맥락에서 sidebar 를 보일 수 있는지 알려 준다. SDK header 에 따르면 이 값이 바뀔 때 알려 주는 delegate method 도 있다. 세션에는 나오지 않는다.

---

### prominent tab

`UITabBarController` 에서는 prominent tab 도 정할 수 있다. prominent tab 은 scroll 하면서 tab bar 가 접혀도 늘 보인다. iOS 27 에서는 `prominentTabIdentifier` 로 어느 tab 이든 prominent 하게 만들 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-prominent.png)
출처: WWDC26 - Modernize your UIKit app

```swift
let tabs = [
    UITab(title: "Discover", image: UIImage(systemName: "globe"), identifier: "discover") { _ in UIViewController() },
    UITab(title: "Cart", image: UIImage(systemName: "cart"), identifier: "cart") { _ in UIViewController() },
]
let tabBarController = UITabBarController(tabs: tabs)
tabBarController.prominentTabIdentifier = "cart"
```

snippet 의 `tabs` 배열은 비어 있어서 tab 둘을 내가 채웠다.

#### prominentTabIdentifier

[prominentTabIdentifier](https://developer.apple.com/documentation/uikit/uitabbarcontroller/prominenttabidentifier){:target="_blank"} 는 prominent 하게 보일 tab 의 identifier 다. SDK header 에 따르면 `nil` 이면 조건이 맞는 search tab 이 기본으로 그 자리를 받는다.

## navigation bar 와 menu

bar 와 menu 에서 다시 살펴볼 곳이 셋 있다.

---

### navigation bar minimization

navigation bar 는 scroll 에 맞춰 밀려 올라가며 사라질 수 있다. 화면에 content 자리가 더 생긴다. 기본으로는 system 이 정한 조건에서 minimize 된다.

이 동작을 한쪽으로 고정할 수 있다. safe area 를 직접 다룬다면 bar minimization 이 inset 을 고치지 않게도 할 수 있다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-minimization.png)
출처: WWDC26 - Modernize your UIKit app

```swift
override init(
    nibName nibNameOrNil: String?,
    bundle nibBundleOrNil: Bundle?
) {
    super.init(nibName: nibNameOrNil, bundle: nibBundleOrNil)

    navigationItem.navigationBarMinimization.minimizationBehavior = .onScrollDown
    navigationItem.navigationBarMinimization.safeAreaAdjustment = .disabled
}
```

여기는 영상과 세션 page 가 다르다. 영상의 화면과 설명은 `navigationItem.barMinimizationBehavior` 를 `.always` 나 `.never` 로, `barMinimizationSafeAreaAdjustment` 를 `.never` 로 둔다고 한다. 세션 page 의 snippet 은 위와 같다. Xcode 27.0 의 SDK 에서 확인하니 영상 쪽 이름은 `UINavigationItem` 에 없어서 error 가 났고, snippet 쪽은 통과했다. 그래서 snippet 을 실었다.

SDK header 에 있는 값은 다음과 같다. 영상이 말한 "한쪽으로 고정" 에 해당하는 것은 `never` 와 scroll 방향 둘이다.

| property | 값 |
| --- | --- |
| `minimizationBehavior` | `automatic`, `never`, `onScrollDown`, `onScrollUp` |
| `safeAreaAdjustment` | `automatic`, `enabled`, `disabled` |
| `restorationBehavior` | `automatic`, `atScrollEdge` |

`restorationBehavior` 는 세션에 나오지 않는다.

#### UIBarMinimization

[UIBarMinimization](https://developer.apple.com/documentation/uikit/uibarminimization-swift.struct){:target="_blank"} 은 navigation bar 가 scroll 에 따라 어떻게 minimize 되는지 담는 구성이다. `UINavigationItem` 의 `navigationBarMinimization` 으로 얻는다.

---

### scroll edge effect

scroll 할 때 바뀐 것이 하나 더 있다. scroll edge effect 의 모양이다. OS 의 기본값을 override 해 둔 곳이 있다면 design 을 다시 본다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-scroll-edge.png)
출처: WWDC26 - Modernize your UIKit app

`.automatic` style 은 이제 기존의 soft 와 hard 사이를 오가지 않는다. 더 또렷한 자기 모양을 갖는다. 예전에 `.automatic` 을 다른 값으로 바꿔 두었다면 그 결정을 다시 따져 본다. `.soft` 로 둔 경우가 특히 그렇다. 더는 system 의 기본 모양과 같지 않다.

#### UIScrollEdgeEffect.Style

[UIScrollEdgeEffect.Style](https://developer.apple.com/documentation/uikit/uiscrolledgeeffect/style-swift.class){:target="_blank"} 은 scroll edge effect 의 모양을 정하는 type 이다. `automatic`, `soft`, `hard` 가 있다.

---

### menu 의 image

Liquid Glass 가 다듬어지면서 menu element 에 넣은 image 가 어떤 맥락에서는 기본으로 보이지 않는다. iPadOS 와 macOS 의 menu bar 가 그런 곳이다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-menu-image.png)
출처: WWDC26 - Modernize your UIKit app

그래도 image 가 보여야 하면 `preferredImageVisibility` 로 system 의 기본 동작을 바꾼다. 언제 image 를 보이는 것이 맞는지는 Human Interface Guidelines 의 [Menus](https://developer.apple.com/design/human-interface-guidelines/menus){:target="_blank"} 를 본다.

세션에는 code 가 없다. SDK 에서 확인한 쓰임은 다음과 같다. 내가 쓴 code 다.

```swift
let action = UIAction(title: "Share", image: UIImage(systemName: "square.and.arrow.up")) { _ in }
action.preferredImageVisibility = .visible
```

#### preferredImageVisibility

[preferredImageVisibility](https://developer.apple.com/documentation/uikit/uimenuelement/preferredimagevisibility){:target="_blank"} 는 menu element 의 image 를 보일지에 대한 선호다. 값은 `automatic`, `visible`, `hidden` 이다.

### drag handler 와 Siri

앱이 drag and drop 을 지원하면 Siri 가 앱의 drag handler 에서 resource 를 읽을 수 있다. context menu 에서 Apple Intelligence 를 부르면 system 이 drag delegate method 를 불러서 content 를 가져온다.

![](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-06-08-WWDC26-278/wwdc26-278-drag.png)
출처: WWDC26 - Modernize your UIKit app

그래서 조심할 것이 생긴다. drag session 이 사용자의 gesture 없이도 시작될 수 있다.

- `sessionWillBegin` 에서 animation 을 돌리거나 modal UI 를 띄우지 않는다.
- drag 가 시작될 때 보이는 stateful UI 가 있다면 그 code 를 `sessionDidMove` 로 옮긴다.

#### sessionWillBegin 과 sessionDidMove

[dragInteraction(_:sessionWillBegin:)](https://developer.apple.com/documentation/uikit/uidraginteractiondelegate/draginteraction%28_:sessionwillbegin:%29){:target="_blank"} 은 drag session 이 시작되기 직전에, [dragInteraction(_:sessionDidMove:)](https://developer.apple.com/documentation/uikit/uidraginteractiondelegate/draginteraction%28_:sessiondidmove:%29){:target="_blank"} 은 drag 위치가 움직일 때 불린다.

## 정리

| 예전 방식 | 바꿀 방식 |
| --- | --- |
| app lifecycle | scene lifecycle (iOS 27 SDK 에서 필수) |
| `UIScreen.main` | `window?.windowScene?.screen` 또는 인자로 받은 screen |
| screen 의 `scale` | `traitCollection.displayScale` |
| screen 의 `bounds` | `effectiveGeometry` 또는 view 의 `bounds` |
| idiom 으로 layout 나누기 | size class, 둘러싼 view 의 크기 |
| interface orientation 으로 layout 나누기 | size class, scene bounds |
| 기기 방향에 맞춘 motion 보정 | `deviceMotionBody`, `headingBody` 에 view 연결 |

실제 프로젝트에 가져갈 점은 다음과 같다.

- project 에서 `UIScreen.main`, `userInterfaceIdiom`, `interfaceOrientation`, `UIDevice.current.orientation` 을 검색하면 고칠 곳이 나온다. 검색어는 내가 고른 것이다.
- trait 은 `layoutSubviews` 같은 추적되는 method 안에서 읽는다. 그러면 갱신 code 가 필요 없다.
- iPhone 전용 앱도 iPad 와 Mac 에서 resize 된다. idiom 이 phone 이라고 좁은 화면을 가정하지 않는다.
- drag delegate 의 `sessionWillBegin` 에 UI code 가 있는지 본다. Siri 가 gesture 없이 부를 수 있다.
- scroll edge effect 를 `.soft` 로 고정해 둔 곳과 menu 의 image 를 iOS 27 에서 다시 본다.
- navigation bar minimization 은 영상의 이름이 아니라 `navigationBarMinimization` 으로 쓴다.
