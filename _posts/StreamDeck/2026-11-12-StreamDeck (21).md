## 트랙패드 위에 올린 맥북 자판

아이패드의 트랙패드 화면은 위아래로 나뉜다. 위는 맥북 자판이고 아래는 트랙패드다. 아이폰에서는 화면이 작아서 키보드 버튼을 누르면 아이폰 키보드가 올라오는 방식이었다. 아이패드는 그럴 필요가 없어서 처음부터 자판을 보여 준다. 화면 전체는 스크롤되지 않는다.

```swift
// MacDeskView.swift (아이패드)
struct MacDeskView: View {
    @Bindable var client: DeckClient

    var body: some View {
        GeometryReader { geo in
            let landscape = geo.size.width > geo.size.height
            VStack(spacing: 0) {
                MacKeyboardView(client: client)
                    .frame(height: geo.size.height * (landscape ? 0.55 : 0.45))
                TrackpadView(client: client, showsKeyboardButton: false)
            }
        }
    }
}
```

#### GeometryReader로 화면 높이를 나누기

[`GeometryReader`](https://developer.apple.com/documentation/swiftui/geometryreader){:target="_blank"}는 자기 자리의 크기를 `geo.size`로 알려 주는 뷰다. 이 코드에서는 그 높이에 세로 화면이면 0.45, 가로 화면이면 0.55를 곱해 자판의 높이로 정했다. 가로로 눕히면 화면 높이가 낮아지므로 자판 몫을 0.55로 더 크게 잡았다. 이 비율이 손에 맞는지는 아직 확인 못 했다. 남은 높이는 아래 `TrackpadView`가 다 쓴다. [`frame(width:height:alignment:)`](https://developer.apple.com/documentation/swiftui/view/frame%28width:height:alignment:%29){:target="_blank"}는 뷰의 높이를 정해 주는 modifier다. 아래쪽의 `TrackpadView`에는 `showsKeyboardButton: false`를 넘겨서 아이폰용 키보드 버튼을 감춘다.

`DeckView`는 기기가 아이폰이면 `TrackpadView`를, 아니면 `MacDeskView`를 보여 준다.

## 줄마다 너비 합이 15인 배열

자판 키를 어디에 놓을지는 화면 코드가 아니라 DeckKit의 `MacKeyboardLayout`에 두었다. 화면과 상관없는 순수한 데이터라서 맥 없이 테스트로 확인할 수 있다([17편](https://haroldfromk.github.io/posts/StreamDeck-(17)/)에서 판단 부분을 DeckKit에 둔 이유와 같다).

먼저 키 하나를 나타내는 타입이다.

```swift
// MacKeyboardLayout.swift (DeckKit)
/// 아이패드 화면 자판의 키 하나
public struct MacKeyCap: Equatable, Sendable {
    public enum Role: Equatable, Sendable {
        case key(UInt16)
        case modifier(KeyModifiers)
        case hanEng
    }

    public let role: Role
    public let label: String
    /// 글자 키 아래 작게 보이는 두벌식 자모. 숫자와 기호 키는 nil
    public let jamo: String?
    /// 1 = 보통 키
    public let width: Double
    public let repeats: Bool
}
```

`role`이 키의 종류다. `.key`는 맥에 키 번호를 보내는 키, `.modifier`는 ⇧ ⌃ ⌥ ⌘ 같은 보조 키, `.hanEng`는 한/영 키다. `label`은 키에 적힌 글자이고, `jamo`는 글자 키 아래 작게 보이는 한글 자모(ㅂ, ㅈ 같은 것)다. `width`는 키 너비로, 보통 키 하나가 1이다.

---

### 키 코드란?

`.key(UInt16)` 안의 숫자가 키 코드다. 맥은 키보드의 키 자리마다 번호를 붙여 두었다. C 키 자리는 8, Space는 49, ←는 123이다. 번호는 글자가 아니라 자리를 가리키기 때문에, 맥이 한글 입력 상태일 때 8번을 받으면 ㅊ이 나오고 영어 입력 상태일 때는 c가 나온다. 자세한 설명은 [16편의 "가상 키 코드란?"](https://haroldfromk.github.io/posts/StreamDeck-(16)/)에 있고, 이 앱이 보내도 되는 번호를 모아 둔 표(`MacKeyCode`)는 17편에서 만들었다. 자판의 글자 키를 누르면 글자가 아니라 이 번호가 맥으로 간다.

---

### 줄 너비를 모두 15로 맞추기

```swift
// MacKeyboardLayout.swift (DeckKit)
/// 맥북 자판 배치. 너비는 모두 4분의 1 단위라 합이 정확히 15다
public enum MacKeyboardLayout {
    public static let rowWidth = 15.0

    public static let rows: [[MacKeyCap]] = [
        [key(MacKeyCode.escape, "esc")] + symbols("`1234567890-=") + [key(MacKeyCode.delete, "⌫", repeats: true)],
        // 생략 (tab 1.5, 글자와 기호 키 12개, \ 1.5)
        [MacKeyCap(role: .hanEng, label: "한/영", jamo: nil, width: 1.75, repeats: false)]
            + letters([("a", "ㅁ"), ("s", "ㄴ"), ("d", "ㅇ"), ("f", "ㄹ"), ("g", "ㅎ"), ("h", "ㅗ"), ("j", "ㅓ"), ("k", "ㅏ"), ("l", "ㅣ")])
            + symbols(";'") + [key(MacKeyCode.returnKey, "return", 2.25)],
        // 생략 (shift 2.25, 글자와 기호 키 10개, shift 2.75)
        [
            modifier(.control, "⌃", 1.25), modifier(.option, "⌥", 1.25), modifier(.command, "⌘", 1.5),
            key(MacKeyCode.space, "", 4.25),
            modifier(.command, "⌘", 1.5), modifier(.option, "⌥", 1.25),
            key(MacKeyCode.left, "←", repeats: true), key(MacKeyCode.up, "↑", repeats: true),
            key(MacKeyCode.down, "↓", repeats: true), key(MacKeyCode.right, "→", repeats: true),
        ],
    ]
}
```

진짜 맥북 자판은 줄마다 키 개수가 다르지만 양쪽 끝이 가지런히 맞는다. 이 자판도 그렇게 만들었다. 첫 줄은 13개의 보통 키 양옆에 esc와 지우기가 1씩 붙고, 둘째 줄은 tab과 `\`가 1.5씩 붙는 식이다. 그래서 키마다 너비를 정하고, 줄마다 너비를 더한 값이 같아야 한다. 아래 그림이 다섯 줄의 실제 값이다.

![다섯 줄의 키 너비를 더하면 모두 15가 된다. 1줄은 1, 13, 1이고 2줄은 1.5, 12, 1.5이고 3줄은 1.75, 11, 2.25이고 4줄은 2.25, 10, 2.75이고 5줄은 1.25, 1.25, 1.5, 4.25, 1.5, 1.25와 화살표 키 네 개가 1씩이라 모두 합치면 15이다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-11-12-StreamDeck-21/touchdeck-21-row-widths.png)

가운데 보통 키 개수가 줄마다 13, 12, 11, 10으로 줄어드는 만큼 양쪽 끝 키가 넓어진다. 5줄은 보통 키가 아니라 보조 키와 Space, 화살표 키 네 개로 채워진다.

화면에서는 이 숫자를 그대로 쓴다. `MacKeyboardView`가 화면 너비를 15로 나눈 값을 `unit`으로 정하고, 키 하나의 너비를 `unit * cap.width`로 준다.

```swift
// MacKeyboardView.swift (아이패드)
GeometryReader { geo in
    let unit = geo.size.width / MacKeyboardLayout.rowWidth
    let rowHeight = geo.size.height / CGFloat(MacKeyboardLayout.rows.count)
    VStack(spacing: 0) {
        ForEach(Array(MacKeyboardLayout.rows.enumerated()), id: \.offset) { _, row in
            HStack(spacing: 0) {
                ForEach(Array(row.enumerated()), id: \.offset) { _, cap in
                    MacKeyCapView(cap: cap, lit: isLit(cap), onPress: { press(cap) })
                        .padding(Self.gap / 2)
                        .frame(width: unit * cap.width, height: rowHeight)
                }
            }
        }
    }
}
.opacity(client.inputState == .ok ? 1 : 0.4)
.disabled(client.inputState != .ok)
```

#### ForEach로 줄과 키를 그리기

1. [`ForEach`](https://developer.apple.com/documentation/swiftui/foreach){:target="_blank"}는 배열의 원소마다 뷰를 하나씩 만든다. 어떤 원소가 어떤 뷰인지 알아볼 이름표(`id`)가 필요한데, 줄과 키에는 이름이 없고 같은 키(⌘, ⇧)도 두 번씩 나온다. 그래서 [`enumerated()`](https://developer.apple.com/documentation/swift/sequence/enumerated%28%29){:target="_blank"}로 원소에 순번(offset)을 붙이고 그 순번을 이름표로 썼다.
2. `HStack(spacing: 0)`은 키를 가로로 빈틈 없이 늘어놓는다. 키 사이의 간격은 키마다 `padding`으로 `gap`(3pt)의 절반인 1.5pt씩 둔다.
3. [`disabled(_:)`](https://developer.apple.com/documentation/swiftui/view/disabled%28%5F:%29){:target="_blank"}는 `true`일 때 뷰의 터치를 막고, [`opacity(_:)`](https://developer.apple.com/documentation/swiftui/view/opacity%28%5F:%29){:target="_blank"}는 투명도를 정한다. 맥이 "된다"(`.ok`)고 답하기 전에는 자판이 흐려지고 눌러도 아무 일도 없다.

줄마다 합이 15라는 약속은 테스트로 묶었다. 너비가 모두 0.25의 배수라서 소수를 더해도 오차 없이 정확히 15가 나온다. 이진수에서 4분의 1은 정확히 표현되는 값이어서 `==`로 비교해도 안전하다.

```swift
// MacKeyboardLayoutTests.swift (DeckKit 테스트)
@Test func rowsHaveEqualWidth() {
    #expect(MacKeyboardLayout.rows.count == 5)
    for row in MacKeyboardLayout.rows { #expect(row.map(\.width).reduce(0, +) == MacKeyboardLayout.rowWidth) }
}
@Test func everyKeyCodeIsValid() {
    for cap in MacKeyboardLayout.rows.joined() { if case .key(let code) = cap.role { #expect(MacKeyCode.all.contains(code)) } }
}
@Test func jamoLabelsMatchKeyPositions() {
    for cap in MacKeyboardLayout.rows.joined() {
        guard case .key(let code) = cap.role, let jamo = cap.jamo else { continue }
        #expect(MacKeyMap.stroke(for: Character(jamo)) == .init(code: code, shift: false))
    }
}
```

[`joined()`](https://developer.apple.com/documentation/swift/sequence/joined%28%29){:target="_blank"}는 배열의 배열(다섯 줄)을 하나로 이어서 키를 한 줄로 훑게 해 준다. 첫 테스트는 줄이 5개이고 줄마다 너비 합이 15인지, 둘째는 `.key`의 번호가 모두 17편의 `MacKeyCode.all`에 있는 번호인지 본다. 셋째는 글자 키 밑에 적힌 두벌식 자모가 그 키 자리의 번호와 맞는지 본다. 예를 들어 Q 키에 적힌 ㅂ이 17편의 한글 자리 표에서도 Q 키 자리인지 확인한다. 라벨을 손으로 적었기 때문에 틀리기 쉬운 곳이다.

## 보조 키 켜짐 상태와 한/영 키

보조 키는 20편의 키 줄처럼 한 번 눌러 켜 두면 다음 키 하나에만 붙는 방식을 그대로 썼다.

```swift
// MacKeyboardView.swift (아이패드)
@State private var armed: KeyModifiers = []

private func isLit(_ cap: MacKeyCap) -> Bool {
    if case .modifier(let m) = cap.role { return armed.contains(m) }
    return false
}

private func press(_ cap: MacKeyCap) {
    switch cap.role {
    case .key(let code):
        client.inputKey(code: code, modifiers: armed)
        armed = []
    case .modifier(let m):
        if armed.contains(m) { armed.remove(m) } else { armed.insert(m) }
    case .hanEng:
        client.inputKey(code: MacKeyCode.space, modifiers: [.control])
        armed = []
    }
}
```

`armed`도 20편과 같은 `KeyModifiers` 값이다.

| 누른 키 | 일어나는 일 |
|---|---|
| 보조 키 | 꺼져 있으면 켜고, 켜져 있으면 끈다. 켜진 키는 색이 바뀐다 |
| 글자나 기호 키 | 그 키 번호와 켜져 있던 보조 키를 맥에 보내고, 보조 키를 모두 끈다 |
| 한/영 키 | ⌃Space를 보내고, 켜져 있던 보조 키는 모두 끈다 |
| 반복 키(⌫, 방향키)를 누르고 있기 | 첫 입력에만 켜진 보조 키가 붙고 곧바로 꺼져서, 이어지는 반복 입력에는 보조 키가 없다 |

⇧, ⌥, ⌘는 자판 양쪽에 하나씩 두 개인데, 어느 쪽을 눌러도 같은 켜짐 상태 하나를 켜고 끈다. 그래서 왼쪽 ⌘를 누르면 오른쪽 ⌘도 같이 켜진 색이 된다. 글자 키를 누르면 켜진 보조 키가 모두 꺼지므로 "다음 키 하나에만" 적용된다.

한/영 키는 `.hanEng`라는 따로 만든 종류다. 키 코드는 Space(49)이고 보조 키는 ⌃로 고정이라서 켜 둔 보조 키는 무시한다. 맥에서 입력 소스를 바꾸는 기본 단축키가 ⌃Space라서 이렇게 보낸다. 이 키는 맥북에서 Caps Lock이 있던 자리(3줄 맨 왼쪽)에 놓았고, 자판 전체에 하나뿐이다. Space 키는 키에 글자를 적지 않아서 VoiceOver(화면을 읽어 주는 기능)가 읽을 이름이 비어 있다. 그래서 라벨이 비어 있는 Space 키만 "스페이스"라고 읽게 했다.

```swift
// MacKeyboardView.swift (아이패드)
.accessibilityLabel(cap.label.isEmpty && cap.role == .key(MacKeyCode.space) ? "스페이스" : cap.label)
```

[`accessibilityLabel(_:)`](https://developer.apple.com/documentation/swiftui/view/accessibilitylabel%28%5F:%29-1d7jv){:target="_blank"}는 VoiceOver가 그 뷰를 읽을 때 쓰는 이름을 정한다.

## 키를 누르고 있으면 반복되는 키

지우기(⌫)와 방향키는 누르고 있으면 계속 입력되어야 한다. 반복하는 키는 이 다섯 개뿐이고, 글자 키는 한 번 누르면 한 번이다. 테스트가 `repeats`가 켜진 키 번호의 집합이 지우기와 방향키 네 개와 같은지 본다.

---

### 키 반복이란?

컴퓨터 키보드에서 글자 키를 계속 누르고 있으면, 처음 한 글자가 나오고 잠깐 쉰 뒤에 연달아 나온다. 이것이 키 반복이다. 처음에 바로 반복되면 한 번만 누르고 싶을 때 두 글자가 나오기 쉬워서 쉬는 시간을 둔다. 이 자판은 첫 누름에 한 번, 0.4초가 지나도 손을 안 떼고 있으면 그때부터 0.08초마다 한 번씩 보낸다.

```swift
// MacKeyboardView.swift (아이패드)
private struct MacKeyCapView: View {
    let cap: MacKeyCap
    let lit: Bool
    let onPress: () -> Void
    @GestureState private var pressing = false
    @State private var repeater: Task<Void, Never>?

    var body: some View {
        face
            .gesture(DragGesture(minimumDistance: 0).updating($pressing) { _, state, _ in state = true })
            .onChange(of: pressing) { _, now in
                if cap.repeats {
                    now ? startRepeating() : stopRepeating()
                } else if now {
                    onPress()
                }
            }
            .onDisappear { stopRepeating() }
            // 생략
    }

    private func startRepeating() {
        guard repeater == nil else { return }
        onPress()
        repeater = Task { @MainActor in
            try? await Task.sleep(for: .seconds(0.4))
            while !Task.isCancelled {
                onPress()
                try? await Task.sleep(for: .seconds(0.08))
            }
        }
    }

    private func stopRepeating() {
        repeater?.cancel()
        repeater = nil
    }
}
```

#### DragGesture와 GestureState로 누르는 동안 알기

1. [`DragGesture(minimumDistance: 0)`](https://developer.apple.com/documentation/swiftui/draggesture/init%28minimumdistance:coordinatespace:%29){:target="_blank"}은 손가락이 닿는 순간부터 반응하는 끌기 제스처다. 최소 거리를 0으로 하면 움직이지 않아도 닿기만 하면 시작된다. 버튼의 `action`은 손을 뗄 때 불리는데, 자판은 손이 닿는 순간 입력되어야 해서 이 방법을 썼다.
2. [`@GestureState`](https://developer.apple.com/documentation/swiftui/gesturestate){:target="_blank"}인 `pressing`은 제스처가 진행되는 동안만 값을 가지고, 제스처가 끝나면 저절로 처음 값(`false`)으로 돌아간다. [`updating(_:body:)`](https://developer.apple.com/documentation/swiftui/gesture/updating%28%5F:body:%29){:target="_blank"}에서 `state = true`로 눌린 동안 `true`를 만든다. 손을 떼거나 다른 터치에 제스처를 뺏겨도 `false`로 돌아와서, 반복이 멈추지 않는 일이 생기지 않는다.
3. 반복하지 않는 키는 `pressing`이 `true`가 되는 순간(손이 닿는 순간)에 `onPress()`를 한 번 부른다.

#### Task로 쉬었다 반복하기

1. [`Task`](https://developer.apple.com/documentation/swift/task){:target="_blank"}는 지금 하던 일과 따로 돌아가는 작업 하나를 만든다. 만든 작업을 `repeater`에 담아 두어야 나중에 멈출 수 있다.
2. [`Task.sleep(for:)`](https://developer.apple.com/documentation/swift/task/sleep%28for:tolerance:clock:%29){:target="_blank"}는 지정한 시간만큼 이 작업을 쉬게 한다. 0.4초 쉰 뒤, 0.08초마다 쉬면서 `onPress()`를 반복한다. 작업이 쉬는 동안 화면은 멈추지 않는다.
3. [`Task.isCancelled`](https://developer.apple.com/documentation/swift/task/iscancelled-swift.type.property){:target="_blank"}는 이 작업이 취소됐는지 알려 준다. [`cancel()`](https://developer.apple.com/documentation/swift/task/cancel%28%29){:target="_blank"}을 부르면 `true`가 되어서 `while` 반복이 끝난다. `startRepeating` 첫머리의 `guard repeater == nil`은 이미 반복 중이면 작업을 또 만들지 않게 한다.
4. [`onDisappear`](https://developer.apple.com/documentation/swiftui/view/ondisappear%28perform:%29){:target="_blank"}는 이 키가 화면에서 사라질 때 부른다. 손가락을 올린 채 칸이 바뀌어도 반복이 남지 않게 `stopRepeating()`을 부른다.

[`onChange(of:initial:_:)`](https://developer.apple.com/documentation/swiftui/view/onchange%28of:initial:%5F:%29){:target="_blank"}는 `pressing`의 값이 바뀔 때마다 클로저를 부른다. 클로저의 두 번째 인자 `now`가 새 값이다. 반복 키의 색은 `pressing` 값으로 바꾼다. 진동은 없고 색만 바뀌며, 반복하지 않는 키도 마찬가지다.

## 트랙패드 기능을 마무리하며 고친 작은 문제

여기부터는 트랙패드 기능 전체를 처음부터 다시 훑으며 찾은 작은 문제들이다. 어느 것도 평소에는 거의 안 보이지만, 맥에 입력을 보내는 기능이라서 한 번 어긋나면 맥에 이상한 일이 생길 수 있다. 문제마다 증상, 원인, 고친 방법 순서로 적는다.

---

### 칸을 닫을 때 맥에 요청이 새던 문제

증상은 이렇다. 아이폰 근접 센서(19편)가 가려진 채로 트랙패드 칸을 닫으면 맥에 시작 요청과 끝 요청이 한 번씩 나갔다. 맥에 손쉬운 사용 권한이 없으면 그 시작 요청이 권한 요청 창을 띄울 수도 있었다. 맥은 조작을 시작하는 요청에서 권한이 없으면 창을 띄운다.

원인은 19편에서 만든 `onDisappear`의 순서다. 19편에서 본 대로 `DeckClient`는 `TrackpadPresence`의 `wantsInput`(`screenOpen && foreground && !covered && !stoppedByMac`)이 바뀌는 순간에만 맥에 시작이나 끝을 보낸다. 센서가 가려지면(`covered`) `wantsInput`은 `false`다. 칸을 닫을 때 코드가 먼저 "가려진 상태 풀기"(`setProximityCovered(false)`)를 하면 화면은 아직 열려 있는 채로 `covered`만 풀려서 `wantsInput`이 잠깐 `true`가 된다. 이때 `DeckClient`는 입력이 필요해졌다고 보고 시작 요청을 보낸다. 바로 뒤의 `setTrackpadOpen(false)`로 `false`가 되면 끝 요청이 나간다.

고친 방법은 순서를 바꾸는 것이다. 화면을 닫은 것을 먼저 알리면 `wantsInput`은 `false`인 채로 가려짐이 풀린다.

```swift
// TrackpadView.swift (고친 뒤)
.onDisappear {
    if Self.isPhone { UIDevice.current.isProximityMonitoringEnabled = false }
    client.setTrackpadOpen(false)
    client.setProximityCovered(false)
}
```

### 앱이 뒤로 가도 켜져 있던 근접 센서

증상은 트랙패드 칸을 연 채 앱을 뒤로 보내도 근접 센서가 계속 켜져 있다는 점이었다. 설계에는 앱이 뒤로 가면 끄는 것으로 적혀 있었다.

원인은 센서를 켜고 끄는 자리가 화면이 나타날 때와 사라질 때뿐이었기 때문이다. 앱이 뒤로 가는 것은 화면이 사라지는 것이 아니라서, `scenePhase`는 `DeckClient`에 "앞에 있지 않다"고 알리기만 하고 센서는 그대로였다.

```swift
// TrackpadView.swift (고친 뒤)
@Environment(\.scenePhase) private var scenePhase

.onChange(of: scenePhase, initial: true) { _, phase in
    client.setTrackpadForeground(phase == .active)
    if Self.isPhone { UIDevice.current.isProximityMonitoringEnabled = (phase == .active) }
}
```

`scenePhase`와 근접 센서를 켜는 `isProximityMonitoringEnabled`는 19편에서 설명했다. 고친 것은 한 줄이다. 앱이 앞에 있을 때(`active`)만 센서를 켜 두고, 뒤로 가면 끈다. 아이패드에는 이 센서가 없어서 `isPhone`일 때만 건드린다.

---

### 손가락 네 개 이상이 세 손가락 밀기로 처리되던 문제

증상은 손가락 네 개 이상을 올리고 움직이면 세 손가락 밀기로 처리된다는 점이었다. 원인은 17편의 `TrackpadGesture.update`에서 손짓의 종류를 정하는 `switch`다. 손가락이 1개면 이동, 2개면 스크롤, 나머지는 모두 밀기였다(`default`). 4개 이상은 정의된 동작이 없는데 `default`가 받아 버렸다.

고친 방법은 아무것도 안 하는 종류 `.ignored`를 만들고, 3개일 때만 밀기로 정하는 것이다.

```swift
// TrackpadGesture.swift (DeckKit)
private enum Kind { case move, scroll, swipe, ignored }

// 생략
switch n {
// 생략 (1, 2개)
case 3:
    kind = .swipe
    if let swipe = swipeCheck(fromStartX, fromStartY) { out.append(swipe) }
default:
    kind = .ignored   // 4손가락 이상은 정의된 동작이 없다
}

// 생략
case .ignored, nil:
    break
```

종류는 처음으로 10pt를 넘게 움직였을 때 한 번 정해지고 그 손짓이 끝날 때까지 바뀌지 않는다. 그래서 4개 이상으로 정해진 손짓은 손을 뗄 때까지 아무것도 보내지 않는다. 테스트를 먼저 쓰고 고치기 전에 실패하는 것을 확인했다.

```swift
// TrackpadGestureTests.swift (DeckKit 테스트)
@Test func fourFingersDoNothing() {
    var g = TrackpadGesture()
    let four = { (x: Double) in [p(x, 100), p(x + 30, 100), p(x + 60, 100), p(x + 90, 100)] }
    _ = g.update(touches: four(200), at: 0)
    #expect(g.update(touches: four(180), at: 0.05) == [])
    #expect(g.update(touches: four(100), at: 0.1) == [])
    #expect(g.update(touches: [], at: 0.2) == [])
}
```

고치기 전에 이 테스트는 이렇게 실패했다.

```
Test fourFingersDoNothing() recorded an issue at TrackpadGestureTests.swift:161:5: Expectation failed: g.update(touches: four(100), at: 0.1) == []
```

네 손가락의 가운데가 200에서 180으로 20pt 움직이면 10pt(17편의 `tapSlop`)를 넘었으니 이 갱신에서 종류가 정해진다. 옛 코드는 여기서 밀기로 정했다. 밀기는 시작점에서 50pt 이상 움직여야 나오므로 이 갱신은 빈 배열이었다. 시작점에서 100pt 떨어진 100까지 옮긴 갱신에서 왼쪽 밀기(`swipeLeft`)가 나와 빈 배열이 아니었다. 고친 뒤에는 세 번의 `update` 모두 빈 배열이다.

### 맥이 한 번에 받는 글자 수 제한

증상은 맥이 한 메시지로 받는 글자 수가 넉넉하다는 점이다. 맥 쪽 글자 받기(`InputHost.text`)는 `TextInput.clean`만 거쳤다. `clean`은 화면 보기 입력칸과 같이 쓰는 규칙이라 줄바꿈과 탭을 띄어쓰기로 바꾸고 2,000자에서 자른다. 그래서 트랙패드 키보드 길도 메시지 하나에 2,000자까지 받았고, 페어링된 기기가 긴 글을 보내면 맥의 입력 줄을 그만큼 채울 수 있었다.

고친 방법은 트랙패드 길에서만 `clean`을 거친 뒤 한 번 더 1,000자에서 자르는 것이다.

```swift
// InputHost.swift (맥)
func text(_ text: String, from session: ClientSession) {
    guard canInput(session) else { return }
    let cleaned = String(TextInput.clean(text).prefix(1000))
    guard !cleaned.isEmpty else { return }
    RemoteTyper.shared.type(cleaned)
}
```

[`prefix(_:)`](https://developer.apple.com/documentation/swift/collection/prefix%28%5F:%29){:target="_blank"}는 앞에서부터 지정한 개수만 가져온다. 문자열에서는 글자(Character) 단위로 세어서 이모지나 조합 글자가 반쪽 나지 않는다. 화면 보기에서 쓰는 입력 길은 그대로 두었다. 이 제한은 트랙패드 키보드 길에만 걸린다.

---

### 화면 보기 길의 스크롤 값 막기

[18편](https://haroldfromk.github.io/posts/StreamDeck-(18)/)에서 맥이 스크롤 값을 `Int32`로 바꾸는 줄이 `1e300`이나 NaN 같은 값에서 앱을 멈추게 한다고 설명하고, 트랙패드 길에서 "숫자이고 10,000 이하"인 값만 받도록 막았다. 그런데 [7편](https://haroldfromk.github.io/posts/StreamDeck-(7)/)의 화면 보기 길(`PointerPlan`의 `.scroll`)은 같은 `PointerInjector.post`로 가는데도 막지 않은 채였다. 증상은 같다. 페어링된 기기가 화면 보기 스크롤로 큰 값을 보내면 맥 앱이 멈춘다.

같은 기준(`maxScroll = 10_000`)을 `PointerPlan`에도 넣었다. 기준을 벗어나면 스크롤만이 아니라 앞의 커서 이동(`.move`)까지 통째로 버린다.

```swift
// PointerInjector.swift (맥)
static let maxScroll = 10_000.0

// 생략
case .scroll:
    // 숫자가 아니거나 너무 크면 버린다 (PointerInjector의 Int32 변환이 죽지 않게)
    guard event.dx.isFinite, event.dy.isFinite,
          abs(event.dx) <= Self.maxScroll, abs(event.dy) <= Self.maxScroll else { return [] }
    return [.move(p), .scroll(dx: event.dx, dy: event.dy)]
```

```swift
// PointerInjectorTests.swift (맥 테스트)
@Test func hugeOrNonNumberScrollIsDropped() {
    // Int32로 바꿀 때 맥 앱이 죽지 않게, 이런 값은 아예 보내지 않는다
    var plan = PointerPlan()
    for (dx, dy) in [(0, 1e300), (-20_000, 0), (Double.nan, 0), (0, -Double.infinity)] {
        let steps = plan.steps(for: PointerEvent(kind: .scroll, x: 0.5, y: 0.5, dx: dx, dy: dy), display: display, now: t0)
        #expect(steps == [])
    }
    let edge = plan.steps(for: PointerEvent(kind: .scroll, x: 0.5, y: 0.5, dx: -10_000, dy: 10_000), display: display, now: t0)
    #expect(edge.last == .scroll(dx: -10_000, dy: 10_000))
}
```

앞의 네 값(`1e300`, -20,000, NaN, 음의 무한대)이 모두 빈 배열이고, 경계인 ±10,000은 그대로 통과한다. 고치기 전에는 이렇게 실패했다.

```
Test hugeOrNonNumberScrollIsDropped() recorded an issue at PointerInjectorTests.swift:67:9: Expectation failed: steps == []
Test hugeOrNonNumberScrollIsDropped() failed after 0.037 seconds with 4 issues.
```

네 값 모두 빈 배열이 아니어서 이슈가 4개였다. 고친 뒤에는 맥 앱 테스트 101개가 모두 통과했다.

## 맥이 준비되기 전에 쌓인 손짓 버리기

증상은 이렇다. 손짓이 한창 진행 중인데 맥의 답이 "된다"(`.ok`)가 아니었던 때가 있다. 예를 들어 맥이 잠겼다 풀렸거나 다른 기기가 쓰던 중이었다. 그동안 `DeckClient`는 `guard inputState == .ok`로 메시지를 보내지 않고 버린다. 그런데 손가락은 계속 화면에 있다. 상태가 `.ok`로 바뀐 뒤에는 시작이 없는 끌기의 끝이나 이동이 맥에 갈 수 있다.

원인은 손짓의 상태가 있는 곳이다. 지금 손가락이 몇 개고 끌기 중인지 같은 상태는 `DeckClient`가 아니라 화면 쪽 `TrackpadSurface`의 UIView(터치를 받는 판)가 `TrackpadGesture`로 들고 있다. 그래서 `DeckClient`가 직접 `gesture.reset()`을 부를 수 없다. 그 UIView에 닿을 길이 없다.

고친 방법은 20편의 `resetToken`과 같다. `DeckClient`가 숫자 하나(`trackpadDiscardCount`)를 올리고, `TrackpadSurface`의 `updateUIView`가 마지막으로 본 숫자와 다를 때만 손짓을 버린다.

```swift
// DeckClient.swift (아이폰, 아이패드)
/// 조작이 다시 가능해질 때마다 늘어난다. 트랙패드가 그 전에 쌓인 손짓을 버리는 신호
private(set) var trackpadDiscardCount = 0

case .inputStatus(let state, let name):
    if state == .ok, inputState != .ok { trackpadDiscardCount += 1 }
    inputState = state
    inputBusyName = name
    // 생략
```

```swift
// TrackpadSurface.swift (아이폰, 아이패드)
struct TrackpadSurface: UIViewRepresentable {
    let onActions: ([TrackpadAction]) -> Void
    /// 값이 바뀌면 진행 중이던 손짓을 버린다 (보낼 수 없는 동안 쌓인 상태가 맥에 새지 않게)
    var discardToken = 0

    func makeUIView(context: Context) -> TouchView {
        let view = TouchView()
        view.onActions = onActions
        view.discardToken = discardToken
        return view
    }

    func updateUIView(_ view: TouchView, context: Context) {
        view.onActions = onActions
        if view.discardToken != discardToken {
            view.discardToken = discardToken
            _ = view.discardGesture()
        }
    }

    final class TouchView: UIView {
        var onActions: ([TrackpadAction]) -> Void = { _ in }
        private var gesture = TrackpadGesture()
        var discardToken = 0

        /// 상태만 지우고, 끌기 끝 같은 동작은 내보내지 않는다
        func discardGesture() -> [TrackpadAction] { gesture.reset() }
        // 생략
    }
}
```

`updateUIView`는 SwiftUI 쪽 값이 바뀔 때마다 불린다. `TrackpadView`가 `discardToken: client.trackpadDiscardCount`를 넘기므로 `DeckClient`의 숫자가 올라가면 이 함수가 불린다. UIView는 마지막으로 본 숫자(`view.discardToken`)와 지금 숫자를 비교해 다를 때만 `discardGesture()`를 부른다.

`discardGesture()`는 `gesture.reset()`을 부른다. `reset()`은 끌기 중이면 끝내는 동작(`dragEnd`)을 돌려주지만, 이 경우는 그 결과를 받아도 쓰지 않는다(`_ =`). 맥에 끝 동작을 보내는 것이 아니라 상태만 지우는 것이다. 맥이 멈춘 동안 시작된 끌기라면 시작이 맥에 가지 않았고, 그 전에 시작된 끌기라면 맥이 조작을 끝낼 때 이미 버튼을 뗐다. 어느 쪽이든 끝만 따로 보내면 안 된다.

숫자는 상태가 `.ok`가 아니다가 `.ok`가 되는 순간에만 올린다(`inputState != .ok`). 이미 `.ok`인데 `.ok`가 또 오면 올리지 않는다. 그래야 정상으로 진행되는 손짓을 도중에 지우지 않는다.

| TrackpadGestureTests | fourFingersDoNothing | 네 손가락은 움직여도 아무 동작도 안 낸다 |
| PointerInjectorTests | hugeOrNonNumberScrollIsDropped | 화면 보기 스크롤이 크거나 숫자가 아니면 버린다 |

실패 원문은 위의 네 손가락과 화면 보기 스크롤 문제에 적어 두었다. `jamoLabelsMatchKeyPositions`와 `everyKeyCodeIsValid`처럼 코드에 적힌 값이 다른 표와 어긋나지 않는지 보는 테스트는 값을 더하거나 고칠 때 실수를 바로 알려 준다.

## 남은 한계

- 이 시점까지는 아이패드 실기기에서 자판을 써 보지 않았다. 키 크기가 손가락에 맞는지, 키 반복의 0.4초와 0.08초가 손에 맞는지, 세로와 가로 화면의 높이 비율(45%, 55%)이 적당한지는 아직 확인 못 했다.
- ⇧를 켠 채 방향키를 길게 누르면 첫 입력에만 ⇧가 붙는다. 이 동작이 손에 맞는지는 아직 확인 못 했다.
- 한/영 키가 ⌃Space를 보내므로, 맥에서 입력 소스 전환 단축키를 바꿔 놓은 사람에게는 한/영이 안 바뀐다. 이 앱은 맥의 단축키 설정을 읽지 않는다.
- 19편에서 만든 "다시 시작" 버튼은 맥의 권한이 없거나 허용이 꺼져 있을 때도 보인다. 그때 안내 글이 맥에서 할 일을 알려 주고 있어서 그대로 두었다.
