## 비밀번호가 맞는데 틀렸다고 나온 증상

아이폰에서 잠금 풀기를 누르면 "맥 비밀번호가 맞지 않아요. 버튼을 길게 눌러 바꿔 주세요"가 떴다. 저장해 둔 비밀번호는 맞았다. 버전이 다르다는 안내도 뜨지 않았다. 맥 앱도 아무 오류를 내지 않았다. 권한이 없어도 키를 보내는 함수는 평소처럼 끝나기 때문이다.

원인을 따라가 보니 맥 앱이 손쉬운 사용 권한을 잃은 상태였다. 권한 목록에서 TouchDeck이 꺼져 있거나, 앱이 바뀌어서 맥이 지금 실행 중인 앱을 전에 허락한 앱과 같은 앱으로 믿지 않을 때가 그렇다. 맥은 이 권한이 없는 앱이 보낸 키를 아무 알림 없이 버린다.

---

### 손쉬운 사용 권한이란?

[3편](https://haroldfromk.github.io/posts/StreamDeck-(3)/)에서 설명한 권한이다. 다른 앱에 키를 누르고 마우스를 움직이는 앱은 시스템 설정의 손쉬운 사용에서 사용자가 직접 켜 줘야 한다. 이 권한이 없다고 해서 앱이 오류를 받거나 멈추지는 않는다. `CGEvent`로 키를 만들어 보내면 보내는 함수는 평소처럼 끝나고, 키만 어디에도 닿지 않고 사라진다. 우편함에 편지를 넣었는데 우체부가 상대 집에 한 번도 가져다주지 않는 것과 비슷하다. 넣는 쪽에서는 성공한 것처럼 보인다.

앱이 "지금 권한이 있나"를 직접 물어볼 수 있는 방법이 있다. 3편에서 쓴 [`AXIsProcessTrusted()`](https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted){:target="_blank"}다. 이 함수를 부른 앱 자신이 손쉬운 사용 권한을 받았으면 true, 아니면 false를 돌려준다. `MediaKey.allowed`가 이 함수를 감싸고 있다.

```swift
// MediaKey.swift (맥)
static var allowed: Bool { AXIsProcessTrusted() }
```

## 권한을 확인하지 않던 한 곳

비밀번호를 치는 `MacUnlocker`는 키를 보내기 전에 권한을 확인하지 않았다. 그러면 이런 일이 일어났다.

1. 맥 앱이 권한을 잃은 상태에서 아이폰이 잠금 풀기를 보낸다.
2. `MacUnlocker`는 키를 치고 `.typed`(쳤다)를 돌려준다. 키는 맥이 버려서 아무것도 입력되지 않았다.
3. `DeckServer`는 2초를 기다린 뒤 맥이 아직 잠겨 있는지 본다. 잠겨 있으니 비밀번호가 틀렸다고 판단해서 `.wrongPassword`를 아이폰에 보낸다.
4. 같은 때에 `UnlockLimiter`에 실패를 기록한다.

11편에서 만든 `UnlockLimiter`는 누가 비밀번호를 찍어 보는 것을 막으려고, 기기마다 300초 안에 3번 틀리면 300초 동안 받지 않는다. 권한이 없는 동안은 치는 족족 틀린 것으로 세어지니, 비밀번호가 맞아도 세 번만 누르면 5분 동안 잠금 풀기가 막힌다. 고쳐야 할 것은 문구가 아니라 "치지도 않았는데 틀렸다고 세는 것"이었다.

```swift
// DeckServer.swift (맥)
// 잠금 화면이 비밀번호를 확인하고 풀리기까지 기다린다
try? await Task.sleep(for: .seconds(2))
if ScreenLock.isPasswordLocked {
    self.unlockLimiters[deviceId, default: UnlockLimiter()].recordFailure(now: .now)
    session?.send(.unlockResult(.wrongPassword))
}
// 생략
```

"2초 뒤에도 잠겨 있으면 틀린 비밀번호"라는 판단이 맞으려면, 치는 쪽이 정말 쳤다는 것이 먼저 보장되어야 한다. 권한이 없을 때는 그 전제가 깨진다.

![고치기 전에는 권한 확인 없이 키를 치고, 키가 버려져 맥이 그대로 잠기면 wrongPassword를 보내 틀린 횟수에 더하며, 300초 안에 3번이면 5분 동안 막힌다. 고친 뒤에는 치기 전에 권한을 확인해서 없으면 화면도 안 깨우고 noPermission을 보내며 틀린 횟수에 넣지 않고, 기능 번호 10 이상인 아이폰에 권한 안내 문구가 뜬다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-11-12-StreamDeck-24/touchdeck-24-flow.png)

다른 키 입력 길은 이미 권한을 먼저 확인하고 있었다. 화면 보기 안의 마우스와 글자 입력(`ScreenHost`), 키패드 입력(`KeyTyper`), 맥 잠그기(`MacLocker`)가 모두 `MediaKey.allowed`를 보고, 없으면 키를 보내지 않는다. `KeyTyper`와 `MacLocker`는 false를 돌려주고, `ScreenHost`는 기기에 입력이 안 된다는 상태를 알린다. 잠금 풀기만 이 확인이 빠져 있었다.

| 키 입력 길 | 권한 확인 |
|---|---|
| 화면 보기 안의 마우스와 글자 입력 (ScreenHost) | <span style="color:#2e9e4f">있음</span> |
| 키패드 입력 (KeyTyper) | <span style="color:#2e9e4f">있음</span> |
| 맥 잠그기 (MacLocker) | <span style="color:#2e9e4f">있음</span> |
| 잠금 풀기 (MacUnlocker) | <span style="color:#e5534b">없음</span> |

## 치기 전에 권한 확인하기

`MacUnlocker.type`이 맨 처음에 권한을 확인하게 했다. 권한이 없으면 화면도 깨우지 않고 키도 치지 않고 `.noPermission`을 돌려준다.

```swift
// MacUnlocker.swift (맥)
enum Outcome: Equatable, Sendable {
    // 생략
    /// 손쉬운 사용 권한이 없어 치지 않았다. 쳐도 키가 버려진다
    case noPermission
}

private let isAllowed: @Sendable () -> Bool

init(post: @escaping @Sendable (RemoteStep) -> Void, isLocked: @escaping @Sendable () -> Bool,
     pause: @escaping @Sendable () -> Void,
     // 생략
     wait: @escaping @Sendable (TimeInterval) -> Void = { _ in },
     isAllowed: @escaping @Sendable () -> Bool = { true }) {
    // 생략
    self.isAllowed = isAllowed
}

func type(_ password: String, done: @escaping @Sendable (Outcome) -> Void) {
    let chunks = TextInput.chunks(password)
    queue.async { [self] in
        // 권한 없이 치면 키가 버려지고 맥은 잠긴 채라 "비밀번호 틀림"으로 보인다. 화면도 깨우지 않는다
        guard isAllowed() else { return done(.noPermission) }
        // 생략
    }
}
```

진짜 앱이 쓰는 `MacUnlocker.shared`를 만들 때는 `isAllowed: { MediaKey.allowed }`를 넘긴다.

#### 클로저로 권한 확인을 받는 isAllowed

- `isAllowed`는 인자 없이 `Bool`을 돌려주는 클로저(코드 덩어리를 값처럼 들고 다니는 것)다. `type`이 불릴 때마다 호출해서 그 순간의 권한을 본다. 시작할 때 한 번만 확인해 두면 앱이 켜진 뒤에 사용자가 권한을 끄는 경우를 못 잡는다.
- `guard isAllowed() else { return done(.noPermission) }`는 권한이 없을 때 곧바로 `done`을 부르고 빠져나간다. `done`은 값을 돌려주지 않는 함수라서 `return done(...)`으로 한 줄에 쓸 수 있다.
- 이 확인을 화면 깨우기 앞에 둔 이유는, 권한이 없으면 깨워 봐야 쓸 데가 없고 꺼져 있던 화면만 불필요하게 켜지기 때문이다.
- `Outcome`에 새 값을 더하면 이 값을 받는 `switch`가 모든 경우를 다뤄야 한다. 그래서 `DeckServer`의 `switch`에도 `noPermission` 분기를 더해야 했다.

### 의존성 주입이란?

`MacUnlocker`가 `MediaKey.allowed`를 직접 부르게 쓰면 간단해 보인다. 그런데 그러면 이 클래스를 시험할 때마다 진짜 맥의 권한 상태를 따라가야 한다. 권한이 있는 맥에서는 "없을 때"를 시험할 수 없고, 없는 맥에서는 "있을 때"를 시험할 수 없다.

그래서 "권한이 있는지는 이 함수에게 물어봐"를 밖에서 끼워 넣을 수 있게 했다. 건전지로 도는 장난감을 떠올리면 쉽다. 건전지가 장난감 안에 붙박이로 들어 있으면, 다 닳았을 때 어떻게 움직이는지 보려고 정말 닳을 때까지 기다려야 한다. 건전지를 끼우는 칸을 두면 새 건전지든 다 닳은 건전지든 넣어 보며 바로 시험할 수 있다. 이렇게 필요한 부품을 안에서 만들지 않고 밖에서 받는 방식을 의존성 주입이라고 부른다.

[2편](https://haroldfromk.github.io/posts/StreamDeck-(2)/)의 `ActionRunner`처럼 이 프로젝트의 `MacUnlocker`는 이미 `post`(키를 보내는 일), `isLocked`(맥이 잠겼는지), `pause`(글자 묶음 사이 쉬기), `isDisplayAsleep`(화면이 꺼졌는지), `wakeDisplay`(화면 켜기), `wait`(기다리기)를 이 방식으로 받고 있었다. 테스트에서는 이 자리에 기록만 하는 가짜를 넣어서, 진짜 키를 치거나 진짜로 기다리지 않고 순서만 확인했다. `isAllowed`가 같은 줄에 하나 더 섰을 뿐이다.

기본값을 `{ true }`로 둔 것은 예전 `MacUnlocker` 테스트를 한 줄도 고치지 않으려는 것이다. 권한을 따지지 않는 예전 테스트는 그대로 "권한 있음"으로 돌아간다.

## 틀린 횟수에 넣지 않고 새 결과 보내기

`MacUnlocker`가 `.noPermission`을 돌려주면 `DeckServer`가 다룬다. [14편](https://haroldfromk.github.io/posts/StreamDeck-(14)/)에서 만든 `displayAsleep`(꺼진 화면이 2초 안에 안 켜져서 치지 않음) 분기 바로 아래에 같은 모양으로 더했다.

```swift
// DeckServer.swift (맥)
case .displayAsleep:
    // 치지 않았으니 틀린 횟수에 넣지 않는다. 결과를 안 보내면 아이폰은 8초 뒤 다시 연결 흐름으로 간다
    // (새 결과 종류를 만들면 예전 아이폰 앱이 그 메시지를 못 읽는다)
    print("[unlock] display did not wake, not typed")
    return
case .noPermission:
    // 치지 않았으니 틀린 횟수에 넣지 않는다. 예전 아이폰 앱은 이 결과를 못 읽어서 보내지 않는다(8초 뒤 다시 연결 흐름)
    print("[unlock] no accessibility permission, not typed")
    if let session, session.protocolVersion >= DeckProtocol.unlockPermission {
        session.send(.unlockResult(.noPermission))
    }
    return
```

두 분기 모두 `return`으로 나가서, 뒤에 있는 "2초 기다렸다가 잠겨 있으면 `recordFailure`" 부분에 닿지 않는다. 틀린 횟수에는 한 번도 오르지 않는다. 새 결과는 DeckKit의 `UnlockResult`에 값 하나로 더했다.

```swift
// Messages.swift (DeckKit)
/// 맥 잠금 풀기 결과
/// noPermission: 맥 앱에 손쉬운 사용 권한이 없어 치지 않았다. 예전 앱은 못 읽으니 DeckProtocol.unlockPermission 이상에만 보낸다
public enum UnlockResult: String, Codable, Sendable {
    case unlocked, wrongPassword, notLocked, notAllowed, notNearby, tooManyTries, noPermission
}
```

아이폰 앱은 이 값을 받으면 "맥 앱에 손쉬운 사용 권한이 없어 치지 않았어요. 맥에서 권한을 다시 켜 주세요"를 보여 준다.

### 기능 번호를 10으로 올린 이유

새 결과를 아무 기기에나 보내면 안 된다. 예전 아이폰 앱은 `noPermission`이라는 값을 모른다. 아는 값 목록에 없는 글자를 받으면 그 메시지를 읽는 데 실패해서, 메시지를 통째로 버린다. 앱이 죽는 것은 아니지만 아이폰은 아무 답도 못 받는다. [7편](https://haroldfromk.github.io/posts/StreamDeck-(7)/)에서 예전 맥 앱이 모르는 메시지를 답 없이 버려서 아이패드가 모니터 목록을 계속 기다린 일과 같은 모양이다. 이번에는 버리는 쪽이 예전 아이폰 앱이다. 14편에서 화면이 안 켜졌을 때 새 결과를 만들지 않은 것도 이 때문이었다. 이번에는 안내가 꼭 필요해서 기능 번호를 올리는 쪽을 골랐다.

그래서 [8편](https://haroldfromk.github.io/posts/StreamDeck-(8)/)에서 만든 기능 번호를 썼다. 연결할 때 서로 "나는 몇 번까지 안다"를 알려 주는 번호다. 번호를 안 보내는 아주 예전 앱은 1로 본다. 이번 결과가 새로 생기면서 번호를 하나 올려 10으로 만들었다.

```swift
// DeckConstants.swift (DeckKit)
/// 1: 버튼, 볼륨, 키패드, 화면 보기(1, 2차)   2: 글자 입력(typeText, pressKey)   3: 키패드 기호   4: 맥 잠금 풀기   5: 맥이 정한 길   6: 맥 잠그기   7: 버튼 옮기기   8: 맥 잠자기   9: 맥 깨우기
/// 10: 잠금 풀기 결과 "손쉬운 사용 권한 없음"
public enum DeckProtocol {
    // 생략
    public static let wakeMac = 9
    public static let unlockPermission = 10
    public static let current = unlockPermission
}
```

기능 번호 10 이상인 아이폰 앱은 권한이 없을 때 안내 문구를 받는다. 9 이하인 앱은 아무 답도 받지 못하고, 8초 뒤 "맥에서 답이 없어 다시 연결하는 중이에요"가 뜬다.

예전 아이폰 앱은 아무것도 받지 못하지만, 비밀번호가 틀렸다는 거짓 안내는 가지 않는다.

## 테스트부터

이번에도 고치기 전에 테스트를 먼저 썼다. 세 개다.

- `noAccessibilityPermissionIsNotTyped` (맥): 권한이 없으면 키도 안 치고 화면도 안 깨우고 `.noPermission`이 나온다.
- `noPermissionResultRoundTrips` (DeckKit): 새 결과가 JSON으로 적혔다가 다시 읽혀도 같은 값이다.
- `noPermissionResultNeedsProtocolTen` (DeckKit): 기능 번호 10이 `unlockPermission`이고 `current`가 그 번호다.

세 테스트 모두 처음에는 빌드부터 실패했다. `.noPermission`이라는 값, `isAllowed`라는 칸, `DeckProtocol.unlockPermission`이라는 이름이 아직 없어서였다. 이 실패가 "테스트가 정말 새 값을 요구하고 있다"는 확인이 된다.

```swift
// MacUnlockerTests.swift (맥 테스트)
/// 손쉬운 사용 권한이 없으면 키가 버려진다. 치지도, 화면을 깨우지도 않고 따로 알려서 틀린 횟수에 넣지 않는다
@Test func noAccessibilityPermissionIsNotTyped() {
    let events = Events()
    let log = StepLog()
    let unlocker = MacUnlocker(post: { log.append($0) }, isLocked: { true }, pause: {},
                               isDisplayAsleep: { true }, wakeDisplay: { events.add("wake") },
                               wait: { events.add("wait \($0)") }, isAllowed: { false })
    let finished = Expectation()
    unlocker.type("pw") { finished.fulfill($0) }
    #expect(finished.wait() == .noPermission)
    #expect(log.steps.isEmpty)
    #expect(events.all.isEmpty)
}
```

일부러 화면이 꺼져 있고(`isDisplayAsleep: { true }`) 맥이 잠긴(`isLocked: { true }`) 상황에서 `isAllowed: { false }`만 줬다. 권한 확인이 화면 깨우기보다 앞에 있지 않으면 `events`에 "wake"가 남아서 이 테스트가 잡아낸다. 결과가 `.noPermission`이고, 친 키 기록(`log.steps`)과 깨우기, 기다리기 기록(`events.all`)이 모두 비어 있어야 통과한다.

```swift
// UnlockTests.swift (DeckKit)
@Test func noPermissionResultRoundTrips() throws {
    #expect(try ServerMessage.decode(ServerMessage.unlockResult(.noPermission).encoded()) == .unlockResult(.noPermission))
    #expect(try ServerMessage.unlockResult(.noPermission).encoded() == #"{"result":"noPermission","type":"unlockResult"}"#)
}
```

둘째 줄의 기댓값에서 작게 틀렸다. 처음에는 `{"type":"unlockResult","result":"noPermission"}`처럼 type이 앞에 오게 썼다가 실패했다. 이 앱의 메시지는 JSON 키를 이름 순서(sortedKeys)로 적는다. `result`가 `type`보다 알파벳으로 앞이라서 `result`가 먼저 온다. 같은 메시지가 언제나 같은 글자로 나오게 하려고 정해 둔 규칙인데, 기댓값을 손으로 쓰다 보니 읽는 순서대로 적어 버렸다.

기능 번호 9를 보던 예전 테스트 `wakeMacNeedsProtocolNine`은 `current`가 9와 같은지 보고 있어서, 9 이상인지 보게 바꿨다.

고친 뒤 맥 테스트는 85개, DeckKit 테스트는 243개가 통과했고, 아이폰 앱 빌드도 성공했다.
