{: .prompt-info }

블루투스로 개조한 Realforce 86U를 맥에 붙이고 MyKVM으로 Surface를 조작했다. 그런데 윈도우에서 Ctrl+C가 복사가 되지 않고 그냥 c만 찍혔다. 맥 습관대로 누르는 Control+Space 한/영 전환도 먹지 않았다. 예전에 쓰던 HHKB는 같은 설정에서 잘 됐다. 달라진 건 키보드뿐이라, 맥이 키를 어떻게 보내는지부터 기록으로 확인했다.

---

## 맥 수정 키 변경이 걸린 Realforce

Realforce(BLKB02_2)에는 맥 시스템 설정의 수정 키 변경이 걸려 있었다. 값은 HID usage(키보드의 키마다 붙은 번호)로 저장되어 있고, 풀어 보면 이렇다.

| 원래 키 | 맥이 받아들이는 키 |
|---|---|
| Caps Lock (0x39) | 오른쪽 Control (0xE4) |
| 왼쪽 Ctrl (0xE0) | Caps Lock |
| 왼쪽 Alt (0xE2) | 왼쪽 Command (0xE3) |
| 왼쪽 Win (0xE3) | 왼쪽 Alt (0xE2) |
| 오른쪽 Alt (0xE6) | 오른쪽 Command (0xE7) |
| 오른쪽 Win (0xE7) | 오른쪽 Alt (0xE6) |
| 오른쪽 Ctrl (0xE4) | Caps Lock |

그래서 키보드의 Caps Lock 자리는 맥에서 "오른쪽 Control"이다. 윈도우에서 Ctrl+C를 누르려고 이 자리를 누른 것이다.

---

### macOS 수정 키 변경이란?

시스템 설정 > 키보드 > 수정 키에서 키보드마다 Caps Lock, Control, Option, Command가 하는 일을 서로 바꾸는 기능이다. 저장 값은 `0x700000000`에 HID usage를 더한 숫자다(예: 오른쪽 Control은 `0x7000000E4`). 키보드가 보낸 신호를 시스템이 먼저 바꿔 버려서, 이후에 오는 앱은 바뀐 키만 본다. 이 변경이 정확히 어느 단계에서 일어나는지는 16편에서 다시 나온다.

---

## 탭 기록으로 본 키

맥이 MyKVM에 무엇을 건네는지 보려고 [`CGEvent.tapCreate`](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate%28tap:place:options:eventsofinterest:callback:userinfo:%29){:target="_blank"}에 [`listenOnly`](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions/listenonly){:target="_blank"}를 주고 이벤트를 찍었다. 3편의 이벤트 탭과 같은 검문소인데, 이벤트를 바꾸거나 막지 않고 보기만 한다. 수정 키는 [`flagsChanged`](https://developer.apple.com/documentation/coregraphics/cgeventtype/flagschanged){:target="_blank"} 이벤트로 오고, 누를 때와 뗄 때 한 번씩 찍힌다. 먼저 Realforce의 Caps Lock 자리다.

```
flags code=0x3E flags=0x00052100 low=0x2100 kbType=40
flags code=0x3E flags=0x00010100 low=0x0100 kbType=40
```

같은 방법으로 맥북 내장 키보드의 오른쪽 control도 찍었다.

```
flags code=0x3E flags=0x00042100 low=0x2100 kbType=91
flags code=0x3E flags=0x00000100 low=0x0100 kbType=91
```

`code=0x3E`는 맥의 가상 키코드로 오른쪽 Control이다. 수정 키 변경으로 바꾼 Realforce가 맥북의 진짜 오른쪽 Control과 같은 키코드로 온다. `kbType`은 [키보드 종류 번호](https://developer.apple.com/documentation/coregraphics/cgeventfield/keyboardeventkeyboardtype){:target="_blank"}라 키보드마다 다르다(Realforce 40, 맥북 91).

---

### CGEventFlags 장치 비트란?

`flags`는 지금 눌려 있는 수정 키를 비트 하나씩으로 표시한 숫자다([`CGEventFlags`](https://developer.apple.com/documentation/coregraphics/cgeventflags){:target="_blank"}). 켜진 칸이 1이다. 이 값에는 두 종류의 비트가 섞여 있다.

- 공통 비트: 어느 쪽 Control이든 켜지는 칸이다. `0x40000`이 Control이다.
- 장치 비트: 왼쪽인지 오른쪽인지를 가르는 칸이다. 오른쪽 Control은 `0x2000`(헤더 이름 `NX_DEVICERCTLKEYMASK`)이다.

맥북의 `0x42100`을 나누면 공통 Control `0x40000`, 오른쪽 Control 장치 비트 `0x2000`, 그리고 `0x100`이 된다. `0x100`은 [`maskNonCoalesced`](https://developer.apple.com/documentation/coregraphics/cgeventflags/masknoncoalesced){:target="_blank"} 비트로, 이 기록의 모든 줄에 늘 붙어 있어서 이 글에서는 늘 붙어 오는 비트로만 본다.

![flags 0x42100 이 공통 Control 비트 0x40000, 오른쪽 Control 장치 비트 0x2000, 늘 붙어 오는 비트 0x100 세 칸으로 나뉘는 그림](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-11-19-MyKVM-15/mykvm-event-flags.png)

Realforce의 `0x52100`은 맥북보다 `0x10000`이 하나 더 켜져 있다. Caps Lock이 켜져 있다는 표시다. 맥은 Caps Lock 상태를 키보드마다 따로 갖는데, 이때 Realforce 쪽만 켜져 있었을 뿐 Control 판단과는 상관이 없다.

---

### 버린 가설

처음에는 "바꾼 키에는 `0x2000` 장치 비트가 안 붙어서, MyKVM이 뗌으로 읽는 게 아닐까" 하고 의심했다. 기록을 보니 Realforce도 `0x2000`이 정상으로 붙어 있었다. 고치기 전에 먼저 재어 본 덕에 엉뚱한 곳을 고치지 않았다.

## 윈도우까지 나간 MyKVM 진단 기록

MyKVM 진단 기록은 Control+C 한 번에 이렇게 남는다.

```
key flags ... sent=1
key down ... sent=1
key up ... sent=1
key flags ... sent=1
```

Control 누름, c 누름, c 뗌, Control 뗌이 모두 윈도우로 나갔다(`sent=1`). 맥 쪽은 정상이다. 그렇다면 문제는 윈도우가 받은 값을 읽는 쪽에 있다.

## 한국어 윈도우의 한자 키

4편에서 정한 대로 MyKVM은 키의 자리를 스캔 코드로 보낸다. 맥 오른쪽 Control은 오른쪽 Ctrl의 스캔 코드 `E0 1D`로 나갔다.

---

### 확장 키(E0)와 한국어 키보드 배열이란?

4편에서 본 확장 표시 그대로, 같은 `1D`라도 앞에 `E0`이 붙으면 오른쪽 Ctrl이다. 이 구분은 [Windows 키보드 입력 문서](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input){:target="_blank"}의 스캔 코드와 확장 키 설명에 있다. MyKVM이 [`SendInput`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput){:target="_blank"}에 넘기는 [`KEYBDINPUT`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput){:target="_blank"}도 `KEYEVENTF_EXTENDEDKEY` 플래그로 확장 키를 따로 표시한다.

그런데 한국어 윈도우의 키보드 배열(한국어 키보드 드라이버)은 이 두 키를 다르게 읽는다. 한국어 키보드에는 스페이스바 오른쪽에 한/영 키와 한자 키가 있어서, 그 자리에 오는 스캔 코드를 그 키들로 해석한다.

- `E0 38`(오른쪽 Alt) → 한/영(`VK_HANGUL`)
- `E0 1D`(오른쪽 Ctrl) → 한자(`VK_HANJA`)

두 이름은 [Virtual-Key Codes 문서](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes){:target="_blank"}에 있다. 그래서 `E0 1D`를 누르고 c를 누르면 윈도우에게는 "Ctrl+C"가 아니라 "한자 + c"다. 한자 키는 수정 키가 아니라 단독 키라 c는 그냥 c로 찍힌다.

![같은 스캔 코드 E0 1D 가 US 배열에서는 오른쪽 Ctrl, 한국어 배열에서는 한자 키가 되고 한국어 쪽이 Ctrl+C 를 한자 + c 로 만든다](https://pub-1fd8ca6711bd4f3f8b74d88a697b50f9.r2.dev/2026-11-19-MyKVM-15/mykvm-hanja-key.png)

예전 HHKB는 왼쪽 Control(`1D`, 확장 아님)이 나갔다. 한국어 배열도 이건 평범한 왼쪽 Ctrl로 읽어서 문제가 없었다. Realforce는 맥 설정 때문에 자주 쓰는 자리가 오른쪽 Control이 되어 문제가 생겼다.

---

## 오른쪽 Control을 왼쪽 Ctrl로

고치는 방법은 단순하다. 맥 오른쪽 Control(`0x3E`)을 윈도우에는 왼쪽 Ctrl(`1D`, 확장 없음)로 보낸다.

```swift
// KeyMap.swift (KVMCore)
public static func winKey(forMacKeyCode code: UInt16) -> WinKey? {
    // 한국어 윈도우 배열은 오른쪽 Ctrl(E0 1D)을 한자 키로 읽어서 Ctrl+C가 "한자 + c"가 된다.
    // 맥 오른쪽 Control(Realforce의 Caps Lock 자리를 바꾼 것 등)은 왼쪽 Ctrl로 넣는다. 반대 방향 표는 그대로 둔다.
    if code == rightControlKeyCode { return WinKey(sc: plain[leftControlKeyCode]!, ext: false, vk: nil) }
    if let sc = plain[code] { return WinKey(sc: sc, ext: false, vk: nil) }
    if let sc = extended[code] { return WinKey(sc: sc, ext: true, vk: nil) }
    return nil
}
```

`winKey` 맨 앞에서 `0x3E`를 가로채 왼쪽 Control(`0x3B`)이 쓰는 스캔 코드를 확장 표시 없이 돌려준다. 이 함수는 맥 키코드를 윈도우 키로 바꾸는 방향이다. 반대 방향(윈도우 키보드로 맥을 조작할 때의 표)은 그대로 둬서, 윈도우 오른쪽 Ctrl은 맥 오른쪽 Control로 남는다. 한/영 전환(Control+Space)도 같은 함수를 거쳐서, Control을 잠깐 뗐다 다시 누르는 키가 이제 왼쪽 Ctrl로 나간다.

테스트에는 두 가지를 넣었다. 오른쪽 Control 누름과 c가 각각 `1D`, `2E`로 나가고 반대 방향 표가 그대로인지 보는 것, 그리고 오른쪽 Control이 눌린 채 Space를 누르면 한/영 키가 나가는지 보는 것이다. Swift 테스트는 120개에서 122개가 됐다.

## 다음 편 예고

이 고침은 한자 키 문제만 피한다. 정말 하고 싶었던 건 윈도우에서는 키캡에 적힌 대로 쓰는 것이다. 맥이 바꾼 결과 위에 대응표를 얹는 방법도 생각해 봤지만, 맥이 Caps Lock을 켜짐과 꺼짐으로만 알려 줘서 맥에서 Caps가 된 왼쪽 Ctrl을 누른 채 다른 키를 쓸 수 없다. 그래서 수정 키 변경이 일어나기 전의 원래 HID 신호를 읽기로 했다. 16편에서 이어진다.
