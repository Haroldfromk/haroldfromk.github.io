16편까지 쓰고 나니 두 가지가 거슬렸다. 하나는 맥에서 윈도우로 넘어갈 때 커서가 바로 넘어가지 않고 맥에 붙은 16MR70 가운데에 나타나는 것이었다(버그 1). 다른 하나는 윈도우에서 맥으로 돌아올 때 경계에서 맥 커서가 잠깐 깜빡이며 다시 윈도우로 튀는 것이었다(버그 2). 둘 다 원인은 같았다. 프로그램이 커서를 옮기면 macOS가 그 거리를 다음 마우스 이벤트에 슬쩍 섞어 보낸다.

## 숨겨서 세워 둔 맥 커서

윈도우를 조작하는 동안 맥 커서는 숨기고 16MR70 가운데인 (2312,500)에 세워 둔다(parking). 맥 화면 끝에 닿은 채로 두면 커서가 더 못 움직여서 마우스 움직임(delta)이 막히기 때문이다(3편의 이벤트 탭이 받는 값이 그 delta다). 윈도우에서 맥으로 돌아올 때는 넘어간 경계 자리로 커서를 옮긴다. 그러니 맥 ↔ 윈도우를 오갈 때마다 MyKVM이 맥 커서를 한 번씩 순간이동시킨다.

---

### 커서 워프란?

사용자가 마우스를 움직이지 않았는데 프로그램이 커서를 다른 자리로 순간이동시키는 것이다. 이 글에서는 워프라고 부른다. 텔레포트하듯 한 번에 가니, 워프한 만큼의 거리가 한꺼번에 움직인 셈이다. 문제는 macOS가 이 거리를 "움직인 양"에 얹어 버리는 데 있다. 아래에서 어떻게 얹는지 본다.

```swift
// CursorControl.swift (MyKVMMac), 지금 코드
static func warp(to point: Point) {
    let cursor = CGEvent(source: nil)?.location
    DiagnosticLog.write("warp to (\(Int(point.x)),\(Int(point.y))) event=\(warpDelta.lastLocation.map { "(\(Int($0.x)),\(Int($0.y)))" } ?? "none") cursor=\(cursor.map { "(\(Int($0.x)),\(Int($0.y)))" } ?? "none")")
    warpDelta.warped(to: point, at: ProcessInfo.processInfo.systemUptime)
    CGWarpMouseCursorPosition(CGPoint(x: point.x, y: point.y))
    // 워프 직후 0.25초 동안 마우스 입력이 막히는 것을 풀어 준다
    CGAssociateMouseAndMouseCursorPosition(1)
}
```

#### CGWarpMouseCursorPosition으로 커서 옮기기

1. [`CGWarpMouseCursorPosition`](https://developer.apple.com/documentation/coregraphics/cgwarpmousecursorposition%28%5F:%29){:target="_blank"}은 커서를 화면 좌표 한 점으로 옮긴다. 마우스를 실제로 움직인 것이 아니라서, 이 함수를 부르면 macOS는 한동안 마우스 입력을 커서에 연결하지 않는다.
2. [`CGAssociateMouseAndMouseCursorPosition(1)`](https://developer.apple.com/documentation/coregraphics/cgassociatemouseandmousecursorposition%28%5F:%29){:target="_blank"}은 마우스와 커서를 다시 연결한다. 워프 직후에는 0.25초쯤 입력이 막히는데, 이렇게 부르면 바로 풀린다.
3. [`CGEvent(source: nil)`](https://developer.apple.com/documentation/coregraphics/cgevent/init%28source:%29){:target="_blank"}는 빈 이벤트를 만든다. 그 [`location`](https://developer.apple.com/documentation/coregraphics/cgevent/location){:target="_blank"}에는 만든 순간의 커서 위치가 들어 있어서, 지금 커서가 어디 있는지 묻는 데 쓴다. 위 코드에서는 진단 기록에 남기려고 불렀다.
4. [`ProcessInfo.systemUptime`](https://developer.apple.com/documentation/foundation/processinfo/systemuptime){:target="_blank"}은 13편에서 본 것처럼 맥을 켠 뒤 흐른 초다. 워프한 시각을 적어 둘 때 쓴다.

### 마우스 이벤트의 delta와 location이란?

마우스가 움직이면 macOS는 이벤트를 하나 만든다. 그 이벤트에는 두 가지 값이 붙는다. delta는 이번에 움직인 양이고(오른쪽으로 3, 아래로 1), location은 그 이벤트에 붙은 위치다. 지도 앱의 "이번에 3걸음 걸었다"와 "지금 여기 있다"의 차이다.

보통은 location이 곧 커서 위치다. 그런데 3편의 이벤트 탭이 보는 HID 단계(손으로 한 입력이 막 들어오는 가장 앞쪽)에서는 다르다. 이 단계의 location은 워프를 반영하지 않고 혼자 흘러간다. 이 점이 버그 2의 원인이었다.

```swift
// EventTap.swift (MyKVMMac)
case .mouseMoved, .leftMouseDragged, .rightMouseDragged, .otherMouseDragged:
    // HID 단계 이벤트에 붙은 위치(event.location)는 실제 커서 위치가 아니다. 워프가 반영되지 않고 혼자 흘러간다.
    let here = CGEvent(source: nil).map { Point(x: $0.location.x, y: $0.location.y) } ?? Point(x: event.location.x, y: event.location.y)
    let delta = CursorControl.movement(Vector(dx: Double(event.getIntegerValueField(.mouseEventDeltaX)),
                                              dy: Double(event.getIntegerValueField(.mouseEventDeltaY))),
                                       location: Point(x: event.location.x, y: event.location.y))
```

#### getIntegerValueField로 움직인 양 읽기

[`getIntegerValueField(_:)`](https://developer.apple.com/documentation/coregraphics/cgevent/getintegervaluefield%28%5F:%29){:target="_blank"}는 이벤트에서 정수 값 하나를 꺼낸다. 어떤 값인지는 인자로 고르고, [`.mouseEventDeltaX`](https://developer.apple.com/documentation/coregraphics/cgeventfield/mouseeventdeltax){:target="_blank"}는 이번에 가로로 움직인 양이다(세로는 `.mouseEventDeltaY`). 커서 위치는 위의 `CGEvent(source: nil)`로 묻고, 움직인 양만 이벤트 값을 쓴다. `CursorControl.movement`는 아래에서 만들 워프 거리 빼기다.

## 16MR 가운데에서 멈춘 커서

처음 코드는 간단했다. 워프할 때마다 `warpCount`를 올리고, 이벤트 탭이 워프 직후 첫 이벤트를 알아보면 그 delta를 0으로 버렸다. 앞서 실기기에서 `1480,-605` 같은 큰 값이 한 번 들어온 걸 보고 만든 것이었다.

```swift
// EventTap.swift (MyKVMMac), 0a8febc 이전
if CursorControl.warpCount != seenWarpCount {
    // 워프 직후 첫 이벤트의 움직인 값에는 옛 자리까지의 거리가 섞여 온다(실기기에서 1480, -605 같은 값). 버린다.
    seenWarpCount = CursorControl.warpCount
    delta = Vector(dx: 0, dy: 0)
}
```

맥 (-14,818)에서 윈도우로 넘어가며 (2312,500)으로 워프했을 때의 기록이다.

```
00:25:09.563 mode -> windows by move ... reported=(-14.28,818.48) delta=(-39,17)
00:25:09.564 first windows move delta=(0.0,0.0)          ← 첫 이벤트는 버림
00:25:09.567 mode -> mac by move ... delta=(2266.0,-314.0) actions=[... "warp(2251.71875,504.484375)"]
```

워프 거리는 (2312+14, 500-818), 즉 약 (2326,-318)이다. 이 거리가 첫째 이벤트가 아니라 둘째 이벤트의 delta(2266,-314)에 섞여 왔다. 첫째 이벤트는 워프 전에 이미 줄 서 있던 것(워프하기 전에 macOS가 앱에 넘기려고 이미 쌓아 둔 이벤트)이라 워프와 관계없는 값이었다. 그림의 (-3,1)은 테스트에 쓴 예시 값이다(실제 기록의 첫째는 옛 코드가 0으로 버린 뒤라 0이다). 첫째만 버렸으니 둘째의 큰 delta가 그대로 통과했고, 그 값이 "맥으로 돌아간다"로 읽혀서 커서가 16MR70 가운데 근처인 (2251,504)로 워프했다.

## 거리를 기억했다가 한 번만 빼기

"첫 이벤트를 버린다"는 틀렸다. 워프가 어느 이벤트에 섞여 올지 모르니 이벤트 순서에 기대지 않고 값으로 알아봐야 한다. 그래서 `WarpDeltaFilter`를 만들었다. 워프할 때 거리와 시간을 적어 두고, 0.5초 안에 오는 이벤트 중 delta가 그 거리와 가까운 것에서 그 거리를 한 번만 뺀다. 첫째든 둘째든 상관없다.

```swift
// WarpDelta.swift (KVMCore)
public mutating func warped(from: Point, to: Point, at time: Double) {
    pending.append((Vector(dx: to.x - from.x, dy: to.y - from.y), time))
}

public mutating func filter(_ delta: Vector, at time: Double) -> Vector {
    pending.removeAll { time - $0.time > window }
    // 남은 값이 워프 거리의 절반보다 작으면 그 워프가 섞인 이벤트로 본다
    guard let index = pending.firstIndex(where: { length(minus(delta, $0.jump)) < length($0.jump) / 2 }) else { return delta }
    let jump = pending.remove(at: index).jump
    return minus(delta, jump)
}

private func minus(_ a: Vector, _ b: Vector) -> Vector { Vector(dx: a.dx - b.dx, dy: a.dy - b.dy) }
private func length(_ v: Vector) -> Double { (v.dx * v.dx + v.dy * v.dy).squareRoot() }
```

#### removeAll과 firstIndex로 워프 거리 찾아 빼기

1. `pending`은 아직 어느 이벤트에도 섞여 오지 않은 워프 거리 목록이다. [`removeAll(where:)`](https://developer.apple.com/documentation/swift/rangereplaceablecollection/removeall%28where:%29){:target="_blank"}는 조건에 맞는 원소를 모두 지운다. 적어 둔 지 0.5초가 지난 거리는 이미 지나간 일이라 버린다.
2. [`firstIndex(where:)`](https://developer.apple.com/documentation/swift/array/firstindex%28where:%29){:target="_blank"}는 조건에 맞는 첫 원소의 위치를 돌려준다. 없으면 nil이라 `guard`에서 이벤트를 그대로 돌려준다.
3. 조건은 "이벤트 delta에서 그 거리를 뺀 값의 길이가 거리 길이의 절반보다 작다"이다. 길이는 [`squareRoot()`](https://developer.apple.com/documentation/swift/double/squareroot%28%29){:target="_blank"}로 구한 피타고라스 거리다.
4. [`remove(at:)`](https://developer.apple.com/documentation/swift/array/remove%28at:%29){:target="_blank"}는 그 위치의 원소를 목록에서 빼고 돌려준다. 이렇게 꺼내 쓰니 같은 거리는 한 번만 빠진다.

절반 기준은 이런 뜻이다. 사용자가 실제로 움직인 양은 수십 px이고 워프 거리는 수천 px이라 둘은 차이가 크다. 그러니 이벤트에서 워프 거리를 뺐을 때 남은 값이 거리의 절반보다 작으면, 이 이벤트에 워프가 섞인 것이 맞다. 아무 상관 없는 이벤트(예를 들어 위의 (-3,1))는 거리를 빼면 오히려 더 커져서 걸러진다.

실기기 기록의 값을 그대로 테스트로 만들었다.

```swift
// WarpDeltaTests.swift (KVMCoreTests)
@Test func jumpInSecondEventIsRemoved() {
    var f = WarpDeltaFilter()
    f.warped(from: Point(x: -14, y: 818), to: Point(x: 2312, y: 500), at: 1.0)
    #expect(f.filter(Vector(dx: -3, dy: 1), at: 1.001) == Vector(dx: -3, dy: 1))
    #expect(f.filter(Vector(dx: 2266, dy: -314), at: 1.004) == Vector(dx: -60, dy: 4))
}

@Test func jumpInFirstEventIsRemoved() {
    var f = WarpDeltaFilter()
    f.warped(from: Point(x: -14, y: 818), to: Point(x: 2312, y: 500), at: 1.0)
    #expect(f.filter(Vector(dx: 2306, dy: -318), at: 1.001) == Vector(dx: -20, dy: 0))
    #expect(f.filter(Vector(dx: 5, dy: 0), at: 1.01) == Vector(dx: 5, dy: 0))
}
```

둘째에 섞여 와도, 첫째에 섞여 와도 빠진다. 두 번째 이벤트 (5,0)은 이미 빠진 뒤라 그대로 통과한다.

## 돌아올 때 경계에서 깜빡인 커서

1차 수정 뒤 맥에서 윈도우로 넘어가는 것은 부드러워졌다. 그런데 윈도우에서 맥으로 돌아오는 쪽이 부자연스러웠다. 경계에서 맥 커서가 잠깐 나타났다가 다시 윈도우로 가 버렸다.

```
00:32:34.427 mode -> mac by move ... actions=[... "warp(2.515625,404.046875)"]
00:32:34.442 mode -> windows by move prev=(2.0,404.0) reported=(-320.5,420.9) delta=(-322.515625,16.953125)
```

맥으로 돌아와 (2.5,404)로 워프하고 15ms 만에 다시 윈도우로 튀었다. 워프 거리를 뺐는데도 delta가 (-322,17)이나 남았다.

원인은 윈도우 모드의 커서와 이벤트 위치가 갈라져 있다는 것이었다. 커서는 (2312,500)에 서 있지만, 이벤트에 붙은 location은 MyKVM이 삼킨 움직임만큼 계속 흘러간다(위에서 본 HID 단계의 성질). 그런데 macOS는 워프 거리를 이 이벤트 위치에서 잰다. 1차 수정은 (2,404)-(2312,500) = (-2310,-96)을 적어 두었다. 그런데 macOS가 실제로 섞어 보낸 값은 (2,404)-(2634,483) = (-2632,-79)였다. 빼고 남은 (-322,17)의 길이가 절반 기준(약 1155)보다 작아서 이 이벤트를 워프가 섞인 이벤트로 보고 엉뚱한 거리를 뺐고, 차이 (-322,17)이 그대로 남았다.

이벤트 위치는 남은 값으로 거꾸로 계산했다. 세워 둔 자리 (2312,500)에서 남은 값 (-322,17)을 빼면 (2634,483)이다. 이렇게 구한 이벤트 위치가 늘 세워 둔 자리의 오른쪽이었다. (2634,483), (2690,398), (3011,435)이다.

## 마지막 이벤트 위치에서 재기

이벤트마다 location을 기억해 두고(`lastLocation`) 워프 거리를 거기서 재도록 고쳤다. 이벤트를 아직 한 번도 못 봤으면 기억할 위치가 없으니 적지 않는다.

```swift
// WarpDelta.swift (KVMCore)
public mutating func warped(to: Point, at time: Double) {
    guard let from = lastLocation else { return }
    warped(from: from, to: to, at: time)
}

/// 이벤트마다 부른다. 워프 거리를 빼고, 이벤트 위치를 기억해 둔다.
public mutating func filter(_ delta: Vector, location: Point, at time: Double) -> Vector {
    lastLocation = location
    return filter(delta, at: time)
}
```

`CursorControl.warp(to:)`는 이제 커서 자리를 묻는 대신 이 `warped(to:at:)`로 거리를 적어 둔다. 아래 테스트는 00:32:34 기록에서 거꾸로 계산한 값으로 만들었다.

```swift
// WarpDeltaTests.swift (KVMCoreTests)
@Test func jumpIsMeasuredFromTheLastEventLocation() {
    var f = WarpDeltaFilter()
    _ = f.filter(Vector(dx: 6, dy: 0), location: Point(x: 2634, y: 483), at: 1.0)
    f.warped(to: Point(x: 2, y: 404), at: 1.001)
    #expect(f.filter(Vector(dx: 4, dy: 0), location: Point(x: 2640, y: 483), at: 1.002) == Vector(dx: 4, dy: 0))
    #expect(f.filter(Vector(dx: -2632, dy: -79), location: Point(x: 2, y: 404), at: 1.005) == Vector(dx: 0, dy: 0))
}
```

워프할 때마다 진단 기록에 이벤트 위치(event)와 커서 위치(cursor)를 같이 남기게 했다. 고친 뒤 실기기 기록이다.

```
00:37:16.186 warp to (11,447) event=(2330,280) cursor=(2312,500)
00:37:17.419 warp to (115,430) event=(2442,458) cursor=(2312,500)
00:37:18.889 warp to (32,448) event=(2415,499) cursor=(2312,500)
```

커서는 세워 둔 자리 그대로인데 이벤트 위치는 늘 다른 곳이다. 돌아온 뒤 15ms 만에 윈도우로 튀는 일도 없어졌다. 써 보니 이제 자연스럽게 넘어간다.

## 정리

워프는 거리가 사라지는 일이 아니라, 거리가 다음 이벤트 어딘가에 숨어서 따라오는 일이었다. "첫 이벤트만 버리기"는 둘째에 오는 경우를 못 막았고, "커서 자리에서 거리 재기"는 윈도우 모드에서 이벤트 위치와 커서가 갈라지는 걸 몰랐다. 지금은 워프 거리를 이벤트 위치에서 재서 적어 두고, 절반 기준에 맞는 이벤트에서 0.5초 안에 한 번만 뺀다. 빠르게 두 번 워프해도 각각 뺀다. 테스트는 Swift 159개에서 166개로 늘었다(`WarpDeltaTests` 7개).
