# 스펙: 블로그 메모 + AI 결함 기록부

작성일: 2026-11-19

## 목적과 전체 흐름

바이브코딩 끝에 쓰는 블로그 메모(`~/Documents/Workspace/blog-notes/<앱>/*.md`)가 이미 인계 노트 역할을 한다. 새 스킬을 만들지 않고, 메모에 "AI 결함" 항목 하나를 더해서 결함 기록부로 이어지게 한다.

```
바이브코딩 세션 --(세션 끝)--> 블로그 메모 --(새 세션에서 읽음)--> 블로그 세션 (blog-post 스킬)
                                    |
                                    +--(AI 결함이 있을 때)--> AI 결함 기록부 (ai-defect-log/entries/)
                                                                   |
                                                                   +--(트러블슈팅 글 쓸 때 참고)--> 블로그 세션
```

블로그 메모는 지금처럼 blog-post 스킬이 읽고, AI 결함이 있었던 메모만 결함 기록부에 항목을 남긴다. 결함 기록부는 나중에 트러블슈팅 글을 쓸 때 다시 블로그로 돌아온다.

## 블로그 메모에 추가할 것

기존 메모 양식(상태, 커밋, 한 일, 겪은 문제, 버린 시도, 정한 것, 실측값, 스크린샷, 설명할 개념 후보)은 그대로 두고, "버린 시도" 다음에 항목 하나만 더한다.

```markdown
- AI 결함:
  - [분류] 현상. 원인: ... 대책: ... (없으면 "없음")
```

### "겪은 문제"와 "AI 결함"의 구분

둘을 섞으면 기록부가 기술 메모 모음이 된다.

| 항목 | 담는 것 | 예 |
| --- | --- | --- |
| 겪은 문제 | 플랫폼, API, 도구의 제약이나 동작 때문에 생긴 문제 | `switch must be exhaustive` 컴파일 오류, Swift Testing 함수 이름에 괄호가 필요한 것 |
| AI 결함 | AI가 만든 코드, 문장, 그림이 틀려서 리뷰나 실행, 사용자 확인에서 잡힌 것 | Saju 메모의 "많은 편" 카드 조건 `maxCount >= 2`가 늘 참이었던 것, 앱 정보 문장이 실제 코드와 다른 인상을 준 것 |

### 고칠 위치

블로그 메모를 쓰는 규칙이 어디에 있는지는 이 스펙에서 정하지 않는다. `~/.claude/`와 각 앱 레포의 CLAUDE.md, 스킬에서 "블로그 메모"를 찾아서 그 양식에 항목을 더한다. 여러 곳에 있으면 고치기 전에 목록을 보여준다.

## AI 결함 기록부 레포

결함 기록부는 별도 레포로 두고, "AI 협업 트러블슈팅" 글을 쓸 때 이 레포를 참고한다. 양식은 정비 품질의 "현상, 원인, 대책, 재발 여부" 틀을 따른다.

- 레포 이름(가정): `ai-defect-log`, 위치는 `~/Documents/Workspace/ai-defect-log`
- 공개 여부: 포트폴리오로 보여줄 수 있게 공개. 그래서 항목에 키, 토큰, 개인 경로, 지인 개인 기록 같은 민감 정보를 적지 않는다.
- 커밋: 스킬이나 Claude는 항목 파일만 만들고, 커밋은 사용자가 확인한 뒤 직접 한다.

### 구조

```
ai-defect-log/
├── README.md            # 목적, 양식, 분류 설명
├── INDEX.md             # 전체 목록 표 (생성물, 직접 수정 금지)
├── entries/
│   └── D-001-svg-cjk-font.md
└── scripts/
    └── build_index.py   # entries/를 읽어 INDEX.md 생성
```

### 항목 양식

분류는 렌더링, 코드 로직, 코드 스타일, 글쓰기 규칙, 사실 오류, 검증 누락으로 시작하고 필요하면 늘린다.

```markdown
---
id: D-001
date: 2026-11-19
project: blog
category: 렌더링
status: 대책 완료   # 조사 중 / 대책 완료 / 재발
source: blog-notes/앱이름/파일명.md   # 메모에서 왔으면
---

## 현상
AI가 만든 SVG 다이어그램의 한글이 PNG에서 네모 칸으로 깨짐

## 원인
일부 text 요소의 font-family가 monospace만 있어 CJK 글리프가 없음

## 대책
- 종류: 규칙 + 스크립트
- 위치: blog-post 스킬 references/diagrams.md, scripts/check_svg.py

## 재발 여부
없음
```

## 연결 방식

블로그 메모를 쓰는 그 단계에서 기록부 항목까지 만든다. 따로 기록하는 단계를 두지 않는다.

1. 블로그 메모를 쓸 때 "AI 결함" 항목을 채운다. 없으면 "없음".
2. "없음"이 아니면, 결함마다 `ai-defect-log/entries/`에 다음 번호(D-0NN)로 항목 파일을 만든다. `source`에는 그 메모 경로를 적는다.
3. `scripts/build_index.py`를 실행해서 INDEX.md를 다시 만든다.
4. 만든 항목 번호와 제목을 보고하고, 커밋은 하지 않는다.

같은 결함이 다시 나오면 새 항목을 만들지 않고, 기존 항목의 status를 "재발"로 바꾸고 "재발 여부"에 날짜와 메모 경로를 더한다. 재발은 대책이 듣지 않았다는 뜻이라, 기록부에서 가장 중요한 신호다.

## 초기 항목

### 기존 블로그 메모에서 찾을 항목

`blog-notes/`에 메모가 30개 넘게 있고, 그중에는 AI가 만든 코드가 리뷰에서 걸린 기록도 있다. 예를 들어 Saju 전체 리뷰 메모의 "많은 편" 카드 조건이 늘 참이던 것이다.

1. 모든 메모를 읽고 위의 "AI 결함" 정의에 맞는 후보를 메모 경로와 함께 목록으로 보여준다.
2. 사용자가 고른 것만 항목으로 만든다. 자동으로 만들지 않는다.
3. 지인이 제보한 기록처럼 다른 사람의 개인 정보가 담긴 메모는 원인과 대책만 적고 원본 자료는 옮기지 않는다.

## 검증 방법과 범위 밖

다음 바이브코딩 세션 하나로 메모부터 기록부 항목까지 한 바퀴 돌려본다.

- [ ] `ai-defect-log` 레포를 만들고 D-001부터 D-009를 넣는다
- [ ] `build_index.py`로 INDEX.md가 만들어지는지 확인한다
- [ ] 기존 메모에서 찾은 후보 목록을 받아서 고른 것만 항목으로 넣는다
- [ ] 다음 바이브코딩 세션에서 쓴 블로그 메모에 "AI 결함" 항목이 들어가는지 확인한다
- [ ] AI 결함이 있었던 세션이면 `entries/`에 항목이 생기고 커밋은 되지 않았는지 확인한다

범위 밖

- blog-post 스킬 보강은 `_specs/blog-skill.md`에서 다룬다.
- 기존 메모 내용은 고치지 않는다. 읽기만 한다.
- 결함 기록부를 바탕으로 한 "AI 협업 트러블슈팅" 글은 항목이 쌓인 뒤 따로 쓴다.
